# webtransport-chat

A chat room over WebTransport (draft-ietf-webtrans-http3, experimental in 0.3.0): a Ktor server on Kuicksilver's engine
and a client in common Kotlin on Kuicksilver's Ktor client engine. Like `samples/realtime-telemetry`, it is a separate
Gradle build that depends on `io.kuicksilver:*` by coordinates (the composite build in `settings.gradle.kts` substitutes
this repository's modules; with published artifacts you would drop `includeBuild`), and it verifies every dependency
against the repository's `gradle/verification-metadata.xml`. It is not published.

Each member is one WebTransport session on `/chat`, and the sample uses both of its halves for what each is good at:

- **messages and membership on a bidirectional stream** the client opens first: reliable and ordered, text lines
  (`HELLO <name>` → `WELCOME <name> <members>`, then `MSG`, `JOIN`, `LEAVE`). The server writes every line under one lock,
  so all members see the room in the same order, the sender's own messages included;
- **typing indicators as datagrams** (`trySendDatagram`, never waited for): one that is lost does not matter, the next
  comes a moment later, and none waits behind a long message on a stream. The server relays at most one per 250 ms per
  member, so a flood is not multiplied by the room;
- **refusals as session close codes**: a taken name, a full room (25 members), a missing `HELLO` or a line over 1024
  bytes closes the session with a code and a reason (`WT_CLOSE_SESSION`), the one message a client is sure to get;
- **untrusted text stays text**: control characters in a message become `?`, on the server and again on the client, so
  no member can send terminal escape sequences to another's console;
- **a slow reader is dropped, not waited for**: each member has a queue of 256 lines; when its stream's flow control
  holds the server's writer and the queue fills, that member's session is closed and the room goes on;
- **graceful stop**: `server.stop(...)` sends GOAWAY, and every member sees `ChatEvent.ServerDraining`
  (`WebTransportSession.drainRequested`) before its session ends.

| File | What it shows |
|---|---|
| `src/commonMain/.../ChatProtocol.kt` | the lines, the datagram, the close codes, the limits |
| `src/commonMain/.../ChatServer.kt` | `embeddedServer(Kuicksilver) { tlsConnector(...); webTransport = true }`, the `webTransport(path, protocols)` route, `acceptBidi`, `receiveDatagram`, `close(code, reason)` |
| `src/commonMain/.../ChatClient.kt` | `HttpClient.webTransport(url, protocols)`, `openBidi`, `trySendDatagram`, `drainRequested`, `closed` |
| `src/commonMain/.../ChatTls.kt`, `SampleCa.kt` | the client's trust: the sample CA from PEM text, and nothing secret |
| `src/jvmMain/.../ServerIdentity.kt`, `SampleServerPem.kt` | the server's identity from PEM files, the public test identity as the loopback fallback |
| `src/jvmMain/.../Main.kt` | a command line server and console client |
| `src/jvmTest/.../ChatTest.kt` | the server and clients in one JVM over real UDP on loopback: the room, typing, leave, a taken name, a full room, bad lines, a slow reader, a graceful stop |

The client and the server are in `commonMain`: the build compiles them for the JVM, macOS and iOS (`iosArm64`,
`iosSimulatorArm64`; CI and the local gate compile macOS and the simulator on every run), so an iOS or Android app
takes `ChatClient` as it is (an Android app adds an `androidTarget`, or copies the file; the engine is the same). Only
the JVM runs the tests and the command line.

**Everything in `commonMain` ships inside every client build**, so no server key lives there: `chatServer(identity)`
takes the identity from its caller, and the JVM server loads it from PEM files (`ServerIdentity.kt`). The sample's
own server certificate and key (`SampleServerPem.kt`, generated by `certs/gen.sh` with the CA) are in `jvmMain`, so no
common-code, iOS or macOS build carries them; the JVM console jar holds both sides, server and client.

## Build and test

From the repository root:

```
./gradlew --max-workers=2 -p samples/webtransport-chat jvmTest
```

Run it by hand (a terminal for the server, one per member):

```
./gradlew -p samples/webtransport-chat jvmRun --args="server 4433"   # 127.0.0.1; the network: "server 4433 0.0.0.0 chain.pem key.pem"
./gradlew -q -p samples/webtransport-chat jvmRun --console=plain --args="client 127.0.0.1 4433 alice"
./gradlew -q -p samples/webtransport-chat jvmRun --console=plain --args="client 127.0.0.1 4433 bob"
```

Every line typed in a client is a message; `/typing` sends a typing indicator (the others print `* alice is typing...`),
`/quit` leaves. Stop the server with Ctrl-C and the clients print `* the server is shutting down`.

The server listens on 127.0.0.1 unless a host is given. Its identity comes from PEM files: `server <port> <host>
<chain.pem> <key.pem>`, or `CHAT_TLS_CHAIN` and `CHAT_TLS_KEY` (an unencrypted PKCS#8 key). Without them it uses the
sample's public test identity, and only on loopback: on any other host it refuses to start, since anyone has that key
and could impersonate the server to every client that trusts the sample CA. For a server on the network, issue its
certificate from a CA of your own and give the clients that CA: `client <host> <port> <name> <ca.pem>`, or
`CHAT_TLS_CA=<ca.pem>` (`ChatTls.clientTrust(caPem)` in an app); without it a client trusts the sample CA only.

## What to look at

- `ChatServer.kt`: the whole server is `chatServer()` (one `tlsConnector`, which serves HTTP/1.1 on TCP and HTTP/3 on
  UDP on the same port) and a `webTransport` route. The route checks the `origin` field with `sameHostOrigin` by
  default: clients that are no browser send none and are admitted.
- `ChatClient.kt`: `join` is one `webTransport(url)` call and one stream; `events` merges the stream's lines with the
  datagrams. Sessions share the client engine's pooled HTTP/3 connection to the server (up to 4 per connection with
  WebTransport flow control; `ChatTest` runs several members on one `HttpClient`).
- `ChatTest.negative_slowReaderIsDropped`: a member that stops reading is closed with code `0x13` once its flow-control
  credit (64 KiB in the test, set by its client's `webTransportInitialMaxData`), the server's send buffer for its
  session (its share of `QuicConfig.maxSendBuffer`) and its queue of 256 lines are full: about 1.3 MiB of messages in
  the test. The speaker never waits for it.
- There is no message rate limit per member: a member sends as fast as its stream and the others' queues take it, and a
  reader that falls behind is dropped. A public room would also bound the messages per second (`readLines`).

## Limits worth knowing

- WebTransport is `@ExperimentalKuicksilverApi` in 0.3.0 (the build opts in for the whole module), and the protocol is
  still a draft: two Kuicksilver endpoints speak draft-17 ([HTTP/3 guide](../../docs/guide/http3.md#webtransport-experimental)).
- **Browsers**: the server speaks the drafts Chrome, Firefox and Safari speak, but this sample ships no web page, and
  a browser needs a certificate it trusts: for a development certificate, one valid for at most 14 days pinned with
  `serverCertificateHashes`, as `ChromeWebTransportTest` and `tools/interop/wt-firefox-manual.sh` do
  ([Ktor guide, WebTransport over HTTP/3](../../docs/guide/ktor.md#webtransport-over-http3-experimental)). A browser
  always sends `origin`: serve the page from the chat server's own origin, or pass a `checkOrigin` that admits the page's.
- The certificates in `SampleCa.kt` and `SampleServerPem.kt` are public test material; never ship them.
