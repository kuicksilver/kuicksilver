# Kuicksilver — threat model

Date: 2026-10-02; as of 0.2.x (2026-10-21). Status: current document, updated with each change it describes; revised after a cross-check against RFC 9000 §21, RFC 9001/9002/9114/9204/9308/8899 and the CVEs of quinn, quic-go, quiche, ngtcp2, msquic, s2n-quic, OpenSSL, Netty, picoquic, quicly. Related: docs/architecture.md, the resource limits in docs/guide/quic.md ("Glitch protection", "Admission and endpoint limits").

## 1. Assets

| Asset | Where it lives | How it is protected |
|---|---|---|
| TLS secrets and packet protection keys | only native `ksl` memory (`ksl_key`, `SSL`, client sessions for resumption — `ksl_session`) | not copied into Kotlin (the TCP session cache holds a `ksl_session` handle, not `i2d_SSL_SESSION` bytes); `OPENSSL_cleanse` on free, intermediate JNI/cinterop buffers are wiped; JVM heap dump test |
| Identity private key | `ksl_pkey` / `ksl_ctx` (now: in native memory, Kotlin holds a handle; later: an external signer, out of process) | parsed once into OpenSSL (since ksl ABI 5), the imported `ByteArray`/`CharArray` and the JNI copy are wiped, freed with the last reference; JVM heap dump test; later — the key never leaves the store |
| Retry token key, stateless reset key, session ticket keys | only `ksl` (handles; HMAC/AEAD inside; ticket keys: a process-wide key ring and registered explicit sets in `ksl_tickets.c`, copied into each context) | generated by `ksl_rand` (ticket keys by `RAND_priv_bytes`), rotated on a schedule inside `ksl`; explicit ticket keys are copied in once and the caller's arrays zeroed; the reset key is separate from CID generation |
| Application plaintext in buffers | the `PacketBuffer` pool | is it wiped on return to the pool? — no (performance); buffers are not shared between connections |
| Server availability (CPU, memory, sockets) | `EndpointCore` | ceilings and `ConnectionAdmission`, §3.2 |
| Client privacy (linkability by CID, address) | `ConnectionIdRegistry` | CID change on migration |

## 2. Attackers

- **Network observer** (passive): sees datagrams.
- **Active network attacker (on-path / off-path)**: forges, delays, duplicates, replays packets; off-path knows addresses but does not see contents.
- **Malicious peer**: a valid connection that violates the protocol or exhausts resources.
- **Malicious server/proxy** (for the client): presents someone else's certificate.
- **Local attacker with access to process memory/a dump** (limited: JVM heap dump, crash report).
- **Malicious dependency/artifact** (supply chain).

Out of scope: OS/kernel compromise, hardware side-channel attacks on AEAD (we rely on OpenSSL), an attacker with root on the host.

## 3. Threats and mitigations

Format: threat → mitigation → verification (positive test / **negative control**).

### 3.1 Amplification

- **Threat:** an off-path attacker sends an Initial with the victim's forged address; the server answers with a large volume.
- **Mitigation:** an amplification limit of 3× the received bytes before address validation (RFC 9000 §8.1): **all** datagram bytes of this connection are counted, including dropped packets, each datagram exactly once (OpenSSL CVE-2026-35191); the limit is lifted only after real address validation; a client Initial ≥ 1200 bytes is mandatory, otherwise ignored; Version Negotiation is no longer than the incoming datagram; Retry when the threshold of incomplete handshakes is exceeded. An Initial with source port 0 is dropped without a reply (no socket listens on port 0, the kernel rejects the send — EINVAL — and such a forged datagram would cost the server a lost send; native-tls review, `EndpointCoreTest.initialFromSourcePortZeroDropped`); link-local IPv6 peers are not served by the accelerated transport (`ksl_udp` drops fe80::/10: the 20-byte address format does not carry a scope id).
- **Verification:** the simulator counts bytes before validation; **negative control**: a packet beyond 3× is not sent; an Initial < 1200 bytes is ignored.

### 3.2 Resource exhaustion

- **Threats:** Initial flood (CPU spent on TLS); thousands of half-open connections; more streams than the limit; an endless CRYPTO buffer; receive memory held by unassembled data; ACK flood; PATH_CHALLENGE flood; `NEW_CONNECTION_ID` beyond the limit.
- **Mitigations:** `ConnectionAdmission` (a limit on handshakes in flight → Retry/Drop), an Initial queue before `admit` with a ceiling, only cheap checks before `ksl` (≥ 1200 bytes, version, DCID ≥ 8); a keyed hash (SipHash) for choosing the loop and for the CID tables (§21.13; picoquic CVE-2025-24946); `maxConnectionsPerIp`, an optional `maxConnectionLifetime` (slowloris, §21.6); a glitch token bucket enabled by default (§21.9); Retry as proof of address under load; a CRYPTO ceiling of 64 KB per level out of order, the Initial stream ending at 64 KiB and the Handshake stream at 256 KiB, CRYPTO past the end of a level TLS has left a PROTOCOL_VIOLATION (RFC 9001 §4.1.3) and at most 256 KiB unread per level in `ksl`, counted in the handshake's buffer bytes for admission; `max_streams`; `active_connection_id_limit`; the reassembly range limits per stream (256) and per connection (4096; internal `QuicLimits.reassemblyRangesPerStream`/`reassemblyRangesPerConnection`, not configurable) with an O(log n) structure (§21.7; quinn CVE-2026-25800, OpenSSL CVE-2026-42772); CRYPTO: `offset+len` checked **before** allocating memory and a separate ceiling in 1-RTT (s2n GHSA-9q54, quiche CVE-2024-1765); refusal beyond `max_streams` before allocating memory (s2n GHSA-475v); metadata of ACK-only packets is not stored (OpenSSL CVE-2026-63075); a ceiling on qlog volume per connection and per `DirectoryQlogSink` (open traces, lifetime bytes); ceilings on the queues (datagrams, undecryptable packets, PATH_CHALLENGE, ACK ranges, early PRIORITY_UPDATE) — connection memory is bounded by the sum of explicit ceilings, there is no separate "budget"; at the endpoint — `ConnectionAdmission` with Retry/Drop at the limit of handshakes in flight; idle timeout.
- **Verification:** a **negative control** for every limit: exceeding it → close with the expected code, process memory does not grow (measured in the test).
- **Long-run verification:** the soak harness `kuicksilver-soak` (CONTRIBUTING.md, "Soak and churn") drives a server and clients on real UDP through transfers, aborts, idle timeouts, stateless resets, migrations, 0-RTT, refusals at a full accept queue and Ktor HTTP/1.1 and HTTP/3 for hours, and fails when RSS, heap, descriptors, `ksl` live objects or any library table grows after warm-up or does not return to its idle level. It found a native key leaked per stateless Initial CONNECTION_CLOSE (a peer could grow server memory within the stateless rate limits) and server connections kept until their idle timeout after a migrated client closed. Opt-in, not part of `check`; 2 h nightly before a prerelease, 24–72 h before a release.

Status (runtime review, 2026-10-08): a stream reset by the peer or stopped by us is retired, and the `MAX_STREAMS` credit is returned — otherwise after `maxBidiStreams` resets the peer was permanently stuck in STREAMS_BLOCKED (`api.StreamRetirementTest.*`); the queue of datagram send commands is bounded (≤ 2 × `datagramSendQueue` + 1, `api.DatagramApiTest.dropOldestFloodStaysBounded`); a qlog trace is not opened for an undecryptable (forgeable) Initial and is always closed, a sink failure (EMFILE) does not bring the endpoint down (`qlog.QlogRobustnessTest.*`); now the directory is created 0700 and refused when it is a symlink, not a directory, another user's, or group/world-writable without the sticky bit, each file is created with `O_CREAT|O_EXCL|O_NOFOLLOW` (JVM `CREATE_NEW` + `NOFOLLOW_LINKS`, Windows `CREATE_NEW` and no reparse-point directory) under `<odcid>_<role>_<random>.sqlog`, the ODCID must be hex, and the sink has an endpoint-wide (sink-wide) ceiling of open traces (256) and of bytes over its lifetime (1 GiB); qlog on a public server stays a disk-exhaustion surface within those ceilings (`qlog.DirectoryQlogSinkTest.negative_reusedOdcidDoesNotTruncateAnotherTrace`, `.negative_openTracesAreBoundedPerSink`, `.negative_totalBytesAreBoundedPerSink`, `.negative_nameThatIsNotHexIsRefused`; `PrivateFilesJvmTest.negative_plantedSymlinkIsNotFollowed`, `.negative_plantedFifoDoesNotBlock`, `.negative_existingFileIsNotTruncated`, `.negative_sharedOrLinkedDirectoryRefused`; `PrivateFilesAppleTest`/`PrivateFilesLinuxTest` the same on Native). Residue: the directory is checked by path before each file is created, so its parent must not be writable by another user either (who could swap the directory between the check and the create); datagrams forwarded between loops are processed in batches of 16 with `yield` (`runtime.LoopGroupTest.forwardedBurstDoesNotMonopoliseTheLoop`); an idle accelerated socket does not occupy a `Dispatchers.IO` thread (`KslReceiveSlicesTest`). Review h-quic (0.2.1): the runtime consumed a peer's RESET_STREAM itself, also for a stream still waiting for `acceptStream()`, so RESET_STREAM (+ STOP_SENDING) returned the `MAX_STREAMS` credit of streams the application never accepted while each waited in the accept queue (~33 KiB): 500 streams against a limit of 10. The reset of a queued stream is now consumed when `acceptStream()` hands it out, so unaccepted streams stay within the stream limits (as quic-go counts a reset stream completed only once the application read the error) (`runtime.UnacceptedStreamLimitTest.negative_resetBidiStreamsDoNotBypassTheLimitOfUnacceptedStreams`, `.negative_resetUniStreamsDoNotBypassTheLimitOfUnacceptedStreams`).

0.2.0 status (runtime, 2026-10-12): a socket that never runs dry (a flood of junk at line rate) no longer starves the loop's timers and the application's commands: the receive loop yields after 16 rounds or 2 ms (`runtime.WorkLimiter`, `runtime.ReceiveFairnessTest.timersFireUnderContinuousReceive`); the accept queue never holds more than `acceptQueue` connections (128 by default) — a client Initial arriving while it is full is refused statelessly with an Initial CONNECTION_CLOSE (CONNECTION_REFUSED) before any handshake state, under the stateless rate limits (`endpoint.AdmissionTest.initialWhileAcceptQueueFullIsRefusedStatelessly`, `.negative_refusalIsAmplificationLimited`, `runtime.LoopGroupTest.initialWhileTheSharedAcceptQueueIsFullIsRefusedStatelessly`; 2026-10-13), and a handshake completing above the limit is closed with CONNECTION_REFUSED (`api.EndpointLifecycleTest.acceptBacklogNeverExceedsAcceptQueue`), while admission counts only the connections waiting for `accept()`, so `acceptQueue` half-open handshakes from spoofed sources do not lock real clients out (`api.EndpointLifecycleTest.negative_spoofedInitialsDoNotLockOutAdmission`); a peer that keeps changing address leaves at most four path objects on the server (`api.MigrationApiTest.serverPathListStaysBoundedAcrossMigrations`); the loop makes no resolver call per datagram (`core.AddressClassNativeTest.ipBytesNeverResolvesHostnames`); datagrams a full socket refuses are counted (`ConnectionStats.datagramsDroppedSocket`).

Security review 2026-10-14 (a suspected cost): every QUIC session and every TCP server connection builds its own `SSL_CTX`. Measured with `tools/bench/ksl-ctx-bench.sh` (2000 iterations, OpenSSL 3.5.9; M-series Mac, and the same Mac's Docker `linux/arm64` manylinux2014 image with its 142-certificate bundle): a server context (QUIC, 0-RTT, ticket keys) costs 56–68 µs, a full QUIC handshake (both sides, P-256) 404–506 µs, so the per-session context adds about 13 % to a handshake a server already does only after the cheap checks and admission (§3.2 above): no amplification. A client context with `TrustConfig.Platform` through OpenSSL (Linux Native) parsed the system CA bundle each time, 3.6 ms per connection on both hosts, seven to nine handshakes' worth; it is now parsed once per process into a shared `X509_STORE` (`ksl_trust_cache.c`), which is reloaded for new contexts when `SSL_CERT_FILE`/`SSL_CERT_DIR` or any searched file or directory changes (path, size, mtime, inode) and is never modified (a context given explicit roots gets its own store first): 145 µs on macOS and 230 µs in Docker per context, the first, cold load included. Verification: C `trust_system_store_shared_and_reloaded_on_change` (two contexts share one store that verifies the server; explicit roots never land in it; a rewritten bundle is parsed again; a bundle that disappeared is reported, not served from the cache).

### 3.3 Forged Retry and tokens

- **Threat:** an attacker sends the client a forged Retry (DCID change, downgrade); or sends the server an Initial with someone else's or a reused token; amplification through NEW_TOKEN.
- **Mitigation:** the Retry Integrity Tag (RFC 9001 §5.8) is checked by the client; the client drops a second Retry, a Retry with an empty token, a Retry with SCID = the original DCID and any Retry after an accepted Initial (§17.2.5). The server token is AEAD under the endpoint key (the key lives in `ksl`) and contains the token type (Retry ≠ NEW_TOKEN, §8.1.1), the ODCID, **the Retry SCID** (0.2.0: an Initial that presents the token under another DCID is refused with `INVALID_TOKEN`, statelessly, RFC 9000 §8.1.3-§8.1.4), the client's address **and port**, and the time; lifetime 10 s; `original_destination_connection_id` and `retry_source_connection_id` are checked in the transport parameters. An Initial with an **invalid** Retry token → close with `INVALID_TOKEN`, no second Retry is sent (§8.1.2). In 0.2.x the server does not issue NEW_TOKEN (planned for 0.3.0) and the client does not store it. `ConnectionAdmission.admit` does not return `Retry` for an attempt whose address is already validated (quinn CVE-2024-45311); the default token handler never treats "no check" as success (Netty CVE-2026-44894).
- **Verification:** the vector of RFC 9001 appendix A.4; **negative controls**: a wrong tag → Retry dropped; a forged / expired / other-address token → `INVALID_TOKEN`; a token reused under another DCID → `INVALID_TOKEN` (`endpoint.RetryTest.negative_retryTokenReusedWithOtherDcid`); empty token, SCID = ODCID, Retry after Initial → dropped; CID mismatch in the TP → `TRANSPORT_PARAMETER_ERROR`.

### 3.4 Forged stateless reset and a reset oracle

- **Threat:** an off-path attacker closes someone else's connection with a forged stateless reset; the client accepts a reset from a third party; **the server itself** becomes an oracle and kills a live connection (RFC 9000 §21.11).
- **Mitigation:** token = HMAC(a **separate** endpoint key in `ksl`, CID) — unpredictable and not derivable from the CID in the header (Netty CVE-2026-50009); only the last 16 bytes of a packet are accepted when they match the token of a **used and not retired** CID (§10.3.1); constant-time comparison (MUST); a zero or empty token slot never matches (quicly CVE-2026-44434); the reply is smaller than the triggering packet and ≥ 21 bytes, its rate is limited (§10.3.3). With N loops on `SO_REUSEPORT` the kernel distributes by 4-tuple: after a NAT rebind a packet of a live connection may arrive at a loop without state — such a loop **does not send a reset**, the decision is made through a shared CID registry or after forwarding to the owner loop. The receiver of a reset goes into draining and gives the application a separate cause, `StatelessReset`.
- **Verification:** **negative controls**: a wrong token → ignored, the connection lives, `invalidResets++`; the token of a retired CID → ignored; a zero token → ignored; a packet of a live connection in another loop → no reset; constant time — code review and a branching test.

Pre-release status: with `loops > 1` each loop answers with a stateless reset only for CIDs with its own routing byte (`EndpointCore.ownerLoop`), a packet with another loop's routing byte is copied to the owner (`LoopGroup.forward`), the reset key is per loop. Verification: `StatelessResetTest.negative_resetNotFromOtherLoop` (core), `MultiLoopTest.forwardedDatagramReachesOwner` (runtime, Linux: traffic of a live connection directed to another loop → delivered to the owner, `statelessResets == 0` on all loops). Runtime review: the loops of a group start only after all of them are created (a datagram for another loop before start no longer brings the group down), the failure of one loop closes the whole group, the shared `accept` queue is closed only by the group — `runtime.LoopGroupTest.*` (in-memory sockets, all platforms).

### 3.5 Tracking by CID and migration

- **Threat:** an observer links the old and the new path by CID (deanonymisation on a network change); an attacker triggers a false migration with a forged source address.
- **Mitigation:** migration uses an unused CID and a new stateless reset token (RFC 9000 §9.5), and already the probe of the new path (and the reply to it) carries its own unused CID rather than the CID of the active path (`core.PathTest.probeUsesUnusedPeerCid`, core review); enough CIDs are requested from the peer in advance; passive migration requires PATH_CHALLENGE, while the path is not validated the 3× amplification limit applies and the old path stays; before validation only probing frames go to the new path; the exception is an unfinished handshake: the server follows the address of the client's last decrypted Handshake packet, and of an Initial packet only after ≥ 1 PTO of silence from the current address (a NAT rebind between the first Initial and the reply; anyone who saw the original DCID can forge an Initial, so it does not move a live path — `core.PathTest.forgedInitialFromThirdAddressDoesNotMovePath`), and does not follow at all with `allowMigration = false`, the reply is limited to 3× what was received from the new address (§8.1), and completing the handshake from someone else's address without the client's keys is impossible — the cost of the attack equals the cost of any fresh Initial; on a visible migration the **old** path is validated as well (§9.3.3), on failure — return to the last validated address (§9.3.2); migration to loopback/link-local is forbidden by default (§21.5.6); `preferred_address` is not advertised and is ignored (§21.5.3). The routing field in the server CID is in clear — the risk is accepted (§4), encrypting the field comes later; the shortcut "≥ 64 bits of entropy in the CID ⇒ address validated" is not used.
- **Verification:** simulator: an address change → a different CID on the new path; **negative control**: a forged source address without PATH_RESPONSE does not switch the sending path.

### 3.6 Certificate substitution / MITM

- **Threats:** someone else's certificate under the same name; "hostname check disabled + system trust"; TOFU substitution at first contact; a proxy with its own certificate instead of the end host's.
- **Mitigations:** the name is always checked (replaceable through `ExpectedName`, cannot be disabled); the pin is always checked, regardless of the base trust; `Tofu` — the pin is remembered at first contact and is mandatory afterwards; `Custom` must check the name (contract + test). `Platform` on Windows Native (0.2.0) is CryptoAPI: the chain is built from the leaf and the presented intermediates for the peer's usage (`serverAuth`/`clientAuth`), then `CertVerifyCertificateChainPolicy(CERT_CHAIN_POLICY_SSL)` with the reference identifier; pins are compared against the chain Windows built, never against a certificate only presented; the leaf's revocation is checked with an unknown status ignored (soft fail, as browsers and rustls-platform-verifier) and network fetches bounded to 10 s, off the handshake's thread. Before it, `Platform` on mingwX64 rejected every peer. On Linux Native a host without a CA store (distroless, `scratch`) fails when the configuration is built, naming every path searched; `SSL_CERT_FILE`/`SSL_CERT_DIR` replace the distribution paths rather than fall back to them, and a directory counts only when it exists (OpenSSL accepts any directory string, which used to turn a missing store into an `UnknownIssuer` at every handshake).
- **Verification:** **negative controls**: someone else's key under the same name → `Verify(HostnameMismatch|UnknownIssuer)`; a publicly valid certificate with a different SPKI under `Pinned` → `PinMismatch`; a key change under `Tofu` → `PinMismatch`. Windows (`WindowsTrustTest`, run in a Windows 11 VM): the test CA is `UnknownIssuer` for the Windows store; with it as the engine's exclusive root a wrong name → `HostnameMismatch`, an expired / not yet valid leaf → `Expired` / `NotYetValid`, another issuer → `UnknownIssuer`, a `clientAuth`-only leaf → `InvalidPurpose`; `negative_pinDoesNotOverrideAPlatformRejection`; against the Internet with `KUICKSILVER_NETWORK_TESTS=1` (`WindowsPlatformTrustNetworkTest`): `www.google.com` accepted, badssl.com's expired, wrong-host, untrusted-root and self-signed certificates rejected with the matching reason. Linux store: C `verify_system_store_missing_names_the_paths`, `LinuxTrustStoreTest.negative_missingStoreNamesTheVariablesAndPaths`. 0.2.0 (security review 2026-10-14): `ksl_ctx_set_option(KSL_OPT_CLIENT_CERT)` on a client context is refused (`test_verify.c` `verify_client_cert_option_refused_on_client`): it used to rewrite `SSL_CTX_set_verify` and turn server verification off; both mode options reject values outside 0..2.

### 3.7 Key leakage

- **Threats:** keys on the JVM/Kotlin heap end up in a dump/crash report; keylog enabled in production through an environment variable; keys remain in freed memory.
- **Mitigations:** key material only in `ksl`; Kotlin holds handles; `OPENSSL_cleanse`; keylog only through the API, `SSLKEYLOGFILE` is not read in release.
- **Verification:** a JVM heap dump test (`HotSpotDiagnosticMXBean.dumpHeap`) — searching for a known secret (from the keylog in a test build) gives 0 matches; there is no precedent in the references, the test is ours; limitations: HPROF does not see native memory, `exportKeyingMaterial`/`hkdfExpandLabel` return secrets in a `ByteArray` on purpose and are excluded; the identity private key is imported from a `CharArray`/`ByteArray` that is wiped and since 0.2.0 (ksl ABI 5) lives only in a native `ksl_pkey` (`TlsIdentity.InMemory` keeps a handle; `SecretsJvmTest.negative_heapDumpNoIdentityPrivateKey`: the EC private scalar is not in the dump while the identity and a context built from it are alive; C `pkey_roundtrip_identity`). Review before 0.2.0: `fromPem` turned the key `CharArray` into a `String` and cut the Base64 body out with `substring`, leaving the key text on the heap, and with several key blocks only the first decoded array was zeroed; it now decodes from the `CharArray` itself (no `String` of the key) and wipes every decoded block on all paths (`SecretsJvmTest.negative_heapDumpNoIdentityPrivateKeyFromPem`: neither the scalar nor a line-spanning stretch of the PEM Base64 is in a dump that includes unreachable objects). What remains is the caller's: a key file read into a `String` before `toCharArray()`, and the caller's `CharArray` until `fromPem` returns. `TlsIdentity.fromPkcs12` and `fromKeyStore` (JVM) are an exception to "the key lives only in a native `ksl_pkey`" (security review 2026-10-14): `KeyStore.load` decrypts the private key into JDK objects (`PrivateKey`, its `BigInteger`s and encoded arrays) that cannot be wiped (`destroy()` is not implemented for RSA and EC keys), and `fromPkcs12` creates and drops such a `KeyStore` itself, so the key stays on the heap as garbage until it is collected and overwritten, visible in a heap dump that includes unreachable objects; the PKCS#8 copy handed to `fromDer` is wiped. Parsing PKCS#12 in `ksl` instead would refuse bundles with the RC2/3DES encryption of older tools, which OpenSSL 3 decrypts only with the legacy provider this build leaves out. Use `fromPem`/`fromDer` when a heap dump must not contain the key. **Negative control**: a release build with `SSLKEYLOGFILE` does not create a file. native-tls review: the TCP client session cache (`SessionCache`) held the DER `i2d_SSL_SESSION` (TLS 1.2 master secret / TLS 1.3 resumption PSK) on the heap for up to 7 days; it now holds a `ksl_session` handle (ABI 4: `ksl_ssl_get1_session`/`ksl_session_free`, `KSL_GET_SESSION` removed), `SSL_SESSION_free` wipes the secret, the `ksl_ssl_get` buffers in JNI and cinterop (keylog, exporter) are wiped. Verification: `SecretsJvmTest.negative_heapDumpNoSecretsTcpSessionCache` — TLS 1.2 with a ticket, the master secret (= the keylog's `CLIENT_RANDOM` = the session master key) is not found in the dump while the session sits in the cache. 0.2.0 (security review 2026-10-14): `keylogFile` opens with `O_NOFOLLOW` (JVM: `NOFOLLOW_LINKS`), checks on the descriptor that the file is regular and owned by the effective user, clears group/other bits of an existing file and refuses file systems without POSIX permissions, so an attacker who plants a symlink or a world-readable file at a path a developer will enable later gets no secrets; Windows only creates the file. Verification: `SecretsJvmTest.negative_keylogFileRefusesSymlink`, `negative_keylogFileExistingModeTightened`, `KeylogFileAppleTest` (same two). Review before 0.2.0: the JVM sink reopened the path for every line with no owner check, so after the file was removed another local user could recreate it (0666 in a shared directory) and receive the secrets; now the JVM opens one channel when the sink is created, checks the attributes right after the open and writes every line through it (the sink is `java.io.Closeable`); Kotlin/Native reopens per line but repeats every check with `fstat` on the new descriptor. Residual (JVM): the check right after the open reads the attributes by path (`NOFOLLOW_LINKS`), since the JVM cannot `fstat` a channel; a swap in that window needs a file this user owns at the path, which another user cannot create. Verification: `SecretsJvmTest.negative_keylogFileRecreatedByAnotherOwnerGetsNothing`. A file with more than one hard link is refused on every POSIX target (`st_nlink == 1`, JVM `unix:nlink`), since the other name may sit where another user can read it: `SecretsJvmTest.negative_keylogFileRefusesHardlink`, `KeylogFileAppleTest.negative_keylogFileRefusesHardlink`. Security review 2026-10-14 : the open had no `O_NONBLOCK` and the regular-file check came after it, so a FIFO another local user planted at the path (before the sink was made, or on Native, which reopens per line, after the file was removed) blocked `open(O_WRONLY)` until a reader appeared: `keylogFile` hung, and on Native the first secret line stalled the QUIC endpoint loop and all its connections. Now Linux and Apple open with `O_NOFOLLOW | O_NONBLOCK` (a FIFO without a reader fails with `ENXIO`, one with a reader fails the `fstat` check) and clear `O_NONBLOCK` on the checked regular file; mingw refuses anything but a regular file after the open (Windows has no FIFOs in the file system; a named pipe does not block the open); the JVM, which cannot open without blocking, reads the attributes without following links before the open and refuses a non-regular file. Verification: `SecretsJvmTest.negative_keylogFileRefusesFifo` (red before: the open blocked), `KeylogFileAppleTest.negative_keylogFileRefusesFifo`, `.negative_keylogFifoSwappedInLaterDoesNotBlock`, `KeylogFileLinuxTest` (the same two). Residual (JVM): a FIFO swapped in between the check and the open by a user who can replace names in the directory still blocks the open (the debug-only key log belongs in a directory only this user can write). 0.2.0 (security review 2026-10-14): the session cache is bounded (256 entries, the least recently stored is evicted and its `ksl_session` freed) and each Ktor client engine owns one that it clears on close, so resumption secrets of a closed engine do not outlive it. Verification: `SessionCacheTest.capEvictsOldestAndFreesNative`, `EngineSessionCacheTest.engineCloseDropsItsSessions`. Security review 2026-10-14 : the session ticket keys (STEKs) were generated in Kotlin (`DefaultTicketKeys`) and kept on the heap for the life of the process, with about four unwiped copies per TCP connection and QUIC session (`current()` copies, the JNI/cinterop concatenation, `SessionTicketConfig.keys`); a heap dump decrypted every ticket under the current or previous key (up to 2 × `rotateEvery`), so 0-RTT data and session contents, and on an mTLS server minted tickets resumed as an authenticated client. Now the keys live in `ksl` only: `ksl_ctx_use_default_ticket_keys` generates and rotates the process-wide keys under a lock (current encrypts, previous decrypts, as before), `ksl_ticket_keys_register` copies explicit keys in once (`SessionTicketConfig` keeps an id and zeroes the caller's arrays, also on failure; the public `keys` property is gone), every temporary (the Kotlin concatenation, the JNI copy, the C snapshot) is wiped. Verification: `SecretsJvmTest.negative_heapDumpNoSessionTicketKeys` (key, AES part and HMAC part absent from a dump with unreachable objects after tickets were issued and resumed; red with a retained copy), `TicketKeysTest.*` (caller arrays zeroed, also on refusal; explicit keys resume across configurations, other keys do not; generated keys resume across connections), C `tickets_default_keys_generated_and_rotated_in_ksl`, `tickets_explicit_keys_registered_once`, `tickets_concurrent_contexts_agree_on_one_key`. Residue: the generated keys are not observable from a JVM test (no binding returns them), so their absence from the heap rests on the absence of any such binding.

### 3.8 0-RTT and replay

- **Threat:** replay of early data: an attacker sends a client's first flight (ClientHello and 0-RTT packets) again, to the same server or another one that shares the ticket keys (RFC 8446 section 8, RFC 9001 section 9.2).
- **Mitigation (0.2.0; ADR-0015):** 0-RTT is off unless both sides opt in (`QuicClientConfig.earlyData`, `QuicServerConfig.earlyData`). Freshness: OpenSSL accepts early data only for an unexpired ticket whose claimed age is within ±10 s of the server's (`SSL_OP_NO_ANTI_REPLAY` is set because OpenSSL's own mode needs the server session cache `ksl` keeps off). Single use: the replay register admits each ticket identity (`key_name ‖ iv`) once while it could pass the freshness check. There is one register per process, shared by every server endpoint, loop and configuration and kept across endpoint restarts: every endpoint of the process can decrypt every ticket issued under the process's keys, and the identity starts with the ticket's key name, so the register is scoped per process per ticket key. It is bounded to 1 MiB and fails closed (no early data) when full; an identity stays in it only when TLS accepted the early data (ticket decrypted, binder verified, fresh), so forged hellos cannot fill it. A backward wall-clock step (OpenSSL's age check uses the wall clock, the register the monotonic one) makes the register refuse early data until the wall clock is past every hello it may have forgotten. Binding: tickets carry a digest of the ALPN, transport limits and HTTP/3 SETTINGS; another configuration gets no early data. Application: HTTP/3 runs only replayable requests (GET, HEAD, OPTIONS by default) before the handshake; others wait for it (a replayer cannot complete it, it lacks the resumption secret) or get 425; clients send only opted-in safe requests early. Refused 0-RTT packets are never processed. Behind a gateway the replay can happen on a previous hop: the Ktor server engine treats a request marked `Early-Data` (RFC 8470 §5.1, any value) as early over HTTP/1.1 and HTTP/3 — `receivedEarly` is true, and a request the policy does not declare replayable gets 425 without reaching the application.
- **Residue:** the register is per process: a replay into another server process that shares `SessionTicketConfig.keys` (or a restarted process, within the ±10 s freshness window, with the same explicit keys) passes the freshness check only, so a replayable request may run once per such process. The generated keys are per process, so this needs explicit shared keys. Early data and client certificates cannot be combined. The register fails closed, so it can be filled by genuine tickets (security review 2026-10-14): a client that collected tickets (two per full handshake, 12 h lifetime) and spends each once in 0-RTT is admitted once per ticket; about 49,000 such hellos per 20–40 s (64 stripes × 768 admissions per half) keep every stripe at its 3/4 limit, and then every client falls back to 1-RTT until the halves expire. This costs the attacker a full handshake per two tickets and turns off only an optimisation (no request is replayed and no handshake fails); a per-source admission limit is not implemented.
- **Verification:** `core.ZeroRttTest.negative_0rttReplayRejected`, `endpoint.ZeroRttEndpointTest.negative_0rttReplayToSecondEndpointRejected`, `core.ZeroRttTest.negative_forgedHellosDoNotFillTheRegister`, `core.ZeroRttTest.concurrentSameTicketGetsEarlyDataOnce`, `endpoint.ZeroRttReplayRegisterTest.negative_wallClockStepBackDoesNotReopenReplay`, `tls.QuicEarlyDataTest.negative_0rttReplayRejected`, `endpoint.ZeroRttReplayRegisterTest.negative_registerFailsClosedWhenFull`, `http3.runtime.EarlyDataTest.negative_unsafeMethodNotProcessedInEarlyData`, `ktor.server.ServerEarlyDataHeaderTest.negative_gatewayMarkedPostIsTooEarlyOverH1`, `.negative_gatewayMarkedRequestsOverH3`, `core.ZeroRttTest.negative_0rttTransportParamsReduced`; C `quic_early_data_needs_transport_verdict`, `quic_early_data_context_mismatch_rejects`; the interop case `zerortt` stays "not supported" until the interop image turns the options on.

### 3.9 Version and protocol downgrade

- **Threats:** a forged Version Negotiation; TLS downgrade.
- **Mitigations:** VN is accepted only before the first received packet; QUIC uses only TLS 1.3 (OpenSSL enforces it with `SSL_set_quic_tls_cbs`); TCP uses 1.2 only explicitly; RFC 9368 compatible version negotiation with its downgrade check (`version_information`: `negative_downgradeAfterVersionNegotiation`, `negative_clientChosenVersionNotInAvailableRejected`, `negative_availableVersionZeroRejected`).
- **Verification:** **negative controls**: a VN after the Initial reply is ignored; the server never processes an incoming VN (msquic CVE-2023-38171); a VN listing our own version is dropped (§6.2).

### 3.11 Supply chain

- **Threats:** tampered OpenSSL sources; a tampered native artifact in the JAR; an OpenSSL vulnerability without an update.
- **Mitigations:** SHA-256 + PGP for the sources; `KslLoader` checks the hash of the library it extracts from the jar before `System.load` (a library named by `-Dkuicksilver.native.path` or the system library of `-Dkuicksilver.native.system=true` is the operator's choice and loads unchecked); SBOM; CVE procedure in `SECURITY.md`; Renovate (`renovate.json`) watches the OpenSSL pin. The manifest check protects the extracted copy against corruption and against replacement in the work directory, not against a tampered jar (a jar that carries both a different library and a matching manifest is the deployment's responsibility: artifact signatures, the SBOM). 0.2.0 (security review 2026-10-14): the work directory (`<java.io.tmpdir>/kuicksilver-native-<user.name>` or `-Dkuicksilver.native.workdir`) must be a real directory owned by the current user and private to it (`rwx------` applied, anything left over refused), never a symbolic link — otherwise another user of the shared temp directory could swap the library between the check and `System.load`; the extracted file is no longer `deleteOnExit`: its name carries the ABI, its content is verified on every start, and a second JVM may be between its own check and `System.load` when the first one exits.
- **Verification:** **negative control**: an artifact with a modified byte does not load (`KslException.NativeLoad`); `KslLoaderTest.negative_workdirSymlinkRefused`, `negative_workdirForeignOwnerRefused`, `sharedLibrarySurvivesOtherJvmExit` (a child JVM loads from the same directory and exits; the file stays). Review before 0.2.0: the work directory is created with `rwx------` in the creating call (`Files.createDirectory` with a POSIX attribute) instead of under the umask and tightened afterwards; an already extracted library is reused only when it is a regular file owned by this user, otherwise it is replaced through a temp file and an atomic move; when the user of the process cannot be determined on a POSIX file system the loader refuses (`NativeLoad`, `IntegrityMismatch`) instead of skipping the owner checks. Without a POSIX view (Windows) only the directory check applies, as before. Verification: `KslLoaderTest.workDirCreatedWithOwnerOnlyPermissions`, `negative_workdirUnknownUserRefused`, `LoaderInstallTest.negative_existingLibraryWithForeignOwnerIsReinstalled`.

Security review 2026-10-14, for this section:
- **Build dependencies.** Plugins and Maven dependencies (the Kotlin, Ktor and kotlinx artifacts compiled into the published klibs and jars, and the publishing and signing plugins) were fetched with no checksum or signature pinning, so a compromised or typosquatted artifact, or a poisoned `~/.gradle` cache on the release Mac, would end up in a signed release. `gradle/verification-metadata.xml` now pins them (Gradle dependency verification: PGP signatures of trusted publisher keys, grouped per publisher, with the keys in `gradle/verification-keyring.keys`, and SHA-256 for artifacts that are unsigned or whose key no key server has); every build, the release included, fails on an artifact that matches neither. The Gradle wrapper distribution is pinned by `distributionSha256Sum`.
- **OpenSSL in the release.** The release reused `build/openssl/<target>` for seven of the twelve targets (iOS, Android, the Kotlin/Native Linux ones), accepted on the version string and `configure-flags.txt` alone, so a debug or sanitizer build left there, or an archive tampered with in that directory (a copied directory or a CI cache), could ship in the AAR and the klibs. `local-release.sh` now rebuilds all twelve from the tarball `fetch.sh` just verified (`KSL_OPENSSL_FRESH=1` bypasses the build cache). Negative controls: `tools/check/native-release-test.sh` (a sanitizer build, another OpenSSL version and, on ELF hosts, debug sections fail).

### 3.12 Linux specifics of accelerated UDP

- **Threats:** does GRO hand over coalesced datagrams from different senders? (the kernel coalesces only identical 4-tuples); wrong segment handling → connections mixed up.
- **Mitigation:** GRO segments get the batch's address; the CID is checked on every segment as on a separate datagram.
- **Verification:** a test with two senders to one socket.

Pre-release status: `ksl_udp_recv` spreads GRO segments over slots, each slot gets the address and mark of the `recvmsg` it came from; truncated (`MSG_TRUNC`) datagrams and those that do not fit a slot are dropped whole, empty ones are not delivered. Verification: `test_udp.c` `udp_gro_two_senders_not_merged`, `udp_truncated_datagram_dropped`; the `KslUdpSocket` wrapper does not allow entering a native call after shutdown and frees the object only with no receiver inside (`KslUdpSocketTest.closeUnblocksReceive`). `KslDatagramIo` hands the core every segment as a separate datagram with its own address (the address instance cache is keyed by the full 20 bytes, port included), so the CID check is per segment (`KslDatagramIoTest.peerAddressInstanceReused`, `loopbackBatchSendReceive`). A dropped datagram does not restart the receive's wait (0.2.1 review): the timeout is one deadline for the call, as on Windows, and a run of 64 dropped datagrams in a row ends a call that may not wait or already holds datagrams. Before, every dropped datagram re-armed the full `poll` timeout, so an off-path sender of about 1,000 empty datagrams a second (spoofed sources are fine) kept the loop's 1 ms receive on its own thread (`BatchReceiver`) from returning, and with it every timer and application command of the loop (`test_udp.c` `negative_udp_dropped_datagrams_keep_the_timeout`, `negative_udp_dropped_run_is_bounded_per_call`).

### 3.13 Optimistic ACK

- **Threat:** the peer acknowledges packets it has not yet received or that we never sent, inflating cwnd (RFC 9000 §21.4; quiche CVE-2025-4820/4821).
- **Mitigation:** an ACK of an unsent number → `PROTOCOL_VIOLATION`; occasionally we skip a packet number and wait to see whether the peer acknowledges it.
- **Verification:** `negative_ackForUnsentPacket`, `negative_ackForSkippedPacketNumber`.

Status (core review): skipped packet numbers, all CIDs (the client's ODCID/SCID, those issued in NEW_CONNECTION_ID, the server format) and PATH_CHALLENGE data are taken directly from the endpoint CSPRNG (`RAND_bytes` through `ksl`, one stream per loop — `KslRandom.newSource()`; the shared `KslRandom` is thread-safe), not from the connection's `Random(seed)`: an observer could recover the 64-bit XorWow seed from two plaintext CIDs and predict the next CIDs (path linking, §9.5) and the skipped numbers (§21.4). Verification: `endpoint.EndpointCoreTest.connectionRandomnessComesFromTheEndpointSource`, `runtime.KslRandomConcurrencyTest.*` (4 threads × 10 000 draws of 32 bytes — no exceptions and no repeats), `endpoint.StatelessCloseConcurrencyTest.concurrentWritersProduceTheSameBytes`.

### 3.14 Request forgery through the client (RFC 9000 §21.5)

- **Threats:** the server points the client at an arbitrary host:port through `Alt-Svc` or `preferred_address`; an attacker makes the client send Initials/tokens to a victim.
- **Mitigations:** `Alt-Svc` is accepted only from a response over verified TLS, port ≥ 1024 is dropped when the origin is < 1024, the cache is bounded; an alternative on a loopback, link-local, private (RFC 1918, RFC 6598, `fc00::/7`) address or a `localhost` name is dropped unless the origin itself is on such an address (the rule migration applies to paths, §3.5), and one on an unspecified, multicast or broadcast address always (security review 2026-10-14: before, a verified origin, such as a public site under the attacker's control, could send `h3="127.0.0.1:443"` or `h3="[fe80::1]:500"` and every client sent padded Initials into its own network for up to `ma`); `preferred_address` is ignored; NEW_TOKEN is not used. An IPv4 literal is classified in every form `inet_aton` and the JVM accept without DNS (`127.1`, `10.1`, `2130706433`: 0.2.1 review, before they counted as DNS names and passed); a numeric host with an octal or hex part (`0177.0.0.1`, `0x7f.1`: octal or hex to inet_aton, decimal or refused by the JVM) or that is no address (`256.1.1.1`) is never a destination.
- **Residue:** only IP literals are classified: an alternative named by a DNS name that resolves to a local address is not caught (the resolver runs in the QUIC connect, and a check before it could be raced by DNS rebinding). That exposure equals a redirect to such a name, which the HTTP client follows anyway.
- **Verification:** `negative_altSvcFromUnverifiedTls`, `AltSvcDestinationTest.negative_altSvcToLocalNetworkFromPublicOrigin`, `.negative_altSvcToUnspecifiedOrMulticastAlwaysRefused`, `.negative_shorthandIpv4AltSvcToLocalNetworkRefused`, `.negative_ambiguousOrInvalidNumericAltSvcHostRefused`, `.localOriginMayPointToLocalAlternatives`, `negative_preferredAddressIgnored`.

### 3.15 Header protection removal and AEAD limits (RFC 9001 §9.5, §6.6)

- **Threats:** timing side channels in HP removal, packet number recovery and decryption; exceeding the key limits.
- **Mitigations:** `PacketProtector`/`ksl` perform HP, packet number recovery and AEAD without secret-dependent timing; a duplicate packet number is **not** dropped before AEAD; the next-phase keys are derived in advance; exceeding the integrity limit → `AEAD_LIMIT_REACHED`, the confidentiality limit → key update; a DATAGRAM frame in Initial/Handshake → `PROTOCOL_VIOLATION`.
- **Verification:** review of the order of operations; `negative_integrityLimit`, `negative_datagramInHandshakeLevel` (`core.DatagramCoreTest`), `negative_duplicatePacketNumberAfterAead`.

### 3.16 PMTUD and ICMP (RFC 8899 §8)

Pre-release status: the core has no ICMP PTB input — the path size is learned only from acknowledged probes (`core.PmtudTest.probeLossNotCongestion`, `blackHoleFallsBackTo1200AndPauses60s`, `atMostThreeLostProbesPerSize`); a probe never exceeds the peer's `max_udp_payload_size` (`peerMaxUdpPayloadCapsSearch`).

- **Threat:** a forged ICMP "Packet Too Big" with `IP_PMTUDISC_DO` produces `EMSGSIZE` and a broken connection (quic-go CVE-2024-53259); black holes.
- **Mitigation:** a socket with `IP_PMTUDISC_PROBE`/`IPV6_DONTFRAG`; ICMP PTB is not processed (planned as a hint for 0.3.0); we never go below 1200; a black hole detector with fallback.
- **Verification:** `core.PmtudTest.negative_icmpPtbIgnored` — ICMP is not a core input (there is no PTB handler), so the test checks that no external input — a datagram shaped like a PTB quoting our packet, a truncated copy of a real packet, a forged short header with our CID, garbage, from the peer's address and from another — changes the MTU established by probes; `core.PmtudTest.congestionBurstDoesNotFallBack` — a burst of losses is not taken for a black hole; the interop case blackhole.

Final pre-release review: a PMTUD pause on a path that is no longer active is lifted by a timer (`Pmtud.onTimeout`), otherwise the connection's deadline got stuck in the past and the endpoint loop never slept (`PmtudTest.pauseOnFormerPathDoesNotStallTimers`).

Pre-release status: a `ksl_udp` socket with the `KSL_UDP_DF` flag sets `IP_PMTUDISC_PROBE` (and `IPV6_DONTFRAG` for v6), `test_udp.c` `udp_df_probe_mode` checks the option value (3, not `_DO`); `EMSGSIZE` on one datagram skips only its slot. native-tls review: destination errors (`EINVAL` for port 0 or link-local IPv6 without a scope id, `EAFNOSUPPORT`, `EADDRNOTAVAIL`, `EDESTADDRREQ`) also lose only the slot and no longer switch ECN/GSO off forever — a forged Initial from port 0 can neither disable ECN on the server nor abort sending a batch (`test_udp.c` `udp_bad_destination_keeps_ecn_and_gso`, Linux); `ksl_udp_recv` drops datagrams from link-local IPv6 (they cannot be answered). The portable NIO socket does not set DF, so PMTUD with real peers is enabled together with `KslDatagramIo`.

0.2.0 status (Apple, Windows; ADR-0006): Darwin has no `_PROBE` mode, so DF is `IP_DONTFRAG`/`IPV6_DONTFRAG` and Darwin may cache a path MTU from a forged ICMPv6 PTB (clamped to at least 1280): a datagram above it fails with `EMSGSIZE`, which loses only that slot, and the black-hole rule falls back to 1200, so sending never stops (not tested: no ICMP injection on the macOS host). Windows sets `IP_DONTFRAGMENT`/`IPV6_DONTFRAG` and `IP_MTU_DISCOVER`/`IPV6_MTU_DISCOVER = PROBE` where the system has it (Windows 10 1703+); its wake socket is bound with `SO_EXCLUSIVEADDRUSE` and connected to itself, so no other local process can fake a shutdown. The Windows tests (`test_udp_win.c`) need a Windows host; their verification for 0.2.0 is pending.

### 3.17 HTTP/3 and QPACK (RFC 9114 §10, RFC 9204 §7)

- **Threats:** encapsulation through an intermediary (CR/LF/NUL and upper case in field names — critical because the Ktor engine translates H3 into the h1 model); unbounded headers and trailers (quic-go CVE-2025-64702, CVE-2026-40898; Netty CVE-2026-44892); memory allocated by the declared frame length (quiche CVE-2026-12523, Netty CVE-2026-42582); buffering of unknown frames and stream types (Netty CVE-2026-56816); per-stream QPACK encoder state and unsent decoder stream data (Netty CVE-2026-100660, -48748); huge QPACK integers and strings (Netty CVE-2026-100661); CRIME-like compression of secrets; flow control deadlocks (RFC 9308 §4.4); buffering of early PRIORITY_UPDATE; a client that withholds unidirectional stream credit to stall the server's accept loop (0.2.1 review).
- **Mitigations:** invalid field names/values (including characters above U+00FF: fields are octets, otherwise U+010A/U+010D would be truncated to LF/CR — a response splitting vector at an h3→h1 gateway) → `H3_MESSAGE_ERROR` at the stream level; since the 0.2.0 review also a `:method` that is not a token, a `:path` that is not `/…` (or `*` for OPTIONS) or holds whitespace, userinfo in `:authority`/`host`, an `:authority`/`host` that is not an RFC 3986 `host [":" port]` (0.2.1 review: `a.example/x?y`, `a b` or `x#y` passed and became the Ktor `Host`) and a second `host` — values an h3→h1 proxy would otherwise copy into a request line (`message.PseudoHeadersTest.negative_h3MethodMustBeToken`, `.negative_h3PathMustBeAbsoluteOrAsterisk`, `.negative_h3UserinfoInAuthorityRejected`, `.negative_h3AuthoritySyntax`, `.negative_h3SecondHostRejected`); `content-length` strictly `1*DIGIT`, conflicting values → malformed; unacknowledged QPACK encoder sections ≤ 1000, above that — no dynamic references (otherwise a peer that acknowledges insertions but not sections would grow memory and O(n) per encode); an unread request body is stopped with `STOP_SENDING H3_NO_ERROR` once the response completes (before the fix the signal was not sent — the channel cancellation `CancellationException` killed the pump; the `MAX_STREAMS` stream credit of a stopped stream is returned: `kuicksilver-quic` retires a stopped receive half once its final size is known, `StreamStateTest.stoppedStreamRetiresOnceFinalSizeIsKnown`, and `unreadBodiesDoNotExhaustStreamCredit` is enabled), the body pump waits for the consumer; `maxFieldSectionSize` by the **decoded** size, including trailers (64 KB) → 431 + `STOP_SENDING H3_EXCESSIVE_LOAD`; the frame length must match the contents, memory is not allocated by the declared length (review: HEADERS of up to 2 × `maxFieldSectionSize` used to be allocated in full from the header — 100 streams of 5 bytes each held ≈ 13 MB; now it accumulates as it arrives); reserved frames and capsules are skipped in a streaming fashion; never-index for Authorization/Cookie/Set-Cookie; ceilings on QPACK integers and strings, on blocked streams, on the decoder stream buffer; control and QPACK streams are read eagerly; `SETTINGS_H3_DATAGRAM` is always sent (against fingerprinting); a ceiling on buffered PRIORITY_UPDATE; `H3_DATAGRAM` without transport DATAGRAM → `SETTINGS_ERROR`; our control and QPACK streams are opened in the background with a 3 s deadline (`H3_GENERAL_PROTOCOL_ERROR` after it), so neither `Http3Endpoint.accept` nor the Ktor server waits on one client (`Http3EndpointAcceptTest.negative_acceptIsNotHeldByAClientWithoutUniStreamCredit`, `ServerH3Test.negative_clientWithoutUniStreamCreditDoesNotStopAccepting`); a unidirectional stream that a peer resets before its type is dropped with a glitch token instead of closing the connection with `H3_INTERNAL_ERROR` (RFC 9114 §6.2; `runtime.UniStreamResetTest.negative_uniStreamResetInsideItsTypeIsTolerated`).
- **Verification:** `negative_h3FieldCrLfNul`, `negative_h3FieldNonLatin1`, `negative_qpackUnackedSectionsCapped`, `invalidOrConflictingContentLengthIsMessageError`, `unreadBodyIsStoppedAfterResponse`, `negative_headersDeclaredLengthNotPreallocated`, `negative_h3DecodedFieldSectionTooLarge`, `negative_h3TrailersTooLarge`, `negative_h3ReservedFrameHugeLength`, `negative_qpackBlockedStreams`, `negative_qpackHugeIntegerOrLiteral`, `negative_qpackFragmentedEncoderInstructionLinear`, `negative_priorityUpdateBufferCap`; fuzzing.

Pre-release status (frame header): the frame header is parsed from two varints without allocating memory by length; a reserved (GREASE) frame with a declared length of 2^62−1 gets the decision "skip" (`frame.FrameHeaderTest.negative_h3ReservedFrameHugeLength`); control frames that are read into memory (SETTINGS, GOAWAY, PRIORITY_UPDATE) are capped at 4096 bytes by the header before reading → `H3_EXCESSIVE_LOAD` (`frame.FrameRulesTest.controlPayloadCap`).

Pre-release status (QPACK primitives): a QPACK integer longer than 10 continuation bytes or above 2^62−1, and a string declared longer than the rest of the buffer or the `QpackLimits.maxStringLength` ceiling (for Huffman — by the decoded length) are rejected before allocating memory (`qpack.PrimitivesTest.negative_qpackHugeIntegerOrLiteral`); review: a 10th continuation byte whose bits would be shifted past bit 62 is an overflow too, it used to be dropped silently (`.negative_qpackIntegerOverflowIn10thContinuationByte`). Since the 0.2.0 review the string ceiling and its outcome depend on where the string is (RFC 9204 §7.4): in a field section the ceiling is our `maxFieldSectionSize` (a raised limit raises it) and a longer string makes the section too large — a stream error (431 on a request stream, `FieldSectionTooLarge` on the client), the connection lives; on the encoder stream it stays 64 KiB and a longer string is a connection error `QPACK_ENCODER_STREAM_ERROR`. Before, one field over 64 KiB closed the whole connection with `QPACK_DECOMPRESSION_FAILED`, also below a raised limit (`qpack.QpackDecoderTest.oversizedSingleFieldIsTooLargeNotAnError`, `runtime.LimitsTest.negative_h3SingleOversizedFieldIs431NotConnectionError`, `.singleOversizedResponseFieldFailsOnlyItsRequest`, `.raisedMaxFieldSectionSizeAcceptsLargeSingleValue`); EOS inside a string and padding longer than 7 bits or not made of ones are errors (`qpack.HuffmanTest`).

Pre-release status (QPACK decoder): the QPACK decoder computes the decoded size of the field section per RFC 9114 §4.2.2 (name + value + 32) while parsing and stops as soon as it exceeds `maxFieldSectionSize` (64 KiB) — `qpack.QpackDecoderTest.negative_h3DecodedFieldSectionTooLarge`; there are no more blocked streams than the advertised `qpackBlockedStreams`, an extra one → `QPACK_DECOMPRESSION_FAILED` (`negative_qpackBlockedStreams`); an incomplete encoder stream instruction is buffered up to 2 × the string ceiling + 64 bytes; a table capacity above the one we advertised → `QPACK_ENCODER_STREAM_ERROR`.

0.2.0 status (STREAM reassembly ranges, §21.7): the internal limit `QuicLimits.reassemblyRangesPerStream` (256; 4096 per connection, not configurable) still bounds the gaps a stream may hold, but reaching it no longer closes the connection with FLOW_CONTROL_ERROR. A packet whose STREAM frame would open one more gap is dropped without being acknowledged, so the peer retransmits it; data that fills an existing gap always merges, and so is a frame at the read offset (it opens no gap; 0.2.1: one that did not reach the first buffered range was refused at the limit, and with nothing readable the stream stalled until the idle timeout), so the connection keeps making progress; a stream holds at most one range beyond the gap limit, the readable one. Before 0.2.0, a burst that lost every other packet within one RTT (a full receive buffer) closed a connection whose peer had stayed within flow control (`core.LossBurstTest`, seen on the macOS CI runner in `MigrationApiTest`). Memory stays bounded by the same ceiling; a peer that keeps fragmenting gains nothing but its own retransmissions (`stream.ReassemblerTest.negative_fragmentedStreamRangesCap`). Review h-quic (0.2.1): a refused frame used to raise the stream's highest offset before the refusal and skip the connection-level charge, and data sent later below that offset merged into a buffered range uncharged: three streams held 1.5 MiB against the 768 KiB connection window, and with the default limits one connection could hold the sum of its stream windows. Every check (final size, stream and connection window, reassembly room) now runs before anything is committed (`stream.ReassemblyFullFlowControlTest.*`), and the refused packet's number counts as seen, so a duplicate or replay does not apply its earlier frames (a DATAGRAM, a PATH_CHALLENGE) twice (`core.RefusedPacketReplayTest`).

0.2.0 status (QPACK reassembly, RFC 9204 §7.4): an encoder-stream instruction that arrives in many fragments is appended to a growing buffer and parsed once its length (known from the string literal's prefix) has arrived; before 0.2.0 every fragment re-copied and re-parsed the accumulated prefix, so a peer sending a 60 KB literal byte by byte cost the decoder ≈ 1.8 GB of memory traffic (`qpack.QpackDecoderTest.negative_qpackFragmentedEncoderInstructionLinear`).

0.2.0 status (request-stream hygiene, RFC 9114 §7.2.8, §4.1.2; RFC 9110 §10.1.4): unknown frames on a request stream spend glitch tokens like those on the control stream — 1001 empty frames close the connection with `H3_EXCESSIVE_LOAD` (`runtime.RequestTest.unknownFramesOnRequestStreamSpendGlitchTokens`); DATA on a response to HEAD or with status 204/304 is a malformed message rather than a body an h3→h1 gateway could forward (`dataInHeadResponseIsMessageError`, `dataIn204ResponseIsMessageError`, `dataIn304ResponseIsMessageError`); `te` in a response or trailers is malformed and the server engine never sends it (`teInResponseIsMalformed`, `ServerH3Test.teStrippedFromH3Response`).

Pre-release status (field validation): CR, LF and NUL in a name or value, upper case and non-token characters in a name, a space or tab at the edges of a value, connection-specific fields (`connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, `upgrade`) and `te` other than `trailers` make the message malformed (`message.FieldValidatorTest.negative_h3FieldCrLfNul`, `.uppercaseNameRejected`, `.connectionSpecificRejected`); malformed is a stream error `H3_MESSAGE_ERROR`, not a connection error (runtime behaviour — next paragraph).

Pre-release status (runtime limits): on a connection, a request with 70 KiB of (decoded) fields gets 431 and `STOP_SENDING H3_EXCESSIVE_LOAD`, the connection lives (`runtime.LimitsTest.negative_h3DecodedFieldSectionTooLarge`) — whether the size comes from many fields or from a single one above the string ceiling (review; before, a single field over 64 KiB was a connection error: `negative_h3SingleOversizedFieldIs431NotConnectionError`); the same for trailers (`negative_h3TrailersTooLarge`); a HEADERS frame declaring 1 GiB is rejected by its header (`headersFrameLengthAboveCapRejectedWithoutReading`); a reserved frame with a declared length of 2^40 on a request stream is skipped in a streaming fashion, a FIN inside it is a connection error `H3_FRAME_ERROR` per RFC 9114 §7.1 (before the review — `H3_REQUEST_INCOMPLETE` on that stream only) (`runtime.LimitsTest.negative_h3ReservedFrameHugeLength`); a malformed request resets only its own stream (`runtime.RequestTest.malformedRequestResetsStreamOnly`); an unknown uni stream is stopped without buffering (`runtime.ConnectionTest.unknownUniStreamStoppedNotFatal`); control and QPACK streams are read eagerly by separate coroutines.

Pre-release status (glitch limiter): the glitch limiter (1000 tokens, 33/s, `Http3Settings.glitchProtection`; see docs/guide/quic.md, "Glitch protection") is spent on unknown and reserved frames of the control stream and on empty uni streams (and on excess `PRIORITY_UPDATE`, next paragraph); exhaustion closes the connection with `H3_EXCESSIVE_LOAD` (`runtime.GlitchLimiterTest.unknownControlFramesFloodClosesExcessiveLoad`: 100 frames — alive, 1000 more — closed).

Pre-release status (priorities): early `PRIORITY_UPDATE`s (for streams not yet opened) are buffered up to `maxEarlyPriorityUpdates` = 32, excess ones are dropped and spend a glitch token (`runtime.PriorityTest.negative_priorityUpdateBufferCap`); a frame longer than 256 bytes is not applied (`oversizedPriorityUpdateIgnored`); every `PRIORITY_UPDATE` spends a glitch token.

Pre-release status (fuzzing): Jazzer targets `h3Frames` (control and request stream frames through `FrameRules`/`SettingsCodec`/QPACK), `capsules` (`CapsuleParser`, buffer ceiling; the parser is not wired to CONNECT streams yet, the Capsule Protocol is not implemented) and `qpackDecode` (encoder stream + field section + pseudo-headers) in `kuicksilver-http3/src/jvmTest/…/fuzz`, seeds from `tools/http3/gen-fuzz-seeds.py` (RFC 9204 appendix B); a 60 s run each (≈ 1.0 million, 16.3 million and 8.0 million inputs respectively, 2026-10-08) — no findings; `jvmTest` runs a regression mode on the seeds.

### 3.18 Fallback to TCP and protocol confusion (RFC 9308 §2, §17; RFC 9114 §10.2)

- **Threats:** an h3 → h1.1 fallback with weakened verification; cross-protocol attacks through ALPN.
- **Mitigations:** the fallback uses the same `TrustConfig`, the same pins and TLS 1.3; ALPN strictly `h3`/`http/1.1`, a mismatch → `no_application_protocol`.
- **Verification:** `negative_fallbackKeepsPins`, `negative_alpnMismatchClosesConnection`.

Pre-release status (Alt-Svc): the client engine learns `Alt-Svc` only from responses over TLS verified by its `TrustConfig`; a response over `http://` does not set an alternative, a 421 removes it (`AltSvcTest.negative_altSvcFromUnverifiedTls`, `.status421RemovesEntry`, `ClientAltSvcTest.plainHttpAltSvcIgnored`); when an alternative is used, SNI and certificate verification follow the origin.

0.2.0 status (Alt-Svc state bounds, RFC 7838 §9.4): what servers can make the client remember is bounded — at most 8 alternatives per origin (`AltSvcTest.negative_altSvcEntriesPerOriginCapped`), at most 1000 origins in `InMemoryAltSvcStore` and `FileAltSvcStore`, the least recently used dropped first, and no more than 8000 records read back from the file (`FileAltSvcStoreTest.negative_altSvcStoreBoundedOrigins`); broken-alternative marks and the networks where QUIC worked are capped the same way (`BrokenAltSvcTest.negative_brokenMarksBounded`), and so is the per-origin RTT the race uses for its head start (`ClientAltSvcTest.srttMapBounded`). ### 3.20 HTTP/1.1 framing and proxies (RFC 9112 §6, §11; RFC 9110 §9.3.6, §11.7.2)

- **Threats:** request smuggling and response splitting through ambiguous message framing (a front proxy and the engine disagreeing on where a message ends); credentials meant for a proxy reaching the origin server.
- **Mitigations:** the client sends `Proxy-Authorization` and `Proxy-Connection` only on the CONNECT to the proxy, never inside the tunnel to the origin, and takes the bytes after a `2xx` CONNECT head as the tunnel's whatever its `Content-Length` says. A response whose Content-Length values conflict or are not `1*DIGIT` fails and its connection is closed (RFC 9112 §6.3 item 5); a response with Content-Length and Transfer-Encoding is framed by the coding and its connection is not reused (item 3); a chunked trailer section is capped at 16 KiB, a response head at 64 KiB (the proxy's CONNECT response too) and the interim (1xx) responses before the final one at 5 (0.2.1: before, a server could make the client buffer a header section of any size, or hold a request with endless 103s); a body cut before its framing ends fails instead of arriving short. The server refuses a request with both Content-Length and Transfer-Encoding with 400 and closes the connection (RFC 9112 §6.1), so bytes a Content-Length-framing front proxy forwarded as body are never parsed as a second request; invalid or conflicting Content-Length, unknown transfer codings and Transfer-Encoding in HTTP/1.0 get the same treatment, and a request without framing has no body. An HTTP/1.1 request without Host, or any request with more than one Host line, gets 400 and the connection closed (RFC 9112 §3.2), so a front proxy that keys on another Host line cannot route or cache by a host the application did not see. The server's own 400 responses carry a fixed body: Ktor CIO sends the parser's message, which embeds the header section read so far, and would reflect cookies and the fields a front proxy added (the class of Apache CVE-2012-0053). Both engines read a chunk-size line strictly by RFC 9112 §7.1 (`1*HEXDIG`, extensions by their grammar, CRLF only with whitespace before it tolerated, at most 128 bytes, a size that fits a signed 64-bit length): a bare CR, a bare LF or a quote outside an extension fails the message, where a lenient recipient behind a strict one (or the reverse) frames the body differently (before 0.2.1 a CR was skipped anywhere in the line, so `1\r0` read as 0x10); on the server the handler's receive of such a body fails with `BadRequestException` (Ktor's 400 unless the application handles it) and the connection closes.
- **Verification:** `ClientProxyTest.negative_proxyCredentialsStayOnTheConnect`, `ClientProxyTest.contentLengthOnConnectResponseIsIgnored`, `ClientH1FramingTest.negative_conflictingContentLengthFailsAndClosesConnection`, `.negative_signedContentLengthRejected`, `.negative_contentLengthWithTransferEncodingIsNotReused`, `.negative_hugeTrailerSectionFails`, `.negative_chunkedBodyCutBeforeLastChunkFails`, `h1.H1ResponseHeadTest.negative_hugeResponseHeadFails`, `.negative_endlessInterimResponsesFail`, `ClientProxyTest.negative_hugeConnectResponseHeadFails`, `ServerH1FramingTest.negative_contentLengthWithTransferEncodingIsRejectedAndClosed`, `.negative_invalidContentLengthIsRejected`, `.negative_unknownTransferCodingIsRejected`, `.negative_bareCrInChunkSizeIsRejected`, `.negative_missingOrRepeatedHostIsRejected`, `.negative_badRequestDoesNotEchoTheHeaderSection`, `h1.ChunkedBodyTest.negative_*` (server and client copies: bare CR, bare LF, malformed sizes and extensions, a quote outside an extension, overlong sizes).

### 3.21 TCP peers that read slowly or not at all (JVM and Android)

- **Threats:** a peer (a client of the HTTP/1.1 server, a server the HTTP/1.1 client talks to, either side of TLS over TCP) that keeps its receive window closed costs us CPU or threads for as long as it likes. ktor-network 3.6.0's JVM writer (`CIOWriter.kt`, `attachForWritingDirectImpl`) retries a `SocketChannel.write` that answers 0 without ever reaching its select: one `Dispatchers.IO` thread at 100 % CPU per such peer, not cancellable, so about 64 of them exhaust `Dispatchers.IO` and stall every coroutine on it (0.2.1 review).
- **Mitigations:** the engines' JVM and Android TCP sockets (`connectTcp`, `bindTcp`) write through `KslNioSocket`: a write that answers 0 suspends in the socket's selector until it is writable, and cancelling the socket's job ends that wait and closes the descriptor, as does a write that fails (a reset); a client connection's `close()` lets the writer drain for at most 3 s, then drops the rest and closes the socket; a server's accepted socket has no close bound of its own (a fixed one cut a slow reader's last response short with a clean EOF), whoever accepted the socket sets its bound (`setCloseTimeout`); a client's `TlsSocket.close()` is bounded (3 s; a server's is set by whoever accepted it), as is `TlsConnection.shutdown()`. Reading stays ktor's, which selects correctly. A socket an application opens with `aSocket` itself and passes to `Socket.tls` still writes through ktor-network: `Socket.tls` gets no `SelectorManager` to wait on (adding a parameter changes the public API in a patch release, reading ktor's internal one by reflection is not acceptable, and a selector of our own would share the socket's interest set and suspensions with ktor's).
- **Verification:** `TcpWriterTest.negative_writerWaitsWithoutSpinningWhileThePeerDoesNotRead` (no thread inside `SocketChannel.write` while the peer does not read, a bounded number of waits), `.negative_tlsCloseReleasesTheSocketWhileThePeerDoesNotRead`, `.negative_plainCloseIsBoundedWhileThePeerDoesNotRead`, `.negative_closeAfterAPeerResetReleasesTheSocket`, `.closeAfterTheWriterFinishedReleasesTheSocket`, `.negative_slowReaderGetsTheWholeResponseThroughClose`, `.negative_slowReaderGetsTheWholeTlsResponseThroughClose`, `SocketTlsTest.negative_closeIsBoundedWhenThePeerStopsReading`, `TlsConnectionTest.negative_shutdownIsBoundedWhenThePeerStopsReading`.

### 3.22 HTTP/1.1 server resource exhaustion (slowloris on both sides, oversized heads) and accept failures

- **Threats:** a client holds HTTP/1.1 connections open without completing a request: it connects and stays silent (on a TLS connector it never sends a ClientHello) or sends the request head a byte at a time, each byte inside the idle timeout. With enough such connections the server runs out of descriptors or memory. A fast client can instead send a head of unbounded size: Ktor's parser limits each line to 8 KiB but not their number, and 0.2.0 buffered megabytes of header fields per request. On the send side, a client can request a large response and never read it: the response writer, its handler and, on close, the socket's write loop wait for the client for ever. Released 0.2.0 had no deadline for the head at all, its 45 s idle timer closed only the output side while the reader kept waiting, and there was no handshake timeout, so one such connection was held for ever. Separately, an `accept()` that fails (EMFILE/ENFILE once the descriptor table is full, which such connections cause) was retried at once: the accept loop spun at 100 % CPU for as long as the condition lasted.
- **Mitigations:** a request-head deadline, `requestHeaderTimeoutSeconds` (default 30 s, positive), counted from the accepted TCP connection for the first request (the TLS handshake runs under it too) and from the end of the previous response on a keep-alive connection, never restarted by arriving bytes; a partial head gets `408 Request Timeout` with `Connection: close` (RFC 9110 §15.5.9), an idle connection is closed without a response (RFC 9112 §9.5; as Go's `net/http` and nginx). The idle timeout (`connectionIdleTimeoutSeconds`) ends the whole connection. A response write that makes no progress for the longer of the idle timeout and 5 minutes (each hand-over to the channel in front of the socket must return within it; nginx `send_timeout`, also between successive writes rather than for the whole response) ends the connection and its handler, upgraded (WebSocket) connections included, and the engine bounds every connection's close the same way: graceful while the drain makes progress (`Socket.bytesSent`, the bytes the kernel took, looked at every second), so a slow reader's last `Connection: close` response is never cut short, and aborted once nothing has moved for the same deadline, or at once when the connection was just cut for not reading (`Socket.abort`: the TLS session released, the socket closed and its write loop ended under it, with `SO_LINGER` 0, so the peer sees a reset; a write loop that fails, or a response stream that fails mid-way, resets the connection the same way rather than ending it with a FIN that would pass a cut close-delimited body for a whole one), so a non-reading client cannot keep the descriptor; the accepted sockets have no close bound of their own (`setCloseTimeout(null)`, §3.21). Cancelling the socket's job without closing it first, as this engine first did, left the descriptor open (on TLS connectors the raw socket's loops ended before its `close()`, which nobody called). On the JVM the ktor-network 3.6.0 writer under all this was itself a CPU DoS, one thread spinning in `SocketChannel.write` per non-reading peer (KTOR-9959, fixed for Ktor 3.6.1, not released yet); the engines' sockets write through their own `KslNioSocket` writer, which waits in the selector instead (§3.21). Progress of a response write is seen about 1 MiB at a time (Ktor's `ByteChannel` in front of the socket), hence the 5-minute floor: clients down to about 3.4 KiB/s keep their responses; finer progress would need a socket that reports what the kernel took. A client that stops reading holds its connection, its handler and the bytes buffered for it (about 4 MiB on a plain connector and 6 MiB on a TLS one on the JVM, the channels' and the kernel's buffers together) for 5 minutes after the buffers filled; its socket is then aborted at once, and the engine waits up to 3 s for the descriptor to be released before it cancels the socket's job as a last resort. A graceful stop gives responses in flight the grace period: a connection ends only once its socket has closed, so the listener and its selector outlive the drain (before, they closed under sockets still sending). A request head is limited to 64 KiB (the HTTP/3 server's default `maxFieldSectionSize`), counted from its first byte by a channel between the socket and the parser, so the parser never sees more; above it `431 Request Header Fields Too Large` (RFC 6585 §5) and close, after reading and dropping the rest for at most 2 s so the client sees the answer rather than a reset (nginx `lingering_close`). Failed accepts back off 5 ms, doubling to 1 s, reset by the next successful accept (Go `net/http` `Server.Serve`), and are logged at most once per 10 s with a count, so a full descriptor table does not flood the log; a failure on a closed listening socket and cancellation end the loop at once. What remains: the deadline bounds each connection, not their number; an attacker with many addresses still holds `connections × 30 s` (no per-IP or global HTTP/1.1 connection limit in 0.2.x: put a proxy or the OS limits in front of a public server). A request body has an inactivity deadline, the idle timeout: no byte of it for that long fails the handler's read and the client gets `408 Request Timeout` (or the connection closes when a response has started), and the connection ends after the request (slow POST, R.U.D.Y.); each wait for the next bytes has its own deadline, so a slow but moving upload is read in full (nginx `client_body_timeout`, likewise between two reads); after `Expect: 100-continue` it starts once `100 Continue` is sent, or when the handler is done without asking for the body; an upgraded connection's bytes have none. The 408 is per call and has a fixed body: the engine's own phase for HTTP/1.1 calls answers it only when the application (StatusPages included) has not, and no exception message reaches the client. A body the handler leaves unread is read and dropped up to 256 KiB (Go's `maxPostHandlerReadBytes`), never more, so a client cannot make the server swallow an unbounded upload after the response; a larger rest, or a chunked one still incomplete when the response head goes out (its size is unknown; Go drains up to the cap at that point, which would consume a body a streaming handler still reads), ends the connection after a response that says `Connection: close`, with up to 2 s of reading and dropping before the close so that the reset of a close over unread input does not destroy the response (`UnreadBodyLingerJvmTest`, red without it on Linux: "Broken pipe"); a request answered without the `100 Continue` it asked for ends it too (RFC 9110 §10.1.1). Empty lines before a request line (RFC 9112 §2.2) are skipped and do not make an idle connection a started request (no 408 for them).

## 4. What we do not protect against

- Traffic analysis by sizes/timings (no padding except Initial); DATAGRAM frames are distinguishable by their reaction to loss.
- Correlation by address on a migration without a CID change on the peer's side; the routing field in the server CID is sent in clear (encryption later).
- An on-path attacker aborting the handshake (RFC 9000 §21.1.1.3) — an accepted risk.
- Linking sessions of one client through TCP-TLS tickets (RFC 9001 §9.1).
- Attacks on OpenSSL itself (we track CVEs) and side channels on the host.
