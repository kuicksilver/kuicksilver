# Kuicksilver — threat model

Date: 2026-10-02, updated 2026-10-08 (K1–K5 statuses and the full review) and 2026-10-13 (K7 statuses, the 0.2.0 work). Status: current document (approved by the owner 2026-10-02, updated per milestone); revised after a cross-check against RFC 9000 §21, RFC 9001/9002/9114/9204/9308/8899 and the CVEs of quinn, quic-go, quiche, ngtcp2, msquic, s2n-quic, OpenSSL, Netty, picoquic, quicly. Related: docs/architecture.md, the resource limits in docs/guide/quic.md ("Glitch protection", "Admission and endpoint limits").

## 1. Assets

| Asset | Where it lives | How it is protected |
|---|---|---|
| TLS secrets and packet protection keys | only native `ksl` memory (`ksl_key`, `SSL`, client sessions for resumption — `ksl_session`) | not copied into Kotlin (the TCP session cache holds a `ksl_session` handle, not `i2d_SSL_SESSION` bytes); `OPENSSL_cleanse` on free, intermediate JNI/cinterop buffers are wiped; JVM heap dump test |
| Identity private key | `ksl_pkey` / `ksl_ctx` (v1: in native memory, Kotlin holds a handle; later: an external signer, out of process) | parsed once into OpenSSL (ksl ABI 5), the imported `ByteArray`/`CharArray` and the JNI copy are wiped, freed with the last reference; JVM heap dump test; v2 — the key never leaves the store |
| Retry token key, stateless reset key, session ticket keys | only `ksl` (handles; HMAC/AEAD inside) | generated by `ksl_rand`, rotated on a schedule; the reset key is separate from CID generation |
| Application plaintext in buffers | the `PacketBuffer` pool | is it wiped on return to the pool? — no (performance); buffers are not shared between connections |
| Server availability (CPU, memory, sockets) | `EndpointCore` | ceilings and `ConnectionAdmission`, §3.2 |
| Client privacy (linkability by CID, address) | `ConnectionIdRegistry` | CID change on migration |

## 2. Attackers

- **Network observer** (passive): sees datagrams.
- **Active network attacker (on-path / off-path)**: forges, delays, duplicates, replays packets; off-path knows addresses but does not see contents.
- **Malicious peer**: a valid connection that violates the protocol or exhausts resources.
- **Malicious server/proxy** (for the client): presents someone else's certificate.
- **Local attacker with access to process memory/a dump** (limited: JVM heap dump, crash report).
- **Malicious dependency/artifact** (supply chain).

Out of scope: OS/kernel compromise, hardware side-channel attacks on AEAD (we rely on OpenSSL), an attacker with root on the host.

## 3. Threats and mitigations

Format: threat → mitigation → verification (positive test / **negative control**).

### 3.1 Amplification

- **Threat:** an off-path attacker sends an Initial with the victim's forged address; the server answers with a large volume.
- **Mitigation:** an amplification limit of 3× the received bytes before address validation (RFC 9000 §8.1): **all** datagram bytes of this connection are counted, including dropped packets, each datagram exactly once (OpenSSL CVE-2026-35191); the limit is lifted only after real address validation; a client Initial ≥ 1200 bytes is mandatory, otherwise ignored; Version Negotiation is no longer than the incoming datagram; Retry when the threshold of incomplete handshakes is exceeded. An Initial with source port 0 is dropped without a reply (no socket listens on port 0, the kernel rejects the send — EINVAL — and such a forged datagram would cost the server a lost send; native-tls review, `EndpointCoreTest.initialFromSourcePortZeroDropped`); link-local IPv6 peers are not served by the accelerated transport (`ksl_udp` drops fe80::/10: the 20-byte address format does not carry a scope id).
- **Verification:** the simulator counts bytes before validation; **negative control**: a packet beyond 3× is not sent; an Initial < 1200 bytes is ignored.

### 3.2 Resource exhaustion

- **Threats:** Initial flood (CPU spent on TLS); thousands of half-open connections; more streams than the limit; an endless CRYPTO buffer; receive memory held by unassembled data; ACK flood; PATH_CHALLENGE flood; `NEW_CONNECTION_ID` beyond the limit.
- **Mitigations:** `ConnectionAdmission` (a limit on handshakes in flight → Retry/Drop), an Initial queue before `admit` with a ceiling, only cheap checks before `ksl` (≥ 1200 bytes, version, DCID ≥ 8); a keyed hash (SipHash) for choosing the loop and for the CID tables (§21.13; picoquic CVE-2025-24946); `maxConnectionsPerIp`, an optional `maxConnectionLifetime` (slowloris, §21.6); a glitch token bucket enabled by default (§21.9); Retry as proof of address under load; a CRYPTO ceiling of 64 KB per level out of order, the Initial stream ending at 64 KiB and the Handshake stream at 256 KiB, CRYPTO past the end of a level TLS has left a PROTOCOL_VIOLATION (RFC 9001 §4.1.3) and at most 256 KiB unread per level in `ksl`, counted in the handshake's buffer bytes for admission; `max_streams`; `active_connection_id_limit`; `maxReassemblyRanges` per stream and per connection with an O(log n) structure (§21.7; quinn CVE-2026-25800, OpenSSL CVE-2026-42772); CRYPTO: `offset+len` checked **before** allocating memory and a separate ceiling in 1-RTT (s2n GHSA-9q54, quiche CVE-2024-1765); refusal beyond `max_streams` before allocating memory (s2n GHSA-475v); metadata of ACK-only packets is not stored (OpenSSL CVE-2026-63075); a ceiling on qlog volume; ceilings on the queues (datagrams, undecryptable packets, PATH_CHALLENGE, ACK ranges, early PRIORITY_UPDATE) — connection memory is bounded by the sum of explicit ceilings, there is no separate "budget"; at the endpoint — `ConnectionAdmission` with Retry/Drop at the limit of handshakes in flight; idle timeout.
- **Verification:** a **negative control** for every limit: exceeding it → close with the expected code, process memory does not grow (measured in the test).
- **Long-run verification:** the soak harness `kuicksilver-soak` (CONTRIBUTING.md, "Soak and churn") drives a server and clients on real UDP through transfers, aborts, idle timeouts, stateless resets, migrations, 0-RTT, refusals at a full accept queue and Ktor HTTP/1.1 and HTTP/3 for hours, and fails when RSS, heap, descriptors, `ksl` live objects or any library table grows after warm-up or does not return to its idle level. It found a native key leaked per stateless Initial CONNECTION_CLOSE (a peer could grow server memory within the stateless rate limits) and server connections kept until their idle timeout after a migrated client closed. Opt-in, not part of `check`; 2 h nightly before a beta, 24–72 h before a release.

Status (runtime review, 2026-10-08): a stream reset by the peer or stopped by us is retired, and the `MAX_STREAMS` credit is returned — otherwise after `maxBidiStreams` resets the peer was permanently stuck in STREAMS_BLOCKED (`api.StreamRetirementTest.*`); the queue of datagram send commands is bounded (≤ 2 × `datagramSendQueue` + 1, `api.DatagramApiTest.dropOldestFloodStaysBounded`); a qlog trace is not opened for an undecryptable (forgeable) Initial and is always closed, a sink failure (EMFILE) does not bring the endpoint down (`qlog.QlogRobustnessTest.*`); datagrams forwarded between loops are processed in batches of 16 with `yield` (`runtime.LoopGroupTest.forwardedBurstDoesNotMonopoliseTheLoop`); an idle accelerated socket does not occupy a `Dispatchers.IO` thread (`KslReceiveSlicesTest`).

K7 status (runtime, 2026-10-12): a socket that never runs dry (a flood of junk at line rate) no longer starves the loop's timers and the application's commands: the receive loop yields after 16 rounds or 2 ms (`runtime.WorkLimiter`, `runtime.ReceiveFairnessTest.timersFireUnderContinuousReceive`); the accept queue never holds more than `acceptQueue` connections (128 by default) — a client Initial arriving while it is full is refused statelessly with an Initial CONNECTION_CLOSE (CONNECTION_REFUSED) before any handshake state, under the stateless rate limits (`endpoint.AdmissionTest.initialWhileAcceptQueueFullIsRefusedStatelessly`, `.negative_refusalIsAmplificationLimited`, `runtime.LoopGroupTest.initialWhileTheSharedAcceptQueueIsFullIsRefusedStatelessly`; 2026-10-13), and a handshake completing above the limit is closed with CONNECTION_REFUSED (`api.EndpointLifecycleTest.acceptBacklogNeverExceedsAcceptQueue`), while admission counts only the connections waiting for `accept()`, so `acceptQueue` half-open handshakes from spoofed sources do not lock real clients out (`api.EndpointLifecycleTest.negative_spoofedInitialsDoNotLockOutAdmission`); a peer that keeps changing address leaves at most four path objects on the server (`api.MigrationApiTest.serverPathListStaysBoundedAcrossMigrations`); the loop makes no resolver call per datagram (`core.AddressClassNativeTest.ipBytesNeverResolvesHostnames`); datagrams a full socket refuses are counted (`ConnectionStats.datagramsDroppedSocket`).

### 3.3 Forged Retry and tokens

- **Threat:** an attacker sends the client a forged Retry (DCID change, downgrade); or sends the server an Initial with someone else's or a reused token; amplification through NEW_TOKEN.
- **Mitigation:** the Retry Integrity Tag (RFC 9001 §5.8) is checked by the client; the client drops a second Retry, a Retry with an empty token, a Retry with SCID = the original DCID and any Retry after an accepted Initial (§17.2.5). The server token is AEAD under the endpoint key (the key lives in `ksl`) and contains the token type (Retry ≠ NEW_TOKEN, §8.1.1), the ODCID, **the Retry SCID** (K7: an Initial that presents the token under another DCID is refused with `INVALID_TOKEN`, statelessly, RFC 9000 §8.1.3-§8.1.4), the client's address **and port**, and the time; lifetime 10 s; `original_destination_connection_id` and `retry_source_connection_id` are checked in the transport parameters. An Initial with an **invalid** Retry token → close with `INVALID_TOKEN`, no second Retry is sent (§8.1.2). In v1 the server does not issue NEW_TOKEN and the client does not store it. `ConnectionAdmission.admit` does not return `Retry` for an attempt whose address is already validated (quinn CVE-2024-45311); the default token handler never treats "no check" as success (Netty CVE-2026-44894).
- **Verification:** the vector of RFC 9001 appendix A.4; **negative controls**: a wrong tag → Retry dropped; a forged / expired / other-address token → `INVALID_TOKEN`; a token reused under another DCID → `INVALID_TOKEN` (`endpoint.RetryTest.negative_retryTokenReusedWithOtherDcid`); empty token, SCID = ODCID, Retry after Initial → dropped; CID mismatch in the TP → `TRANSPORT_PARAMETER_ERROR`.

### 3.4 Forged stateless reset and a reset oracle

- **Threat:** an off-path attacker closes someone else's connection with a forged stateless reset; the client accepts a reset from a third party; **the server itself** becomes an oracle and kills a live connection (RFC 9000 §21.11).
- **Mitigation:** token = HMAC(a **separate** endpoint key in `ksl`, CID) — unpredictable and not derivable from the CID in the header (Netty CVE-2026-50009); only the last 16 bytes of a packet are accepted when they match the token of a **used and not retired** CID (§10.3.1); constant-time comparison (MUST); a zero or empty token slot never matches (quicly CVE-2026-44434); the reply is smaller than the triggering packet and ≥ 21 bytes, its rate is limited (§10.3.3). With N loops on `SO_REUSEPORT` the kernel distributes by 4-tuple: after a NAT rebind a packet of a live connection may arrive at a loop without state — such a loop **does not send a reset**, the decision is made through a shared CID registry or after forwarding to the owner loop. The receiver of a reset goes into draining and gives the application a separate cause, `StatelessReset`.
- **Verification:** **negative controls**: a wrong token → ignored, the connection lives, `invalidResets++`; the token of a retired CID → ignored; a zero token → ignored; a packet of a live connection in another loop → no reset; constant time — code review and a branching test.

K3 status: with `loops > 1` each loop answers with a stateless reset only for CIDs with its own routing byte (`EndpointCore.ownerLoop`), a packet with another loop's routing byte is copied to the owner (`LoopGroup.forward`), the reset key is per loop. Verification: `StatelessResetTest.negative_resetNotFromOtherLoop` (core), `MultiLoopTest.forwardedDatagramReachesOwner` (runtime, Linux: traffic of a live connection directed to another loop → delivered to the owner, `statelessResets == 0` on all loops). Runtime review: the loops of a group start only after all of them are created (a datagram for another loop before start no longer brings the group down), the failure of one loop closes the whole group, the shared `accept` queue is closed only by the group — `runtime.LoopGroupTest.*` (in-memory sockets, all platforms).

### 3.5 Tracking by CID and migration

- **Threat:** an observer links the old and the new path by CID (deanonymisation on a network change); an attacker triggers a false migration with a forged source address.
- **Mitigation:** migration uses an unused CID and a new stateless reset token (RFC 9000 §9.5), and already the probe of the new path (and the reply to it) carries its own unused CID rather than the CID of the active path (`core.PathTest.probeUsesUnusedPeerCid`, core review); enough CIDs are requested from the peer in advance; passive migration requires PATH_CHALLENGE, while the path is not validated the 3× amplification limit applies and the old path stays; before validation only probing frames go to the new path; the exception is an unfinished handshake: the server follows the address of the client's last decrypted Handshake packet, and of an Initial packet only after ≥ 1 PTO of silence from the current address (a NAT rebind between the first Initial and the reply; anyone who saw the original DCID can forge an Initial, so it does not move a live path — `core.PathTest.forgedInitialFromThirdAddressDoesNotMovePath`), and does not follow at all with `allowMigration = false`, the reply is limited to 3× what was received from the new address (§8.1), and completing the handshake from someone else's address without the client's keys is impossible — the cost of the attack equals the cost of any fresh Initial; on a visible migration the **old** path is validated as well (§9.3.3), on failure — return to the last validated address (§9.3.2); migration to loopback/link-local is forbidden by default (§21.5.6); `preferred_address` is not advertised in v1 and is ignored (§21.5.3). The routing field in the server CID is in clear — the risk is accepted (§4), encrypting the field comes later; the shortcut "≥ 64 bits of entropy in the CID ⇒ address validated" is not used.
- **Verification:** simulator: an address change → a different CID on the new path; **negative control**: a forged source address without PATH_RESPONSE does not switch the sending path.

### 3.6 Certificate substitution / MITM

- **Threats:** someone else's certificate under the same name; "hostname check disabled + system trust"; TOFU substitution at first contact; a proxy with its own certificate instead of the end host's.
- **Mitigations:** the name is always checked (replaceable through `ExpectedName`, cannot be disabled); the pin is always checked, regardless of the base trust; `Tofu` — the pin is remembered at first contact and is mandatory afterwards; `Custom` must check the name (contract + test). `Platform` on Windows Native (beta readiness) is CryptoAPI: the chain is built from the leaf and the presented intermediates for the peer's usage (`serverAuth`/`clientAuth`), then `CertVerifyCertificateChainPolicy(CERT_CHAIN_POLICY_SSL)` with the reference identifier; pins are compared against the chain Windows built, never against a certificate only presented; the leaf's revocation is checked with an unknown status ignored (soft fail, as browsers and rustls-platform-verifier) and network fetches bounded to 10 s, off the handshake's thread. Before it, `Platform` on mingwX64 rejected every peer. On Linux Native a host without a CA store (distroless, `scratch`) fails when the configuration is built, naming every path searched; `SSL_CERT_FILE`/`SSL_CERT_DIR` replace the distribution paths rather than fall back to them, and a directory counts only when it exists (OpenSSL accepts any directory string, which used to turn a missing store into an `UnknownIssuer` at every handshake).
- **Verification:** **negative controls**: someone else's key under the same name → `Verify(HostnameMismatch|UnknownIssuer)`; a publicly valid certificate with a different SPKI under `Pinned` → `PinMismatch`; a key change under `Tofu` → `PinMismatch`. Windows (`WindowsTrustTest`, run in a Windows 11 VM): the test CA is `UnknownIssuer` for the Windows store; with it as the engine's exclusive root a wrong name → `HostnameMismatch`, an expired / not yet valid leaf → `Expired` / `NotYetValid`, another issuer → `UnknownIssuer`, a `clientAuth`-only leaf → `InvalidPurpose`; `negative_pinDoesNotOverrideAPlatformRejection`; against the Internet with `KUICKSILVER_NETWORK_TESTS=1` (`WindowsPlatformTrustNetworkTest`): `www.google.com` accepted, badssl.com's expired, wrong-host, untrusted-root and self-signed certificates rejected with the matching reason. Linux store: C `verify_system_store_missing_names_the_paths`, `LinuxTrustStoreTest.negative_missingStoreNamesTheVariablesAndPaths`. K7 (F4.4): `ksl_ctx_set_option(KSL_OPT_CLIENT_CERT)` on a client context is refused (`test_verify.c` `verify_client_cert_option_refused_on_client`): it used to rewrite `SSL_CTX_set_verify` and turn server verification off; both mode options reject values outside 0..2.

### 3.7 Key leakage

- **Threats:** keys on the JVM/Kotlin heap end up in a dump/crash report; keylog enabled in production through an environment variable; keys remain in freed memory.
- **Mitigations:** key material only in `ksl`; Kotlin holds handles; `OPENSSL_cleanse`; keylog only through the API, `SSLKEYLOGFILE` is not read in release.
- **Verification:** a JVM heap dump test (`HotSpotDiagnosticMXBean.dumpHeap`) — searching for a known secret (from the keylog in a test build) gives 0 matches; there is no precedent in the references, the test is ours; limitations: HPROF does not see native memory, `exportKeyingMaterial`/`hkdfExpandLabel` return secrets in a `ByteArray` on purpose and are excluded; the identity private key is imported from a `CharArray`/`ByteArray` that is wiped and from K7 (F4.6, ksl ABI 5) lives only in a native `ksl_pkey` (`TlsIdentity.InMemory` keeps a handle; `SecretsJvmTest.negative_heapDumpNoIdentityPrivateKey`: the EC private scalar is not in the dump while the identity and a context built from it are alive; C `pkey_roundtrip_identity`). Review of k7/f4-native-tls: `fromPem` turned the key `CharArray` into a `String` and cut the Base64 body out with `substring`, leaving the key text on the heap, and with several key blocks only the first decoded array was zeroed; it now decodes from the `CharArray` itself (no `String` of the key) and wipes every decoded block on all paths (`SecretsJvmTest.negative_heapDumpNoIdentityPrivateKeyFromPem`: neither the scalar nor a line-spanning stretch of the PEM Base64 is in a dump that includes unreachable objects). What remains is the caller's: a key file read into a `String` before `toCharArray()`, and the caller's `CharArray` until `fromPem` returns. **Negative control**: a release build with `SSLKEYLOGFILE` does not create a file. native-tls review: the TCP client session cache (`SessionCache`) held the DER `i2d_SSL_SESSION` (TLS 1.2 master secret / TLS 1.3 resumption PSK) on the heap for up to 7 days; it now holds a `ksl_session` handle (ABI 4: `ksl_ssl_get1_session`/`ksl_session_free`, `KSL_GET_SESSION` removed), `SSL_SESSION_free` wipes the secret, the `ksl_ssl_get` buffers in JNI and cinterop (keylog, exporter) are wiped. Verification: `SecretsJvmTest.negative_heapDumpNoSecretsTcpSessionCache` — TLS 1.2 with a ticket, the master secret (= the keylog's `CLIENT_RANDOM` = the session master key) is not found in the dump while the session sits in the cache. K7 (F4.1): `keylogFile` opens with `O_NOFOLLOW` (JVM: `NOFOLLOW_LINKS`), checks on the descriptor that the file is regular and owned by the effective user, clears group/other bits of an existing file and refuses file systems without POSIX permissions, so an attacker who plants a symlink or a world-readable file at a path a developer will enable later gets no secrets; Windows only creates the file. Verification: `SecretsJvmTest.negative_keylogFileRefusesSymlink`, `negative_keylogFileExistingModeTightened`, `KeylogFileAppleTest` (same two). Review of k7/f4-native-tls: the JVM sink reopened the path for every line with no owner check, so after the file was removed another local user could recreate it (0666 in a shared directory) and receive the secrets; now the JVM opens one channel when the sink is created, checks the attributes right after the open and writes every line through it (the sink is `java.io.Closeable`); Kotlin/Native reopens per line but repeats every check with `fstat` on the new descriptor. Residual (JVM): the check right after the open reads the attributes by path (`NOFOLLOW_LINKS`), since the JVM cannot `fstat` a channel; a swap in that window needs a file this user owns at the path, which another user cannot create. Verification: `SecretsJvmTest.negative_keylogFileRecreatedByAnotherOwnerGetsNothing`. A file with more than one hard link is refused on every POSIX target (`st_nlink == 1`, JVM `unix:nlink`), since the other name may sit where another user can read it: `SecretsJvmTest.negative_keylogFileRefusesHardlink`, `KeylogFileAppleTest.negative_keylogFileRefusesHardlink`. K7 (F4.5): the session cache is bounded (256 entries, the least recently stored is evicted and its `ksl_session` freed) and each Ktor client engine owns one that it clears on close, so resumption secrets of a closed engine do not outlive it. Verification: `SessionCacheTest.capEvictsOldestAndFreesNative`, `EngineSessionCacheTest.engineCloseDropsItsSessions`.

### 3.8 0-RTT and replay

- **Threat:** replay of early data: an attacker sends a client's first flight (ClientHello and 0-RTT packets) again, to the same server or another one that shares the ticket keys (RFC 8446 section 8, RFC 9001 section 9.2).
- **Mitigation (K7, G; ADR-0015):** 0-RTT is off unless both sides opt in (`QuicClientConfig.earlyData`, `QuicServerConfig.earlyData`). Freshness: OpenSSL accepts early data only for an unexpired ticket whose claimed age is within ±10 s of the server's (`SSL_OP_NO_ANTI_REPLAY` is set because OpenSSL's own mode needs the server session cache `ksl` keeps off). Single use: the replay register admits each ticket identity (`key_name ‖ iv`) once while it could pass the freshness check. There is one register per process, shared by every server endpoint, loop and configuration and kept across endpoint restarts: every endpoint of the process can decrypt every ticket issued under the process's keys, and the identity starts with the ticket's key name, so the register is scoped per process per ticket key. It is bounded to 1 MiB and fails closed (no early data) when full; an identity stays in it only when TLS accepted the early data (ticket decrypted, binder verified, fresh), so forged hellos cannot fill it. A backward wall-clock step (OpenSSL's age check uses the wall clock, the register the monotonic one) makes the register refuse early data until the wall clock is past every hello it may have forgotten. Binding: tickets carry a digest of the ALPN, transport limits and HTTP/3 SETTINGS; another configuration gets no early data. Application: HTTP/3 runs only replayable requests (GET, HEAD, OPTIONS by default) before the handshake; others wait for it (a replayer cannot complete it, it lacks the resumption secret) or get 425; clients send only opted-in safe requests early. Refused 0-RTT packets are never processed.
- **Residue:** the register is per process: a replay into another server process that shares `SessionTicketConfig.keys` (or a restarted process, within the ±10 s freshness window, with the same explicit keys) passes the freshness check only, so a replayable request may run once per such process. The generated keys are per process, so this needs explicit shared keys. Early data and client certificates cannot be combined.
- **Verification:** `core.ZeroRttTest.negative_0rttReplayRejected`, `endpoint.ZeroRttEndpointTest.negative_0rttReplayToSecondEndpointRejected`, `core.ZeroRttTest.negative_forgedHellosDoNotFillTheRegister`, `core.ZeroRttTest.concurrentSameTicketGetsEarlyDataOnce`, `endpoint.ZeroRttReplayRegisterTest.negative_wallClockStepBackDoesNotReopenReplay`, `tls.QuicEarlyDataTest.negative_0rttReplayRejected`, `endpoint.ZeroRttReplayRegisterTest.negative_registerFailsClosedWhenFull`, `http3.runtime.EarlyDataTest.negative_unsafeMethodNotProcessedInEarlyData`, `core.ZeroRttTest.negative_0rttTransportParamsReduced`; C `quic_early_data_needs_transport_verdict`, `quic_early_data_context_mismatch_rejects`; the interop case `zerortt` stays "not supported" until the interop image turns the options on.

### 3.9 Version and protocol downgrade

- **Threats:** a forged Version Negotiation; TLS downgrade.
- **Mitigations:** VN is accepted only before the first received packet; QUIC uses only TLS 1.3 (OpenSSL enforces it with `SSL_set_quic_tls_cbs`); TCP uses 1.2 only explicitly; `available_versions`/RFC 9368 — later.
- **Verification:** **negative controls**: a VN after the Initial reply is ignored; the server never processes an incoming VN (msquic CVE-2023-38171); a VN listing our own version is dropped (§6.2).

### 3.10 Parsing errors and memory

- **Threats:** overflows in `ksl`, malformed frames, varint overflows, infinite loops in the QPACK decoder.
- **Mitigations:** `ksl` — minimal code, all buffers with lengths, no `strlen`; Kotlin — bounds checks; fuzzing with Jazzer and libFuzzer; size limits.
- **Verification:** fuzzing corpus in CI, an ASan/UBSan build of `ksl` in CI.

CONNECTION_CLOSE, unknown types — plus application actions, loss, duplication, reordering, ECN marks, NAT rebinding and

datagram over 1500 bytes overflowed the endpoint's answer buffer (`endpointRoute`, `packetRecvServer`;
`StatelessResetTest.negative_resetForJumboDatagramFitsItsBuffer`); (2) a Retry token too large for the client's next

(4) the early-data verdict of a failed TLS session leaked `KslException` (`zeroRttHello`;
`QuicEarlyDataTest.negative_earlyDataVerdictAfterFailedHandshake`); (5) a malformed `QuicSessionTicket.remembered` blob threw

connection (the addresses it sent PATH_CHALLENGE to, its MTU updates) grew with every challenge, so forged copies of a

### 3.11 Supply chain

- **Threats:** tampered OpenSSL sources; a tampered native artifact in the JAR; an OpenSSL vulnerability without an update.
- **Mitigations:** SHA-256 + PGP for the sources; `KslLoader` checks the hash of the library it extracts from the jar before `System.load` (a library named by `-Dkuicksilver.native.path` or the system library of `-Dkuicksilver.native.system=true` is the operator's choice and loads unchecked); SBOM; CVE procedure in `SECURITY.md`; Dependabot/Renovate on OpenSSL. The manifest check protects the extracted copy against corruption and against replacement in the work directory, not against a tampered jar (a jar that carries both a different library and a matching manifest is the deployment's responsibility: artifact signatures, the SBOM). K7 (F4.2): the work directory (`<java.io.tmpdir>/kuicksilver-native-<user.name>` or `-Dkuicksilver.native.workdir`) must be a real directory owned by the current user and private to it (`rwx------` applied, anything left over refused), never a symbolic link — otherwise another user of the shared temp directory could swap the library between the check and `System.load`; the extracted file is no longer `deleteOnExit`: its name carries the ABI, its content is verified on every start, and a second JVM may be between its own check and `System.load` when the first one exits.
- **Verification:** **negative control**: an artifact with a modified byte does not load (`KslException.NativeLoad`); `KslLoaderTest.negative_workdirSymlinkRefused`, `negative_workdirForeignOwnerRefused`, `sharedLibrarySurvivesOtherJvmExit` (a child JVM loads from the same directory and exits; the file stays). Review of k7/f4-native-tls: the work directory is created with `rwx------` in the creating call (`Files.createDirectory` with a POSIX attribute) instead of under the umask and tightened afterwards; an already extracted library is reused only when it is a regular file owned by this user, otherwise it is replaced through a temp file and an atomic move; when the user of the process cannot be determined on a POSIX file system the loader refuses (`NativeLoad`, `IntegrityMismatch`) instead of skipping the owner checks. Without a POSIX view (Windows) only the directory check applies, as before. Verification: `KslLoaderTest.workDirCreatedWithOwnerOnlyPermissions`, `negative_workdirUnknownUserRefused`, `LoaderInstallTest.negative_existingLibraryWithForeignOwnerIsReinstalled`.

### 3.12 Linux specifics of accelerated UDP

- **Threats:** does GRO hand over coalesced datagrams from different senders? (the kernel coalesces only identical 4-tuples); wrong segment handling → connections mixed up.
- **Mitigation:** GRO segments get the batch's address; the CID is checked on every segment as on a separate datagram.
- **Verification:** a test with two senders to one socket.

K3 status: `ksl_udp_recv` spreads GRO segments over slots, each slot gets the address and mark of the `recvmsg` it came from; truncated (`MSG_TRUNC`) datagrams and those that do not fit a slot are dropped whole, empty ones are not delivered. Verification: `test_udp.c` `udp_gro_two_senders_not_merged`, `udp_truncated_datagram_dropped`; the `KslUdpSocket` wrapper does not allow entering a native call after shutdown and frees the object only with no receiver inside (`KslUdpSocketTest.closeUnblocksReceive`). `KslDatagramIo` hands the core every segment as a separate datagram with its own address (the address instance cache is keyed by the full 20 bytes, port included), so the CID check is per segment (`KslDatagramIoTest.peerAddressInstanceReused`, `loopbackBatchSendReceive`).

### 3.13 Optimistic ACK

- **Threat:** the peer acknowledges packets it has not yet received or that we never sent, inflating cwnd (RFC 9000 §21.4; quiche CVE-2025-4820/4821).
- **Mitigation:** an ACK of an unsent number → `PROTOCOL_VIOLATION`; occasionally we skip a packet number and wait to see whether the peer acknowledges it.
- **Verification:** `negative_ackForUnsentPacket`, `negative_ackForSkippedPacketNumber`.

Status (core review): skipped packet numbers, all CIDs (the client's ODCID/SCID, those issued in NEW_CONNECTION_ID, the server format) and PATH_CHALLENGE data are taken directly from the endpoint CSPRNG (`RAND_bytes` through `ksl`, one stream per loop — `KslRandom.newSource()`; the shared `KslRandom` is thread-safe), not from the connection's `Random(seed)`: an observer could recover the 64-bit XorWow seed from two plaintext CIDs and predict the next CIDs (path linking, §9.5) and the skipped numbers (§21.4). Verification: `endpoint.EndpointCoreTest.connectionRandomnessComesFromTheEndpointSource`, `runtime.KslRandomConcurrencyTest.*` (4 threads × 10 000 draws of 32 bytes — no exceptions and no repeats), `endpoint.StatelessCloseConcurrencyTest.concurrentWritersProduceTheSameBytes`.

### 3.14 Request forgery through the client (RFC 9000 §21.5)

- **Threats:** the server points the client at an arbitrary host:port through `Alt-Svc` or `preferred_address`; an attacker makes the client send Initials/tokens to a victim.
- **Mitigations:** `Alt-Svc` is accepted only from a response over verified TLS, port ≥ 1024 is dropped when the origin is < 1024, the cache is bounded; `preferred_address` is ignored; NEW_TOKEN is not used.
- **Verification:** `negative_altSvcFromUnverifiedTls`, `negative_preferredAddressIgnored`.

### 3.15 Header protection removal and AEAD limits (RFC 9001 §9.5, §6.6)

- **Threats:** timing side channels in HP removal, packet number recovery and decryption; exceeding the key limits.
- **Mitigations:** `PacketProtector`/`ksl` perform HP, packet number recovery and AEAD without secret-dependent timing; a duplicate packet number is **not** dropped before AEAD; the next-phase keys are derived in advance; exceeding the integrity limit → `AEAD_LIMIT_REACHED`, the confidentiality limit → key update; a DATAGRAM frame in Initial/Handshake → `PROTOCOL_VIOLATION`.
- **Verification:** review of the order of operations; `negative_integrityLimit`, `negative_datagramInHandshakeLevel` (`core.DatagramCoreTest`, K3), `negative_duplicatePacketNumberAfterAead`.

### 3.16 PMTUD and ICMP (RFC 8899 §8)

K3 status: the core has no ICMP PTB input — the path size is learned only from acknowledged probes (`core.PmtudTest.probeLossNotCongestion`, `blackHoleFallsBackTo1200AndPauses60s`, `atMostThreeLostProbesPerSize`); a probe never exceeds the peer's `max_udp_payload_size` (`peerMaxUdpPayloadCapsSearch`).

- **Threat:** a forged ICMP "Packet Too Big" with `IP_PMTUDISC_DO` produces `EMSGSIZE` and a broken connection (quic-go CVE-2024-53259); black holes.
- **Mitigation:** a socket with `IP_PMTUDISC_PROBE`/`IPV6_DONTFRAG`; ICMP PTB is not processed in v1; we never go below 1200; a black hole detector with fallback.
- **Verification:** `core.PmtudTest.negative_icmpPtbIgnored` — ICMP is not a core input (there is no PTB handler), so the test checks that no external input — a datagram shaped like a PTB quoting our packet, a truncated copy of a real packet, a forged short header with our CID, garbage, from the peer's address and from another — changes the MTU established by probes; `core.PmtudTest.congestionBurstDoesNotFallBack` — a burst of losses is not taken for a black hole; the interop case blackhole.

Final K3 review: a PMTUD pause on a path that is no longer active is lifted by a timer (`Pmtud.onTimeout`), otherwise the connection's deadline got stuck in the past and the endpoint loop never slept (`PmtudTest.pauseOnFormerPathDoesNotStallTimers`).

K3 status: a `ksl_udp` socket with the `KSL_UDP_DF` flag sets `IP_PMTUDISC_PROBE` (and `IPV6_DONTFRAG` for v6), `test_udp.c` `udp_df_probe_mode` checks the option value (3, not `_DO`); `EMSGSIZE` on one datagram skips only its slot. native-tls review: destination errors (`EINVAL` for port 0 or link-local IPv6 without a scope id, `EAFNOSUPPORT`, `EADDRNOTAVAIL`, `EDESTADDRREQ`) also lose only the slot and no longer switch ECN/GSO off forever — a forged Initial from port 0 can neither disable ECN on the server nor abort sending a batch (`test_udp.c` `udp_bad_destination_keeps_ecn_and_gso`, Linux); `ksl_udp_recv` drops datagrams from link-local IPv6 (they cannot be answered). The portable NIO socket does not set DF, so PMTUD with real peers is enabled together with `KslDatagramIo`.

K7 status (Apple, Windows; ADR-0006): Darwin has no `_PROBE` mode, so DF is `IP_DONTFRAG`/`IPV6_DONTFRAG` and Darwin may cache a path MTU from a forged ICMPv6 PTB (clamped to at least 1280): a datagram above it fails with `EMSGSIZE`, which loses only that slot, and the black-hole rule falls back to 1200, so sending never stops (not tested: no ICMP injection on the macOS host). Windows sets `IP_DONTFRAGMENT`/`IPV6_DONTFRAG` and `IP_MTU_DISCOVER`/`IPV6_MTU_DISCOVER = PROBE` where the system has it (Windows 10 1703+); its wake socket is bound with `SO_EXCLUSIVEADDRUSE` and connected to itself, so no other local process can fake a shutdown. The Windows tests (`test_udp_win.c`) need a Windows host; their verification for 0.2.0 is pending.

### 3.17 HTTP/3 and QPACK (RFC 9114 §10, RFC 9204 §7)

- **Threats:** encapsulation through an intermediary (CR/LF/NUL and upper case in field names — critical because the Ktor engine translates H3 into the h1 model); unbounded headers and trailers (quic-go CVE-2025-64702, CVE-2026-40898; Netty CVE-2026-44892); memory allocated by the declared frame length (quiche CVE-2026-12523, Netty CVE-2026-42582); buffering of unknown frames and stream types (Netty CVE-2026-56816); per-stream QPACK encoder state and unsent decoder stream data (Netty CVE-2026-100660, -48748); huge QPACK integers and strings (Netty CVE-2026-100661); CRIME-like compression of secrets; flow control deadlocks (RFC 9308 §4.4); buffering of early PRIORITY_UPDATE.
- **Mitigations:** invalid field names/values (including characters above U+00FF: fields are octets, otherwise U+010A/U+010D would be truncated to LF/CR — a response splitting vector at an h3→h1 gateway) → `H3_MESSAGE_ERROR` at the stream level; `content-length` strictly `1*DIGIT`, conflicting values → malformed; unacknowledged QPACK encoder sections ≤ 1000, above that — no dynamic references (otherwise a peer that acknowledges insertions but not sections would grow memory and O(n) per encode); an unread request body is stopped with `STOP_SENDING H3_NO_ERROR` once the response completes (before the fix the signal was not sent — the channel cancellation `CancellationException` killed the pump; the `MAX_STREAMS` stream credit of a stopped stream is returned: `kuicksilver-quic` retires a stopped receive half once its final size is known, `StreamStateTest.stoppedStreamRetiresOnceFinalSizeIsKnown`, and `unreadBodiesDoNotExhaustStreamCredit` is enabled), the body pump waits for the consumer; `maxFieldSectionSize` by the **decoded** size, including trailers (64 KB) → 431 + `STOP_SENDING H3_EXCESSIVE_LOAD`; the frame length must match the contents, memory is not allocated by the declared length (review: HEADERS of up to 2 × `maxFieldSectionSize` used to be allocated in full from the header — 100 streams of 5 bytes each held ≈ 13 MB; now it accumulates as it arrives); reserved frames and capsules are skipped in a streaming fashion; never-index for Authorization/Cookie/Set-Cookie; ceilings on QPACK integers and strings, on blocked streams, on the decoder stream buffer; control and QPACK streams are read eagerly; `SETTINGS_H3_DATAGRAM` is always sent (against fingerprinting); a ceiling on buffered PRIORITY_UPDATE; `H3_DATAGRAM` without transport DATAGRAM → `SETTINGS_ERROR`.
- **Verification:** `negative_h3FieldCrLfNul`, `negative_h3FieldNonLatin1`, `negative_qpackUnackedSectionsCapped`, `invalidOrConflictingContentLengthIsMessageError`, `unreadBodyIsStoppedAfterResponse`, `negative_headersDeclaredLengthNotPreallocated`, `negative_h3DecodedFieldSectionTooLarge`, `negative_h3TrailersTooLarge`, `negative_h3ReservedFrameHugeLength`, `negative_qpackBlockedStreams`, `negative_qpackHugeIntegerOrLiteral`, `negative_qpackFragmentedEncoderInstructionLinear`, `negative_priorityUpdateBufferCap`; fuzzing.

K5 status (frame header): the frame header is parsed from two varints without allocating memory by length; a reserved (GREASE) frame with a declared length of 2^62−1 gets the decision "skip" (`frame.FrameHeaderTest.negative_h3ReservedFrameHugeLength`); control frames that are read into memory (SETTINGS, GOAWAY, PRIORITY_UPDATE) are capped at 4096 bytes by the header before reading → `H3_EXCESSIVE_LOAD` (`frame.FrameRulesTest.controlPayloadCap`).

K5 status (QPACK primitives): a QPACK integer longer than 10 continuation bytes or above 2^62−1, and a string declared longer than the rest of the buffer or the `QpackLimits.maxStringLength` ceiling (64 KiB by default, for Huffman — by the decoded length) are rejected before allocating memory with `QPACK_DECOMPRESSION_FAILED` (`qpack.PrimitivesTest.negative_qpackHugeIntegerOrLiteral`); EOS inside a string and padding longer than 7 bits or not made of ones are errors (`qpack.HuffmanTest`).

K5 status (QPACK decoder): the QPACK decoder computes the decoded size of the field section per RFC 9114 §4.2.2 (name + value + 32) while parsing and stops as soon as it exceeds `maxFieldSectionSize` (64 KiB) — `qpack.QpackDecoderTest.negative_h3DecodedFieldSectionTooLarge`; there are no more blocked streams than the advertised `qpackBlockedStreams`, an extra one → `QPACK_DECOMPRESSION_FAILED` (`negative_qpackBlockedStreams`); an incomplete encoder stream instruction is buffered up to 2 × the string ceiling + 64 bytes; a table capacity above the one we advertised → `QPACK_ENCODER_STREAM_ERROR`.

K7 status (STREAM reassembly ranges, §21.7): `maxReassemblyRanges` still bounds the gaps a stream may hold, but reaching it no longer closes the connection with FLOW_CONTROL_ERROR. A packet whose STREAM frame would open one more gap is dropped without being acknowledged, so the peer retransmits it; data that fills an existing gap always merges, so the connection keeps making progress. Before K7, a burst that lost every other packet within one RTT (a full receive buffer) closed a connection whose peer had stayed within flow control (`core.LossBurstTest`, seen on the macOS CI runner in `MigrationApiTest`). Memory stays bounded by the same ceiling; a peer that keeps fragmenting gains nothing but its own retransmissions (`stream.ReassemblerTest.negative_fragmentedStreamRangesCap`).

K7 status (QPACK reassembly, RFC 9204 §7.4): an encoder-stream instruction that arrives in many fragments is appended to a growing buffer and parsed once its length (known from the string literal's prefix) has arrived; before K7 every fragment re-copied and re-parsed the accumulated prefix, so a peer sending a 60 KB literal byte by byte cost the decoder ≈ 1.8 GB of memory traffic (`qpack.QpackDecoderTest.negative_qpackFragmentedEncoderInstructionLinear`).

K7 status (request-stream hygiene, RFC 9114 §7.2.8, §4.1.2; RFC 9110 §10.1.4): unknown frames on a request stream spend glitch tokens like those on the control stream — 1001 empty frames close the connection with `H3_EXCESSIVE_LOAD` (`runtime.RequestTest.unknownFramesOnRequestStreamSpendGlitchTokens`); DATA on a response to HEAD or with status 204/304 is a malformed message rather than a body an h3→h1 gateway could forward (`dataInHeadResponseIsMessageError`, `dataIn204ResponseIsMessageError`, `dataIn304ResponseIsMessageError`); `te` in a response or trailers is malformed and the server engine never sends it (`teInResponseIsMalformed`, `ServerH3Test.teStrippedFromH3Response`).

K5 status (field validation): CR, LF and NUL in a name or value, upper case and non-token characters in a name, a space or tab at the edges of a value, connection-specific fields (`connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, `upgrade`) and `te` other than `trailers` make the message malformed (`message.FieldValidatorTest.negative_h3FieldCrLfNul`, `.uppercaseNameRejected`, `.connectionSpecificRejected`); malformed is a stream error `H3_MESSAGE_ERROR`, not a connection error (runtime behaviour — next paragraph).

K5 status (runtime limits): on a connection, a request with 70 KiB of (decoded) fields gets 431 and `STOP_SENDING H3_EXCESSIVE_LOAD`, the connection lives (`runtime.LimitsTest.negative_h3DecodedFieldSectionTooLarge`); the same for trailers (`negative_h3TrailersTooLarge`); a HEADERS frame declaring 1 GiB is rejected by its header (`headersFrameLengthAboveCapRejectedWithoutReading`); a reserved frame with a declared length of 2^40 on a request stream is skipped in a streaming fashion, a FIN inside it is a connection error `H3_FRAME_ERROR` per RFC 9114 §7.1 (before the review — `H3_REQUEST_INCOMPLETE` on that stream only) (`runtime.LimitsTest.negative_h3ReservedFrameHugeLength`); a malformed request resets only its own stream (`runtime.RequestTest.malformedRequestResetsStreamOnly`); an unknown uni stream is stopped without buffering (`runtime.ConnectionTest.unknownUniStreamStoppedNotFatal`); control and QPACK streams are read eagerly by separate coroutines.

K5 status (glitch limiter): the glitch limiter (1000 tokens, 33/s, `Http3Settings.glitchProtection`; see docs/guide/quic.md, "Glitch protection") is spent on unknown and reserved frames of the control stream and on empty uni streams (and on excess `PRIORITY_UPDATE`, next paragraph); exhaustion closes the connection with `H3_EXCESSIVE_LOAD` (`runtime.GlitchLimiterTest.unknownControlFramesFloodClosesExcessiveLoad`: 100 frames — alive, 1000 more — closed).

K5 status (priorities): early `PRIORITY_UPDATE`s (for streams not yet opened) are buffered up to `maxEarlyPriorityUpdates` = 32, excess ones are dropped and spend a glitch token (`runtime.PriorityTest.negative_priorityUpdateBufferCap`); a frame longer than 256 bytes is not applied (`oversizedPriorityUpdateIgnored`); every `PRIORITY_UPDATE` spends a glitch token.

K5 status (fuzzing): Jazzer targets `h3Frames` (control and request stream frames through `FrameRules`/`SettingsCodec`/QPACK), `capsules` (`CapsuleParser`, buffer ceiling) and `qpackDecode` (encoder stream + field section + pseudo-headers) in `kuicksilver-http3/src/jvmTest/…/fuzz`, seeds from `tools/http3/gen-fuzz-seeds.py` (RFC 9204 appendix B); a 60 s run each (≈ 1.0 million, 16.3 million and 8.0 million inputs respectively, 2026-10-08) — no findings; `jvmTest` runs a regression mode on the seeds.

### 3.18 Fallback to TCP and protocol confusion (RFC 9308 §2, §17; RFC 9114 §10.2)

- **Threats:** an h3 → h1.1 fallback with weakened verification; cross-protocol attacks through ALPN.
- **Mitigations:** the fallback uses the same `TrustConfig`, the same pins and TLS 1.3; ALPN strictly `h3`/`http/1.1`, a mismatch → `no_application_protocol`.
- **Verification:** `negative_fallbackKeepsPins`, `negative_alpnMismatchClosesConnection`.

K5 status (Alt-Svc): the client engine learns `Alt-Svc` only from responses over TLS verified by its `TrustConfig`; a response over `http://` does not set an alternative, a 421 removes it (`AltSvcTest.negative_altSvcFromUnverifiedTls`, `.status421RemovesEntry`, `ClientAltSvcTest.plainHttpAltSvcIgnored`); when an alternative is used, SNI and certificate verification follow the origin.

K7 status (Alt-Svc state bounds, RFC 7838 §9.4): what servers can make the client remember is bounded — at most 8 alternatives per origin (`AltSvcTest.negative_altSvcEntriesPerOriginCapped`), at most 1000 origins in `InMemoryAltSvcStore` and `FileAltSvcStore`, the least recently used dropped first, and no more than 8000 records read back from the file (`FileAltSvcStoreTest.negative_altSvcStoreBoundedOrigins`); broken-alternative marks and the networks where QUIC worked are capped the same way (`BrokenAltSvcTest.negative_brokenMarksBounded`), and so is the per-origin RTT the race uses for its head start (`ClientAltSvcTest.srttMapBounded`). The file is written after the engine's lock is released, so a slow disk does not stall requests, and an older snapshot never overwrites a newer one (`FileAltSvcStoreTest.writesBehindTheCacheAreDeferredAndOrdered`); a repeated header is not rewritten (`identicalPutDoesNotRewrite`, `refreshedExpiryRewrittenOnlyPastHalfLifetime`).

K5 status (fallback): the fallback from HTTP/3 to HTTP/1.1 uses the same `TlsConfig` (trust, pins, TLS 1.3): with h3 unavailable and a pin that does not match the server key, the request ends with `TlsException` rather than succeeding over TCP (`ClientFallbackTest.negative_fallbackKeepsPins`); ALPN on TCP is strictly `http/1.1`, on QUIC `h3` (a mismatch — `no_application_protocol`, `negative_alpnMismatchClosesConnection` — K1); a non-idempotent request that went out over h3 is not retried over h1.1 (`nonIdempotentNotRetriedAfterHeadersSent`).

### 3.19 Bind and connect misdirection on Kotlin/Native TCP

- **Threats:** a server connector meant for one address (a loopback-only admin endpoint on `::1`) listens on every interface; a client request meant for a remote IPv6 host is delivered to a local process that holds the same port (cleartext `http://` is answered by it; with TLS, host-name verification fails). Ktor 3.6.0's Kotlin/Native `ktor-network` did both: it binds and connects every IPv6 address as `::` (`NativeIPv6SocketAddress.nativeAddress` never copies the address, [ktor-native-ipv6.md](../upstream/ktor-native-ipv6.md)); dual-stack on Linux and Apple, a `::1` connector also accepted IPv4.
- **Mitigations:** the engines' TCP sockets come from `kuicksilver-ktor-network` (`bindTcp`, `connectTcp`): on Kotlin/Native they pass the `sockaddr` from `getaddrinfo` to `bind`/`connect` unchanged (on the JVM and Android `ktor-network` is correct and used as it is). The portable Native UDP socket, still on `ktor-network`, fails closed: it refuses a specific IPv6 bind address and IPv6 destinations instead of using `::`.
- **Verification:** `ServerH1Test.negative_ipv6ConnectorListensOnItsAddressOnly` (an IPv4 connect to a `::1` connector's port is refused), `ClientH1Test.negative_h1ToIpv6LiteralReachesThatAddressOnly` (a request to `[::ffff:127.0.0.1]`, where nothing listens, does not reach the `::1` server), `TcpSocketsTest.negative_ipv6ListenerDoesNotAcceptIpv4`, `TcpSocketsTest.negative_connectToAnotherIpv6AddressDoesNotReachTheListener`, `KtorDatagramIoTest.negative_portableRefusesASpecificIpv6Address`, `.negative_portableRefusesIpv6Destinations`; positive: `ClientH1Test.plainHttpToIpv6Literal`, `ClientH3Test.h1ToIpv6Loopback` (also on Windows Native, where the connect to `::` was refused), `TcpSocketsNativeTest`.

## 4. What we do not protect against

- Traffic analysis by sizes/timings (no padding in v1 except Initial); DATAGRAM frames are distinguishable by their reaction to loss.
- Correlation by address on a migration without a CID change on the peer's side; the routing field in the server CID is sent in clear (encryption later).
- An on-path attacker aborting the handshake (RFC 9000 §21.1.1.3) — an accepted risk.
- Linking sessions of one client through TCP-TLS tickets (RFC 9001 §9.1).
- Attacks on OpenSSL itself (we track CVEs) and side channels on the host.
