# RFC 9001 — Using TLS to Secure QUIC

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="tls-1-3-in-quic-keys"></a>TLS 1.3 in QUIC, keys, header protection, key update, Retry tag

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9001.

**Requirement.** TLS 1.3 in QUIC, keys, header protection, key update, Retry tag.

Quoted: "the endpoint MUST stop using those keys"; "MUST NOT exceed the limits when sending early data".

**Recorded status.** ✅ 0.2.0

**How it is met.**

- `QuicTlsSession`/`PacketProtector` over `ksl`
- appendices A.1–A.6 byte for byte (`RfcVectorsTest`, C `test_key.c`), key update `next()`, Retry tag/A.2
- ✅ 0.2.0 §6 key update in `ConnectionCore`: the next phase's keys are derived when the current ones are installed (§9.5), the previous read keys live until a packet of the new phase authenticated and 3 × PTO after it (§6.1 MUST; 0.2.0 review: after our own update the window used to start at the update, so an idle connection lost the peer's old-phase packets — `core.KeyUpdateTest.ownUpdateKeepsOldReadKeyUntilNewPhaseArrives`), the HP key is shared (§5.4), the first update — after the handshake is confirmed, the following ones — after an ACK of a packet of the current phase (§6.1) and 3 × PTO after that ACK (§6.5 SHOULD, 0.2.0: `nextUpdateWaitsThreePtoAfterConfirmingAck`), KEY_UPDATE_ERROR on a repeated peer update without our ACK (§6.2 MAY)
- §6.4 (0.3.0 red-team finding): "Packets with higher packet numbers MUST be protected with either the same or newer packet protection keys than packets with lower packet numbers. An endpoint that successfully removes protection with old keys when newer keys were used for packets with lower packet numbers MUST treat this as a connection error of type KEY_UPDATE_ERROR." `KeyPhase` keeps the lowest and highest packet number opened with the current keys, the highest opened with any older generation and the highest opened with a generation older than the previous one, and every opened packet is checked against them in either order of arrival: newer keys below a packet number older keys opened, and older keys above one newer keys opened (the previous keys are only tried below the current phase, §6.5); one packet number opened under two keys is KEY_UPDATE_ERROR as well, by RFC 9000 §12.3 ("A QUIC endpoint MUST NOT reuse a packet number within the same packet number space"), not by §6.4. Until 0.3.0 a new phase was compared only with the lowest packet number of the current one, and a current-phase packet lowered that number unchecked — `core.RedTeamKeyPhaseTest.*`, `core.KeyPhaseOrderingTest.*` (consecutive updates, reuse of a packet number, honest reordering), and `core.KeyPhasePropertyTest.keyPhaseMatchesTheModel`: 3000 random runs against a model that searches the whole history (key choice, §6.4 and §6.2 errors, §6.1/§6.5 permission to initiate, the 3 × PTO retention of the old read keys); honest-peer runs must never end in an error
- §6.2 MAY, taken (0.3.0): an ACK frame in a packet opened with the previous keys that acknowledges a packet we protected with the current keys is KEY_UPDATE_ERROR (the peer acknowledged an update without updating) — `core.KeyPhaseOrderingTest.negative_ackOfNewPhaseCarriedWithOldKeys`
- §6 "Endpoints MUST NOT send a TLS KeyUpdate message. Endpoints MUST treat the receipt of a TLS KeyUpdate message as a connection error of type 0x010a": the transport reads the handshake message headers of the 1-RTT CRYPTO stream and closes with 0x010a on a KeyUpdate before any TLS stack sees it (OpenSSL in QUIC mode also answers one with unexpected_message); `ksl_ssl_key_update` refuses a QUIC-mode session (0.3.0; it would have written one) — `core.TlsKeyUpdateMessageTest.*` (both directions, split across frames, Null and `KslQuicCrypto`), C `quic_tls_key_update_received_by_server` / `_by_client`
- AEAD limits §6.6: automatic update at 7/8 of the AES-GCM confidentiality limit (2^23); when no update is possible, the connection closes with AEAD_LIMIT_REACHED while 16 packets are still left under the key ("It is RECOMMENDED that endpoints immediately close the connection with a connection error of type AEAD_LIMIT_REACHED before reaching a state where key updates are not possible"), and once a key sealed as many packets as its limit nothing more is sealed with it, the CONNECTION_CLOSE and its repetitions in the closing state included ("MUST stop using those keys"). Until 0.3.0 the close came at the limit and its copies went out under the exhausted key, one per PTO while the peer kept sending (0.3.0 cross-review) — `core.AeadLimitsTest.negative_confidentialityLimitWithoutPossibleUpdateCloses`
- §5.3 cipher suites: QUIC takes TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384 and TLS_CHACHA20_POLY1305_SHA256; the QUIC config check refuses any other suite (TLS_AES_128_CCM_8_SHA256, which §5.3 excludes, and TLS_AES_128_CCM_SHA256, which §5.3 allows but QUIC packet protection here does not offer, nor its §6.6 limits of 2^21.5). Until 0.3.0 a CCM suite passed the check and the handshake failed once the suite was chosen (0.3.0 cross-review) — `tls.TlsConfigTest.negative_ccmRejectedInQuic`, `.ccm8RejectedInQuic`
- the 0-RTT key, which cannot be updated, counts its packets too and stops at its limit, the rest waiting for 1-RTT (RFC 9001 §6.6 "the endpoint MUST stop using those keys", and RFC 9846 §5.5 "MUST NOT exceed the limits when sending early data" since early data has no key update; 0.2.1 RFC review — `core.ZeroRttTest.negative_zeroRttStopsAtTheAeadLimit`)
- integrity limit 2^52 (AES-GCM) / 2^36 (ChaCha20) counted over the authentication failures of every key, Initial included (§6.6 "across all keys"; 0.2.1 RFC review: Initial failures did not count — `core.AeadLimitsTest.initialAeadFailuresCount`), after which no packet is processed any more (0.2.0) — `core.AeadLimitsTest.*` (6 tests, including `negative_integrityLimit`, `negative_noPacketProcessedAfterIntegrityLimit`)
- §5.7 (0.2.1 RFC review): a server holds a client's 1-RTT packets that arrive before the handshake completes (the TLS stack gives it the 1-RTT read key before the client's Finished is verified) with the packets waiting for keys, and processes them once the Finished is verified
- a Finished that fails leaves them unused
- they share the 32-packet cap of packets waiting for keys (`QuicLimits.undecryptablePackets`), the rest is dropped and resent by the client's loss recovery, and a datagram of held packets is no Stateless Reset candidate — `core.HandshakeTest.negative_serverDefersOneRttUntilFinished`, `.heldOneRttBeyondTheCapIsDroppedAndResent`, `.heldOneRttPacketIsNoStatelessResetCandidate`
- the OpenSSL 3.5 QUIC interface is confirmed on cinterop and JNI

**Tests that pin it.**

- ✅ 0.2.0 (handshake in the transport — `core.HandshakeTest.*`, `crypto.*`)
- a peer's first update that arrives before any packet of phase 0 was processed is taken as the update (§6.2; 0.2.1 RFC review, it was KEY_UPDATE_ERROR — `core.KeyUpdateTest.firstPeerPacketMayAlreadyBeInTheNextPhase`) — `core.KeyUpdateTest.*` (12 tests, Null and `KslQuicCrypto`, AES-128/AES-256/ChaCha20), `crypto.PacketProtectionTest.splitUnprotectEqualsK2Unprotect`, `.keyPhaseBitReadableAfterHeaderProtectionRemoved`
- §8.2 (0.2.0): no quic_transport_parameters → 0x016d — `core.HandshakeTest.negative_missingTransportParametersIsMissingExtension`
- §8.4 (0.2.0): a ClientHello with a legacy_session_id → PROTOCOL_VIOLATION — `core.HandshakeTest.negative_clientHelloWithLegacySessionIdIsProtocolViolation`
- `QuicConnection.keyUpdate()` waits for the §6.1 and §6.5 permission — `api.QuicApiTest.keyUpdateSuspendsUntilConfirmedThenUpdates`
- interop `keyupdate` — `HqInteropTest.keyupdateTestcaseInitiatesUpdate` and the runner matrix

**Peer interop notes.**

- §4.1.3 (0.2.0 review, was a pre-authentication memory sink): the Initial CRYPTO stream is sealed when TLS reads Handshake and the Handshake stream at handshake completion, data past a sealed stream's end or a gap left at a key change is PROTOCOL_VIOLATION, the Initial stream ends at 64 KiB and the Handshake one at 256 KiB (CRYPTO_BUFFER_EXCEEDED, as ngtcp2), `ksl` refuses data below its read level and holds at most 256 KiB unread per level, which counts toward admission's handshake buffer — `core.HandshakeLimitsTest.negative_cryptoPastEndOfPreviousLevel`, `.negative_cryptoGapAtKeyChange`, `.negative_cryptoInitialLevelCap`, `.unreadTlsInputCountsTowardHandshakeBuffer`, C `quic_crypto_at_previous_level_refused`, `quic_crypto_level_buffer_capped`

## <a id="s4-6-0-rtt"></a>§4.6, §4.6.1–4.6.3 — 0-RTT

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9001 §4.6, §4.6.1–4.6.3.

**Requirement.** 0-RTT.

Quoted: "MUST reset the state of all streams".

**Recorded status.** ✅ 0.2.0 (opt-in, ADR-0015)

**How it is met.**

- `QuicClientConfig.earlyData`, `QuicServerConfig.earlyData`, `QuicEndpoint.connectEarly`
- tickets with `max_early_data` 0xffffffff (another value received → PROTOCOL_VIOLATION, §4.6.1, 0.2.0: OpenSSL's illegal_parameter is mapped — `core.ZeroRttTest.negative_invalidMaxEarlyDataIsProtocolViolation`; a ticket without the extension allows no 0-RTT, also one renewed on a resumption of a 0-RTT ticket, 0.3.0: "To indicate that the server does not accept 0-RTT data, the early_data extension is omitted from the NewSessionTicket" — C `negative_quic_renewed_ticket_without_early_data_refuses_0rtt`, `QuicEarlyDataTest.negative_renewedTicketWithoutEarlyDataCarriesNo0Rtt`; a server's SNI override keeps the sentinel, or omits the extension when it accepts no 0-RTT — C `quic_sni_override_keeps_early_data`), bound to a digest of ALPN, transport limits and application settings and to the QUIC version (RFC 9369 §5, 0.2.0: a ticket belongs to the negotiated version of its connection; neither the client nor the server resumes it for a connection started in another version — `core.ZeroRttTest.negative_ticketOfAnotherVersionIsNotUsed`, C `quic_ticket_bound_to_its_version`)
- its `QuicStream` fails with `QuicException.StreamError.EarlyDataRejected` and the application sends again on new streams (`ZeroRttRejected` closes the connection only for another ALPN or under `Required`)
- a stream reset in 0-RTT before the answer and whose reset the server never acknowledges keeps nothing beyond the answer: at an acceptance its size stands and its wrapper goes, as for a stream reset in 1-RTT; at a rejection it fails with `EarlyDataRejected` and goes, and nothing of it waits for an acknowledgment (0.3.0: after an acceptance the wrapper stayed until the acknowledgment or the connection's end) — `api.ZeroRttApiTest.acceptedEarlyStreamsResetAndNeverAcknowledgedLetTheirWrappersGo`, `.negative_rejectedEarlyStreamsResetAndNeverAcknowledgedFailAndGo`, `core.ZeroRttTest.earlyStreamRetiredBeforeTheAnswerIsOfferedAgainAtTheAcceptance`
- a stream opened before the runtime learnt of the rejection is a stream of its own (0.2.1 review: it got the dropped stream's wrapper, and a reset of the early stream reached it) — `api.ZeroRttApiTest.streamOpenedBeforeTheRuntimeSawTheRejectionIsItsOwn`
- §4.6.2 "When 0-RTT is rejected, ... a client SHOULD treat receipt of an acknowledgment for a 0-RTT packet as a connection error of type PROTOCOL_VIOLATION, if it is able to detect the condition": the client keeps the packet numbers of its first and last 0-RTT packet (0-RTT stops once the 1-RTT key exists, so every 1-RTT packet numbers above them), and after a rejection an ACK frame that covers any of them closes the connection with PROTOCOL_VIOLATION (0.3.0 cross-review) — `core.ZeroRttTest.negative_ackOfARejectedZeroRttPacketIsProtocolViolation` (the check, and a server's ACK frame of those packet numbers closing the client end to end)
- §4.6.2 "A server will always reject 0-RTT if it sends a TLS HelloRetryRequest", 0.3.0: a client's second ClientHello goes at the Initial level (§4.1.4; OpenSSL drops its write keys to none on the HelloRetryRequest without telling the QUIC callbacks, so `ksl_quic.c` takes the level from the message) and without `early_data` (RFC 9846 §4.2.2; the connection offers its own copy of the session, whose `max_early_data` `ksl_msg_cb` clears on the HelloRetryRequest), and no second 0-RTT key is handed out — C `negative_quic_early_data_rejected_after_hello_retry_request`
- the HTTP/3 client sends SETTINGS in 0-RTT, opens its control and QPACK streams again after a rejection (only if the rejection dropped them) and sends SETTINGS once more, then the control frames of the dropped stream still wanted (a GOAWAY), emits no QPACK Stream Cancellation for the dropped early requests, and repeats each early request once (a safe method, RFC 9110 §9.2.2)
- the client in 0-RTT holds the server's 1-RTT packets until the handshake's end settled the 0-RTT, as ngtcp2's client buffers them until its handshake completed (0.3.0, CI run 45756922960 review): a rejection resets our streams and limits first, and the server's 0.5-RTT frames are read after it, so its MAX_DATA and MAX_STREAMS are no longer lost to the reset, an ACK of a rejected 0-RTT packet in that flight is a PROTOCOL_VIOLATION (it was taken as an acknowledgment before), and the runtime hands a server's stream out only with `earlyDataAccepted` settled — `core.ZeroRttTest.aServerStreamOfTheHalfRttFlightIsReportedAfterTheRejection`, `.halfRttMaxDataAndMaxStreamsSurviveTheRejection`, `.negative_aHalfRttAckOfARejectedZeroRttPacketIsProtocolViolation`, `.anAcceptedZeroRttReadsTheHalfRttFlightAfterTheAcceptance`
- the HTTP/3 client hands its critical streams to writers only once the attempt that opened them is still current (0.3.0, CI run 45756922960): a rejection noted while the first attempt, opened in 0-RTT, waited to report its streams open superseded it, and it reported them anyway; our encoder's Set Dynamic Table Capacity, made for the next generation once the server's SETTINGS arrived, met no streams (`critical == null`) and was dropped, and the server closed with QPACK_ENCODER_STREAM_ERROR (RFC 9204 §3.2.3). A superseded attempt now leaves the streams to the next one, a write for a generation whose streams are not open yet waits for them (decoder-stream bytes too), and encoder instructions made for a dropped encoder stream close the connection with H3_INTERNAL_ERROR instead of going silently — `runtime.EarlyDataTest.aRejectionNotedAsTheFirstAttemptEndsLeavesTheStreamsToTheNextOne`, `.negative_encoderInstructionsForADroppedGenerationFailTheConnection`
- defence in depth: the HTTP/3 client reads no stream of the server before it knows the server's answer to its 0-RTT, against a transport that would hand one out earlier (ours does not, see the row above); the wait ends with the connection — `runtime.EarlyDataTest.aServerStreamTakenBeforeTheRejectionIsReportedWaitsForIt`, `.negative_aServerStreamWaitingForTheAnswerEndsWithTheConnection`

**Tests that pin it.**

- across a compatible upgrade 0-RTT stays in the original version on both sides (RFC 9369 §4.1, 0.2.0 — `core.ZeroRttTest.zeroRttStaysInTheOriginalVersionAcrossAnUpgrade`, C `quic_early_key_in_original_version_after_upgrade`)
- `core.ZeroRttTest.zeroRttRejectedResetsStreams`, `.rejectedWithSmallerLimitsResetsStreamsAndContinues`, `api.ZeroRttApiTest.rejectedZeroRttFailsEarlyStreamsAndTheConnectionGoesOn`, HTTP/3 `runtime.EarlyDataTest.earlyRequestIsSentAgainAfterRejection`, `.rejectedZeroRttReopensTheControlAndQpackStreams`, `.aRejectionNotedAsTheFirstAttemptEndsLeavesTheStreamsToTheNextOne`, `.aServerStreamTakenBeforeTheRejectionIsReportedWaitsForIt`, `.negative_aServerStreamWaitingForTheAnswerEndsWithTheConnection`, `.negative_encoderInstructionsForADroppedGenerationFailTheConnection`, `core.ZeroRttTest.aServerStreamOfTheHalfRttFlightIsReportedAfterTheRejection`, `.halfRttMaxDataAndMaxStreamsSurviveTheRejection`, `.negative_aHalfRttAckOfARejectedZeroRttPacketIsProtocolViolation`, `core.ZeroRttTest.*`, `api.ZeroRttApiTest.*`, `endpoint.ZeroRttEndpointTest.zeroRttBeforeInitialIsBuffered`, `tls.QuicEarlyDataTest.*`, C `test_early.c`
- the runner's `resumption` and `zerortt` cases green against all six peers in both roles ([Interop matrix, 0.2.0](../interop.md#interop-matrix-020-quic-interop-runner-740c05a-2026-10-13))

**Peer interop notes.**

- 0-RTT streams reset before the answer (0.3.0): quic-go keeps a reset `SendStream` until its RESET_STREAM is acknowledged (`send_stream.go:558`, `:952-971`) and does nothing to its streams at an acceptance, only drops the 0-RTT sealer (`internal/handshake/crypto_setup.go:528-529`); ngtcp2 closes a stream only once the RESET_STREAM is acknowledged (`ngtcp2_conn.c:13191-13198`, `ngtcp2_rtb.c:700-708`) and at an acceptance only discards the early key, when the 1-RTT read key is installed (`ngtcp2_conn_install_rx_key`, `ngtcp2_conn.c:11408-11421`); quiche drops the send buffer at the reset (`stream/send_buf.rs:492-506`) and collects the stream when the RESET_STREAM is acknowledged (`lib.rs:3756-3758`). All three send a lost RESET_STREAM again from the frame's own fields (quic-go `send_stream.go:973-986`, ngtcp2 `ngtcp2_rtb.c:361-366`, quiche `lib.rs:4320-4326`), as we do; our core keeps only the stream's ID for the acknowledgment, and the runtime's wrapper (channels, ticker) goes at retirement, or, for a stream whose size waits for the 0-RTT answer, at an acceptance. At a rejection quic-go (`connection.go:2336-2339`, `streams_map.go:361-368`) and ngtcp2 (`conn_discard_early_data_state`, `ngtcp2_conn.c:13439-13468`) drop every stream, as we do; quiche only calls `SSL_reset_early_data_reject` (`tls/mod.rs:656-659`)
- §4.6.2, 0.2.1: a rejection resets the state of all streams ("MUST reset the state of all streams") — every stream the client opened is dropped without a frame, its ID, credit and the stream counts start over from the server's new transport parameters (RFC 9000 §7.4.1), as ngtcp2 (`conn_discard_early_data_state`) and quic-go (`streamsMap.ResetFor0RTT`)

## <a id="s4-9-3-discarding-0-rtt-keys"></a>§4.9.3 — discarding 0-RTT keys

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9001 §4.9.3.

**Requirement.** Discarding 0-RTT keys.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- the client drops the 0-RTT key with the 1-RTT key, the server 3 PTO after the first 1-RTT packet
- refused 0-RTT packets are never processed

**Tests that pin it.**

- `core.ZeroRttTest.zeroRttDataAnsweredBeforeHandshakeCompletes`, `zeroRttRejectedResetsStreams`
