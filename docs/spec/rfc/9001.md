# RFC 9001 — Using TLS to Secure QUIC

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="tls-1-3-in-quic-keys"></a>TLS 1.3 in QUIC, keys, header protection, key update, Retry tag

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9001.

**Requirement.** TLS 1.3 in QUIC, keys, header protection, key update, Retry tag.

Quoted: "the endpoint MUST stop using those keys"; "MUST NOT exceed the limits when sending early data".

**Recorded status.** ✅ 0.2.0

**How it is met.**

- `QuicTlsSession`/`PacketProtector` over `ksl`
- appendices A.1–A.6 byte for byte (`RfcVectorsTest`, C `test_key.c`), key update `next()`, Retry tag/A.2
- ✅ 0.2.0 §6 key update in `ConnectionCore`: the next phase's keys are derived when the current ones are installed (§9.5), the previous read keys live until a packet of the new phase authenticated and 3 × PTO after it (§6.1 MUST; 0.2.0 review: after our own update the window used to start at the update, so an idle connection lost the peer's old-phase packets — `core.KeyUpdateTest.ownUpdateKeepsOldReadKeyUntilNewPhaseArrives`), the HP key is shared (§5.4), the first update — after the handshake is confirmed, the following ones — after an ACK of a packet of the current phase (§6.1) and 3 × PTO after that ACK (§6.5 SHOULD, 0.2.0: `nextUpdateWaitsThreePtoAfterConfirmingAck`), KEY_UPDATE_ERROR when a packet opens only with the next keys although its number is below the lowest of the current phase (a check stricter than the RFC: the §6.4 MUST, about old keys and a higher packet number, cannot arise since `KeyPhase.readKey` never tries old keys above the current phase) and on a repeated peer update without our ACK (§6.2 MAY)
- AEAD limits §6.6: automatic update at 7/8 of the AES-GCM confidentiality limit (2^23), AEAD_LIMIT_REACHED if an update is impossible
- the 0-RTT key, which cannot be updated, counts its packets too and stops at its limit, the rest waiting for 1-RTT (RFC 9001 §6.6 "the endpoint MUST stop using those keys", and RFC 9846 §5.5 "MUST NOT exceed the limits when sending early data" since early data has no key update; 0.2.1 RFC review — `core.ZeroRttTest.negative_zeroRttStopsAtTheAeadLimit`)
- integrity limit 2^52 (AES-GCM) / 2^36 (ChaCha20) counted over the authentication failures of every key, Initial included (§6.6 "across all keys"; 0.2.1 RFC review: Initial failures did not count — `core.AeadLimitsTest.initialAeadFailuresCount`), after which no packet is processed any more (0.2.0) — `core.AeadLimitsTest.*` (6 tests, including `negative_integrityLimit`, `negative_noPacketProcessedAfterIntegrityLimit`)
- §5.7 (0.2.1 RFC review): a server holds a client's 1-RTT packets that arrive before the handshake completes (the TLS stack gives it the 1-RTT read key before the client's Finished is verified) with the packets waiting for keys, and processes them once the Finished is verified
- a Finished that fails leaves them unused
- they share the 32-packet cap of packets waiting for keys (`QuicLimits.undecryptablePackets`), the rest is dropped and resent by the client's loss recovery, and a datagram of held packets is no Stateless Reset candidate — `core.HandshakeTest.negative_serverDefersOneRttUntilFinished`, `.heldOneRttBeyondTheCapIsDroppedAndResent`, `.heldOneRttPacketIsNoStatelessResetCandidate`
- the OpenSSL 3.5 QUIC interface is confirmed on cinterop and JNI

**Tests that pin it.**

- ✅ 0.2.0 (handshake in the transport — `core.HandshakeTest.*`, `crypto.*`)
- a peer's first update that arrives before any packet of phase 0 was processed is taken as the update (§6.2; 0.2.1 RFC review, it was KEY_UPDATE_ERROR — `core.KeyUpdateTest.firstPeerPacketMayAlreadyBeInTheNextPhase`) — `core.KeyUpdateTest.*` (12 tests, Null and `KslQuicCrypto`, AES-128/AES-256/ChaCha20), `crypto.PacketProtectionTest.splitUnprotectEqualsK2Unprotect`, `.keyPhaseBitReadableAfterHeaderProtectionRemoved`
- §8.2 (0.2.0): no quic_transport_parameters → 0x016d — `core.HandshakeTest.negative_missingTransportParametersIsMissingExtension`
- §8.4 (0.2.0): a ClientHello with a legacy_session_id → PROTOCOL_VIOLATION — `core.HandshakeTest.negative_clientHelloWithLegacySessionIdIsProtocolViolation`
- `QuicConnection.keyUpdate()` waits for the §6.1 and §6.5 permission — `api.QuicApiTest.keyUpdateSuspendsUntilConfirmedThenUpdates`
- interop `keyupdate` — `HqInteropTest.keyupdateTestcaseInitiatesUpdate` and the runner matrix

**Peer interop notes.**

- §4.1.3 (0.2.0 review, was a pre-authentication memory sink): the Initial CRYPTO stream is sealed when TLS reads Handshake and the Handshake stream at handshake completion, data past a sealed stream's end or a gap left at a key change is PROTOCOL_VIOLATION, the Initial stream ends at 64 KiB and the Handshake one at 256 KiB (CRYPTO_BUFFER_EXCEEDED, as ngtcp2), `ksl` refuses data below its read level and holds at most 256 KiB unread per level, which counts toward admission's handshake buffer — `core.HandshakeLimitsTest.negative_cryptoPastEndOfPreviousLevel`, `.negative_cryptoGapAtKeyChange`, `.negative_cryptoInitialLevelCap`, `.unreadTlsInputCountsTowardHandshakeBuffer`, C `quic_crypto_at_previous_level_refused`, `quic_crypto_level_buffer_capped`

## <a id="s4-6-0-rtt"></a>§4.6, §4.6.1–4.6.3 — 0-RTT

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9001 §4.6, §4.6.1–4.6.3.

**Requirement.** 0-RTT.

Quoted: "MUST reset the state of all streams".

**Recorded status.** ✅ 0.2.0 (opt-in, ADR-0015)

**How it is met.**

- `QuicClientConfig.earlyData`, `QuicServerConfig.earlyData`, `QuicEndpoint.connectEarly`
- tickets with `max_early_data` 0xffffffff (another value received → PROTOCOL_VIOLATION, §4.6.1, 0.2.0: OpenSSL's illegal_parameter is mapped — `core.ZeroRttTest.negative_invalidMaxEarlyDataIsProtocolViolation`), bound to a digest of ALPN, transport limits and application settings and to the QUIC version (RFC 9369 §5, 0.2.0: a ticket belongs to the negotiated version of its connection; neither the client nor the server resumes it for a connection started in another version — `core.ZeroRttTest.negative_ticketOfAnotherVersionIsNotUsed`, C `quic_ticket_bound_to_its_version`)
- its `QuicStream` fails with `QuicException.StreamError.EarlyDataRejected` and the application sends again on new streams (`ZeroRttRejected` closes the connection only for another ALPN or under `Required`)
- a stream opened before the runtime learnt of the rejection is a stream of its own (0.2.1 review: it got the dropped stream's wrapper, and a reset of the early stream reached it) — `api.ZeroRttApiTest.streamOpenedBeforeTheRuntimeSawTheRejectionIsItsOwn`
- the HTTP/3 client sends SETTINGS in 0-RTT, opens its control and QPACK streams again after a rejection (only if the rejection dropped them) and sends SETTINGS once more, then the control frames of the dropped stream still wanted (a GOAWAY), emits no QPACK Stream Cancellation for the dropped early requests, and repeats each early request once (a safe method, RFC 9110 §9.2.2)

**Tests that pin it.**

- across a compatible upgrade 0-RTT stays in the original version on both sides (RFC 9369 §4.1, 0.2.0 — `core.ZeroRttTest.zeroRttStaysInTheOriginalVersionAcrossAnUpgrade`, C `quic_early_key_in_original_version_after_upgrade`)
- `core.ZeroRttTest.zeroRttRejectedResetsStreams`, `.rejectedWithSmallerLimitsResetsStreamsAndContinues`, `api.ZeroRttApiTest.rejectedZeroRttFailsEarlyStreamsAndTheConnectionGoesOn`, HTTP/3 `runtime.EarlyDataTest.earlyRequestIsSentAgainAfterRejection`, `.rejectedZeroRttReopensTheControlAndQpackStreams`, `core.ZeroRttTest.*`, `api.ZeroRttApiTest.*`, `endpoint.ZeroRttEndpointTest.zeroRttBeforeInitialIsBuffered`, `tls.QuicEarlyDataTest.*`, C `test_early.c`
- the runner's `resumption` and `zerortt` cases green against all six peers in both roles ([Interop matrix, 0.2.0](../interop.md#interop-matrix-020-quic-interop-runner-740c05a-2026-10-13))

**Peer interop notes.**

- §4.6.2, 0.2.1: a rejection resets the state of all streams ("MUST reset the state of all streams") — every stream the client opened is dropped without a frame, its ID, credit and the stream counts start over from the server's new transport parameters (RFC 9000 §7.4.1), as ngtcp2 (`conn_discard_early_data_state`) and quic-go (`streamsMap.ResetFor0RTT`)

## <a id="s4-9-3-discarding-0-rtt-keys"></a>§4.9.3 — discarding 0-RTT keys

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9001 §4.9.3.

**Requirement.** Discarding 0-RTT keys.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- the client drops the 0-RTT key with the 1-RTT key, the server 3 PTO after the first 1-RTT packet
- refused 0-RTT packets are never processed

**Tests that pin it.**

- `core.ZeroRttTest.zeroRttDataAnsweredBeforeHandshakeCompletes`, `zeroRttRejectedResetsStreams`
