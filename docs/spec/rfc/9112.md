# RFC 9112 — HTTP/1.1

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="http-1-1"></a>HTTP/1.1

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9112.

**Requirement.** HTTP/1.1.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- server ✅: the connection pipeline vendored from `ktor-server-cio` (`h1/ServerPipeline.kt`) over TLS 1.3 (`kuicksilver-ktor-network`), keep-alive, chunked, `100-continue`, ALPN `http/1.1` — `ServerH1Test.*`, `SslConnectorBridgeTest.*`
- client ✅: request writing and response parsing — vendored code of the Ktor 3.6.0 CIO client over `TlsConnection`, keep-alive with a pool, a CONNECT tunnel through an HTTP proxy, `ConnectTimeoutException`/`SocketTimeoutException`, SSE, WebSocket (101 → `RawWebSocket`), interim 1xx (100 Continue, 103) are skipped until the final response, any number of them, bounded by bytes: 64 KiB of interim heads in all before one final response (0.2.1; before without a bound, then at most 5, which broke the §15.2 MUST) — RFC 9110 §15.2 (review: `informationalResponsesAreSkipped`, `continueResponseIsSkipped`, `h1.H1ResponseHeadTest.manyInterimResponsesAreSkipped`, `.negative_endlessInterimResponsesFail`)
- a response head larger than 64 KiB fails the request and closes the connection (0.2.1) — `ClientH1Test.*`
- a streamed request body goes out in parallel with reading the response, the socket timeout applies to every wait for data, including the body, and measures inactivity: a request body that keeps moving restarts it, so a long upload does not time out (0.2.1; before, it covered the whole wait for the response head, upload included) (`responseHeadersBeforeTheRequestBodyEnds`, `socketTimeoutCoversTheBody`, `h1.H1SocketTimeoutTest.*`, `InactivityTest.*`)
- the vendored Ktor 3.6.0 contract: client `contract.*` (93 tests × h1/h3), server `KuicksilverH1*` (81 tests: cleartext and TLS)

## <a id="s6-1-client-response-framing"></a>§6.1, §6.3, §7.1, §8, §9.6 — client response framing

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9112 §6.1, §6.3, §7.1, §8, §9.6 (client response framing).

**Requirement.** The client frames a response as §6.3 orders: HEAD, 1xx, 204, 304 without a body.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- a final `chunked` coding (with a trailer section, discarded per §7.1.2, at most 16 KiB; the chunk-size line strictly by §7.1: `1*HEXDIG`, extensions by their grammar, CRLF only, no whitespace right before it (BWS only before `;` and around `=`; 0.2.1, before tolerated) — a bare CR (§2.2) or bare LF fails the response, 0.2.1 review)
- another transfer coding or no framing at all → read until the server closes (item 4, item 8; the vendored Ktor CIO code failed the latter)
- Content-Length `1*DIGIT` of any length (leading zeros ignored, RFC 9110 §8.6: any value ≥ 0 is valid), identical repeated values accepted (§8.6), conflicting or invalid values fail the response and close the connection (item 5)
- a valid length of 10^18 or more is refused as this client's limit (`ParserException` naming the limit; 0.2.1 review, before any value over 18 characters was invalid)
- Content-Length with Transfer-Encoding is framed by the coding and the connection is not reused (item 3)
- an HTTP/1.0 response with Transfer-Encoding has faulty framing even with a Content-Length (§6.1 MUST): neither field frames it, the body is read as sent until the server closes (item 8) and the connection is closed (0.2.1 review; before, its chunked coding was decoded)
- a body cut before its framing ends is incomplete (§8) and fails, and so does a head cut before its empty line, the proxy's CONNECT response included, with `ClosedReadChannelException` so an idempotent request keeps its stale-connection retry (0.2.1 review; before, Ktor's parser took it for a complete head without fields)
- a request with `Connection: close` is the last on its connection (§9.6)

**Tests that pin it.**

- `ClientH1FramingTest.*`, `h1.ChunkedBodyTest.*`, `ClientH1FramingTest.negative_whitespaceBeforeTheChunkLineEndFails`, `h1.H1ResponseHeadTest.negative_headCutBeforeTheEmptyLineFails`, `.negative_connectHeadCutBeforeTheEmptyLineFails`, `ClientH1FramingTest.http10ResponseWithTransferEncodingIsCloseDelimited`

## <a id="s6-1-client-request-framing"></a>§6.1, §6.2 — client request framing

Status: 🔶 since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9112 §6.1, §6.2 (client request framing).

**Requirement.** A request body is framed by Content-Length when it has a length and no transfer coding, else chunk-encoded.

**Recorded status.** 🔶 0.2.1 (§6.1 first contact: ⬜ 0.3.0)

**How it is met.**

- a coding the application sets (`Transfer-Encoding` of the request or of its `OutgoingContent`) goes first and `chunked` is added as the final coding (§6.1 MUST), and Content-Length is then not sent (§6.2 MUST NOT; 0.2.1 review: before, `Transfer-Encoding: gzip` went out over a chunk-encoded body, and with a length both fields went out)

**Tests that pin it.**

- `ClientH1FramingTest.contentTransferEncodingEndsWithChunked`, `ClientH1Test.postAndChunked`

**Open items.**

- open (⬜ 0.3.0), §6.1 MUST NOT "send a request containing Transfer-Encoding unless it knows the server will handle HTTP/1.1 requests": not met yet — a request whose body needs a transfer coding (a streamed body of unknown length, or a coding the application sets) is sent chunked on the first contact with a server too, before any response or ALPN `http/1.1` showed that it handles HTTP/1.1
- planned: remember the version per route (ALPN, prior responses) and, while it is unknown, frame the body by Content-Length from a bounded buffer

## <a id="s6-1-server-request-framing"></a>§6.1, §6.3, §7.1 — server request framing

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9112 §6.1, §6.3, §7.1 (server request framing).

**Requirement.** The server frames a request as §6.3 orders: a final `chunked` coding (trailer section accepted and discarded, at most 16 KiB; the chunk-size line strictly by §7.1 — `1*HEXDIG`, extensions by their grammar, CRLF only, no whitespace right before it (BWS only before `;` and around `=`; 0.2.1, before tolerated); a bare CR (§2.2), a bare LF or a quote outside an extension → the handler's receive fails with `BadRequestException` (Ktor's 400) and the connection closes; before 0.2.1 a CR was skipped anywhere in the line), else Content-Length (`1*DIGIT` of any length, leading zeros ignored, identical repeats are one length; a valid length of 10^18 or more gets `413 Content Too Large` and close, RFC 9110 §8.6 "Any Content-Length field value greater than or equal to zero is valid" and §15.5.14; 0.2.1 review, before 400), else no body — also for a POST with `Connection: close` (item 7; Ktor CIO read such a request to EOF).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- Content-Length with Transfer-Encoding (§6.1: the server MUST close after responding — refused with 400 and close; before 0.2.0 the next bytes were served as a second, smuggled request), Transfer-Encoding in HTTP/1.0, a final coding other than `chunked` (also `chunked, identity` and `identity` alone: `identity` is no transfer coding since RFC 7230 and is never dropped), `chunked` twice, invalid or conflicting Content-Length → 400 and close
- a coding the server does not implement before the final `chunked` (`gzip, chunked`, `identity, chunked`) → 501 and close (§6.1 SHOULD)
- §3.2: an HTTP/1.1 request without Host, or any request with more than one Host line → 400 and close (0.2.1; before, served with the first value)
- a Host value that is not `uri-host [":" port]` (RFC 3986 reg-name, IPv4, IP-literal; `port = *DIGIT`, so `a.example:` (the default port; Ktor's parser refused it, the head check hands it on without the colon) and digits up to 65535 are accepted, while a port above 65535 is no TCP port (RFC 9110 §4.2.1, §4.2.2) and is invalid; an empty Host is accepted) → 400 and close, and the same check for an absolute-form target's authority (0.2.1; before, Ktor's parser refused only `/?#@` and a trailing colon, so `a b`, `[::1`, `h:x` reached `serverHost`)

**Tests that pin it.**

- `ServerH1FramingTest.*` (including `negative_unimplementedTransferCodingGets501`, `negative_chunkedTwiceOrNotFinalIsRejected`, `negative_contentLengthWithTransferEncodingIsRejectedAndClosed`, `negative_bareCrInChunkSizeIsRejected`, `negative_whitespaceBeforeTheChunkLineEndIsRejected`, `negative_missingOrRepeatedHostIsRejected`, `negative_invalidHostIsRejected`, `validHostsAreServed`), `h1.ChunkedBodyTest.*`

## <a id="s2-3-server-request-line"></a>§2.3, §3, §3.1; RFC 9110 §6.2, §15.6.6 — server request line

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9112 §2.3, §3, §3.1; RFC 9110 §6.2, §15.6.6 (server request line).

**Requirement.** The request line is checked before Ktor's parser reads it: the method is a token (§3.1), the separators are SP, HTAB, VT, FF or a bare CR (§3 lets a server take them as SP), any other control character or a Unicode space (U+00A0, ...) anywhere in the line → 400 (so is a TLS ClientHello sent optimistically, which starts with 0x16, RFC 9931 §6.1).

**Recorded status.** ✅ 0.2.1

**How it is met.**

- the version is `"HTTP/" DIGIT "." DIGIT`, case-sensitive (§2.3), else 400
- whitespace before the method and after the version is ignored (§3 MAY)
- the request-target must match its form (§3.2): origin-form with RFC 3986 path and query characters, absolute-form (an absolute-URI, no fragment), authority-form for CONNECT only with a non-empty host (`CONNECT :443` names no tunnel destination, RFC 9110 §9.3.6) and a port 1–65535 (§9.3.6 MUST reject an empty or invalid port), asterisk-form for OPTIONS only

**Tests that pin it.**

- `h1.H1RequestHeadCheckTest.*` (including `negative_invalidRequestTargetGets400`, `negative_redirectNeverLeavesTheServer`, `negative_redirectOnlyForAnOtherwiseValidHead`, `invalidOriginFormOfGetIsRedirectedProperlyEncoded`, `validRequestTargetsAreServed`)

**Peer interop notes.**

- a higher minor version (HTTP/1.2) is processed as HTTP/1.1 (RFC 9110 §6.2 SHOULD; before 0.2.1, 400), another major version gets `505 HTTP Version Not Supported` with `Connection: close` and a `text/plain` body naming the versions the connection speaks (§15.6.6, including its SHOULD for a representation that says what is supported; before, 400), as Go's net/http
- an invalid one is an invalid request line → 400 and close (§3.2 SHOULD), or for a GET or HEAD whose origin-form target only has characters to encode (`|`, `{`, `^`, `[`, which browsers send unencoded because the WHATWG URL standard leaves them, non-ASCII bytes, a lone `%`) `301 Moved Permanently` to the target properly encoded, the other answer §3.2 names, sent only once the field section, its Host (§3.2) and framing (§6.3) are valid too (else their 400 or 501), with a Location that is an absolute-path reference to this server: a target whose Location could be a network-path reference (RFC 3986 §4.2: it starts with `//`, also once `%2F`, `%5C`, `%2E` are decoded, `\` is read as `/` and dot segments are removed) gets 400 instead (a 301 to `//evil.example/%5E` was an open redirect), and so does one with a raw `#` (encoded as `%23` it names another resource, RFC 3986 §2.2, so no encoding is proper) (0.2.1; before, any run of non-whitespace reached routing)

## <a id="s9-3-server-request-close"></a>§9.3, §9.6 — server request `close`

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9112 §9.3, §9.6 (server request `close`).

**Requirement.** A request whose Connection options include `close` (a list, any case, any of several lines; `close` wins over `keep-alive`) or an HTTP/1.0 request without `keep-alive` is the last on its connection, and its final response says `Connection: close` (§9.6 SHOULD; MUST close after it), the `close` added after the options the application listed (RFC 9110 §7.6.1: they name hop-by-hop fields; `keep-alive` dropped) (0.2.1; before, Ktor's `ConnectionOptions` read the first line only, took `keep-alive, close` as keep-alive and `Connection: TE` on HTTP/1.0 as keep-alive, and only a field of exactly `close` was announced).

**Recorded status.** ✅ 0.2.1

**Tests that pin it.**

- `ServerH1FramingTest.negative_connectionCloseInAListIsAnnouncedAndEndsTheConnection`, `ServerH1ResponseFramingTest.negative_closeIsAddedToTheApplicationsConnectionOptions`, `contract.HttpServerCommonTestSuite.testRequestTwiceNoKeepAlive`

## <a id="s9-3-2-server-pipelining"></a>§9.3.2 — server pipelining

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9112 §9.3.2 (server pipelining).

**Requirement.** Responses go out in request order.

Quoted: "MAY process ... in parallel if they all have safe methods".

**Recorded status.** ✅ 0.2.1

**How it is met.**

- the next pipelined request is read once the previous response head is out, the handlers of requests with safe methods (GET, HEAD, OPTIONS, TRACE) may then overlap, and a request with any other method runs alone: after every earlier handler has ended and before the next request is read ("MAY process ... in parallel if they all have safe methods") (0.2.1; before, a pipelined DELETE could run while the PUT before it was still running)

**Tests that pin it.**

- `h1.H1PipelineOrderTest.*`, `h1.H1PipelineFailedResponseTest.negative_aFailedPipelinedResponseIsNotSkipped`, `ServerH1Test.keepAliveTwoRequests`

## <a id="s4-server-status-line"></a>§4 — server status line

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9112 §4 (server status line).

**Requirement.** The status line is always `HTTP/1.1`.

**Recorded status.** ✅ 0.2.1

**Tests that pin it.**

- `ServerH1ResponseFramingTest.negative_invalidReasonPhraseIsReplaced`

**Peer interop notes.**

- an application's status description that is not a reason-phrase (`*( HTAB / SP / VCHAR / obs-text )`: CR, LF, NUL, other controls) is replaced by the registered reason of its code, or none for an unregistered code, as Netty refuses such a reason (0.2.1; before, written unchecked: `HttpStatusCode(200, "OK\r\nX: 1")` split the response)

## <a id="s9-6-server-staged-close"></a>§9.6 — server staged close

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9112 §9.6 (server staged close).

**Requirement.** A response that ends the connection while the client may still be sending (a 400, 414, 431, 501 or 505 refusal of the head or its framing, a malformed chunked body, a body left unread) is written and half-closed, then the input is read and dropped for up to 2 s before the close, or until the server stops (nginx `lingering_close`, Go's `closeWriteAndWait`), so the kernel does not reset the connection over unread input and destroy the response (0.2.1; before, only after a 431 and an abandoned body).

**Recorded status.** ✅ 0.2.1

**Tests that pin it.**

- `h1.H1PipelineRefusalLingerTest.negative_aRefusedRequestIsReadBeforeTheClose`, `h1.H1PipelineHeadLimitTest.*`, `h1.H1PipelineStopTest.lingerAfterARefusalEndsAtStop`
