# RFC 9218 — Extensible Prioritization Scheme for HTTP

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="priorities-transport-part-the-scheduler"></a>priorities (transport part: the scheduler)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9218.

**Requirement.** Priorities (transport part: the scheduler). §10: "It is RECOMMENDED that, when possible, servers respect the urgency parameter"; "Non-incremental responses of the same urgency SHOULD be served by prioritizing bandwidth allocation in ascending order of the stream ID"; "Incremental responses of the same urgency SHOULD be served by sharing bandwidth among them"; "It is RECOMMENDED that servers avoid such starvation where possible" (early non-incremental responses holding back incremental ones of the same urgency); §10.1: "servers SHOULD allocate some amount of bandwidths to streams acting as tunnels".

**Recorded status.** ✅ 0.2.0

**How it is met.** `quic/stream/StreamScheduler.kt`:

- critical streams first, then strict urgency; within a level retransmissions first, then non-incremental streams by ascending id and incremental streams round-robin
- within a level the incremental and the non-incremental queues take turns frame by frame (as quic-go's framer does), so neither kind starves the other (§10); until 0.3.0 every non-incremental stream went strictly first, and an unsignalled tunnel or WebSocket (u=3, i) got nothing while a default u=3 response had data
- a stream marked as a tunnel (HTTP/3 marks every CONNECT stream, on both sides) gets one frame in 16 whatever its urgency once no critical stream has data (§10.1); an ordinary less urgent stream still waits
- the turns cost a few bit tests per frame and allocate nothing

**Tests that pin it.**

- `stream.StreamSchedulerTest.urgencyStrict`, `stream.StreamSchedulerTest.nonIncrementalByIdAscending`, `stream.StreamSchedulerTest.incrementalRoundRobin`, `stream.StreamSchedulerTest.retransmissionsBeforeNewDataOnSameLevel`, `stream.StreamSchedulerTest.urgencyOutOfRangeRejected`, `stream.StreamSchedulerTest.incrementalAndNonIncrementalShareOneUrgency`, `stream.StreamSchedulerTest.tunnelGetsShareBehindMoreUrgentStream`, `stream.StreamSchedulerTest.negative_lessUrgentStreamGetsNoShare`, `stream.StreamSchedulerTest.negative_tunnelShareNeverPreemptsCriticalStreams`, `runtime.PriorityTest.tunnelGetsShareBehindUrgentResponse`

**Peer interop notes.**

- quiche orders the same level strictly (non-incremental first, `quiche/src/stream/mod.rs`), which does not meet the §10 recommendation; quic-go alternates incremental and non-incremental streams per urgency (`framer.go`, `lastSendWasIncremental`), the rule used here

## <a id="priorities-http-part"></a>priorities (HTTP part)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9218.

**Requirement.** Priorities (HTTP part).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- the scheduler is the transport one (8 urgency levels, incremental ones round-robin, the two kinds taking turns within a level, a share for tunnels; see the row above)

**Peer interop notes.**

- control and QPACK streams — u=0 until 0.3.0, from 0.3.0 ahead of every request stream whatever its urgency, so a peer's u=0 cannot hold back our SETTINGS, GOAWAY or QPACK instructions (as quiche and neqo) — `stream.StreamSchedulerTest.criticalStreamsBeforeEveryUrgency`, `runtime.PriorityTest.criticalStreamsGoBeforeAnUrgentResponse`

## <a id="s7-priority-update"></a>§7–8 — PRIORITY_UPDATE

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9218 §7–8.

**Requirement.** `PRIORITY_UPDATE`: the server applies the client's signal to the response stream, a server priority from `respond(priority)` overrides the client's.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- a frame arriving before the stream is opened is remembered (≤ 32, extra ones are dropped with a glitch token), also for a stream the transport opened whose HEADERS are still on the way, such as a reordered stream 4 behind stream 8 (review: it was taken for a finished request and dropped)
- an id beyond the bidirectional stream limit we granted (MAX_STREAMS) → `H3_ID_ERROR` (§7.2 SHOULD, review), the header is ignored if `PRIORITY_UPDATE` came earlier
- an id of a non-request stream → `H3_ID_ERROR`
- a frame of any length up to the 4096-byte ceiling of control frames is checked and applied; until 0.3.0 one above 256 bytes was ignored before the id checks, so the `H3_ID_ERROR` MUST was skipped for it (§7.2) and a long valid update was lost (§7 "Servers SHOULD buffer the most recently received PRIORITY_UPDATE frame and apply it")
- a client that receives `PRIORITY_UPDATE` → `H3_FRAME_UNEXPECTED`
- an id of a WebTransport bidirectional stream is no `H3_ID_ERROR`: draft-ietf-webtrans-http3-16 §4.3 keeps every client-initiated bidirectional stream a request stream ("All client-initiated bidirectional streams are reserved by HTTP/3 as request streams [...] WebTransport extends HTTP/3 to allow clients to declare and to use alternative request stream rules"), and §3.4 gives WebTransport streams no priority signal of their own ("WebTransport does not provide any priority signaling mechanism for streams and datagrams within a WebTransport session"); such an update is kept like one for a request whose HEADERS are on the way (bounded by the early buffer, dropped when the stream ends) and never applied
- `Http3Response.updatePriority`

**Tests that pin it.**

- `runtime.PriorityTest.*` (including `negative_priorityUpdateBufferCap`, `earlyPriorityUpdateForReorderedStreamApplies`, `priorityUpdateBeyondStreamLimitIsIdError`, `longPriorityUpdateApplied`, `negative_longPriorityUpdateForNonRequestStreamIsIdError`, `negative_longPriorityUpdateBeyondStreamLimitIsIdError`)

## <a id="s4-the-priority-field"></a>§4–5 — the `Priority` field

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9218 §4–5.

**Requirement.** The `Priority` field: a Structured Fields dictionary, `u` 0–7, `i`.

Quoted: "MUST be ignored (i.e., treated as if the field were not present in the section)"; "Failure to parse the Priority Field Value MAY be treated as a connection error".

**Recorded status.** ✅ 0.2.0

**How it is met.**

- parsed strictly as an RFC 8941 Dictionary (§4.2: keys, Integers, Decimals, Strings, Tokens, Byte Sequences, Booleans, Inner Lists and parameters, a later member of the same key overwrites an earlier one), and a value that is not one is ignored as a whole (every parameter absent)
- the same parser reads the Priority Field Value of `PRIORITY_UPDATE` (§7), and one that fails to parse sets the stream to the defaults, deliberately: §4 has receivers parse it as RFC 8941 §4.2, whose failed parse "MUST be ignored (i.e., treated as if the field were not present in the section)", so the frame carries no parameter, and §7 says "A PRIORITY_UPDATE frame communicates a complete set of all priority parameters [...] Omitting a priority parameter is a signal to use its default value"
- dropping the frame instead would keep an earlier signal that this complete set replaces
- the connection error §7 allows ("Failure to parse the Priority Field Value MAY be treated as a connection error", `H3_GENERAL_PROTOCOL_ERROR`) is not used, since a value our strict parser refuses but a lenient peer's accepts is no attack on the connection
- a field that fails to parse also counts as absent where only its presence matters: a CONNECT with one is an unsignalled tunnel on both sides, and a response field that fails to parse is no server choice, so the client's later `PRIORITY_UPDATE`s still apply (until 0.3.0 both took the field as present)
- several `priority` field lines are combined with ", " before parsing
- unknown keys and member parameters are ignored, a `u` that is not an Integer 0–7 or an `i` that is not a Boolean is ignored on its own (§4.1, §4.2), defaults u=3, i=false
- the client sends the field only for non-defaults

**Tests that pin it.**

- `message.PriorityFieldTest.*`, `runtime.PriorityTest.invalidPriorityUpdateValueMeansDefaults`, `.priorityFieldLinesAreCombined`, `.negative_garbledConnectFieldStaysTunnel`, `.negative_garbledResponseFieldKeepsClientUpdates`, `message.PseudoHeadersTest.buildRequestRoundTrip`

## <a id="s8-local-scheduling"></a>§8, §10.1, §11 — local scheduling

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9218 §8, §10.1, §11 (local scheduling).

**Requirement.** The client schedules its request stream with its own signal, given as `Http3Request.priority` or as a `priority` header (sent once); `Http3Request.priority` replaces a `priority` header, so the signal the server gets is the one we schedule with (until 0.3.0 the header went out and the explicit priority scheduled — `message.PseudoHeadersTest.priorityReplacesThePriorityHeader`).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- §10.1 and §11: a CONNECT without a signal is incremental, so it shares with the other incremental streams of its urgency, and every CONNECT gets one frame in 16 even behind more urgent streams (`.tunnelGetsShareBehindUrgentResponse`); until 0.3.0 an unsignalled tunnel shared only with incremental streams and starved behind a same-urgency non-incremental response
- the server merges a `priority` field of its response into the stream's current priority (absent parameters keep the client's values, or an unsignalled tunnel's incremental default — `.responseFieldKeepsTunnelIncremental`) and schedules with it, an explicit `respond(priority)` wins, later PRIORITY_UPDATEs no longer change it
- a CONNECT without a signal is incremental locally on both sides, the client's signal reads as the default

**Tests that pin it.**

- `runtime.PriorityTest.headerFieldDrivesClientScheduling`, `.responseFieldMergesIntoServerScheduling`, `.connectTunnelDefaultsToIncremental`, `.tunnelGetsShareBehindUrgentResponse`, `message.PriorityFieldTest.mergeKeepsAbsentParameters`, `message.PseudoHeadersTest.priorityReplacesThePriorityHeader`

## <a id="ktor-server"></a>Ktor server

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9218 (Ktor server).

**Requirement.** `ApplicationRequest.priority` / `priorityUpdates`: the client's signal — over h3 and h2 the `priority` field and later PRIORITY_UPDATEs, over h1 the `Priority` field lines as one dictionary, otherwise the default.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- a garbled field reads as the defaults and the request is served
- `ApplicationResponse.priority(urgency, incremental)` writes the `Priority` field with only the given parameters (§8), over h3 and h2 merged into the client's signal for the response's scheduling
- over h2 the response's DATA is scheduled by that result ([§10 on HTTP/2](#s10-http2-server-scheduling)), and each PRIORITY_UPDATE ([§7.1](#s7-1-http2-priority-update)), one that came before the request included, updates `priorityUpdates` and reschedules the response unless the response set its own field
- over h1 the field only

**Tests that pin it.**

- `ServerPriorityTest.*` (including `h2ResponseScheduledByPriority`, `h2PriorityUpdateReachesHandler`)

## <a id="ktor-client"></a>Ktor client

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9218 (Ktor client).

**Requirement.** `HttpRequestBuilder.priority(urgency, incremental)` (urgency 0–7, else `IllegalArgumentException`): over h3 `Http3Request.priority` — the `priority` field only for non-defaults, the request's own stream scheduled with it, Extended CONNECT for WebSockets too.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- over h2 the `Priority` field, the request's own DATA scheduled with it, and an RFC 7540 weight in the HEADERS until the server's SETTINGS say it ignores those ([§2.1.1](#s2-1-1-client-signals-before-settings)); over h1 the `Priority` field only
- a raw `Priority` header on the same request is dropped (one signal)
- `HttpResponse.updatePriority` sends PRIORITY_UPDATE over h3 and h2 (true), false over h1 (a 421 or failure resent over h1 included), over h2 when the server left SETTINGS_NO_RFC7540_PRIORITIES at 0 (§2.1.1), after the call, once the body was read to the end, or on a gone connection

**Tests that pin it.**

- `ClientPriorityTest.*`, `ServerPriorityTest.h2PriorityUpdateReachesHandler` (kuicksilver-ktor-server)

## <a id="s10-http2-server-scheduling"></a>§10, §10.1 — server scheduling on HTTP/2

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** As on HTTP/3 (§10): urgency respected, non-incremental responses of one urgency "in ascending order of the stream ID", incremental ones "sharing bandwidth among them", no starvation of incremental responses by early non-incremental ones; §10.1: "servers SHOULD allocate some amount of bandwidths to streams acting as tunnels".

**How it is met.** `http2/core/DataScheduler.kt`, `http2/core/H2ConnectionCore.kt`, `ktor/server/h2/H2Call.kt`, `ktor/server/h2/H2Response.kt`:

- the connection's DATA frames go by the same rules as the QUIC scheduler's: urgency, non-incremental by id, incremental round-robin, the two kinds taking turns within an urgency, a CONNECT stream one frame in 16 whatever its urgency
- a writer hands one 16 KiB frame at a time to the core; when that frame is written and the writer holds more, the less urgent streams wait for its next frame for at most 2 ms (a core deadline), so priority shows on the wire and a writer that does not come back holds nobody up
- the Ktor server sets each stream's priority from the request's `Priority` field (an unsignalled CONNECT incremental, as on HTTP/3), merged with the response's own field (§8); a field that fails to parse counts as absent
- until 0.3.0 the DATA of all streams went round-robin whatever their priority

**Tests that pin it.**

- `core.PriorityTest.*` (kuicksilver-http2: `urgencyFirst`, `nonIncrementalInStreamOrder`, `incrementalShare`, `incrementalAndNonIncrementalTakeTurns`, `tunnelGetsShareBehindMoreUrgentResponse`, `negative_lessUrgentResponseGetsNoShare`, `negative_silentUrgentWriterDoesNotStallTheConnection`, `priorityChangeApplies`), `ServerPriorityTest.h2ResponseScheduledByPriority`

## <a id="s2-1-no-rfc7540-priorities"></a>§2.1 — SETTINGS_NO_RFC7540_PRIORITIES on HTTP/2

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** "The value of SETTINGS_NO_RFC7540_PRIORITIES MUST be 0 or 1. Any value other than 0 or 1 MUST be treated as a connection error [...] of type PROTOCOL_ERROR"; "If endpoints use SETTINGS_NO_RFC7540_PRIORITIES, they MUST send it in the first SETTINGS frame"; "A server that receives SETTINGS_NO_RFC7540_PRIORITIES with a value of 1 MUST ignore HTTP/2 priority signals."

**How it is met.** `http2/core/H2ConnectionCore.kt`, `H2ConnectionCore.frames.kt`:

- a server sends the setting with 1 in its first SETTINGS frame and never changes it; a client leaves it out (the initial value 0: §2.1 says "If endpoints use SETTINGS_NO_RFC7540_PRIORITIES, they MUST send it in the first SETTINGS frame", and value 1 would declare that "they are not using HTTP/2 priority signals", which a client following §2.1.1 does); a received value above 1 is a PROTOCOL_ERROR connection error
- RFC 7540 signals (PRIORITY frames, HEADERS priority fields) are parsed for their frame errors and otherwise ignored; after the peer's value 1 the RFC 7540 self-dependency check is skipped as well, so such signals are ignored completely (until 0.3.0 a self-dependent one was still a stream error)

**Tests that pin it.**

- `core.StreamStateTest.selfDependencyIgnoredAfterNoRfc7540Priorities`, `.negative_selfDependencyIsStreamError`, `.clientPrefaceAndSettings`, `core.SettingsTest.*`

## <a id="s2-1-1-client-signals-before-settings"></a>§2.1.1 — client signals before the server's SETTINGS

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** "until the client receives the SETTINGS frame from the server, the client SHOULD send both the HTTP/2 priority signals and the signals of this prioritization scheme"; "Once the client receives the first SETTINGS frame that contains the SETTINGS_NO_RFC7540_PRIORITIES parameter with a value of 1, it SHOULD stop sending the HTTP/2 priority signals"; "if the client receives SETTINGS_NO_RFC7540_PRIORITIES with a value of 0 or if the settings parameter was absent, it SHOULD stop sending PRIORITY_UPDATE frames".

**How it is met.** `http2/core/H2ConnectionCore.kt`, `http2/runtime/H2Connections.kt`, `ktor/client/h2/H2Exchange.kt`:

- the client's first SETTINGS leaves SETTINGS_NO_RFC7540_PRIORITIES out (see §2.1), and its request HEADERS carry an RFC 7540 signal next to the `priority` field: dependency 0, not exclusive, a weight from the request's urgency
- the weight is Chromium's mapping of its eight priorities to HTTP/2 weights (`Spdy3PriorityToHttp2Weight`, 255.9 / 7 per step): u=0 to u=7 give 256, 220, 183, 147, 110, 74, 37, 1; the incremental parameter has no RFC 7540 counterpart (with every request on stream 0, weights only share bandwidth among siblings) and is left out
- once the server's SETTINGS say SETTINGS_NO_RFC7540_PRIORITIES = 1 no further request carries the signal; with 0 or without the setting the signal goes on (§2.1.1 asks to stop only on 1)
- PRIORITY_UPDATE goes out before the server's SETTINGS and while they say 1; after SETTINGS with 0 or without the setting `updatePriority` returns false and nothing is sent
- our server parses the signals for their errors and ignores them either way (RFC 9113 §5.3.2), and sends the setting with 1
- until 0.3.0 the client sent SETTINGS_NO_RFC7540_PRIORITIES = 1 and no RFC 7540 signal

**Tests that pin it.**

- `core.ClientRfc7540SignalTest.*` (kuicksilver-http2: `weightFollowsUrgency`, `signalsBeforeTheServersSettings`, `signalsGoOnWhenTheServerKeepsRfc7540Priorities`, `negative_noSignalsOnceTheServerIgnoresThem`), `core.PriorityUpdateTest.clientSendsUpdates`

## <a id="s7-1-http2-priority-update"></a>§7.1 — the HTTP/2 PRIORITY_UPDATE frame

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** "The Stream Identifier field [...] MUST be zero (0x0). Receiving a PRIORITY_UPDATE frame with a field of any other value MUST be treated as a connection error of type PROTOCOL_ERROR"; the prioritized idle streams plus the active ones "MUST NOT exceed the value of the SETTINGS_MAX_CONCURRENT_STREAMS parameter. Servers that receive such a PRIORITY_UPDATE MUST respond with a connection error of type PROTOCOL_ERROR"; "Servers that receive a PRIORITY_UPDATE for a push stream in the idle state MUST respond with a connection error of type PROTOCOL_ERROR"; a prioritized stream ID of 0x0 "MUST respond with a connection error of type PROTOCOL_ERROR"; "Servers MUST NOT send PRIORITY_UPDATE frames. If a client receives a PRIORITY_UPDATE frame, it MUST respond with a connection error of type PROTOCOL_ERROR"; clients "SHOULD provide a prioritized stream ID that refers to a stream in the 'open', 'half-closed (local)', or 'idle' state"; §7: "Servers SHOULD buffer the most recently received PRIORITY_UPDATE frame and apply it once the referenced stream is opened."

**How it is met.** `http2/frame/FrameDecoder.kt`, `http2/core/H2ConnectionCore.frames.kt` (`onPriorityUpdate`), `http2/runtime/H2Runtime.kt`, `ktor/server/h2/H2Call.kt`:

- the decoder reads type 0x10: a stream identifier other than 0 is a PROTOCOL_ERROR connection error, a payload shorter than the 4-byte Prioritized Stream ID a FRAME_SIZE_ERROR (RFC 9113 §4.2)
- a server: prioritized stream 0 → PROTOCOL_ERROR; an even (server-initiated, push) stream → PROTOCOL_ERROR, since we never push and every push stream is idle; an open or half-closed (remote) request → the value reaches the request (`H2ServerStream.onPriorityUpdate`); a half-closed (local) or closed stream → dropped, as §7.1 allows; an idle request stream → the latest value is kept and handed over with the request's HEADERS (it overrides the `priority` field, §7), as long as those kept and the active streams stay within our SETTINGS_MAX_CONCURRENT_STREAMS, else PROTOCOL_ERROR; idle streams that a newer stream closed (RFC 9113 §5.1.1) drop their value; each frame spends a glitch token, as PRIORITY does
- the Ktor server parses the value as a complete set (a parameter left out is its default; one that fails to parse means the defaults, as on HTTP/3), updates `priorityUpdates`, and reschedules the response unless the response chose its own priority (§8)
- a client never receives one without ending the connection with PROTOCOL_ERROR, and sends one only for a stream that may still receive data, never as a server
- until 0.3.0 a server ignored the frame as an unknown type and a client did not refuse it

**Tests that pin it.**

- `core.PriorityUpdateTest.*` (kuicksilver-http2: `appliedToAnOpenStream`, `earlyUpdateArrivesWithTheRequest`, `updateForAClosedStreamIsDiscarded`, `negative_onARequestStream`, `negative_forStreamZero`, `negative_forAPushStream`, `negative_tooManyPrioritizedIdleStreams`, `negative_tooShort`, `clientSendsUpdates`), `core.StreamStateTest.negative_clientRejectsPriorityUpdate`, `ServerPriorityTest.h2PriorityUpdateReachesHandler`
