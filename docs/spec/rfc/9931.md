## <a id="s8-server-connect"></a>§8 (updates RFC 9112; server CONNECT) — server CONNECT

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9931 §8 (updates RFC 9112; server CONNECT).

**Requirement.** Every CONNECT is refused and is the last request on its connection: the engine cannot tunnel (the handler gets no connection), so a 2xx from the application, which would promise "tunnel mode immediately after the response header section" (RFC 9110 §9.3.6), is replaced by `501 Not Implemented` with a short text and a warning in the application log.

**Recorded status.** ✅ 0.2.1 (tunnels: ⬜ 0.3.0)

**How it is met.**

- a refusal (that 501, or any other status the application or Ktor gives, also a failing handler's 500) MUST close the connection without processing any further request, close option or not
- every response to CONNECT says `Connection: close`, the handler is awaited, then the input is read and dropped (never parsed) for up to 2 s
- the §8 MAY (keep the connection for a User-Agent known to wait for a 2xx) is not used (0.2.1; before, a refused CONNECT left the connection open and the optimistically sent bytes behind it were executed as the next request, and a 2xx went out framed as a body).

**Tests that pin it.**

- `h1.H1PipelineConnectTest.negative_refusedConnectEndsTheConnection`, `ServerH1ResponseFramingTest.negative_2xxToConnectIsAnswered501`

**Open items.**

- Open (⬜ 0.3.0): CONNECT tunnels (a 2xx that hands the handler the connection)
