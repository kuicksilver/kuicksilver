# RFC 1928/1929 — SOCKS Protocol Version 5 (RFC 1928) and Username/Password Authentication for SOCKS V5 (RFC 1929)

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="s3-socks5-client"></a>§3–§6 (client) — SOCKS5 client

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 1928 §3–§6 (client).

**Requirement.** SOCKS5 CONNECT only (no BIND, no UDP ASSOCIATE, no SOCKS4): method negotiation offering "no authentication" and, with credentials, username/password (§3 "SHOULD support USERNAME/PASSWORD authentication methods"). The GSSAPI method of the same sentence is [its own row](#s3-gssapi).

**Recorded status.** ✅ 0.3.0 (🔶 until the open-rows audit of 2026-11, which split the GSSAPI method into its own ❌ row)

**How it is met.**

- a name as ATYP 3 for the proxy to resolve (`ProxyBuilder.socks`), address literals as ATYP 1/4
- the reply's bound address read with its length checked and dropped
- a reply other than "succeeded" → `ProxyException(replyCode = REP)`, an unknown ATYP, a non-SOCKS5 version or an unoffered method → `ProxyException` before any TLS
- every step under the connect timeout
- §3 "If the selected METHOD is X'FF', none of the methods listed by the client are acceptable, and the client MUST
  close the connection": X'FF' → `ProxyException` (`Socks5.kt`), and the pool closes the TCP connection to the proxy
  (`H1Pool.kt`); RSV is sent as X'00' (§4)

**Tests that pin it.**

- `h1.Socks5Test.*`, `ClientSocksProxyTest.httpsThroughSocks5`, `.plainHttpThroughSocksUsesOriginForm`, `.negative_socksReplyFailsTheRequest`

**Scope.** CONNECT only: BIND and UDP ASSOCIATE (§4) are not offered, as HTTP needs neither; their requirements bind a
server and a UDP client, not a CONNECT client.

**Open items.** None.

## <a id="username-password"></a>RFC 1929 — username/password

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 1929.

**Requirement.** Username/password: offered only with credentials, sent only when the proxy picks method 02.

**Recorded status.** ✅ 0.3.0 (🔶 until the open-rows audit of 2026-11, which found nothing of RFC 1929 missing)

**How it is met.**

- credentials are sent only when the proxy chose username/password, never to one that chose "no authentication"
- the reply's VER is 1 or 5: §2 defines the reply as `VER STATUS` with VER X'01' and gives the client no rule for another value, and some proxies answer with the SOCKS version, 5 ([compatibility shims](../compat-shims.md#8-socks5-usernamepassword-reply-with-ver-5)); any other VER fails the connection
- a rejection → `ProxyException` naming the proxy, not the credentials; §2 "it MUST close the connection" binds the
  server, and the client closes it as well

**Tests that pin it.**

- `h1.Socks5Test.authReplyVersion5Tolerated`, `.negative_socksCredentialsNotSentWhenServerChoosesNoAuth`, `.negative_socksAuthRejected`, `.negative_socksOverlongCredentialsRejected`, `.negative_socksEmptyPasswordRejected`, `ClientSocksProxyTest.socks5UsernamePassword`, `.negative_socks5ProxyWithAnEmptyPasswordIsAConfigurationError`, `ProxyResolverTest.negative_socks5UrlWithAnEmptyPasswordFails`

**Peer interop notes.**

- user 1–255 and password 1–255 bytes (§2: PASSWD is 1 to 255 octets; curl and Go send an empty password as PLEN 0 anyway), else `IllegalArgumentException` before anything is sent, and for the password already when the SOCKS5 proxy is configured (the engine's creation for `proxy` with `proxyCredentials` or URL user info, `ResolvedProxy.socks5` for a resolver's)

**Open items.** None.

## <a id="s3-gssapi"></a>§3 — GSSAPI method

Status: ❌ · [summary](../rfc-compliance.md#http)

Original row: RFC 1928 §3 (split from the SOCKS5 client row by the open-rows audit of 2026-11).

**Requirement.** §3 "Compliant implementations MUST support GSSAPI and SHOULD support USERNAME/PASSWORD authentication
methods." GSSAPI is method X'01', specified in RFC 1961.

**Recorded status.** ❌ (not planned for 0.x)

**Why not.** The client does not offer GSSAPI: its method list is "no authentication" and, with credentials,
username/password (`Socks5.kt`). GSSAPI for SOCKS needs a Kerberos (GSS-API) implementation on every platform the
client runs on — GSS.framework on Apple, SSPI on Windows, libgssapi on Linux, JGSS on the JVM — and Android has none,
plus the RFC 1961 sub-negotiation and per-message protection. This is a MUST of RFC 1928 that Kuicksilver does not meet;
it is stated here rather than marked as a subset.

**Behaviour.** A proxy that requires GSSAPI answers our method list with X'FF'; the request fails with
`ProxyException` ("accepts no acceptable authentication method") and the connection to the proxy is closed (§3).

**Notes on peers.**

- Go's `golang.org/x/net/internal/socks` offers only X'00' and X'02' (`socks.go`, `AuthMethodNotRequired`,
  `AuthMethodUsernamePassword`).

**Open items.** Not planned for 0.x.
