## <a id="loss-detection-pto-newreno"></a>loss detection, PTO, NewReno

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9002.

**Requirement.** Loss detection, PTO, NewReno.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- `QuicConfig.initialRtt` (§6.2.2) validated in (0, 10 s], the first PTO is 3 x initialRtt
- after it min_rtt restarts from the newest sample (§5.2) and a new period needs packets sent after that sample
- NewReno's congestion avoidance carries the remainder of mds × acked / cwnd (it stopped growing above 1.44 MB)

**Tests that pin it.**

- `recovery.LossDetectionTest.initialPto999ms`, `recovery.LossDetectionTest.initialPtoFollowsInitialRtt`, `QuicConfigTest.negative_initialRttMustBePositive`, `core.PathTest.validationTimeoutFollowsInitialRtt`, `recovery.LossDetectionTest.appSpacePtoAddsMaxAckDelayAfterConfirmed`, `recovery.LossDetectionTest.ptoBackoffDoubles`, `recovery.LossDetectionTest.ptoCountResetOnAck`, `recovery.LossDetectionTest.clientAntiDeadlockPtoWithNothingInFlight`, `recovery.LossDetectionTest.negative_ackForUnsentPacket`, `recovery.LossDetectionTest.negative_ackForSkippedPacketNumber`, `recovery.NewRenoTest.*`, `recovery.PacerTest.*`, `recovery.LossDetectionTest.persistentCongestionIgnoresPacketsSentBeforeTheFirstRttSample`, `.persistentCongestionSpansAckOnlyAndSkippedPacketNumbers`, `.anAcknowledgedPacketBetweenTheLostOnesBreaksPersistentCongestion`, `.persistentCongestionSpanIsBetweenAckElicitingPackets`, `.persistentCongestionIsJudgedPerPath`, `.persistentCongestionResetsMinRttToTheNewestSample`, `core.AppLimitedTest.*`, `recovery.NewRenoTest.congestionAvoidanceKeepsGrowingAboveMssSquared`
- §6.2.2.1 (core review): a server that has exhausted its amplification limit does not arm the PTO until the client sends more — `core.HandshakeLimitsTest.ptoNotArmedWhileAmplificationBlocked`
- §6.2.4 (0.2.0 release gate, run 20261015-005204, `kuicksilver->ngtcp2:handshakeloss`): a PTO probe resends the frames of the oldest unacknowledged packets that hold CRYPTO, STREAM, stream control frames or HANDSHAKE_DONE and that no earlier probe took, so successive probes cycle through what is outstanding
- it used to take the two oldest packets whatever they held, and when those were a PING and NEW_CONNECTION_ID frames and every client ACK was lost, 30 s of probes were ACK + PING while HANDSHAKE_DONE and the response, each lost once, were never resent — `core.PtoProbeContentTest.probesResendDataBehindPingOnlyPackets`
- resent STREAM data never carries the FIN (one still in flight needs no copy, a lost one goes as an empty frame of its own): quiche's receiver takes the final size from a frame whose bytes it already read, drops the frame as a duplicate and never wakes the application for the FIN, so once probes carried data `kuicksilver->quiche:handshakeloss` lost one request in 50 (run 20261015-170940) — `stream.SendStreamTest.retransmittedDataDoesNotCarryAFinThatIsStillInFlight`

**History.**

- 0.2.0 review: persistent congestion (§7.6.2) between two lost ack-eliciting packets, both sent after the first RTT sample (a lossy handshake used to collapse to the minimum window; ngtcp2's first_rtt_sample_ts), broken only by a packet acknowledged between them (each space keeps the acknowledged ranges above its oldest outstanding packet, so ACK-only and skipped packet numbers no longer break it), judged per path

**Peer interop notes.**

- the window grows only when the sender used it before the ACK frame (§7.8, quic-go's isCwndLimited: at most 3 datagrams unused, or more than half in flight in slow start)
- a PMTU probe arms the PTO (as ngtcp2's PTO_ELICITING probes)
