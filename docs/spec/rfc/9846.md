# RFC 9846 — The Transport Layer Security (TLS) Protocol Version 1.3 (obsoletes RFC 8446)

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="s8-0-rtt-anti-replay"></a>§8, §4.3.10 — 0-RTT anti-replay

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9846 §8, §4.3.10.

**Requirement.** 0-RTT anti-replay.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- OpenSSL's ticket-age freshness (±10 s), a per-server replay register keyed by the ticket identity (two rotating 20 s halves, 1 MiB, fails closed), single-use client tickets

**Tests that pin it.**

- `core.ZeroRttTest.negative_0rttReplayRejected`, `tls.QuicEarlyDataTest.negative_0rttReplayRejected`, `endpoint.ZeroRttReplayRegisterTest.*`

## <a id="s4-3-10-0-rtt-under-the-psk-s-parameters"></a>§4.3.10 (RFC 8446 §4.2.10); RFC 9001 §4.6.1 — 0-RTT only under the PSK's version, cipher suite and ALPN

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: O.1 in the 0.3.0 plan.

**Requirement.** "In order to accept early data, the server MUST have selected the first key offered in the client's "pre_shared_key" extension. In addition, it MUST verify that the following values are the same as those associated with the selected PSK: The selected TLS version number, The selected cipher suite, The selected ALPN protocol, if any" (RFC 9846 §4.3.10; RFC 8446 §4.2.10 the same); for a ticket, the associated values "are those which were negotiated in the connection which established the PSK" (RFC 8446 §4.2.10). RFC 9001 §4.6.1 carries QUIC 0-RTT over the same TLS `early_data` extension.

**Recorded status.** ✅ 0.3.0; before, the cipher-suite comparison was missing (OpenSSL 3.5 compares only the suite's hash).

**How it is met.**

- version: TLS 1.3 only (a QUIC context offers nothing else; OpenSSL's `final_early_data` needs a TLS 1.3 resumption)
- first PSK: OpenSSL (`tls_parse_ctos_psk` sets `early_data_ok` only for identity 0)
- cipher suite: `allow_early_data_cb` (`kuicksilver-native/src/c/ksl_ctx.c`) refuses early data when the suite selected for this handshake (`SSL_get_pending_cipher`) is not the one of the resumed session (`SSL_SESSION_get0_cipher`). OpenSSL 3.5.9 resumes a PSK under another suite with the same hash (`ssl/statem/extensions_srvr.c`, `tls_parse_ctos_psk`: only `EVP_MD_is_a`) and accepted its early data; OpenSSL 4.1.0 adds the same comparison (`ssl/statem/extensions_srvr.c:1584-1591`, PR 32032). The handshake continues in 1-RTT with the PSK.
- ALPN: OpenSSL compares the selected protocol with the session's (`statem_srvr.c`, `tls_handle_alpn`) and writes the selected protocol into every renewed ticket. It keeps the old one only when a resumption selects none (fixed in 4.1, PR 32401), which a QUIC connection cannot complete (RFC 9001 §8.1: `ksl_client_hello_cb` and `ksl_drive` refuse it). On the client, an OpenSSL 3.5 ticket received on a resumed connection kept the resumed session's ALPN (`tls_process_new_session_ticket` duplicates the session; fixed in 4.1, PR 32401): the client then offered 0-RTT for the old protocol and aborted with illegal_parameter when the server, right by the ticket's own connection, accepted it under the new one. `ksl_ssl_get1_session` now gives every ticket received on the connection that connection's protocol (`own_alpn`, `kuicksilver-native/src/c/ksl_ssl.c`).
- the transport's replay verdict and the configuration context bound into the ticket come on top ([anti-replay](#s8-0-rtt-anti-replay), [RFC 9001 §4.6](9001.md#s4-6-0-rtt))

**Tests that pin it.**

- C `negative_quic_early_data_cipher_suite_mismatch_rejects` (a TLS_AES_128_GCM_SHA256 ticket resumed where only TLS_CHACHA20_POLY1305_SHA256 is allowed: 0-RTT rejected, the PSK resumes in 1-RTT; the same suite accepts), `tls.QuicEarlyDataTest.negative_zeroRttUnderAnotherCipherSuiteRejected` (the same through `QuicTlsSession`)
- C `negative_quic_early_data_alpn_mismatch_rejects` (an h3 ticket under hq-interop and a ticket renewed on an hq-interop resumption under h3 are rejected; the renewed ticket under its own protocol is accepted)

**Peer interop notes.**

- OpenSSL 4.1.0 makes both checks itself; ksl keeps its own while it builds on 3.5.

## <a id="tls-1-3"></a>(obsoletes RFC 8446) — TLS 1.3

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#tls)

Original row: RFC 9846 (obsoletes RFC 8446).

**Requirement.** TLS 1.3.

**Recorded status.** ✅ 0.2.0, against RFC 8446 (section numbers here are RFC 9846's: the handshake sections moved one down, §4.1 → §4.2 … §4.6 → §4.7; appendix D → E, E → F); §4.2.2/§4.2.3 ✅ 0.2.1: a hello whose `legacy_version` is not 0x0303 is refused with `protocol_version` on both sides (OpenSSL accepted 0x0301/0x0302; the server in the ClientHello callback, the client by disabling every version before OpenSSL checks the ServerHello) — C `tcp_legacy_version_must_be_0303`; §4.7.3 ✅ 0.2.1: the KeyUpdate epoch never passes 2^48−1 updates (after the last allowed one no KeyUpdate of ours, a peer's `update_requested` flag ignored (SHOULD), the last keys used until their §5.5 record limit, where the session ends; received updates are not counted) — C `tcp_key_update_epoch_is_bounded`; no second `update_requested` until the peer's KeyUpdate (a further request goes out as `update_not_requested`) — C `tcp_second_update_requested_waits_for_the_peer`; §6, §6.2 ✅ 0.2.1: `general_error` (117) is named, a TLS 1.3 error alert at level warning is reported by its code — `AlertNameTest.alertNames`; App. C.4 ✅ 0.2.1 (SHOULD): six tickets per TCP full handshake (the appendix's example: "a web browser using HTTP/1.1 might open six connections to a server"), one per resumption, six kept per origin by the client, each used once — C `tcp_client_keeps_every_ticket`, `SessionCacheTest.severalTicketsPerOrigin`, `SessionResumptionTest.sixConnectionsResumeFromOneFullHandshake`; App. E.5: TLS 1.0 and 1.1 refused even at the ksl level — C `tcp_default_versions_and_tls12_profile`; §6.1 🔶 0.2.1: a TCP connection whose application stream failed never ends with `close_notify`; a TLS 1.3 server and a TLS 1.2 client send the fatal alert internal_error after what they had sent (`ksl_tcp_abort`: OpenSSL 3.5 sends an alert on an established connection only when building a handshake message fails, so ksl fails a NewSessionTicket, or a TLS 1.2 renegotiation ClientHello before any of it is written); open: a TLS 1.3 client and a TLS 1.2 server (no such message); §5.5 (MUST; RFC 8446 said SHOULD) ✅ 0.2.1: over TCP the sending key is updated (KeyUpdate) before the negotiated AEAD's limit: every 2^23 records under AES-GCM (limit 2^24.5), 2^22 under AES-CCM (limit 2^23, RFC 9147 App. B.1, as RFC 9846 gives none), none under ChaCha20-Poly1305 (no limit); a session whose KeyUpdate cannot go out ends before the limit, with internal_error where an alert can be sent (OpenSSL sends KeyUpdate only on request; TLS 1.2 has none) — C `tcp_record_limits_per_cipher`

**Tests that pin it.**

- through OpenSSL 3.5
- `TlsConnection` (TCP) and `QuicTlsSession`
- `TlsConnectionTest`, `QuicHandshakeTest`, C `tcp_key_update_before_record_limit`, `tcp_abort_sends_internal_error`, `TlsConnectionTest.negative_aFailedServerOutputSendsInternalError`, `TlsFailedStreamTest.negative_aFailedTlsStreamEndsWithInternalError`

## <a id="s4-5-1-server-identity-replaced-at-run-time"></a>§4.5.1, §4.5.2, §4.7.1 — server identity replaced at run time, tickets bound to it

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 8446 §4.4.2, §4.6.1 in the 0.3.0 plan (RFC 9846 numbers the handshake sections one down).

**Requirement.** The Certificate message carries the sender's chain, its own certificate first (§4.5.1), and
CertificateVerify signs the transcript with the private key of that certificate (§4.5.2): a server that replaces its
identity while running must never pair one identity's chain with another's key. A resumed handshake carries no
Certificate (§2.2), so resumption must not outlive the identity it authenticated (§4.7.1, below).

**Recorded status.** ✅ 0.3.0: `TlsIdentity.Reloadable` (experimental) holds the current `TlsIdentity.InMemory` behind an
atomic reference. Every TCP connection and every QUIC session builds its own OpenSSL context and takes chain and key from
one snapshot (`withCurrentKey`: a snapshot replaced and closed between the load and the use is retried with the new one),
so a handshake presents a whole identity and a reload reaches only handshakes that start after it. The replaced identity
is closed at once; its native key is freed when the last context built from it is gone (OpenSSL holds its own reference
per context). `reload` refuses a closed identity, an expired leaf and a leaf not valid yet (5 minutes of skew),
keeping the old one; a mismatched key and chain never become an `InMemory`. Tickets carry the SHA-256 of the leaf they
were issued under and resume only under the same leaf (see the next section), so a reload ends resumption of the old
sessions and refuses their 0-RTT; the replay register is per process and not reset. A client's ticket also remembers the
client identity it was authenticated with and is resumed only under it.

**Tests that pin it.**

- `ReloadableIdentityTest.newHandshakeSeesReloadedLeaf`, `.liveConnectionKeepsOldIdentityAfterReload`,
  `.reloadDuringHandshakesNeverTearsThePair` (200 handshakes racing 200 reloads, each presents A or B whole),
  `.snapshotReplacedBeforeUseIsRetried`, `.negative_ticketIssuedBeforeReloadIsNotResumed`,
  `.negative_clientTicketOfAnotherClientIdentityNotResumed`, `.reloadManyTimesFreesEveryNativeKey` (`ksl.pkey`, `ksl.ctx`
  back to their level after 300 reloads), `.negative_mismatchedPairFailsBeforeReloadClosedIdentityRefused`,
  `.negative_reloadRejectsExpiredLeaf`, `.negative_reloadRejectsLeafExpiredOnTheClock`, `.negative_reloadRejectsLeafNotYetValid`,
  `.negative_identityClosedDuringReloadNeverBecomesCurrent`, `.negative_handshakeAndReloadAfterCloseFail`
- `ReloadIdentityQuicTest.newQuicHandshakeSeesReloadedLeaf`, `.negative_earlyDataOfTicketFromBeforeReloadRefused` (and
  the replay of a fresh ticket's first flight is still refused)

## <a id="s4-7-1-resumption-lifetime"></a>§4.7.1 — total lifetime of resumption keying material

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** "It is RECOMMENDED that implementations place limits on the total lifetime of such keying material;
these limits should take into account the lifetime of the peer's certificate, the likelihood of intervening revocation,
and the time since the peer's online CertificateVerify signature."

**Recorded status.** ✅ 0.3.0 (before: not met). Every resumption renews the ticket (`SSL_TICKET_RETURN_USE_RENEW`, single-use
client tickets) and OpenSSL gives the renewed session a fresh time, so a client reconnecting within the ticket lifetime
resumed forever. Now every server writes into the ticket (`ticket_gen_cb`) the SHA-256 of its leaf certificate, the time
of the full handshake that authenticated the session (a renewed ticket keeps the original one) and the leaf's notAfter,
and `ticket_dec_cb` resumes only under the same leaf, at most 7 days after that full handshake, and not past notAfter;
otherwise a full handshake runs (an authentication time up to 60 s ahead of the clock is accepted, for nodes sharing
ticket keys). The lifetime a ticket announces is cut to what is left of both bounds, and none is issued with no time
left (BoringSSL `ssl_session.cc:208-209` clamps the same way). 7 days is BoringSSL's `SSL_DEFAULT_SESSION_AUTH_TIMEOUT`, which bounds renewals the same
way (`ssl/ssl_session.cc:132`, `:190-209`, `:255-260`: a renewed session keeps `auth_timeout` and its timeout never
exceeds it). Tickets of earlier versions (without these fields) are not resumed.

**Tests that pin it.**

- C `tcp_resumption_bounded_by_authentication_time_notafter_and_leaf` (ticket clock moved: renewals resume at 2, 4 and
  6 days and are refused past 7; a ticket of another leaf is refused; past notAfter is refused),
  `tcp_ticket_lifetime_clamped_to_authentication_and_notafter` (announced lifetime cut, no ticket past notAfter, 60 s skew)
- `ReloadableIdentityTest.negative_ticketIssuedBeforeReloadIsNotResumed`,
  `ReloadIdentityQuicTest.negative_earlyDataOfTicketFromBeforeReloadRefused`

## <a id="s4-5-1-3-weak-certificate-signatures-and-keys"></a>§4.5.1.3 — MD5 and SHA-1 certificate signatures; keys below 112 bits

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** "Any endpoint receiving any certificate which it would need to validate using any signature algorithm
using an MD5 hash MUST abort the handshake with a "bad_certificate" alert. SHA-1 is deprecated and it is RECOMMENDED that
any endpoint receiving any certificate which it would need to validate using any signature algorithm using a SHA-1 hash
abort the handshake with a "bad_certificate" alert. For clarity, this means that endpoints can accept these algorithms
for certificates that are self-signed or are trust anchors." Key sizes come from RFC 9325 §4.5 (RSA at least 2048 bits,
curves at least 224 bits; [its row](9325.md#s4-5-public-key-length)); Kuicksilver holds every peer chain to OpenSSL's
security level 2, 112 bits, which meets both.

**Recorded status.** ✅ 0.3.0 (before: met only where OpenSSL verified the chain, `AnchoredCa` and `Platform` on Linux,
whose default security level 2 refuses both; under `Platform` elsewhere the platform verifier decided, and the JDK,
Android and Windows verifiers accept 1024-bit RSA; a `Custom` or `Tofu` trust checked nothing of the kind). `ksl` now
runs OpenSSL's own security-level checks (`crypto/x509/x509_vfy.c` `check_key_level`, `check_sig_level`,
`check_auth_level` of the pinned OpenSSL 3.5.9) on the chain the peer sent whenever the handshake pauses for Kotlin-side
trust (`ksl_chain_security` in `kuicksilver-native/src/c/ksl_verify.c`), before the platform verifier or a
`CertificateVerifier` is asked: every presented certificate reachable from the leaf through issuer edges that hold is
checked, an edge being a certificate whose name and key identifiers fit (`X509_check_issued`) and whose key verifies the
signature (`X509_verify`), each certificate once and every verifying issuer followed (cross-certificates too); name
matching alone let a decoy with the intermediate's subject, no key identifiers and a strong self-signed key end the walk
before the weak intermediate (second review of T.5). At most 101 certificates are visited and 2n + 2 signatures verified
for n sent; a chain needing more is refused with `CERT_CHAIN_TOO_LONG` (`unknown_ca`; `VerifyReason.UnknownIssuer` in Kotlin, C `chain_security_bounds`). On it, every key needs 112
security bits (RSA and DSA 2048 bits, elliptic curves 224 bits; the leaf's failure is `X509_V_ERR_EE_KEY_TOO_SMALL`, any other `X509_V_ERR_CA_KEY_TOO_SMALL`), and every signature too (SHA-1 counts 63 bits,
MD5 39: `X509_V_ERR_CA_MD_TOO_WEAK`) except the own signature of a certificate that is self-signed in fact:
`X509_self_signed(x, 1)`, its signature verifying under its own key. OpenSSL's `EXFLAG_SS` alone would not do: it is set
from names, key identifiers and the signature's algorithm (`crypto/x509/v3_purp.c`), so a CA-issued certificate whose
subject repeats its issuer's name and that has no key identifiers carries it too (review of T.5). libssl maps the three
errors to `bad_certificate` (42), as on OpenSSL's path (`ssl/statem/statem_lib.c` x509table); with `genericAlerts` the
wire carries `handshake_failure` (40) and the reason stays local. Kotlin reports `TlsException.Verify` with
`VerifyReason.WeakKey` or `VerifyReason.WeakSignature` on both paths (OpenSSL's path reported
`Custom("X509 verification error 66")` before). A server verifies client certificates only through OpenSSL
(`AnchoredCa`), whose level 2 applies. Limits: on the pause path `ksl` sees only what the peer sent, so an anchor the
platform takes from its own store is the platform's to judge; and every presented certificate on a verified path from
the leaf is checked, which is stricter than OpenSSL: a
presented certificate the platform treats as its anchor (an intermediate in its store, or a cross-certificate the server
sends above it) still has its key and signature checked, where OpenSSL stops at the first trusted certificate.

**Tests that pin it.**

- C `verify_peer_chain_security_level` (pause and OpenSSL paths: a 1024-bit RSA leaf or intermediate, a P-192
  intermediate, a SHA-1-signed intermediate or leaf, an MD5-signed leaf, a 1024-bit root sent along, a self-issued but
  not self-signed MD5 leaf or SHA-1 intermediate, a self-signed 1024-bit leaf are refused with bad_certificate and the
  X509 error, the pause never reached; a 2048-bit RSA leaf, a P-256 leaf, a P-224 intermediate, a SHA-1 self-signed root
  sent along and a SHA-1 self-signed P-256 leaf are accepted; generic alerts; a 1024-bit client certificate refused by
  the server), `tcp_weak_chain_refused_before_the_pause` (TLS 1.3 and 1.2 over TCP)
- C `verify_peer_chain_security_level` also: a self-signed decoy with the intermediate's name sent before a SHA-1 or a
  1024-bit intermediate does not hide it; an unrelated certificate sent along is not on the path
- `ChainSecurityLevelTest` (common; its `Platform` cases run where `Platform` pauses, JVM, Android, Apple and Windows:
  `Platform` refuses the weak chains with `WeakKey` / `WeakSignature` and alert 42 before the platform is asked, the
  self-issued ones included, and asks it about 2048-bit RSA, P-256 and a P-224 intermediate; a `Custom` verifier is not
  asked about a weak chain; `Tofu` refuses a self-signed 1024-bit key at first contact without storing a pin and pins a
  SHA-1 self-signed P-256 leaf; `AnchoredCa` refuses the same chains with the same reasons)
