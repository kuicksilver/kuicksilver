## <a id="s3-df-on-the-socket-for-pmtud"></a>§3, §4.1 — DF on the socket for PMTUD probes

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 8899 §3, §4.1.

**Requirement.** DF on the socket for PMTUD probes.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- `EMSGSIZE` — skip one slot (counted with its size, `ksl_udp_emsgsize`, ksl ABI 7)
- Apple has no error queue (an unconnected socket gets no ICMP), Windows reports ICMP without MTU or quote (only `WSAEMSGSIZE` is used), NIO neither
- `KslDatagramIo` reports `caps.df`, and the search reaches 1452 on loopback (JVM Linux and macOS, Native Linux and macOS, Android).
- The portable NIO socket (0.3.0): DF is set wherever possible (§14 "UDP datagrams MUST NOT be fragmented at the IP layer. In IPv4, the Don't Fragment (DF) bit MUST be set if possible"). Per half of the socket (IPv4, and the IPv6 half of a dual-stack AF_INET6 channel), probe mode where the system takes it: `IP_MTU_DISCOVER` = `IP_PMTUDISC_PROBE` (on a dual-stack channel this is what covers v4-mapped traffic: `IPV6_MTU_DISCOVER` alone does not), `IPV6_MTU_DISCOVER` = `IPV6_PMTUDISC_PROBE` with `IPV6_DONTFRAG`; set through `ksl` on the JVM (`ksl_udp_fd_df_probe` on the channel's descriptor, reached through kuicksilver-tls `KslSocketDf`), through `android.system.Os` on Android, and on Windows through `ksl` as `ksl_udp_win.c` does (`IP_DONTFRAGMENT` / `IPV6_DONTFRAG` first, then PROBE). With probe mode on every half: ✅ §14 and §14.2.1 (no fragmentation, no path MTU cache a forged ICMP message could lower). Otherwise: a half that refuses probe mode (`ksl` present but the system says no: a seccomp filter, gVisor, a Windows without `IP_MTU_DISCOVER`) gets DO mode; without `ksl` the JDK's `IP_DONTFRAGMENT` (JDK 19 and later) is set, DO mode on Linux and Windows, `IP_DONTFRAG` on Apple. On Linux and Windows the JDK's option sets only the IPv6 half of a dual-stack channel, so a channel whose IPv4 half has no DF and whose bind address is IPv4 is opened AF_INET instead (bound to 0.0.0.0 it then reaches IPv4 peers only). DF is not possible, and RFC 9000's "if possible" applies, for: the JVM without `ksl` below JDK 19 (no `IP_DONTFRAGMENT`; JDK 17 has none), IPv4-mapped traffic of a dual-stack channel bound to an IPv6 address without `ksl` (or whose IPv4 half refused both modes), Android where the options are refused; such a socket logs a warning once, as does one without probe mode on every half. DO mode never fragments, but there §14.2.1 ("MUST ignore an ICMP message that claims the PMTU has decreased below QUIC's smallest allowed maximum datagram size") is a limitation the system imposes: a forged ICMP message claiming less than 1200 makes it refuse every send to that peer (Linux EMSGSIZE for ten minutes, quic-go CVE-2024-53259; Windows WSAEMSGSIZE, verified on a Windows 11 VM against a non-loopback peer, PROBE, DONT and NOT_SET sockets unaffected, loopback unaffected, so `NioDatagramIoTest` cannot reproduce it there). Mitigation (§14: "cease sending QUIC packets ... on the affected path"): a refusal of a datagram of at most 1200 bytes (the portable socket's, repeated on an immediate retry, which a connected socket's one-shot ICMP error passes; or the accelerated socket's EMSGSIZE count, taken after every batch, stateless ones too, and charged only to a batch with a datagram of that size) closes that path when it is not the active one, else ends the connection with a CONNECTION_CLOSE of NO_VIABLE_PATH, which an HTTP/3 client answers with its TCP fallback (`FallbackReason.Http3Error`), instead of losing datagrams until the idle timeout — `api.PathMtuRefusedTest`. The JDK's text for EMSGSIZE is matched in English, as Windows words it, and as `strerror` gives it in the process's locale (through `ksl`); without `ksl` under a non-English locale a Linux refusal is not recognized and its datagrams are lost until the idle timeout. Real QUIC with kuicksilver's TLS needs `ksl`, which sets probe mode, so the cases without it matter only where the system refuses probe mode or with a third-party `QuicCrypto`. Apple: see Open items — `NioDatagramIoTest.nioSetsDontFragmentWherePossible`, `.dfChoicePerProbeOutcome`, `.dfGapPerCase`, `.ipv4BindGetsDfOnItsTraffic`, `.messageTooLongPerPlatform`, `.aRefusalFailsThePathOnlyWhenTheRetryIsRefusedToo`, `test_udp.c` `udp_fd_df_probe`, `udp_fd_df_probe_forged_ptb` (a forged PTB for a random 127.x.y.z destination in a user and network namespace; positive control: a DO socket gets EMSGSIZE, a WANT one fragments; the probe-mode sockets' 1200 bytes go out as one packet with DF), `test_udp_win.c` `udp_win_fd_df_probe`, Android `DfProbeAndroidTest.portableSocketIsInProbeModeOnBothHalves` (device test); and keeps its datagrams within 1200 bytes: PMTUD is inactive there

**Tests that pin it.**

- `test_udp.c` `udp_df_probe_mode` (Linux and Apple), `udp_recverr_port_unreachable_keeps_socket`, `udp_ptb_ring`, `udp_emsgsize_counted` (Apple), `udp_recverr_local_emsgsize_queued`, `udp_recverr_ptb_parsed` and `udp_recverr_forged_ptb_keeps_sending` (Linux, in a user namespace, SKIP without one)
- `KslDatagramIoTest.negative_icmpPortUnreachableDoesNotKillTheSocket`
- `KslUdpSocketTest.grantedFlags`
- `KslDatagramIoTest.realUdpServerClient50MiBAccelerated`

**History.**

- 0.2.0: Apple — `IP_DONTFRAG`/`IPV6_DONTFRAG` (Darwin has no PMTUDISC modes)
- 0.2.0: Windows — `IP_DONTFRAGMENT`/`IPV6_DONTFRAG` plus `IP_MTU_DISCOVER`/`IPV6_MTU_DISCOVER = PROBE` where the system has it (Windows 10 1703+; verification on a Windows host pending)
- 0.3.0: Linux and Android also set `IP_RECVERR`/`IPV6_RECVERR` and drain the ICMP error queue, so an ICMP port or host unreachable never fails the receive and ICMP Packet Too Big messages reach the core as hints (`ksl_udp_take_ptb`)

**Peer interop notes.**

- `ksl_udp` (Linux, Android) — `IP_PMTUDISC_PROBE` + `IPV6_DONTFRAG`, not `_DO` (CVE-2024-53259 quic-go)

## <a id="s3-probing-black-holes-ptb-timers"></a>§3, §4.3, §4.6, §5.1.1 — probing, black holes, Packet Too Big, timers

Status: 🔶 since 0.3.0 · [summary](../rfc-compliance.md#quic)

**Requirement.** The DPLPMTUD rules RFC 9000 §14.3 takes from this document, item by item.

**How it is met.**

- §3 item 7 and RFC 9000 §14.4 (probe loss is no congestion signal): probes are tracked for loss (`SentFrames.PMTU_PROBE`) but never counted toward the congestion window, and their loss reaches no controller; a PLPMTU raise does not raise the window either: `onMtuUpdate` of NewReno and CUBIC sets only the segment size and the minimum window (`NewReno.kt`, `Cubic.kt`), BBR recomputes its initial window only before anything was delivered (`Bbr.kt`) — `core.PmtudTest.probeLossNotCongestion` (a transfer during the search on a link that drops every probe: no congestion event), `.ccNotifiedOnMtuChange`
- §4.3 black-hole detection: three lost packets above 1200 bytes with no later full-size packet acknowledged, or two consecutive PTOs while an ack-eliciting packet above 1200 bytes is unanswered, fall back to 1200 and pause the search 60 s; a full-size packet acknowledged afterwards undoes the verdict (details in the [RFC 9000 §14 row](9000.md#s14-dplpmtud-mtu-1200-minimum)) — `core.PmtudTest.blackHoleFallsBackTo1200AndPauses60s`, `.congestionBurstDoesNotFallBack`, `.stalledPeerIsNotABlackHole`, `.unansweredSmallPacketsAreNotABlackHole`
- §4.6.1, §4.6.2 Packet Too Big validation: a PTB is a hint (`QuicConfig.pmtudIcmpHints`): it must quote one of the connection's packets on its active path (our ID or the path's peer ID), come for `path.remote` on that socket, claim a size the path sent more than, and leave at least 1200 bytes of payload; at or above the current size it ends the larger probes at once ("PLPMTU < PL_PTB_SIZE < PROBED_SIZE ... The PLPMTU is not updated"); below it ("BASE_PLPMTU <= PL_PTB_SIZE < PLPMTU ... The PLPMTU SHOULD be set to BASE_PLPMTU") the size drops to 1200 at once, provisionally as RFC 9000 §14.2.1 allows ("Any reduction in QUIC's maximum datagram size in response to ICMP messages MAY be provisional until QUIC's loss detection algorithm determines that the quoted packet has actually been lost"): one probe of the old size goes first, its acknowledgment restores the old size and search state, and once loss detection fails it the search starts with the PTB size ("The PL_PTB_SIZE reported in the PTB message can be used to initialize a search algorithm"), without the black-hole pause. The PTB never sets the size ("MUST NOT be used directly to set the PLPMTU"): only the base or an acknowledged probe does. A probe of the old size acknowledged after a drop, also late, suspends PTB processing for 600 s (§8: "a PL sender could therefore suspend processing of PTB messages (e.g., in a robustness mode after detecting that subsequent probes actually confirm that a size larger than the PTB_SIZE is supported by a path)"), and only a probe sent after the drop counts (a probe sent before it, acknowledged after, neither restores nor suspends), so validated but forged PTBs hold the path at 1200 for about one probe round trip per 600 s (the probe goes once the congestion window has room, `Pmtud.deferProbe`). A quote that matched no connection ID bytes (zero-length IDs) is ignored altogether, neither lowering the size nor capping the search, RFC 9000 §14.2.1 asks for "connection IDs" "when possible" and the address and port alone are what an off-path attacker guesses. A congestion window still at its initial value when the size drops is lowered with it (RFC 9002 §7.2) and not raised on a restore (§3 item 7: "An update to the PLPMTU (or MPS) MUST NOT increase the congestion window measured in bytes"); at most 64 PTBs a second per endpoint are examined — `core.PmtudTest.negative_ptbWithForeignCidIgnored`, `.negative_ptbBelowQuicMinimumIgnored`, `.ptbQuotingAProbeEndsThatSizeAtOnce`, `.negative_ptbFloodIsRateLimited`, `.negative_forgedPtbDropIsProvisionalAndSuspendsPtbs`, `.negative_forgedPtbsCannotHoldThePathAtTheBase`, `.ptbDropsToBaseThenSearchesFromItsSize`, `.negative_aLateAckOfTheOldSizeAfterTheDropStoodRestoresItAndSuspendsPtbs`, `.negative_lossesOfPacketsLargerThanTheSizeInUseAreNoBlackHole`, `.ptbDuringABulkTransferDropsToBaseWithoutBlackHolePause`, `.negative_ptbSequencesKeepTheSearchSafeAndLive`, `.negative_aProbeSentBeforeThePtbNeitherOverturnsItNorRaisesTheSize`, `.negative_ptbBelowTheMtuWithZeroLengthIdsIsIgnored`, `.negative_ptbAboveTheMtuWithZeroLengthIdsDoesNotCapTheSearch`, `.negative_aProbeOfAReplacedSearchRaisesNothing`
- §5.1.1 timers and constants. A probe fails when QUIC's loss detection declares it lost (RFC 9002 packet or time threshold), but never earlier than 1 s after it was sent: the next probe goes at the later of the two (`Pmtud.minProbeTimer`, "This value MUST NOT be smaller than 1 second"); a probe loss detection never judges fails 16 s after it was sent, or 3 × PTO when that is longer (`Pmtud.probeTimer`). An acknowledgment that comes after the verdict still confirms the size (`Pmtud` keeps the packet numbers of its last four probes and matches the ACK ranges against those declared lost), except for a probe sent before a black-hole verdict. MAX_PROBES 3 (a size is given up after three failed probes, about 3 s on a short path; the one probe of the old size after a Packet Too Big only decides whether the drop to the base stands, and the search may try that size again); PMTU_RAISE_TIMER 600 s (`Pmtud.research`); no CONFIRMATION_TIMER (an acknowledged PL, RFC 9000 §14.3.2). A size settled by a Packet Too Big (§4.6.2) or the kernel's EMSGSIZE for the probe is given up at once; the interval between probes is at least an RTT (§8) — `core.PmtudTest.negative_aLostProbeFailsNoEarlierThanOneSecondAfterItWasSent`, `.searchStopsBelowLinkMtu` (a 1400-byte path settles within 10 s), `core.CongestionWindowTest.aProbeDeclaredLostAndThenAcknowledgedRaisesTheMtu`, `core.PmtudTest.negative_aLateAckOfAProbeSentBeforeABlackHoleVerdictRaisesNothing`, `.atMostThreeLostProbesPerSize`, `.researchAfter600s`, `.ptbDropsToBaseThenSearchesFromItsSize`
- Is a loss-detection verdict a PROBE_TIMER? RFC 9000 §14.3: "DPLPMTUD relies on tracking loss or acknowledgment of QUIC packets that are carried in PMTU probes"; RFC 8899 §4.2 lets an acknowledged PL's own mechanism ("Transport protocols can include end-to-end methods that detect and report reception of specific datagrams that they send") "be used by DPLPMTUD to acknowledge reception of a probe packet", and §5.1.1 allows "a single timer" for the timer functions. But §5.1.1 bounds PROBE_TIMER for every PL ("This value MUST NOT be smaller than 1 second and SHOULD be larger than 15 seconds"; only the CONFIRMATION_TIMER has an exception for acknowledged PLs), §5.2 counts a probe as failed when it is "not acknowledged within the period of the PROBE_TIMER", and RFC 9000 states no other value. So the 1 s floor is kept, and the 15 s SHOULD is a deviation, not an interpretation (see Open items)

**History.**

- 0.3.0 cross-review: a probe declared lost by loss detection counted as failed at once and the next went out, so a size was given up within a few RTTs (about 100 ms on a 20 ms path), below §5.1.1's 1 s floor, and the row recorded loss detection "in the place of PROBE_TIMER". quic-go also fails a probe when loss detection declares it lost; ngtcp2 runs a timer of its own of one PTO, three for the last probe of a size (`ngtcp2_pmtud_probe_sent`), below the floor as well. A 16 s PROBE_TIMER per probe was tried first: a search on a tunnel narrower than the upper bound then took 2–3 minutes to settle, and the owner chose the floor of the MUST with the loss-detection verdict instead
- 0.3.0 cross-review: a probe declared lost and acknowledged after all never counted as acknowledged (lost probes are not in loss detection's spurious-loss memory); the size is confirmed now

- 0.3.0 red-team: a validated PTB below the size in use kept the size until three confirmation probes of it were lost (§4.6.2 says the PLPMTU SHOULD be set to BASE_PLPMTU); it now drops to the base at once, provisionally (RFC 9000 §14.2.1), with the §8 suspension bounding forged ones

**Open items.**

- Apple, portable socket: DF is the JDK's `IP_DONTFRAGMENT` (`IP_DONTFRAG` / `IPV6_DONTFRAG`; Darwin has no PMTUDISC modes). Known: Darwin clamps a path MTU from an ICMPv6 Packet Too Big to at least 1280, above the 1248 bytes a 1200-byte payload needs over IPv6. Unverified: whether a forged IPv4 Fragmentation Needed lowers what a DF socket may send to a peer (no ICMP injection on the macOS host); if it does, the refusal ends the connection as in DO mode.
- §5.1.1 "SHOULD be larger than 15 seconds" is not followed (owner decision, 0.3.0): with MAX_PROBES 3, every size above the path's MTU would cost about 48 s, and a search on a tunnel 2–3 minutes during which larger datagrams stay unused. The SHOULD guards a PL that cannot tell a late acknowledgment from a loss (its guidance is the UDP usage guidelines, BCP 145 §3.1.1); QUIC's loss detection waits for the packet or time threshold (RFC 9002 §6.1, robust to reordering), a late acknowledgment still confirms the size, and the 1 s floor of the MUST holds
