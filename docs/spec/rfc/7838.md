# RFC 7838 — HTTP Alternative Services

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="alt-svc"></a>Alt-Svc

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7838.

**Requirement.** Alt-Svc.

**Recorded status.** ✅ 0.2.0 (client: `AltSvcCache`/`AltSvcStore` — a cache by origin, `ma` 86400, replacement by a new header, `clear`, a 421 from the origin changes nothing (RFC 9110 §15.5.20: not authoritative) and a 421 over HTTP/3 from an alternative removes that alternative only (§6), an unprivileged alternative port for a privileged origin is dropped, only from responses over verified TLS, `Alt-Used`, `persist` and `clearOnNetworkChange` — `AltSvcTest.*` (including `negative_altSvcFromUnverifiedTls`, `.status421LeavesEntries`, `.removeAlternativeKeepsTheOthers`); the persistent store `FileAltSvcStore` (one TSV file, atomic rewrite, expired entries are dropped on load) — `FileAltSvcStoreTest.*`, `ClientAltSvcTest.*`, including `clearOverH1RemovesCachedAlternative`: an `Alt-Svc` of a response over h1.1 is processed even while the alternative is cached — broken, lost the race, fallback — a new list or `clear` replaces the entry, otherwise a stale one would be kept until `ma` (review), and `misdirectedOverH1KeepsCachedAlternative`; server ✅: `Alt-Svc: h3=":<port>"; ma=86400` in h1.1 responses of the TLS connector where h3 is up (on HTTP/2 an ALTSVC frame since 0.3.0, [§4](#s4-altsvc-frame)); the application's own header and a 421 response are left untouched; `altSvc = false` — `ServerH3Test.altSvcOnH1Responses`, `.altSvcDisabled`, `.appAltSvcNotOverwritten`, `ServerH3DisabledTest.*`)

**How it is met.**

- cache by origin, `ma` 86400, `clear`, 421, ports, `Alt-Used`, `persist`
- the server header with a switch
- clocks: freshness (`ma`) runs on the wall clock, since an entry's expiry is epoch time that `FileAltSvcStore` keeps
  across restarts, where a monotonic clock would start over (a wall-clock step moves every expiry by the step: forward
  expires early, backward keeps an entry longer by at most the step); broken marks, kept in memory only, run on a
  since 0.3.0 on both a monotonic clock and the wall clock, ending on whichever passes first (`BrokenAltSvc`): a backward
  step of the wall clock cannot extend a backoff and deep sleep, which stops the monotonic clock on Android and iOS,
  cannot stretch it (`ClientAltSvcTest.negative_brokenMarksRunOnAMonotonicClock`, `BrokenAltSvcTest.negative_markEndsOnEitherClock`)
- the later rows refine it: [`clear` in a list, port digits, `Age`](#s3-clear-port-age), [§4 ALTSVC frame](#s4-altsvc-frame),
  [§9.4 clearing](#s9-4-clear-origin-data), [stored records](#s3-stored-records), [choice of alternative](#s2-4-choice)

## <a id="s2-2-cache-bounds"></a>§2.2, §3 — cache bounds

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7838 §2.2, §3, §9.4 (cache bounds). Until 0.3.0 the row also cited §9.4, which it does not cover: §9.4's
requirement (removal with origin-specific data) is [its own row](#s9-4-clear-origin-data) since 0.3.0.

**Requirement.** The client keeps at most 8 alternatives per origin (the first of the header, in the server's order of preference) and 1000 origins, least recently used dropped first, in both built-in stores and in the broken marks.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- `FileAltSvcStore` reads at most 8000 records, always replaces the cached alternatives with a new header in memory (a shorter `ma` shortens the expiry, §3) and skips only the disk write when the expiry moved later by less than half its lifetime, and is written outside the engine's lock (a write survives the cancellation of its request; a pending one is flushed when the engine closes)

**Tests that pin it.**

- `AltSvcTest.negative_altSvcEntriesPerOriginCapped`, `FileAltSvcStoreTest.negative_altSvcStoreBoundedOrigins`, `.identicalPutDoesNotRewrite`, `.refreshedExpiryRewrittenOnlyPastHalfLifetime`, `.shorterMaxAgeReplacesCachedExpiry`, `.writesBehindTheCacheAreDeferredAndOrdered`, `ClientAltSvcTest.deferredAltSvcWriteSurvivesCancellation`, `BrokenAltSvcTest.negative_brokenMarksBounded`

## <a id="s2-4-race-and-fallback"></a>§2.4; RFC 8305 §5 — race and fallback

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7838 §2.4; RFC 8305 §5 (race and fallback).

**Requirement.** The h3/h1 connection race makes exactly one HTTP/1.1 attempt: when both setups fail the race's HTTP/1.1 failure is the result (before 0.2.0 a second TCP connection was opened).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- an HTTP/1.1 connection that finished just as HTTP/3 won, or while the caller was cancelled, is closed, not leaked
- a fallback that succeeds after a connection-level HTTP/3 failure (setup, QUIC transport, an H3 connection error) marks the alternative broken for the origin (5 min, doubling), as a lost race already did — a single stream reset, a malformed message or a locally refused field section does not, nor does the server's CONNECTION_REFUSED since 0.3.0 ([CONNECTION_REFUSED is no broken alternative](#s2-4-connection-refused))

**Tests that pin it.**

- `ProtocolRaceTest.losingH1ResultIsHandedToOnLoser`, `.loserIsHandedOverWhenCallerIsCancelled`, `ClientFallbackTest.raceFailureMakesOneH1Attempt`, `.h3FailureWithH1SuccessMarksBroken`, `.streamErrorDoesNotMarkAlternativeBroken`

## <a id="s3-alt-svc-on-http-3-responses"></a>§3, §3.1 (Alt-Svc on HTTP/3 responses, quoted-string, `ma`) — Alt-Svc on HTTP/3 responses

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 7838 §3, §3.1 (Alt-Svc on HTTP/3 responses, quoted-string, `ma`).

**Requirement.** The client processes `Alt-Svc` on every response of an origin over verified TLS, HTTP/3 ones included: `clear` or a new list received over the alternative replaces the cached alternatives (before 0.2.0 only HTTP/1.1 responses were looked at, so a client on HTTP/3 kept a retired alternative until `ma` ran out).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- quoted strings are processed per RFC 9110 §5.6.4 — a quoted-pair is one character, an escaped `"` neither ends the string nor lets a comma split the list
- `ma` is delta-seconds (`1*DIGIT`, a sign makes the alternative invalid), and one too large to represent counts as 2147483648 (§3.1 takes delta-seconds from RFC 9111 §1.2.2, whose MUST is addressed to a cache; the Alt-Svc cache follows it; 0.2.1 review, before the alternative was dropped)
- the alt-authority's host must be an RFC 3986 `host` (§3: `uri-host ":" port`): an IP-literal in brackets, or a reg-name / IPv4 address of unreserved, pct-encoded and sub-delims characters; any other (a space, a control character, a bare IPv6 address) makes the alternative malformed and it is skipped (0.3.0; before, the text was taken as it was and reached the diagnostics log line)

**Tests that pin it.**

- `ClientAltSvcH3Test.clearOverH3RemovesCachedAlternative`, `.newListOverH3ReplacesCachedAlternative`, `AltSvcTest.quotedPairsAreProcessed`, `.overflowingMaIsCapped`, `.negative_altSvcHostThatIsNoUriHostIsSkipped`

## <a id="s2-2-network-change"></a>§2.2 — network change

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7838 §2.2 (network change).

**Requirement.** Section 2.2: "clients SHOULD remove from cache all alternative services that lack the "persist" flag
with the value "1" when they detect such a change, when information about network state is available." Section 3.1: "By
default, cached alternative services will be cleared when the client detects a network change."

**Recorded status.** ✅ 0.3.0 (0.2.1: only changes `networkId` reported while the engine ran; a restart on another
network, and the networks `connectionMigration` follows, were not seen)

**How it is met.**

- the engine's network is `networkId()`, or, while `networkId` is not set, the networks `connectionMigration` follows
  (`Http3ConnectionMigration.networks`: the system source of the `followDefaultNetwork` factories, collected while the
  client is open; `KuicksilverEngine.checkNetwork`); without either the engine has no information about network state
  and sees no change
- a change drops the alternatives without `persist=1` (`http3 { clearOnNetworkChange }`, true by default since 0.2.1)
  and resets the broken marks, QUIC confirmation and the HTTPS record cache; `persist=1` alternatives stay
- across restarts, with `networkId`: the store keeps the network its entries were learned on (`AltSvcStore.networkId`;
  `FileAltSvcStore` writes it as a first `network` line, which earlier versions skip), and the first network the engine
  sees is compared with it; an unknown one (an older file, an application's store that keeps none) counts as another
  network
- a followed network is compared in memory only, never stored: on Android the factory's value is the `Network`, a number
  the system gives each new connection (every switch is seen; the number is reused after a reboot); on iOS and macOS it
  is the default path's identity (`nwPathIdentities()`: interface, gateways, the interface's IPv4 addresses with masks
  and global IPv6 /64 prefixes), so a move between two Wi-Fi networks on one interface is a change too, and a path that
  tells neither gateways nor addresses counts as a change at each update. Since neither survives a restart, the first
  value after a start counts as a change, and the alternatives and HTTPS records learned before it came are dropped the
  same way; requests wait for that value until one deadline, 200 ms after the client was created, then go on without
  it. A source that fails or ends leaves the engine without network information (HTTPS records dropped and no longer
  kept); a store that throws while a change is applied loses that change, not the following. Network state the platform
  does not expose (two networks with the same gateways and addresses) is not seen; `networkId` gives an identity of the
  application's own

**Tests that pin it.**

- `AltSvcTest.networkChangeClearsNonPersistent`, `ClientAltSvcTest.networkChangeForgetsNonPersistentAlternativesByDefault`,
  `.negative_networkChangeAcrossRestartForgetsNonPersistent`, `.negative_connectionMigrationNetworkChangeForgetsNonPersistent`,
  `.negative_followedNetworkIsNotTrustedAcrossRestarts`, `.negative_failingStoreDoesNotStopNetworkFollowing`,
  `.negative_silentNetworkSourceDelaysNoRequestPastTheDeadline`, `NwPathIdentityTest.negative_sameInterfaceAnotherNetworkIsAnotherIdentity`,
  `ClientHttpsRecordTest.negative_recordsKeptBeforeTheFirstNetworkAreFlushed`, `.negative_failedNetworkSourceStopsCaching`,
  `FileAltSvcStoreTest.negative_networkIdSurvivesANewInstance`

## <a id="s3-clear-port-age"></a>§3, §3.1 — `clear` among alternatives, port digits, `Age`

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Section 3: "A field value containing the special value "clear" indicates that the origin requests all
alternatives for that origin to be invalidated (including those specified in the same response, in case of an invalid
reply containing both "clear" and alternative services)"; `alt-authority` is `[ uri-host ] ":" port` with RFC 3986's
`port = *DIGIT`. Section 3.1: an alternative "is considered fresh for 24 hours from generation of the message"; "The
delta-seconds value indicates the number of seconds since the response was generated for which the alternative service
is considered fresh"; "See Section 4.2.3 of [RFC7234] for details on determining the response age" (now RFC 9111).

**Recorded status.** ✅ 0.3.0 (before: only a value that was `clear` as a whole cleared; `toIntOrNull` took `+443` as a
port; freshness counted from receipt and ignored `Age`)

**How it is met.**

- `AltSvcParser.parse`: any top-level list element that is exactly `clear` (case-sensitive) clears the origin, whatever
  else the value or another field line lists
- `AltSvcParser.portOf`: digits only, 1..65535 (a sign, a space or hex makes the alternative malformed), on the header
  path and for stored records
- `AltSvcCache.onResponse`: the expiry is the generation time plus `ma`, the generation time being the receipt time
  minus `corrected_age_value = age_value + response_delay` (RFC 9111 §4.2.3: it "MAY be used as the
  corrected_initial_age"); `age_value` is the first member of the `Age` field, an invalid one ignored (RFC 9111 §5.1,
  "SHOULD use the first member", "SHOULD ignore the field"), one too large 2147483648 (§1.2.2); the response delay is
  the time from the request (`HttpResponseData.requestTime`) to the response. The `Date`-based `apparent_age` is not
  used (§4.2.3 offers it as the conservative option only)

**Tests that pin it.**

- `AltSvcTest.negative_clearAmongAlternativesInvalidatesThemAll`, `.negative_altSvcPortWithSignIsSkipped`,
  `.negative_altSvcFreshnessAccountsForAge`, `.negative_invalidOrListAgeHandledAsRfc9111Says`

## <a id="s4-altsvc-frame"></a>§3, §4 — the ALTSVC HTTP/2 frame

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Section 3: "When using HTTP/2 ([RFC7540]), servers SHOULD instead send an ALTSVC frame (Section 4). A
single ALTSVC frame can be sent for a connection; a new frame is not needed for every request. Note that, despite this
recommendation, Alt-Svc header fields remain valid in responses delivered over HTTP/2." Section 4: "The ALTSVC
frame type is 0xa"; its payload is `Origin-Len (16)`, `Origin?`, `Alt-Svc-Field-Value`; "The ALTSVC frame does not
define any flags"; "An ALTSVC frame from a server to a client on a stream other than stream 0 indicates that the conveyed
alternative service is associated with the origin of that stream"; on stream 0 with the origin in the Origin field, and
"An association with an origin that the client does not consider authoritative for the current connection MUST be
ignored"; "A device acting as a server MUST ignore it"; "An ALTSVC frame on stream 0 with empty (length 0) "Origin"
information is invalid and MUST be ignored. An ALTSVC frame on a stream other than stream 0 containing non-empty
"Origin" information is invalid and MUST be ignored"; "Receiving an ALTSVC frame is semantically equivalent to receiving
an Alt-Svc header field." "An intermediary MUST NOT forward ALTSVC frames": Kuicksilver is no intermediary.

**Recorded status.** ✅ 0.3.0 (before: the server put the `Alt-Svc` field on every HTTP/2 response and never sent the
frame; the client skipped the frame as an unknown type)

**How it is met.**

- `kuicksilver-http2`: `FrameType.ALTSVC`, `FrameEncoder.altSvc`, `Frame.AltSvc`; the decoder takes the frame only on a
  client (`FrameDecoder.altSvcFrames`), so a server skips it as an unknown frame; a client core reports a valid one as
  `H2Event.AltSvc` and ignores stream 0 with an empty Origin, another stream with a non-empty one, a stream it never
  opened, and a malformed frame (Origin-Len past the payload); every ALTSVC costs a glitch (RFC 9113 §10.5)
- server (`H2ConnectionCore.sendAltSvc`, `ktor-server h2/H2AltSvc.kt`, `H2Response`): the engine's value (`h3=":<port>";
  ma=86400`, or `clear` under `Http3Advertising.Clear`/`Drain`) goes out as an ALTSVC frame on the request stream, empty
  Origin, queued with the control frames ahead of the response's HEADERS, once per origin (the request's `:authority`)
  and value on the connection, and again 12 hours (half the advertised `ma`) after the last one, so a client whose entry
  expired or was cleared learns it again on a long-lived connection. The field stays on every HTTP/2 response too, with
  the same reading of the value: section 3 keeps it valid, and clients that read only the header (curl, Kuicksilver
  clients before 0.3.0, other stacks) would otherwise never learn HTTP/3 from an HTTP/2 server. An application's own
  `Alt-Svc` field and a 421 are left as on HTTP/1.1
- client (`H1Pool`, `KuicksilverEngine.onAltSvcFrame`, `AltSvcCache.onAltSvcFrame`): a frame on a request stream is for
  the connection's origin (the client's HTTP/2 connections serve one origin each), one on stream 0 only when its Origin
  is that origin (`isAltSvcFrameOrigin`, RFC 6454 §6.2 serialization); learned as a header is, in `Auto`, over verified
  TLS, never through a proxy. Frames wait as the latest value per origin (at most 1000 origins) and one coroutine learns
  them in order of arrival: the last frame of an origin holds, a flood costs one value per origin, and a store that
  throws loses that frame only

**Tests that pin it.**

- `AltSvcFrameTest.serverSendsAltSvcOnTheStreamBeforeItsResponse`, `.serverAltSvcFrameLayout`,
  `.negative_serverAltSvcNeedsAnOpenStreamAndAFittingValue`, `.negative_clientIgnoresInvalidAltSvcFrames`,
  `.negative_serverIgnoresAltSvcFrames`, `ServerH2Test.negative_altSvcGoesOutAsAnAltSvcFrameOnH2`,
  `H2AltSvcTest.negative_frameRefreshedAfterTheIntervalAndOnAChange`, `.negative_unsentFrameIsSentOnTheNextStream`,
  `ClientAltSvcTest.negative_altSvcFrameOverH2IsLearned`, `.negative_altSvcFramesLearnedInOrderAndBounded`, `.negative_failingStoreDoesNotSilenceAltSvcFrames`,
  `AltSvcTest.negative_altSvcFrameOriginMustBeTheConnectionsOrigin`;
  h2spec 2.6.0 (`tools/interop/h2spec.sh`) passes all 146 cases

**Notes.** Section 4: "it would be unwise to mix the use of Alt-Svc header fields with the use of ALTSVC frames, as the
sequence of receipt might be hard to predict." The engine's frame and field come from one reading of the value per
response, so they never disagree, and a change of the value (`http3Advertising`) reaches both on the next response; the
order of receipt then does not matter. When the application sets its own field, the engine sends no frame for that
response.

## <a id="s9-4-clear-origin-data"></a>§9.4 — removal with origin-specific data

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** "In a user agent, any alternative service information MUST be removed when origin-specific data is
cleared (typically, when cookies [RFC6265] are cleared)."

**Recorded status.** ✅ 0.3.0 (before: no supported way; `AltSvcStore` had no clear-all, and changing the store from
outside raced the engine's lock)

**How it is met.**

- `HttpClient.clearAlternativeServices(origin)` (experimental; `KuicksilverEngine.clearAlternativeServices`): under the
  engine's lock, the origin's cached alternatives (persistent ones too), its broken marks and its RTT, or without an
  origin everything (`AltSvcStore.clear()`, `BrokenAltSvc.clear`, the RTT map, the networks where QUIC was confirmed);
  a `FileAltSvcStore` is written before the call returns
- `AltSvcStore.clear()` has a default that throws `UnsupportedOperationException`, so a store written for 0.2.x keeps
  working; for such a store a full clear removes the origins the engine saw during this run (at most the 1000 most
  recent) one by one, logs a warning that entries of other origins it kept from earlier may remain and returns false
  (`clearAlternativeServices` answers whether everything asked for went); the KDoc asks implementers to override it to
  meet this section fully
- the library has no cookie store of its own: the application calls it where it clears cookies or site data (the guide
  says so); open HTTP/3 connections stay (`closeHttp3Connections()`)

**Tests that pin it.**

- `ClientAltSvcTest.negative_clearAlternativeServicesRemovesOriginData`, `FileAltSvcStoreTest.negative_clearRemovesEveryOriginOnDisk`,
  `AltSvcTest.negative_inMemoryStoreClearForgetsEverything`, `.negative_storeWithoutClearFallsBackToTheOriginsSeen`,

## <a id="s2-4-choice"></a>§2.4 — choice among cached alternatives

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Section 2.4: a client "SHOULD use that alternative service for all requests to the associated origin as
soon as it is available, provided the alternative service information is fresh"; "If a client becomes aware of multiple
alternative services, it chooses the most suitable according to its own criteria"; "if the connection to the alternative
service fails or is unresponsive, the client MAY fall back to using the origin or another alternative service".

**Recorded status.** ✅ 0.3.0 (before: the first fresh alternative only, so a broken mark on it sent the call to TCP even
with a second fresh one cached)

**How it is met.**

- `AltSvcCache.h3For` with the engine's "not marked broken": the first fresh alternative in the server's order of
  preference (section 3) that is not broken; when all are, the first one, whose mark sends the call to TCP
- one alternative per call: a call does not try a second alternative after the first failed in that call (the fallback
  is to the origin over TCP, [§2.4; RFC 8305 §5](#s2-4-race-and-fallback)); the next call takes the next unbroken one

**Tests that pin it.**

- `ClientAltSvcTest.negative_brokenFirstAlternativeUsesTheNextOne`

## <a id="s3-server-clear"></a>§2.2, §3 — server `clear` at run time

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Section 3: "A field value containing the special value "clear" indicates that the origin requests all
alternatives for that origin to be invalidated (including those specified in the same response, in case of an invalid
reply containing both "clear" and alternative services)." Section 2.2: "Alternative services are fully authoritative for
the origin in question, including the ability to clear or update cached alternative service entries, extend freshness
lifetimes, and any other authority the origin server would have." A server that stops offering HTTP/3 sends `clear`, on
the origin and on the alternative, so clients drop the alternative it advertised with `ma=86400` instead of trying it
until it expires.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `KuicksilverApplicationEngine.http3Advertising` (`Http3Advertising.On`, `Clear`, `Drain`), a volatile value the
  engine's `Alt-Svc` providers read as each response head goes out: HTTP/1.1 (`TcpListener.kt`, `http3AltSvc`;
  `h1/H1Response.kt`) and HTTP/3 (`Http3Listener.kt`, `h3AltSvc`; `h3/H3Call.kt`), so the next response on a keep-alive
  connection follows a change; before 0.3.0 the HTTP/1.1 value was fixed per TCP connection
- HTTP/1.1: `On` sends `h3=":<port>"; ma=86400`, `Clear` and `Drain` send exactly `clear`; HTTP/2: the same field, and
  the same value in an ALTSVC frame ([§4](#s4-altsvc-frame)), read as each response head goes out and sent again when it
  changes; HTTP/3:
  nothing under `On`, `clear` under `Clear` and `Drain`; only where the engine sends `Alt-Svc` at all (a TLS connector serving HTTP/3,
  `altSvc = true`); an application's own `Alt-Svc` and a 421 are left as they are
- the switch is not persisted (`persist`, section 3.1, concerns the client's cache): a new engine starts at `On`

**Tests that pin it.**

- `ServerHttp3AdvertisingTest.clearSendsAltSvcClearOnTheSameConnection`, `.h3ResponsesSayClearWhileWithdrawn`,
  `.altSvcOffSendsNoHeaderInAnyMode`, `.negative_appAltSvcNotOverridden`, `.negative_appAltSvcAnd421NotOverriddenOverH3`, `.backToOnAdvertisesAndAcceptsAgain`

**Notes.** A client may keep using an HTTP/3 connection it already has after `clear` (section 2.2 lets existing
connections continue); `Drain` moves those to TCP with GOAWAY. WebSocket (RFC 9220) and WebTransport Extended CONNECT
answers, error answers included, carry no engine `clear` on HTTP/3: only plain responses do, and the next one on the
same connection withdraws the alternative.

## <a id="s2-4-connection-refused"></a>§2.2, §2.4, §3; RFC 9000 §5.2.2, §10.2.3, §20.1 — CONNECTION_REFUSED is no broken alternative

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** RFC 9000 section 5.2.2: "If a server refuses to accept a new connection, it SHOULD send an Initial
packet containing a CONNECTION_CLOSE frame with error code CONNECTION_REFUSED"; section 20.1 defines CONNECTION_REFUSED
(0x02) as "The server refused to accept a new connection". A server does that when it cannot take a client now (a full
accept queue, a drain, a stop), which says nothing about the alternative itself. RFC 7838 section 2.2 makes the
origin's alternatives authoritative until they expire or the origin clears or replaces them (section 3), and section
2.4 lets a client fall back when an alternative fails. So the refused call falls back, and the alternative stays valid:
marking it broken for minutes to days after a refusal would put a whole origin on HTTP/1.1 through one rolling restart
of a multi-instance server, although the next connection (to another instance behind the same address, or to the same
one once it takes clients again) would be accepted.

**Recorded status.** ✅ 0.3.0 (before 0.3.0 the refusal marked the alternative broken for 5 minutes, doubling up to
2 days)

**How it is met.**

- `isTransientRefusal` (`KuicksilverEngine.kt`): a `QuicException.ConnectionLost.TransportClosed` from the peer with
  code `TransportError.CONNECTION_REFUSED`, as the failure or wrapped as not sent, whether it came at the first Initial
  (stateless) or on an established connection (a Kuicksilver server closes a connection whose handshake completed into a
  full accept queue with it, "accept queue full", `EndpointLoop.kt`; quic-go `server.go:886` `handleNewConn` likewise)
- the race's losing HTTP/3 setup and a request's fallback after an HTTP/3 failure (`marksAlternativeBroken`) skip the
  broken mark for it; the call reports `ProtocolDiagnostics.fallback = Refused` with the failure in `h3Failure`, the
  `Alt-Svc` cache keeps the alternative, and the next call races HTTP/3 again, as after `FallbackReason.H3NotReady`;
  repeated refusals escalate nothing
- any other close of the setup by the server (another transport code, a TLS alert), version negotiation without a common
  version and a handshake timeout still mark the alternative broken (section 2.4)
- the h3/h1 race still makes the one HTTP/1.1 attempt per call ([§2.4; RFC 8305 §5](#s2-4-race-and-fallback)); HTTP/3
  connects to the first address of the resolution and does not try another address of the same alternative after a
  refusal (no address race over QUIC, docs/guide/ktor.md)
- peers: quic-go's server sends CONNECTION_REFUSED for a full queue or a closing server (`server.go:876` `refuseNewConn`,
  `server.go:886` `handleNewConn`), quinn's `Endpoint::refuse` likewise (`quinn-proto/src/endpoint.rs:829`): a server-side load signal

**Tests that pin it.**

- `ClientFallbackTest.connectionRefusedFallsBackWithoutMarkingBroken`, `.refusedRetryAfterRejectionDoesNotMarkBroken`
  (the request's own fallback: rejected unprocessed, repeated on a new connection that is refused), `.negative_otherSetupCloseStillMarksBroken`,
  `ProtocolDiagnosticsTest.connectionRefusedIsTransient`, `.negative_otherSetupFailuresAreNotTransient`

## <a id="s2-4-close-after-goaway"></a>§2.4; RFC 9114 §5.2 — a close after GOAWAY is no broken alternative

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** RFC 9114 section 5.2: "An endpoint that completes a graceful shutdown SHOULD use the H3_NO_ERROR error
code when closing the connection", after GOAWAY; a server that stops gives open requests a grace period and then closes
what is left. That is the server ending the connection in order, not the alternative failing (RFC 7838 section 2.4):
marking it broken would put the origin on HTTP/1.1 for minutes to days after every rolling restart that caught a long
request (a long poll, a server-sent event stream, a slow response).

**Recorded status.** ✅ 0.3.0 (before 0.3.0 such a close marked the alternative broken for 5 minutes, doubling up to 2
days, when a request in flight fell back to HTTP/1.1)

**How it is met.**

- `H3Pool.execute`: a request whose connection fails with a graceful close by the peer (`isPeerShutdownClose`: an
  application CONNECTION_CLOSE with H3_NO_ERROR, or with an unknown code, which reads as H3_NO_ERROR under RFC 9114
  section 9, or a transport close with NO_ERROR) after that connection received GOAWAY
  (`Http3Connection.goAwayReceived`) carries `H3ClosedAfterGoAwayKey`; the engine's fallback (`fallbackToH1`) then does
  not mark the alternative broken (`ProtocolDiagnostics.fallback` still says `Http3Error`, without `marked broken`)
- both are required: the GOAWAY (an H3_NO_ERROR close without one first still marks the alternative broken: it cannot be
  told from an unknown code) and H3_NO_ERROR (a close with an error code such as H3_INTERNAL_ERROR after GOAWAY still
  marks it: servers send GOAWAY early for other reasons too, such as a cap on requests per connection); a transport
  error code, a stream reset and a local failure are no such close
- the fallback itself is unchanged: only an idempotent request with a replayable body that has no response yet goes
  again over HTTP/1.1; a request above the GOAWAY id is repeated over HTTP/3 on a new connection (RFC 9114 section 5.2)

**Tests that pin it.**

- `ClientFallbackTest.closeAfterGoAwayDoesNotMarkBroken`, `.negative_errorCloseAfterGoAwayMarksBroken`,
  `.negative_closeWithoutGoAwayMarksBroken`,
  `ProtocolDiagnosticsTest.peerShutdownClose`
