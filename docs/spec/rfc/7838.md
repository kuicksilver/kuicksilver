# RFC 7838 — HTTP Alternative Services

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="alt-svc"></a>Alt-Svc

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7838.

**Requirement.** Alt-Svc.

**Recorded status.** ✅ 0.2.0 (client: `AltSvcCache`/`AltSvcStore` — a cache by origin, `ma` 86400, replacement by a new header, `clear`, 421 removes, an unprivileged alternative port for a privileged origin is dropped, only from responses over verified TLS, `Alt-Used`, `persist` and `clearOnNetworkChange` — `AltSvcTest.*`; the persistent store `FileAltSvcStore` (one TSV file, atomic rewrite, expired entries are dropped on load) — `FileAltSvcStoreTest.*` (including `negative_altSvcFromUnverifiedTls`), `ClientAltSvcTest.*`, including `clearOverH1RemovesCachedAlternative`: an `Alt-Svc` of a response over h1.1 is processed even while the alternative is cached — broken, lost the race, fallback — a new list or `clear` replaces the entry, otherwise a stale one would be kept until `ma` (review); server ✅: `Alt-Svc: h3=":<port>"; ma=86400` in h1.1 responses of the TLS connector where h3 is up; the application's own header and a 421 response are left untouched; `altSvc = false` — `ServerH3Test.altSvcOnH1Responses`, `.altSvcDisabled`, `.appAltSvcNotOverwritten`, `ServerH3DisabledTest.*`)

**How it is met.**

- cache by origin, `ma` 86400, `clear`, 421, ports, `Alt-Used`, `persist`
- the server header with a switch

## <a id="s2-2-cache-bounds"></a>§2.2, §3, §9.4 — cache bounds

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7838 §2.2, §3, §9.4 (cache bounds).

**Requirement.** The client keeps at most 8 alternatives per origin (the first of the header, in the server's order of preference) and 1000 origins, least recently used dropped first, in both built-in stores and in the broken marks.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- `FileAltSvcStore` reads at most 8000 records, always replaces the cached alternatives with a new header in memory (a shorter `ma` shortens the expiry, §3) and skips only the disk write when the expiry moved later by less than half its lifetime, and is written outside the engine's lock (a write survives the cancellation of its request; a pending one is flushed when the engine closes)

**Tests that pin it.**

- `AltSvcTest.negative_altSvcEntriesPerOriginCapped`, `FileAltSvcStoreTest.negative_altSvcStoreBoundedOrigins`, `.identicalPutDoesNotRewrite`, `.refreshedExpiryRewrittenOnlyPastHalfLifetime`, `.shorterMaxAgeReplacesCachedExpiry`, `.writesBehindTheCacheAreDeferredAndOrdered`, `ClientAltSvcTest.deferredAltSvcWriteSurvivesCancellation`, `BrokenAltSvcTest.negative_brokenMarksBounded`

## <a id="s2-4-race-and-fallback"></a>§2.4; RFC 8305 §5 — race and fallback

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7838 §2.4; RFC 8305 §5 (race and fallback).

**Requirement.** The h3/h1 connection race makes exactly one HTTP/1.1 attempt: when both setups fail the race's HTTP/1.1 failure is the result (before 0.2.0 a second TCP connection was opened).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- an HTTP/1.1 connection that finished just as HTTP/3 won, or while the caller was cancelled, is closed, not leaked
- a fallback that succeeds after a connection-level HTTP/3 failure (setup, QUIC transport, an H3 connection error) marks the alternative broken for the origin (5 min, doubling), as a lost race already did — a single stream reset, a malformed message or a locally refused field section does not, nor does the server's CONNECTION_REFUSED since 0.3.0 ([CONNECTION_REFUSED is no broken alternative](#s2-4-connection-refused))

**Tests that pin it.**

- `ProtocolRaceTest.losingH1ResultIsHandedToOnLoser`, `.loserIsHandedOverWhenCallerIsCancelled`, `ClientFallbackTest.raceFailureMakesOneH1Attempt`, `.h3FailureWithH1SuccessMarksBroken`, `.streamErrorDoesNotMarkAlternativeBroken`

## <a id="s3-alt-svc-on-http-3-responses"></a>§3, §3.1 (Alt-Svc on HTTP/3 responses, quoted-string, `ma`) — Alt-Svc on HTTP/3 responses

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 7838 §3, §3.1 (Alt-Svc on HTTP/3 responses, quoted-string, `ma`).

**Requirement.** The client processes `Alt-Svc` on every response of an origin over verified TLS, HTTP/3 ones included: `clear` or a new list received over the alternative replaces the cached alternatives (before 0.2.0 only HTTP/1.1 responses were looked at, so a client on HTTP/3 kept a retired alternative until `ma` ran out).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- quoted strings are processed per RFC 9110 §5.6.4 — a quoted-pair is one character, an escaped `"` neither ends the string nor lets a comma split the list
- `ma` is delta-seconds (`1*DIGIT`, a sign makes the alternative invalid), and one too large to represent counts as 2147483648 (§3.1 takes delta-seconds from RFC 9111 §1.2.2, whose MUST is addressed to a cache; the Alt-Svc cache follows it; 0.2.1 review, before the alternative was dropped)
- the alt-authority's host must be an RFC 3986 `host` (§3: `uri-host ":" port`): an IP-literal in brackets, or a reg-name / IPv4 address of unreserved, pct-encoded and sub-delims characters; any other (a space, a control character, a bare IPv6 address) makes the alternative malformed and it is skipped (0.3.0; before, the text was taken as it was and reached the diagnostics log line)

**Tests that pin it.**

- `ClientAltSvcH3Test.clearOverH3RemovesCachedAlternative`, `.newListOverH3ReplacesCachedAlternative`, `AltSvcTest.quotedPairsAreProcessed`, `.overflowingMaIsCapped`, `.negative_altSvcHostThatIsNoUriHostIsSkipped`

## <a id="s3-server-clear"></a>§2.2, §3 — server `clear` at run time

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Section 3: "A field value containing the special value "clear" indicates that the origin requests all
alternatives for that origin to be invalidated (including those specified in the same response, in case of an invalid
reply containing both "clear" and alternative services)." Section 2.2: "Alternative services are fully authoritative for
the origin in question, including the ability to clear or update cached alternative service entries, extend freshness
lifetimes, and any other authority the origin server would have." A server that stops offering HTTP/3 sends `clear`, on
the origin and on the alternative, so clients drop the alternative it advertised with `ma=86400` instead of trying it
until it expires.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `KuicksilverApplicationEngine.http3Advertising` (`Http3Advertising.On`, `Clear`, `Drain`), a volatile value the
  engine's `Alt-Svc` providers read as each response head goes out: HTTP/1.1 (`TcpListener.kt`, `http3AltSvc`;
  `h1/H1Response.kt`) and HTTP/3 (`Http3Listener.kt`, `h3AltSvc`; `h3/H3Call.kt`), so the next response on a keep-alive
  connection follows a change; before 0.3.0 the HTTP/1.1 value was fixed per TCP connection
- HTTP/1.1: `On` sends `h3=":<port>"; ma=86400`, `Clear` and `Drain` send exactly `clear`; HTTP/3: nothing under `On`,
  `clear` under `Clear` and `Drain`; only where the engine sends `Alt-Svc` at all (a TLS connector serving HTTP/3,
  `altSvc = true`); an application's own `Alt-Svc` and a 421 are left as they are
- the switch is not persisted (`persist`, section 3.1, concerns the client's cache): a new engine starts at `On`

**Tests that pin it.**

- `ServerHttp3AdvertisingTest.clearSendsAltSvcClearOnTheSameConnection`, `.h3ResponsesSayClearWhileWithdrawn`,
  `.altSvcOffSendsNoHeaderInAnyMode`, `.negative_appAltSvcNotOverridden`, `.negative_appAltSvcAnd421NotOverriddenOverH3`, `.backToOnAdvertisesAndAcceptsAgain`

**Notes.** A client may keep using an HTTP/3 connection it already has after `clear` (section 2.2 lets existing
connections continue); `Drain` moves those to TCP with GOAWAY. WebSocket (RFC 9220) and WebTransport Extended CONNECT
answers, error answers included, carry no engine `clear` on HTTP/3: only plain responses do, and the next one on the
same connection withdraws the alternative.

## <a id="s2-4-connection-refused"></a>§2.2, §2.4, §3; RFC 9000 §5.2.2, §10.2.3, §20.1 — CONNECTION_REFUSED is no broken alternative

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** RFC 9000 section 5.2.2: "If a server refuses to accept a new connection, it SHOULD send an Initial
packet containing a CONNECTION_CLOSE frame with error code CONNECTION_REFUSED"; section 20.1 defines CONNECTION_REFUSED
(0x02) as "The server refused to accept a new connection". A server does that when it cannot take a client now (a full
accept queue, a drain, a stop), which says nothing about the alternative itself. RFC 7838 section 2.2 makes the
origin's alternatives authoritative until they expire or the origin clears or replaces them (section 3), and section
2.4 lets a client fall back when an alternative fails. So the refused call falls back, and the alternative stays valid:
marking it broken for minutes to days after a refusal would put a whole origin on HTTP/1.1 through one rolling restart
of a multi-instance server, although the next connection (to another instance behind the same address, or to the same
one once it takes clients again) would be accepted.

**Recorded status.** ✅ 0.3.0 (before 0.3.0 the refusal marked the alternative broken for 5 minutes, doubling up to
2 days)

**How it is met.**

- `isTransientRefusal` (`KuicksilverEngine.kt`): a `QuicException.ConnectionLost.TransportClosed` from the peer with
  code `TransportError.CONNECTION_REFUSED`, as the failure or wrapped as not sent, whether it came at the first Initial
  (stateless) or on an established connection (a Kuicksilver server closes a connection whose handshake completed into a
  full accept queue with it, "accept queue full", `EndpointLoop.kt`; quic-go `server.go:886` `handleNewConn` likewise)
- the race's losing HTTP/3 setup and a request's fallback after an HTTP/3 failure (`marksAlternativeBroken`) skip the
  broken mark for it; the call reports `ProtocolDiagnostics.fallback = Refused` with the failure in `h3Failure`, the
  `Alt-Svc` cache keeps the alternative, and the next call races HTTP/3 again, as after `FallbackReason.H3NotReady`;
  repeated refusals escalate nothing
- any other close of the setup by the server (another transport code, a TLS alert), version negotiation without a common
  version and a handshake timeout still mark the alternative broken (section 2.4)
- the h3/h1 race still makes the one HTTP/1.1 attempt per call ([§2.4; RFC 8305 §5](#s2-4-race-and-fallback)); HTTP/3
  connects to the first address of the resolution and does not try another address of the same alternative after a
  refusal (no address race over QUIC, docs/guide/ktor.md)
- peers: quic-go's server sends CONNECTION_REFUSED for a full queue or a closing server (`server.go:876` `refuseNewConn`,
  `server.go:886` `handleNewConn`), quinn's `Endpoint::refuse` likewise (`quinn-proto/src/endpoint.rs:829`): a server-side load signal

**Tests that pin it.**

- `ClientFallbackTest.connectionRefusedFallsBackWithoutMarkingBroken`, `.refusedRetryAfterRejectionDoesNotMarkBroken`
  (the request's own fallback: rejected unprocessed, repeated on a new connection that is refused), `.negative_otherSetupCloseStillMarksBroken`,
  `ProtocolDiagnosticsTest.connectionRefusedIsTransient`, `.negative_otherSetupFailuresAreNotTransient`

## <a id="s2-4-close-after-goaway"></a>§2.4; RFC 9114 §5.2 — a close after GOAWAY is no broken alternative

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** RFC 9114 section 5.2: "An endpoint that completes a graceful shutdown SHOULD use the H3_NO_ERROR error
code when closing the connection", after GOAWAY; a server that stops gives open requests a grace period and then closes
what is left. That is the server ending the connection in order, not the alternative failing (RFC 7838 section 2.4):
marking it broken would put the origin on HTTP/1.1 for minutes to days after every rolling restart that caught a long
request (a long poll, a server-sent event stream, a slow response).

**Recorded status.** ✅ 0.3.0 (before 0.3.0 such a close marked the alternative broken for 5 minutes, doubling up to 2
days, when a request in flight fell back to HTTP/1.1)

**How it is met.**

- `H3Pool.execute`: a request whose connection fails with a graceful close by the peer (`isPeerShutdownClose`: an
  application CONNECTION_CLOSE with H3_NO_ERROR, or with an unknown code, which reads as H3_NO_ERROR under RFC 9114
  section 9, or a transport close with NO_ERROR) after that connection received GOAWAY
  (`Http3Connection.goAwayReceived`) carries `H3ClosedAfterGoAwayKey`; the engine's fallback (`fallbackToH1`) then does
  not mark the alternative broken (`ProtocolDiagnostics.fallback` still says `Http3Error`, without `marked broken`)
- both are required: the GOAWAY (an H3_NO_ERROR close without one first still marks the alternative broken: it cannot be
  told from an unknown code) and H3_NO_ERROR (a close with an error code such as H3_INTERNAL_ERROR after GOAWAY still
  marks it: servers send GOAWAY early for other reasons too, such as a cap on requests per connection); a transport
  error code, a stream reset and a local failure are no such close
- the fallback itself is unchanged: only an idempotent request with a replayable body that has no response yet goes
  again over HTTP/1.1; a request above the GOAWAY id is repeated over HTTP/3 on a new connection (RFC 9114 section 5.2)

**Tests that pin it.**

- `ClientFallbackTest.closeAfterGoAwayDoesNotMarkBroken`, `.negative_errorCloseAfterGoAwayMarksBroken`,
  `.negative_closeWithoutGoAwayMarksBroken`,
  `ProtocolDiagnosticsTest.peerShutdownClose`
