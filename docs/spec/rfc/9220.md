## <a id="extended-connect-websocket-over-h3"></a>Extended CONNECT / WebSocket over h3

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9220.

**Requirement.** Extended CONNECT / WebSocket over h3.

**Recorded status.** ✅ 0.2.0 (HTTP/3 level)

**How it is met.**

- `SETTINGS_ENABLE_CONNECT_PROTOCOL` from `Http3Settings.enableConnectProtocol`
- the client waits for the peer's SETTINGS and without the setting throws `Http3Exception.Settings` (`connect`); a `request()` with a `protocol` waits too and throws IllegalArgumentException without it (`RequestTest.negative_protocolNeedsTheServersConnectSetting`; before 0.3.0 it went out)
- `:protocol` without the setting on the server → `H3_MESSAGE_ERROR`
- `:protocol` is "a value from the 'Hypertext Transfer Protocol (HTTP) Upgrade Token Registry'" (RFC 8441 §4, which §3 applies), a token (RFC 9110 §16.7): an empty or non-token value is malformed on the server and refused with IllegalArgumentException before the client sends it (`message.PseudoHeadersTest.negative_protocolIsAToken`, `runtime.ExtendedConnectTest.negative_connectProtocolMustBeAToken`); it is matched in any case, as RFC 9110 §7.8 has recipients compare protocol names ("SHOULD use case-insensitive comparison"), for `websocket` and the WebTransport tokens alike (`webtransport.WebTransportSessionTest.tokenMatchedCaseInsensitively`, `ServerWebSocketH3Test.protocolTokenMatchedCaseInsensitively`; 0.3.0 review: before, the engine answered `WebSocket` with 501 while the library took it as a WebSocket without datagrams)
- a non-2xx → `ConnectRejected(status)`
- the data stream in both directions is `Http3Stream`, the directions close independently (the server's FIN does not cut the client's direction, RFC 9114 §4.4; review: `serverHalfCloseKeepsClientDirection`; once the 2xx went out (server) or arrived (client) only DATA may follow, a HEADERS frame on the tunnel is a connection error `H3_FRAME_UNEXPECTED` (RFC 9114 §4.4; 0.2.0 review: it was taken as trailers and ended the input — `headersOnEstablishedTunnelIsFrameUnexpectedOnServer`, `...OnClient`), and we send none either: `Http3ResponseWriter.finish(trailers)` on a 2xx to CONNECT throws IllegalArgumentException before anything goes out, so the tunnel can still end with a FIN, and a client request with trailers on a CONNECT, classic or Extended, is refused before a stream is opened (RFC 9114 §4.4, "Once the CONNECT method has completed, only DATA frames are permitted to be sent on the stream"; 0.3.0 review: before, both went out and the peer closed the connection with `H3_FRAME_UNEXPECTED` — `negative_serverTrailersOnAnEstablishedTunnelAreRefused`, `negative_connectRequestWithTrailersIsRefused`); the datagram registration is removed on both sides when both directions have ended or the stream was reset, review: `cleanEndUnregistersDatagrams`) — `runtime.ExtendedConnectTest.*`
- server engine: `:protocol = websocket` → a synthetic GET with `Upgrade: websocket` for Ktor `webSocket {}` routes, response `:status 200`, another protocol → 501 (§3: "the server SHOULD respond to the request with a 501"), and so is `websocket` with `webSocketsOverHttp3 = false`, also when `webTransport` advertises Extended CONNECT (`negative_webSocketsOffAre501EvenWithWebTransport`; 0.3.0 review: before, it reached the `webSocket {}` route); a 2xx from a route other than `webSocket` (a `get` on the path) is answered 501 instead, since only the upgrade accepts a WebSocket and any 2xx to CONNECT switches to tunnel mode (RFC 9110 §9.3.6; `negative_plainRouteAnswering2xxIsNoWebSocket`; 0.3.0 review: before, a streamed 200 reached the client as an open WebSocket), and the call reports that 501 in `call.response.status()`; a WebSocket CONNECT that announces capsules and breaks RFC 9297 §3.2 keeps the library's 400 and STOP_SENDING `H3_MESSAGE_ERROR`, never followed by the engine's reset of an unanswered call, and the call reports the 400 (`negative_capsuleRequestBreakingSection32Gets400`); a Close from the client after the server's Close reaches the server (review: `serverInitiatedCloseReceivesClientReason`); a call cancelled while its upgrade runs aborts both directions with `H3_REQUEST_CANCELLED`, STOP_SENDING first, then RESET_STREAM (§3: "RST exceptions are represented with a stream error ... of type H3_REQUEST_CANCELLED"; RFC 9114 §4.1.1) instead of leaving the stream open (`cancelledUpgradeResetsItsStream`, `negative_cancelledUpgradeStopsTheClientWithRequestCancelled`; 0.3.0 review: before, the STOP_SENDING carried `H3_NO_ERROR`), while an orderly end stops an unread client direction with `H3_NO_ERROR` — `ServerWebSocketH3Test.*`
- client engine: WebSocket via Extended CONNECT with `H3Only` or an open h3 connection with `ENABLE_CONNECT_PROTOCOL`, a 2xx response is shown to the plugin as 101 — `ClientH3Test.webSocketOverH3`; a connection that received GOAWAY does not count (RFC 9114 §5.2; 0.3.0 review: before, it did) — `ClientH3WebSocketTest.negative_goAwayConnectionDoesNotCountForExtendedConnect`
- client engine, with connection migration (RFC 9000 §9, opt-in `http3 { connectionMigration }`, 0.3.0): the WebSocket is a stream of the pooled HTTP/3 connection and moves with it when the network changes; the session carries on with no reconnect, every message both ways arrives once and in order (a fragmented message whose first half crossed the old network included), pings both ways and a Close with code and reason either way after the switch — `ClientMigrationTest.webSocketSurvivesNetworkSwitch`, `.webSocketSurvivesNetworkSwitchServerCloses` (loopback, the old socket deaf once the connection moved); without the option, or towards a server that sent `disable_active_migration`, the session ends at the connection's idle timeout once the old path is gone, `incoming` fails and `closeReason` is 1006 (RFC 6455 §7.1.5) — `.negative_webSocketEndsWithItsNetworkWithoutMigration`, `.negative_webSocketEndsWithItsNetworkWhenServerDisablesMigration`
- client engine: a `wss` WebSocket belongs to the `https` origin (§3 applies RFC 8441 §5: `:scheme` MUST be `https` for `wss`), so Alt-Svc alternatives, broken marks and RTTs are shared with `https` requests to the same host and port (RFC 7838 §2.4: the alternative serves all requests to its origin), and an Alt-Svc header on the WebSocket's HTTP/1.1 answer is filed under the `https` origin (0.3.0; before, `wss` was an origin of its own) — `ClientDiagnosticsTest.wssSharesTheHttpsOrigin`
