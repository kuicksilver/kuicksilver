## <a id="extended-connect-websocket-over-h3"></a>Extended CONNECT / WebSocket over h3

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9220.

**Requirement.** Extended CONNECT / WebSocket over h3.

**Recorded status.** ✅ 0.2.0 (HTTP/3 level)

**How it is met.**

- `SETTINGS_ENABLE_CONNECT_PROTOCOL` from `Http3Settings.enableConnectProtocol`
- the client waits for the peer's SETTINGS and without the setting throws `Http3Exception.Settings`
- `:protocol` without the setting on the server → `H3_MESSAGE_ERROR`
- a non-2xx → `ConnectRejected(status)`
- the data stream in both directions is `Http3Stream`, the directions close independently (the server's FIN does not cut the client's direction, RFC 9114 §4.4; review: `serverHalfCloseKeepsClientDirection`; once the 2xx went out (server) or arrived (client) only DATA may follow, a HEADERS frame on the tunnel is a connection error `H3_FRAME_UNEXPECTED` (RFC 9114 §4.4; 0.2.0 review: it was taken as trailers and ended the input — `headersOnEstablishedTunnelIsFrameUnexpectedOnServer`, `...OnClient`); the datagram registration is removed on both sides when both directions have ended or the stream was reset, review: `cleanEndUnregistersDatagrams`) — `runtime.ExtendedConnectTest.*`
- server engine: `:protocol = websocket` → a synthetic GET with `Upgrade: websocket` for Ktor `webSocket {}` routes, response `:status 200`, another protocol → 501, a Close from the client after the server's Close reaches the server (review: `serverInitiatedCloseReceivesClientReason`) — `ServerWebSocketH3Test.*`
- client engine: WebSocket via Extended CONNECT with `H3Only` or an open h3 connection with `ENABLE_CONNECT_PROTOCOL`, a 2xx response is shown to the plugin as 101 — `ClientH3Test.webSocketOverH3`
