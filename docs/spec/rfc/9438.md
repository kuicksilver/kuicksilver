## <a id="cubic"></a>CUBIC

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9438.

**Requirement.** CUBIC.

**Recorded status.** ✅ 0.2.0 (§4.10 with HyStart++ in the initial slow start only since 0.3.0)

**How it is met.**

- `Cubic` by default (`QuicConfig.congestionController`, NewReno remains an option), arithmetic in bytes, C = 0.4, β = 0.7, fast convergence (§4.7: W_max = cwnd·(1+β)/2 on a loss below the previous W_max), target W_cubic(t + RTT) clamped to [cwnd, 1.5·cwnd] (§4.2) where t leaves out application-limited ACKs and time with nothing in flight (0.2.0; Linux shifts the epoch the same way), Reno-friendly region with α = 3(1−β)/(1+β) (§4.3) that becomes 1 once W_est reaches the window before the last reduction (0.2.0), minimum window of 2 datagrams on persistent congestion, ECN-CE as a congestion event, one reduction per recovery period
- §4.10 slow start: "CUBIC SHOULD use the HyStart++ slow start algorithm [RFC9406]", in the initial slow start only (details: [RFC 9406](9406.md#hystart)); a later slow start, after persistent congestion, is Reno slow start up to the ssthresh the loss set. "When CUBIC uses HyStart++ [RFC9406], it may exit the first slow start without incurring any packet loss and thus W_max is undefined. In this special case, CUBIC sets cwnd_prior = cwnd and switches to congestion avoidance": the exit after the fifth CSS round sets ssthresh and cwnd_prior to cwnd, and the first congestion avoidance ACK starts the epoch with K = 0, W_max = W_est = cwnd (as §4.8 after a timeout)
- RTT samples reach the controller through `CongestionController.onRttSample` (the default hook is empty)
- pacing and `sendQuantum` — as for NewReno

**Tests that pin it.**

- `recovery.CubicTest.*` (18: `initialWindowLikeNewReno`, `lossReducesToSeventyPercent`, `fastConvergenceLowersWmax`, `growthReachesWmaxAtK`, `renoFriendlyRegionOnShortRtt`, `appLimitedDoesNotGrow`, `persistentCongestionToMinimum`, `ecnCeIsCongestionEvent`, `noSecondReductionInsideRecovery`, `hystartEntersCssOnRttIncrease`, `hystartExitsAfterFiveCssRounds`, `hystartBackToSlowStartWhenRttDrops`, `idleTimeIsNotPartOfTheCubicEpoch`, `applicationLimitedTimeIsNotPartOfTheCubicEpoch`, `renoFriendlyAlphaBecomesOneAtThePriorWindow`, `hystartCssBaselineIsTheRoundThatEnteredIt`, `hystartEverySampleOfARoundCounts`, `hystartOnlyInTheInitialSlowStart`), `QuicConfigTest.defaultControllerIsCubic`, `testing.CubicScenarioTest.noHystartInTheSlowStartAfterPersistentCongestion`, `testing.SimulatorTest.cubicTransferWithLossFinishes` (10 MiB, 5 % loss, seed 1..5), Monte Carlo

**History.**

- 0.3.0 cross-review: HyStart++ ran in every slow start, the one after persistent congestion included, with the round state of the initial one (its round end, its minimum RTT), so a rising RTT in that slow start entered Conservative Slow Start and five rounds later set ssthresh to a window far below the one the loss had set (290 542 → 88 800 bytes on the 50 Mbit/s, 40 ms simulation); the exit by HyStart++ did not set cwnd_prior (§4.10; no visible effect, the Reno-friendly α reached 1 on the first ACK either way); the fast convergence reference said §4.6 (multiplicative decrease) instead of §4.7
- 0.3.0 cross-review: the pacing rate, 1.25 × cwnd / smoothed_rtt in `Long` arithmetic, overflowed above a window of about 7.4 GB (100 Gbit/s × 0.6 s) and the pacer then held the next datagram for hours; it is computed in `Double` above that window and saturates — `recovery.PacerTest.negative_windowControllersPaceAWindowAbove7GB` (NewReno too)
