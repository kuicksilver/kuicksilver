## <a id="s8-address-validation-retry-amplification-limit"></a>§8 — address validation, Retry, amplification limit

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9000 §8.

**Requirement.** Address validation, Retry, amplification limit.

**Recorded status.** ✅ 0.2.0 (amplification limit); §8.1 Retry

**How it is met.**

- no repeated check for an Initial routed by DCID into an existing connection
- a forged/expired/foreign token → stateless Initial CONNECTION_CLOSE INVALID_TOKEN
- the client accepts exactly one Retry before any server packet, with a non-empty token, a new SCID and a correct tag (RFC 9001 §5.8, vectors of appendix A.4 v1/v2 byte for byte), derives new Initial keys from the Retry SCID, resends CRYPTO without a congestion event (RFC 9002 §6.3) and checks `retry_source_connection_id`/`original_destination_connection_id` (§7.3)

**Tests that pin it.**

- `HandshakeLimitsTest.negative_amplificationLimit`, `HandshakeLimitsTest.negative_amplificationCountsDiscarded`, `HandshakeLimitsTest.negative_duplicateDatagramCountedOnce`, `HandshakeLimitsTest.addressValidatedOnlyByHandshakePacket`
- NEW_TOKEN: see the §8.1.3 row
- threat model 3.3
- packet numbers go on after a Retry (§17.2.5.2) — `endpoint.RetryTest.packetNumbersContinueAfterRetry`

**Peer interop notes.**

- the server, as decided by `ConnectionAdmission` (`Allow | Retry | Drop | Close(code)`; `default()` — Retry at ≥ 256 handshakes in flight or > 8 MiB of their buffers, Allow for an address a Retry or NEW_TOKEN token validated (0.3.0), `AlwaysRetry` — for the interop case `retry`; Retry for an already validated address is a contract violation, the attempt is dropped, `EndpointStats.admissionContractViolations`; `Close(code)` → stateless Initial CONNECTION_CLOSE §10.2.3; a new Initial before `admit` passes only cheap checks — 1200 bytes, version, DCID ≥ 8, not a reflecting port 53/123/1900/5353/11211 — and is copied into a bounded queue of 1024, overflow is a drop; `maxConnectionsPerIp` 256, `maxConnectionLifetime` → CONNECTION_CLOSE NO_ERROR; `endpoint.AdmissionTest.*` 22 tests) answers with a Retry carrying the token `0x01 ‖ nonce ‖ AEAD(issuedAt ‖ ODCID)` under a key held in `ksl`, bound to address, port and version (lifetime 10 s, key rotation once an hour)
- the Retry SCID is only the DCID of the client's following Initials, not the peer CID with sequence number 0: that becomes the SCID of the server's Initial, even if it differs from the Retry SCID (§7.2, this is how ngtcp2 and quinn answer — found by an interop run of the `retry` case) — `endpoint.RetryTest.*` (21 tests)

## <a id="s8-1-3-new-token-server-side"></a>§8.1.3, §8.1.4, §19.7 — NEW_TOKEN, server side

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9000 §8.1.3, §8.1.4, §19.7.

**Requirement.** NEW_TOKEN: the server issues tokens and admits their holders without a Retry.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- token `0x02 ‖ nonce(8) ‖ AEAD(issuedAt)`, AAD `0x02 ‖ client IP` (no port, no connection ID: nothing links the two connections, §8.1.3 MUST)
- each kind has its own key per hourly generation, and the nonce is the generation (top byte) and that key's counter (56 bits, random start, never wraps), so AES-GCM never sees a nonce twice under one key
- keys kept for the lifetime (`QuicServerConfig.newTokenLifetime`, 24 h, null issues none, at most 7 days) and shared by every loop of a group
- a valid token validates the address (`ConnectionAttempt.addressValidated`, no anti-amplification limit) once — a nonce register (fails closed) treats a replay as no token (§8.1.4) — sized by `newTokenReplayCapacity` (at least 1,048,576 tokens per lifetime, 32 MiB, made on the first token shown), full → the token counts as absent
- a token that does not validate is treated as absent, never INVALID_TOKEN (§8.1.3)
- a policy may still send a NEW_TOKEN holder a Retry
- `EndpointStats.newTokensIssued/Accepted/Rejected`

**Tests that pin it.**

- `endpoint.NewTokenTest.serverIssuesOneTokenAfterHandshake`, `.validTokenSkipsRetryAndLiftsAmplification`, `.tokenBoundToIpNotPort`, `.tokenAcceptedUpToItsLifetime`, `.tokenFromOneLoopValidOnAnother`, `.secondTokenAfterMigrationToNewIp`, `.negative_invalidNewTokenIsTreatedAsAbsent`, `.negative_replayedNewTokenValidatesOnce`, `.negative_tokenOfAnInitialThatMadeNoConnectionCanBeUsedAgain`, `.negative_fullReplayRegisterFailsClosed`, `.negative_retryTokenNotAcceptedAsNewTokenAndViceVersa`, `.negative_newTokenNonceIsUniqueAndCarriesNoConnectionData`, `.negative_eachTokenKindHasItsOwnKeyAndCounter`, `.negative_counterNeverWraps`, `.replayRegisterHoldsItsProductionCapacity`, `.replayCapacitySizesTheRegister`

**Peer interop notes.**

- once the handshake is confirmed the server sends one NEW_TOKEN in 1-RTT after HANDSHAKE_DONE (repeated with the same bytes on loss), and one more after validating the client on a new IP (§9.3 SHOULD, as ngtcp2), at most four per connection

## <a id="s8-1-3-new-token-client-side"></a>§8.1.3, §17.2.5.3, §19.7 — NEW_TOKEN, client side

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9000 §8.1.3, §17.2.5.3, §19.7.

**Requirement.** NEW_TOKEN: the client keeps tokens and presents them.

**Recorded status.** ✅ 0.3.0, opt-in (`QuicClientConfig.tokenStore`, null by default: a token links connections)

**How it is met.**

- tokens go to the store under `"<SNI>:<port>"` (the IP literal without SNI), so one is never sent to another server name (§8.1.3 MUST NOT)
- `take` removes it (single use)
- it goes in every Initial of the next connection until a Retry token replaces it (§17.2.5.3)
- at most 8 per connection of ≤ 1024 bytes, each further NEW_TOKEN frame spends a glitch token (§21.9)
- a store that throws, or whose call runs past 250 ms, is logged and the connection goes on without a token
- NEW_TOKEN from a client → PROTOCOL_VIOLATION (§19.7)

**Tests that pin it.**

## <a id="s21-7-reassembly-memory-of-a-stream"></a>§21.7 — reassembly memory of a stream

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9000 §21.7.

**Requirement.** Reassembly memory of a stream.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- an internal limit (`QuicLimits.reassemblyRangesPerStream`, 256; 4096 per connection, not configurable) bounds the gaps a stream may hold
- a STREAM frame that would open one more is dropped unacknowledged (the peer retransmits it) instead of closing the connection with FLOW_CONTROL_ERROR, and data that fills a gap always merges, as does a frame at the read offset, which opens no gap and makes data readable (before 0.2.1 one that did not reach the first buffered range was refused at the limit: nothing was readable, nothing freed a range, and the stream stalled until the idle timeout; the CRYPTO streams share the reassembler).
- The refused frame changes nothing (0.2.1 review: it raised the stream's highest offset without charging the connection window, so data later buffered below it was never charged and a stream could hold its whole window outside the connection limit, §4.1)
- its packet number counts as seen but is never acknowledged, so a copy of the packet is dropped as a duplicate after the frames ahead of the refused one ran (§12.3, §13.1)

**Tests that pin it.**

- `stream.ReassemblerTest.negative_fragmentedStreamRangesCap`, `core.LossBurstTest.alternatingLossOnALongPathKeepsTheConnection`, `stream.ReassemblyFullFlowControlTest.negative_refusedFrameStillChargesTheConnectionWindow`, `.negative_aRefusedFrameChangesNothing`, `core.RefusedPacketReplayTest.negative_aReplayedRefusedPacketIsNotProcessedTwice`, `recovery.AckTrackerTest.refusedPacketIsSeenButNeverAcknowledged`, `stream.ReassemblerTest.aFrameAtTheReadOffsetIsTakenAtTheGapLimit`, `core.HandshakeLimitsTest.cryptoFrameAtTheReadOffsetIsTakenAtTheGapLimit`

## <a id="s9-migration-path-challenge-passive-and-active"></a>§9 — migration, PATH_CHALLENGE, passive and active

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9000 §9.

**Requirement.** Migration, PATH_CHALLENGE, passive and active.

Quoted: "MAY continue to use the current connection ID".

**Recorded status.** ✅ 0.2.0 (passive server migration, NAT rebind, path validation, CID rotation)

**How it is met.**

- a new source address of a 1-RTT packet becomes a path in the Validating state (PATH_CHALLENGE with new unpredictable data in every repeat, a response to any of the last 8 accepted, §8.2.1, §13.3; timeout max(3 × PTO, 6 × the configured initial RTT) §8.2.4 — never the RTT a client endpoint remembered for the first path, which seeds only that path, `endpoint.EndpointCoreTest.rememberedRttDoesNotShrinkPathValidation`, `core.PathTest.everyPathChallengeRepeatCarriesFreshData`; a challenge the amplification limit kept below 1200 bytes validates the address and starts a second, full-size validation, §8.2.1, `core.PathTest.amplificationLimitedChallengeIsFollowedByAFullSizeOne`), switching only on a non-probing packet with the highest number (§9.3), the previous path is also checked against off-path spoofing (§9.3.3), on failure — back to the last validated path (§9.3.2) or a silent close `ConnectionLost.NoViablePath`
- a NAT rebind (same IP, different port) inherits cc/RTT, a new IP starts from initial values
- ACKs, losses and ECN of packets of a closed or evicted path do not reach the active path's controller (core review, `core.PathTest.lostProbeOnClosedPathDoesNotTouchActiveCwnd`)
- 3× amplification limit on an unvalidated path (§9.3.1)
- PATH_RESPONSE goes to the source address of the challenge, padded to 1200 (§8.2.2), queue ≤ 3 (above that — glitch), responses of a path that was closed or evicted by a fifth address leave the queue (`core.PathTest.evictedPathFreesResponseSlots`, core review)
- a new path takes an unused peer CID, the old one is retired (§9.5)
- packets on a non-active path (a client probe from a new socket, a server PATH_RESPONSE/PATH_CHALLENGE to a new address, checking the old path after migration) carry their own unused peer CID, not the active path's CID (core review: probes used to go out with the active path's DCID — §9.5 MUST NOT)
- a path gets a CID on its first send and keeps it when it becomes active, the CID is retired when the check of a non-active path is over, or the path failed, was closed or evicted
- rotation every 10 000 packets
- retired local CIDs are still routed for 3 × PTO (§5.1.2)
- the client drops datagrams from an unknown server address (§9 MUST; a PATH_CHALLENGE from there used to create a path — core review, `core.ReceivePathTest.negative_clientDropsPacketFromUnknownServerAddress`)
- `disable_active_migration` is advertised only when `allowMigration = false`, migration to loopback/link-local from a non-loopback connection is forbidden
- active client migration — see the "RFC 9000 §9 (active)" row

**Tests that pin it.**

- `core.PathTest.*`, `testing.SimulatorTest.natRebindMidTransferKeepsCwnd` (50 MiB, rebind at 10 MiB)

**Peer interop notes.**

- `core/Paths.kt` — up to 4 paths with their own cc/RTT/pacer/MTU/amplification budget (when all four are taken, a path neither active nor last validated makes room: an idle one first, then — §8.2.4 abandoning — the validating path heard from longest ago, on a migration at once, on a probe only after max(3 x PTO, 5 s) of silence as quic-go's `pathTimeout`; `core.PathTest.rapidMigrationsKeepTheNewestPath`)
- ACKs and losses are attributed to the controller of the path the packets went on (`CongestionEvent.pathId`, §9.4 — otherwise losses of "old" packets on an address change reset the new path's window: found by the interop case `rebind-addr`, reproduced by `SimulatorTest.periodicAddressRebindDownloadKeepsThroughput`)
- without a spare CID the client does not probe from another socket and does not reuse the active CID (§9.5): the probe waits up to max(3 × PTO, 6 × initialRtt) for a NEW_CONNECTION_ID and probes as soon as one arrives, otherwise it fails with `PathFailureReason.NoSpareConnectionId` (0.2.0, after an iOS report; quic-go keeps such a path queued, ngtcp2/quiche refuse with `NGTCP2_ERR_CONN_ID_BLOCKED`/`OutOfIdentifiers`) — `core.EarlyMigrationTest.migrationRightAfterHandshakeCompletesOnceTheConnectionIdArrives`, `.probeWithoutSpareConnectionIdFailsWithNoSpareConnectionId`, `api.NetworkMigratorTest.noSpareConnectionIdFailsDistinctlyAndRetriesWhenOneArrives`, the server on the same socket keeps the current one only while the client's packets from the new address carry the same DCID as on the active path (a NAT rebinding; §9.5 "MAY continue to use the current connection ID")
- a client that switched to another of our IDs gets a fresh ID of its own or, with none spare, nothing until it provides one (as ngtcp2's CONN_ID_BLOCKED), and the server keeps the ID it answered a probe with for the switch that follows — `core.PathTest.probeUsesUnusedPeerCid`, `.serverWithoutSpareCidDoesNotReuseItTowardAMigratingClient`, `.serverKeepsTheProbedPathsCidForTheSwitch`

## <a id="s9-rebind-during-the-handshake"></a>§9, §8.1 — rebind during the handshake

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9000 §9, §8.1 (rebind during the handshake).

**Requirement.** The client's address changes between its first Initial and the server's answer.

**Recorded status.** ✅ 0.2.0 (re-check, interop `rebind-port` with picoquic), reworked in 0.2.1

**How it is met.**

- a server in the Handshaking state follows a new client address (§9 allows to "proceed with path validation and allow the peer to migrate"), never with `allowMigration = false` or to loopback/link-local (`core.PathTest.forgedInitialFromThirdAddressDoesNotMovePath`), and only with the highest-numbered packet of its space, so a delayed older packet from the old address does not move it back (§9.3, `handshakeTimeRebindIgnoresAnOlderPacketFromTheOldAddress`). **When:** a Handshake packet moves the path at once
- none leads a move that comes with the ClientHello's completion (no ServerHello has left, the client could not read it)
- PMTU probes are not sent on a path under validation. **What validates the new address:** no packet's source address proves anything, since an off-path attacker that sees the client's datagrams can race a copy of any of them from a spoofed address and the genuine one is dropped as a duplicate (§9.3.3, §21.1.3.2).
- A client Handshake packet validates the active address only if it came from there and the server's whole handshake flight (every CRYPTO-carrying Initial and Handshake packet) went there and nowhere else (§8.1: the client can only have read it there)
- an acknowledgement in a Handshake or 1-RTT packet of a packet sent to the current address validates it (those keys are not public)
- so does a PATH_RESPONSE.
- A path validated that way but with its challenge unanswered settles as validated at the deadline rather than closing the connection (`unansweredHandshakeTimeChallengeDoesNotCloseTheConnection`). **Deadline and fallback (§9.3.2, §8.2.4):** every handshake-time move keeps the address it left
- if nothing validates the new one within max(3 x PTO, 6 x initial RTT) the move is undone, also after the handshake completed (a raced copy can carry the client's Finished; the completion itself validates no moved-to address): the path returns to the old address with its state and budget, everything in flight is resent there at once, and the server follows no other address until the handshake completes
- after the handshake completed, an old address the whole flight had gone to (and only it) when the path moved counts as reached by the client.
- A newer packet from the old address takes the path back before the deadline
- only the first such restore of a connection resends at once, later ones leave it to the PTO, so an attacker alternating raced copies with the client's own packets costs ACKs, not flights. **Known limit:** a client that really rebinds from C to S mid-handshake while an observer races copies of its packets from C: each copy from C is a newer packet from the old address, so the path keeps returning to the dead C and the handshake fails at the handshake timeout
- The cure, challenging both candidates as separate paths, is planned for 0.3.0 ([roadmap](../../roadmap.md)).
- Consequence for a real rebind: a client that rebound answers the flight or the challenge from its new address well inside the period and keeps it
- one whose new address gets nothing through for a whole period ends on its old address, frozen there for the rest of the handshake, as with those implementations.
- Packets in flight to the old address are resent by PTO.

**Tests that pin it.**

## <a id="s9-6-preferred-address"></a>§9.6, §18.2 — preferred address

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

**Requirement.** Preferred address.

**Recorded status.** ✅ 0.3.0 (server; experimental `QuicServerConfig.preferredAddress`)

**How it is met.**

- `disable_active_migration` does not stop the move and is lifted after it (§18.2)

## <a id="s14-dplpmtud-mtu-1200-minimum"></a>§14, RFC 8899 — DPLPMTUD, MTU 1200 minimum

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9000 §14, RFC 8899.

**Requirement.** DPLPMTUD, MTU 1200 minimum.

Quoted: "MUST be set if possible".

**Recorded status.** ✅ 0.2.0

**How it is met.**

- `core/Pmtud.kt` per path, enabled with `caps.df` and `QuicConfig.pmtud` (true by default)
- binary search from 1200 to min(`maxUdpPayloadSize` 1452, the peer's `max_udp_payload_size` — §14.3) with a step of 20, up to 3 probes per size, one final probe of the upper bound
- probes are 1-RTT packets PING + PADDING of exactly the probe size, only after Confirmed, ack-eliciting but outside the congestion window, their loss is not a congestion signal (§14.4)
- black hole — 3 lost packets > 1200, after the first of which no packet ≥ the current MTU sent later was acknowledged (the verdict comes after the whole ACK is processed: loss detection reports an ACK's losses before its new acknowledgements, and a loss burst under congestion was otherwise taken for a black hole — core review) **or** two consecutive PTOs with MTU > 1200 while an ack-eliciting packet > 1200 is unanswered (without ACKs loss detection does not work; small packets alone cannot be lost to the MTU) → fall back to 1200, `cc.onMtuUpdate(1200)`, pause 60 s, undone (MTU and search state back, no pause) when a full-size packet sent after the packets the verdict rested on is acknowledged afterwards — a peer that only stalled for a few PTOs (§4.1: an acknowledged packet confirms its size)
- a new search after 600 s
- event `ConnectionEvent.MtuUpdated`, `stats.pathMtu`
- `maxDatagramPayload`/`maxDatagramSize` follow the MTU, the datagram queue drops entries that no longer fit (`stats.datagramsDroppedSend`)
- at most 64 a second per endpoint are looked at (`EndpointStats.ptbAccepted`/`ptbIgnored`)
- a PTB at or above the current size ends the larger probes at once (§4.6.2), one below it starts confirmation probes of the current size — an acknowledged one forgets the PTB, three lost ones lower to the PTB size (rounded down to the 20-byte step, never below 1200, no pause), and a black hole detected meanwhile falls to the PTB size instead of 1200
- EMSGSIZE on the probe in flight settles that size at once.
- Sources by target: PTB on Linux and Android (accelerated socket), EMSGSIZE on every accelerated socket (Linux, Android, Apple, Windows), nothing on NIO (threat-model 3.16)
- the portable NIO socket sets DF where the runtime has the option (`IP_DONTFRAGMENT`, JDK 19 and later, 0.2.1: RFC 9000 §14 "MUST be set if possible"; Android, older JDKs and the Kotlin/Native ktor-network fallback expose no such option) but runs no PMTUD → without the accelerated UDP the MTU stays at 1200

## <a id="s21-6-peer-chosen-acks-max-data-and"></a>§21.6; RFC 9002 appendix A.7 — peer-chosen ACKs, MAX_DATA and stream counts cost no linear pass

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9000 §21.6; RFC 9002 appendix A.7.

**Requirement.** Peer-chosen ACKs, MAX_DATA and stream counts cost no linear pass.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- loss detection walks only the packets below the largest acknowledged one
- a MAX_DATA that raises nothing touches no stream and one that does reschedules only the streams that ran out of connection credit

**Tests that pin it.**

- `recovery.LossDetectionTest.ackOfOldestPacketIsSublinear`, `ackOfTombstoneRangeIsSublinear`, `stream.StreamStateTest.maxDataWithoutGrowthTouchesNoStream`, `stream.StreamSchedulerTest.addIsLogarithmicAtTenThousandStreams`

**Peer interop notes.**

- sent packets sit in a packet-number-ordered array (`recovery.SentPackets`) where an ACK range is found by binary search and acknowledged packets leave tombstones compacted once they outnumber the live ones (a repeated ACK over acknowledged ranges finds no tombstone run: the packet threshold declares everything more than 3 below the largest acknowledged lost on the same ACK and the front skip drops it) (ngtcp2 uses a skip list for the same lookups)
- the stream scheduler keeps one min-heap by id or round-robin list per (urgency, retransmission, incremental) instead of scanning every stream (as quiche orders streams in an intrusive tree)

## <a id="s4-1-a-blocked-sender-asks-again-a"></a>§4.1, §10.1, §13.3, §19.12–§19.14 — a blocked sender asks again, a receiver answers a stale report

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9000 §4.1, §10.1, §13.3, §19.12–§19.14.

**Requirement.** A blocked sender asks again, a receiver answers a stale report.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- DATA_BLOCKED / STREAM_DATA_BLOCKED / STREAMS_BLOCKED go out once per limit and again when the packet carrying one is lost while the sender is still blocked at that limit.
- While it stays blocked, the sender also repeats DATA_BLOCKED / STREAM_DATA_BLOCKED on a timer (`core/ConnectionCore.timers.kt`, `blockedRepeatGap`): 1 PTO after the report, then gaps of 2, 4 and 8 PTOs through the 32nd repeat (report n, 4 ≤ n ≤ 32, 8n − 17 PTOs after the first; a PTO without backoff, since the lossy path that ate the update also delays the sender's own PTO), then doubling gaps from 16 PTOs up to a third of the effective idle timeout (the smaller of both sides' `max_idle_timeout`, at least 3 PTO, §10.1), or 10 s when neither side has an idle timeout (the gap of the default 30 s, so turning the idle timeout off does not change the traffic, and a lost update after a long block costs at most 10 s).
- A report at a new limit goes out at once and restarts the fast gaps.
- STREAMS_BLOCKED has no timer: it is repeated only when lost (a receiver answers a stale one with MAX_STREAMS, row §2–§4).
- A receiver that already granted more answers a stale DATA_BLOCKED / STREAM_DATA_BLOCKED with its current MAX_DATA / MAX_STREAM_DATA at once (at most once per smoothed RTT per connection or stream; faster repeats are not answered and spend no glitch token, row §21.9)
- a PTO probe for a packet that carried only stream control frames (MAX_DATA, MAX_STREAM_DATA, MAX_STREAMS, *_BLOCKED) carries those frames, not a bare PING.
- The first 32 repeats keep the old gaps because they are what finds a lost window update: at the 75 % loss of every answer in `FlowBlockedTest`, 32 lost answers in a row have probability 1e-4 per blocked limit (0.75^32; at 10 % loss 1e-32), so later repeats almost always face a receiver that does not read.
- The cap of a third of the idle timeout keeps the decided keep-alive semantics: at least two reports and their ACKs fall in every idle period, so one lost exchange does not end a blocked connection (with a short idle timeout, 3 PTO, the old 4 and 8 PTO gaps let it idle out — `.aBlockedConnectionWithAShortIdleTimeoutDoesNotIdleOut`).
- it answers a received DATA_BLOCKED / STREAM_DATA_BLOCKED with MAX_DATA / MAX_STREAM_DATA, as we do.
- None of the four repeats a report on a timer

**Tests that pin it.**

- With the backoff: about 95 (`core.BlockedBackoffTest`).
- `core.FlowBlockedTest.lostWindowUpdatesDoNotStallAnUpload` (stall bounds derived from the schedule: unchanged median bound 97 PTO, the 1 % union bound over all episodes 281 → 737 PTO because its 37th report now falls in the backoff; measured stalls unchanged), `.negative_dataBlockedFloodIsRateLimited`, `core.BlockedBackoffTest.*`, `stream.BlockedFramesTest.*`

**History.**

- Before (review of the BBR work, 2026-10-13): an upload over a return path with 75 % loss stalled for 10+ s — the sender had nothing in flight and the receiver's only copy of its window update waited behind 64 × PTO. **Why the backoff.** Each repeat is ack-eliciting and restarts both idle timers, so the earlier fixed 8 PTO gap made a connection whose reader stopped send a report every 1–3 s on a WAN path for as long as it stayed blocked (about 2 000 in 10 minutes at the simulator's 36 ms PTO).

**Peer interop notes.**

- The behaviour of the reference implementations below (a report once per limit, again only on loss), was considered and not taken: it gives up the timer `FlowBlockedTest`'s bounds rest on (a lost answer waits for the receiver's own PTO backoff again, the case that stalled 8 MiB uploads at 75 % loss for up to 28.9 s before 0.2.0) and lets a connection blocked by a reader that stopped idle out unless the application enables keep-alive. **References** (source read 2026-10-14): quic-go 432b156 sends DATA_BLOCKED / STREAM_DATA_BLOCKED once per limit (`IsNewlyBlocked`, `lastBlockedAt` in `flow_controller_*.go`) and STREAMS_BLOCKED once per limit (`streams_map_outgoing.go`), retransmits any lost one as a control frame (`retransmission_queue.go`) even when no longer blocked, ignores received ones (`connection.go`, `streams_map.go` `HandleStreamDataBlockedFrame`). quiche 925b225 sends STREAM_DATA_BLOCKED once per limit (`blocked_at` in `lib.rs`) and DATA_BLOCKED on every `stream_send` that finds the connection window short, never retransmits either ("an optional advisory signal"), retransmits a lost STREAMS_BLOCKED while it carries the latest limit (`force_retransmit_sent_limit_eq`), and only counts received ones. ngtcp2 4822893 sends DATA_BLOCKED / STREAM_DATA_BLOCKED once per limit (`last_blocked_offset`), retransmits a lost one only while still blocked at that limit (`ngtcp2_strm_require_retransmit_stream_data_blocked`), never sends STREAMS_BLOCKED, and only validates received ones. msquic 6cf8270 sends DATA_BLOCKED when the connection becomes blocked and does not retransmit it, retransmits a lost STREAM_DATA_BLOCKED and also queues it again on every acknowledgement while the stream stays blocked (`QuicLossDetectionOnPacketAcknowledged`: "if this design of immediate resending after ACK ever gets too chatty ... add exponential backoff"), so a blocked stream reports once per RTT
- none but msquic keeps a blocked connection alive by itself.

## <a id="s7-4-1-remembered-transport-parameters-for-0-rtt"></a>§7.4.1 — remembered transport parameters for 0-RTT

**Requirement.** Remembered transport parameters for 0-RTT.

**Recorded status.** ✅ 0.2.0
