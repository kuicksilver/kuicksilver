## <a id="tls-1-3-as-every-protocols"></a>(BCP 195) §4 — new protocols default to TLS 1.3; clients give only the minimum version

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 9852 (BCP 195). The anchor keeps its old name ("TLS 1.3 as every protocol's default") so that links stay
valid; the row was narrowed in 0.3.0 to what §4 asks, which is about new protocols and about how a client states its versions.

**Requirement.** §4: "Any new protocol that uses TLS MUST specify TLS 1.3 as its default. For example, QUIC [QUICTLS]
requires TLS 1.3 ... If deployment considerations are a concern, the protocol MAY specify TLS 1.2 as an additional,
non-default option." And: "If the application is using a TLS implementation that supports TLS version negotiation and if
it knows that the TLS implementation will use the highest version supported, then clients SHOULD specify just the minimum
version they want. This MUST be TLS 1.3 or TLS 1.2". §5 changes RFC 9325 §3.1.1 for new protocols only (TLS 1.3 MUST, TLS
1.2 MAY); HTTP/1.1 and HTTP/2 over TCP are not new protocols (RFC 9113 §9.2 runs HTTP/2 over TLS 1.2 or later).

**Recorded status.** ✅ 0.3.0 (0.2.0 recorded the row as "TLS 1.3 as every protocol's default", which §4 does not say; a
client context then also capped its top version at TLS 1.3).

**How it is met.**

- The new protocols here are TLS 1.3 only: QUIC and HTTP/3 (RFC 9001 §4.2; `TlsConfig.validateFor(quic)` refuses anything
  else, the Ktor client gives its QUIC connections TLS 1.3 whatever `tls { versions }` says, the server its HTTP/3 listener).
- HTTP/1.1 and HTTP/2 over TCP: TLS 1.3 or TLS 1.2. `TlsVersions.Tls13` is the default of a `TlsConfig` and of the Ktor
  server's connectors; the Ktor client allows TLS 1.2 by default since 0.3.0 (`Tls12And13`), and TLS 1.3 is negotiated
  whenever the peer has it (OpenSSL picks the highest version both offer, RFC 9325 §3.1.1 "MUST prefer to negotiate TLS
  1.3"); a stripped 1.3 offer fails on the downgrade sentinel ([RFC 9846 §4.2.3](9846.md#s4-2-3-downgrade-protection)).
- Clients give only the minimum (SHOULD): a `ksl` client context sets its floor (`KSL_OPT_MIN_VERSION`, TLS 1.3 or 1.2)
  and leaves its top open (`SSL_CTX_set_max_proto_version` 0, OpenSSL's highest: TLS 1.3 in 4.1), so a later OpenSSL with a
  newer version offers it without a change here; a QUIC session raises its floor to TLS 1.3 (`ksl_ctx.c`, the session copy
  of the context's bounds). A server context keeps TLS 1.3 as its top. TLS 1.0 and 1.1 can never be the floor.

**Tests that pin it.**

- C `tcp_default_versions_and_tls12_profile` (a new client context has the floor TLS 1.3 and no top, a server context TLS
  1.3 only; TLS 1.0 and 1.1 refused as bounds), `TlsConfigTest.quicRequiresTls13Only`
- `ClientTls12DowngradeTest.negative_aStrippedTls13OfferIsNotDowngradedTo12`, `ClientTls12JdkServerTest.defaultClientIsServedByATls12OnlyServer`
  (TLS 1.3 with a server that has it)

**History.**

- 0.3.0: the row narrowed to §4 as written; client contexts specify only their minimum version.
