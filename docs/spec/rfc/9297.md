## <a id="http-datagrams"></a>HTTP datagrams

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9297.

**Requirement.** HTTP datagrams.

**Recorded status.** ✅ 0.2.0 for §2 (HTTP/3 datagrams); ✅ 0.3.0 for §3 (the Capsule Protocol on Extended CONNECT streams with datagram semantics, every one but `websocket`; HTTP/1.1 and HTTP/2 — no, ADR-0009)

**How it is met.**

- `SETTINGS_H3_DATAGRAM` is always sent (1 only with transport datagrams)
- use only after the setting has been sent and received
- `H3_DATAGRAM=1` without the transport `max_datagram_frame_size` → `H3_SETTINGS_ERROR`. RFC 9297 does not state this check in words; HTTP/3 Datagrams are QUIC DATAGRAM frames (§2.1), and quic-go (`http3/conn.go:248-250`) and quiche (`h3/mod.rs:3101-3110`) close the same way. Only an absent or 0 parameter closes: any value above 0 is support (RFC 9221 §3; `QuicConnection.peerSupportsDatagrams`), not a non-zero `maxDatagramSize`, as quic-go checks (quiche also closes for limits too small for its own frames, which neither RFC asks). With a limit of 1 or 2 the SETTINGS are taken and an HTTP/3 datagram, which needs at least a byte of Quarter Stream ID, is too large (`runtime.H3DatagramTest.h3DatagramWithATinyTransportLimitIsNoSettingsError`, `.h3DatagramOverAOneByteTransportLimitIsTooLarge`; before, a limit of 2 was a SETTINGS_ERROR)
- §2.1.1: the setting is bound into the server's 0-RTT ticket context, so a server that no longer sends `H3_DATAGRAM=1` gives a ticket issued with it no early data instead of a reduced setting (`runtime.EarlyDataTest.h3DatagramChangeInvalidatesEarlyData`)
- quarter stream ID, an ID of a stream not yet created is dropped silently (`runtime.H3DatagramTest.unknownStreamDroppedSilently`), one beyond the client-initiated bidirectional stream limit (the one we granted on a server, the one granted to us on a client) — `H3_ID_ERROR`, the §2.1 SHOULD (before 0.2.1 dropped silently; `negative_datagramBeyondTheStreamLimitIsIdErrorOnTheServer`, `negative_datagramBeyondTheStreamLimitIsIdErrorOnTheClient`), a truncated one — `H3_DATAGRAM_ERROR`
- §2: a datagram for a request without datagram semantics whose request (server) or response (client) direction is still open aborts that stream with `H3_DATAGRAM_ERROR` (STOP_SENDING and RESET_STREAM), the connection lives on; only an Extended CONNECT has them, except RFC 9220's `websocket` (an Extended CONNECT with a protocol the library does not know, an application's own served through `Http3Stream`, counts as having them: the application that accepted it defines what its datagrams mean): a GET or POST (the RFC's examples), a classic CONNECT (a TCP tunnel, RFC 9110 §9.3.6) and a WebSocket stream have none, and none is sent on them (`trySendDatagram` → `Closed`; "HTTP Datagrams MUST only be sent with an association to an HTTP request that explicitly supports them"), not as DATAGRAM capsules either, since those streams do not speak the Capsule Protocol (below) — `runtime.H3DatagramTest.negative_datagramForAWebSocketStreamAbortsItOnTheServer`, `.negative_datagramForAWebSocketStreamAbortsItOnTheClient` (0.3.0; before, every CONNECT took them)
- after that direction ended it is dropped silently (§2.1); the direction counts as ended once all of it arrived, read or not (RFC 9000 "Data Recvd"; `runtime.H3DatagramTest.datagramForAWholeUnreadPostIsDropped`)
- a per-stream API (`Http3Stream.datagrams`/`trySendDatagram`), a queue of 32 per stream
- §2.1 stream state (0.2.0 review): datagrams that arrive after the stream's receive side closed are dropped (the flow ends there), none are sent once our send side is closed (`trySendDatagram` → `Closed`, `sendDatagram` → `IllegalStateException`) — `runtime.H3DatagramTest.datagramsAfterReceiveSideClosedAreDropped`, `.noDatagramsAfterSendSideClosed` (class `H3DatagramTest` in `ExtendedConnectTest.kt`)
- the Capsule Protocol (§3) on Extended CONNECT streams with datagram semantics, `Http3Stream.useCapsuleProtocol(CapsuleConfig)` → `CapsuleStream`; §3.2: "The Capsule Protocol only applies to definitions of new HTTP upgrade tokens", which a classic CONNECT has not and `websocket` (RFC 9220) does not use, so on those streams `useCapsuleProtocol` throws `IllegalStateException` and leaves the stream as it was (`CapsuleStreamTest.negative_noCapsuleProtocolOnAWebSocketStream`, `.negative_noCapsuleProtocolOnAClassicConnect`; 0.3.0 review: before, both took it, and with HTTP/3 datagrams off a DATAGRAM capsule went into a WebSocket's bytes) (capsules of declared `knownTypes` up to `maxCapsuleLength`, 64 KiB by default; a single writer, so capsules never interleave): §3.2 — unknown types are skipped as their bytes arrive, never buffered (`message.CapsuleParserTest.unknownSkippedStreaming`, `runtime.CapsuleStreamTest.unknownCapsuleSkipped`), a known capsule above the limit is a malformed message (`CapsuleStreamTest.negative_knownCapsuleAboveLimit`), and `content-length`/`content-type`/`transfer-encoding` or a 204/205/206 response with the Capsule Protocol is malformed (`negative_capsuleProtocolWithContentLength`, `negative_capsuleProtocolWith204`; our own message breaking it is an `IllegalStateException`, `ownContentTypeRejected`) — malformed means the stream is reset and stopped with `H3_MESSAGE_ERROR`, `Http3Exception.MessageError`, the connection lives on. A message that announces the Capsule Protocol (`Capsule-Protocol: ?1`) is checked before any tunnel exists: `acceptConnect` answers such a request that breaks §3.2 with 400 and STOP_SENDING `H3_MESSAGE_ERROR` (RFC 9114 §4.1.2) instead of a 200 (`negative_capsuleRequestBreakingSection32IsRefusedBeforeAny200`), `connect` fails on such a 2xx and aborts the stream with `H3_MESSAGE_ERROR` (`negative_capsuleResponseBreakingSection32FailsTheConnect`), and our own such CONNECT request or 2xx is refused with `IllegalArgumentException` before it is sent (`negative_ownCapsuleRequestBreakingSection32IsRefused`, `negative_capsuleProtocolFieldRefusedOnOwnResponses`; 0.3.0 review: before, the check waited for `useCapsuleProtocol`, after the 200)
- §3.4 — `CapsuleProtocol.isEnabled` reads the `Capsule-Protocol` field as a Structured Field Boolean, parameters ignored (`capsuleProtocolFieldParsing`), and it is not required on a stream; "The Capsule-Protocol header field MUST NOT be used on HTTP responses with a status code that is both different from 101 (Switching Protocols) and outside the 2xx (Successful) range": the server refuses it in a 1xx or a 3xx–5xx response with `IllegalArgumentException`, as any invalid response field (`negative_capsuleProtocolFieldRefusedOnOwnResponses`; 0.3.0 review: before, it went out)
- §3.5 — DATAGRAM capsules are received alongside QUIC datagrams in one flow (`datagramCapsuleReceivedWithQuicDatagrams`), one longer than `maxDatagramLength` is dropped without buffering (`CapsuleParserTest.negative_datagramCapsuleAboveLimitSkipped`), and when HTTP/3 datagrams are unsupported a datagram is sent as a DATAGRAM capsule (`datagramFallback`, on by default; `datagramCapsuleFallback`, `datagramFallbackOff`), but one too large for QUIC is not (`tooLargeDoesNotFallBack`)

**Tests that pin it.**

- §3.3 — a FIN inside a capsule is malformed, not a clean end (`CapsuleParserTest.negative_truncatedCapsuleAtFinIsMessageError`, `CapsuleStreamTest.negative_truncatedCapsuleResetsStream`)
- Jazzer `capsules` — `runtime.H3DatagramTest.*` (in `ExtendedConnectTest.kt`), `runtime.CapsuleStreamTest.*`

**History.**

- before 0.2.1 such datagrams were dropped, and a WebTransport server kept them for 5 s (`negative_datagramForAGetAbortsItsStreamOnTheServer`, `negative_datagramForAGetAbortsItsStreamOnTheClient`, `datagramForAWholeGetIsDropped`, `webtransport.WtStreamRoutingTest.datagramsForAnOpenGetLeaveTheSlotsToASession`, `.datagramKeptForWhatBecomesAGetAbortsIt`)
