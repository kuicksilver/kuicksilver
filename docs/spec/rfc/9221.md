## <a id="datagram-frames"></a>DATAGRAM frames

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9221.

**Requirement.** DATAGRAM frames.

**Recorded status.** ✅ 0.2.0 (core)

**How it is met.**

- `max_datagram_frame_size` 65 535 by default (`QuicConfig.maxDatagramFrameSize`, 0 — do not advertise and reject the frames with PROTOCOL_VIOLATION)
- `ConnectionCore.maxDatagramPayload` = min(the largest payload whose whole frame fits the peer's limit, a packet-filling frame (MTU − short header − tag) − frame header − 32 bytes kept for an ACK); the ACK reserve never comes out of the peer's limit, so any limit above 0 is support (§3: "A value greater than 0 indicates that the endpoint supports the DATAGRAM frame types"), a limit of 2 for empty datagrams only. A limit of 1 is support that no frame we send fits (it admits only an empty type-0x30 frame ending its packet; we write 0x31 with a Length): `sendDatagram` answers `TooLarge(max = 0)` even for an empty payload (`max` is the largest payload that fits, 0 also when none does), as ngtcp2 refuses such a datagram as too large (`ngtcp2_conn.c:12461-12464`); quiche reports no datagram (`dgram_max_writable_len` → None). 0 — the peer does not support it
- sending through `DatagramSender.onTransmit(DatagramPacketWriter)` while a 1-RTT packet is assembled, only with an open congestion window, the frames are ack-eliciting, counted by CC, never retransmitted — `onAcked(id)`/`onLost(id)` (§5)
- receiving: a frame larger than our limit (the whole frame: type, the Length field only for 0x31, data — `DatagramCoreTest.typeWithoutLengthAtExactMax`, core review) → PROTOCOL_VIOLATION (§3), in Initial/Handshake → PROTOCOL_VIOLATION (decoder), a receive queue of 128 evicting the oldest and `ConnectionStats.datagramsDropped`, event `DatagramsReadable`, `readDatagram(into, offset)`
- coroutine API: `QuicConnection.sendDatagram(data, policy)` / `trySendDatagram` (without entering the loop: a bounded command queue — no more than `datagramSendQueue`, overflow evicts the oldest — + atomic counters; total buffered ≤ 2 × `datagramSendQueue` + 1), policies `DropOldest`, `Reject` (`QueueFull`, `sendDatagram` waits for room), `LatestWins(key)` (replacement in the queue by key), send queue ≤ 32 / 1 MiB (`datagramSendQueue`, `datagramSendQueueBytes`), `TooLarge(max)`/`DatagramTooLarge`, `Unsupported(PeerDoesNotSupport|Disabled)`/`DatagramUnsupported`, `datagrams: Flow<Datagram>` reads the core's queue directly (one buffer of 128 evicting the oldest), `maxDatagramSize: StateFlow<Int>`, `peerSupportsDatagrams` (experimental: the peer advertised `max_datagram_frame_size` above 0, §3, which `maxDatagramSize` floored at 0 cannot show for a limit of 2 or 1; `sendDatagram` answers `PeerDoesNotSupport` exactly when it is false, `TooLarge` for what a small limit does not fit) — `api.DatagramApiTest.aPeerLimitOfTwoIsSupportForEmptyDatagrams`, `.aPeerLimitOfOneIsSupportThatNothingFits`

**Tests that pin it.**

- `core.DatagramCoreTest.*` (14: `maxDatagramFrameSizeAdvertised`, `payloadLimitFromMtuAndPeer`, `aSmallPeerLimitStillCarriesDatagrams`, `aPeerLimitOfOneByteTakesNoDatagram`, `peerWithoutSupportGivesZero`, `onTransmitCalledAtPacketAssembly`, `ackedCallback`, `datagramNeverRetransmitted`, `datagramsRespectCongestionWindow`, `negative_datagramInHandshakeLevel`, `datagramAboveAdvertisedSizeIsProtocolViolation`, `receiveQueueDropsOldestAt128`, `maxSizeDatagramDeliveredWhileAcking`, `typeWithoutLengthAtExactMax`), `ReceivePathTest.datagramFrameWithoutSupportIsProtocolViolation`
- `api.DatagramApiTest.*` (14: `echoDatagrams`, `trySendDatagramAfterCloseAnswersClosed`, `negative_datagramQueueCap`, `dropOldestFloodStaysBounded`, `latestWinsReplacesByKey`, `tooLargeResultAndException`, `unsupportedWhenPeerDisabled`, `aSmallPeerLimitSendsSmallDatagrams`, `aPeerLimitOfTwoIsSupportForEmptyDatagrams`, `aPeerLimitOfOneIsSupportThatNothingFits`, `unsupportedWhenLocallyDisabled`, `maxDatagramSizeFlowTracksPathMtu`, `queuedDatagramsAboveNewMtuDroppedAfterBlackHole`, `sendDatagramUnderRejectSuspendsUntilSpace`), `core.DatagramCoreTest.typeWithoutLengthAtExactMax`, `DatagramApiAllocationTest.trySendNeverSuspendsOrAllocatesPerCall`, `testing.SimulatorTest.realtimeScenarioStreamsAndDatagrams`
- a frame always fits the room left in its packet (§5: no fragmentation): the payload offered is the largest whose type, Length and payload fit, for every room (RFC review: with 66 bytes left it was 64, a 67-byte frame, and the connection failed with an internal error) — `core.DatagramWriterTest.payloadOfRemainingAlwaysFits`
