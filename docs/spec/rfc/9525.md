## <a id="hostname-verification"></a>(obsoletes RFC 6125) — hostname verification

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 9525 (obsoletes RFC 6125).

**Requirement.** Hostname verification.

**Recorded status.** ✅ 0.2.0 (`VerificationNegativeTest`, C `test_quic.c` `test_no_verify_name`, `KslSmokeTest.forgottenVerifyNameFails`)

**How it is met.**

- a single matcher from `ksl` on all platforms
- DNS-ID and IP-ID; a reference identifier (`HostName.normalize`) is an IP literal by the strict grammar (IPv4 octets without leading zeros, IPv6 per RFC 4291 §2.2, no zone ID) or a DNS name of LDH labels of 1–63 octets (RFC 1123 §2.1, RFC 5890 §2.3.1), at most 253 octets, whose last label is not all digits (RFC 3696 §2); anything else (`010.0.0.1`, `1.2.3`, `-a.example`, a 64-octet label) is refused with `TlsException.Config`, as Go's `net.ParseIP` and `x509` refuse it (0.3.0; before, a leading-zero quad was taken for an IP literal and the rest for names) — `HostNameTest.negative_sloppyIdentifiersRejected`, `.validIdentifiersAtTheLimitsAreAccepted`
- no SRV-ID/URI-ID
- replaceable, cannot be disabled
- the reference identifier is the URL's host (section 6.1.1: intermediate values of a DNS resolution "MUST NOT be treated as" reference identifiers), never an address the client engine's resolver answered, an application's `dns` included (`ClientDnsTest.negative_theResolvedAddressNeverStandsInForTheName`, `.negative_theResolvedAddressNeverStandsInForTheNameOverHttp3`; [RFC 8305 §3, §4](8305.md#s3-s4-application-resolver))
- an `https://` proxy (0.3.0) is a service of its own: its certificate is checked against the proxy's host as configured, never the origin's name (the origin's `ExpectedName` does not carry over), and the origin's certificate inside the tunnel against the origin's (`ClientHttpsProxyTest.negative_proxyCertificateValidForTheOriginButNotTheProxyFails`, `.proxyNamedByAddressIsCheckedAgainstTheAddressWithoutSni`; [RFC 9110, https proxy](9110.md#https-proxy))
