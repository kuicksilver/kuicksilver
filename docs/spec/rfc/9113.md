# RFC 9113 — HTTP/2

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="http-2"></a>HTTP/2

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113.

**Requirement.** HTTP/2.

**Recorded status.** ✅ 0.3.0 (both engines; server push and h2c are optional and not offered, rows below)

**How it is met.**

- ADR-0017: a new module `kuicksilver-http2` next to `kuicksilver-http3`, a sans-IO core (`frame`, `hpack`, `core`,
  `message`) checked by `:kuicksilver-http2:checkHttp2Architecture`; HTTP/2 only after ALPN `h2` over TLS (no h2c,
  sections 3.2 and 3.3 make it optional), no server push.
- A coroutine runtime (`io.kuicksilver.http2.runtime`) drives the core over the engines' byte channels; the Ktor client
  engine uses it on the TCP path (`kuicksilver-ktor-client/.../h2/`), and the Ktor server engine on TLS connectors with
  `http2` set (`kuicksilver-ktor-server/.../Http2Serving.kt`, `.../h2/`): see the client and server rows below.
- Conformance of the server: h2spec 2.6.0 passes all 146 cases (generic, http2, hpack) against the JVM and the macOS
  server (`tools/interop/h2spec.sh`, 2026-11-06; [interop results](../interop.md)); the release gate runs it against the
  Linux server too.

**History.**

- 0.2.x: ❌ by decision (ADR-0009, "No HTTP/2 in v1"), superseded by ADR-0017 on 2026-11-04.
- 0.3.0: the client engine speaks HTTP/2 (`http2 { enabled = true }` by default); the server engine serves it when
  `http2` is set (off by default, experimental), with engine-level flood defences (§10.5 below) and h2spec passing.

**Open items.**

- None for RFC 9113. WebSockets over HTTP/2 (RFC 8441, Extended CONNECT) are a separate extension, offered by both
  engines since 0.3.0: [RFC 8441](8441.md#websocket-over-http-2).

## <a id="s3-2-starting-http-2-client"></a>§3.2, §3.3 — starting HTTP/2 (client)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §3.2, §3.3.

**Requirement.** A client starts HTTP/2 over TLS by offering `h2` in ALPN (RFC 7301) and sends the connection preface
once the server selected it (§3.2, §3.4); the server's preface is a SETTINGS frame. TLS use follows §9.2.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `H1Pool.connect` offers `["h2", "http/1.1"]` on every `https://` connection over TCP (directly, through an HTTP
  CONNECT tunnel or SOCKS5: ALPN is inside the TLS session with the origin, as OkHttp does) when `http2.enabled` is true,
  the request is not a WebSocket (a WebSocket takes HTTP/2 only on a connection that is there already, [RFC
  8441](8441.md#s5-websocket-client); a connection of its own offers `http/1.1` only, as Chromium's) and the route
  did not answer HTTP_1_1_REQUIRED lately; otherwise `["http/1.1"]`, as in 0.2. HTTP/2 starts only when
  `TlsConnection.negotiatedAlpn` is `h2`.
- The client preface and our SETTINGS go out at once (`H2ClientConnection.start`), and the first request right after them:
  §3.4, "clients are permitted to send additional frames to the server immediately after sending the client connection
  preface, without waiting to receive the server connection preface". Until the server's SETTINGS arrive its settings
  have their §6.5.2 initial values, except that the connection takes one stream only (that request's): with
  SETTINGS_MAX_CONCURRENT_STREAMS still unknown, more would meet a server that refuses streams above its limit (§5.1.2:
  REFUSED_STREAM or PROTOCOL_ERROR); the other requests wait for the SETTINGS. A REFUSED_STREAM on that first stream is
  not processed (§8.7), sent again and not counted against the connection. The server's SETTINGS must arrive within what
  the request's connect timeout left, else the connection ends with SETTINGS_TIMEOUT (§6.5.3: ours cannot be acknowledged
  before them; the acknowledgement's own 10 s count from the server's preface) and the call fails with
  `ConnectTimeoutException`, or with the connection's end when its content had started to go out.
- §9.2: HTTP/2 runs over TLS 1.3, or over TLS 1.2 when the client allows it (`TlsVersions.Tls12And13`, which offers
  `h2` as well); SNI from the URL's host either way (a domain name; an IP literal is never sent, RFC 6066 §3). The TLS 1.2
  rules (see §8, §9 below) are kept: no compression, no renegotiation (a server's attempt is a connection error of type
  PROTOCOL_ERROR, §9.2.1), and only suites §9.2.2 does not prohibit.

**Tests that pin it.**

- `ClientH2Test.negotiatesH2AndMultiplexes`, `.serverWithoutH2StaysOnH1`, `.disabledOffersOnlyHttp11`, `.tls12AllowedStillOffersH2`,
  `.webSocketGoesOverH1Only`, `.throughConnectProxyIsH2`, `.negative_noServerSettingsWithinConnectTimeoutFails`
- `H2InteropTest` (JVM): Netty's HTTP/2 server over JDK TLS
- `runtime.H2RuntimeTest.negative_noServerPrefaceFailsTheRequestsAtTheDeadline`

## <a id="s3-2-starting-http-2-server"></a>§3.2, §3.3 — starting HTTP/2 (server)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §3.2, §3.3 (server side).

**Requirement.** A server that supports HTTP/2 over TLS selects `h2` in ALPN (RFC 7301) and then speaks HTTP/2 only;
its preface is a SETTINGS frame, the first frame it sends (§3.4); TLS use follows §9.2 (TLS 1.2 or later, SNI; for
TLS 1.3, no post-handshake authentication, §9.2.3).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `TcpListener.kt`, `tcpTlsConfig`: with `Configuration.http2` (off by default in 0.3.0) every TLS connector offers
  `["h2", "http/1.1"]`; the server picks by its own order (`SSL_select_next_proto` in `ksl_ctx.c`, RFC 7301 §3.2), so a
  client that offers both gets HTTP/2 and one that offers only `http/1.1` (WebSockets included) gets HTTP/1.1 on the same
  port. A connection whose handshake agreed on `h2` is served by `serveH2` (`Http2Serving.kt`) instead of the HTTP/1.1
  pipeline; the core sends our SETTINGS first, before any other frame.
- §9.2: the server engine negotiates TLS 1.3 only (its connectors have no TLS 1.2 option), so the TLS 1.2 rules of
  §9.2.1 and §9.2.2 do not arise; `tcpTlsConfig` offers `h2` only on a TLS 1.3 configuration in any case. SNI is
  supported (`sniSelector`); `ksl` never sends a post-handshake CertificateRequest (§9.2.3).

**Tests that pin it.**

- `ServerH2Test.servesH2WhenOffered`, `.h1ClientStillServed`, `.disabledByDefaultOffersOnlyHttp11`

## <a id="s4-frame-codec"></a>§4.1–4.2, §5.5, §6 — frame codec

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §4.1–4.2, §5.5, §6.

**Requirement.** The 9-octet frame header with a 24-bit length, the reserved bit ignored on receipt and sent as 0, flags
without meaning ignored and left unset (§4.1); a frame above SETTINGS_MAX_FRAME_SIZE or too small for its mandatory
fields is a FRAME_SIZE_ERROR, a connection error for frames that carry a field block, SETTINGS and frames on stream 0
(§4.2); unknown frame types are discarded (§5.5); the per-type rules of §6: DATA, HEADERS, PRIORITY, RST_STREAM,
PUSH_PROMISE and CONTINUATION on stream 0 and SETTINGS, PING and GOAWAY on another stream are PROTOCOL_ERROR; padding
that does not fit the payload is PROTOCOL_ERROR (§6.1, §6.2, §6.6); SETTINGS whose length is not a multiple of 6, a
SETTINGS ACK with a payload, PING other than 8 octets, RST_STREAM and WINDOW_UPDATE other than 4, GOAWAY under 8 are
connection FRAME_SIZE_ERRORs; PRIORITY other than 5 octets is a stream FRAME_SIZE_ERROR (§6.3).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `kuicksilver-http2/src/commonMain/kotlin/io/kuicksilver/http2/frame/FrameDecoder.kt`: the header is checked before a
  payload buffer exists (so a declared length never sizes an allocation above the limit), and the buffer starts at
  16 KiB at most and grows with the bytes received (a raised `maxFrameSize` lets no peer hold 16 MiB with a 9-byte
  header and a stall); every frame type with a fixed
  length is checked from the header alone; unknown types stream past without a buffer and come out as `Frame.Unknown`
  (the connection still needs to see them: inside a field block they are a connection error, §6.10). Connection errors
  are thrown by `feed`, a stream error by `next` after the frame was consumed whole, so the decoder stays in sync.
- `FrameEncoder.kt` writes the reserved bits and the undefined flags as 0; `Http2ErrorCode.of` maps an unknown code to
  INTERNAL_ERROR without special behaviour (§7).
- An oversized frame is always a connection error, also where §4.2 would allow a stream error: §5.4 lets an endpoint
  treat a stream error as a connection error, and the oversized payload would have to be skipped unread anyway.

**Tests that pin it.**

- `frame.FrameCodecTest.roundTripEveryType` (byte by byte), `.paddingStripped`,
  `.negative_padLengthBeyondPayloadIsProtocolError`, `.negative_frameAboveMaxFrameSizeIsFrameSizeError` (no allocation
  beyond the header), `.negative_largeDeclaredFrameIsBufferedAsItArrives`, `.negative_settingsLengthNotMultipleOfSixIsFrameSizeError`,
  `.negative_pingLengthNotEightIsFrameSizeError`, `.negative_windowUpdateLengthNotFour`,
  `.negative_streamIdOnConnectionFrameIsProtocolError`, `.negative_dataOnStreamZero`, `.unknownFrameTypeSkippedStreaming`
  (1 MiB of an unknown type, nothing buffered), `.reservedBitIgnored`, `.errorCodesOfSection7`

**History.**

- 0.3.0: new (ADR-0017).

**Notes on peers.**

- Netty 4.2.16 (`DefaultHttp2FrameReader.java:196`, `preProcessFrame`) and nghttp2 (`nghttp2_session.c`, the frame
  header state of `nghttp2_session_mem_recv2`) also check the declared length against the maximum from the header,
  before reading the payload.

## <a id="s3-4-connection-preface"></a>§3.4 — connection preface

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §3.4.

**Requirement.** The client sends the 24-octet preface and then a SETTINGS frame; the server's preface is a SETTINGS frame as its first frame; an invalid preface is a connection error of type PROTOCOL_ERROR. HTTP/2 over TLS is selected by ALPN `h2`; h2c (§3.2, §3.3) is not offered.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `kuicksilver-http2/src/commonMain/kotlin/io/kuicksilver/http2/core/H2ConnectionCore.kt`: the preface and our SETTINGS (with SETTINGS_ENABLE_PUSH = 0 from a client, SETTINGS_NO_RFC7540_PRIORITIES = 1 from a server)
  and a WINDOW_UPDATE that raises the connection window are queued at construction and written before anything else, even
  before the GOAWAY of an error found first; the server compares the preface byte by byte; the peer's first frame must be a
  SETTINGS frame that is not an acknowledgement. Every error before that SETTINGS frame is PROTOCOL_ERROR, also one the
  frame decoder finds first (a length above SETTINGS_MAX_FRAME_SIZE, as an HTTP/1.1 answer's "HTT" reads, or a PING of 7
  bytes); only a malformed SETTINGS frame keeps the FRAME_SIZE_ERROR of §6.5.

- `kuicksilver-http2/src/commonMain/kotlin/io/kuicksilver/http2/runtime/H2Connections.kt`: `H2ClientConnection.start` returns
  once the preface is queued, without waiting for the server's ("To avoid unnecessary latency, clients are permitted to send
  additional frames to the server immediately after sending the client connection preface, without waiting to receive the
  server connection preface"); `prefaceTimeout` bounds the wait for the server's preface (`H2ConnectionCore.expectPeerPrefaceBy`).

**Tests that pin it.**

- `core.StreamStateTest.clientPrefaceAndSettings` (a client's output read by a server core), `.negative_invalidPrefaceOrFirstFrame`
- `runtime.H2RuntimeTest.firstRequestLeavesBeforeTheServerPreface`, `.negative_noServerPrefaceFailsTheRequestsAtTheDeadline`,
  `.oneStreamUntilTheServerSettingsThenItsLimit`, `.negative_prefaceDeadlineBeyondTheSettingsAckTimeout`;
  `ClientH2Test.burstBeforeTheServerSettingsStaysWithinTheirLimit`, `.negative_noServerSettingsAfterTheBodyStartedIsNotAConnectTimeout`

## <a id="s4-3-field-blocks-and-continuation"></a>§4.3, §4.3.1, §6.2, §6.10 — field blocks and CONTINUATION

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §4.3, §4.3.1, §6.2, §6.10.

**Requirement.** Field blocks are sent as a contiguous sequence of HEADERS or PUSH_PROMISE and CONTINUATION frames, with no other frame in between; a receiver treats any other frame, or a frame of another stream, inside a field block as a connection error of type PROTOCOL_ERROR; every field block MUST be decoded (the compression state is shared), and a decoding error is a COMPRESSION_ERROR.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- Sending (§4.3.1): there is one HPACK encoder per connection, so a field list is queued as is and encoded only when `poll`
  takes it, in the order the blocks go on the wire; a list dropped before that (a reset, a GOAWAY) never touches the
  encoder, and a change of the peer's SETTINGS_HEADER_TABLE_SIZE is signalled at the start of the first block after our
  acknowledgement. A field block is one array of HEADERS and CONTINUATION frames of at most min(the peer's
  SETTINGS_MAX_FRAME_SIZE, 16 384) bytes each, written whole by `poll` (a block cut by a short buffer is finished before
  anything else).
- Our decoder's table starts at 4 096, as both sides' do (§4.3.1), and our own SETTINGS_HEADER_TABLE_SIZE holds once the
  peer acknowledged it.
- Receiving: `HeaderBlockCollector` gathers the fragments under the limits of §10.5; any other frame, an unknown type
  included, inside a block is a PROTOCOL_ERROR; every block is decoded, also for streams that are refused, reset or
  discarded after our GOAWAY.

**Tests that pin it.**

- `core.StreamStateTest.negative_frameInsideFieldBlockIsProtocolError`, `.fieldBlockSplitOverContinuationFrames`, `core.SettingsTest.largeFieldSectionSplitIntoContinuationFrames`, `core.GoAwayTest.negative_newStreamAfterGoAwayRefused` (HPACK stays in step), `core.CompressionOrderTest.*` (interim and final responses on two streams, trailers then another stream, a reset of a queued response, a table size reduction, a block cut by a short write: each decoded by an independent decoder in wire order), `core.StreamStateTest.negative_decoderTableStartsAt4096UntilOurSettingsAreAcknowledged`

## <a id="s5-1-stream-states-and-identifiers"></a>§5.1, §5.1.1 — stream states and identifiers

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §5.1, §5.1.1.

**Requirement.** The states of §5.1 and the frames each allows: frames other than HEADERS and PRIORITY on an idle stream are a PROTOCOL_ERROR; frames other than WINDOW_UPDATE, PRIORITY and RST_STREAM on a half-closed (remote) stream are a STREAM_CLOSED stream error; DATA on a stream that is not open or half-closed (local) is STREAM_CLOSED (§6.1); after sending RST_STREAM an endpoint processes late frames minimally; client streams are odd, new identifiers grow, and an unexpected identifier is a PROTOCOL_ERROR; a HEADERS frame without END_STREAM after the final field section is malformed (§8.1).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `H2Stream.kt` (open, half-closed (local), half-closed (remote), closed; the reserved states never exist: we never push and
  cancel any push that arrives before our SETTINGS were acknowledged).
- Closed streams are remembered (at least 256, twice our concurrency limit): frames on one we reset or discarded are
  processed minimally (DATA still counts toward and is credited back to the connection window, field blocks still feed
  HPACK); frames on one closed otherwise get STREAM_CLOSED, HEADERS as a connection error (the "closed" state allows it;
  RFC 7540 §5.1 required it after END_STREAM both ways, and h2spec http2/5.1/12 checks it), DATA as a stream error (§6.1);
  DATA on one no longer remembered gets STREAM_CLOSED too (§6.1), and HEADERS with an identifier not above the last one
  and not remembered is the unexpected identifier of §5.1.1.

**Tests that pin it.**

- `core.StreamStateTest.requestResponseWalksTheStatesOfSection51`, `.interimResponsesThenFinalThenTrailers`, `.negative_dataOnClosedStreamIsStreamClosed`, `.negative_headersOnAClosedStreamIsAConnectionError`, `.framesOnAStreamWeResetAreDiscarded`, `.negative_evenStreamFromClientIsProtocolError`, `.negative_streamIdDecreasingIsProtocolError`, `.negative_framesOnIdleStreamsAreProtocolErrors`, `.negative_secondFieldSectionWithoutEndStreamIsMalformed`

## <a id="s5-1-2-stream-concurrency"></a>§5.1.2 — stream concurrency

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §5.1.2.

**Requirement.** Endpoints MUST NOT exceed the limit set by their peer; an endpoint that receives a HEADERS frame over its advertised limit MUST treat it as a stream error of type PROTOCOL_ERROR or REFUSED_STREAM.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `openStream` throws `H2StreamLimit` at the peer's SETTINGS_MAX_CONCURRENT_STREAMS (the engine waits or opens another
  connection); a peer's new stream over ours is refused with REFUSED_STREAM, before any application processing. A stream
  the peer reset keeps counting until the driver calls `release` (its handler finished), so resets cannot run more
  handlers than the limit (threat model 3.23).

**Tests that pin it.**

- `core.SettingsTest.peerMaxConcurrentStreamsRespected`, `core.FloodTest.negative_resetStreamStillRunningCountsTowardConcurrency`, `.negative_rapidResetHandlersStayWithinConcurrency`

## <a id="s5-2-flow-control"></a>§5.2, §6.9 — flow control

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §5.2, §6.9, §6.9.1, §6.9.2.

**Requirement.** A sender MUST NOT send a flow-controlled frame beyond either window; DATA always counts toward the connection window, padding included; a WINDOW_UPDATE of 0 is a PROTOCOL_ERROR (stream or connection); a window above 2^31 − 1 is a FLOW_CONTROL_ERROR (stream or connection); a change of SETTINGS_INITIAL_WINDOW_SIZE moves the window of every stream with an active flow-control window (open or half-closed (remote)) by the difference, possibly below zero, and one above the maximum is a FLOW_CONTROL_ERROR; a SETTINGS frame cannot alter the connection window.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- Receiving (`RecvWindow.kt`): WINDOW_UPDATE goes out only after the driver reports with `consumed` that the application
  read the data (back-pressure), once a quarter of the window was consumed; windows start at 512 KiB per stream and
  768 KiB for the connection and double, as in kuicksilver-quic, while the application reads a window in under four
  round trips, up to 6 MiB and 15 MiB; padding is credited back at once. A smaller initial window of ours only applies once
  our SETTINGS are acknowledged. Stream credit is one coalesced WINDOW_UPDATE written after the control frames and dropped
  when the stream is reset (§6.4); content delivered but never read goes back to the connection window when the stream is
  reset or released, so a dropped response does not shrink the connection. On the sending side, DATA queued but never
  written (the stream was reset or went away with a GOAWAY) gives its window back to the connection.
- Sending: `sendData` takes at most one frame within both windows and holds at most one DATA frame per stream, so
  nothing is buffered beyond the window; `H2Event.WindowAvailable` says when to offer more.
- A smaller SETTINGS_INITIAL_WINDOW_SIZE of the peer (§6.9.2): its acknowledgement is queued on receipt, after the DATA
  frames `sendData` already took from the larger window (each at most 16 KiB, at most one per stream, needing no window
  to be written). The peer counts what follows the acknowledgement against the smaller window, so those frames must
  precede it; written after it, they overran that window and the peer reset the stream with FLOW_CONTROL_ERROR.
- Our smaller SETTINGS_INITIAL_WINDOW_SIZE (§6.9.3): until the peer acknowledges it, our receiver counts the peer's DATA
  against the previous window, and applies the difference to every stream's window when the acknowledgement arrives;
  DATA the peer sent before it applied the new value is therefore never taken for an overrun.

**Tests that pin it.**

- `core.FlowControlTest.windowUpdateOnlyAfterConsumed`, `.senderStopsAtTheWindowUntilTheReceiverReads`, `.autotuneDoublesUpToMax`, `.negative_dataBeyondWindowIsFlowControlError`, `.negative_windowOverflowIsFlowControlError`, `.negative_windowUpdateOfZero`, `.initialWindowChangeAdjustsOpenStreams`, `.initialWindowChangeLeavesStreamsWeCannotSendOn`, `.negative_droppedDataReturnsConnectionWindow`, `.negative_clientDroppedRequestDataReturnsConnectionWindow`, `.windowUpdatesOnClosedStreamsAreFree`, `.aPeerResetPurgesQueuedStreamCreditAndReturnsUnreadContent`, `.releaseReturnsUnreadContentToTheConnection`, `.zeroWindowSenderBlocksWithoutBuffering`, `.oneFrameAtATimePerStream`, `.paddingIsCreditedBackAtOnce`, `.dataTakenBeforeASmallerInitialWindowIsWrittenBeforeTheAck`, `.settingsAckFollowsDataTakenFromTheLargerWindow`, `.droppedDataReleasesTheHeldSettingsAck`, `.lastDataOfAHalfClosedStreamHoldsTheAck`, `.twoShrinkingSettingsKeepTheirAckOrder`, `core.SettingsTest.ourSmallerSettingsTakeEffectWhenAcknowledged`

## <a id="s5-3-priority"></a>§5.3, §6.3 — priority

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §5.3, §6.3.

**Requirement.** The RFC 7540 priority scheme is deprecated (§5.3.2); the frame fields remain; PRIORITY may arrive in any state, including idle and closed (§6.3), its length must be 5 (a FRAME_SIZE_ERROR stream error) and it must not be on stream 0.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- PRIORITY frames and the HEADERS priority fields are parsed and checked, then ignored: no dependency tree, so a PRIORITY
  flood allocates nothing, and each PRIORITY frame takes a glitch token (§10.5). A server sends
  SETTINGS_NO_RFC7540_PRIORITIES = 1 (RFC 9218 §2.1); a client sends an RFC 7540 signal in its request HEADERS (dependency
  0, not exclusive, a weight from the RFC 9218 urgency) until the server's SETTINGS say 1 (RFC 9218 §2.1.1, ADR-0017).
- A stream that depends on itself is a PROTOCOL_ERROR stream error. RFC 9113 does not retain this rule; it is RFC 7540
  §5.3.1, kept because RFC 7540 peers and h2spec expect it, and only while the peer has not sent
  SETTINGS_NO_RFC7540_PRIORITIES = 1: after it the HEADERS priority fields and PRIORITY frames are ignored without that
  check, since RFC 9218 §2.1 says "A server that receives SETTINGS_NO_RFC7540_PRIORITIES with a value of 1 MUST ignore
  HTTP/2 priority signals" (until 0.3.0 the check ran regardless).

**Tests that pin it.**

- `core.StreamStateTest.negative_selfDependencyIsStreamError`, `.selfDependencyIgnoredAfterNoRfc7540Priorities`, `.priorityOnIdleStreamIsAllowedAndIgnored`, `core.FloodTest.negative_priorityFloodCreatesNoState`

## <a id="s5-4-error-handling"></a>§5.4, §6.4 — error handling and RST_STREAM

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §5.4, §6.4.

**Requirement.** A connection error SHOULD be preceded by a GOAWAY with the last processed stream and its code, after which the connection is closed; a stream error is a RST_STREAM; RST_STREAM MUST NOT be sent on an idle stream, and one received for an idle stream is a PROTOCOL_ERROR; an endpoint MUST NOT answer a RST_STREAM with a RST_STREAM.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- A stream whose HEADERS were never written is still idle to the peer: `reset` drops it without a RST_STREAM (the next
  stream we open closes it implicitly, §5.1.1) and reports it as not processed; a stream error inside a field block
  (§6.2, §6.10) or before the peer's SETTINGS (§3.4) is a connection PROTOCOL_ERROR.
- A connection error queues only our GOAWAY (after a partly written frame, and after the preface if it was not written yet),
  reports `H2Event.Closed` and every open stream as reset; a stream error sends one RST_STREAM per stream and marks the
  stream so its late frames are discarded; a stream error on an idle stream, where no RST_STREAM is allowed, becomes a
  connection error (§5.4 allows treating a stream error as a connection error).
- The GOAWAY reaches the peer: once the core ended and the runtime wrote its last frames, the transport is closed in
  order behind them (`H2Runtime.writeLoop`). The client engine passes `closeTransportGracefully`: the TLS session sends
  what is in its output, then close_notify, waits for the peer's and flushes the socket before the FIN, within 1 s in all
  (`H1Pool.closeOrderly`); the server's `TlsSocket.close` does the same. A connection whose PING went unanswered writes its
  GOAWAY the same way (closed hard after 2 s when the writer cannot get it out); so does any client connection once its
  core ended (a server that stops reading cannot hold the transport and the pool's slot); only a transport that failed is
  closed at once. Closing the engine sends GOAWAY (NO_ERROR) on every HTTP/2 connection and waits for those connections to end (at
  most 1 s) and for the orderly closes (at most 2 s more), about 3 s in all.

**Tests that pin it.**

## <a id="s6-5-settings"></a>§6.5 — SETTINGS

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §6.5, §6.5.2, §6.5.3.

**Requirement.** Values are processed in order and acknowledged immediately; unknown settings are ignored; SETTINGS_ENABLE_PUSH other than 0 or 1, and 1 from a server, SETTINGS_MAX_FRAME_SIZE outside 2^14..2^24 − 1 are PROTOCOL_ERRORs; SETTINGS_INITIAL_WINDOW_SIZE above 2^31 − 1 is a FLOW_CONTROL_ERROR; a SETTINGS not acknowledged in reasonable time MAY end the connection with SETTINGS_TIMEOUT; SETTINGS_HEADER_TABLE_SIZE bounds the HPACK table; SETTINGS_MAX_HEADER_LIST_SIZE is advisory.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- The peer's values apply as they arrive (window differences, the HPACK encoder's table, the frame size we send, its
  concurrency limit); ours apply once acknowledged where they are tighter than the protocol's initial values. An
  unacknowledged SETTINGS ends the connection with SETTINGS_TIMEOUT after `Http2Settings.settingsAckTimeout` (10 s).
- Acknowledgement (§6.5.3, "MUST immediately emit"): it is queued into the ordered output as soon as the SETTINGS are
  processed and needs nothing from the peer. Like every control frame it is written after a frame already partly
  written and after earlier control frames and PING answers. One for SETTINGS that shrink SETTINGS_INITIAL_WINDOW_SIZE
  is queued after the DATA frames whose window was already taken (each at most 16 KiB, at most one per stream, needing
  no window: see §5.2 above), so while those are written other control frames, stream credit, field blocks and other
  streams' DATA may still go before it. Acknowledgements keep the order of their SETTINGS, and held ones count toward
  `Http2Settings.maxControlFramesQueued` (CVE-2019-9515).
- A field section larger than the peer's SETTINGS_MAX_HEADER_LIST_SIZE is not sent (`H2HeaderListTooLarge`, before HPACK
  changes state). SETTINGS_ENABLE_CONNECT_PROTOCOL (RFC 8441) and SETTINGS_NO_RFC7540_PRIORITIES (RFC 9218) other than 0
  or 1 are PROTOCOL_ERRORs, as those documents require.

**Tests that pin it.**

- `core.SettingsTest.ackSent`, `.negative_settingsAckTimeoutIsSettingsTimeout`, `.negative_enablePushFromServerIsProtocolError`, `.negative_maxFrameSizeOutOfRange`, `.negative_initialWindowSizeAboveMaximumIsFlowControlError`, `.negative_booleanSettingsOtherThanZeroOrOne`, `.peerHeaderListSizeHonouredWhenSending`, `.peerHeaderTableSizeZeroSentAsUpdate`, `core.FlowControlTest.settingsAckFollowsDataTakenFromTheLargerWindow`, `.twoShrinkingSettingsKeepTheirAckOrder`, `core.FloodTest.negative_settingsFloodBehindAHeldAckBounded`

## <a id="s6-8-goaway"></a>§6.8 — GOAWAY

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §6.8.

**Requirement.** After receiving GOAWAY an endpoint MUST NOT open new streams on the connection; streams above the last stream identifier were not processed and can be retried; an endpoint MUST NOT increase the last stream identifier it sends; a graceful shutdown can first send 2^31 − 1 and, after a round trip, the real last stream; after sending GOAWAY, frames creating streams above the last identifier are ignored (their field blocks still decoded).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `goAway(graceful = true)` sends GOAWAY(2^31 − 1) and a PING, and the final GOAWAY when the PING is answered or, at the
  latest, after `Http2Settings.settingsAckTimeout` (requests that crossed the first GOAWAY are kept; that PING is never
  forgotten among our others); a later GOAWAY never names a higher stream; a received GOAWAY reports our streams above
  its identifier as `notProcessed`, and so are streams whose HEADERS were still queued, whatever their identifier: they
  are dropped unwritten, so no stream is opened after the GOAWAY arrived; once no stream is left and the driver released them all, `H2Event.Closed` is
  reported.

## <a id="s10-5-denial-of-service"></a>§10.5 — denial of service

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §10.5, §10.5.1.

**Requirement.** An endpoint should limit the resources a peer can make it commit: SETTINGS, PING, empty frames, CONTINUATION, header list size, stream resets; it can treat abusive patterns as a connection error of type ENHANCE_YOUR_CALM.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `H2Limits.kt` and the core, all per connection (threat model 3.23), each ending the connection with ENHANCE_YOUR_CALM:
  - a field block is collected to at most twice SETTINGS_MAX_HEADER_LIST_SIZE compressed bytes, `maxContinuationFrames` (8)
    CONTINUATION frames and `maxHeaderBlockTime` (10 s) before decoding; a block above SETTINGS_MAX_HEADER_LIST_SIZE but
    within twice it is decoded (HPACK stays in step) and fails only its stream (`tooLarge`: a server answers 431, a client
    fails the request);
  - at most `maxControlFramesQueued` (10 000) control frames wait for the peer to read them;
  - at most `maxEmptyFrames` (100) empty DATA frames in a row;
  - a glitch budget (`glitchBurst` 10 000, refilled at `glitchesPerSecond` 330: nghttp2's numbers); counted events:
    PRIORITY, unknown frame types and empty DATA (as nghttp2), every stream error the peer causes (our RST_STREAM answers to
    its errors: MadeYouReset), SETTINGS (our addition), and a PING with no DATA or HEADERS of ours since the previous PING
    (our addition, after grpc-go's ping strikes, `http2_server.go:279-281`, `:906-910`: a gRPC client's bandwidth probe
    follows our DATA, `bdp_estimator.go`, and is free). WINDOW_UPDATE on a closed stream is free: Go's client credits
    every 4 KiB it reads, also while it still reads a body whose stream is already closed on our side (`transport.go:2261-2265`);
  - on a server, a budget for the client's RST_STREAM frames (`resetBurst` 1000, `resetsPerSecond` 33, as nghttp2), which a
    client does not apply (a server may end a response early with RST_STREAM NO_ERROR, §8.1);
  - more than 4 x SETTINGS_MAX_CONCURRENT_STREAMS refused streams in a row (a reset stream counts until its handler
    returns).
- A client takes any number of interim (1xx) responses, but their field sections together stay within
  SETTINGS_MAX_HEADER_LIST_SIZE, as in kuicksilver-http3; past that the response is discarded (RST_STREAM CANCEL, §8.2).
- Per-frame work does not grow with the number of streams: counters for open and running streams, and only the streams
  waiting for window are looked at when window arrives.
- The server engine on top (`Http2Serving.kt`, `RepeatOffenders.kt`, `TcpListener.kt`): a reset stream's handler is
  cancelled and its stream counts until the handler returns, so running handlers never pass SETTINGS_MAX_CONCURRENT_STREAMS;
  a connection that is over gets the send-stall deadline for what it still has to write, then its socket is aborted (a
  flood that does not read our answers cannot hold it until the idle timeout); opt-in (`http2RepeatOffenderPenalty`, off
  by default: behind a shared address one flooder would lock everyone out, and §10.5 does not ask for it), an address
  whose connections end in a flood limit's ENHANCE_YOUR_CALM three times within a minute has its TCP connections closed
  at accept, before TLS, for the penalty (an IPv4-mapped peer as its IPv4 address, IPv6 by its /56, at most 4096
  addresses remembered).

  PRIORITY, unknown frames, empty DATA and stream errors (`session_update_glitch_ratelim` call sites, e.g.
  `nghttp2_session.c:3712`, `:5731`, `:5844`, `:6026`); a reset limit of 1000 refilled at 33 per second that only a server

## <a id="s8-messages-and-tls-in-the-engines"></a>§8, §9 — messages and TLS (client)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §8, §9.

**Requirement.** HTTP semantics over HTTP/2 (§8: field validity, pseudo-header fields, malformed messages, content-length, CONNECT and Extended CONNECT) and TLS usage (§9.2: TLS 1.2 or later with SNI, no renegotiation or compression, the TLS 1.2 cipher suite block list).

**Recorded status.** ✅ 0.3.0 (the client; the server: see the next section)

**How it is met.**

- The connection core enforces the frame-level rules of §8.1 (field sections only at the start and end of a stream,
  END_STREAM on trailers, none on an interim response, no DATA before the final field section) and treats a 101 response
  as malformed (§8.6: HTTP/2 does not support it).
- `io.kuicksilver.http2.message` (`H2Fields`, `H2Messages`) is the port of kuicksilver-http3's field rules (ADR-0017):
  lowercase token names and values without NUL, CR, LF or edge whitespace (§8.2.1, as RFC 9110 §5.5 for other controls),
  no connection-specific fields and `te` only `trailers` (§8.2.2), pseudo-header fields first, known, once and in the right
  message (§8.3), `:authority` and `host` as RFC 3986 authorities and equal when both are present (§8.3.1), content-length
  digits only and consistent. `tools/vectors/http-fields.json` holds the cases both copies run (`HttpFieldVectorsTest` in
  each module).
- The client builds requests with `:method`, `:scheme`, `:authority` (never `host`, §8.3.1) and `:path` and checks them
  against the same rules; connection-specific fields of the Ktor request are dropped. Every response is checked: a
  malformed one (§8.1.1: a field rule, content-length that does not match the DATA, content in a HEAD, 204 or 304
  response) resets its stream with PROTOCOL_ERROR and fails the call with `Http2Exception.MalformedMessage`; interim
  responses are skipped (100 Continue releases an `Expect: 100-continue` body); trailers are checked and do not end the
  body early. A response field section above our SETTINGS_MAX_HEADER_LIST_SIZE fails its call only
  (`Http2Exception.FieldSectionTooLarge`) and resets the stream with CANCEL.
- §8.1: a server that answers before the whole request and resets the stream with NO_ERROR stops our sending; the
  response stands.
- §8.5 CONNECT is not used by the client (proxies are reached over HTTP/1.1 CONNECT before TLS). The internal
  `H2ClientConnection.open` refuses `:protocol` (RFC 8441 §4, Extended CONNECT) with IllegalArgumentException until the
  server has sent SETTINGS_ENABLE_CONNECT_PROTOCOL = 1 (the Ktor engine never sends `:protocol` over HTTP/2).
- §9.2: TLS 1.2 or later (TLS 1.3 by default; TLS 1.2 only when the client allows it, `TlsVersions.Tls12And13`), with
  SNI for a domain name (`sniOf`), and the general guidance of RFC 9325 (the TLS 1.2 profile of RFC 10015). Over TLS 1.2:
  - §9.2.1 compression: every `ksl` context sets `SSL_OP_NO_COMPRESSION` (`ksl_ctx_new`; the C test
    `tcp_tls12_profile_and_ems` checks it).
  - §9.2.1 renegotiation: every context sets `SSL_OP_NO_RENEGOTIATION`, so `ksl` never starts one and OpenSSL refuses a
    server's HelloRequest with a no_renegotiation warning. "An endpoint MUST treat a TLS renegotiation as a connection
    error (Section 5.4.1) of type PROTOCOL_ERROR": `ksl_msg_cb` sees the HelloRequest of an established TLS 1.2 session
    before OpenSSL refuses it and reports it (`KSL_GET_RENEGOTIATION`; the read stops there), `TlsConnection` fails the
    input of an `h2` connection after the plaintext that came before it (`renegotiationAttempted`), and
    `H2ClientConnection.start(connectionErrorOf)` turns that into a connection error: GOAWAY with PROTOCOL_ERROR on the
    output, which still works, then close_notify (§5.4 above), and the calls fail with `Http2Exception.ConnectionClosed`
    (`code` PROTOCOL_ERROR, `byPeer` false). A server that asked for the renegotiation fails on our no_renegotiation
    warning, which goes first (OpenSSL: "Terminate with a fatal alert because if the application tried to renegotiate it
    presumably had a good reason"; the JDK alike), so it does not read that GOAWAY. Over `http/1.1` the connection goes on,
    as before. The client never renegotiates for credentials, so the "prior to sending the connection preface" case does
    not arise; the server's SHOULD is not ours.
- §9.2.3 (TLS 1.3): "HTTP/2 clients MUST treat a TLS post-handshake CertificateRequest message as a connection error
  (Section 5.4.1) of type PROTOCOL_ERROR." `ksl` never offers post_handshake_auth, so OpenSSL refuses a server's
  CertificateRequest with unexpected_message before the message type is visible to anyone (the read transition fails
  before the message callback); `TlsConnection` notes that refusal (`postHandshakeMessageRefused`: TLS 1.3,
  unexpected_message sent by us, `SSL_R_UNEXPECTED_MESSAGE`), and the engine's `connectionErrorOf` makes it a connection
  error of type PROTOCOL_ERROR: the calls fail with `Http2Exception.ConnectionClosed` (`code` PROTOCOL_ERROR); the GOAWAY
  is attempted, but the TLS session already ended with the fatal alert. Any other post-handshake message OpenSSL refuses
  there is a PROTOCOL_ERROR too. No server we can drive sends a CertificateRequest to a client that did not offer
  post_handshake_auth (OpenSSL and the JDK refuse to), so the recognition is tested on the failure as ksl reports it.
  - §9.2.1 key exchange sizes: the TLS 1.2 suites are ECDHE only (no DHE, so the DHE sizes do not arise) over X25519,
    P-256, X448, P-384 and P-521, all of at least 224 bits.
  - §9.2.2 cipher suites: the TLS 1.2 list is the fixed profile `TLS12_PROFILE` (ECDHE-ECDSA and ECDHE-RSA with
    AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305), and `ksl_ctx_set_ciphers` refuses any other TLS 1.2 suite: none is on
    the Appendix A list, so no prohibited suite can be negotiated and INADEQUATE_SECURITY (a MAY) never applies; the
    mandatory `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` with P-256 is in it.

## <a id="s8-messages-and-tls-server"></a>§8, §9 — messages and TLS (server)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §8, §9 (server side).

**Requirement.** As the client section, for the requests a server receives: field validity (§8.2.1), no
connection-specific fields and `te` only `trailers` (§8.2.2), cookie fields joined with `"; "` before they leave HTTP/2
(§8.2.3), request pseudo-header fields (§8.3.1: `:method`, `:scheme`, `:path` present and not empty, `:authority` without
userinfo, a `host` that identifies another entity than `:authority` SHOULD make the request malformed), content that
matches `content-length` (§8.1.1, both ways: a response is a message too), a malformed request a stream error of type
PROTOCOL_ERROR; a server MUST NOT generate connection-specific fields and never sends 101 (§8.6); CONNECT (§8.5); a
request the server did not process may be refused only when that is guaranteed (§8.7); a field section above
SETTINGS_MAX_HEADER_LIST_SIZE may get 431 (§8.2, §10.5.1); a stream error affects only its stream and no RST_STREAM
answers a RST_STREAM (§5.4.2); and TLS (§9.2).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `H2Messages.parseRequest` (the rules above, the shared vectors of `tools/vectors/http-fields.json`) runs on every
  request field section before the engine sees it (`H2Runtime.newRequest`); a malformed one, and one whose HEADERS end the
  stream with a non-zero `content-length`, is reset with PROTOCOL_ERROR and never delivered; content that does not match
  `content-length` resets the stream when it shows (and cancels the handler). `host` and `:authority` are compared as
  RFC 9110 §4.2.3 normalizes them (case-insensitive host, a missing port is the scheme's default); `:scheme` must have
  the syntax of a URI scheme (RFC 3986 §3.1; §8.3.1 calls it the scheme portion of the target URI). A field section above
  our SETTINGS_MAX_HEADER_LIST_SIZE is answered 431 (with `date`); when the stream can no longer send by the time its
  event is handled (the client reset it, or a later error in the same read closed it) nothing is answered, and when the
  client's own SETTINGS_MAX_HEADER_LIST_SIZE is too small for the 431 head (§6.5.2) the stream is reset with CANCEL;
  either way the stream is released and the connection goes on. Only the field section that opens a stream is a
  request (`H2Event.HeadersReceived.opening`): trailers that reach a stream the handler already released while its
  response is still being written are dropped, pseudo-header fields or not (§8.1), and never start a handler outside
  SETTINGS_MAX_CONCURRENT_STREAMS (§5.1.2). What the server generates obeys the same rules (§8.2.1, §8.2.2, §8.3.2):
  `H2Runtime.respond` and `respondTrailers` refuse a field name that is not a lowercase token, a value with NUL, CR, LF,
  another control character or a character above U+00FF, a connection-specific field or `te`, and a `:status` outside
  100..599 or 101; the section is never sent, the stream is reset with INTERNAL_ERROR and the call fails with
  IllegalArgumentException. HPACK (and QPACK) refuse a character above U+00FF instead of sending its low byte. A classic
  CONNECT (§8.5) is answered 501, the engine having no tunnels; an Extended CONNECT for `websocket` is a WebSocket (RFC
  8441, with `webSocketsOverHttp2`: [RFC 8441](8441.md#s5-websocket-server)), for any other protocol 501. Without
  `webSocketsOverHttp2` SETTINGS_ENABLE_CONNECT_PROTOCOL is not sent, so `:protocol` is malformed (RFC 8441 §3). A
  CONNECT stream carries no field section after its request (§8.5: anything but DATA and stream management frames
  "MUST be treated as a stream error"): a client's HEADERS there is a stream error PROTOCOL_ERROR, and a content-length
  of a CONNECT request is not held against the tunnel's bytes (RFC 9110 §9.3.6: "A CONNECT request message does not have
  content").
- `h2/H2Call.kt`, `h2/H2Request.kt`: each stream is a Ktor call (`httpVersion` "HTTP/2", the connection's scheme
  `https` whatever `:scheme` names, `:authority` as `Host`, split `cookie` fields joined with `"; "`); `Expect: 100-continue` gets an interim 100 when the
  handler first reads the body (RFC 9110 §10.1.1), another expectation 417.
- `h2/H2Response.kt`: names lowercase, connection-specific fields and `te` dropped (§8.2.2), values without edge
  whitespace; no content for HEAD, 204 or 304, and no Content-Length on 204 (nor Ktor's `0` on 304); `Date` on every
  response, the engine's own 425 and 501 included (RFC 9110 §6.6.1); an HTTP/1.1 upgrade answer becomes 501, and an
  application's 1xx as a final response a 500 without content (§8.6). Content that does not match the response's
  `content-length` never goes out as a complete response: the stream is reset with INTERNAL_ERROR before the extra bytes
  or instead of the END_STREAM of a short body (§8.1.1). A call that ends without a response on a live stream resets it
  (INTERNAL_ERROR); a stream the client reset, or that ended both ways, gets nothing more (§5.4.2, §5.1; the core refuses
  such a reset too). Whatever a call throws ends its stream only: it is logged, the handlers run under a supervisor, and
  no error response is tried on a stream that already failed (§5.4.2). REFUSED_STREAM only for a stream above our
  SETTINGS_MAX_CONCURRENT_STREAMS, before any processing (§8.7, the core). A client's RST_STREAM, NO_ERROR included,
  cancels its handler (the NO_ERROR rule of §8.1 is the client's, for a server's early response).
- §8.1: a request still arriving when its handler is done with a complete response is stopped with RST_STREAM NO_ERROR
  after the response's last frame (`H2ConnectionCore.release`; Go's `server.go` `wroteFrame` does the same), so a
  released stream does not take content nobody reads.
- §9.2: TLS 1.3 only (see [§3.2, §3.3 (server)](#s3-2-starting-http-2-server)).

## <a id="s8-7-request-reliability"></a>§8.7 — request reliability (client)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §8.7.

**Requirement.** A request on a stream above the last stream identifier of a GOAWAY, or refused with REFUSED_STREAM, was
not processed and can be retried whatever its method; other failures do not say that.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- The core reports such streams as `notProcessed`; the runtime surfaces them as `Http2Exception` with `notProcessed`,
  and so is a stream whose HEADERS never left this client (a lost connection). The engine repeats such a request at most
  twice (as over HTTP/3), on a usable connection of the route or a new one, emitting `retry` and counting `attempts`; a
  streamed body that was already consumed cannot be repeated (`H3BodyConsumed`). A second REFUSED_STREAM on one
  connection retires it (OkHttp `RealConnection.trackFailure`).
- HTTP_1_1_REQUIRED (§7) marks the route: its new connections offer only `http/1.1` for 5 minutes, doubling up to 2
  days (`FallbackReason.H2Refused`). Whether the server answered on the request's stream (RST_STREAM) or for the
  connection (GOAWAY), the request goes again over HTTP/1.1 only when it was provably not processed or is idempotent
  with a body that can be sent again (RFC 9110 §9.2.2); otherwise the call fails with `Http11RequiredException`, which
  says the route now uses HTTP/1.1 and the application may repeat the request (owner decision, 2026-11-05). A malformed
  or too large response on such a connection stays the response's failure.
- Any other failure fails the call: no silent repeat over HTTP/1.1.

## <a id="s9-1-connection-management"></a>§9.1 — connection management (client)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §9.1.

**Requirement.** Clients SHOULD NOT open more than one HTTP/2 connection to a given host and port pair (an origin);
a client can open another when the first reaches the server's SETTINGS_MAX_CONCURRENT_STREAMS. Idle connections may be
closed with GOAWAY.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `H2Pool`: one connection per route (scheme, host, port, proxy) while it has a free stream. Only one request at a time
  connects to a route that may speak HTTP/2 (ALPN is known only after the handshake): the others wait for its outcome
  without a pool permit, within their connect timeout, and use its connection, or connect in parallel when it turned
  out HTTP/1.1 (Go's `dialCall`; routes last seen on HTTP/1.1 do not wait, at most 1000 remembered). A connection that
  still finds another HTTP/2 connection with room is closed (OkHttp `RealRoutePlanner`). At the server's limit a second connection opens, within
  `maxConnectionsPerRoute`; at that limit a request waits for a free stream within the connect timeout.
- A connection without streams for `idleTimeout`, or past `maxConnectionLifetime`, gets GOAWAY (NO_ERROR) and closes once
  its streams are done; a server's GOAWAY moves new requests to a new connection.
- Waits on the server: its preface is bounded by the connect timeout and our SETTINGS acknowledgement by
  `settingsAckTimeout`; a connection from which nothing arrived for 10 s is checked with a PING before it takes a request
  (bounded by half the connect timeout, at most 5 s; Chromium checks a session "at risk of loss" the same way; one PING
  per connection at a time, shared by the requests that wait for it). One that does not answer takes no new request: it
  gets GOAWAY when calls still run on it (they finish or fail on their own) and is closed when none do, while the
  request, never sent there, takes another connection. A response or a shut
  send window is bounded by the request's socket timeout, or `pingInterval`, when set: with neither (Ktor's default), a
  connection that dies in the middle of an exchange holds that call until TCP itself gives up, as over HTTP/1.1.

## <a id="s9-1-connection-management-server"></a>§9.1 — connection management (server)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §9.1 (server side), §6.8.

**Requirement.** Servers may close idle connections; the endpoint that closes the connection SHOULD first send GOAWAY
(§9.1). A graceful shutdown can first send GOAWAY with 2^31 − 1 and, after a round trip, the last stream taken (§6.8).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `Http2Serving.kt`, `serveH2`: the client's connection preface must arrive within what is left of
  `requestHeaderTimeoutSeconds` after the TLS handshake, else GOAWAY (NO_ERROR, last stream 0) and close; each field
  block within `requestHeaderTimeoutSeconds` (the core's `maxHeaderBlockTime`, bounded by it; else GOAWAY
  ENHANCE_YOUR_CALM); each wait for request content within `connectionIdleTimeoutSeconds` (`RequestBodyTimeout`, 408
  when nothing answered); each wait for the client's window within the send-stall deadline (the stream is reset with
  CANCEL). A connection without requests for `connectionIdleTimeoutSeconds` (counted on a monotonic request count, so a
  request that came and went restarts it) gets the two-step GOAWAY and closes; one that cannot even write it within the
  send-stall deadline once its last request is done is aborted. Every close goes through `closeWithin`, as on HTTP/1.1;
  the TLS close waits up to 3 s for the client's close_notify.
- A second graceful GOAWAY (an idle close under way when the engine stops) keeps the first one's two steps.
- A stop (`draining`) sends the two-step GOAWAY of the core to every HTTP/2 connection: the requests taken finish,
  streams opened after the second GOAWAY are discarded (the client learns from its last stream identifier that they were
  not processed), and the connection closes when its requests are done or at the end of the grace period.
- A client's RST_STREAM cancels its handler (`H2ServerStream.invokeOnFailure`).

## <a id="s9-1-1-connection-reuse"></a>§9.1.1 — connection reuse across origins

Status: ❌ · [summary](../rfc-compliance.md#http)

Original row: RFC 9113 §9.1.1.

**Requirement.** A connection MAY be reused for another origin whose host the certificate covers and that resolves to the
same address (coalescing); it is optional.

**Recorded status.** ❌ by decision for 0.3.0

**How it is met.**

- ADR-0017 (owner decision 6): no coalescing in 0.3.0; each route has its own connections.
- Server side: a request a coalescing client sends for a host the connection's certificate does not name gets 421 on its
  stream (0.3.0; [RFC 9110 §7.4](9110.md#s7-4-server-misdirected-requests)).
