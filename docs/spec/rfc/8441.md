# RFC 8441 — Bootstrapping WebSockets with HTTP/2

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="websocket-over-http-2"></a>§3, §4 — SETTINGS_ENABLE_CONNECT_PROTOCOL and Extended CONNECT

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §3: "The value of the parameter MUST be 0 or 1"; "Upon receipt of SETTINGS_ENABLE_CONNECT_PROTOCOL with a
value of 1, a client MAY use the Extended CONNECT ... Receipt of this parameter by a server does not have any impact";
"A sender MUST NOT send a SETTINGS_ENABLE_CONNECT_PROTOCOL parameter with the value of 0 after previously sending a
value of 1"; without the setting a `:protocol` request is malformed (a stream error). §4: `:protocol` "MAY be included
on request HEADERS", is single valued and "contains a value from the 'Hypertext Transfer Protocol (HTTP) Upgrade Token
Registry'"; "On requests that contain the :protocol pseudo-header field, the :scheme and :path pseudo-header fields of
the target URI ... MUST also be included"; `:authority` keeps its usual meaning and "the server MUST NOT create a
tunnel to the host indicated by the :authority". The stream is then a CONNECT tunnel of RFC 9113 §8.5: after the initial
HEADERS of each side only DATA (and stream management frames) go on it, anything else "MUST be treated as a stream
error"; a 2xx switches to tunnel mode and a client "MUST ignore any Content-Length" in it (RFC 9110 §9.3.6).

**Recorded status.** ✅ 0.3.0 (both engines)

**How it is met.**

- `kuicksilver-http2`, core: a server started with `enableConnectProtocol` (`H2ServerConnection.start`; the Ktor server's
  `webSocketsOverHttp2`) puts SETTINGS_ENABLE_CONNECT_PROTOCOL = 1 in its first SETTINGS and never sends it again, so
  never a 0 after it; a client core cannot be asked to send it (IllegalArgumentException). A value above 1 is a
  connection error PROTOCOL_ERROR; a server's 0 after its 1 is one too on the client, as in nghttp2, since Extended
  CONNECT streams opened meanwhile would turn malformed; a server ignores the parameter
  (`core/H2ConnectionCore.frames.kt`).
- `message/H2Fields.kt`: `:protocol` only with the setting (on the server: the one it sent; on the client: the server's,
  checked before a stream opens, IllegalArgumentException otherwise), only on CONNECT, as a token (the form of an
  Upgrade Token Registry name, RFC 9110 §16.7), and with `:scheme`, `:path` and `:authority`, which then follow the
  rules of an ordinary request (RFC 9113 §8.3.1), not those of a classic CONNECT; a request without the setting is a
  stream error PROTOCOL_ERROR.
- `runtime/H2Runtime.kt`: a CONNECT answered with a 2xx is a tunnel: its DATA are not message content (no content-length
  holds them, the client ignores one in the 2xx), END_STREAM ends each direction in order, a HEADERS frame after the
  initial ones is a stream error PROTOCOL_ERROR on either side, a server's 2xx to CONNECT never carries a content-length
  ("A server MUST NOT send any Transfer-Encoding or Content-Length header fields in a 2xx": the head is refused,
  IllegalArgumentException, and the stream reset with INTERNAL_ERROR) (and a server's `trailers` on a tunnel throws
  IllegalStateException instead of sending one); a CONNECT request's own content-length is not held against the tunnel's
  bytes (RFC 9110 §9.3.6: "A CONNECT request message does not have content"). Flow control is that of any stream (RFC
  9113 §5.2): credit goes back only as the application reads.
- `H2ClientConnection.serverAllowsExtendedConnect` and `awaitServerSettings()` let the client engine decide on the
  server's SETTINGS, never on the initial value.
- No tunnel to `:authority` is ever made: the server engine serves `websocket` only (§5 below); any other `:protocol`,
  and a classic CONNECT, gets 501.

**Tests that pin it.**

- `core.SettingsTest.extendedConnectAdvertisedOnlyWhenEnabled`, `.negative_serverWithdrawingExtendedConnectIsAProtocolError`,
  `.negative_booleanSettingsOtherThanZeroOrOne`
- `message.H2MessagesTest.negative_extendedConnectNeedsTheSetting`, `.negative_extendedConnectProtocolIsAToken`
- `runtime.H2ExtendedConnectTest.serverSettingIsSeenByTheClient`, `.tunnelCarriesDataBothWaysAndEndsInOrder`,
  `.negative_protocolOnlyWithConnect`, `.negative_noProtocolWithoutTheServersSetting`,
  `.contentLengthOfASuccessfulConnectResponseIsIgnored`, `.negative_headersOnAConnectedStreamAreAStreamError`,
  `.refusedConnectIsAnOrdinaryResponse`, `.negative_noTrailersOnAConnectStream`,
  `.negative_contentLengthInASuccessfulConnectResponseIsNeverSent`;
  `runtime.H2RuntimeTest.negative_extendedConnectNeedsTheServersSetting`

**History.**

- 0.3.0: the first release with HTTP/2 (ADR-0017), WebSockets over HTTP/2 in both engines included.

**Notes on peers.** nghttp2 ends the connection when a server takes the setting back
(`nghttp2_session.c`, "server attempted to disable SETTINGS_ENABLE_CONNECT_PROTOCOL") and also ignores a content-length
of a 2xx to CONNECT (`nghttp2_http.c`). OkHttp has no RFC 8441.

## <a id="s5-websocket-server"></a>§5 — WebSocket over HTTP/2 (server engine)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §5: `:protocol` "MUST have a value of "websocket""; the request "replaces the GET-based request in
[RFC6455]"; Connection and Upgrade "MUST NOT be included"; "Implementations using this extended CONNECT to bootstrap
WebSockets do not do the processing of the Sec-WebSocket-Key and Sec-WebSocket-Accept header fields"; Origin,
Sec-WebSocket-Version, -Protocol and -Extensions are used as in RFC 6455; after the handshake the stream is the
WebSocket's TCP connection: "Orderly TCP-level closures are represented as END_STREAM flags", "RST exceptions are
represented with the RST_STREAM frame ... with the CANCEL error code".

**Recorded status.** ✅ 0.3.0 (`http2 = true`, `webSocketsOverHttp2` on by default)

**How it is met.**

- `Http2Serving.kt`: with `webSocketsOverHttp2` the connection advertises the setting (§3); a CONNECT whose `:protocol`
  is `websocket` (any case, RFC 9110 §7.8) is a WebSocket call, any other CONNECT 501 (as RFC 9220 §3 has it for HTTP/3).
  Before the application sees it, its Sec-WebSocket-Version must be one field `13` (RFC 6455 §4.2.1): none or several
  give 400, another value 426 with `sec-websocket-version: 13` (§4.2.2).
- `h2/WebSocketOverH2.kt`: the request reaches Ktor's pipeline as the HTTP/1.1 upgrade request its `WebSockets` plugin
  knows (`GET`, `Connection: Upgrade`, `Upgrade: websocket`, a random `Sec-WebSocket-Key` that never goes on the wire,
  `Host` from `:authority`), so `webSocket {}` routes serve it unchanged, with `call.request.httpVersion` `"HTTP/2"`.
  The upgrade is answered `:status 200` with the plugin's other headers (`sec-websocket-protocol`,
  `sec-websocket-extensions`) and without `sec-websocket-accept`, `content-length` and connection-specific fields. A 2xx
  from a route that is not a WebSocket one becomes 501 (RFC 9110 §9.3.6: a 2xx is a tunnel; nobody accepted one); an
  extension conflict refuses the upgrade before anything is sent, as over HTTP/1.1.
- The session reads the stream's DATA through the frame guard (RFC 6455 §5.1, §5.2; permessage-deflate as over
  HTTP/1.1) and writes its frames as DATA within the client's windows; a wait for window longer than the send-stall
  deadline resets the stream. The session's end ends the stream with END_STREAM; the client's rest is not read (the
  stream is released, which stops it with RST_STREAM NO_ERROR after our END_STREAM, RFC 9113 §8.1). A call cancelled
  or failed while the session runs resets the stream with CANCEL; a client's RST_STREAM ends the session; neither
  reaches the connection. The stream is not bounded by the request-body idle timeout: a WebSocket may be quiet.

## <a id="s5-websocket-client"></a>§5 — WebSocket over HTTP/2 (client engine)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** As for the server, from the client's side: the CONNECT with `:protocol = websocket`, "The scheme of the
target URI ... MUST be "https" for "wss"-schemed WebSockets", no Connection, Upgrade or Host, no Sec-WebSocket-Key
processing, and RFC 6455's rules for the other fields (§4.1: an extension or a subprotocol the client did not offer
fails the connection); §3: no `:protocol` before the server's SETTINGS_ENABLE_CONNECT_PROTOCOL = 1 arrived.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `h1/H1Pool.kt` (`webSocketConnection`): a `wss://` WebSocket looks for a usable HTTP/2 connection of its `https`
  origin's route (the same connections, proxy included); one whose server's SETTINGS allowed Extended CONNECT takes a
  stream for it. One whose SETTINGS have not arrived yet (its first request in flight) is waited for, within the connect
  timeout, before the WebSocket decides (§3). Without one (no HTTP/2 connection, a server without the setting, no free
  stream, the route marked HTTP_1_1_REQUIRED) the WebSocket opens a connection of its own offering `http/1.1` only and
  upgrades as in 0.2: a WebSocket never opens an HTTP/2 connection (Chromium does the same). It holds its remote host's
  CONNECTING key (RFC 6455 §4.1) until the server answered, within the connect timeout, as over HTTP/1.1.
- `h2/H2WebSocket.kt`: CONNECT with `:protocol = websocket`, `:scheme` `https`, the URI's authority and path (query
  included), and Ktor's handshake fields without `sec-websocket-key`, `sec-websocket-accept`, `connection`, `upgrade` and
  `host`; `sec-websocket-version: 13`, `origin`, cookies, `sec-websocket-protocol`, `sec-websocket-extensions` and the
  request's priority go as they are. A 2xx answer opens the session after its extensions (`webSocketAfterHandshake`) and
  its subprotocol (one of those offered, at most one field, RFC 6455 §4.1, §11.3.4) were checked; it is reported to Ktor
  as 101 with version `HTTP_2_0`. Any other answer is an ordinary response, which fails Ktor's handshake as an HTTP/1.1
  answer without 101 does. REFUSED_STREAM and streams above a GOAWAY go again (RFC 9113 §8.7), HTTP_1_1_REQUIRED marks
  the route and the WebSocket goes over HTTP/1.1.
- The session's input goes through the frame guard (server frames unmasked, RSV bits as negotiated, permessage-deflate)
  and is credited as the session reads; its output goes as DATA within the server's windows, a send stall bounded by the
  socket timeout. A session that ended in order (its output closed) ends the stream with END_STREAM and waits up to 5 s
  for the server's (RFC 6455 §7.1.1); a handshake refused here or a call that failed or was cancelled resets the stream
  with CANCEL. A cancelled `webSocket {}` block is closed by Ktor itself with a Close frame, so it ends in order.
