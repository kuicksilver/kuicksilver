# RFC 9325 — Recommendations for Secure Use of TLS and DTLS

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="s3-1-1-tls-1-2"></a>§3.1.1 — TLS 1.2 supported, TLS 1.3 preferred

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** "Implementations MUST support TLS 1.2 [RFC5246]." "Implementations SHOULD support TLS 1.3 [RFC8446] and,
if implemented, MUST prefer to negotiate TLS 1.3 over earlier versions of TLS." "To the extent that an implementation
supports TLS 1.2 (even if it defaults to TLS 1.3), it MUST follow the recommendations regarding TLS 1.2 specified in this
document." "New transport protocols that integrate the TLS/DTLS handshake protocol and/or record layer MUST use only
TLS/DTLS 1.3 (for instance, QUIC [RFC9001] took this approach)." And the versions below: "Implementations MUST NOT
negotiate SSL version 2", "SSL version 3", "TLS version 1.0 [RFC2246]", "TLS version 1.1 [RFC4346]".

**Recorded status.** ✅ 0.3.0 (before: the TLS layer and the Ktor client offered TLS 1.2 on request since 0.2.0, but
every TCP connector of the Ktor server engine was TLS 1.3 only, so a server built on the engine could not support TLS 1.2).
The ✅ is for TLS 1.2 support and the preference for TLS 1.3. Of the TLS 1.2 recommendations the last quote refers to,
one is a recorded deviation: deterministic ECDSA, RECOMMENDED by §4.2 ([§4.2, 🔶](#s4-2-deterministic-ecdsa)); the
others are met as listed below.

**How it is met.**

- TLS layer (`kuicksilver-tls`): `TlsVersions.Tls12And13` allows TLS 1.2 over TCP on either side; `TlsVersions.Tls13`
  stays the default (RFC 9852). QUIC refuses anything but `Tls13` when the configuration is built (`validateFor`, RFC 9001
  §4.2). TLS 1.0 and 1.1 can never be configured: `ksl_ctx_set_option` takes only `KSL_TLS1_2` or `KSL_TLS1_3` as bounds,
  and OpenSSL is built without SSLv2 and SSLv3.
- Ktor server (`kuicksilver-ktor-server`, 0.3.0): `tlsConnector(identity) { versions = TlsVersions.Tls12And13 }`
  (*experimental*, off by default), the `EngineMain` key `kuicksilver.tls.versions = tls12And13` for the deployment port,
  and on the JVM Ktor's own `sslConnector { enabledProtocols = listOf("TLSv1.2", "TLSv1.3") }`
  (`ktor.security.ssl.enabledProtocols`; `SslConnectorBridge.kt` `sslVersions`). TLS 1.2 alone, TLS 1.0 or 1.1 there
  fail the start with `TlsException.Config`. The connector's TCP configuration carries the versions
  (`KuicksilverTlsConnector.tlsConfig(alpn, handshakeTimeout, quic = false)`); its HTTP/3 listener on the same port gets a
  TLS 1.3-only configuration (`quic = true`). A default connector refuses a TLS 1.2 client with `protocol_version` (RFC
  9846 App. E.2: "If the "supported_versions" extension is absent and the server only supports versions greater than
  ClientHello.legacy_version, the server MUST abort the handshake with a "protocol_version" alert").
- TLS 1.3 preferred: OpenSSL negotiates the highest version both sides offer, so a client with TLS 1.3 gets it from a
  `Tls12And13` server too; a server that negotiates TLS 1.2 sets the RFC 9846 §4.1.3 downgrade sentinel ("If negotiating
  TLS 1.2, TLS 1.3 servers MUST set the last 8 bytes of their Random value to the bytes: 44 4F 57 4E 47 52 44 01"), so a
  client with TLS 1.3 detects an attacker who stripped it from the offer.
- The TLS 1.2 recommendations of this document, on the server as on the client: no compression (§3.3,
  `SSL_OP_NO_COMPRESSION`); the renegotiation_info extension (§3.5, RFC 5746, always in OpenSSL) and no renegotiation at
  all (`SSL_OP_NO_RENEGOTIATION`; on an `h2` connection an attempt is a PROTOCOL_ERROR, RFC 9113 §9.2.1); Extended Master
  Secret required ([§3.5](#s3-5-ems)); only ECDHE with AES-GCM or ChaCha20-Poly1305 (§4.1, §4.2, RFC 10015: no NULL, RC4,
  export, static RSA, (EC)DH, DHE or CBC suites, nothing under 128 bits), in the order of [§4.2.1](#s4-2-1-suite-preference);
  keys and signatures of at least 112 bits ([§4.5](#s4-5-public-key-length)); SNI with `unrecognized_name` for a name an
  `sniSelector` does not know (§3.7); ALPN with `no_application_protocol` when nothing matches (§3.8). Not met: §4.2's
  RECOMMENDED deterministic ECDSA ([§4.2](#s4-2-deterministic-ecdsa)).
- Resumption (§3.4): tickets are AES-256 encrypted and HMAC-SHA256 authenticated (`ksl_ctx.c`), the keys rotate every
  `SessionTicketConfig.rotateEvery` (at most 7 days, default 1 day) and a ticket lives at most half of that. "A TLS 1.2
  server SHOULD NOT resume sessions that are too old, e.g., sessions that have been open longer than two
  ticket-encryption key rotation periods": a renewed TLS 1.2 ticket keeps the time of the full handshake (OpenSSL gives
  only a TLS 1.3 ticket a fresh one, `ssl/statem/statem_srvr.c` `tls_construct_new_session_ticket`), so a TLS 1.2 session
  resumes for at most `ticketLifetime` after its full handshake, under half a rotation period. With explicit
  `SessionTicketConfig` keys the library rotates nothing: `rotateEvery` is then the period the application declares,
  and the "two rotation periods" reading holds when it replaces its keys at least that often (the guide asks it to); the
  bound of `ticketLifetime` after the full handshake holds either way.
- Client certificates, `sniSelector` identities and the HTTP/1.1 and HTTP/2 serving are the same over TLS 1.2; HTTP/2 is
  offered over TLS 1.2 too (RFC 9113 §9.2, [details](9113.md#s3-2-starting-http-2-server)).

**Tests that pin it.**

- `ServerTls12Test.tls12ClientServedWhenAllowed` (version 1.2, EMS used, a TLS 1.3 client still served),
  `.negative_defaultConnectorRefusesTls12WithProtocolVersion`, `.h2OverTls12WhenHttp2On`,
  `.tls12ClientCertificateReachesTheApplication`, `.tls12WithSniSelector`, `.tls12And13ConnectorStillServesHttp3`,
  `.negative_http2OverTls12WithoutRsaCertificateIsLogged` (JVM and Kotlin/Native, a raw `ksl` TLS 1.2 client)
- `ServerTls12JdkClientTest` (the JDK's TLS 1.2 client): `.jdkTls12ClientOverHttp11`, `.jdkTls12ClientOverH2`,
  `.negative_defaultConnectorRefusesJdkTls12`, `.negative_cbcSha1AndStaticRsaOnlyClientsRefused`,
  `.negative_jdkTls12ClientWithoutEmsRefused` (a forked JVM with `jdk.tls.useExtendedMasterSecret=false`),
  `.negative_renegotiationOnH2EndsWithGoaway`, `.tls12ServerHelloCarriesTheDowngradeSentinel` (also renegotiation_info,
  type 0xff01, in the ServerHello: §3.5, "TLS 1.2 clients and servers MUST implement the renegotiation_info extension"),
  `.rsaConnectorServesTheMandatoryHttp2Tls12Suite`
- `EngineMainTest.tlsVersionsKeyParsed`, `.tlsVersionsKeyServesTls12`, `.negative_tlsVersionsKeyWithSslPortRefused`;
  `SslConnectorBridgeTest.enabledProtocolsMapToVersions`, `.enabledProtocolsWithTls12ServeTls12Clients`
- `Tls12ResumptionWindowTest.negative_tls12SessionNotResumedPastTheFirstTicketsLifetime` (kuicksilver-tls)
- C `tcp_default_versions_and_tls12_profile`, `tcp_tls12_profile_and_ems`, `tcp_tls12_server_suite_choice`;
  `TlsConfigTest.quicRequiresTls13Only`

**History.**

- 0.3.0: the Ktor server engine's connectors gain the `versions` option (TLS 1.2 opt-in), the `EngineMain` key
  `kuicksilver.tls.versions` and the mapping of Ktor's `enabledProtocols`; HTTP/2 is offered over TLS 1.2 by the server.

## <a id="s3-5-ems"></a>§3.5 — TLS 1.2 implementations support Extended Master Secret

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#tls)

**Requirement.** TLS 1.2 implementations MUST support the extended master secret extension (§3.5).

**How it is met.** Recorded in the row [RFC 5246 (obsoleted by RFC 9846; TLS 1.2 itself stays as written there)](5246.md#tls-1-2-tcp-explicit-only):

- only with an explicit `TlsVersions`, only with EMS (RFC 7627 §5.2: an endpoint that does not interoperate with legacy peers SHOULD abort the handshake, and ksl's refusal is that local policy; the extension is named `extended_main_secret` by RFC 9846 App. D, which leaves RFC 7627's rules in place; RFC 9325 §3.5: TLS 1.2 implementations MUST support it)

## <a id="s4-2-deterministic-ecdsa"></a>§4.2 — deterministic ECDSA

Status: 🔶 since 0.3.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** "When using ECDSA signatures for authentication of TLS peers, it is RECOMMENDED that implementations use
the NIST curve P-256. In addition, to avoid predictable or repeated nonces (which could reveal the long-term signing key),
it is RECOMMENDED that implementations implement "deterministic ECDSA" as specified in [RFC6979] and in line with the
recommendations in [RFC8446]." The same section goes on: "In deployments where side-channel attacks and fault injection
attacks are a concern, implementation strategies combining both randomness and determinism (for example, as described in
[CFRG-DET-SIGS]) can be used to avoid the risk of successful extraction of the signing key."

**Recorded status.** 🔶 0.3.0, an accepted deviation: the handshake signatures are not RFC 6979 deterministic ECDSA.

**How it is met.**

- P-256: the test and documented certificates are P-256, and P-256 is among the groups and signature schemes of both
  sides; the curve of a certificate is the deployment's choice.
- The nonce: OpenSSL 3.5's libssl passes no `nonce-type` parameter when it signs in the handshake
  (`EVP_DigestSignInit_ex` with NULL parameters: `ssl/statem/statem_srvr.c` `tls_construct_server_key_exchange`, the TLS
  1.2 ServerKeyExchange; `ssl/statem/statem_lib.c` `tls_construct_cert_verify`, the TLS 1.3 server CertificateVerify and
  a client's CertificateVerify with an ECDSA client certificate). The ECDSA nonce is then OpenSSL's default
  (`crypto/ec/ecdsa_ossl.c` `ecdsa_sign_setup` → `ossl_bn_gen_dsa_nonce_fixed_top`, `crypto/bn/bn_rand.c`), which hashes
  the private key, the message digest and fresh random bytes together: a nonce that is neither predictable nor repeated
  even with a weak random source (a failing one makes the signing fail with an error instead), the "combining both randomness and determinism" approach the section names for
  deployments where side channels and fault injection are a concern, but not the RFC 6979 construction.
- Deviation: Kuicksilver does not add a signing provider of its own to force `nonce-type=1`. Removal condition: a
  built-in provider with `nonce-type=1`, or libssl support for asking it in the handshake.

**Tests that pin it.** None: the nonce is OpenSSL's, and a deterministic one would show only as equal signatures of
equal input, which the handshake never signs twice.

## <a id="s4-2-1-suite-preference"></a>§4.2.1 — TLS 1.2 suite preference

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** §4.2.1 is the implementation detail of §4.2, "Cipher Suites for TLS 1.2", so its "first proposal" is
the first TLS 1.2 suite (a client's TLS 1.3 suites come before it in its ClientHello, as in every client that offers
both). "Clients SHOULD include TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 as the first proposal to any server.
Servers MUST prefer this cipher suite over weaker cipher suites whenever it is proposed, even if it is not the first
proposal. Clients are of course free to offer stronger cipher suites, e.g., using AES-256; when they do, the server SHOULD
prefer the stronger cipher suite unless there are compelling reasons (e.g., seriously degraded performance) to choose
otherwise." "Clients and servers SHOULD support the NIST P-256 (secp256r1) [RFC8422] and X25519 (x25519) [RFC7748]
curves."

**Recorded status.** ✅ 0.3.0 (before: a client offered TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256 first, and a TLS 1.2
server took the client's order, so a client that offered AES-128 before AES-256 got AES-128).

**How it is met.**

- `ksl_ctx.c`: a client's TLS 1.2 list is `TLS12_PROFILE_CLIENT`, TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 its first TLS
  1.2 suite.
- A server's list is `TLS12_PROFILE_SERVER`: the AES-256-GCM suites, then ChaCha20-Poly1305 (also a 256-bit key), then
  AES-128-GCM. In a TLS 1.2 handshake `server_name_cb` sets `SSL_OP_CIPHER_SERVER_PREFERENCE` (OpenSSL chooses the
  TLS 1.2 suite after that callback and a TLS 1.3 one before it), so the server's order
  decides, and `SSL_OP_PRIORITIZE_CHACHA`, so a client that puts ChaCha20-Poly1305 first (one without AES instructions,
  for which AES-GCM is the "seriously degraded performance" the SHOULD allows for) keeps it. The profile has nothing weaker
  than TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256, so the MUST holds whatever the client offers. TLS 1.3 keeps the client's
  order (no such rule for it, §4.3).
- Groups: X25519 and P-256 on both sides (with X448, P-384, P-521; `ksl_ctx_new`).

**Tests that pin it.**

- C `tcp_tls12_server_suite_choice` (AES-256 chosen over a client's AES-128 first, ksl's own client list against an RSA
  server, the RSA AES-128 suite alone accepted, a ChaCha20-first client kept, static RSA, CBC and SHA-1 lists refused with
  handshake_failure; TLS 1.3 keeps the client's order: an AES-256-first client gets AES-256 where the server's own TLS 1.3
  order would give AES-128, which fails when the server preference is set on the context; the client's first TLS 1.2
  suite), `tcp_default_versions_and_tls12_profile`
- `ServerTls12JdkClientTest.jdkTls12ClientOverHttp11` (the JDK offering AES-128 first gets AES-256)

## <a id="s4-4-aead-limits"></a>§4.4 — AEAD record limits

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** SHOULD respect the AEAD limits, RECOMMENDED 2^24.5 records for AES-GCM (§4.4).

**How it is met.** Recorded in the row [RFC 5246 (obsoleted by RFC 9846; TLS 1.2 itself stays as written there)](5246.md#tls-1-2-tcp-explicit-only):

- RFC 9325 §4.4 (SHOULD, RECOMMENDED limit 2^24.5 records for AES-GCM): with no KeyUpdate and no renegotiation a connection ends before its keys reach the AEAD's limit (2^24.5 records for AES-GCM, none for ChaCha20-Poly1305), with internal_error where an alert can be sent (a client) — C `tcp_record_limits_per_cipher`

## <a id="s4-5-public-key-length"></a>§4.5 — public key length

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** "DH key lengths of at least 2048 bits are REQUIRED"; "Curves of less than 224 bits MUST NOT be used";
"When using RSA, servers MUST authenticate using certificates with at least a 2048-bit modulus for the public key. In
addition, the use of the SHA-256 hash algorithm is RECOMMENDED and SHA-1 or MD5 MUST NOT be used [RFC9155]".

**Recorded status.** ✅ 0.3.0 (before: the peer's certificate keys were checked only where OpenSSL verified the chain, and an own certificate signed with SHA-1 or MD5 loaded).

**How it is met.**

- Key exchange: no finite-field DH at all (`no-dh` in `tools/openssl/configure-flags.txt`; RFC 10015 profile for TLS 1.2),
  and the groups are X25519MLKEM768, X25519, P-256, X448, P-384 and P-521 (`kuicksilver-native/src/c/ksl_ctx.c`), none
  under 224 bits.
- This endpoint's own certificate (a server's, and a client certificate): OpenSSL's default security level 2, which
  the Kotlin layer never lowers (only the C test hooks pass `@SECLEVEL` to `ksl_ctx_set_ciphers`), refuses to load an
  identity whose keys are under 112 bits (RSA under 2048, curves under 224; `ssl/ssl_rsa.c`, `ssl/ssl_cert.c`
  `ssl_security_cert` of OpenSSL 3.5.9). OpenSSL does not check the chain's signatures there (`SSL_SECOP_CA_MD` is
  never used), so `ksl_ctx_set_identity_pkey` runs the configured chain through the same walk as a peer's
  (`ksl_chain_security`): a SHA-1- or MD5-signed certificate, a self-signed root's own signature excepted, is refused
  and the `TlsIdentity` factories throw `TlsException.Config`.
- The peer's certificates: every key on the path, and every certificate signature on it except the anchor's, needs 112
  bits under every trust configuration (no SHA-1, no MD5), checked by OpenSSL on the path it builds, by `ksl` on the path
  the platform verifier built under `Platform` on the JVM, Android, Apple and Windows (T.5b), and by `ksl` on the
  presented chain under `Custom` and `Tofu`; see [RFC 9846 §4.5.1.3](9846.md#s4-5-1-3-weak-certificate-signatures-and-keys).
- Handshake signatures (RFC 9155): at level 2 OpenSSL neither offers nor accepts a SHA-1 or MD5 signature algorithm
  (`ssl/t1_lib.c` `sigalg_security_bits` counts SHA-1 as 64 bits and MD5 as 39, checked against 112 with
  `SSL_SECOP_SIGALG_CHECK`).

**Tests that pin it.** C `verify_peer_chain_security_level`, `identity_security_level` (MD5- and SHA-1-signed own leaf,
a SHA-1-signed intermediate and a self-issued MD5 leaf refused as identities, also for a client; a SHA-1 self-signed root
at the end of the configured chain accepted), `verify_built_path_level`, `tcp_weak_chain_refused_before_the_pause`;
`ChainSecurityLevelTest` (`negative_identitySignedWithSha1OrMd5IsRefused` and the RFC 9846 §4.5.1.3 row's cases),
`PlatformBuiltPathJvmTest`, `AppleBuiltPathTest`.

## <a id="s7-5-revocation"></a>§7.5 — certificate revocation

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** "TLS implementations MUST implement a strategy to distrust revoked certificates." "For the common use cases
of public key certificates in TLS, servers SHOULD support the following as a best practice given the current state of the
art and as a foundation for a possible future solution: OCSP [RFC6960] and OCSP stapling using the status_request extension
defined in [RFC6066]."

**Recorded status.** ⬜ not scheduled until 0.3.0 (only the platform verifiers checked revocation).

**How it is met.**

- Stapled OCSP (client): [`RevocationPolicy`](../../../kuicksilver-tls/src/commonMain/kotlin/io/kuicksilver/tls/Revocation.kt),
  default `StapledIfPresent`, checks the response a server staples by RFC 6960 §3.2 wherever `ksl` verifies the chain
  (`AnchoredCa`, `Platform` on Linux Native, inside `Pinned` and `ExpectedName`): revoked or unsatisfactory fails with
  bad_certificate_status_response (RFC 6066 §8). The default soft-fails a server that staples nothing, as §7.5 describes
  ("clients typically 'soft-fail'"; a server "can simply ignore the client's request"); `RequireStapled` hard-fails, and so
  does every policy but `Off` for a must-staple certificate (RFC 7633, which §7.5 cites). See the
  [RFC 6960 row](6960.md#ocsp-stapling).
- CRLs: `TrustConfig.AnchoredCa(roots, crls)` adds application CRLs to the verifier's store (`ksl_ctx_set_crls`); every
  certificate on the path whose issuer has a configured CRL is checked against it, on clients and for client certificates on
  servers (a `ReloadableCa` reload replaces them; tickets of the old CRLs resume nothing), and on resumption.
- Server: `TlsConfig.ocspStapling` (`OcspStapling`) staples a configured response over TCP and QUIC, only when it is for
  the leaf sent and fresh — the SHOULD; an identity chosen by `sniSelector` staples the response of its own
  `ServerTlsOverride`.
- `TrustConfig.Platform` off Linux Native: the OS verifier decides. Apple `SecTrust` and Windows `CertGetCertificateChain`
  apply their own revocation policy; on Android the default trust manager checks only its built-in blocklist, and the JDK
  checks revocation only when the application enables it, so there nothing checks revocation under `Platform` unless the
  application turns it on or uses `AnchoredCa`. `Custom` and `Tofu`: the application's verifier decides (it may suspend for
  OCSP).

**Tests that pin it.** C `revocation_ocsp_check`, `revocation_stapling`, `revocation_crls`; `RevocationTest`.

**Open items.** None. Not offered (not required by §7.5): OCSP requests sent by the client itself, OCSP for intermediates,
CRL fetching from distribution points.
