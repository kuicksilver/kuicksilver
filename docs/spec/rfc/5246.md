## <a id="tls-1-2-tcp-explicit-only"></a>(obsoleted by RFC 9846; TLS 1.2 itself stays as written there) — TLS 1.2 (TCP only; the Ktor client's default, opt-in elsewhere)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 5246 (obsoleted by RFC 9846; TLS 1.2 itself stays as written there). The anchor keeps its old name
(`tls-1-2-tcp-explicit-only`, from when TLS 1.2 was opt-in everywhere) so that the links to it stay valid; the title says
what holds since 0.3.0.

**Requirement.** TLS 1.2 (TCP only; the Ktor client's default, opt-in elsewhere).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- key exchange per RFC 10015 (ECDHE only)
- the Ktor server's connectors offer it since 0.3.0 with `versions = TlsVersions.Tls12And13` (EngineMain
  `kuicksilver.tls.versions`, Ktor's `enabledProtocols`); see [RFC 9325 §3.1.1](9325.md#s3-1-1-tls-1-2)
- over TCP only, with `TlsVersions.Tls12And13`: the default of the Ktor client's `tls { versions }` since 0.3.0, explicit
  for a `TlsConfig` and the Ktor server; only with EMS (RFC 7627 §5.2: an endpoint that does not interoperate with legacy peers SHOULD abort the handshake, and ksl's refusal is that local policy; the extension is named `extended_main_secret` by RFC 9846 App. D, which leaves RFC 7627's rules in place; RFC 9325 §3.5: TLS 1.2 implementations MUST support it)
- RFC 9325 §4.4 (SHOULD, RECOMMENDED limit 2^24.5 records for AES-GCM): with no KeyUpdate and no renegotiation a connection ends before its keys reach the AEAD's limit (2^24.5 records for AES-GCM, none for ChaCha20-Poly1305), with internal_error where an alert can be sent (a client) — C `tcp_record_limits_per_cipher`

- Resuming a TLS 1.2 session while offering TLS 1.3: a client whose cached session is TLS 1.2 offers it with both versions
  in `supported_versions`, as OpenSSL does. RFC 9846 App. E.1 says a client "using a ticket for resumption SHOULD initiate
  the connection using the version that was previously negotiated"; RFC 9325 §3.1.1 says implementations "MUST prefer to
  negotiate TLS 1.3 over earlier versions of TLS". The MUST is kept over the SHOULD: a server that gained TLS 1.3 since gets
  it (a full TLS 1.3 handshake, the 1.2 ticket ignored), one still at TLS 1.2 resumes (`ClientTls12KslServerTest.tls12SessionIsResumedOnTheEnginesNextConnection`),
  and capping the offer at 1.2 would let a stale ticket keep a connection on TLS 1.2 against a server that has 1.3.

**Tests that pin it.**

- rejected for QUIC when the configuration is built (`TlsConfigTest.quicRequiresTls13Only`)
- `ServerTls12Test`, `ServerTls12JdkClientTest` (the Ktor server's connectors, 0.3.0)
- `ClientTls12JdkServerTest`, `ClientTls12DowngradeTest`, `ClientTls12KslServerTest` (a raw `ksl` server capped at TLS 1.2,
  JVM and Kotlin/Native: HTTP/1.1, HTTP/2, pins, resumption, a server without EMS), `H2InteropTest.tls12ServerGetsH2` (the
  Ktor client's default, 0.3.0)
- C `tcp_tls12_profile_and_ems` (a TLS 1.2 peer without EMS is refused with `KSL_E_EMS_REQUIRED` and `handshake_failure` from either side), `TlsConnectionTest.tls12And13PeersNegotiateTls13`

**History.**

- 0.3.0: the Ktor client offers TLS 1.2 next to 1.3 over TCP by default (`tls { versions = TlsVersions.Tls12And13 }`; it was
  `Tls13`); a connection of it that offers ECH stays TLS 1.3 only
- 0.2.1: a peer without EMS is refused before Finished with `handshake_failure` (§7.2.2; the server when the ClientHello lacks it, the client when the ServerHello does), where it used to be dropped after the handshake without an alert
