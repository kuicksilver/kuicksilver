# RFC 7633 — X.509v3 Transport Layer Security (TLS) Feature Extension

Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="tls-feature"></a>TLS feature extension (must-staple)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** §4.3.3: "A client MUST treat a certificate with a TLS feature extension as an invalid certificate if the
features offered by the server do not contain all features present in both the client's ClientHello message and the TLS
feature extension. In the case that use of TLS with a valid certificate is mandated by explicit security policy,
application protocol specification, or other means, the client MUST refuse the connection." §4.2.3.1: "In the case that a
client determines that the server configuration is inconsistent with a feature declaration specifying support for the TLS
status_request extension, it SHOULD reject the TLS configuration." (Text checked against rfc7633.txt.) The only feature
in use is `status_request` (5), "must-staple".

**Recorded status.** ✅ 0.3.0

**How it is met.**

- every client whose `TlsConfig.revocation` is not `RevocationPolicy.Off` sends `status_request` (RFC 6066 §8) on every trust
  path, so the MUST of §4.3.3 applies to every handshake with a must-staple leaf; the leaf's TLS feature extension is read
  by `ksl_ocsp.c` `must_staple`
- a must-staple leaf without a good stapled response (none, "unknown", or one without an issuer to check it against) fails
  with `VerifyReason.UnknownRevocationStatus` and alert 113 (bad_certificate_status_response); a response that is revoked
  or not satisfactory fails as any staple does ([RFC 6960](6960.md#ocsp-stapling))
- on every trust path: where `ksl` verifies the chain (`AnchoredCa`, `Platform` on Linux Native, inside `Pinned` and
  `ExpectedName`) the staple is checked against the issuer that verifier trusted; where the platform's verifier
  (`Platform` on the JVM, Android, Apple and Windows) or the application's (`Custom`, `Tofu`) decides trust, after its yes,
  against the issuer of the path that verifier accepted, else the presented certificate whose key signed the leaf
  (`ksl_ocsp.c` `issuer_among`: a certificate that only copies the issuer's name and key identifier, or carries the
  leaf's own key, is never used). Before 0.3.0 only the
  first held (the Go, OpenSSL and BoringSSL clients have no must-staple support at all; the RFC binds a client that
  supports the extension, and Kuicksilver does)
- a connection is never accepted with the certificate treated as invalid: the MAY of §4.2.3.1 to accept an inconsistent
  configuration (a client that obtains the status another way, or that would otherwise send in clear) is not used; the
  only way out is `RevocationPolicy.Off`, which sends no `status_request` (so the ClientHello has no feature in common
  with the certificate) and checks nothing
- a resumed session presents no certificate: it resumes only while the response its full handshake checked is fresh

**Tests that pin it.**

- C `revocation_stapling` (`negative_must_staple`, `negative_must_staple_without_issuer`, `negative_paused_must_staple`,
  `negative_paused_must_staple_without_issuer`, `negative_paused_impostor_issuer`, `negative_paused_impostor_before_the_issuer`,
  `negative_paused_impostor_candidate`), C `revocation_issuer_among`, `RevocationTest.negative_quicMustStapleLeafWithoutStaple`,
  `.negative_mustStapleEnforcedOnEveryTrustPath`, `.mustStapleLeafWithItsStaplePassesOnEveryTrustPath`,
  `.verifiersIssuerIsHandedToTheStapleCheck`, `.negative_verifiersIssuerIsWhatTheStapleIsCheckedAgainst`, `RealTrustManagerStapleJvmTest.negative_mustStapleLeafWithoutStapleFailsUnderTheJdkTrustManager`
  (the JDK's PKIX trust manager as the verifier)

**Peer notes.** A server that holds a must-staple certificate and does not staple fails on every path, which is what the
extension asks for; such certificates are rare.

**Open items.** None.
