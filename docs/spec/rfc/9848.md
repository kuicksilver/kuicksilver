## <a id="ech-https-records"></a>The `ech` parameter of HTTPS records

Status: ✅ met since 0.3.0 (experimental API) · [summary](../rfc-compliance.md#http)

Original row: RFC 9848.

**Requirement.** The `ech` SvcParam of SVCB and HTTPS records carries the server's ECH configuration list, and a client
that uses it follows the rules of the RFC for its connections (including the SVCB-reliant behaviour).

**Recorded status.** ✅ met by the Ktor client for HTTPS records, over QUIC and TLS over TCP (owner decision of 2026-11-18,
[ADR-0019](../../adr/0019-openssl-4-and-ech.md)). The client looks HTTPS records up in `Http3DiscoveryMode.Auto` with
`http3.httpsRecords` set ([RFC 9460](9460.md)); in the other modes, and through a proxy (RFC 9460 section 3.2), it does no
SVCB resolution, so the sections below apply where it does.

**How it is met.**

- `kuicksilver-ktor-client`: `SvcbCodec` reads key 5 into `SvcbRecord.ech` after checking its framing;
  `serviceEndpoints(ech = true)` hands each endpoint its record's value; `HttpsResolution.Endpoints.echReliant`; the engine
  (`KuicksilverEngine.autoWithRecords`, `awaitResolutions`) gives each endpoint an `EchRoute` that its QUIC and TCP sides
  share, and `EchClientConfig.fromHttpsRecords` (default on) turns it on.

**Peers.** None of the local peer sources (quic-go, quiche, ngtcp2, msquic, quinn) reads the `ech` SvcParam: their
libraries take no HTTPS records. ngtcp2's example client takes an ECHConfigList from a file and, after an `ech_required`
failure, writes the retry configurations back to that file for the next run (`examples/client.cc` lines 860-869 and the
`--ech-config-list-file` help at 2156-2162): the application's retry, as here with `ech.configLists`.

**Open items.**

- None. The DNS queries themselves are not hidden by ECH (section 8): protect them with an `Exchange(secure = true)`
  source (DNS over HTTPS), which also makes a failed resolution abandon the request (RFC 9460 section 3.1).
