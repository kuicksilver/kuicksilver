## <a id="hystart"></a>HyStart++ in CUBIC's initial slow start

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: none until 0.3.0 (HyStart++ was described in the [RFC 9438](9438.md#cubic) row only).

**Requirement.** RFC 9438 §4.10: "CUBIC SHOULD use the HyStart++ slow start algorithm [RFC9406]". RFC 9406 §4.2 (rounds measured by the ACK of a packet sent after the round began; per ACK `cwnd = cwnd + min(N, L * SMSS)`; the delay-increase check once a round has `N_RTT_SAMPLE` samples; Conservative Slow Start with `cssBaselineMinRtt`, growth divided by `CSS_GROWTH_DIVISOR`, at most `CSS_ROUNDS` rounds counting the partial one, back to slow start when a round's minimum drops below the baseline); §4.3: the RECOMMENDED constants, "The minimum value of CSS_GROWTH_DIVISOR MUST be at least 2", "A paced TCP implementation SHOULD use L = infinity", "implementations of HyStart++ are RECOMMENDED to take at least N_RTT_SAMPLE RTT samples", and "An implementation SHOULD use HyStart++ only for the initial slow start (when the ssthresh is at its initial value of arbitrarily high per [RFC5681]) and fall back to using standard slow start for the remainder of the connection lifetime. ... An implementation MAY use HyStart++ to grow the restart window [RFC5681] after a long idle period."

**Recorded status.** ✅ 0.2.0 (the algorithm); ✅ 0.3.0 (the initial slow start only)

**How it is met.**

- `Cubic` (the default controller; `Cubic(hystart = false)` turns HyStart++ off): every RTT sample of an ACK in slow start is consumed with that ACK (`CongestionController.onRttSample`); a round ends with the ACK of a packet sent after it began, and its minimum becomes `lastRoundMinRTT`
- the constants are the RECOMMENDED ones: `MIN_RTT_THRESH` 4 ms, `MAX_RTT_THRESH` 16 ms, `MIN_RTT_DIVISOR` 8, `N_RTT_SAMPLE` 8, `CSS_GROWTH_DIVISOR` 4, `CSS_ROUNDS` 5; every sender is paced (RFC 9002 §7.7), so L is infinite: slow start adds every newly acknowledged byte, CSS a quarter of it
- the check runs on every ACK of a round from its 8th sample on; `RttThresh = max(4 ms, min(lastRoundMinRTT / 8, 16 ms))`; entering CSS takes the round's own minimum as `cssBaselineMinRtt`; a CSS round whose minimum falls below it resumes slow start; the fifth CSS round (the partial one CSS began in counts) ends slow start with ssthresh = cwnd (and, RFC 9438 §4.10, cwnd_prior = cwnd)
- loss or an ECN-CE mark in slow start or CSS is CUBIC's congestion event (RFC 9438 §4.6): ssthresh and cwnd go to β·cwnd, which ends slow start; §4.2's "enter congestion avoidance by setting the ssthresh to the current cwnd" names the exit, the multiplicative decrease is the controller's
- §4.3 SHOULD: HyStart++ runs only while ssthresh is still infinite (`Cubic.inHystart`); every congestion event sets a finite ssthresh, so the slow start after persistent congestion (RFC 9002 §7.6.2: the window back to 2 datagrams) is standard slow start up to the ssthresh the loss set, and the HyStart++ round state of the initial slow start is never used again
- the MAY (HyStart++ for the restart window after idle) is not taken: CUBIC keeps its window across idle periods and has no restart window
- NewReno (RFC 9002 appendix B) and BBR (its own Startup) do not use HyStart++

**Tests that pin it.**

- `recovery.CubicTest.hystartEntersCssOnRttIncrease`, `.hystartExitsAfterFiveCssRounds`, `.hystartBackToSlowStartWhenRttDrops`, `.hystartCssBaselineIsTheRoundThatEnteredIt`, `.hystartEverySampleOfARoundCounts`, `.hystartOnlyInTheInitialSlowStart`
- `testing.CubicScenarioTest.noHystartInTheSlowStartAfterPersistentCongestion`: a 50 Mbit/s, 40 ms simulated bottleneck under virtual time, a 6 s blackhole into persistent congestion, then a rising delay; three seeds

**History.**

- 0.3.0 cross-review: HyStart++ ran in every slow start with the round state of the initial one; after persistent congestion a rising RTT entered CSS and ended slow start far below the ssthresh the loss had set (290 542 → 88 800 bytes in the scenario above). ngtcp2 does the same (`ngtcp2_cc.c`)

**Peer interop notes.**

- none: the slow start algorithm is the sender's own choice
