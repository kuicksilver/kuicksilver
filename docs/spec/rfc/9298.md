# RFC 9298 — Proxying UDP in HTTP (CONNECT-UDP)

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

Both sides are in `kuicksilver-http3`, over HTTP/3 only ([ADR-0024](../../adr/0024-connect-udp-over-http3.md)): the client is
`Http3Connection.connectUdp` and its `UdpTunnel`, the proxy `UdpProxy` (`ConnectUdp.kt`; the runtime in `connectudp/`,
the sans-IO template, host syntax and address classes in `message/UdpUriTemplate.kt`, `message/UdpHost.kt`,
`message/UdpAddressClass.kt`). The tests are in `kuicksilver-http3/src/commonTest/.../connectudp/` and
`message/UdpUriTemplateTest.kt`, `message/DatagramFilterParserTest.kt`, plus `RealUdpConnectUdpTest` (JVM, real UDP on
loopback) and the Jazzer targets `ConnectUdpFuzzTest.udpTemplate` and `.udpDatagrams`.

Peers, from their sources: quic-go's MASQUE library (masque-go) is not among the local reference clones; picoquic's
`picomask` (`picohttp/picomask.c`) and quiche's tokio-quiche (`tokio-quiche/src/http3/driver/datagram.rs`,
`tokio-quiche/src/socket/connected.rs`) are, and are cited below.

## <a id="s2-uri-template"></a>§2, §3 — the URI Template and the target variables

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §2: a client is configured with a URI Template with the variables `target_host` and `target_port`; the
template "MUST be a level 3 template or lower", "MUST be in absolute form and MUST include non-empty scheme, authority, and
path components", its path "MUST start with a slash", "All template variables MUST be within the path or query
components", it "MUST contain the two variables", "MUST only contain ASCII characters in the range 0x21-0x7E inclusive" (percent-encoding allowed) and "MUST NOT
use Reserved Expansion ("+" operator), Fragment Expansion ("#" operator), Label Expansion with Dot-Prefix, Path Segment
Expansion with Slash-Prefix, nor Path-Style Parameter Expansion with Semicolon-Prefix"; "Clients SHOULD validate the
requirements above", and a client that finds one broken "MUST reject its configuration and abort the request without
sending it to the UDP proxy". Deployments "SHOULD offer service" at the default template `/.well-known/masque/udp/{target_host}/{target_port}/`
for clients that know only the proxy's host and port. §3: `target_host` is an IPv6address, IPv4address or reg-name (no
zone identifiers), both variables "MUST NOT be empty", the colons of an IPv6 literal "MUST be percent-encoded", and
`target_port` "MUST represent an integer between 1 and 65535 inclusive".

**How it is met.**

- `UdpProxyTemplate.parse` (client) checks every requirement above and throws `IllegalArgumentException` naming the rule;
  on top it refuses a userinfo in the authority (RFC 9114 §4.3.1 forbids sending one) and a fragment. `expand` is RFC 6570
  expansion with the unreserved set, so `2001:db8::42` comes out as `2001%3Adb8%3A%3A42`; an IPv6 literal may be given with
  or without brackets, a zone (`%`) is refused, the port must be 1..65535, a host must be an IP literal or a DNS host name.
  `connectUdp` checks the target before a stream is opened.
- `UdpProxyTemplate.wellKnown(authority)` is the default template; `UdpProxyConfig.pathTemplate` defaults to its path, so a
  proxy serves there unless configured otherwise.
- The proxy (`UdpUriTemplate.match`) reads the target from `:path` in one pass. A path of another shape is answered 404; a
  value that breaks §3 (empty, a port outside 1..65535 or not a number, not percent-encoded as the expansion would have
  it, unencoded colons, a zone identifier, brackets, a decoded byte outside ASCII 0x21-0x7E) is answered 400. A reg-name
  must be a DNS host name whose last label is not all digits (RFC 3696 §2), so `127.1` or `0x7f.1`, which some resolvers
  read as numbers, never reach one. A server's own template must be one a request can be read back from without
  guessing (each variable once, a simple expression with one variable, after an expression the end, a `{&...}` or a
  literal no value can contain); `UdpProxyConfig` refuses others.

**Tests that pin it.** `message.UdpUriTemplateTest.rfcExamplesExpand`, `.ipv6TargetIsPercentEncodedWithoutBrackets`,
`.negative_templatesBreakingSection2AreRejected`, `.negative_invalidTargetsAreRejectedByTheClient`,
`.negative_invalidTargetValuesAreInvalidNotMatched`, `.negative_ambiguousServerTemplatesAreRejected`,
`.expandThenMatchRoundTrips`, `.hostSyntax`; `connectudp.ConnectUdpTest.negative_invalidTargetValuesAndPathsAreRefused`,
`.negative_clientRefusesBeforeSending`; the Jazzer target `ConnectUdpFuzzTest.udpTemplate`.

**Notes on peers.** picoquic expands templates with its own RFC 6570 subset and percent-encodes everything outside the
unreserved set (`picohttp/h3zero_url_template.c:144-188`), its proxy reads the target from fixed query parameters `h` and
`p` only and does not resolve names (`picohttp/picomask.c:268-304`).

## <a id="s3-1-udp-proxy-handling"></a>§3.1 — UDP proxy handling

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** The proxy decodes the variables and opens a UDP socket to the target. "if the "target_host" is a DNS name,
the UDP proxy MUST perform DNS resolution before replying to the HTTP request. If errors occur during this process, the
UDP proxy MUST reject the request and SHOULD send details using an appropriate Proxy-Status header field". A proxy on a
non-connected socket "MUST validate the IP source address and UDP source port on received packets"; "Packets that do not
match MUST be discarded". "The UDP proxy MUST keep the socket open while the request stream is open"; one notified "that
its socket is no longer usable ... MUST close the request stream"; one that closes idle sockets "MUST close the request
stream when closing the socket" and "SHOULD NOT use a period lower than two minutes". A successful response "indicates
that the UDP proxy has opened a socket to the requested target". "UDP proxies MUST NOT introduce fragmentation at the IP
layer when forwarding HTTP Datagrams onto a UDP socket; overly large datagrams are silently dropped. In IPv4, the Don't
Fragment (DF) bit MUST be set, if possible, to prevent fragmentation on the path."

**How it is met.**

- A DNS name is resolved by `UdpProxyConfig.resolver` before the answer, bounded by `resolveTimeout`: a failure or no
  address is 502 with `proxy-status: <proxyName>; error=dns_error`, a timeout 504 with `dns_timeout` (RFC 9209 §2.3).
- The socket is opened (`socketFactory`, on a wildcard address of the target's family) before the 200, so the 200 means an
  open socket; nothing is sent to the target before the 200 (the forwarding starts after `acceptConnect` returned).
- No fragmentation, ✅ strict: a payload above what the proxy's link carries (`linkMtu` less 28 bytes for IPv4, 48 for
  IPv6) is dropped silently, and every target socket has DF for the target's family, or there is no tunnel. "MUST NOT
  introduce fragmentation at the IP layer" has no qualifier; only the DF bit is "if possible", and a socket without DF
  could fragment locally once an ICMP message lowered the path MTU its kernel caches, so the proxy does not use one (owner
  decision, as "no DF, no QUIC" for its own endpoint). The default `socketFactory` is `DatagramIo.open`: DF in probe mode
  (the accelerated socket on Linux, Android and Windows: `IP_MTU_DISCOVER` = `IP_PMTUDISC_PROBE`, `IPV6_DONTFRAG`,
  `IP_DONTFRAGMENT`; the portable socket through `ksl` on the JVM and `android.system.Os` on Android), else DO mode (a half
  that refuses probe mode; Apple's `IP_DONTFRAG` / `IPV6_DONTFRAG`; the JDK's `IP_DONTFRAGMENT`), so the kernel never
  fragments. Where that is impossible for the target's family (the factory throws `QuicException.DontFragmentUnavailable`:
  the JVM without `ksl` below JDK 19, the Kotlin/Native portable ktor-network socket, a system refusing both modes; or the
  socket's `noDontFragmentFamily` is that family) the request is refused with 500 and `proxy-status: <proxyName>;
  error=proxy_configuration_error; details="no Don't Fragment for <family> targets on this host"` (RFC 9209 §2.3.24:
  "The intermediary encountered an error regarding its configuration", recommended status 500), and targets of the other
  family are still served — `connectudp.ConnectUdpTest.negative_aTargetFamilyWithoutDontFragmentIsRefused`,
  `.negative_aSocketFactoryWithoutDontFragmentRefusesTheTunnel`, `connectudp.PortableTruncationTest` (the JVM portable
  socket, with DF; skipped on Kotlin/Native, whose portable socket cannot set DF). `linkMtu` must still be the smallest MTU
  on the way to the targets for datagrams to arrive beyond the first hop: DF makes a larger one dropped, never fragmented.
- No cut payload: a datagram from a target above `linkMtu` bytes is dropped whole (`droppedTooLargeFromTarget`): the
  receive slot is one byte longer than the link carries, since a portable socket truncates a datagram to its buffer and
  §5 carries "the unmodified payload".
- The socket is not connected: every received datagram's address and port are compared with the target's
  (`InetSocketAddress.sameIpAs`) and others dropped (`UdpProxyStats.droppedForeignSource`).
- An ICMP port unreachable for the tunnel's target is the operating system saying the socket "is no longer usable": the
  accelerated socket on Linux and Android, which reads the error queue (`IP_RECVERR` with DF), reports it with its kind
  and the start of the payload it quotes (`ksl_udp_take_unreachable`, a ring of 8), and the tunnel is closed (reset and
  STOP_SENDING `H3_CONNECT_ERROR`, `UdpProxyStats.closedUnreachable`), looked for every second. ICMP can be forged by
  anyone who guesses the proxy socket's port, so a report is first checked as RFC 8085 section 5.2 asks: it must be for
  the target's address and port and quote the start of one of the 16 payloads the tunnel sent last, 8 bytes of it at
  least (all of it when it is shorter), so a guessed byte or two does not pass. A host (ICMPv6
  address) unreachable, often transient, is not acted on, nor is a report that quotes the headers only (a router's
  8-byte quote) or a payload the tunnel did not send; these are counted in `ignoredUnreachable`. Apple platforms, Windows
  and the portable sockets are told nothing of an ICMP error on an unconnected socket, so there the tunnel ends by the
  other ways below.
- The socket and the stream end together: on the client's FIN the proxy closes the socket and ends its side (FIN); on the
  client's reset or a lost connection it closes the socket and resets; a failing socket (`receive` or `send` throws) resets
  and stops the stream with `H3_CONNECT_ERROR`; after `idleTimeout` (two minutes by default, `UdpProxyConfig` refuses less)
  without a datagram either way it closes the socket, sends FIN and STOP_SENDING `H3_NO_ERROR`. A cancelled `serve` resets
  the stream with `H3_CONNECT_ERROR` (before the answer, `H3_REQUEST_CANCELLED`).

## <a id="s3-4-http3-requests-and-responses"></a>§3.4, §3.5 — HTTP/3 requests and responses

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Over HTTP/3 (§3.4, which covers HTTP/2 too; see the next section) a UDP proxying request is an Extended CONNECT (RFC 9220, which needs
`SETTINGS_ENABLE_CONNECT_PROTOCOL`): `:method` CONNECT, `:protocol` `connect-udp`, `:authority` the proxy's, `:scheme` and
`:path` not empty and taken from the expanded template; one that breaks this is malformed (RFC 9114 §4.1.2). The proxy
SHALL reply with a status code "in the 2xx (Successful) range", and the response "SHALL meet the requirements of HTTP
responses that start the Capsule Protocol" (RFC 9297 §3.2); "If any of these requirements are not met, the client MUST
treat this proxying attempt as failed and abort the request" (§3.5), as for "Any response other than a successful
response" (§3.1). Neither request nor response carries content (§3). The tunnel uses the Capsule Protocol (RFC 9297 §3.2: no content, no `content-length`); RFC 9114 §4.4:
after the 2xx only DATA frames travel on the stream.

**How it is met.**

- The client sends `:method` CONNECT, `:protocol` `connect-udp`, the template's `:scheme`, `:authority` and expanded
  `:path`, and `capsule-protocol: ?1` as the RFC's examples do; Extended CONNECT waits for the server's SETTINGS
  (`Http3Exception.Settings` without `SETTINGS_ENABLE_CONNECT_PROTOCOL`). A non-2xx fails `connectUdp` with
  `Http3Exception.ConnectRejected` (status and fields, `proxy-status` among them) and the stream is not used.
- The proxy answers 200 with `capsule-protocol: ?1` and no content; a request whose `:protocol` is another token is
  refused with 400; without `capsule-protocol: ?1` it is refused with 400 unless `requireCapsuleProtocolField` is false
  (the RFC shows the field in its examples but does not require it; this is our default, as the brief of a MASQUE proxy
  is to talk to clients that send it). The Capsule Protocol's own checks (RFC 9297 §3.2: content fields, 204/205/206) are
  `acceptConnect`'s and `useCapsuleProtocol`'s. The data stream carries capsules only; DATA frames only (RFC 9114 §4.4) as
  for every Extended CONNECT.

**Tests that pin it.** `connectudp.ConnectUdpTest.tunnelCarriesPayloadsBothWays`,
`.negative_missingCapsuleProtocolFieldIsRefused`, `.capsuleProtocolFieldNotRequiredWhenConfigured`,
`.negative_otherProtocolIsRefused`, `.negative_dnsFailureAndTimeoutAreRefusedWithProxyStatus` (a refusal reaches the client
as `ConnectRejected` with its `proxy-status`), `.negative_forbiddenTargetsAreRefusedByDefault`.

## <a id="s3-2-http1-and-http2"></a>§3.2, §3.3; §3.4, §3.5 over HTTP/2 — HTTP/1.1 and HTTP/2

Status: ❌ · [summary](../rfc-compliance.md#http)

**Requirement.** §3.2 and §3.3: over HTTP/1.1 a UDP proxying request is a GET with `Connection: Upgrade` and `Upgrade:
connect-udp` ("A UDP proxying request that does not conform to these restrictions is malformed. The recipient of such a
malformed request MUST respond with an error and SHOULD use the 400 (Bad Request) status code"), answered with 101. §3.4
and §3.5 cover HTTP/2 together with HTTP/3: an Extended CONNECT (RFC 8441), answered with a 2xx.

**Not planned.** The Capsule Protocol is implemented on HTTP/3 only (RFC 9297 row), and §6 says "UDP proxying SHOULD be
performed over HTTP/3 to allow leveraging the QUIC DATAGRAM frame": over TCP every datagram is a capsule behind
head-of-line blocking, and the proxied QUIC inside would run two loss recoveries. Neither the client nor the proxy offers
CONNECT-UDP on HTTP/1.1 or HTTP/2 ([ADR-0024](../../adr/0024-connect-udp-over-http3.md)): an HTTP/1.1 `Upgrade:
connect-udp` reaches the application as an ordinary GET, and the Ktor server engine answers an HTTP/2 Extended CONNECT
with `:protocol` `connect-udp` with 501, as every protocol it does not serve (`Http2Serving.kt`). Nothing in RFC 9298 requires every
version.

## <a id="s4-context-ids-and-payload"></a>§4, §5 — Context IDs and the HTTP Datagram payload

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §5: every HTTP datagram of the tunnel starts with a Context ID varint; Context ID 0 carries "the
unmodified payload of a UDP packet", which may be empty. "endpoints MUST NOT send HTTP Datagrams with a UDP Proxying
Payload field longer than 65527 using Context ID zero", and "An endpoint that receives an HTTP Datagram using Context ID
zero whose UDP Proxying Payload field is longer than 65527 MUST abort the corresponding stream". A proxy that can only send
payloads of a certain length because of its link MTU "has no choice but to discard" longer ones, and "If the discarded HTTP
Datagram was transported by a DATAGRAM capsule, the receiver SHOULD discard that capsule without buffering the capsule
contents". §4 and §5: a datagram with an unknown Context ID "SHALL" be dropped silently or buffered for about a round
trip; buffering "SHOULD" be limited. The DATAGRAM capsule (RFC 9297 §3.5) carries datagrams when HTTP/3 datagrams are not
negotiated.

**How it is met.**

- Both sides send UDP payloads as Context ID 0 (`udpDatagram`); `UdpTunnel.trySend`/`send` refuse more than 65527 bytes
  with `IllegalArgumentException`.
- Every HTTP datagram is judged by its Context ID before it is delivered (`DatagramFilter`): on a QUIC datagram at once, in
  a DATAGRAM capsule as soon as the Context ID varint is in, before the rest of the value is buffered (`CapsuleParser`'s
  filter). Context ID 0 with more than 65527 bytes aborts the stream (RESET_STREAM and STOP_SENDING `H3_DATAGRAM_ERROR`)
  whatever the capsule's length; any other Context ID is dropped, nothing being registered (no extension is implemented),
  without buffering; a datagram too short for a Context ID is dropped. The proxy drops payloads above its link's
  (`linkMtu` 1500 by default, less 28 for IPv4 and 48 for IPv6) the same way, a capsule without buffering it.
- Datagrams of a request that arrive before the proxy accepted it are held as for any request (32 per stream, about a
  round trip; RFC 9297 row); unknown Context IDs are never buffered.
- With HTTP/3 datagrams off on either side, both sides send DATAGRAM capsules (`CapsuleConfig.datagramFallback`).

`.eightByteContextIdIsRead`, `.negative_unknownContextSkippedWithoutBuffering`,
`.negative_oversizedContextZeroAbortsBeforeItsBytesArrive`, `.skippedByTheFilterIsNotBuffered`,
`.negative_emptyOrTruncatedContextIdIsDropped`; `connectudp.ConnectUdpTest.negative_oversizedUdpPayloadAbortsTheStream`,
`.negative_payloadAboveTheLinkMtuIsDropped`, `.negative_unknownContextIdIsDroppedByTheProxy`,
`.negative_unknownContextIdIsDroppedByTheClient`, `.datagramCapsulesWhenHttpDatagramsAreOff`,
`.tunnelCarriesPayloadsBothWays` (the empty payload); the Jazzer target `ConnectUdpFuzzTest.udpDatagrams`.

**Notes on peers.** picomask prefixes forwarded packets with the Quarter Stream ID and no Context ID

Context ID to the application.

## <a id="s6-performance-mtu-ecn"></a>§6 — performance, MTU and ECN

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §6: proxies "SHOULD NOT queue packets in order to increase batching"; the HTTP connection "MUST NOT
disable congestion control" without knowing the inner traffic is congestion-controlled. §6.1: a proxy using QUIC DATAGRAM
frames that receives a payload from the target too large for one "SHOULD NOT send the UDP payload in a DATAGRAM capsule"
and "SHOULD drop the UDP payload and send an ICMP Packet Too Big message to the target". §6.2: "A UDP proxy MUST ignore
ECN bits in the IP header of UDP packets received from the target, and it MUST set the ECN bits to Not-ECT on UDP packets
it sends to the target."

**How it is met.**

- Each datagram is forwarded as it arrives, in both directions, never held for a batch; congestion control is never
  turned off.
- A target payload too large for the client's QUIC DATAGRAM frames is dropped (`UdpProxyStats.droppedTooLargeForClient`),
  never sent as a capsule; with HTTP/3 datagrams not negotiated (no QUIC DATAGRAM frames in use) it goes as a capsule.
- The proxy's socket has ECN marking turned off (`DatagramIo.disableEcnMarking`) and every datagram it sends is marked
  Not-ECT; ECN marks received are not read.
- The client's `asDatagramIo` reports no ECN, so a QUIC connection inside never relies on marks the tunnel cannot carry.

**The Packet Too Big (§6.1), with the privilege.** §6.1: "In this scenario, the UDP proxy SHOULD drop the UDP payload
and send an ICMP Packet Too Big message to the target; see Section 3.2 of [ICMP6]". With `UdpProxyConfig.packetTooBig`
(true by default) the proxy probes once, at its first tunnel, whether it can open a raw ICMP socket
(`PacketTooBigSender.probe`, `ksl_icmp_open`), and says so in `UdpProxyStats.packetTooBig`. When it can (Linux and
Android with `CAP_NET_RAW`), each tunnel answers a dropped payload with the message (`ksl_icmp_ptb_build`,
`ksl_icmp_send`):

- IPv4: Destination Unreachable, code 4 (fragmentation needed and DF set, RFC 792) with the Next-Hop MTU (RFC 1191
  section 4); IPv6: Packet Too Big, type 2, with the MTU (RFC 4443 section 3.2). The MTU is the largest UDP payload the
  client's DATAGRAM frames carry now, plus the UDP and IP headers; an IPv6 MTU below 1280 is not sent (RFC 8200
  section 5 has receivers ignore it), nor one that is not below the datagram's own size. So an IPv6 target is never
  sent one while the client's datagram limit is below 1233 bytes (1280 less the 48 bytes of IPv6 and UDP headers, plus
  the one byte of the Context ID); its payload is dropped and counted only.
- The quote is the datagram as the target sent it: an IPv4 or IPv6 header and the UDP header rebuilt from what the proxy
  knows (the addresses and ports, the lengths, DF; the TTL or hop limit, identification and traffic class are not known
  and are 64 and 0), with valid checksums, then the payload: as much as keeps the IPv4 error within a 576-byte datagram
  (RFC 1812 section 4.3.2.3), the IPv6 one within 1280 bytes (RFC 4443 section 2.4 (c)). Checksums: ICMP over the
  message, ICMPv6 over the pseudo-header.
- It leaves from the proxy's address the target sent to (`IP_PKTINFO`, `IPV6_PKTINFO`): the destination the
  accelerated socket reports for each datagram it receives on a wildcard bind (the default `socketFactory`), else the
  socket's own address when it is bound to one address (a custom `socketFactory`; it takes only datagrams sent to that
  address; an IPv4-mapped one, `::ffff:a.b.c.d` on a dual-stack socket, as its IPv4 address, the target's family).
  A wildcard socket (all address bytes zero, in any spelling) that reports no destination (the portable socket) has no
  address to answer from: no message goes, and the drop is counted in `UdpProxyStats.packetTooBigNoSource`. A socket
  bound to one address can still be handed datagrams for others (TPROXY with `IP_TRANSPARENT`, a BPF `sk_lookup`
  program); its message then leaves from the bound address, and the target's kernel, matching it to a socket by the
  quoted addresses and ports, finds none and drops it: harmless, and such deployments bind the wildcard instead.
- A message the raw socket does not send (the family's socket did not open, the kernel refused it) is counted in
  `UdpProxyStats.packetTooBigFailed`; its rate-limit tokens stay spent.
- Rate (RFC 4443 section 2.4 (f)): a token bucket per target address, shared by every tunnel to it, of 5 messages
  refilled at 10 a second (the 4096 latest targets kept), and one over the whole proxy of 50 refilled at 100 a second;
  one message per dropped payload at most, so never more than the drops.
- One sender per proxy: one raw socket per family at most, opened at the first message and closed when the last tunnel
  ends; its use is serialised. Linux hands every ICMP message the host receives to each raw ICMP socket, so a socket per
  tunnel would multiply that work by the tunnels. The socket only sends: every ICMP type is filtered on receive
  (`ICMP_FILTER`, `ICMP6_FILTER`; a socket whose filter cannot be set is closed, not used), and it is non-blocking.

**Without the privilege** (`UdpProxyStats.packetTooBig` = `Unavailable`; also on Apple platforms and Windows, whose raw
sockets need root or administrator rights and are not offered, and with `packetTooBig = false`, `Off`): the payload is
dropped and counted in `droppedTooLargeForClient`, and no message is sent. The unprivileged ICMP sockets cannot carry it:
Linux and Android "ping" sockets (`SOCK_DGRAM`, `IPPROTO_ICMP`/`IPPROTO_ICMPV6`) send Echo Requests only, Darwin's
`SOCK_DGRAM` ICMP sockets Echo, Timestamp, Information and Address Mask requests only, Windows offers `IcmpSendEcho`
(these limits are from the kernels' documented behaviour). The target then learns the limit from the loss, through
DPLPMTUD (RFC 8899) or its own probing, which is what the SHOULD NOT about capsules protects.

tests' `icmp_linux_*` send IPv4 and IPv6 messages through `ksl_icmp_send` from the proxy's address, checked by a second
raw socket (type, code, MTU, checksum, quote, source) and taken by the target's error queue as a Packet Too Big; they
read the kernel's port unreachable for a closed port, and forged port and host unreachable messages, through
`ksl_udp_take_unreachable`. `LinuxIcmpCheckTest` runs the proxy over real UDP: the target's kernel takes the message of
a dropped payload, from a proxy socket bound to 127.0.0.1 and from one bound to the wildcard (the destination reported
per datagram, as the default `socketFactory` gets it), a real port unreachable closes the tunnel, a forged one quoting a payload never sent is ignored. A
macOS host cannot run these (no raw sockets to grant); they run where that script is run.

## <a id="s7-security-considerations"></a>§7 — security considerations

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §7: servers "ought to restrict its use to authenticated users"; unauthorized access follows "unless the
UDP proxy disallows UDP proxying requests to vulnerable targets, such as the UDP proxy's own addresses and localhost,
link-local, multicast, and broadcast addresses"; a proxy can be a tool of volumetric attacks, which a limit of packets
before the target answers mitigates in part. The considerations of RFC 9297 §4 apply.

**How it is met.**

- `UdpTargetFilter.PublicOnly`, the default, refuses every address that is not globally reachable unicast: loopback,
  unspecified, private and shared space, link-local, multicast, the limited broadcast address, 240.0.0.0/4, the
  documentation and benchmarking ranges and the other non-global blocks of the IANA special-purpose registries; for IPv6
  only 2000::/3 less its special blocks; an IPv4-mapped, NAT64 (64:ff9b::/96) or 6to4 address is judged by its IPv4
  address. The filter sees the resolved addresses and the socket sends to the one it allowed (no second resolution, so no
  DNS rebinding between check and use). Refusals are 403 with `destination_ip_prohibited`, before a socket exists.
  The proxy's own addresses are refused too (`refuseOwnAddresses`, on by default): the address the request's connection
  reached (the path's local address, which the accelerated socket reports on a wildcard bind) and the listener's when it
  is bound to one, compared by the IPv4 address an IPv4-mapped, NAT64 (`64:ff9b::/96`) or 6to4 (`2002::/16`) target
  carries. Other addresses of the host (NAT aliases, other interfaces), which the library does not list, go to
  `UdpTargetFilter.excluding`; `addresses`,
  `hosts`, `ports`, `and` and `or` build allow-lists; `AllowAll` is `@DelicateKuicksilverApi`.
- Floods (CWE-400): a token bucket per tunnel (`packetRate`, `packetBurst`) and one per client over all its tunnels
  (`clientPacketRate`, `clientPacketBurst`), a client being its IPv4 address or its IPv6 /64 (`clientIpv6Prefix`);
  `unansweredLimit` payloads a client may send to a target that has never answered (256 by default; 0 turns it off for
  one-way protocols), counted per client and target across its tunnels and kept two minutes after its last tunnel, so
  reopening does not start over; `maxTunnels` and `maxTunnelsPerClient` (503 and 429 with `connection_limit_reached`); a
  system resolver of 16 lookups at once and 4 per client (a lookup no deadline interrupts keeps its thread, and counts,
  until it returns; one more is answered 503), and bounded memory per tunnel (the parser holds at most one datagram of the link's
  size, 32 queued datagrams, a receive batch of four).
- Authentication is the application's: `serve` is called for requests it has admitted (the guide says so).
- The threat model's [§3.29](../threat-model.md#3-29-connect-udp-proxy-rfc-9298-7) has the threats and the controls.

**Tests that pin it.** `connectudp.UdpTargetFilterTest.negative_publicOnlyRefusesSpecialPurposeAddresses`,
`.publicOnlyAllowsGlobalUnicast`, `.prefixesHostsPortsAndCombinators`;
`connectudp.ConnectUdpTest.negative_forbiddenTargetsAreRefusedByDefault`, `.negative_rateLimitDropsBeyondTheBurst`,
`.negative_unansweredTargetIsNotFlooded`, `.negative_tunnelLimitsAreEnforced`, `.negative_theProxysOwnAddressIsRefused`,
`.negative_aClientsTunnelsShareOneRate`, `.negative_reopeningATunnelDoesNotResetTheUnansweredLimit`, `.clientKeys`,
`.negative_theSystemResolverBoundsItsBlockedLookups`, `.negative_oneClientCannotTakeEveryLookup`; `ClientConnectUdpProxyTest.negative_tunnelsDoNotShareTicketsWithDirectConnections`
(the Ktor client keeps a tunnel's session tickets apart from direct connections', so the origin cannot link them).

**Notes on peers.** picoquic refuses targets on a list of reflection-prone ports (`picoquic/port_blocking.c:109-128`,
called from `picohttp/picomask.c:288`); here no port is refused by default, since the proxy cannot spoof a source and a
reflected answer comes back to the proxy and the client itself, not to a third party; `UdpTargetFilter.ports` restricts
ports where a deployment wants it.

## <a id="client-tunnel-and-proxied-quic"></a>The client tunnel and proxied QUIC

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Not a requirement of the RFC: what a client does with a tunnel. MASQUE's use is QUIC and HTTP/3 to a target
through the proxy (§6 discusses its nested congestion control and loss recovery).

**How it is met.** `UdpTunnel` sends and receives UDP payloads (`trySend`, `send`, `payloads`); `asDatagramIo()` is a
`DatagramIo` over the tunnel for a QUIC endpoint (`QuicEndpointConfig.io`), so a `QuicEndpoint` or `Http3Endpoint`
connection runs through the proxy with TLS end to end. It reports the target's literal (or 192.0.2.1 for a DNS name, which
the client does not resolve) as the source of everything it receives, sends every datagram to the target, and has no ECN,
GSO or Don't Fragment, so the inner connection keeps to 1200-byte datagrams. The connection to the proxy must then carry
HTTP datagrams of 1200 bytes and their framing: a path MTU above about 1250, which DPLPMTUD finds on a socket that sets
Don't Fragment (the accelerated one); over a 1200-byte path the inner handshake times out.

**Tests that pin it.** `connectudp.ProxiedQuicTest.http3ThroughTheProxy`, `.tunnelSocketShape`;
`RealUdpConnectUdpTest.http3ThroughTheProxyOverRealUdp`, `.udpEchoThroughTheProxy`.

**Notes on peers.** tokio-quiche's `Socket` abstracts "real UDP-based connections and in-process tunneled flows like
(multi-hop) MASQUE flows" (`tokio-quiche/src/socket/connected.rs:36-41`); picomask raises the path MTU of the connection to
the proxy to at least 1300 bytes (`PICOMASK_MTU_MIN`, `picohttp/picomask.h:48`, applied at `picohttp/picomask.c:345-346`) for
the same reason as the 1250 here.

The Ktor engines use both sides: the client's `connectUdpProxy` runs each HTTP/3 connection to an origin it applies to
through a tunnel (`H3Pool.connectThroughUdpProxy`: a connection to the proxy, `connectUdp` to the origin's name, an endpoint
on `asDatagramIo`, the origin's TLS; never a fallback to TCP or a direct connection, no Alt-Svc), and the server's
`connectUdp(proxy)` route takes CONNECT-UDP requests through the pipeline, so authentication runs first
(`ConnectUdpRouting.kt`). Tests: `ClientConnectUdpProxyTest.http3ThroughTheProxy`,
`.negative_aRefusedTunnelNeverFallsBackToADirectConnection`, `ServerConnectUdpTest.tunnelThroughTheRoute`,
`.negative_aRefusalBeforeTheRouteGoesOutAsItIs`.

**Open items.** A connection to the proxy carries one tunnel: tunnels to several origins do not share one yet.
