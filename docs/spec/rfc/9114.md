# RFC 9114 — HTTP/3

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="http-3"></a>HTTP/3

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9114.

**Requirement.** HTTP/3.

**Recorded status.** ✅ 0.2.0 (by section below; server push is not implemented; the runner's interop case `http3` is green against every peer that supports it — section [Interop http3](../interop.md#interop-http3-quic-interop-runner-740c05a-2026-10-08); `curl --http3-only` against the Ktor server — the `ServerH3Test` sibling `CurlHttp3Test.curlDownloadsOverHttp3Only`)

**How it is met.**

- module `kuicksilver-http3`
- the Ktor engines on top of it pass the vendored Ktor 3.6.0 contract in h3 mode (client: 93 tests, server: `KuicksilverH3*` — 62 tests; `docs/guide/ktor.md`, "Compatibility")

## <a id="s7-1-frames"></a>§7.1, §7.2 — frames

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9114 §7.1, §7.2.

**Requirement.** Frames: header, types, reserved (GREASE) types are skipped, H2 types → `H3_FRAME_UNEXPECTED`, the length does not set the buffer size (review: the HEADERS payload is accumulated as it arrives rather than allocated from the declared length; 0.2.1 review: the HEADERS bound is at most `Int.MAX_VALUE`, so at `maxFieldSectionSize` = 2^30 a declared 2^31 is refused unread instead of overflowing).

**Recorded status.** ✅ 0.2.0

**Tests that pin it.**

- `runtime.LimitsTest.negative_headersDeclaredLengthNotPreallocated`, `runtime.RequestFramesTest.negative_headersLengthAboveIntRangeIsTooLarge`, `frame.FrameHeaderTest.parsesIncrementally`, `.negative_h3ReservedFrameHugeLength`, `frame.FrameRulesTest.h2FramesUnexpected`, `.greaseIsSkipped`, `.controlPayloadCap`, `frame.VarIntTest.*`

## <a id="s7-2-4-settings"></a>§7.2.4, §6.2.1 — SETTINGS

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9114 §7.2.4, §6.2.1.

**Requirement.** SETTINGS: first on the control stream, once (any other first frame → `H3_MISSING_SETTINGS`, the WebTransport `WT_STREAM` signal too — review: it gave `H3_FRAME_ERROR`. Two MUSTs meet there: RFC 9114 §6.2.1 "If the first frame of the control stream is any other frame type, this MUST be treated as a connection error of type H3_MISSING_SETTINGS", and draft-ietf-webtrans-http3-16 §4.3 "Receiving this frame type in any other circumstances MUST be treated as a connection error of type H3_FRAME_ERROR". We follow RFC 9114: it is the base protocol the draft extends, its rule applies to every frame type before the type is interpreted, so the code does not depend on whether WebTransport is enabled and is what a peer without WebTransport reports too, and it is a published RFC where the other is a draft; `WT_STREAM` later on the control stream is `H3_FRAME_ERROR` as the draft says).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- H2 settings, duplicates, booleans > 1 → `H3_SETTINGS_ERROR`

**Tests that pin it.**

- `frame.SettingsCodecTest.*`, `frame.FrameRulesTest.controlFirstMustBeSettings`, `.wtStreamFirstOnControlIsMissingSettings`, `.secondSettingsUnexpected`, `.dataOnControlUnexpected`, `.settingsOnRequestUnexpected`

## <a id="s4-1-request-response"></a>§4.1, §4.1.2 — request/response

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9114 §4.1, §4.1.2.

**Requirement.** Request/response on a bidirectional stream, body as DATA frames with the backpressure of ktor-io channels, trailers, 1xx and 103 (the client accepts any number, RFC 9110 §15.2 MUST, 0.2.1: their decoded field sections together hold at most `maxFieldSectionSize`, 64 KiB by default, past which the request fails with H3_EXCESSIVE_LOAD and its stream is reset — `runtime.RequestTest.manyInformationalResponsesAreAccepted`, `.negative_endlessInformationalIsExcessiveLoad`; until 0.2.1 at most 5), unknown frames are skipped in a streaming fashion.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- malformed (including a `content-length` mismatch; `content-length` must be `1*DIGIT` and fit in a Long (review: `PseudoHeadersTest.contentLengthOverflowIsMalformed`), several values are allowed only if identical and are collapsed into one for the application — RFC 9110 §8.6; a response to HEAD and a 2xx to CONNECT may carry `content-length` without a body; the server drops what the application writes to a HEAD, 204 or 304 response — review: `ServerH3Test.headAnd204And304SendNoData`) → stream error `H3_MESSAGE_ERROR`, the connection stays alive
- a request body the application has not finished reading by the end of the response is reset with `STOP_SENDING H3_NO_ERROR` (review: the signal goes out from `responseComplete()` directly; a stopped receive half retires in `kuicksilver-quic` as soon as its final size is known, and the `MAX_STREAMS` credit is returned — `stream.StreamStateTest.stoppedStreamRetiresOnceFinalSizeIsKnown`, `RequestTest.unreadBodiesDoNotExhaustStreamCredit`), and the body pump waits for the consumer (a buffer ≤ 1 MiB of the ktor-io channel) instead of accumulating the whole body in memory
- a rejected response field (or a failure to write the headers) resets the stream with `H3_INTERNAL_ERROR` rather than leaving it half-open (review)
- a request stream that ended (FIN) without a complete request between frames → `H3_REQUEST_INCOMPLETE`, a response stream that ended without HEADERS → `H3_MESSAGE_ERROR`, `Http3Exception.MessageError` (no `:status`, §4.1.2; review: it was `H3_REQUEST_INCOMPLETE`, a code for requests — `runtime.RequestTest.responseStreamEndingWithoutHeadersIsMessageError`)
- cancellation → `H3_REQUEST_CANCELLED`
- a message whose stream came whole (its FIN and every byte before it, RFC 9000 §3.2 "Data Recvd") before the connection closed is delivered whole however late it is read: RFC 9000 §10.2 lets open streams "be assumed to be implicitly reset" (a permission, not a requirement to discard), §3.2 lets a RESET_STREAM be withheld once the data is completely received, and §4.1 says "Clients MUST NOT discard complete responses as a result of having their request terminated abruptly"
- whether it came whole is settled when the transport is gone, and its reader then hands the rest over without waiting for the application, so the session ends

**Tests that pin it.**

- a FIN inside a frame → connection error `H3_FRAME_ERROR` (§7.1; review: `runtime.ConnectionTest.truncatedFrameAtFinIsFrameError`)
- a stream cut short gets the one-second drain grace (0.2.1 review: the grace cut whole bodies too, and a local close could leave an unread whole body holding the session — `runtime.ConnectionEndTest.wholeResponseReaderRunLateReadsWhole`, `.unreadWholeRequestBodyLetsTheSessionEnd`, `.unreadBodyWholeOnlyAfterALocalCloseLetsTheSessionEnd`, `.unreadBodyIsCutAfterTheGrace`)
- `runtime.RequestTest.*` (including `invalidOrConflictingContentLengthIsMessageError`, `headResponseWithContentLength`, `invalidResponseFieldResetsStream`, `unreadBodyIsStoppedAfterResponse`), `runtime.LimitsTest.negative_h3ReservedFrameHugeLength`, `runtime.RfcPinTest.*` (review pins: DATA before HEADERS and DATA or HEADERS after trailers → `H3_FRAME_UNEXPECTED` on both sides, FIN before HEADERS → `H3_REQUEST_INCOMPLETE`, a client's GOAWAY id ≢ 0 mod 4 and PRIORITY_UPDATE for a push → `H3_ID_ERROR`, a second QPACK encoder or decoder stream → `H3_STREAM_CREATION_ERROR`)

## <a id="s4-2-2-field-section-size"></a>§4.2.2; RFC 9204 §7.4 — field section size

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9114 §4.2.2; RFC 9204 §7.4.

**Requirement.** `SETTINGS_MAX_FIELD_SECTION_SIZE` 64 KiB by decoded size, including trailers → the server answers 431 and `STOP_SENDING H3_EXCESSIVE_LOAD`, the client — `Http3Exception.FieldSectionTooLarge` (a stream error, the connection lives).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- this holds for a single field too: the QPACK string ceiling in field sections is `maxFieldSectionSize` (review: it was a fixed 64 KiB, and one longer string closed the connection with `QPACK_DECOMPRESSION_FAILED`, also below a raised limit)
- HEADERS longer than 2 × the limit is rejected from the frame header without reading
- on the encoder stream the string ceiling is min(`qpackMaxTableCapacity`, `maxFieldSectionSize`), at least 64 KiB and at most 256 MiB, so an insert as large as the largest field we accept that fits the table is processed (§7.4 SHOULD; review: it was a fixed 64 KiB)
- an instruction cut by the transport waits whole for up to 4 × min(table capacity, 2 × that ceiling) + 64 bytes, since a Huffman literal takes up to 4 bytes per octet (30-bit codes, RFC 7541 appendix B; review: 2 × the ceiling refused such an insert the table takes, `qpack.QpackDecoderTest.huffmanInsertLongerThanTwiceTheCeilingAccepted`)

**Tests that pin it.**

- `runtime.LimitsTest.negative_h3DecodedFieldSectionTooLarge`, `.negative_h3SingleOversizedFieldIs431NotConnectionError`, `.singleOversizedResponseFieldFailsOnlyItsRequest`, `.raisedMaxFieldSectionSizeAcceptsLargeSingleValue`, `qpack.QpackDecoderTest.oversizedSingleFieldIsTooLargeNotAnError`, `.largeInsertWithinCapacityAccepted`, `.negative_h3TrailersTooLarge`, `.responseHeadersTooLargeOnClient`, `.headersFrameLengthAboveCapRejectedWithoutReading`

## <a id="s6-1-control-and-qpack-streams"></a>§6.1–6.2, §6.2.1–6.2.3 — control and QPACK streams

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9114 §6.1–6.2, §6.2.1–6.2.3.

**Requirement.** The control and QPACK streams are opened and SETTINGS are sent at once (0.2.1 review: by a coroutine of the connection, so `Http3Connection.server` and `Http3Endpoint.accept` never wait for a client's stream credit; a peer that does not allow the three unidirectional streams within 3 s gets `H3_GENERAL_PROTOCOL_ERROR`, a client `connect` fails with it).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- our own side grants at least three: `Http3Endpoint.bind`/`connect`/`connectEarly` and the Ktor engines refuse `maxUniStreams` < 3 with IllegalArgumentException
- a GREASE setting, a GREASE frame and a GREASE uni stream by default
- a second control/QPACK stream → `H3_STREAM_CREATION_ERROR`
- closing a critical one → `H3_CLOSED_CRITICAL_STREAM`
- an unknown uni stream → `STOP_SENDING H3_STREAM_CREATION_ERROR`
- a uni stream that ends or is reset before its type is dropped and spends a glitch token (0.2.1 review: a reset inside the type closed the connection with `H3_INTERNAL_ERROR`; a critical stream reset after its type stays `H3_CLOSED_CRITICAL_STREAM`)
- a server bidi → `H3_STREAM_CREATION_ERROR`
- a push stream at the client → `H3_ID_ERROR`, at the server → `H3_STREAM_CREATION_ERROR`

**Tests that pin it.**

- `runtime.ConnectionTest.*`, `runtime.UniStreamResetTest.*`, `runtime.SessionStartTest.*` (`negative_serverStartDoesNotWaitForUniStreamCredit`, `negative_clientStartFailsWithoutUniStreamCredit`), `Http3EndpointAcceptTest.negative_acceptIsNotHeldByAClientWithoutUniStreamCredit`, `Http3EndpointAcceptTest.negative_fewerThanThreeUniStreamsIsRefused`, `ServerQuicConfigTest.negative_fewerThanThreeUniStreamsAreRefused`, `ClientH3Test.negative_fewerThanThreeUniStreamsAreRefused`, `ServerH3Test.negative_clientWithoutUniStreamCreditDoesNotStopAccepting`

## <a id="s5-2-idle-close-after-goaway"></a>§5.2 — idle close after GOAWAY

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9114 §5.2 (idle close after GOAWAY).

**Requirement.** A request stream counts as in flight from its first byte, not from its parsed HEADERS: a request below the final GOAWAY id whose HEADERS are still arriving keeps the connection open and is served.

Quoted: "MAY initiate an immediate closure of the connection".

**Recorded status.** ✅ 0.2.0

**How it is met.**

- every early exit (truncated, malformed, 431, rejected) releases it (before 0.2.0 the idle close could cut such a request off)
- HEADERS still incomplete 10 s after the final GOAWAY are rejected with `H3_REQUEST_REJECTED`, so a stalled peer cannot hold the connection open forever
- a client that gets GOAWAY before its own SETTINGS went out closes idle with `H3_NO_ERROR` and `Http3Connection.client` returns it (a request on it → `RequestNotProcessed(retrySafe = true)`; before 0.2.1 the start failed with that close), also when the server's own `H3_NO_ERROR` close comes first (§5.2: it "MAY initiate an immediate closure of the connection"), while any other error after the GOAWAY (a second SETTINGS → `H3_FRAME_UNEXPECTED`, RFC 9114 §7.2.4, or the peer's error close) still fails the start

**Tests that pin it.**

- `runtime.SessionStartTest.goAwayBeforeTheClientSettingsLeaveRefusesRequestsAsNotProcessed`, `runtime.SessionStartTest.peerNoErrorCloseAfterGoAwayRefusesRequestsAsNotProcessed`, `runtime.SessionStartTest.negative_protocolErrorAfterGoAwayFailsTheStart`, `runtime.GoAwayTest.unreadRequestHeadersKeepConnectionOpenAfterGoAway`, `.incompleteRequestHeadersRejectedAfterGoAwayDeadline`, `.inFlightRequestsCompleteBeforeIdleClose`, `.anIdleClientClosesAfterGoAway`, `.aResponseStillBeingReceivedSurvivesTheGoAwayIdleClose`, `.aClientThatNeverClosesIsClosedOnlyAfterItsResponseFinished` (the idle close waits until every answered request stream is finished at the QUIC level, then for the client's own close, 3 s at most; a fixed 200 ms after the last answer cut responses still in flight)

## <a id="s7-2-8-unknown-frames-on-request-streams"></a>§7.2.8, §8.1 (request streams) — unknown frames on request streams

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9114 §7.2.8, §8.1 (request streams).

**Requirement.** Unknown and reserved frames on a request stream are skipped without buffering.

**Recorded status.** ✅ 0.2.0

**How it is met.**

**Tests that pin it.**

## <a id="s4-2-field-validation"></a>§4.2, §4.3 — field validation

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9114 §4.2, §4.3.

**Requirement.** Fields: the name is a lowercase token, CR/LF/NUL, any other control character than HTAB in a value (0x01–0x1F, 0x7F; §10.3, review), whitespace at the edges of the value, characters above U+00FF (fields are ISO-8859-1 octets; U+010A would be truncated to LF — review), connection-specific fields, `te` ≠ `trailers` (compared case-insensitively: `"trailers"` is a quoted string of RFC 9110 §10.1.4's ABNF, RFC 9110 §2.1 uses RFC 5234's ABNF, and RFC 5234 §2.3 says "ABNF strings are case insensitive"; the transfer-coding names of the same rule are case-insensitive too, RFC 9112 §7; review: `Trailers` was refused) → malformed.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- request and response pseudo-headers (order, duplicates, unknown ones, CONNECT, `:authority`/`host`, `:status` 100–599), trailers without pseudo-headers
- outgoing: a request (pseudo-header values and fields, `te` ≠ `trailers` included) and request or response trailers that the peer would reject fail locally with `IllegalArgumentException` before anything is sent (trailers also reset the stream)
- §4.2.1: the server engine joins split `cookie` fields with "; " into one header for the application (review)

**Tests that pin it.**

- `message.FieldValidatorTest.*`, `message.PseudoHeadersTest.*` (file `MessageTest.kt`; including `negative_h3FieldCrLfNul`, `negative_h3FieldControlChars`, `teTrailersCaseInsensitive`, `negative_h3FieldNonLatin1`, `negative_h3MethodMustBeToken`, `negative_h3PathMustBeAbsoluteOrAsterisk`, `negative_h3UserinfoInAuthorityRejected`, `negative_h3AuthoritySyntax`, `negative_classicConnectNeedsAPort`, `negative_h3SecondHostRejected`), `h3.H3AuthorityTest.hostAndPort`, `.defaultPortFollowsTheScheme`, `ServerH3Test.schemeAndDefaultPortFollowTheRequest` (ktor-server: `local.scheme` and the default `serverPort` follow `:scheme`), `runtime.RequestTest.invalidOutgoingRequestFailsLocally`, `.controlCharInRequestFieldIsMessageError`, `.invalidResponseFieldResetsStream`, `.invalidServerTrailersFailFinish`, `.invalidClientTrailersFailRequest`, `ServerH3Test.cookieCrumbsAreJoined`

**History.**

- review (as quic-go): `:method` must be a token, `:path` must start with `/` (or be `*` for OPTIONS) and hold no whitespace, `:authority` (or the `host` standing in for it) must not carry userinfo, a second `host` is malformed
- 0.2.1 review: `:authority` and `host` must be an RFC 3986 authority, `host [":" port]` (port ≤ 65535, a non-empty host for http, https and CONNECT, and a port for a classic CONNECT, whose authority-form is `uri-host ":" port`, RFC 9110 §9.3.6; port 0 is refused too, since no tunnel can reach it, RFC 6335 §6) — a path, query, fragment or space in them is malformed, as HTTP/1.1 refuses them in `Host`

## <a id="s4-6-server-push"></a>§4.6, §7.2.3, §7.2.5, §7.2.7 — server push

Status: ❌ · [summary](../rfc-compliance.md#http)

Original row: RFC 9114 §4.6, §7.2.3, §7.2.5, §7.2.7.

**Requirement.** Server push.

Quoted: "Implementations SHOULD track the use of these features and set limits on their use".

**Recorded status.** ❌

**Reason.**

- codes by role: `PUSH_PROMISE` at the client → `H3_ID_ERROR`, at the server → `H3_FRAME_UNEXPECTED`
- `CANCEL_PUSH` → `H3_ID_ERROR`
- `MAX_PUSH_ID` at the client → `H3_FRAME_UNEXPECTED`
- the server reads `MAX_PUSH_ID` all the same (review): a smaller value than before → `H3_ID_ERROR` (§7.2.7), a payload that is not one varint → `H3_FRAME_ERROR` (§7.1), the first valid one is free and every later one spends a glitch token, since without push it does no useful work (§10.5: "Implementations SHOULD track the use of these features and set limits on their use"), so a flood of them, increasing ones included, ends in `H3_EXCESSIVE_LOAD` (0.2.1 review: valid ones were free) — `frame.FrameRulesTest.pushPromiseCodesByRole`, `.maxPushIdProcessedOnServer`, `runtime.ConnectionTest.decreasingMaxPushIdIsIdError`, `.malformedMaxPushIdIsFrameError`, `.firstMaxPushIdIsFreeAndLaterOnesSpendGlitchTokens`, `.negative_maxPushIdFloodIsExcessiveLoad`

**Open items.**

- not planned
