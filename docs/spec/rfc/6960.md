## <a id="ocsp-stapling"></a>/ 6961 (6961 obsoleted by RFC 9846: `status_request_v2` is `ocsp_multi_RESERVED`) — OCSP, stapling

Status: ⬜ (not scheduled) · [summary](../rfc-compliance.md#tls)

Original row: RFC 6960 / 6961 (6961 obsoleted by RFC 9846: `status_request_v2` is `ocsp_multi_RESERVED`).

**Requirement.** OCSP, stapling.

**Recorded status.** ⬜ later (behind a flag)

**How it is met.**

- Kuicksilver itself performs no revocation checking (no OCSP, no stapling, no CRLs) on its own paths.
- Under `TrustConfig.Platform` revocation depends on the platform verifier: Apple `SecTrust` (`SecTrustEvaluateAsyncWithError`) applies the system's revocation policy, `errSecCertificateRevoked` maps to `VerifyReason.Revoked` and an incomplete revocation check (-67635) to `VerifyReason.UnknownRevocationStatus`
- Windows (`CertGetCertificateChain` with `CERT_CHAIN_REVOCATION_CHECK_END_CERT`) checks the leaf, maps `CRYPT_E_REVOKED`/`CERT_E_REVOKED` to `Revoked` and soft-fails an unknown status (`CERT_CHAIN_POLICY_IGNORE_ALL_REV_UNKNOWN_FLAGS`; `CRYPT_E_NO_REVOCATION_CHECK`, `CRYPT_E_REVOCATION_OFFLINE` and `CERT_E_REVOCATION_FAILURE`, if the policy reports them, map to `UnknownRevocationStatus`)
- the JDK default `TrustManager` (PKIX) checks revocation only when the application enables it (e.g. `com.sun.net.ssl.checkRevocation`), and then `REVOKED` maps to `Revoked` and `UNDETERMINED_REVOCATION_STATUS` to `UnknownRevocationStatus` (the path rebuilt for pins runs with `isRevocationEnabled = false`)
- Android's default trust manager does not check revocation (only its built-in blocklist, reported as `Revoked`)
- `Revoked` also appears when the peer sends a `certificate_revoked` alert

**Open items.**

- Linux Native and every other `TrustConfig` mode use the OpenSSL verifier without CRLs or OCSP — a known limitation (RFC 9325 §7.5).
