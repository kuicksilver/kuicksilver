# RFC 6960 — Online Certificate Status Protocol (OCSP) and stapling

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="ocsp-stapling"></a>OCSP responses stapled through `status_request` (RFC 6066 §8, RFC 9846 §4.5.1.1)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

**Requirement.** RFC 6960 §3.2: "Prior to accepting a signed response for a particular certificate as valid, OCSP clients
SHALL confirm that: 1. The certificate identified in a received response corresponds to the certificate that was identified
in the corresponding request; 2. The signature on the response is valid; 3. The identity of the signer matches the intended
recipient of the request; 4. The signer is currently authorized to provide a response for the certificate in question; 5.
The time at which the status being indicated is known to be correct (thisUpdate) is sufficiently recent; 6. When available,
the time at or before which newer information will be available about the status of the certificate (nextUpdate) is greater
than the current time." §4.2.2.2: relying systems "MUST reject the response if the certificate required to validate the
signature on the response does not meet at least one of the following criteria" (a local signing authority, the CA that
issued the certificate, or a certificate with id-kp-OCSPSigning that CA issued), and "MUST recognize a delegation
certificate as being issued by the CA that issued the certificate in question only if the delegation certificate and the
certificate being checked for revocation were signed by the same key". RFC 6066 §8: "Clients requesting an OCSP response
and receiving an OCSP response in a "CertificateStatus" message MUST check the OCSP response and abort the handshake if the
response is not satisfactory with bad_certificate_status_response(113) alert"; a server "MUST NOT send the
"CertificateStatus" message unless it received a "status_request" extension in the client hello message". RFC 9846
§4.5.1.1: in TLS 1.3 "the body of the "status_request" extension from
the server MUST be a CertificateStatus structure as defined in [RFC6066]".

**Recorded status.** ⬜ until 0.3.0 (no OCSP, no stapling, no CRLs on Kuicksilver's own paths; the bundled OpenSSL was built
with `no-http`, which also turns off its ocsp module).

**How it is met.**

- The bundled OpenSSL includes the ocsp module since 0.3.0 (`no-http` dropped from `tools/openssl/configure-flags.txt`).
- `ksl_ocsp_check` (`kuicksilver-native/src/c/ksl_ocsp.c`) runs the §3.2 checks: the certID (under the hash the response
  uses) names the leaf and the issuer the handshake's verifier trusted (1, 3); the signature verifies (2); the signer is the
  issuer's key, or a delegated responder with id-kp-OCSPSigning whose certificate verifies under the issuer's key and is
  valid now (4, §4.2.2.2; no locally configured responders, the MAY of that section); thisUpdate is at most 5 minutes in the
  future and nextUpdate at most 5 minutes past (5, 6; §4.2.2.1 "SHOULD be considered unreliable" otherwise); a response
  without nextUpdate counts as fresh for one day after thisUpdate (Kuicksilver's policy: §4.2.2.1 says newer information is
  "available all the time"). The responder's own revocation status is not checked (§4.2.2.2.1 leaves it to local policy).
- Client ([`RevocationPolicy`](../../../kuicksilver-tls/src/commonMain/kotlin/io/kuicksilver/tls/Revocation.kt), default
  `StapledIfPresent`): `status_request` is sent and the stapled response checked where `ksl`'s own verifier runs
  (`AnchoredCa`, `Platform` on Linux Native, inside `Pinned` and `ExpectedName`), after the chain is verified; revoked fails
  (`VerifyReason.Revoked`), a response failing a check fails (`VerifyReason.InvalidStatusResponse`), both with
  bad_certificate_status_response (113) as RFC 6066 §8 requires; no response or "unknown" passes, except under
  `RequireStapled` and for an RFC 7633 must-staple leaf (`VerifyReason.UnknownRevocationStatus`, alert 113). A server's
  `status_request` that the client did not offer is refused by OpenSSL (unsupported_extension, RFC 9846 §4.2).
- Server ([`OcspStapling`](../../../kuicksilver-tls/src/commonMain/kotlin/io/kuicksilver/tls/Revocation.kt)): the
  configured response is stapled only to a client that sent `status_request` (RFC 6066 §8), only when it is for the leaf the
  handshake presents (issuer from the configured chain), verifies and is fresh at that moment; TCP (TLS 1.2
  CertificateStatus, TLS 1.3 CertificateEntry) and QUIC alike. `OcspStapling.update` replaces it at run time. An identity
  chosen by `sniSelector` (TCP) staples the response of its own `ServerTlsOverride`, never the default identity's. The
  server keeps its verdict on a response per context and uses it only inside the response's interval, bounded by a
  delegated responder certificate's validity.
- Resumption: a session whose full handshake checked a stapled response resumes only while that response is fresh; under
  `RequireStapled` a session without one never resumes.
- RFC 6066 §8, server side: "Servers that receive a client hello containing the "status_request" extension MAY return a
  suitable certificate status response to the client along with their certificate. If OCSP is requested, they SHOULD use
  the information contained in the extension when selecting an OCSP responder and SHOULD include request_extensions in the
  OCSP request." Kuicksilver's server sends no OCSP request per handshake: the application fetches the response before
  (`OcspStapling.update`), and a response is a "suitable certificate status response" the server MAY return. The first
  SHOULD is met as far as a fetched response allows: when the client names responders (`responder_id_list`), the response
  is stapled only if one of them signed it (`ksl_ocsp.c` `responder_wanted`; C `negative_responder_not_named`). The second
  SHOULD concerns the OCSP request, which is not made per client, so a client's `request_extensions` (a nonce, typically)
  cannot be carried into it; such a client gets the pre-fetched response, which carries no nonce of its own. Our client
  sends an empty `responder_id_list` and no `request_extensions` (OpenSSL's default), so it asks neither of a server.

**Scope.** Only the leaf's status (RFC 9325 §7.5: OCSP for intermediates "remains impractical"); the client fetches no OCSP
response itself (no OCSP requests, RFC 9325 §7.5 on the "scaling and privacy issues" of plain OCSP); under
`TrustConfig.Platform` off Linux the platform verifier keeps its own revocation behaviour, and `Custom` and `Tofu` decide
alone.

**Tests that pin it.** C `revocation_ocsp_check` (good, delegated, revoked, unknown and the `negative_*` stale, future, no
nextUpdate, mismatch, wrong issuer, unauthorized, no OCSPSigning, bad signature, trailing, try-later, truncated),
`revocation_stapling` (QUIC, TLS 1.3 and TLS 1.2 over TCP), `RevocationTest`; fixtures from
`tools/certs/gen-revocation-certs.sh` (`openssl ocsp`).

**Peer notes.** BoringSSL sends `status_request` only after `SSL_enable_ocsp_stapling` and leaves the check to its caller
(`ssl/extensions.cc`); msquic's OpenSSL back end refuses `QUIC_CREDENTIAL_FLAG_ENABLE_OCSP` ("Schannel only currently",
`src/platform/tls_openssl.c`). The defaults of curl, OkHttp, the JDK and browsers were not verified against their sources.

**Open items.** None for this row; file-based OCSP response and CRL reload keys of the Ktor server configuration are not
offered (the application calls `OcspStapling.update` or `ReloadableCa.reload`).
