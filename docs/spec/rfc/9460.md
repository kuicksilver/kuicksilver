# RFC 9460 — Service Binding and Parameter Specification via the DNS (SVCB and HTTPS RRs)

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="https-rr-as-a-source-of"></a>HTTPS RR as a source of h3

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 9460.

**Requirement.** The client side of RFC 9460 for the `https` and `http` schemes, checked against the RFC text
(`refs/rfc/rfc9460.txt`): SVCB resolution and connection through its endpoints (sections 2.4, 2.5, 3, 7.1.2, 7.2, 8, 9,
9.1), resolution failures and protected DNS (section 3.1), proxies (section 3.2), the performance rules (sections 5,
5.1), Alt-Svc together with records (section 9.3), SNI (section 9.4), the `http` upgrade (section 9.5) and the DNS cache
per network and AliasMode "." (section 12).

**Recorded status.** ✅ 0.3.0 (opt-in, `Http3ClientConfig.httpsRecords`). Choices the RFC leaves open: the address
hints are parsed, not used (section 7.3: MAY; the client always resolves the TargetName); `ech` is not supported, so a
record that makes it mandatory is skipped and an optional one ignored (section 8); with a proxy no SVCB resolution is
done (section 3.2, a deliberate choice: through a proxy the engine uses named destinations, and the SHOULD asks for "a
separate SVCB resolution procedure with appropriate privacy properties"; the system resolver would disclose the
destinations to the local network's resolver, which the proxy exists to avoid, and even an `Exchange(secure = true)`
discloses them to the DoH operator, a party the proxy configuration did not choose for that, and the engine cannot tell
whether that is acceptable; so it takes the branch for when this "is not possible": "SVCB-optional clients MUST disable
SVCB resolution entirely"). Section 9.6's second paragraph (an HTTP proxy connection upgraded when "clients that find a
corresponding HTTPS RR") does not arise: proxy names are never looked up, so no record is found for them. Section 9's
"Clients that restrict the destination port in "https" URIs (e.g., using the "bad ports" list from [FETCH]) SHOULD apply
the same restriction to the "port" SvcParam" does not apply either: the engine restricts no port of an `https` URI. An
AliasMode record whose TargetName is not a host name (bytes other than letters, digits, `-` and `_`, written `\DDD`) is
treated like "." (ignored, section 12), also for the section 9.5 upgrade, which it does not trigger. Plain DNS failures
are nonfatal (section 3.1: MAY). An optimistic connection to the origin before the records arrive sends nothing a
SvcParam the engine honours could change: the ALPN list does not depend on the record (section 7.1.2) and ECH is not
used (section 5.1, MUST NOT). The system resolver (`HttpsRecordSource.System`): `ksl_dns_query` on Linux, Apple and Windows, Android from
API 29 (`DnsResolver.rawQuery`), none on Android below 29; DNS over HTTPS through the application's
`HttpsRecordSource.Exchange`.

**How it is met.**

- `kuicksilver-ktor-client/src/commonMain/kotlin/io/kuicksilver/ktor/client/KuicksilverEngine.kt` (`autoWithRecords`,
  `attempt`, `h3Alone`, `awaitResolution`): the records, waited for while the origin's addresses resolve (section 3,
  SHOULD issue in parallel) and `httpsRecordExtraWait` longer (section 5.1); the endpoints tried in order, each over the
  transports of its ALPN set (section 7.1.2: QUIC and TCP racing, TCP to the TargetName and port through
  `RequestDns.connectTo`), the next one after a failure to connect, then the origin without SVCB (section 3); SNI,
  `:authority` and the certificate check name the origin (sections 2.3, 9.1 and 9.4, MUST)
- `dns/HttpsRecordCache.kt`: `HttpsRecords.resolve`, SVCB resolution as section 3 defines it: AliasMode records
  followed (one at random among several, section 2.4.2; "." ignored, section 12), at most 8 steps and a name seen twice
  falling back to the authority as if there were no record (section 3.1, MUST), the compatible ServiceMode endpoints by
  ascending SvcPriority, shuffled within a level (section 2.4.1; at most 32 of them, the lowest priorities first, so a
  forged RRset of thousands of records cannot make thousands of connection attempts), each with the transports its SVCB ALPN set allows
  (section 7.1.2, default set `http/1.1` per section 9; an endpoint with no supported protocol is not attempted), and
  after an AliasMode chain the final $QNAME with the authority's port appended (section 3, SHALL; TCP only, since an
  endpoint without SvcParams has the default ALPN set only), also when a later lookup fails or the request stops
  waiting for the rest of the chain ("whether successful or not"; only the chain-length limit falls back to the
  authority, section 3.1); the
  cache (each answer for its TTL, at most a day, counted on both the monotonic and the wall clock and expired once
  either has seen it pass, `ExpiryClock`: neither a wall clock stepped back nor a device that slept keeps an answer
  longer, and only a wall clock stepped back during sleep could; "no records" for the SOA's negative TTL, RFC 2308 section 5: "the minimum of the SOA.MINIMUM
  field and SOA's TTL", no longer than a CNAME that led there, since the negative answer is about "the data field of
  the last CNAME" (RFC 2308 section 1) and a CNAME "may be cached" only for its TTL (RFC 1035 section 3.2.1), and not
  at all without an SOA; 1000 names and 1 MiB each for records and addresses, no RRset or address list of over 64;
  cleared on a new `networkId`; failures not kept), the other HTTPS
  RRsets and the A/AAAA records of an answer kept and used before any follow-up query (section 5, SHOULD;
  `DnsMessage.read`, `RequestDns.seed`; with both families a name's addresses are its answer and no lookup follows;
  with one family alone, which may be a response that omitted the other, section 5.2, that family is used at once and
  the name's lookup still runs, its other family's addresses joining when they come within the 50 ms resolution delay
  of Happy Eyeballs, IPv6 first (as with both families seeded), section 3: "Clients resolve AAAA and/or A records for the selected TargetName and MAY choose
  between them using an approach such as Happy Eyeballs"; a later answer cannot join a race in progress, the open
  RFC 8305 §3 item;
  a TargetName that is a CNAME gets the RRset and addresses at the end of its chain, as its own query would "after
  following CNAMEs as normal", section 3, no longer than the chain's TTL, and kept beyond the resolution only when every
  name of the chain is in the query's bailiwick, RFC 2181 section 5.4.1),
  the A/AAAA of each alias target looked up in parallel with its SVCB query (section 5, speculative queries), the
  extra wait at least 50 ms (section 5.1),
  one lookup per name, each bounded by the connect timeout (at most 30 s)
- section 9.5: before an `http` request (not `ws`, not through a proxy, not to an IP address) the records of the
  matching `https` URL (port 80 made 443) are looked up and waited for; an AliasMode record (not ".") or a compatible
  ServiceMode record makes the engine answer 307 with that URL in `Location`, without connecting (`httpsUpgrade`), which
  Ktor's `HttpRedirect` follows like a server's 307; nothing is remembered beyond the records' TTL (no HSTS-like state:
  no more trust than a cleartext 307, MUST NOT). Section 9.6 asks the same for WebSockets only of clients that use the
  Fetch WebSocket handshake ([FETCH-WEBSOCKETS]), which this engine does not; a `wss` request uses the records as any
  `https` one
- section 9.3: with a cached Alt-Svc alternative its alt-authority's records are resolved as well (in parallel with the
  origin's); their TargetName and port carry the QUIC attempts, only those whose ALPN set has `h3` (the only protocol
  the engine takes from Alt-Svc), and an alternative whose records offer no `h3` is not connected to
- section 12: the record cache is partitioned by `networkId` (flushed when it changes) and is off while `networkId` is
  not set, since the engine cannot see a network change then (MUST)
- a host in Unicode (not converted to A-labels, RFC 5890 section 2.3.2.1) cannot be put in a DNS query: it has no SVCB
  resolution and counts as "no records", not as a failed lookup, so a secure source does not abandon the request (the
  engine does no IDNA conversion; such a host does not resolve over TCP either)
- section 3.1, the system resolver: `HttpsRecordSource.System` treats failures as nonfatal, since the engine cannot tell
  whether the system's answers are protected; `HttpsRecordSource.ProtectedSystem { ... }` lets the application say so
  per request, and on Android `HttpsRecordSource.followingPrivateDns(connectivity)` reports strict Private DNS (DNS
  over TLS to a configured server, `LinkProperties.getPrivateDnsServerName()` and `isPrivateDnsActive`; the opportunistic
  mode can fall back to plain DNS and counts as unprotected). The engine has no Android `Context`, so strict Private DNS
  is honoured only when the application opts in with `followingPrivateDns`; plain `System` stays nonfatal on Android
  too. On Apple platforms (encrypted DNS through
  `NEDNSSettingsManager` or a profile), Linux and Windows no public API reports whether the system resolver encrypts, so
  there `System` stays nonfatal unless the application supplies the check: a limit of the platforms, stated here rather
  than claimed away
- section 3.1: `HttpsRecordSource.Exchange(secure = true)` declares protected answers: a failed resolution (error
  answer, transport error, timeout) abandons the request (SHOULD), which waits for the answer rather than the extra
  wait; an `Exchange` without `secure` treats a failure as nonfatal (MAY, its answers being unprotected as far as the
  engine knows); for `System` see the system-resolver bullet above. A malformed RRset is never a failure: it is
  rejected and the connection goes on without SVCB (section 2.2, MUST; `SvcbMalformedException`)
- `HttpsRecordSource.kt`: `Off`, `System`, `Exchange` (RFC 8484 wire format, ID 0: DoH clients "SHOULD use a DNS ID
  of 0 in every DNS request", RFC 8484 section 4.1; the engine checks the question of the response, not its ID, which
  "can be used by the requester to match up replies to outstanding queries", RFC 1035 section 4.1.1, so the exchange ties a response to its query: DNS over HTTPS and TLS do, and the KDoc asks
  an exchange over plain UDP or TCP to set and check a random ID of its own); `System` through
  `kuicksilver-tls` `KslDns` (`ksl_dns_query`, `kuicksilver-native/src/c/ksl_dns.c`; at most 4 lookups at once) and
  `DnsResolver.rawQuery` on Android

## <a id="s2-2-svcb-https-rdata"></a>§2.2, §7, §8 — SVCB/HTTPS RDATA, mandatory, AliasMode

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** The RDATA format (§2.2: SvcPriority, an uncompressed TargetName, SvcParams in strictly increasing key
order, no value past the end of the RDATA; a malformed RR makes the client reject the whole RRSet), the values of the keys
it reads (§7: `alpn` with non-empty ids, an empty `no-default-alpn`, a two-byte `port`, `ipv4hint`/`ipv6hint` of whole
addresses), `mandatory` (§8: no self-reference, keys in increasing order, every listed key present; an RR that needs a
key the client does not support is skipped), AliasMode (§2.4.2: its SvcParams are ignored; an RRSet with an AliasMode
record has its ServiceMode records ignored, §2.4.1) and TargetName "." (§2.5).

**How it is met.**

- `kuicksilver-ktor-client/src/commonMain/kotlin/io/kuicksilver/ktor/client/dns/SvcbRecord.kt`: `SvcbCodec.parseRdata`
  (sans-IO, reads only inside the RDATA, allocates at most its length), `serviceEndpoints` (ServiceMode endpoints by
  SvcPriority with their transports), `aliasTarget` (one AliasMode record at random), `httpsQueryName` (§9.1)
- `dns/DnsMessage.kt`: the query (ID 0, RD) and the answer section: the question must be the one asked, the CNAME chain
  is followed (the TTL is the smallest along it), compression pointers must point back (at most 128 per name), a TTL with
  the top bit set counts as 0, in a message and in the record lists of Apple and Windows alike (RFC 2181 §8:
  "Implementations should treat TTL values received with the most significant bit set as if the entire value received
  was zero"), TC and an RCODE other than NOERROR/NXDOMAIN are errors. The DNS is "an untrusted channel that might be
  controlled by an attacker" (§9.2.2), so the work is linear in the message and bounded: a message over 65535 bytes is
  refused (RFC 1035 §4.2.2: "a two byte length field which gives the message length"; RFC 8484 §6: "This media type
  restricts the maximum size of the DNS message to 65535 bytes"), the TargetNames are followed with a work list, each
  TargetName walked once (at most 16 CNAMEs) and each owner's RRset parsed once, at most 16 other RRsets per answer, the
  `mandatory` keys checked in one merge pass (§8), and the read checks the lookup's coroutine every 64 units of work,
  so the lookup's timeout stops it
- `ech` is ignored (no client ECH in OpenSSL 3.5): a record that lists it in `mandatory` is skipped; the address hints are
  checked but not used to connect (§7.3 allows it)

**Tests that pin it.**

- `SvcbResolutionTest.*` (section 3: order, transports, shuffle, the appended AliasMode endpoint, chain limit and
  loop, AliasMode "."; section 5: records carried by an earlier answer, also for an alias target that is a CNAME, the
  alias target prefetched), `DnsMessageTest.negativeTtlComesFromTheSoa`, `.otherRrsetsAndAddressesOfTheAnswerAreKept`,
  `.relatedRrsetOfACnameTargetIsFiledUnderTheTargetName`, `.negative_cnameTargetLeavingTheZoneIsNotInBailiwick`,
  `.negative_hostileLargestAnswerIsReadInLinearTime` (3447 records with distinct TargetNames in 65520 bytes: 13 ms, where
  the earlier walk took over a minute), `.negative_readStopsAtACheckpoint`, `.negative_messageOverTheDnsMaximumIsRejected`,
  `.negative_relatedRrsetsFollowedAreCapped`, `SvcbRecordTest.*` (the Appendix D.1/D.2 vectors byte for byte, and the D.3-style failures: keys out of order or
  repeated, `mandatory` naming itself or a missing key, an empty alpn-id, a three-byte `port`, an `ipv4hint` that is not
  whole addresses, a compressed TargetName, a label over 63 bytes, a cut RDATA), `DnsMessageTest.*` (CNAME chain and
  TTL, other owners ignored, compression loops and forward pointers, a malformed record rejecting its RRSet)
- fuzzing: the `client.svcb` target (`SvcbFuzzTest.svcbMessage`, seeds from `tools/fuzz/gen-svcb-seeds.py`): only DNS
  errors escape, every record read is written back and read again into an equal one, and a whole message is read with
  its other RRsets and addresses within the work bound above (counted by the checkpoints), at most 16 other RRsets, at
  most 32 endpoints, and addresses of 4 or 16 bytes

**Open items.** None.
