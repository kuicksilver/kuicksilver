# RFC 8305 — Happy Eyeballs Version 2

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="s4-tcp-address-race"></a>§4–§6 (TCP) — TCP address race

Status: 🔶 since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 8305 §4–§6 (TCP).

**Requirement.** Interleaving (First Address Family Count 1, the resolver's first family leads), 250 ms connection attempt delay (`connectionAttemptDelay`, 10 ms..2 s or infinite for one address after another), the next attempt at once when one fails, losers cancelled or, when they connected too, closed.

**Recorded status.** 🔶 0.3.0 (§3, §4 on the desktop JVM, §7: ⬜ 0.3.0)

**How it is met.**

- the h1.1 connect to the origin and to an HTTP proxy
- one resolution per request for both sides of the h3/h1 race, HTTP/3 takes its first address (no race between addresses over QUIC)
- §4 MUST sort by RFC 6724 destination address selection — met where the platform resolver sorts (getaddrinfo on Linux, Apple, Windows, Android's resolver), not on the desktop JVM, where `getAllByName` puts IPv4 first unless `java.net.preferIPv6Addresses` says otherwise
- §7 SHOULD (no 464XLAT): NAT64 synthesis for IPv4 literals and A-only names on an IPv6-only network is not done

**Tests that pin it.**

- `HappyEyeballsTest.*`, `ClientH1Test.h1FallsBackToSecondAddress`, `ClientRaceTest.raceResolvesTheNameOnce`

**Open items.**

- open (⬜ 0.3.0, need an asynchronous per-family resolver and an RFC 6724 sort of our own): §3 SHOULD — AAAA and A as separate asynchronous queries, the first attempt without waiting for both families, the 50 ms resolution delay (getaddrinfo and `InetAddress.getAllByName` answer once, with both families)

## <a id="happy-eyeballs"></a>Happy Eyeballs

Status: 🔶 since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 8305.

**Requirement.** Happy Eyeballs (h3/h1.1 race; the TCP address race: the row above, [§4–§6](#s4-tcp-address-race)).

**Recorded status.** 🔶 0.2.0 (feature subset: HTTP/3 tries one address, see the notes)

**How it is met.**

- a connection establishment race: h3 first, h1.1 on an h3 error or after a head start of 1.5 × sRTT (250 ms without history, clamped to 100 ms–2 s)
- §5 against the race: the attempts are never simultaneous (SHOULD NOT) and h1.1 never starts within 10 ms of h3 (MUST NOT; 0.2.1: on a network without confirmed QUIC it started at once), an explicit `hardDelay` must be 10 ms–2 s (MUST lower bound, SHOULD upper bound; 0.2.1, before any value was taken) or `Duration.INFINITE` (h1.1 only after h3 failed, an explicit choice, bounded by the connect timeout)
- once one setup succeeds the other is cancelled (SHOULD) — an h1.1 connection that completed anyway is closed, while a QUIC setup that lost goes on to serve the next requests, as RFC 7838 §2.4 says a client SHOULD use an alternative "as soon as it is available"
- the request goes once, on the winner
- platform network identifiers come through the `networkId` hook

**Tests that pin it.**

- broken per (origin, alternative) with a backoff of 5 min → ×2 → 2 days, reset on a `networkId` change — `ProtocolRaceTest.*` (`.minimumHeadStartOnUnconfirmedNetwork`, `.negative_hardDelayOutsideRfc8305BoundsIsRefused`), `BrokenAltSvcTest.*`, `ClientFallbackTest.*`

**Open items.**

- feature subset: HTTP/3 connects to the first address of the resolution only (no address race over QUIC; the h1.1 side races every address, row above: [§4–§6](#s4-tcp-address-race)), and curl's soft delay ("no UDP packets from the server") is not implemented — the QUIC API has no such signal
