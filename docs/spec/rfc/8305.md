# RFC 8305 — Happy Eyeballs Version 2

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="s4-tcp-address-race"></a>§3–§7 — address race (TCP and QUIC)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 8305 §4–§6 (TCP).

**Requirement.** The Happy Eyeballs algorithm for every connection the Ktor client engine makes to a host: HTTP/1.1 and HTTP/2 over TCP to the origin and to an HTTP proxy, HTTP/3 over QUIC (the request's connection and a WebTransport session's): separate asynchronous AAAA and A queries with the Resolution Delay (§3), an RFC 6724 sort and interleaved families (§4), staggered attempts (§5), answers that arrive during the race (§6), and NAT64 on IPv6-only networks (§7).

**Recorded status.** ✅ 0.3.0 (0.3.0 before this: the TCP race only, over one answer with both families, ordered by the resolver; HTTP/3 took the first address)

**How it is met.** (`kuicksilver-ktor-network`: `NameResolution.kt`, `AddressSelection.kt`, `HappyEyeballs.kt` `raceAddresses`; `kuicksilver-ktor-client`: `RequestDns`, `Nat64`, `H1Pool`, `H3Pool`; `ksl_net.c`)

- §3, "Both queries SHOULD be made as soon after one another as possible, with the AAAA query made first and immediately followed by the A query" and "the client SHOULD treat DNS resolution as asynchronous. Note that if the platform does not offer an asynchronous DNS API, this behavior can be simulated by making two separate synchronous queries on different threads, one per address family": each family is its own `getaddrinfo` (`AF_INET6`, then `AF_INET`, with flags of our own so that Apple's `AI_V4MAPPED` default does not turn the IPv6 query into a wait for the A answer), on two threads of the lookup dispatcher; on the JVM and Android through `ksl_resolve` (JNI), since `InetAddress` asks for both families in one call; on Kotlin/Native the same C function. An application that replaced the JDK's resolver (`InetAddressResolverProvider`, `jdk.net.hosts.file`) keeps it: lookups then go through `InetAddress`, one call for both families. `java.net.preferIPv4Stack=true` makes the AAAA answer empty (the JDK opens IPv4 sockets only).
- §3, "if a positive AAAA response (a response with at least one valid AAAA record) is received first, the first IPv6 connection attempt is immediately started"; "If a positive A response is received first due to reordering, the client SHOULD wait a short time for the AAAA response ... The recommended value for the Resolution Delay is 50 milliseconds."; a negative AAAA answer within it ("no error, no data"), or a failed one, starts IPv4 at once; "If the AAAA response arrives while these connection attempts are in progress but before any connection has been established, then the newly received IPv6 addresses are incorporated into the list of available candidate addresses": late answers of either family join the race.
- §4, "First, the client MUST sort the addresses received up to this point using Destination Address Selection ([RFC6724], Section 6).": `DestinationSort`, our own on every platform, also for the addresses an HTTPS answer carried (RFC 9460 section 5, `RequestDns.seed`): the ten rules in order with the default policy table (section 2.1), IPv4 as IPv4-mapped (section 3.2), Source(D) the address the system would send from (a connected UDP socket, no packet sent), and its attributes from `ksl_addr_info`: Rule 3 (deprecated) from a netlink address dump on Linux and Android, `SIOCGIFAFLAG_IN6` on macOS and `DadState` on Windows; Rule 7 (an encapsulating tunnel) from the interface type (Linux sit, ipip, ip6tnl, GRE; Apple gif, stf; Windows `IF_TYPE_TUNNEL`); Rule 9 with the source's on-link prefix length (64 bits for IPv6, 32 for IPv4 when the system does not report it). Where the system does not report a source's state (iOS for deprecation, Android apps for tunnels, where the link-layer entries are hidden), Rules 3 and 7 decide nothing, as in the platforms' own resolvers. Rule 4 decides nothing: no supported platform has Mobile IPv6 home addresses. The RTT and "used address" rules apply "If the client is stateful and has a history of expected round-trip times (RTTs) for the routes to access each address" and "If the client keeps track of which addresses it used in the past": the engine keeps neither per address.
- §4, "the client SHOULD modify the ordered list to interleave address families": First Address Family Count 1 (`interleaveFamilies`); a late answer is sorted in with the rest and the next attempt is the first address not yet tried in the whole ordered list, so the families keep alternating.
- §5, "connection attempts SHOULD NOT be made simultaneously": one attempt, then the next after `connectionAttemptDelay` (250 ms, "One recommended value for a default delay is 250 milliseconds."; 100 ms to 2 s, the Minimum and Maximum Connection Attempt Delay of section 8, or infinite for one after another) or when an attempt failed, but never "within 10 milliseconds of the previous attempt" (MUST); "Once one of the connection attempts succeeds ..., all other connections attempts that have not yet succeeded SHOULD be canceled. Any address that was not yet attempted as a connection SHOULD be ignored": the losers are cancelled (a cancelled QUIC connect closes its connection), a loser that connected anyway is closed, the lookups still out stop being waited for while the system lookups themselves run to their end ("the DNS client resolver SHOULD still process DNS replies from the network for a short period of time"). TCP attempts succeed with the TCP handshake, QUIC attempts with the QUIC handshake. With `earlyData` and a ticket for the server, the first QUIC attempt can send 0-RTT at once and is used without racing the others (scope note below). When every QUIC attempt failed, a refusal (CONNECTION_REFUSED) is reported only when every address refused; a connect timeout carries every attempt's failure.
- §6: added addresses join as above. Removed addresses do not occur: the system resolvers answer once per query (no DNS push).
- §7, "On platforms that do not support 464XLAT, the Happy Eyeballs engine SHOULD follow the recommendations in this section" and "SHOULD only be enabled when the host detects one of these networks": `Nat64.ipv6OnlyNetwork`, a global IPv6 source address and no IPv4 one (or only a link-local one) for global destinations; a platform that runs 464XLAT (Android's clatd, iOS on cellular) has an IPv4 address and route and is not taken for such a network. On such a network an IPv4 address is synthesized only when the host has no route to it (a LAN's, a VPN's and loopback addresses stay as they are), never a loopback, link-local or multicast one, and the Well-Known Prefix never for a non-global one (RFC 6052 section 3.1: "The Well-Known Prefix MUST NOT be used to represent non-global IPv4 addresses"). The prefixes: the platform's own synthesis where there is one (Apple: `getaddrinfo` of the literal with `AI_DEFAULT`, `ksl_nat64_synthesize`), else RFC 7050 section 3 (an AAAA query for `ipv4only.arpa` through the system resolver, made only once an address needs synthesis, one query at a time; every plausible prefix (`2000::/3`, `64:ff9b::/96`, `64:ff9b:1::/48`) in the order received; cached for the answer's TTL, at least 60 s, and refreshed in the background from ten seconds before it ends; a negative answer not asked again within its TTL, its SOA's or 3 h where the platform hands out records without it; 30 s between failed queries; dropped on a new `networkId` or a new IPv6 /64). Section 3.2's connectivity check is the race itself: "The second approach is to simply attempt to use the learned Pref64::/n." The synthesis covers IPv4 literals (§7.1) and A answers. The A query is made only when the AAAA answer is negative or failed (§7.3, a VPN resolver's A-only name), or as the Last Resort Local Synthesis 2 s after the last attempt started without a connection, or at once when every attempt failed (§7.2). Nothing waits for the prefix unless an address needs it. On Android (API 30) the prefix Android knows (`LinkProperties.getNat64Prefix`, learnt from a PREF64 router advertisement or RFC 7050) is used when the application gave the engine a `ConnectivityManager` (`Http3ConnectionMigration.followDefaultNetwork`, `HttpsRecordSource.followingPrivateDns`); otherwise, without 464XLAT there, the `ipv4only.arpa` query goes through its resolver.
- §3.1 (the DNS servers' order and number) is the system resolver's: the engine sends no DNS query of its own for addresses.
- HTTP/3: the h3/h1 race ([Happy Eyeballs](#happy-eyeballs)) races QUIC over all addresses on one side and TCP over all addresses on the other, both from the request's one resolution.

**Tests that pin it.**

- `HappyEyeballsResolutionTest.*` (AAAA first, the Resolution Delay, a late AAAA joining, slow A, broken IPv6, IPv4-only and IPv6-only hosts, `negative_aFailureWithin10msWaitsForTheGap`, `negative_slowAaaaDoesNotHoldIpv4PastTheResolutionDelay`, NAT64 A on a negative AAAA, the Last Resort after 2 s, `negative_nat64AsksAAtOnceWhenEveryIpv6AttemptFailed`), `HappyEyeballsTest.*`, `AddressSelectionTest.*` (the examples of RFC 6724 section 10.2 rule by rule, the policy table, scopes), `KslNetTest.*`, `ResolveTcpTest.*`, `RequestDnsTest.*`, `Nat64Test.*` (RFC 6052 Tables 1 and 2, RFC 7050 discovery and its caching, the IPv6-only heuristic), `ClientHappyEyeballsTest.h3RacesTheAddressesOfAName`, `.negative_aStalledAaaaQueryDoesNotHoldTheConnection`, `ClientH1Test.h1FallsBackToSecondAddress`, `ClientRaceTest.raceResolvesTheNameOnce`, the `ksl` C tests `run_net`

**History.**

- 0.3.0 (k10): the TCP race over one answer of both families in the resolver's order; HTTP/3 to the first address; no per-family queries, no RFC 6724 sort of our own on the desktop JVM and for HTTPS-record addresses, no NAT64. Then the whole of §3 to §7 as above, for TCP and QUIC.

**Scope.**

- With `earlyData` and a session ticket, an HTTP/3 setup sends 0-RTT on the first address of the order without racing the others: 0-RTT that waited for a race would not be early; a failed handshake there fails its requests, which fall back over TCP (where the TCP race tries every address).

**Open items.**

- None for RFC 8305. RFC 7050 section 3.1 ("the node SHOULD communicate with a trusted DNS64 server over a secure channel or use DNSSEC"; accepted as the platform's): Apple's own synthesis is used where it exists; elsewhere the discovery asks the system resolver, which is the network's DNS64 and is encrypted only where the platform is set up so (Android's Private DNS, an encrypted-DNS profile, systemd-resolved over TLS); "DNSSEC validation cannot be utilized in the case of a WKP". A forged prefix redirects connections to IPv4 literals and A-only names, and TLS still authenticates the server ([threat model 3.24](../threat-model.md#324-nat64-prefix-discovery-rfc-8305-7-rfc-7050-31)).

## <a id="happy-eyeballs"></a>Happy Eyeballs

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 8305.

**Requirement.** Happy Eyeballs between protocols: the h3/h1.1 race (the address race of each side: the row above, [§3–§7](#s4-tcp-address-race)).

**Recorded status.** ✅ 0.3.0 (🔶 0.2.0 to 0.3.0: HTTP/3 tried the first address only)

**How it is met.**

- a connection establishment race: h3 first, h1.1 on an h3 error or after a head start of 1.5 × sRTT (250 ms without history, clamped to 100 ms–2 s)
- §5 against the race: the attempts are never simultaneous (SHOULD NOT) and h1.1 never starts within 10 ms of h3 (MUST NOT; 0.2.1: on a network without confirmed QUIC it started at once), an explicit `hardDelay` must be 10 ms–2 s (MUST lower bound, SHOULD upper bound; 0.2.1, before any value was taken) or `Duration.INFINITE` (h1.1 only after h3 failed, an explicit choice, bounded by the connect timeout)
- each side races the addresses of the request's one resolution (0.3.0: HTTP/3 too, over QUIC; with `H3Only` there is no h1.1 side and the QUIC race alone reaches a working address)
- once one setup succeeds the other is cancelled (SHOULD) — an h1.1 connection that completed anyway is closed, while a QUIC setup that lost goes on to serve the next requests, as RFC 7838 §2.4 says a client SHOULD use an alternative "as soon as it is available"
- the request goes once, on the winner
- platform network identifiers come through the `networkId` hook

**Tests that pin it.**

- broken per (origin, alternative) with a backoff of 5 min → ×2 → 2 days, reset on a `networkId` change — `ProtocolRaceTest.*` (`.minimumHeadStartOnUnconfirmedNetwork`, `.negative_hardDelayOutsideRfc8305BoundsIsRefused`), `BrokenAltSvcTest.*`, `ClientFallbackTest.*`, `ClientHappyEyeballsTest.h3RacesTheAddressesOfAName`

**Open items.**

- None.
