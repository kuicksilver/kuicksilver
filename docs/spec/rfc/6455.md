# RFC 6455 — The WebSocket Protocol

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="s4-1-websocket-extensions-in-the-ktor-engines"></a>§4.1, §5.1, §5.2, §9.1; RFC 7692 §6.1; RFC 9220 §3 — WebSocket extensions in the Ktor engines

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 6455 §4.1, §5.1, §5.2, §9.1; RFC 7692 §6.1; RFC 9220 §3 (WebSocket extensions in the Ktor engines).

**Requirement.** The client engine declares `WebSocketExtensionsCapability`, so Ktor's plugin offers and negotiates the installed extensions over HTTP/1.1 and HTTP/3.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- a 101 (or RFC 9220 2xx) that accepts an extension the client did not offer fails the handshake with `WebSocketException`
- both engines check every frame's first byte against what the handshake negotiated: an RSV bit no negotiated extension defines, RSV1 of permessage-deflate on a continuation or control frame, a reserved opcode, or a masked frame from a server / an unmasked one from a client (§5.1) fails the connection with 1002: the engine hands Ktor's session a Close 1002 in place of the bad frame, the session answers it on the wire and reports it as its `closeReason`
- an accepted extension the engine does not know may use every RSV bit

**Tests that pin it.**

- `ClientWebSocketExtensionsTest.*` (h1 and h3), `ClientDeflateKtorTest.*` (JVM, Ktor's `WebSocketDeflateExtension` on both ends), `ServerWebSocketGuardTest.*`

## <a id="s4-1-connecting-through-a-proxy"></a>§4.1 (client: connecting, through a proxy) — connecting, through a proxy

Status: 🔶 since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 6455 §4.1 (client: connecting, through a proxy).

**Requirement.** Step 2: at most one WebSocket connection in the CONNECTING state per remote host (MUST): a WebSocket over HTTP/1.1 holds every IP address its name resolves to, whatever the port ("If multiple connections to the same IP address are attempted simultaneously, the client MUST serialize them"), from the moment the pool gives it a connection or the room to open one (a WebSocket waiting for a pool slot holds nothing) until the server answers the handshake, so a second one to the same address waits whatever name and port it uses (0.2.1; before, both connected at once).

**Recorded status.** 🔶 0.3.0 (PAC: ⬜ 0.3.0)

**How it is met.**

- the answer must arrive within the connect timeout, counted from then, else `ConnectTimeoutException` and the address is free again, so a server that never answers cannot hold the others back for longer
- RFC 9220 WebSockets are streams of an open HTTP/3 connection and open none.
- Step 3 (SHOULD): through a configured proxy the client asks it for a TCP connection — `ws://` and `wss://` in a CONNECT tunnel (item 2; not an absolute-form Upgrade), SOCKS5 CONNECT
- step 4: a proxy error fails the connection (`ProxyException`, MUST)
- step 5: TLS and SNI to the origin inside the tunnel (MUST).
- no PAC script is ever given a URI by the engine, so the step's PAC URI rule has nothing to apply to

**Tests that pin it.**

- `ClientWebSocketConnectingTest.negative_secondHandshakeToTheSameAddressWaitsForTheFirst`, `.negative_handshakeToAnotherPortOfTheAddressWaits`, `.negative_stalledHandshakeTimesOutAndFreesTheAddress`, `.negative_waitingForAPoolSlotHoldsNoAddress`, `h1.WebSocketConnectingTest.*`, `ClientSocksProxyTest.wsThroughHttpProxyUsesConnect`, `.connect407FailsWithProxyException`

**Open items.**

- through an HTTP proxy or a SOCKS5 proxy that resolves names the client cannot know the address, so the key is the name (MUST assume distinct hosts; SHOULD limit pending connections: one per name)
- Open (⬜ 0.3.0): a proxy configured only through a PAC script on Apple and Windows is not used (the resolver does not run PAC, see `proxyResolver`), so step 3's SHOULD is unmet for that configuration
