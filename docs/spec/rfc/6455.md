# RFC 6455 — The WebSocket Protocol

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="s4-1-websocket-extensions-in-the-ktor-engines"></a>§4.1, §5.1, §5.2, §9.1; RFC 7692 §6.1; RFC 9220 §3 — WebSocket extensions in the Ktor engines

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 6455 §4.1, §5.1, §5.2, §9.1; RFC 7692 §6.1; RFC 9220 §3 (WebSocket extensions in the Ktor engines).

**Requirement.** The client engine declares `WebSocketExtensionsCapability`, so Ktor's plugin offers and negotiates the installed extensions over HTTP/1.1 and HTTP/3.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- a 101 (or RFC 9220 2xx) that accepts an extension the client did not offer fails the handshake with `WebSocketException`
- both engines check every frame's first byte against what the handshake negotiated: an RSV bit no negotiated extension defines, RSV1 of permessage-deflate on a continuation or control frame, a reserved opcode, a masked frame from a server / an unmasked one from a client (§5.1), or a 64-bit payload length with its most significant bit set (§5.2: MUST be 0) fails the connection with 1002: the engine hands Ktor's session a Close 1002 in place of the bad frame, the session answers it on the wire and reports it as its `closeReason`
- an accepted extension the engine does not know may use every RSV bit
- a connection that fails inside a frame (also while the guard waits for room, or inflates a compressed message) fails the session's input with the connection's cause, never ends it as if the peer had closed the stream (0.3.0) — `WebSocketFrameGuardTest.negative_aFailureInsideAPayloadFailsTheOutput`, `GuardInflateTest.negative_aFailureInsideACompressedPayloadFailsTheOutput`

**Tests that pin it.**

- `ClientWebSocketExtensionsTest.*` (h1 and h3), `ClientDeflateKtorTest.*` (JVM, Ktor's `WebSocketDeflateExtension` on both ends), `ServerWebSocketGuardTest.*`, `WebSocketFrameGuardTest.negative_lengthWithTopBitClosesWith1002`

## <a id="s4-1-connecting-through-a-proxy"></a>§4.1 (client: connecting, through a proxy) — connecting, through a proxy

Status: 🔶 since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 6455 §4.1 (client: connecting, through a proxy).

**Requirement.** Step 2: at most one WebSocket connection in the CONNECTING state per remote host (MUST): a WebSocket over HTTP/1.1 holds every IP address its name resolves to, whatever the port ("If multiple connections to the same IP address are attempted simultaneously, the client MUST serialize them"), from before it asks the pool for a connection (a WebSocket waiting for the address holds nothing of the pool, and that wait does not count against its connect timeout; a connection the h3/h1 race already opened is used only when the address is free at once, else it goes back to the pool; 0.3.0) until the server answers the handshake, so a second one to the same address waits whatever name and port it uses (0.2.1; before, both connected at once).

**Recorded status.** 🔶 0.3.0 (PAC on Apple and Windows since the open-rows audit of 2026-11; on Apple the engine's own PAC engine since then too; the PAC URI rule is not met on the JVM and Android, and not verified on Windows, see Open items)

**How it is met.**

- the answer must arrive within the connect timeout, counted from then, else `ConnectTimeoutException` and the address is free again, so a server that never answers cannot hold the others back for longer
- RFC 9220 WebSockets are streams of an open HTTP/3 connection and open none.
- Step 3 (SHOULD): through a configured proxy the client asks it for a TCP connection — `ws://` and `wss://` in a CONNECT tunnel (item 2; not an absolute-form Upgrade), SOCKS5 CONNECT
- step 4: a proxy error fails the connection (`ProxyException`, MUST)
- step 5: TLS and SNI to the origin inside the tunnel (MUST).
- a proxy configured by a PAC script or WPAD is used: on Apple platforms the engine runs the script itself
  (`evaluatePac`): a PAC entry of the system settings (a URL, or the script) or, when the settings say "auto discover"
  and CFNetwork gives no PAC entry, WPAD's discovery (DHCP option 252 on macOS, then `wpad.<domain>` down to two labels,
  `wpadCandidates`); the script is downloaded by the engine (`http`, `https`, `file`, at most 1 MiB, cached 30 min) and
  run on JavaScriptCore with the PAC utility functions (`PacContext`, `PAC_UTILS_JS`) under a time limit (`PacRunner`;
  threat model 3.20.3). On Windows WinHTTP runs automatic detection and the PAC URL (`WinHttpGetProxyForUrl`,
  `winHttpPac`); on the JVM and Android the platform's `ProxySelector` does. A script that cannot be fetched or run
  (Apple: within 5 s; Windows: WinHTTP's timeouts of 5 s per step) gives the next setting (on Windows the fixed proxy),
  else a direct connection, with one warning (`PAC_FAILED`)
- the step's PAC rule ("the URI to pass the function MUST be constructed from /host/, /port/, /resource name/, and the
  /secure/ flag using the definition of a WebSocket URI"): the engine passes `ws://` or `wss://`, host, port and resource
  name (`pacTarget`) to the platform's PAC engine, and keeps a WebSocket's answer per resource name, not per host and
  port only. WinHTTP knows only `http` and `https`: when it refuses the WebSocket URI as an unknown scheme
  (ERROR_WINHTTP_UNRECOGNIZED_SCHEME), the same URI goes again as `http://` or `https://`. On Apple platforms the
  script gets the whole URI (`pac.PacEngineAppleTest.theScriptGetsTheWholeWebSocketUri`); CFNetwork's own PAC engine,
  used before, dropped the path and query, which is why the engine no longer uses it

**Tests that pin it.**

- PAC: `ProxyResolverTest.pacEntryIsRunAndItsAnswerPicked`, `.negative_failedPacFallsToTheNextEntryWithAWarning`,
  `.windowsRunsPacBeforeTheFixedProxy`, `.pacTargetIsTheWebSocketUri`, `.webSocketAnswersAreKeptPerResource`,
  `pac.PacEngineAppleTest.*` (the whole WebSocket URI reaches the script; a `file:` script and a plain `http:` one run;
  failures fall to the next entry; the sandbox; a runaway script; the size cap; the cache; WPAD's candidates; answers),
  `pac.PacUtilsAppleTest.*` (each utility function, the `…Ex` ones included) (macOS); the WinHTTP call itself is
  compiled for mingwX64, not run (no Windows host in the test run)
- `ClientWebSocketConnectingTest.negative_secondHandshakeToTheSameAddressWaitsForTheFirst`, `.negative_handshakeToAnotherPortOfTheAddressWaits`, `.negative_stalledHandshakeTimesOutAndFreesTheAddress`, `.aWebSocketWaitingForAPoolSlotHoldsItsAddressOnly`, `.aWebSocketWaitingForTheAddressHoldsNothingOfThePool`, `.aRaceOpenedConnectionIsNotHeldWhileItsWebSocketWaitsForTheAddress`, `.handshakesToTwoAddressesDoNotWait`, `h1.WebSocketConnectingTest.*`, `ClientSocksProxyTest.wsThroughHttpProxyUsesConnect`, `.connect407FailsWithProxyException`

- through an HTTP proxy or a SOCKS5 proxy that resolves names the client cannot know the address, so the key is the
  name (step 2: MUST assume distinct hosts; SHOULD limit pending connections: one per name)

**Open items.**

- The PAC URI rule (MUST) on the JVM and Android: `ProxySelector.select` gets `http://` or `https://`, host and port
  (`ProxyResolver.jvmCommon.kt`), not the WebSocket URI, and the platform's PAC engine (Android's, a JDK's) decides what
  its script sees; meeting it there needs a PAC engine of our own as on Apple, not scheduled.
- Windows: whether WinHTTP passes the path and query of the URI on to the script is not verified (no Windows host in
  the test run).
- iOS has no public API for DHCP options or DNS search domains: WPAD there tries the host name's domain only.
