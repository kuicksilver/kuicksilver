## <a id="s4-1-websocket-extensions-in-the-ktor-engines"></a>§4.1 step 5, §5.1, §5.2, §9.1; RFC 7692 §6.1; RFC 9220 §3 — WebSocket extensions in the Ktor engines

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 6455 §4.1, §5.1, §5.2, §9.1; RFC 7692 §6.1; RFC 9220 §3 (WebSocket extensions in the Ktor engines).

**Requirement.** The client engine declares `WebSocketExtensionsCapability`, so Ktor's plugin offers and negotiates the installed extensions over HTTP/1.1, HTTP/2 (RFC 8441) and HTTP/3. §4.1 step 5: an answer that "indicates the use of an extension that was not present in the client's handshake" fails the connection (MUST). §5.2: RSV1-3 "MUST be 0 unless an extension is negotiated that defines meanings for non-zero values. If a nonzero value is received and none of the negotiated extensions defines the meaning of such a nonzero value, the receiving endpoint MUST _Fail the WebSocket Connection_"; RFC 7692 §6.1: "An endpoint MUST NOT set the "Per-Message Compressed" bit of control frames and non-first fragments of a data message. An endpoint receiving such a frame MUST _Fail the WebSocket Connection_."

**Recorded status.** ✅ 0.3.0

**How it is met.**

- a 101 (or RFC 9220 2xx) that accepts an extension the client did not offer fails the handshake with `WebSocketException`
- both engines check every frame's first byte against what the handshake negotiated: an RSV bit no negotiated extension defines, RSV1 on a continuation or control frame whenever permessage-deflate was negotiated (whatever other extension was too), a reserved opcode, a masked frame from a server / an unmasked one from a client (§5.1), or a 64-bit payload length with its most significant bit set (§5.2: MUST be 0) fails the connection with 1002: the engine hands Ktor's session a Close 1002 in place of the bad frame, the session answers it on the wire and reports it as its `closeReason`
- the bits of another negotiated extension are those its Ktor factory declares (`rsv1`, `rsv2`, `rsv3`); an accepted extension no installed Ktor extension implements (the application's own, through raw headers) may use every RSV bit
- a connection that fails inside a frame (also while the guard waits for room, or inflates a compressed message) fails the session's input with the connection's cause, never ends it as if the peer had closed the stream (0.3.0) — `WebSocketFrameGuardTest.negative_aFailureInsideAPayloadFailsTheOutput`, `GuardInflateTest.negative_aFailureInsideACompressedPayloadFailsTheOutput`

**Tests that pin it.**

- `ClientWebSocketExtensionsTest.*` (h1 and h3), `ClientH2WebSocketTest.negative_unofferedExtensionOrSubprotocolFailsTheHandshake`, `ServerWebSocketH2Test.negative_rsv1WithoutNegotiationClosesWith1002`, `.perMessageDeflateOverH2` (h2), `ClientDeflateKtorTest.*` (JVM, Ktor's `WebSocketDeflateExtension` on both ends), `ServerWebSocketGuardTest.*`, `WebSocketFrameGuardTest.negative_lengthWithTopBitClosesWith1002`, `WebSocketInputRulesTest.negative_rsv1PlacementIsCheckedBesideAnotherExtension`, `.unknownExtensionAllowsEveryBit`

**History.** Before 0.3.0, RSV1 placement was checked only when permessage-deflate was the one extension negotiated, and any other extension allowed every bit (cross-review 2026-11).

## <a id="s4-1-client-handshake"></a>§4.1 steps 2–6, §11.3 (client) — the server's opening handshake

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §4.1: "If the response lacks an |Upgrade| header field or the |Upgrade| header field contains a value that is not an ASCII case-insensitive match for the value "websocket", the client MUST _Fail the WebSocket Connection_"; the same for a |Connection| field without the token "Upgrade"; "If the response lacks a |Sec-WebSocket-Accept| header field or the |Sec-WebSocket-Accept| contains a value other than the base64-encoded SHA-1 of the concatenation of the |Sec-WebSocket-Key| (as a string, not base64-decoded) with the string "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" but ignoring any leading and trailing whitespace, the client MUST _Fail the WebSocket Connection_"; a |Sec-WebSocket-Protocol| that "indicates the use of a subprotocol that was not present in the client's handshake" (step 6) fails it too, as does any answer that "does not conform to the requirements for the server's handshake". §11.3.2–§11.3.4: |Sec-WebSocket-Extensions|, |Sec-WebSocket-Accept| and |Sec-WebSocket-Protocol| "MUST NOT appear more than once in an HTTP response". The key: "The nonce MUST be selected randomly for each connection." RFC 8441 §5 (RFC 9220 §3) drops the key, Accept, Upgrade and Connection, and keeps |Sec-WebSocket-Protocol| and |Sec-WebSocket-Extensions| "as defined in [RFC6455]".

**Recorded status.** ✅ 0.3.0

**How it is met.**

- over HTTP/1.1 the engine sends a key of its own for every connection it sends the handshake on: 16 bytes from OpenSSL's CSPRNG, base64-encoded, in place of the key of Ktor's request body (so a redirect Ktor follows, or a request sent again on a new connection, never repeats a key)
- on a 101 it requires exactly one `Upgrade: websocket` (ASCII case-insensitive), a `Connection` with the token `Upgrade`, and exactly one `Sec-WebSocket-Accept` equal to the base64 SHA-1 of its key and the GUID (surrounding whitespace ignored); over HTTP/1.1 and HTTP/3 alike, at most one `Sec-WebSocket-Extensions` with only offered extensions (step 5), and at most one `Sec-WebSocket-Protocol` naming a subprotocol the request offered
- anything else fails the call with `WebSocketException` ("Handshake exception: …") before a session exists; the connection is closed over HTTP/1.1, the stream reset with CANCEL over HTTP/2 and with H3_REQUEST_CANCELLED over HTTP/3
- a 101 to a request that asked for no upgrade fails with `ParserException` (RFC 9110 §15.2.2)

**Tests that pin it.**

- `ClientWebSocketHandshakeTest.negative_wrongAcceptFailsTheHandshake`, `.negative_missingAcceptFailsTheHandshake`, `.negative_twoAcceptsFailTheHandshake`, `.negative_missingUpgradeFailsTheHandshake`, `.negative_otherUpgradeFailsTheHandshake`, `.negative_missingConnectionFailsTheHandshake`, `.negative_connectionWithoutUpgradeTokenFailsTheHandshake`, `.negative_unofferedSubprotocolFailsTheHandshake`, `.negative_subprotocolWhenNoneOfferedFailsTheHandshake`, `.negative_twoSubprotocolsFailTheHandshake`, `.negative_twoExtensionsFieldsFailTheHandshake`, `.negative_eachConnectionGetsANewKey`, `.validAnswerOpensTheSession`, `ClientWebSocketExtensionsTest.negative_unofferedSubprotocolFailsHandshakeH3`

**History.** Before 0.3.0 only the status and the extensions were checked: Ktor's client plugin checks the status alone, and the engines never called `WebSocketContent.verify()`; the key was Ktor's, the same for every connection of one request (cross-review 2026-11, W3-1, W3-22).

## <a id="s4-2-server-handshake"></a>§4.2.1, §4.2.2, §11.3.1, §11.3.5 (server); RFC 8441 §5 — the client's opening handshake

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §4.2.1: "If the server, while reading the handshake, finds that the client did not send a handshake that matches the description below …, the server MUST stop processing the client's handshake and return an HTTP response with an appropriate error code (such as 400 Bad Request)"; the description includes "A |Sec-WebSocket-Key| header field with a base64-encoded … value that, when decoded, is 16 bytes in length" and "A |Sec-WebSocket-Version| header field, with a value of 13". §4.2.2, /version/: "If this version does not match a version understood by the server, the server MUST abort the WebSocket handshake described in this section and instead send an appropriate HTTP error code (such as 426 Upgrade Required) and a |Sec-WebSocket-Version| header field indicating the version(s) the server is capable of understanding." §11.3.1 and §11.3.5: the key and the version "MUST NOT appear more than once in an HTTP request". RFC 8441 §5: the version is used in the Extended CONNECT "as defined in [RFC6455]"; the key is not processed.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- when the application answers a WebSocket upgrade request with Ktor's upgrade, the engine checks the request first, before anything is committed: over HTTP/1.1 exactly one `Sec-WebSocket-Key` that decodes from base64 to 16 bytes, and on both protocols exactly one `Sec-WebSocket-Version`; otherwise the answer is `400 Bad Request`
- a version other than 13 gets `426 Upgrade Required` over HTTP/1.1, with `Upgrade: websocket` (RFC 9110 §15.5.22 requires it in a 426), and `400` over HTTP/2 and HTTP/3, which have no `Upgrade` field (RFC 9113 §8.2.2, RFC 9114 §4.2)
- every refusal carries `Sec-WebSocket-Version: 13` and a short text; the application's WebSocket handler does not run
- over HTTP/3 the engine no longer adds a `sec-websocket-version` the client did not send
- an HTTP/1.0 upgrade request is not an upgrade (RFC 9110 §7.8, since 0.2.1); a request a WebSocket route does not take is answered by the application as any other

**Tests that pin it.**

- `ServerWebSocketHandshakeTest.negative_missingKeyGets400`, `.negative_keyNotSixteenBytesGets400`, `.negative_twoKeysGet400`, `.negative_missingVersionGets400`, `.negative_twoVersionFieldsGet400`, `.negative_otherVersionGets426`, `.negative_missingVersionGets400H3`, `.negative_otherVersionGets400H3`, `ServerWebSocketH2Test.negative_versionOtherThan13IsRefused` (HTTP/2), `.validHandshakeIsUpgraded`, `.negative_unreadableOwnAnswerClosesWith1011` (an answer of its own the engine cannot read: Close 1011 instead of a silent end)

**History.** Before 0.3.0 Ktor's route checked only `Connection` and `Upgrade`, so a request without a key got a 101 without `Sec-WebSocket-Accept`, and version 8 got a 101; over HTTP/3 a missing version was made up as 13 (cross-review 2026-11, W3-5).

## <a id="s5-sending-frames"></a>§5.1, §5.3, §5.4, §5.6, §7.4 (sending) — the frames the engines send

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §5.1: "A server MUST NOT mask any frames that it sends to the client." §5.3: "the masking key MUST be derived from a strong source of entropy, and the masking key for a given frame MUST NOT make it simple for a server/proxy to predict the masking key for a subsequent frame." §5.4: "A fragmented message consists of a single frame with the FIN bit clear and an opcode other than 0, followed by zero or more frames with the FIN bit clear and the opcode set to 0, and terminated by a single frame with the FIN bit set and an opcode of 0." §5.6: a text message's "whole message MUST contain valid UTF-8". §7.4.1: 1005, 1006 and 1015 "MUST NOT be set as a status code in a Close control frame by an endpoint"; §5.5.1: the reason is UTF-8.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- Ktor's session writes into the engine's output guard (`guardWebSocketOutput`), which hands each frame on rewritten as it passes, in the writer's own coroutine
- client: Ktor writes unmasked frames and the guard masks every frame with a new 4-byte key from OpenSSL's CSPRNG (`RAND_bytes`, drawn 64 keys at a time); Ktor draws its keys from `kotlin.random.Random`, which is not a CSPRNG on any platform
- server: no frame is masked, whatever Ktor's `WebSockets { masking }` says (a key Ktor set is removed)
- the frames after the first of a fragmented message go out with opcode 0 (Ktor 3.6.1's common writer, used on Kotlin/Native, gives each fragment the message's opcode)
- a Close whose code an endpoint may not send (0-999, 1004-1006, 1015, 1016-2999, 5000 and above) goes out with no body ("no status code"), one whose reason is not UTF-8 keeps its code without the reason
- compressed messages go out as RFC 7692 §6.1 wants, RSV1 on the first frame only, whichever extension compressed them: this library's `PerMessageDeflate` sends them so; Ktor's `WebSocketDeflateExtension` compresses each fragment on its own and sets RSV1 on all of them, so the output guard (which recognises it by type, so an Android release build's renaming does not matter; this follows Ktor 3.6.x's extension, with `ClientDeflateKtorTest` as the canary) gives each non-final fragment its 0x00 0x00 0xff 0xff back (the fragments become one DEFLATE stream) and clears RSV1 on the continuations; a message it cannot make right (a fragment Ktor left uncompressed, or RSV1 on a continuation from another sender) is refused before that frame goes out
- text is checked as UTF-8 as it passes; a message that is not is never sent whole: the write fails with `ProtocolViolationException`. The last piece of a text message (its last bytes, or for a compressed one its last compressed piece, once its decompression ended) is held back until the whole message is known to be UTF-8, so the peer never receives an invalid message whole. A refusal before a frame's header (the RFC 7692 refusals above, an empty last frame) fails the connection as §7.1.7 asks: a Close with 1011, then the end of the stream (FIN), and nothing after the Close; one inside a frame whose header is out leaves no place for a Close, and the connection is reset. A text message this library's `PerMessageDeflate` compresses is checked by the extension before compression (the same failure, on every engine); one another extension compresses is inflated on the side by the output guard, the whole message as one stream (each fragment on its own for Ktor's), and checked there (RFC 7692 §6: after decompression the payload is "subject to the constraints for the original data type again"). Ktor's `Frame.Text(String)` and `send(String)` always encode UTF-8; this concerns `Frame.Text(fin, ByteArray)` with the application's own bytes
- after this side's own Close (§5.5.1: "After sending a Close frame, the application MUST NOT send any more data frames") data frames are discarded, not sent and without failing the write, so a session that ends in order still does; control frames still pass. Ktor's sessions send nothing after their Close; this bounds what an application's own `ProtocolUpgrade` can write once an HTTP/2 engine stopped holding its writer at the peer's window (the lead is released at the own Close). On the server, once the client's Close arrived, the message in progress may finish (its continuations up to its FIN: §1.4, an endpoint "may delay sending a Close frame until its current message is sent", and §7.1.2) but a data frame that starts a new message is discarded with its continuations, so what goes out between the client's Close and the server's own is bounded by one message (every server engine: the rule is in the output guard, told of the client's Close by the input guard; this also drops new messages a Ktor session queued before the client's Close that reach the guard after it)

**Tests that pin it.**

- `WebSocketOutputGuardTest.negative_clientFramesGetFreshMaskingKeys`, `.negative_serverFramesAreNeverMasked`, `.negative_laterFragmentsAreSentAsContinuations`, `.ktorRawSessionThroughTheGuard`, `.negative_closeWithAForbiddenCodeGoesOutWithoutABody`, `.negative_closeReasonNotUtf8IsDropped`, `.negative_textThatIsNotUtf8IsNotSent`, `.negative_compressedTextOfAnotherExtensionIsChecked`, `.negative_ktorStyleFragmentedMessageIsMadeRfc7692`, `.negative_uncompressedFragmentInsideAKtorStyleMessageIsRefused`, `.negative_rsv1OnAContinuationIsRefused`, `.rfc7692FragmentedMessageIsInflatedAsOneStream`, `.ownDeflateMessagesPassAsTheyAre`, `.negative_textEndingInsideACharacterNeverArrivesWhole`, `.negative_compressedTextEndingInsideACharacterNeverArrivesWhole`, `.negative_emptyLastFrameOfInvalidTextClosesWith1011`, `.textOfAnApplicationExtensionIsNotChecked`, `.negative_dataFramesAfterTheOwnCloseAreDiscarded`, `ServerWebSocketH2Test.negative_newMessagesAfterTheClientsCloseAreDiscarded`, `.frameSplitAcrossFlushes`, `.outputWrittenByteByByte`, `SentCompressionJvmTest.*`, `ClientDeflateKtorTest.ktorsFragmentedCompressedMessageGoesOutAsRfc7692`, `PerMessageDeflateTest.negative_compressedTextThatIsNotUtf8IsRefused`, `ClientDeflateKtorTest.negative_invalidUtf8CompressedByKtorsExtensionIsNotSent`, `ClientWebSocketHandshakeTest.negative_clientEngineMasksEveryFrameWithANewKey`, `ClientH3WebSocketTest.negative_clientEngineMasksEveryFrameWithANewKeyH3`, `ServerWebSocketHandshakeTest.negative_serverNeverMasks`, `.negative_serverNeverMasksH3`

**Scope.** RFC 6455 puts no duty on the engine for the payload of an extension the application brings with its own specification (section 9: an extension defines what its data is): the engines check the base protocol and permessage-deflate (RFC 7692), whichever implementation negotiated it. With another extension agreed, text messages are not checked, in either direction, and a payload it transforms without an RSV bit passes as it is; Close reasons are always checked.

**History.** Before 0.3.0 the masking keys were Ktor's, a server configured with `masking = true` masked its frames, and a fragmented message sent from Kotlin/Native went out with the message's opcode on every fragment (cross-review 2026-11, W3-6, W3-7, W3-23).

## <a id="s5-receiving-frames"></a>§5.4, §5.5, §5.5.1, §5.6, §7.4, §8.1 (receiving) — control frames, fragments, Close frames and UTF-8

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §5.5: "All control frames MUST have a payload length of 125 bytes or less and MUST NOT be fragmented." §5.4: continuations follow a first fragment and messages do not interleave. §5.5.1: "If there is a body, the first two bytes of the body MUST be a 2-byte unsigned integer (in network byte order) representing a status code with value /code/ defined in Section 7.4"; "If an endpoint receives a Close frame and did not previously send a Close frame, the endpoint MUST send a Close frame in response." §7.4.2: 0-999 "are not used"; 1000-2999 "are reserved for definition by this protocol, its future revisions, and extensions specified in a permanent and readily available public specification". §8.1: "When an endpoint is to interpret a byte stream as UTF-8 but finds that the byte stream is not, in fact, a valid UTF-8 stream, that endpoint MUST _Fail the WebSocket Connection_."

**Recorded status.** ✅ 0.3.0

**How it is met.**

- the frame guard in front of Ktor's session fails the connection with 1002 for a control frame with FIN clear or over 125 bytes, a continuation outside a fragmented message, a new message inside one, a Close body of 1 byte, and a Close code an endpoint may not send (valid: 1000-1003, 1007-1011, 1012-1014 as registered with IANA since, 3000-4999); these were left to Ktor's readers, whose common (Kotlin/Native) reader closes `incoming` before it queues its 1002, so an application closing at that moment sent 1000 first
- a 16-bit or 64-bit length that is not the minimal encoding (§5.2: "the minimal number of bytes MUST be used to encode the length"; §10.7 lets the recipient fail the connection) fails it with 1002
- the engines decompress every permessage-deflate message themselves, whichever extension negotiated it (this library's `PerMessageDeflate`, or Ktor's `WebSocketDeflateExtension`, by the parameters of the answer), and hand Ktor's session the plain frames, which Ktor's extension passes on unchanged
- a text message that is not UTF-8 as a whole (a character split across fragments is fine; a message that ends inside one is not), checked after decompression, and a Close reason that is not UTF-8 fail it with 1007; the reason no longer reaches Ktor's `CloseReason`, whose length check failed inside the session (1006 and no Close sent)
- a text message is checked as it streams and handed on unmasked in frames of at most 64 KiB, the first with its opcode and the rest continuations; none of the bytes that broke it is handed on
- a valid Close is answered by Ktor's session with the same code (§5.5.1)

**Tests that pin it.**

- `WebSocketInputRulesTest.negative_nonMinimalLengthClosesWith1002`, `.inputFedByteByByte`, `.checkedTextIsReframedInPiecesOf64KiB`, `.negative_fragmentedControlFrameClosesWith1002`, `.negative_controlFrameOver125BytesClosesWith1002`, `.negative_continuationOutsideAMessageClosesWith1002`, `.negative_newMessageInsideAFragmentedOneClosesWith1002`, `.negative_closeWithAReservedOrUnusedCodeClosesWith1002`, `.closeWithAValidCodePasses`, `.negative_closeWithAOneByteBodyClosesWith1002`, `.negative_closeReasonNotUtf8ClosesWith1007`, `.negative_invalidUtf8TextClosesWith1007`, `.negative_invalidUtf8AcrossFragmentsClosesWith1007`, `.negative_textEndingInsideACharacterClosesWith1007`, `.negative_overlongSurrogateAndOutOfRangeSequencesClose1007`, `.validUtf8SplitAcrossMaskedFragmentsPasses`, `.binaryIsNotCheckedForUtf8`, `.negative_invalidUtf8InACompressedTextClosesWith1007`, `ServerWebSocketHandshakeTest.negative_invalidUtf8ClosesWith1007`, `ClientDeflateKtorTest.negative_compressedInvalidUtf8ThroughKtorsExtensionClosesWith1007`, `ClientWebSocketExtensionsTest.rsv1OnFirstFrameWithDeflateNegotiatedPasses`

**Scope.** RFC 6455 puts no duty on the engine for the payload of an extension the application brings with its own specification (section 9: an extension defines what its data is): the engines check the base protocol and permessage-deflate (RFC 7692), whichever implementation negotiated it. With another extension agreed, text messages are not checked, in either direction, and a payload it transforms without an RSV bit passes as it is; Close reasons are always checked.

**History.** Before 0.3.0 no endpoint checked UTF-8 (1007 was never sent), and a Close with 1005, 1006, 1015 or an unused code was echoed or, with 1006, left unanswered (cross-review 2026-11, W3-2, W3-4, W3-21).

## <a id="s10-4-limits"></a>§10.4 — frame and message size limits

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** §10.4: "Implementations that have implementation- and/or platform-specific limitations regarding the frame size or total message size after reassembly from multiple frames MUST protect themselves against exceeding those limits. … Such an implementation SHOULD impose a limit on frame sizes and the total message size after reassembly from multiple frames."

**Recorded status.** ✅ 0.3.0

**How it is met.**

- both engines take `webSocketMaxMessageSize` (16 MiB by default, as `PerMessageDeflate`'s `maxInflatedMessageSize`): an uncompressed frame whose header claims more, or that takes its message past it, fails the connection with 1009 from its header, before any of its payload is read — Ktor's JVM reader allocates a frame's whole claimed length at once, so a 14-byte header claiming 2 GiB no longer reaches it
- a compressed message (whichever extension negotiated permessage-deflate) is held to the smaller of the two limits, counted as it inflates, in pieces of 64 KiB ([RFC 7692, decompression limit](7692.md#decompression-limit)); its compressed frames are held to 8 times that limit plus 64 KiB in all, from their headers, so a compressed frame claiming more is refused before its payload is read too
- over HTTP/1.1, HTTP/2 and HTTP/3, as client and as server; Ktor's `WebSockets { maxFrameSize }` applies on top

**Tests that pin it.**

- `WebSocketInputRulesTest.negative_frameOverTheLimitClosesWith1009FromItsHeader`, `.negative_compressedFrameOverTheCompressedBoundClosesWith1009FromItsHeader`, `.negative_fragmentedMessageOverTheLimitClosesWith1009`, `.messageAtTheLimitPasses`, `.negative_compressedMessageOverTheLimitClosesWith1009`, `ClientWebSocketHandshakeTest.negative_frameOverTheLimitClosesWith1009`, `ServerWebSocketHandshakeTest.negative_frameOverTheLimitClosesWith1009`, `.negative_messageOverTheConfiguredLimitClosesWith1009`

**History.** Before 0.3.0 only compressed messages had a limit: the engines passed Ktor no `maxFrameSize`, so its defaults applied (`Long.MAX_VALUE` on the server, `Int.MAX_VALUE` on the client) (cross-review 2026-11, W3-3).

## <a id="s4-1-connecting-through-a-proxy"></a>§4.1 (client: connecting, through a proxy) — connecting, through a proxy

Status: 🔶 since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 6455 §4.1 (client: connecting, through a proxy).

**Requirement.** Step 2: at most one WebSocket connection in the CONNECTING state per remote host (MUST): a WebSocket holds its URL's host name and the IP address its connection actually goes to, whatever the port ("If multiple connections to the same IP address are attempted simultaneously, the client MUST serialize them ... even if the remote host is known by another name"): over HTTP/1.1 the name and the addresses of the families its resolution answered with (one that stalls is not waited for past the 50 ms Resolution Delay of RFC 8305) from before it asks the pool for a connection (a WebSocket waiting for the address holds nothing of the pool, and that wait does not count against its connect timeout; a connection the h3/h1 race already opened is used only when the address is free at once, else it goes back to the pool; 0.3.0) until the server answers the handshake, and, once it has its connection, that connection's own address too (taken without waiting: when another WebSocket holds it, the connection goes back and this one waits for every key, that one too), so a second one to the same name, or to the same address under any name and port, waits (0.2.1; before, both connected at once; 0.3.0: the name and the connection's own address, as Happy Eyeballs may connect to an address of a family that answered late).

**Recorded status.** 🔶 0.3.0 (PAC on Apple and Windows since the open-rows audit of 2026-11, on Apple with the engine's own PAC engine; the PAC URI rule is met for `ws`, and for `wss` only on opt-in: by default a `wss` URI reaches the script as its origin, an owner-approved security deviation (2026-11-13), see "The PAC URI rule and its deviation" below)

**How it is met.**

- the answer must arrive within the connect timeout, counted from then, else `ConnectTimeoutException` and the address is free again, so a server that never answers cannot hold the others back for longer
- a WebSocket over HTTP/3 (RFC 9220) is CONNECTING from its Extended CONNECT until the server answers it: it holds the URL's name and the address of the QUIC connection it uses (no lookup), shared with HTTP/1.1, for that time, so a second WebSocket to the host over either protocol waits for it; the answer must come within the connect timeout, else `ConnectTimeoutException` and the address is free again (0.3.0; before, HTTP/3 handshakes to one host ran at once)
- a WebSocket over HTTP/2 (RFC 8441) is a stream of an HTTP/2 connection that is open already and opens none; it holds the same per-address lock from before its Extended CONNECT until the server answers it, within the connect timeout, as over HTTP/1.1 and HTTP/3
- Step 3 (SHOULD): through a configured proxy the client asks it for a TCP connection — `ws://` and `wss://` in a CONNECT tunnel (item 2; not an absolute-form Upgrade), SOCKS5 CONNECT
- step 4: a proxy error fails the connection (`ProxyException`, MUST)
- step 5: TLS and SNI to the origin inside the tunnel (MUST).
- PAC and WPAD, where they run:
  - Apple platforms: the engine's own PAC engine (`evaluatePac`): a PAC entry of the system settings (a URL, or the
  script) or, when the settings say "auto discover" and CFNetwork gives no PAC entry, WPAD's discovery
  (`wpadCandidates`: DHCP option 252 on macOS, `http` or `https` only; then `wpad.<domain>` for each configured DNS
  search domain exactly, never a parent domain; then `http://wpad/wpad.dat`, which the system resolver completes with
  its search domains; iOS gives neither DHCP options nor search domains through an API Kotlin/Native binds, so there
  only the last); the script is downloaded by the engine (`http`, `https`, `file`; the body read only up to 1 MiB;
  one download per URL at a time, a cancelled lookup leaving the others waiting; cached 30 min, a failed or timed-out
  one 1 min) and run on JavaScriptCore with the
  PAC utility functions (`PacContext`, `PAC_UTILS_JS`), each run limited to 2 s from its start, its DNS lookups
  bounded within that (`PacRunner`, `PacDns`; threat model 3.20.3); a lookup waits at most 5 s, each WPAD candidate
  getting a share of it. An answer naming only proxies the engine cannot use (`HTTPS`, `SOCKS4`) fails closed: the
  next setting with a warning (`PAC_UNSUPPORTED`), and with none the request fails instead of going direct. A WPAD
  discovery that found no script is logged once at Info (`WPAD_NOT_FOUND`), as on Windows.
  - Windows: WinHTTP runs automatic detection (WPAD) and the PAC URL (`WinHttpGetProxyForUrl`, `winHttpPac`); a lookup
  waits for WinHTTP's call at most 5 s (`BoundedPac`; WinHTTP's own timeouts of 5 s bound only the steps of the
  script's download, and its synchronous call cannot be cancelled, so a call still running then ends on its own thread
  with its answer dropped; at most 4 calls run at once, and none starts while one that overran still runs, the
  counts taken atomically before a call starts); a WPAD detection that found no script is logged once
  at Info (`WPAD_NOT_FOUND`; automatic detection is on by default on Windows) and remembered for 5 minutes
  (`WpadFailures`). Not verified at runtime (no Windows host in the test run).
  - JVM and Android: the platform's `ProxySelector` (Android's `PacProxySelector`; the JDK's selector with
  `java.net.useSystemProxies` hands the OS only scheme and host).
  - Everywhere: a script that cannot be fetched or run in time gives the next setting (on Windows the fixed proxy), else
  a direct connection, with one warning (`PAC_FAILED`)
- the step's PAC rule, see "The PAC URI rule and its deviation" below: `ws` met, `wss` met only with
  `pacFullWebSocketUrl`; the engine keeps a WebSocket's answer per resource name, not per host and port only. WinHTTP
  knows only `http` and `https`: when it refuses a WebSocket URI as an unknown scheme
  (ERROR_WINHTTP_UNRECOGNIZED_SCHEME), the same URI goes again as `http://` or `https://`. On the JVM and Android
  `ProxySelector.select` gets the WebSocket's resource name (`selectorUri`), with `ws` mapped to `http` and `wss` to
  `https`: the selectors know no other scheme (the JDK's gives `ws` and `wss` no proxy at all). A selector the
  application installs that runs PAC gets the whole URI.

**The PAC URI rule and its deviation (owner-approved security deviation, 0.3.0).** RFC 6455 section 4.1, step 3:

> For the purpose of proxy autoconfiguration scripts, the URI to pass the function MUST be constructed from /host/,
> /port/, /resource name/, and the /secure/ flag using the definition of a WebSocket URI as given in Section 3.

The rule dates from 2011. In 2016 the class of attack it walks into was fixed in the platforms: a PAC script can send
any string it is given out through `dnsResolve("<data>.attacker.example")`, and the script is code from the network
(a WPAD answer on the local network, a plain-`http` PAC URL), so a path or query that carries a token leaks to whoever
wrote the script.

- CVE-2016-3763 (Android): "net/PacProxySelector.java in the Proxy Auto-Config (PAC) feature in Android 4.x before
  4.4.4, 5.0.x before 5.0.2, 5.1.x before 5.1.1, and 6.x before 2016-07-01 does not ensure that URL information is
  restricted to a scheme, host, and port, which allows remote attackers to discover credentials by operating a server
  with a PAC script" (NVD). Since then `android.net.PacProxySelector` replaces the path of every non-`http` URI with `/`
  ("Strip path and username/password from URI so it's not visible to PAC script. The path often contains credentials
  the app does not want exposed to a potentially malicious PAC script."; AOSP `frameworks/base`, main).
- CVE-2016-5134 (Chrome before 52.0.2743.82, "a related issue to CVE-2016-3763", NVD): Chromium commit
  81357b39c643fc746517fd6ce5cb2076b7ddc3f4 ("Sanitize https:// URLs before sending them to PAC scripts", 2016-05-21).
  Chromium's `SanitizeUrlForProxyResolution` (net/proxy_resolution/proxy_resolution_url_sanitizer.cc) clears user
  name, password and fragment, and for a cryptographic scheme (`https`, `wss`: `GURL::SchemeIsCryptographic`) the path
  and query; it runs on every URL before the resolver, WebSocket ones included (the stream factory resolves the
  `ws`/`wss` URL itself). net/docs/proxy.md: "Effectively `url` will be limited to a `scheme://host:port/` style
  URL", "There is currently no option to turn off sanitization of URLs passed to PAC scripts (removed in Chrome 75)",
  and `http://` URLs keep path and query.
- Firefox strips the path of every URL by default (`network.proxy.autoconfig_url.include_path`, default `false`,
  modules/libpref/init/all.js; netwerk/base/ProxyAutoConfig.cpp keeps "the initial slash").

The Android and Chrome behaviour is a deliberate security fix of those platforms, not a defect, and the engine now
follows the same rule by default (`pacTarget`, on Apple platforms and Windows):

| URL | The script gets (default) | With `pacFullWebSocketUrl`, the settings' own script |
|---|---|---|
| `wss://h:8443/chat?token=x` | `wss://h:8443/` | `wss://h:8443/chat?token=x` |
| `ws://h/chat?room=1` | `ws://h/chat?room=1` | the same |
| `https://h/p?q` | `https://h/` | the same |
| `http://h:8080/p?q` | `http://h:8080/` | the same |

The URI is built as Chromium builds it: no user info or fragment, the host in lower case, a default port left out
(the `host` argument is in lower case too, `pacHost`).
`ws` keeps its resource name, so the rule is met there, as Chromium and Android keep the path of plain URLs (whoever
can serve the script can read a `ws://` request on the wire anyway). `http` and `https` requests give the origin
(RFC 6455 says nothing of them): `https` as in the browsers; `http` because the engine keeps answers per scheme, host
and port (Chromium and Android pass an `http` path, Firefox strips it). For `wss` the rule is met only when the
application sets `KuicksilverEngineConfig.pacFullWebSocketUrl` (*experimental*, off by default), and then only for the
script the system settings name, and only when it is out of the local network's reach (`pacUrlIsPrivate`): on Apple
platforms a PAC entry whose script is the settings' own (`ProxyAutoConfigJavaScript`), or whose URL is the settings'
own (`ProxyAutoConfigURLString`, compared as CFNetwork's `absoluteString` with the settings' string, exactly; a
mismatch gives the origin) and `https` or local `file`, with `ProxyAutoConfigEnable` on (`applePacTarget`); on Windows the
settings' "Use setup script" URL when `https` or local `file` (`winPacTarget`). A script found by WPAD (automatic detection,
DHCP option 252, `wpad.<domain>`) or fetched over plain `http` never gets more than the origin, whatever the setting
says: a LAN attacker can serve either. "Local `file`" is `file:///…` or `file://localhost/…`; a `file:` URL with a
host (`file://srv/share/p.pac`, the UNC form `file:////srv/…`) is fetched over SMB from that host and counts as remote.

**Open items.**

- The PAC URI rule for `wss` (MUST) is not met by default: the deviation above, approved by the owner (2026-11-13) and
  listed in the 0.3.0 release notes. With `pacFullWebSocketUrl` it is met on Apple platforms (and on Windows if WinHTTP
  passes the URI on, see below) for the settings' own script.
- Where the platform's selector runs PAC (JVM and Android), the platform decides, checked against their sources:
  - Android (`android.net.PacProxySelector`, API 35 and 36.1 sources, and main): for any scheme but `http` it replaces
  the path with `/` before the PAC service sees the URL (the CVE-2016-3763 fix above). A `ws://` WebSocket, given as
  `http://…/resource?query`, reaches the script whole; a `wss://` one reaches it as `https://host:port/`, the same rule
  the engine follows; `pacFullWebSocketUrl` does not apply there.
  - The JDK's `sun.net.spi.DefaultProxySelector` (JDK 21 sources): `select` passes only the scheme and the host to the
  native `getSystemProxies(protocol, host)`, so whatever PAC the OS settings run with `java.net.useSystemProxies` (on
  Windows WinHTTP's) sees no port, path or query. The native part was not read (not in `src.zip`); without
  `useSystemProxies` the JDK runs no PAC.
  - In both, the scheme is `http`/`https`, not `ws`/`wss`, because the selectors know no other.
- Windows: whether WinHTTP passes the path and query of a whole URI (the opt-in) on to the script, or strips them as
  browsers do, is not verified (no Windows host in the test run; Microsoft's `WinHttpGetProxyForUrl` page says
  nothing of it). By default the engine passes the origin of `wss` and `https` anyway. A manual check is ready (`WinPacUrlCheckTest` in mingwTest with the echo script
  `tools/check/win-pac-echo.pac`; steps in [win-pac-check.md](../../../tools/check/win-pac-check.md)) and has not run yet.
- iOS: WPAD tries only `http://wpad/wpad.dat`, which the system resolver completes with its search domains: iOS has no
  public API for DHCP options, and libresolv's `res_ninit` (whose state lists the search domains) is in the SDK but has
  no Kotlin/Native binding.
