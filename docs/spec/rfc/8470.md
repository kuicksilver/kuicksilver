## <a id="http-3-over-0-rtt"></a>RFC 9114 §7.2.4.2 — HTTP/3 over 0-RTT

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 8470; RFC 9114 §7.2.4.2.

**Requirement.** HTTP/3 over 0-RTT.

Quoted: "settings MUST be sent as soon as the transport is ready to send data".

**Recorded status.** ✅ 0.2.0

**How it is met.**

- the client sends its SETTINGS at once, in 0-RTT too (§7.2.4.2 "settings MUST be sent as soon as the transport is ready to send data"; after a rejected 0-RTT on new control and QPACK streams, 0.2.1), sends early only safe methods without a body that opted in, retries a 425 once
- the client side of §7.2.4.2: "Clients SHOULD store the settings the server provided in the HTTP/3 connection where
  resumption information was provided": once the server's SETTINGS arrive, the client keeps them (reserved identifiers
  left out) with every session ticket that connection received or receives (`QuicConnection.rememberWithTickets`,
  internal API; stored with the transport parameters the ticket remembers). A 0-RTT connection resumed with such a
  ticket reads them back (`rememberedApplicationData`) and complies with them until the server's own SETTINGS arrive
  ("A client MUST comply with stored settings ... when attempting 0-RTT"): SETTINGS_MAX_FIELD_SECTION_SIZE bounds what
  it sends; QPACK stays static-only and Extended CONNECT and datagrams wait for the new SETTINGS, which is within any
  stored values. A ticket without stored settings gets the defaults, as before.
- the two checks of §7.2.4.2 after an accepted 0-RTT (`StoredSettings.incompatibility`): new SETTINGS "not compatible
  with the previously specified settings" (a lower limit, a feature turned off, another non-zero
  SETTINGS_QPACK_MAX_TABLE_CAPACITY, RFC 9204 §3.2.3; every setting the client understands is compared, also one that
  was stored with its default or not stored at all, so a SETTINGS_MAX_FIELD_SECTION_SIZE that was unlimited and now
  is not counts as lower), and a SETTINGS frame that omits a setting the client
  understands that was stored with a non-default value, end the connection with `H3_SETTINGS_ERROR`
- the server's side of §7.2.4.2: every value of our SETTINGS frame (GREASE aside) is part of the early-data context bound into our tickets (`Http3Settings.earlyDataContext`), so a ticket issued under other SETTINGS gets no 0-RTT ("MUST NOT accept 0-RTT data" unless compatible: we require them equal); our SETTINGS frame always carries every value that differs from its default
- the server binds SETTINGS into tickets and holds non-replayable early requests until the handshake (or answers 425 under `Reject425`); a request answered 425, or held for a handshake that then failed, is forgotten at once (its stream, its PRIORITY_UPDATE and datagram routing), not when the connection ends
- §5.1: the Ktor server engine treats a request a gateway marked `Early-Data` (any instance or value) as early over HTTP/1.1 and HTTP/3 — `receivedEarly` is true, a request the policy does not declare replayable gets 425 (0.2.0)

**Tests that pin it.**

- `http3.runtime.EarlyDataTest.*` (`negative_unsafeMethodNotProcessedInEarlyData`, `reject425PolicyAndOneRetry`, `clientSendsSettingsIn0Rtt`, `rejectedZeroRttReopensTheControlAndQpackStreams`, `liveCriticalStreamsSurviveARejectionNotedWhileTheyAreSetUp`, `anAttemptTheRejectionInterruptsIsMadeAgain`, `controlFramesOfTheDroppedControlStreamAreSentAgainWhenStillWanted`, `aControlWriteInTheRejectionWindowWaitsInsteadOfSpinning`, `rejectionBookkeepingRunsOnTheSessionDispatcher`, `h3DatagramChangeInvalidatesEarlyData`, `storedSettingsBindTheZeroRttRequests`, `negative_settingsIncompatibleWithTheStoredOnesAreSettingsError`), `http3.runtime.StoredSettingsTest.*`, `http3.Http3SettingsTest.earlyDataContextCoversEveryValueOfOurSettings`, `kuicksilver-quic` `core.ZeroRttTest.applicationDataRidesWithTheRememberedParameters`, `ktor.client.ClientEarlyDataTest`, `ktor.server.ServerEarlyDataHeaderTest.*`

## <a id="s4-client-0-rtt-race-and-fallback"></a>§4; RFC 7838 §2.4; RFC 8305 §5 — client 0-RTT, race and fallback

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 8470 §4; RFC 7838 §2.4; RFC 8305 §5 (client 0-RTT, race and fallback).

**Requirement.** With `http3 { earlyData = true }` a 0-RTT connection wins the h3/h1 race before its handshake only on a network where QUIC was confirmed (elsewhere it must complete the handshake, as Chromium requires confirmation).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- network confirmation, the alternative's "working" mark and the remembered RTT wait for the handshake
- the connect timeout bounds the 0-RTT handshake (the handshake timer is cut to it), so a GET sent early on a path that dropped UDP falls back to HTTP/1.1 within it
- a request that waits for the handshake (unsafe method or a body) and sees it fail was never sent and falls back like a failed setup (`H3NotSent`), POST included (before 0.2.0: a 0-RTT start won every race, confirmed QUIC and stored the initial RTT; a blocked path held a GET for the 10 s handshake timeout; a POST failed without fallback)

**Tests that pin it.**

- `ClientEarlyDataTest.udpBlockedWith0RttFallsBackWithinConnectTimeout`, `.postWaitingForAFailedHandshakeFallsBack`, `.earlyConnectionDoesNotWinTheRaceOnAnUnconfirmedNetwork` (JVM)
