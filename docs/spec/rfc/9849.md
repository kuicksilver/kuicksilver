## <a id="ech"></a>Encrypted Client Hello

Status: ⬜ planned for 0.3.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 9849.

**Requirement.** Encrypted Client Hello: the client encrypts the inner ClientHello (with the real server name) under the
server's ECH configuration, and the server decrypts it, accepts or rejects it, and sends retry configurations.

**Recorded status.** ⬜ planned for 0.3.0 (owner decision of 2026-11-18, [ADR-0019](../../adr/0019-openssl-4-and-ech.md)).

**How it is met.**

- Not yet: the pinned OpenSSL 3.5 LTS has no ECH. ECH needs OpenSSL 4.x, which ADR-0019 adopts (4.1.x now, 4.2 LTS once
  it is released).
- Planned scope: a client that takes the ECH configuration list from the origin's HTTPS record
  ([RFC 9848](9848.md#ech-https-records)) or from the application, retries once with the server's retry configurations,
  and sends GREASE ECH by default where it has no configuration; a server in shared mode with key rotation and retry
  configurations. Split mode is not planned (OpenSSL does not support it, and the RFC makes it an optional topology).
- Every MUST and SHOULD of the RFC is listed when the work starts, starting with a spike of ECH through the QUIC TLS
  callbacks `ksl` uses.

**Open items.**

- Everything above; the certificate check against the public name when the server rejects ECH, under every trust
  configuration (ADR-0011, ADR-0012).
