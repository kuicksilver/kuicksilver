# RFC 9849 — TLS Encrypted Client Hello

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="ech"></a>Encrypted Client Hello

Status: 🔶 accepted deviations (below: §6.1.7, accepted deviation, upstream issue https://github.com/openssl/openssl/issues/33831; the alert of three client aborts over TCP; the ALPN padding of §6.1.3); otherwise met since 0.3.0 (experimental API) · [summary](../rfc-compliance.md#tls)

Original row: RFC 9849.

**Requirement.** Encrypted Client Hello: the client encrypts the inner ClientHello (with the real server name) under the
server's ECH configuration, and the server decrypts it, accepts or rejects it, and sends retry configurations.

**Recorded status.** 🔶: met for the client and for a server in shared mode except one MUST of section 6.1.7 (accepted
deviation, upstream issue https://github.com/openssl/openssl/issues/33831), the alert of three client aborts over TCP and
the SHOULD of ALPN padding (see "Deviations"), in `ksl`, `kuicksilver-tls` and both Ktor
engines (owner decision of 2026-11-18, [ADR-0019](../../adr/0019-openssl-4-and-ech.md)). Split mode (section 3.1) is a
topology the RFC allows, not one it requires; it is not implemented ([its row](#split-mode)).

**How it is met.**

- OpenSSL 4.1.0 implements the protocol (the ECH extension, HPKE, the inner and outer ClientHello, acceptance
  confirmation, `retry_configs`, GREASE, shared mode on the server); Kuicksilver moved to it for ECH and carries four
  patches (ADR-0019): two upstream ones for ECH after a HelloRetryRequest (a client's own custom extension, which every
  QUIC client has; a rejection that follows a HelloRetryRequest: bugs B and C), and two of its own:
  `openssl-4.1.0-ech-retry-configs-raw.patch` (M1: `SSL_ech_get1_retry_config` hands over the server's `retry_configs`
  as sent once their framing holds, instead of dropping the whole list for one ECHConfig it cannot use) and
  `openssl-4.1.0-ech-sni-padding.patch` (the inner server_name padding of section 6.1.3). Upstream issues for both are
  drafted, to be filed.
- `ksl` checks what OpenSSL 4.1 does not (`ksl_ech.c`): the syntax of every ECHConfigList (`list_syntax_ok`), the
  outcomes of sections 5, 6.1.2, 6.1.6 and 6.2.1 around the handshake (`ksl_ech_check_done`, `ksl_ech_check_failed`,
  `ksl_ech_status`), the inner ClientHello's versions on a server (`ksl_ech_inner_versions_ok`, section 7.1), and a GREASE
  cipher suite per handshake (`ksl_ech_before_handshake`, section 6.2.1).
- `ksl` (`kuicksilver-native/src/c/ksl_ech.c`, `ksl.h`): `KSL_SET_ECH_CONFIG_LIST`, `KSL_OPT_ECH_GREASE`,
  `KSL_GET_ECH_STATUS`, `KSL_GET_ECH_RETRY_CONFIGS`, `KSL_GET_VERIFY_NAME`, `ksl_ech_config_list_check`, `ksl_ech_keys_new`
  and `ksl_ctx_set_ech_keys`, over QUIC (the TLS callbacks) and TCP.
- `kuicksilver-tls` (experimental): `TlsConfig.Builder.echConfigList` (`EchConfigList`), `echGrease` (default true) and
  `echKeys` (`EchServerKeys`, with `rotate`); `TlsConnection.echStatus` and `QuicTlsSession.echStatus` (`EchStatus`);
  `TlsException.EchRejected` with the server's retry configurations.
- The Ktor client (`kuicksilver-ktor-client`, `Ech.kt`, `H1Pool.connect`, `H3Pool`): the configuration of the endpoint
  (an HTTPS record's `ech`, [RFC 9848](9848.md#ech-https-records)) or of the host (`ech.configLists`), GREASE otherwise
  (`ech.grease`), the single retry with `retry_configs` per connection attempt (`EchRoute`, `withEchRetry`), over TCP and
  QUIC, inside a proxy's tunnel too. The Ktor server: `KuicksilverTlsConnector.Builder.echKeys` (TCP and HTTP/3) and the
  `EngineMain` key `kuicksilver.tls.echKeys`.

**Deviations.**

- Section 6.1.7: "If the server requests a client certificate, the client MUST respond with an empty Certificate
  message, denoting no client certificate." OpenSSL 4.1 sends `ech_required` as soon as the server's Finished is verified
  and never answers the CertificateRequest, so the empty Certificate message is not sent; BoringSSL sends it, then its
  Finished, then `ech_required` (`ssl/tls13_client.cc` lines 992-995, `ssl/handshake_client.cc` lines 1772-1779). In both
  cases no client certificate is sent, which is what the requirement protects; the C test
  `ech_rejection_sends_no_client_certificate` pins that. Accepted deviation, upstream issue
  https://github.com/openssl/openssl/issues/33831.
- The alert of three client aborts over TCP. Over QUIC the CONNECTION_CLOSE carries the alert the section names. Over
  TCP: after a rejection with a `pre_shared_key` in the ServerHello (section 6.1.2, `illegal_parameter`) or with
  `retry_configs` that do not parse (section 6.1.6, `decode_error`), OpenSSL 4.1 has already written `ech_required` when
  `ksl` sees the outcome, so that is the alert on the wire; the handshake fails, no rejection and no retry configuration
  is reported, and the error message names the section. With `retry_configs` on an accepted ECH (section 5,
  `unsupported_extension`) or malformed ones after GREASE (section 6.2.1, `decode_error`), the client's Finished is already
  written and OpenSSL 4.1 has no call to send an alert afterwards: the connection ends without one, before the session
  counts as established. 🔶 accepted deviation; upstream issues to be filed (OpenSSL should check these itself, before
  its own `ech_required`; drafts H, I and J of 2026-11-19).
- Section 6.1.3, ALPN padding (SHOULD). OpenSSL 4.1 pads the inner ClientHello for the server name only and has no API
  to add padding for another extension; its outer-ALPN API (`SSL_ech_set1_outer_alpn_protos`) sets what the outer
  ClientHello shows, not the inner padding. The rounding of the whole to 32 bytes covers part of the difference between
  ALPN lists (Kuicksilver's profiles: `h3`; `h2` with `http/1.1`). 🔶 until OpenSSL offers it; an upstream observation is
  in draft F.

**Peers.** BoringSSL ends a rejected handshake the same way, after the server's Finished, with `ech_required`
(`ssl/handshake_client.cc` lines 1772-1779), and reports early data as under the inner ClientHello only ("The server can
only accept early data with ClientHelloInner", `ssl/encrypted_client_hello.cc` lines 1108-1113); unlike OpenSSL it sends
an empty client Certificate before the alert (`ssl/tls13_client.cc` lines 992-995). quiche has no ECH API of its own (no
ECH symbol in its sources). The retry policy (one retry, without ECH when securely disabled) is the application's in
BoringSSL; Kuicksilver's engine makes it.

**Interop.** `LiveEchTest` (opt-in, `-Pkuicksilver.liveEch=true`, network) connects to Cloudflare's
`crypto.cloudflare.com` with the `ech` of its HTTPS record and with a configured list, over TCP and HTTP/3, and checks that
its trace reports `sni=encrypted`.

**Open items.**

- The upstream issues for the carried patches (M1, padding) and for the TCP alerts (sections 5, 6.1.2, 6.1.6, 6.2.1),
  drafted 2026-11-19, to be filed; the section 6.1.7 deviation is filed as
  https://github.com/openssl/openssl/issues/33831. Split mode is [not planned](#split-mode).

## <a id="split-mode"></a>Split mode

Status: ❌ not planned · [summary](../rfc-compliance.md#tls)

**Requirement.** Sections 3.1 and 7.2: a client-facing server that decrypts the outer ClientHello and forwards the inner
one to a backend server, which confirms ECH acceptance.

**Why not.** OpenSSL 4.1 has no split mode, and the RFC defines it as one of two topologies, not a requirement; the
Kuicksilver server is always both servers (shared mode).
