# RFC 7692 — Compression Extensions for WebSocket

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

`PerMessageDeflate` (`kuicksilver-ktor-network/src/commonMain/kotlin/io/kuicksilver/ktor/network/websocket/PerMessageDeflate.kt`) is a Ktor `WebSocketExtension`: it works in Ktor's client and server `WebSockets` plugins on any engine. Kuicksilver's engines also decompress in their frame guard (`WebSocketFrameGuard.kt`), so that a message over the limit is closed with 1009. DEFLATE itself is java.util.zip on the JVM and Android and the platform's zlib (`platform.zlib`) on Kotlin/Native (`RawDeflate.kt` and its two actuals); the codec of section 7.2 is `DeflateCodec.kt`.

## <a id="s5-negotiation"></a>§5, §7, §7.1 — negotiation of permessage-deflate

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Section 7: a server declines an offer with a parameter not defined for an offer, an invalid value, a repeated parameter, or a configuration it does not support (MUST); a client fails the connection on a response with a parameter not defined for a response, an invalid value, a repeated parameter, or a configuration it does not support (MUST). Section 5: a server MUST NOT accept a PMCE together with another extension that conflicts with it on RSV1, nor with one whose output it compresses when that extension needs frame boundaries preserved or uses the "Extension data" field or reserved bits per frame; a client that receives such an answer, or one accepting a PMCE it did not offer, MUST fail the connection. Section 7.1: the four parameters and their values (`server_max_window_bits` and `client_max_window_bits` 8 to 15 without leading zeros, also as a quoted-string; the `*_no_context_takeover` ones without a value); a server that accepts an offer with `server_no_context_takeover` includes it (MUST); a server answers `server_max_window_bits` with a value no larger than offered (MUST); a server includes `client_max_window_bits` only when the offer had it (MUST NOT otherwise); context takeover is not used by the side whose `*_no_context_takeover` was agreed (MUST NOT).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- client offer: `permessage-deflate` with `client_no_context_takeover` and `server_no_context_takeover` as configured; `client_max_window_bits` is never offered, so the client compresses with a 32 KiB window
- client: a response with an unknown, repeated or malformed parameter, `client_max_window_bits`, `permessage-deflate` twice, or without a `server_no_context_takeover` the client asked for fails the handshake (`ProtocolViolationException` from the extension; Kuicksilver's client engine fails it earlier with `WebSocketException`, before a session opens); any valid `server_max_window_bits` (8 to 15) is accepted, since the inflater's 32 KiB window reads every smaller one; `client_no_context_takeover` in the response binds the client's compressor
- server: the offers are tried in order and the first one it can keep to is accepted with one element; an invalid offer is declined; an offered `server_max_window_bits` is answered with the same value when the deflater can keep to it (9 to 15 on Kotlin/Native, where zlib refuses a raw stream with an 8-bit window; 15 on the JVM and Android, whose `Deflater` has a fixed window) and the offer is declined otherwise; `server_no_context_takeover` and `client_no_context_takeover` are echoed (and added when configured); `client_max_window_bits` is a hint that is not answered
- another extension that uses RSV1: Kuicksilver's server engine refuses an upgrade whose negotiated extensions (Ktor's plugin negotiates each installed one on its own) include two that claim the same RSV bit (their factories' `rsv1`/`rsv2`/`rsv3`) before anything is sent, and the call fails with `IllegalStateException` (500); Kuicksilver's client engine fails a handshake whose answer accepts two installed extensions claiming the same bit with `WebSocketException` (an extension cannot see the others, so on other engines this rests with Ktor, whose own conflict check in `WebSocketExtensionsConfig` never fires in 3.6.1)
- section 5's other conditions cannot arise in Ktor: Ktor's session hands extensions whole messages (frame boundaries are never preserved for any extension) and a Ktor `Frame` has no "Extension data" field, so the per-frame attributes an extension can have are its RSV bits, which the check above covers
- parameter names and the extension name are compared without regard to case (as OkHttp and Netty do; RFC 7692 does not say)

**Tests that pin it.**

- `PerMessageDeflateTest.clientOffer`, `.clientAcceptsValidResponses`, `.clientNoContextTakeoverFromServerIsHonoured`, `.negative_unrequestedClientMaxWindowBitsRejected`, `.negative_invalidResponseParametersFail`, `.negative_requestedServerNoContextTakeoverMissingFails`, `.serverAcceptsTheFirstValidOffer`, `.negative_serverDeclinesInvalidOffers`, `.serverMaxWindowBitsHonouredOrDeclined`, `.serverCompressesWithinTheNegotiatedWindow` (Kotlin/Native: a 9-bit window, read back with a 9-bit inflater)
- `ClientDeflateTest.negative_invalidDeflateResponseFailsHandshake`, `.negative_deflateAcceptedWithAnotherRsv1ExtensionFailsHandshake`, `.oneRsv1ExtensionAcceptedPasses`, `ServerDeflateTest.invalidOfferDeclined`, `.negative_twoRsv1ExtensionsAreNotBothAccepted`, `.negative_twoRsv1ExtensionsAreNotBothAcceptedH3`

**Notes on peers.** OkHttp (`WebSocketExtensions.parse`, 5.3.2) marks any unexpected or repeated parameter, a parameter value where none belongs and a non-numeric window as unknown values, and its `client_max_window_bits` must be 15; Netty's handshakers decline offers and responses the same way and cap `server_max_window_bits` at their configured window. Ktor's `WebSocketDeflateExtension` throws `IllegalStateException` on `client_max_window_bits` other than 15 and on an offered `server_max_window_bits` other than 15.

## <a id="s6-compression-and-decompression"></a>§6, §7.2 — compression and decompression

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Section 6: a PMCE operates on data messages only; RSV1 is set on the first frame of a compressed message and on no other frame (MUST NOT on control frames and non-first fragments; an endpoint receiving one fails the connection, MUST). Section 7.2.1: compress all the octets of the message with DEFLATE, end with an empty stored block, remove its 0x00 0x00 0xff 0xff. Section 7.2.2: append 0x00 0x00 0xff 0xff to the payload and inflate; without the agreed `*_no_context_takeover` of that direction, each new message MUST be decompressed with the LZ77 window used for the last one; without an agreed `*_max_window_bits` the window MUST be 32,768 bytes. Section 7.2.3.4: a sender may end a message with a final block (BFINAL), followed by one 0x00 (an empty stored block's header bits and padding) so that the payload decompresses as the others do.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- outgoing Text and Binary messages are compressed (`MessageDeflater`): each fragment is sync-flushed, the final fragment loses the 0x00 0x00 0xff 0xff of its flush, and is a single 0x00 when the flush wrote nothing (section 7.2.3.6); RSV1 is set on the first frame of a message only and a fragmented message is one DEFLATE stream; control frames are never touched
- incoming compressed messages are inflated with a 32 KiB window (`MessageInflater`): in Ktor's session for the reassembled message, or in Kuicksilver's engines' frame guard as the frames arrive
- a final block ends zlib's stream: the next message gets a new stream primed with the window (the last 32 KiB of output, kept on every platform: the JDK's Inflater cannot hand the window over, and zlib's inflateGetDictionary needs zlib 1.2.7.1, newer than the glibc 2.17 Linux floor) via inflateSetDictionary, so with context takeover it is decompressed with the last message's window as section 7.2.2 requires; after a final block only the one 0x00 of section 7.2.3.4 may follow (RFC 1951 ends the data at the final block; anything more fails as malformed, 1002)
- malformed as well (1002 on Kuicksilver's engines, `ProtocolViolationException` elsewhere): an RSV1 message without payload (the empty message is the single 0x00 of section 7.2.3.6); on Kotlin/Native, a message that does not end at a DEFLATE block boundary once the 4 octets are appended (zlib's `data_type`), i.e. one cut short. The JDK's `Inflater` does not report the boundary, so on the JVM and Android such a message is not detected; OkHttp's `MessageInflater` (5.3.2) has the same gap. The close reason says "Invalid compressed data", never zlib's own text
- RSV1 on a continuation or control frame fails the connection with 1002 in Kuicksilver's engines (frame guard, [RFC 6455 details](6455.md#s4-1-websocket-extensions-in-the-ktor-engines)); on another engine Ktor's session hands extensions reassembled messages, so the bit of a continuation is not visible to the extension
- context takeover: the windows carry over between messages unless `*_no_context_takeover` was agreed for that direction (the compressor is reset after each message, the inflater before the next)

- `GuardInflateTest.*` (the engines' frame guard), `ClientDeflateTest.roundTripOverH1`, `.roundTripOverH3`, `.wireFormatAgainstARawServer`, `ServerDeflateTest.compressedEchoH1`, `.compressedEchoH3`
- interop: `ClientDeflateKtorTest.kuicksilverClientWithKtorServerExtensionH1`, `…H3`, `.ktorClientWithKuicksilverServerExtensionH1`, `…H3` (JVM; Ktor's `WebSocketDeflateExtension` on the other end)

**Notes on peers.** Ktor's `WebSocketDeflateExtension` sets RSV1 on every fragment of a compressed message (Kuicksilver's engines close such a peer with 1002 when it fragments) and, in 3.6.1, fails to compress an empty message after an earlier one. OkHttp compresses whole messages and, like Kuicksilver, takes what follows a final block as the end of the message (`MessageInflater`, 5.3.2).

## <a id="decompression-limit"></a>Decompression limit (RFC 6455 §7.4.1, §10.4)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** RFC 7692 sets no limit of its own (its section 8 is about CRIME, below). RFC 6455 section 10.4: an implementation with limits on message size MUST protect itself against exceeding them and SHOULD limit the reassembled message size; section 7.4.1 defines 1009 for a message too big to process.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `maxInflatedMessageSize` (16 MiB by default) bounds what one message may inflate to; the output is produced and counted in pieces of 64 KiB and nothing is sized by what the data claims, so at most one piece more than the limit is ever produced
- Kuicksilver's engines decompress in the frame guard and close with 1009 once a message passes the limit, over HTTP/1.1 and HTTP/3, as client and as server; Ktor's session answers that Close, so 1009 is on the wire and is the session's `closeReason`; malformed data closes with 1002
- on another engine the extension fails the message with `FrameTooBigException` (Ktor's session then ends without sending 1009)
- no separate ratio limit: DEFLATE cannot expand more than about 1032 times, so work is bounded by the compressed size too, and a ratio limit would only refuse legitimate repetitive messages
- compressed bytes are bounded too: a message whose compressed data passes 8 times the limit plus 64 KiB fails as too big (1009), so data that inflates to nothing (empty blocks) cannot stream on without bound; a sender that sync-flushes one-byte fragments needs about 6 bytes per fragment, well within it
- memory per connection: about 256 KiB of deflater state (32 KiB window), about 40 KiB of inflater state, 32 KiB of output history (context takeover, JVM and Android only: Kotlin/Native reads the window from zlib) and 80 KiB of buffers, each made on first use; Kuicksilver's engines free the zlib state when the session ends; on other engines a cleaner frees it when the extension is collected, so many short sessions can hold native memory until the garbage collector runs

**Tests that pin it.**

- `PerMessageDeflateTest.negative_inflateBombStopsAtLimit`, `.messageAtTheLimitPasses`, `.negative_endlessEmptyBlocksStopAtTheCompressedLimit`, `.disposedExtensionRefusesFurtherWork`, `GuardInflateTest.negative_inflateBombClosesWith1009`, `.negative_endlessEmptyBlocksCloseWith1009`, `.negative_emptyCompressedMessageClosesWith1002`, `.largeMessageIsHandedOnInPiecesOf64KiB`, `ClientDeflateTest.negative_bombFromServerClosesWith1009`, `.negative_bombFromServerClosesWith1009H3`, `ServerDeflateTest.negative_bombFromClientClosesWith1009`, `.negative_bombFromClientClosesWith1009H3`

**Notes on peers.** Ktor's `WebSocketDeflateExtension` limits a message to 256 MiB by default; OkHttp's `MessageInflater` (5.3.2) has no inflated-size limit of its own; Netty's decoder takes a `maxAllocation`.

## <a id="s8-security-considerations"></a>§8 — compression side channels (CRIME)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Section 8: history-based compression combined with a secure transport has a known exploit (CRIME); implementors should pay attention to it when integrating the extension with other extensions or protocols.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- what is compressed is the application's choice: `compressIf { }` keeps chosen messages uncompressed (decided on a message's first frame), `serverNoContextTakeover` and `clientNoContextTakeover` stop messages from sharing an LZ77 window, and `minSizeToCompress` leaves small messages alone
- the guide ("WebSocket compression", "Compression and secrets") and threat model 3.20.2 say not to put secrets into compressed messages that also carry attacker-influenced data, and that within one message they always share a window

**Tests that pin it.**

- `PerMessageDeflateTest.compressIfKeepsChosenMessagesUncompressed`, `.noContextTakeoverResetsDictionary`, `.messagesBelowMinSizeAreSentUncompressed`
