# RFC 9110 — HTTP Semantics

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="s9-2-2-client-retry"></a>§9.2.2; RFC 9112 §9.2, §9.3.1 — client retry

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §9.2.2; RFC 9112 §9.2, §9.3.1 (client retry).

**Requirement.** A pooled HTTP/1.1 connection the server closed while idle is replaced once, transparently, for idempotent requests only (GET, HEAD, OPTIONS, PUT, DELETE, TRACE).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- a non-idempotent request that failed on such a connection may have been processed and surfaces its `IOException` instead of being sent again
- a connection already closed for reading is dropped when taken from the pool, and a connection the h3/h1 race just opened never earns the retry, while an idle pooled one the race handed out does (before 0.2.0 a POST was replayed and the race dropped the pooled flag)
- an idle pooled connection with unread bytes, such as an unsolicited `408 Request Timeout` sent before the server closes (RFC 9110 §15.5.9), is closed instead of reused, so the next request gets a fresh connection rather than that stale answer (RFC 9112 §9.2: the client MUST NOT consider data on a connection without outstanding requests a valid response, SHOULD close it; 0.2.1 review)

**Tests that pin it.**

- `ClientH1Test.staleConnectionRetriedOnceForGet`, `.negative_postNotRetriedOnStaleConnection`, `ClientRaceTest.staleConnectionFromTheRaceIsRetried`, `h1.H1IdleConnectionTest.*`

## <a id="s9-3-6-client-connect-tunnel"></a>§9.3.6, §11.7.2; RFC 9931 §8 — client CONNECT tunnel

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §9.3.6, §11.7.2; RFC 9931 §8 (client CONNECT tunnel).

**Requirement.** HTTPS through an HTTP proxy: a CONNECT tunnel (before the fix the proxy address was cast to the wrong type and every proxied request failed).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- `Proxy-Authorization` and `Proxy-Connection` go on the CONNECT only, never inside the tunnel to the origin
- `Content-Length`/`Transfer-Encoding` of a `2xx` CONNECT response are ignored
- interim 1xx responses before the CONNECT's final one are skipped, with the same 64 KiB bound by bytes as for a request (RFC 9110 §15.2; 0.2.1 review, before a 1xx failed the tunnel), a 101 is a final answer that refuses the tunnel
- no tunnel byte (TLS ClientHello, WebSocket handshake) is sent before the proxy's 2xx (RFC 9931 §8 MUST, option 1: wait for a 2xx before forwarding payload)

**Tests that pin it.**

- `ClientProxyTest.negative_proxyCredentialsStayOnTheConnect`, `.contentLengthOnConnectResponseIsIgnored`, `.interimResponsesBeforeTheConnectAnswerAreSkipped`, `.negative_noTunnelByteBeforeTheConnectAnswer`, `h1.H1ResponseHeadTest.negative_endlessInterimResponsesToTheConnectFail`

## <a id="s5-5-client-response-head"></a>§5.5, §6.2, §15; RFC 9112 §2.2, §4, §5.2 — client response head

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §5.5, §6.2, §15; RFC 9112 §2.2, §4, §5.2 (client response head).

**Requirement.** The response head and the proxy's CONNECT response are read by the engine before Ktor's parser sees them: a control character other than HTAB (NUL, a bare CR, 0x01–0x08, 0x0A–0x1F, 0x7F) in a field line or the reason phrase fails the response with `ParserException` and closes the connection (§5.5: NUL, CR and LF MUST be rejected or replaced, the other CTLs are invalid; 0.2.1 review, before NUL reached the application).

Quoted: "A client ... SHOULD process ... as if it had a 5xx (Server Error) status code".

**Recorded status.** ✅ 0.2.1

**How it is met.**

- an obs-fold is replaced with one SP (§5.2: a user agent MUST; before, Ktor's parser failed the response), a field value that starts with a Unicode space sent as obs-text (U+00A0, ...) is kept as sent (§5.5: opaque data; §5.6.3: OWS is SP and HTAB; Ktor's parser skipped it), so such a Content-Length or Transfer-Encoding is invalid framing (RFC 9112 §6.3) and the application sees other values as the server sent them (0.2.1 review, as the server engine), and a line that starts with whitespace right after the status line is rejected (§2.2)
- obs-text in a field value reaches the application as on the server (server request field lines): decoded as UTF-8 when it is valid UTF-8, else byte for byte as ISO-8859-1 (0.3.0; before, U+FFFD); the framing fields refuse obs-text either way
- the status line is `HTTP-version SP 3DIGIT [SP reason-phrase]`, else `ParserException` (before, `HTTP/1.1 20` and `HTTP/1.1 2000` without a reason phrase passed)
- three digits outside 100–599 are an invalid status code, which "A client ... SHOULD process ... as if it had a 5xx (Server Error) status code" (RFC 9110 §15): the response is a 500 with the code and reason sent as its description (`600 Six`; before 0.2.1 it was passed on as is, a 042 looking like a success) (the SP before an absent reason phrase may be missing: nothing requires a client to reject that line, and §4 has it ignore the reason phrase), `HTTP/1.x` with x > 1 is processed as HTTP/1.1 (RFC 9110 §6.2 SHOULD; before, it failed), another major version fails

**Tests that pin it.**

- `h1.H1ResponseHeadTest.negative_nulInFieldValueFails`, `.htabAndObsTextInFieldValuePass`, `.obsTextThatIsNotUtf8IsPassedOnByteForByte`, `.obsFoldInResponseIsUnfolded`, `.negative_foldRightAfterTheStatusLineFails`, `.negative_statusCodeNotThreeDigitsFails`, `.invalidStatusCodeIsProcessedAs5xx`, `.negative_unicodeSpaceBeforeAFramingValueIsInvalid`, `.unicodeSpaceBeforeAFieldValueIsKept`, `.statusLineWithoutReasonPhraseIsAccepted`, `.higherMinorVersionIsProcessedAsHttp11`

## <a id="s5-1-server-request-field-lines"></a>§5.1, §5.5, §5.6.3; RFC 9112 §5.1, §5.2 — server request field lines

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §5.1, §5.5, §5.6.3; RFC 9112 §5.1, §5.2 (server request field lines).

**Requirement.** A field name that is not a token (DEL, bytes above 0x7F; before 0.2.1 passed), empty, followed by whitespace before the colon, or an obs-fold line → 400 and close.

**Recorded status.** ✅ 0.2.1

**How it is met.**

- a value that starts with obs-text decoding to a Unicode space (U+00A0, U+2000, ...) reaches the engine and the application as sent (OWS is only SP and HTAB, obs-text is opaque field content, §5.5 SHOULD; Ktor's parser stripped it, so `X-A: <U+00A0>a` arrived as `a` and `Content-Length: <U+00A0>5` framed a body), which makes such a Content-Length, Transfer-Encoding or Host invalid → 400 and close (0.2.1)
- obs-text is passed on (0.2.1; before, Ktor's parser refused only CR and LF and a NUL reached the application) as opaque data (§5.5 SHOULD): a value that is valid UTF-8 (`é` sent as `C3 A9`) arrives decoded as UTF-8, one that is not (`é` sent alone as Latin-1 `E9`) arrives byte for byte, each byte as the char of the same code (ISO-8859-1), so `caf<E9>` is `café` (0.3.0; before, Ktor's parser made such bytes U+FFFD and they were lost). The head check reads the value from the bytes and puts it in place of the parser's. The engine itself never interprets obs-text: the framing fields Host, Content-Length and Transfer-Encoding are ASCII grammars that refuse it either way

**Tests that pin it.**

- `h1.H1RequestHeadCheckTest.negative_controlCharactersInAFieldValueAreRejected`, `.tabsSpacesAndObsTextInAFieldValueAreAccepted`, `.obsTextThatIsNotUtf8IsPassedOnByteForByte`, `.negative_fieldNameMustBeAToken`, `.unicodeSpaceBeforeAFieldValueIsKept`, `.negative_unicodeSpaceBeforeAFramingValueIsRejected`, `.unicodeSpaceInsideAFieldValueIsAccepted`, `ServerH1FramingTest.negative_nonOwsWhitespaceInFramingFieldsIsRejected`

**Peer interop notes.**

- a field value with a control character other than HTAB (NUL, VT, FF, DEL, a bare CR, ...) → 400 and close (§5.5: a recipient of CR, LF or NUL MUST reject the message or replace them with SP; field-content is VCHAR, obs-text, SP and HTAB), as Go's net/http

## <a id="s8-6-server-response-framing-fields"></a>§8.6; RFC 9112 §6.1, §6.2 — server response framing fields

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §8.6; RFC 9112 §6.1, §6.2 (server response framing fields).

**Requirement.** No 2xx response to CONNECT goes out (the engine answers 501 instead, see the RFC 9931 §8 row), so none carries Content-Length or Transfer-Encoding (MUST NOT).

**Recorded status.** ✅ 0.2.1

**How it is met.**

- a response with Transfer-Encoding never also carries Content-Length (§6.2 MUST NOT): an application's Content-Length on content Ktor frames with `chunked` is dropped (0.2.1; before, both went out)
- a 1xx or 204 response goes out without Content-Length and Transfer-Encoding (MUST NOT), a 304 without Transfer-Encoding and without the `Content-Length: 0` Ktor adds for empty content (a 304 MAY omit it; MUST NOT send one other than the 200's length; an application's other value stays) (0.2.1; before, `respond(NoContent)` said `Content-Length: 0` and a streamed 204 or 304 `Transfer-Encoding: chunked`)

**Tests that pin it.**

- `ServerH1ResponseFramingTest.negative_noFramingFieldsOn204And304`, `.negative_noContentLengthWithTransferEncoding`, `.negative_2xxToConnectIsAnswered501`

## <a id="s9-3-2-server-responses-without-content"></a>§9.3.2, §6.4.1, §15.3.5, §15.4.5; RFC 9112 §6.3 item 1 — server responses without content

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §9.3.2, §6.4.1, §15.3.5, §15.4.5; RFC 9112 §6.3 item 1 (server responses without content).

**Requirement.** What the application writes for a response to HEAD, or for a 1xx, 204 or 304 response, is dropped and its fields stay (a HEAD response keeps the Content-Length or Transfer-Encoding a GET would have), and a streamed body for one is never produced (its writer does not run, its channel is not read).

**Recorded status.** ✅ 0.2.1

**How it is met.**

- the engine's own 400 and 505 to a HEAD request keep their Content-Length and carry no content (`h1.H1RequestHeadCheckTest.negative_noContentInARefusalOfHead`)
- an HTTP/1.0 HEAD response is not forced to close (0.2.1; before, `head("/") { call.respondText("x") }` without AutoHeadResponse sent `x`, which a keep-alive client read as the start of the next response).
- The HTTP/3 server already dropped it

**Tests that pin it.**

- `ServerH1ResponseFramingTest.negative_noContentForHeadAnd204And304`, `ServerH3Test.headAnd204And304SendNoData`

## <a id="s15-5-9-server-timeouts"></a>§15.5.9; RFC 9112 §9.5 — server timeouts

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §15.5.9; RFC 9112 §9.5 (server timeouts).

**Requirement.** A request head must be complete `requestHeaderTimeoutSeconds` (30 s) after the accepted connection (TLS handshake included) or the end of the previous response.

**Recorded status.** ✅ 0.2.1

**How it is met.**

- a client that sent part of it gets `408 Request Timeout` with `Connection: close` (§15.5.9: the server has decided to close), one that sent nothing is closed without a response (§9.5: a server may close an inactive connection at any time; a 408 there could cross a request the client is sending).
- The idle timeout closes both directions (before 0.2.1 it closed only the output and the reader waited for ever)
- a request body with no byte for the idle timeout gets 408 (§15.5.9) and the connection closes, the wait after `Expect: 100-continue` starting once `100 Continue` is sent (§10.1.1)

**Tests that pin it.**

- `h1.H1PipelineTimeoutTest.*`, `ServerH1TimeoutTest.*`

## <a id="s10-1-1-expect-100-continue"></a>§10.1.1 — `Expect: 100-continue`

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** Upon a complete HTTP/1.1 (or later) request head with a 100-continue expectation and content to follow, a server "MUST either send an immediate response with a final status code, if that status can be determined by examining just the method, target URI, and header fields, or send an immediate 100 (Continue) response"; it MUST ignore the expectation in HTTP/1.0 and "MAY omit sending a 100 (Continue) response if ... the framing indicates that there is no content". A client "SHOULD NOT wait for an indefinite period before sending the content".

**How it is met.**

- Server, HTTP/1.1, HTTP/2 and HTTP/3: `100 Continue` goes out as the call is dispatched, before the application runs (0.3.0; before, HTTP/1.1 and HTTP/2 sent it when the application first read the content, and HTTP/3 never sent it). The final statuses the head alone determines go out instead of it, without a 100: 400 for a malformed head or framing, 413 for a Content-Length too large to process, 431 for a head over its limit, 421 for a host the connection's certificate does not name (0.3.0, [§7.4](#s7-4-server-misdirected-requests)), 425 for a request a gateway forwarded from early data that is not replayable, 501 for a CONNECT. HTTP/1.0 ignores the expectation; a request without content (no Content-Length or Transfer-Encoding over HTTP/1.1; `content-length: 0` or END_STREAM with the head over HTTP/2 and HTTP/3) gets no 100 (the MAY). Another expectation is answered `417 Expectation Failed` (a MAY) when the application reads the content, over HTTP/1.1 and HTTP/2. The body deadline (`connectionIdleTimeoutSeconds`) starts once the 100 is sent; content the application leaves unread is drained as any other (up to 256 KiB, else the connection closes after the response), and a request answered 425 without the 100 is not waited for.
- Client: `Expect: 100-continue` only on a request with content; the content waits for the `100`, for a final status (then it is not sent), or 1 s at most, then goes anyway; after a `417` the request is repeated without the expectation.

**Tests that pin it.**

- `ServerH1BodyTest.expectContinueGets100BeforeTheHandlerReads`, `.negative_aHeadDeterminedFinalStatusSendsNo100`, `ServerH2Test.expectContinueGets100BeforeTheHandlerReads`, `.expectContinueGetsAnInterim100`, `ServerH3Test.expectContinueGets100BeforeTheHandlerReads`, `ServerH1TimeoutTest.negative_bodyThatNeverFollowsContinueGets408`, `h1.H1PipelineBodyTimeoutTest.expectContinueDeadlineStartsWhenContinueIsSent`, `h1.H1PipelineContinueTest.*`, `ClientH1Test.expectContinueFinalStatusFirstSendsNoBody`, `.expectContinueBodyWaitsForContinue`, `.expectContinueBodySentAfterTimeoutWithoutAnswer`

## <a id="s7-4-server-misdirected-requests"></a>§7.4, §15.5.20; RFC 9113 §9.1.1; RFC 9114 §3.3 — server: misdirected requests (421)

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

**Requirement.** RFC 9110 section 7.4: "Unless the connection is from a trusted gateway, an origin server MUST reject a
request if any scheme-specific requirements for the target URI are not met. In particular, a request for an "https"
resource MUST be rejected unless it has been received over a connection that has been secured via a certificate valid for
that target URI's origin, as defined by Section 4.2.2." Section 15.5.20: an origin server "sends 421 to reject a target URI
that does not match an origin for which the server has been configured (Section 4.3.1) or does not match the connection
context over which the request was received (Section 7.4)". RFC 9113 section 9.1.1 and RFC 9114 section 3.3 let a client
reuse a connection "for requests with multiple different URI authority components" (browsers do, for hosts the
certificate names at the same address) and name the 421 as the server's way to say it "is not authoritative for a
request". Section 4.3.4 defines "valid for the origin": the client checks the host against the certificate as RFC 6125
(now RFC 9525) section 6 says, an IP-ID for an IP literal, a DNS-ID otherwise, and "A reference identity of type CN-ID
MUST NOT be used by clients".

**How it is met.**

- Server engine, HTTP/1.1 over TLS, HTTP/2 and HTTP/3 (0.3.0; before, a request for any host was served on any
  connection): before the application sees a request whose target URI is `https`, its host is checked against the leaf
  certificate this very connection presented (the `sniSelector` override, or the snapshot of a `TlsIdentity.Reloadable`
  taken for its handshake, so a reload changes nothing for open connections). A host the certificate does not name gets
  `421 Misdirected Request`, and the call never reaches the application (its routing and interceptors do not run).
  HTTP/1.1 keeps the connection for the next request; HTTP/2 and HTTP/3 end only that stream (with the 421 and END_STREAM,
  or the 421 and FIN) and go on serving the connection's other requests, as a client that retries "over a different
  connection" (section 15.5.20) expects.
- The target URI: the absolute-form's scheme and authority over HTTP/1.1, else `https` and `Host` (RFC 9112 section 3.3);
  `:scheme` and `:authority`, else `host`, over HTTP/2 and HTTP/3. A request without any authority takes the server's own
  (RFC 9112 section 3.3) and is not checked; a classic CONNECT names a tunnel's destination, not an origin, and keeps its
  501 (Extended CONNECT for WebSockets and WebTransport is checked); a target URI with the `http` scheme over TLS has no
  certificate requirement and is not checked.
- The name check (`Certificate.matchesHost`, kuicksilver-tls; the client side's matcher is OpenSSL's, with the same flags):
  subjectAltName only; a DNS name matches after ASCII lower-casing and removal of one trailing dot, a wildcard only as the
  whole left-most label standing for exactly one non-empty label of a name with at least two more (`*.wild.test` matches
  `a.wild.test`, not `wild.test` or `a.b.wild.test`), never a partial wildcard; an IP literal (IPv4, or IPv6 with or without
  brackets) matches an iPAddress entry with the same bytes, never a dNSName spelling it; the subject CN is never used. A
  host that is no valid reference identifier (not ASCII: IDNs must arrive as A-labels; malformed) matches nothing. The port
  plays no part: a certificate names none, and section 4.3.3's check of the port is not a requirement (no BCP 14 keyword),
  so a server behind port forwarding keeps working; a server that serves distinct services on two ports checks the port in
  its routing.
- Connections an `sniSelector` set up (0.3.0): the selector may give each name its own identity, client-certificate
  requirement and trust, and which policy another name would get is unknown without running it again. A request on such
  a connection must therefore also be for the name the connection was set up for: its SNI name, or an IP literal when the
  ClientHello carried no SNI (clients send none for addresses, RFC 6066 section 3); anything else gets 421, both ways (a
  request for a name that requires a client certificate on a connection that asked for none, and a request for another
  name on a connection that did). Section 7.4: the decision "is specifically directed at whether the server has been
  configured to process requests for that target URI and whether the connection context is appropriate for that
  request"; section 15.5.20: 421 for a target URI that "does not match the connection context over which the request was
  received". nginx answers 421 for Host ≠ SNI when `ssl_verify_client` is on, Caddy's `strict_sni_host` does the same and
  is on by default with client authentication; Kuicksilver applies it on every `sniSelector` connector, since a selector
  can set client authentication for any name. Such connectors serve no HTTP/3 (QUIC cannot pick an identity per name),
  so the rule concerns HTTP/1.1 and HTTP/2. Browsers then do not coalesce onto these connections and open one per name.
- The exception: `tlsConnector { trustedGateway = true }` turns the check off for one connector whose every client is a
  trusted gateway ("Unless the connection is from a trusted gateway"), such as a TLS-terminating proxy that re-encrypts with
  an internal certificate. False by default.
- Plain connectors (0.3.0): a plain connection is "secured" by no certificate, so an `https` target over it, which only the
  absolute form can carry (`GET https://host/ HTTP/1.1`), gets 421. Origin-form requests and `http` targets are served for
  any host: their target URI is `http`. `plainConnector { trustedGateway = true }` is the exception for a connector whose
  clients are all trusted gateways.
- Peers, for comparison: nginx answers 421 only when the Host differs from the SNI name and `ssl_verify_client` is on for
  the server block (`ngx_http_set_virtual_server`); Caddy's `strict_sni_host` (on by default with client authentication)
  compares Host with SNI; Go's `net/http`, Netty and Ktor's own engines do not check. Kuicksilver checks the certificate,
  which is what section 7.4 asks for, and keeps the reuse browsers make for hosts the certificate names.
- Library: `kuicksilver-http3`'s server (`Http3Connection.server`) hands every request to the application, the origin
  server; `QuicConnection.localCertificates`, `TlsConnection.localCertificates` and `Certificate.matchesHost` give it what
  the check needs.

**Tests that pin it.**

- `ServerMisdirectedRequestTest.negative_h1HostTheCertificateDoesNotNameGets421`, `.h1HostsTheCertificateNames`,
  `.negative_h1HostsTheCertificateDoesNotName`, `.trustedGatewayConnectorServesAnyHost`,
  `.negative_h1CertificateChosenBySniIsTheOneChecked`, `.negative_h1RequestForStricterSniPolicyOnLaxConnectionGets421`,
  `.negative_h1RequestForAnotherSniPolicyOnStrictConnectionGets421`, `.sniPolicyConnectionsServeTheirOwnName`,
  `.negative_h2RequestForAnotherSniPolicyGets421`, `.trustedGatewayConnectorServesAnyNameOverSniPolicy`, `.negative_plainConnectorRejectsAbsoluteFormHttps`,
  `.trustedGatewayPlainConnectorServesAbsoluteFormHttps`,
  `.negative_h2CoalescedRequestGets421AndConnectionStaysUsable`, `.negative_h3CoalescedRequestGets421AndConnectionStaysUsable`,
