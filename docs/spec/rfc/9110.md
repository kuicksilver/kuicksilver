# RFC 9110 — HTTP Semantics

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="s9-2-2-client-retry"></a>§9.2.2; RFC 9112 §9.2, §9.3.1 — client retry

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §9.2.2; RFC 9112 §9.2, §9.3.1 (client retry).

**Requirement.** A pooled HTTP/1.1 connection the server closed while idle is replaced once, transparently, for idempotent requests only (GET, HEAD, OPTIONS, PUT, DELETE, TRACE).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- a non-idempotent request that failed on such a connection may have been processed and surfaces its `IOException` instead of being sent again
- a connection already closed for reading is dropped when taken from the pool, and a connection the h3/h1 race just opened never earns the retry, while an idle pooled one the race handed out does (before 0.2.0 a POST was replayed and the race dropped the pooled flag)
- an idle pooled connection with unread bytes, such as an unsolicited `408 Request Timeout` sent before the server closes (RFC 9110 §15.5.9), is closed instead of reused, so the next request gets a fresh connection rather than that stale answer (RFC 9112 §9.2: the client MUST NOT consider data on a connection without outstanding requests a valid response, SHOULD close it; 0.2.1 review)

**Tests that pin it.**

- `ClientH1Test.staleConnectionRetriedOnceForGet`, `.negative_postNotRetriedOnStaleConnection`, `ClientRaceTest.staleConnectionFromTheRaceIsRetried`, `h1.H1IdleConnectionTest.*`

## <a id="s9-3-6-client-connect-tunnel"></a>§9.3.6, §11.7.2; RFC 9931 §8 — client CONNECT tunnel

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §9.3.6, §11.7.2; RFC 9931 §8 (client CONNECT tunnel).

**Requirement.** HTTPS through an HTTP proxy: a CONNECT tunnel (before the fix the proxy address was cast to the wrong type and every proxied request failed).

**Recorded status.** ✅ 0.2.0

**How it is met.**

- `Proxy-Authorization` and `Proxy-Connection` go on the CONNECT only, never inside the tunnel to the origin
- `Content-Length`/`Transfer-Encoding` of a `2xx` CONNECT response are ignored
- interim 1xx responses before the CONNECT's final one are skipped, with the same 64 KiB bound by bytes as for a request (RFC 9110 §15.2; 0.2.1 review, before a 1xx failed the tunnel), a 101 is a final answer that refuses the tunnel
- no tunnel byte (TLS ClientHello, WebSocket handshake) is sent before the proxy's 2xx (RFC 9931 §8 MUST, option 1: wait for a 2xx before forwarding payload)

**Tests that pin it.**

- `ClientProxyTest.negative_proxyCredentialsStayOnTheConnect`, `.contentLengthOnConnectResponseIsIgnored`, `.interimResponsesBeforeTheConnectAnswerAreSkipped`, `.negative_noTunnelByteBeforeTheConnectAnswer`, `h1.H1ResponseHeadTest.negative_endlessInterimResponsesToTheConnectFail`

## <a id="s5-5-client-response-head"></a>§5.5, §6.2, §15; RFC 9112 §2.2, §4, §5.2 — client response head

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §5.5, §6.2, §15; RFC 9112 §2.2, §4, §5.2 (client response head).

**Requirement.** The response head and the proxy's CONNECT response are read by the engine before Ktor's parser sees them: a control character other than HTAB (NUL, a bare CR, 0x01–0x08, 0x0A–0x1F, 0x7F) in a field line or the reason phrase fails the response with `ParserException` and closes the connection (§5.5: NUL, CR and LF MUST be rejected or replaced, the other CTLs are invalid; 0.2.1 review, before NUL reached the application).

Quoted: "A client ... SHOULD process ... as if it had a 5xx (Server Error) status code".

**Recorded status.** ✅ 0.2.1

**How it is met.**

- an obs-fold is replaced with one SP (§5.2: a user agent MUST; before, Ktor's parser failed the response), a field value that starts with a Unicode space sent as obs-text (U+00A0, ...) is kept as sent (§5.5: opaque data; §5.6.3: OWS is SP and HTAB; Ktor's parser skipped it), so such a Content-Length or Transfer-Encoding is invalid framing (RFC 9112 §6.3) and the application sees other values as the server sent them (0.2.1 review, as the server engine), and a line that starts with whitespace right after the status line is rejected (§2.2)
- the status line is `HTTP-version SP 3DIGIT [SP reason-phrase]`, else `ParserException` (before, `HTTP/1.1 20` and `HTTP/1.1 2000` without a reason phrase passed)
- three digits outside 100–599 are an invalid status code, which "A client ... SHOULD process ... as if it had a 5xx (Server Error) status code" (RFC 9110 §15): the response is a 500 with the code and reason sent as its description (`600 Six`; before 0.2.1 it was passed on as is, a 042 looking like a success) (the SP before an absent reason phrase may be missing: nothing requires a client to reject that line, and §4 has it ignore the reason phrase), `HTTP/1.x` with x > 1 is processed as HTTP/1.1 (RFC 9110 §6.2 SHOULD; before, it failed), another major version fails

**Tests that pin it.**

- `h1.H1ResponseHeadTest.negative_nulInFieldValueFails`, `.htabAndObsTextInFieldValuePass`, `.obsFoldInResponseIsUnfolded`, `.negative_foldRightAfterTheStatusLineFails`, `.negative_statusCodeNotThreeDigitsFails`, `.invalidStatusCodeIsProcessedAs5xx`, `.negative_unicodeSpaceBeforeAFramingValueIsInvalid`, `.unicodeSpaceBeforeAFieldValueIsKept`, `.statusLineWithoutReasonPhraseIsAccepted`, `.higherMinorVersionIsProcessedAsHttp11`

## <a id="s5-1-server-request-field-lines"></a>§5.1, §5.5, §5.6.3; RFC 9112 §5.1, §5.2 — server request field lines

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §5.1, §5.5, §5.6.3; RFC 9112 §5.1, §5.2 (server request field lines).

**Requirement.** A field name that is not a token (DEL, bytes above 0x7F; before 0.2.1 passed), empty, followed by whitespace before the colon, or an obs-fold line → 400 and close.

**Recorded status.** ✅ 0.2.1

**How it is met.**

- a value that starts with obs-text decoding to a Unicode space (U+00A0, U+2000, ...) reaches the engine and the application as sent (OWS is only SP and HTAB, obs-text is opaque field content, §5.5 SHOULD; Ktor's parser stripped it, so `X-A: <U+00A0>a` arrived as `a` and `Content-Length: <U+00A0>5` framed a body), which makes such a Content-Length, Transfer-Encoding or Host invalid → 400 and close (0.2.1)
- obs-text is passed on (0.2.1; before, Ktor's parser refused only CR and LF and a NUL reached the application)

**Tests that pin it.**

- `h1.H1RequestHeadCheckTest.negative_controlCharactersInAFieldValueAreRejected`, `.tabsSpacesAndObsTextInAFieldValueAreAccepted`, `.negative_fieldNameMustBeAToken`, `.unicodeSpaceBeforeAFieldValueIsKept`, `.negative_unicodeSpaceBeforeAFramingValueIsRejected`, `.unicodeSpaceInsideAFieldValueIsAccepted`, `ServerH1FramingTest.negative_nonOwsWhitespaceInFramingFieldsIsRejected`

**Peer interop notes.**

- a field value with a control character other than HTAB (NUL, VT, FF, DEL, a bare CR, ...) → 400 and close (§5.5: a recipient of CR, LF or NUL MUST reject the message or replace them with SP; field-content is VCHAR, obs-text, SP and HTAB), as Go's net/http

## <a id="s8-6-server-response-framing-fields"></a>§8.6; RFC 9112 §6.1, §6.2 — server response framing fields

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §8.6; RFC 9112 §6.1, §6.2 (server response framing fields).

**Requirement.** No 2xx response to CONNECT goes out (the engine answers 501 instead, see the RFC 9931 §8 row), so none carries Content-Length or Transfer-Encoding (MUST NOT).

**Recorded status.** ✅ 0.2.1

**How it is met.**

- a response with Transfer-Encoding never also carries Content-Length (§6.2 MUST NOT): an application's Content-Length on content Ktor frames with `chunked` is dropped (0.2.1; before, both went out)
- a 1xx or 204 response goes out without Content-Length and Transfer-Encoding (MUST NOT), a 304 without Transfer-Encoding and without the `Content-Length: 0` Ktor adds for empty content (a 304 MAY omit it; MUST NOT send one other than the 200's length; an application's other value stays) (0.2.1; before, `respond(NoContent)` said `Content-Length: 0` and a streamed 204 or 304 `Transfer-Encoding: chunked`)

**Tests that pin it.**

- `ServerH1ResponseFramingTest.negative_noFramingFieldsOn204And304`, `.negative_noContentLengthWithTransferEncoding`, `.negative_2xxToConnectIsAnswered501`

## <a id="s9-3-2-server-responses-without-content"></a>§9.3.2, §6.4.1, §15.3.5, §15.4.5; RFC 9112 §6.3 item 1 — server responses without content

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §9.3.2, §6.4.1, §15.3.5, §15.4.5; RFC 9112 §6.3 item 1 (server responses without content).

**Requirement.** What the application writes for a response to HEAD, or for a 1xx, 204 or 304 response, is dropped and its fields stay (a HEAD response keeps the Content-Length or Transfer-Encoding a GET would have), and a streamed body for one is never produced (its writer does not run, its channel is not read).

**Recorded status.** ✅ 0.2.1

**How it is met.**

- the engine's own 400 and 505 to a HEAD request keep their Content-Length and carry no content (`h1.H1RequestHeadCheckTest.negative_noContentInARefusalOfHead`)
- an HTTP/1.0 HEAD response is not forced to close (0.2.1; before, `head("/") { call.respondText("x") }` without AutoHeadResponse sent `x`, which a keep-alive client read as the start of the next response).
- The HTTP/3 server already dropped it

**Tests that pin it.**

- `ServerH1ResponseFramingTest.negative_noContentForHeadAnd204And304`, `ServerH3Test.headAnd204And304SendNoData`

## <a id="s6-6-1-server-date"></a>§6.6.1 — server Date

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §6.6.1 (server Date).

**Requirement.** Every final response the HTTP/1.1 engine writes carries `Date` in IMF-fixdate unless the application set one (Ktor's DefaultHeaders plugin does): application responses and the engine's own 400, 408, 414, 431, 501 and 505 (MUST for an origin server with a clock in 2xx–4xx, MAY in 5xx; not on `100 Continue`), formatted once per second and shared by the responses of that second (0.2.1; before, only with DefaultHeaders, never on the engine's refusals).

**Recorded status.** ✅ 0.2.1

**Tests that pin it.**

- `ServerH1ResponseFramingTest.responsesCarryDate`, `h1.HttpDateCacheTest.oneFormattingPerSecond`

## <a id="s7-8-server-upgrade-in-http-1-0"></a>§7.8, §15.2 — server Upgrade in HTTP/1.0

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §7.8, §15.2 (server Upgrade in HTTP/1.0).

**Requirement.** The Upgrade field of an HTTP/1.0 request is ignored: the engine does not switch and the application does not see it (MUST ignore; and no 1xx to an HTTP/1.0 client) (0.2.1; before, Ktor's upgrade check did not look at the version, and a WebSocket route answered an HTTP/1.0 client with 101).

**Recorded status.** ✅ 0.2.1

**Tests that pin it.**

- `ServerWebSocketGuardTest.negative_http10UpgradeIsIgnored`

## <a id="s15-5-9-server-timeouts"></a>§15.5.9; RFC 9112 §9.5 — server timeouts

Status: ✅ since 0.2.1 · [summary](../rfc-compliance.md#http)

Original row: RFC 9110 §15.5.9; RFC 9112 §9.5 (server timeouts).

**Requirement.** A request head must be complete `requestHeaderTimeoutSeconds` (30 s) after the accepted connection (TLS handshake included) or the end of the previous response.

**Recorded status.** ✅ 0.2.1

**How it is met.**

- a client that sent part of it gets `408 Request Timeout` with `Connection: close` (§15.5.9: the server has decided to close), one that sent nothing is closed without a response (§9.5: a server may close an inactive connection at any time; a 408 there could cross a request the client is sending).
- The idle timeout closes both directions (before 0.2.1 it closed only the output and the reader waited for ever)
- a request body with no byte for the idle timeout gets 408 (§15.5.9) and the connection closes, the wait after `Expect: 100-continue` starting once `100 Continue` is sent (§10.1.1)

**Tests that pin it.**

- `h1.H1PipelineTimeoutTest.*`, `ServerH1TimeoutTest.*`
