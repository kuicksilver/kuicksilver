# RFC 8879 — TLS Certificate Compression

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="certificate-compression"></a>certificate compression

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 8879.

**Requirement.** Certificate compression, on both sides, over TLS 1.3 (QUIC and TCP).

**Recorded status.** ✅ 0.3.0 (owner decision of 2026-11-16, which reversed "not planned for 0.x": a compressed certificate
chain keeps a server's first flight within QUIC's amplification limit, RFC 9000 §8.1); [roadmap](../../roadmap.md#feature-parity-decided-2026-11-16)

**How it is met.**

- OpenSSL 3.5 implements the extension and the message; its codecs are zlib 1.4 and brotli 1.2.1, built into libcrypto from
  pinned, verified tarballs ([ADR-0025](../../adr/0025-zlib-and-brotli-in-libcrypto.md)); zstd is not built
- on by default on both sides (`TlsConfig.Builder.certificateCompression`, `KSL_OPT_CERT_COMPRESSION`), offering brotli, then
  zlib: a client in its ClientHello, a server in its CertificateRequest
- a server's chain is compressed once per context, when `ksl_ctx_freeze` makes the context immutable (OpenSSL sends only a
  chain compressed beforehand); a chain no algorithm makes smaller goes out as a plain Certificate; a client compresses its
  certificate per handshake (OpenSSL), as the CertificateRequest context is part of the message
- Android and iOS ship brotli's decoder only ([ADR-0025](../../adr/0025-zlib-and-brotli-in-libcrypto.md), for size): there
  a server compresses its chain with zlib and a client sends its certificate uncompressed, as OpenSSL keeps one list for
  what it decompresses and what it compresses with (the extension lists what the sender can decompress, §3, so both
  algorithms are still offered there)
- what the peer's chain came in is `TlsConnection.peerCertificateCompression` and `peerCertificateCompression` of a QUIC
  connection (`KSL_GET_CERT_COMPRESSION`, noted by `ksl_msg_cb` when the message arrives)
- measured with the test chains, the server's QUIC first flight (CRYPTO bytes at Initial and Handshake level): one EC leaf
  1824 → 1782 bytes; leaf and intermediate 2215 → 2003; the 13.7 KB leaf of 700 names and its intermediate 15523 → 2689.
  Plain, the last one exceeds three times a 2400-byte ClientHello and the server stops at 7200 bytes until the client is
  heard again; compressed, its whole flight goes out at once (3104 bytes in datagrams). A WebPKI-like RSA-2048 leaf and
  intermediate (not in the test PKI) measured 2464 → 1876 bytes of Certificate message with brotli

**Tests that pin it.**

- C `negative_aDecoderOnlyClientSendsItsCertificateUncompressed`, `certcomp_quic_default_and_mtls`, `certcomp_tcp_default_brotli_both_ways`, `certcomp_default_is_on_without_the_option`,
  `certcomp_quic_first_flight_smaller`, `negative_certcomp_option_values`
- `CertificateCompressionTest.quicServerChainAndClientCertificateComeCompressedWithBrotli`,
  `.tcpServerChainAndClientCertificateComeCompressedWithBrotli`, `.onByDefault`, `.anOverrideKeepsTheBaseChoice`,
  `.aResumptionHasNoCertificateToCompress`
- `HandshakeLimitsTest.compressedChainFitsTheFirstFlightInsideTheAmplificationLimit`,
  `.negative_plainBigChainIsHeldByTheAmplificationLimit`

**Peers.** OpenSSL itself offers and accepts all of its algorithms by default once it has one (`ssl/ssl_lib.c`, the default
preference list), but a server sends only what was compressed beforehand (`SSL_CTX_compress_certs`). BoringSSL has no
algorithm of its own (`SSL_CTX_add_cert_compression_alg`); ngtcp2's BoringSSL examples register brotli when libbrotli is
found; quiche, quic-go (Go's `crypto/tls`), msquic, quinn and picoquic have none in their sources.

## <a id="s3-negotiation"></a>§3 — the compress_certificate extension

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 8879 §3.

**Requirement.** The extension (27) in a ClientHello offers compressed server certificates, in a CertificateRequest
compressed client certificates; `algorithms<2..2^8-2>`; "if TLS 1.2 or earlier is negotiated, the peers MUST ignore this
extension".

**How it is met.**

- OpenSSL sends it only where TLS 1.3 can be negotiated and ignores it in TLS 1.2 (`SSL_EXT_TLS1_3_ONLY`); a ClientHello whose
  list is empty, of odd length or followed by other bytes is `decode_error`; algorithms the server does not have (zstd, an
  unknown code point) are skipped, and with none left the Certificate goes out plain
- with the option off ksl sets `SSL_OP_NO_RX_CERTIFICATE_COMPRESSION` and `SSL_OP_NO_TX_CERTIFICATE_COMPRESSION`: no extension,
  no compressed certificate sent

**Tests that pin it.**

- C `negative_certcomp_client_hello_extension`, `negative_certcomp_tls12_no_certificate_or_record_compression`,
  `certcomp_tcp_tls12_capable_peers_compress_under_tls13`, `negative_certcomp_peer_without_it_gets_plain_certificates`
- `CertificateCompressionTest.negative_quicPeerWithoutCompressionGetsPlainCertificates`,
  `.negative_tcpPeerWithoutCompressionGetsPlainCertificates`, `.tls12And13PeersCompressUnderTls13`

## <a id="s4-compressed-certificate"></a>§4 — the CompressedCertificate message

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 8879 §4.

**Requirement.** The algorithm "MUST be one of the algorithms listed in the peer's compress_certificate extension"; an
uncompressed_length that does not match the output "MUST abort the connection with the bad_certificate alert"; the data is
"the encoded Certificate message that would have been sent"; a message that "cannot be decompressed" MUST end the connection
with bad_certificate.

**How it is met.**

- a sender takes the first algorithm of the peer's list that is also its own (OpenSSL); a receiver refuses one it did not
  offer with `illegal_parameter` (47), the alert RFC 8446 §6.2 gives a field inconsistent with the handshake (RFC 8879 names
  none for this); a length that does not match, data that does not decompress and an uncompressed_length of 0 are
  `bad_certificate` (42); an empty or short compressed_certificate_message is `decode_error` (50); a CompressedCertificate to
  a side that did not offer the extension is `unexpected_message` (10)
- "the Certificate message that would have been sent": over TLS 1.3 a stapled OCSP response is part of it (the leaf's
  CertificateEntry), and the chain compressed at `ksl_ctx_freeze` holds no session's response. A session that staples sends
  its Certificate uncompressed (`server_status` in `ksl_ocsp.c`); before that a stapled status, a revoked one included, was
  gone for every client that offered compression

**Tests that pin it.**

- C `negative_certcomp_malformed_compressed_certificate` (each field of the server's message, with a valid zlib and brotli
  message as the controls), `negative_certcomp_malformed_client_certificate` (the same on the server's side)
- `CertificateCompressionTest.negative_wrongUncompressedLengthIsBadCertificate`,
  `.negative_algorithmNotOfferedIsIllegalParameter`, `.anUnchangedCompressedCertificateIsAccepted`,
  `.negative_aStaplingSessionSendsItsCertificateUncompressed`

## <a id="s5-security"></a>§5 — decompression limits

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 8879 §5.

**Requirement.** "After decompression, the Certificate message MUST be processed as if it were encoded without being
compressed"; implementations "SHOULD bound the memory usage when decompressing", "MUST limit the size of the resulting
decompressed chain to the specified uncompressed length, and they MUST abort the connection if the size of the output of the
decompression function exceeds that limit", and "MUST apply the same limit as if no compression were used".

**How it is met.**

- OpenSSL's certificate list bound, `max_cert_list` (100 KiB, the default ksl keeps), bounds a plain Certificate, a
  CompressedCertificate and its uncompressed_length alike: a larger announced length is `bad_certificate` before anything is
  decompressed, so at most 100 KiB is allocated for the output; the decompressor writes into exactly uncompressed_length bytes
  and anything else it produces is `bad_certificate` (a zlib or brotli bomb of 1 MiB of zeros stops there)
- brotli's own memory: brotli 1.2.1 sizes its ring buffer by the meta-block length the stream declares (68 bytes made it
  allocate 16.8 MiB); the one-shot decoder OpenSSL calls is `ksl`'s (`tools/openssl/brotli/ksl_decompress.c`), which caps
  its allocations at 3 times uncompressed_length plus 256 KiB, more than any honest stream needs
- the decompressed message goes through the same parser and verification as a plain one (OpenSSL's
  `tls_process_server_certificate`); threat model §3.30 (CWE-409)
- record compression stays off (RFC 9325 §3.3, `SSL_OP_NO_COMPRESSION` and OpenSSL's security level): certificate chains hold
  no secret, so compressing them gives no CRIME-style oracle

**Tests that pin it.**

- C `negative_certcomp_malformed_compressed_certificate` (bombs with zlib and brotli, uncompressed_length above the bound
  and 2^24-1, the 68-byte brotli stream), `negative_certcomp_brotli_memory_bounded`,
  `negative_certcomp_tls12_no_certificate_or_record_compression`
- `CertificateCompressionTest.negative_decompressionBombIsBadCertificate`,
  `.negative_uncompressedLengthAboveTheCertificateListBoundIsBadCertificate`

## <a id="padding-and-rpk"></a>§5, §4 — padding, raw public keys, §6 middleboxes

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 8879 §4, §5, §6.

**Requirement.** "Any padding scheme covering the Certificate message has to address compression within its design or
disable it altogether"; an RFC 7250 raw public key is compressed in its altered form; §6: TLS 1.3 only.

**How it is met.** Kuicksilver pads no handshake message, and uses no raw public keys (OpenSSL compresses only X.509
chains). TLS 1.3 only, as in §3.

**Tests that pin it.** C `negative_certcomp_tls12_no_certificate_or_record_compression`.
