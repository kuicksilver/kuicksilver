## <a id="compatible-version-negotiation-quic-v2"></a>compatible version negotiation, QUIC v2

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9368 / 9369.

**Requirement.** Compatible version negotiation, QUIC v2.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- v2 (`0x6b3343cf`) opt-in on the wire through `quicConfig { versions }`
- v2 labels by the negotiated version through `ksl_ssl_set` (`ksl` ABI 2)
- 0-RTT and tickets across versions: see the RFC 9001 §4.6 row
- RFC 9368 §4 MAY taken strictly on the client (0.3.0 hardening, as ngtcp2): "Clients MUST NOT complete the handshake if they are reacting to a Version Negotiation packet and the Version Information is missing, but MAY do so otherwise." A server that upgraded our version through compatible negotiation (its packets in another version than our first Initial, no Version Negotiation) implements this document, so a missing `version_information` there is a VERSION_NEGOTIATION_ERROR; a server that keeps our version may still omit it (an RFC 9000-only server). picoquic completes such a handshake ("TODO"); quic-go has no compatible negotiation
- RFC 9368 §8 (0.3.0 hardening; before, the handshake failed): a client "starting a QUIC version 1 connection in response to a received Version Negotiation packet" whose server sent no `version_information` "SHALL proceed as if the server's transport parameters contained a version_information transport parameter with a Chosen Version set to 0x00000001 and an Available Version list containing exactly one version set to 0x00000001", so a client that started with v2 reaches a server that knows only QUIC v1 and not this document (ngtcp2 does the same); the downgrade checks run on that substitute. After a Version Negotiation to any other version the parameter stays required (VERSION_NEGOTIATION_ERROR)

**Tests that pin it.**

- `version_information` (0x11) with a downgrade check — `wire.VersionInformationTest.versionInformationRoundTrip`, `.negative_serverChosenVersionMismatchesPacketVersion`, `.negative_clientChosenVersionMismatchesInitial`, `.negative_downgradeAfterVersionNegotiation`, `.missingVersionInformationAfterVnToV1IsTakenAsV1Only`, `.negative_missingVersionInformationAfterVnToV2IsError`, `.validNegotiationPasses`, `.negative_compatibleUpgradeWithoutVersionInformation`, `.missingVersionInformationWithoutUpgradeIsAccepted`
- RFC 9369 §4.1: a Retry in another version than the client's Initial is ignored — `endpoint.RetryTest.negative_retryInOtherVersionIgnored`
- end-to-end negotiation — `core.VersionUpgradeTest.compatibleUpgradeV1ToV2`, `.clientStartingInV2`, `.v1OnlyServerKeepsV1`, `.serverOrderV1V2StaysV1`, `.defaultConfigNeverSendsV2`, `.versionInformationCheckedOnBothSides`

**History.**

- 0.2.0 review, RFC 9368 §4: an Available Version of zero and a client Chosen Version missing from its Available Versions are parsing failures, an empty server list after Version Negotiation is VERSION_NEGOTIATION_ERROR — `.negative_availableVersionZeroRejected`, `.negative_clientChosenVersionNotInAvailableRejected`, `.negative_emptyAvailableVersionsAfterVnRejected`
