## <a id="compatible-version-negotiation-quic-v2"></a>compatible version negotiation, QUIC v2

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#quic)

Original row: RFC 9368 / 9369.

**Requirement.** Compatible version negotiation, QUIC v2.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- v2 (`0x6b3343cf`) opt-in on the wire through `QuicConfig.versions`
- v2 labels by the negotiated version through `ksl_ssl_set` (`ksl` ABI 2)
- 0-RTT and tickets across versions: see the RFC 9001 §4.6 row

**Tests that pin it.**

- `version_information` (0x11) with a downgrade check — `wire.VersionInformationTest.versionInformationRoundTrip`, `.negative_serverChosenVersionMismatchesPacketVersion`, `.negative_clientChosenVersionMismatchesInitial`, `.negative_downgradeAfterVersionNegotiation`, `.missingVersionInformationAfterVnIsError`, `.validNegotiationPasses`
- RFC 9369 §4.1: a Retry in another version than the client's Initial is ignored — `endpoint.RetryTest.negative_retryInOtherVersionIgnored`
- end-to-end negotiation — `core.VersionUpgradeTest.compatibleUpgradeV1ToV2`, `.clientStartingInV2`, `.v1OnlyServerKeepsV1`, `.serverOrderV1V2StaysV1`, `.defaultConfigNeverSendsV2`, `.versionInformationCheckedOnBothSides`

**History.**

- 0.2.0 review, RFC 9368 §4: an Available Version of zero and a client Chosen Version missing from its Available Versions are parsing failures, an empty server list after Version Negotiation is VERSION_NEGOTIATION_ERROR — `.negative_availableVersionZeroRejected`, `.negative_clientChosenVersionNotInAvailableRejected`, `.negative_emptyAvailableVersionsAfterVnRejected`

**Peer interop notes.**

- interop case `v2` (client `versions=[V2,V1]`, `initialVersion=V1`; server `[V2,V1]`), runner 740c05a, 2026-10-07: ngtcp2 ✓✓, msquic ✓✓, picoquic ✓ (we are the client) / ✕ (we are the server — a picoquic defect: the packet that starts the switch to the new version is not decrypted but is acknowledged), quiche — does not support the case
