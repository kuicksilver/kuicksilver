# RFC 7301 — TLS Application-Layer Protocol Negotiation Extension

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset or accepted deviation · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

## <a id="alpn"></a>RFC 9001 §8.1 — ALPN

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 7301, RFC 9001 §8.1.

**Requirement.** ALPN.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- mandatory for QUIC (an empty list is a configuration error), a mismatch closes the connection
- in QUIC a server refuses a ClientHello without the extension and a client a server that negotiated none, both with `no_application_protocol` (CRYPTO_ERROR 0x0178; OpenSSL alone checks only an offered list without overlap)
- over TCP a ClientHello without the extension completes without ALPN, unless the server sets `alpnFallback` (0.3.0): then it is refused with `no_application_protocol` where the protocols in effect (`alpn` or the `sniSelector` answer's, non-empty, without `h3`) leave the fallback out. `ksl` decides it (`KSL_OPT_ALPN_POLICY`) at every ClientHello, the second one after a HelloRetryRequest included (RFC 9846 §4.2.2 forbids the client to change it but tells no server to compare, and OpenSSL does not), and again when the handshake completes. 120 as in RFC 9001 §8.1 ("if an application protocol is not negotiated"); not `missing_extension`, which RFC 9846 §6.2 keeps for an extension "mandatory to send for the offered TLS version or other negotiated parameters"

**Tests that pin it.**

- `TlsConfigTest.emptyAlpnInQuicIsConfigError`, `TlsConnectionTest.negative_alpnMismatchClosesConnection`, `QuicHandshakeTest.handshakeAnchoredCaAlpnH3`, C `quic_no_alpn_is_no_application_protocol`
- `TlsServerTest.negative_aClientWithoutAlpnIsRefusedWhereTheFallbackIsNotOffered`, `.aClientWithoutAlpnConnectsWhereTheFallbackIsOfferedOrNoneIsSet`, `QuicSniTest.aQuicServerIgnoresTheAlpnFallback`, `AlpnExtensionAlertTest.aWellFormedOrAbsentAlpnExtensionGetsThePolicysAnswer`, C `tcp_alpn_policy` (ALPN dropped after a HelloRetryRequest, the check at completion)

## <a id="s3-1-protocol-name-lengths"></a>§3.1 — protocol name lengths

Status: ✅ since 0.2.0 · [summary](../rfc-compliance.md#tls)

Original row: RFC 7301 §3.1.

**Requirement.** Protocol names are 1..255 bytes (UTF-8), not characters.

**Recorded status.** ✅ 0.2.0

**How it is met.**

- the list fits ksl's 255-byte wire buffer
- a server's SNI override passes the same checks
- a server answers a ClientHello whose ALPN extension is malformed ("ProtocolName protocol_name_list<2..2^16-1>", each "ProtocolName<1..2^8-1>", lengths exact) with `decode_error` in `ksl_client_hello_cb`, before the SNI pause or an ALPN policy could answer it with another alert (0.3.0)

**Tests that pin it.**

- `TlsConfigTest.negative_alpnLengthCountedInBytes`, `TlsConfigTest.negative_overrideClientAuthNeedsAnchoredCa`
- `AlpnExtensionAlertTest.negative_aMalformedAlpnExtensionIsDecodeErrorWithOrWithoutTheFallback`, C `negative_malformed_alpn_extension_is_decode_error`
