# RFC 7541 — HPACK: Header Compression for HTTP/2

Details of the rows of the [RFC compliance summary](../rfc-compliance.md) for this document. Each section gives the requirement, how Kuicksilver meets it (with the files), the tests that pin it, its history, notes on peers and the open items. Status: ✅ met · 🔶 feature subset · ⬜ planned · ❌ not planned; "since" is the release from which the current behaviour holds (history below and in [CHANGELOG.md](../../../CHANGELOG.md)).

The code is in `kuicksilver-http2/src/commonMain/kotlin/io/kuicksilver/http2/hpack/` (ADR-0017); it is sans-IO and checked
by `:kuicksilver-http2:checkHttp2Architecture`. QPACK's use of RFC 7541 sections 5.1–5.2 and appendix B is in
[RFC 9204](9204.md#s4-1-primitives-and-static-table).

## <a id="hpack"></a>HPACK

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7541.

**Requirement.** HPACK: the static and dynamic tables (§2.3, §4), the representations (§6), the primitives (§5),
the examples of appendix C.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `HpackDecoder.kt` decodes the five representations of §6 (indexed, literal with incremental indexing, without
  indexing, never indexed, dynamic table size update) over the 1-based index space of §2.3.3; `HpackEncoder.kt` writes
  indexed fields, literals with a static or dynamic name reference and size updates.
- The static table (appendix A) and the Huffman code (appendix B) are generated from the RFC text by
  `tools/http/gen-tables.py`, which also writes the appendix C examples to
  `tools/vectors/hpack-rfc7541-appendix-c.json` and `tools/vectors/hpack-huffman.json` and their Kotlin form for the
  tests; `--check` fails when a committed file, or the Huffman table of `kuicksilver-http3`, differs, and without the RFC
  text (the CI lint job and `tools/ci/local-matrix.sh`) it checks that both modules' tables, the vectors, their Kotlin form
  and the digests agree; `HuffmanTableParityTest` in both modules compares the table's SHA-256 with the generator's.

**Tests that pin it.**

- `hpack.HpackRfcVectorsTest.appendixC2toC6` (every example of C.2–C.6 decoded with the table and its size after each
  block; C.3–C.6 also encoded byte for byte), `.appendixC1Integers`, `.huffmanVectors`, `.huffmanRoundTripAllBytes`,
  `hpack.StaticTableTest.rfc7541AppendixA`, `hpack.HuffmanTableParityTest.tableMatchesGenerator` (and kuicksilver-http3's `qpack.HuffmanTableParityTest.tableMatchesGenerator`)

**History.**

- 0.3.0: new (ADR-0017).

## <a id="s4-dynamic-table-and-size-updates"></a>§2.3, §4, §6.3 — dynamic table and size updates

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7541 §2.3, §4, §6.3.

**Requirement.** Entry size is name + value + 32 (§4.1); eviction from the oldest, and an entry larger than the table
empties it (§4.3, §4.4); a size update MUST occur at the beginning of the first block after a change, and when the
maximum changed more than once the smallest MUST be signalled (§4.2); a size update above the protocol's limit is a
decoding error (§6.3); an index of 0 or beyond the table is a decoding error (§2.3.3, §6.1).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- Decoder: a size update after the first field, or above our SETTINGS_HEADER_TABLE_SIZE, is an `HpackError`; when the
  acknowledged setting falls below the table's size (`HpackDecoder.setMaxTableSize`), the next block must start with an
  update to at most the smallest such value.
- Encoder: the table is min(our ceiling of 4096, the peer's SETTINGS_HEADER_TABLE_SIZE); every change is signalled at
  the start of the next block, the smallest value first, then the final one.

**Tests that pin it.**

- `hpack.HpackLimitsTest.negative_tableSizeUpdateAboveSettingIsCompressionError`,
  `.negative_tableSizeUpdateAfterFirstFieldIsCompressionError`, `.negative_requiredTableSizeUpdateMissing`,
  `.negative_indexZeroAndBeyondTable`, `.encoderRespectsPeerTableSize`; the table states of
  `hpack.HpackRfcVectorsTest.appendixC2toC6` (C.5 and C.6 evict at 256 bytes)

**History.**

- 0.3.0: new.

## <a id="s5-integers-strings-huffman"></a>§5.1–5.2, app. B — integers, strings, Huffman

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7541 §5.1–5.2, app. B.

**Requirement.** Integer encodings that exceed implementation limits, in value or octet length, MUST be decoding
errors (§5.1); a Huffman string with padding longer than 7 bits, padding that is not the most significant bits of EOS,
or the EOS symbol inside MUST be decoding errors (§5.2).

**Recorded status.** ✅ 0.3.0

**How it is met.**

- `HpackPrimitives.kt` (copied from kuicksilver-http3's `QpackPrimitives.kt`, ADR-0017): integers above 2^31 − 1 or
  with more than five continuation bytes are errors (no HPACK quantity is larger); a string's declared length is checked
  against the bytes left in the block and against the decoder's `maxStringLength` before anything is allocated.
- `Huffman.kt` (copied from kuicksilver-http3): the output never grows past `maxStringLength`; EOS, long or non-ones
  padding and invalid codes are errors. The encoder chooses Huffman only when it is shorter (§5.2 leaves this open).

**Tests that pin it.**

- `hpack.HpackLimitsTest.negative_integerOverflow`, `.negative_hugeStringLengthRejectedBeforeAllocation`,
  `.negative_huffmanEosOrBadPadding`

**History.**

- 0.3.0: new.

## <a id="s7-security"></a>§7 — security

Status: ✅ since 0.3.0 · [summary](../rfc-compliance.md#http)

Original row: RFC 7541 §7.

**Requirement.** Compression-based attacks on secrets (§7.1): never-indexed literals for values that are secret or
easy to guess (§7.1.3); memory consumption of the decoder (§7.3): the dynamic table is bounded by the setting, and a
decoder can limit the strings and the decoded list it accepts.

**Recorded status.** ✅ 0.3.0

**How it is met.**

- The encoder sends `authorization`, `proxy-authorization`, `set-cookie` and `cookie` values under 20 bytes as never
  indexed literals, and per-message values (`:path`, `content-length`, dates, validators, `location`) and fields above
  half the table without indexing.
- The application marks its own fields sensitive, and keeps the representation of fields it forwards (§6.2.3 "when a
  peer sends a header field that it received represented as a literal header field never indexed, it MUST use the same
  representation to forward this header field"; §7.1.3 "An intermediary MUST NOT re-encode a value that uses the
  never-indexed literal representation with another representation that would index it"): the decoder reports each
  field's never-indexed bit (`HpackDecoder.decodeFields`), the HTTP/2 runtime hands the never-indexed regular fields of
  a request or response to the engines (`H2ServerStream.neverIndexed`, `H2ResponseHead.neverIndexed`), and the encoder
  sends the fields named by the caller as never indexed literals, neither referring to the table nor adding to it
  (`HpackEncoder.encode(fields, neverIndexed)`). In the Ktor engines (experimental): `ApplicationRequest.neverIndexedHeaders`
  and `ApplicationResponse.neverIndex` on the server, `HttpResponse.neverIndexedHeaders` and `HttpRequestBuilder.neverIndex`
  on the client, so an application that proxies with both engines can keep the bit.
- The decoder counts the decoded list as RFC 9113 §6.5.2 does; past its `maxHeaderListSize` the sink gets no more fields
  but the block is decoded to its end, so the table stays in step with the encoder and the connection can go on (RFC
  9113 §8.2); indexed references reuse the table's strings, so a block of references to one large entry (an "HPACK
  bomb") allocates nothing per reference. The connection core bounds the compressed block before it is decoded
  (threat model 3.23).

**Tests that pin it.**

- `hpack.HpackLimitsTest.sensitiveFieldsNeverIndexed`, `.neverIndexedBitIsReportedOnDecoding`,
  `.negative_fieldsMarkedNeverIndexedAreNeitherIndexedNorReferenced`, `ServerH2Test.neverIndexedFieldsCrossBothEngines`
  (the client's marked field and its `authorization` reach the server's call as never indexed, the server's marked
  response field reaches the client), `.negative_hpackBomb` (16 KiB of one-byte references to a
  4 KiB entry: 16 fields reach the sink, nothing is allocated for the references, the next block still resolves)

**History.**

- 0.3.0: new; the application API for the never-indexed bit came with the open-rows audit of 2026-11 (before, the bit
  was dropped on decoding and only the engine's own list of credentials was sent never indexed).

**Notes on peers.**

- OkHttp 5.3.2 does not use never-indexed literals for sensitive fields (`Hpack.kt`, KDoc of `Writer.writeHeaders`:
  "This does not use 'never indexed' semantics for sensitive headers"); Netty 4.2.16 leaves it to a
  `SensitivityDetector` whose default (`Http2HeadersEncoder.NEVER_SENSITIVE`) marks nothing. nghttp2 never indexes
  `authorization` and `cookie` values under 20 bytes ("the same criteria used in Firefox", `nghttp2_hd.c:1394-1400`); we
  add `proxy-authorization` and `set-cookie`.

**Scope.** Header sections only: trailers of either engine are sent with the engine's own rules and their bit is not
reported, as the Ktor APIs carry no per-field trailer metadata. The same Ktor API carries QPACK's 'N' bit over HTTP/3
([RFC 9204](9204.md#s2-2-decoder)).

**Open items.** None.
