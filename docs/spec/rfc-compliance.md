Date: 2026-10-02; as of 0.2.1 (2026-10-21). Status: living document, updated with each change it describes. Legend: ✅ implemented · 🔶 partial · ⬜ planned (release) · ❌ not planned (reason).

0.2.0 is the first release (TLS, QUIC v1/v2, HTTP/3, the Ktor engines and the 0.2.0 work); the "Status" column shows the release that brought the behaviour (0.2.0, or 0.2.1 for what changed after it) and the tests that pin it. ⬜ rows are planned; see [the roadmap](../roadmap.md).

`msquic->kuicksilver:rebind-addr` (not required since 2026-10-09) — when the simulator's rebind at 1 s swallows msquic's PATH_CHALLENGE to the new address (run 20261009-040848: pn 430 to the new address and pn 431 to the old one both lost), msquic retransmits the challenge only to the old address, keeps sending data to the new one under its amplification limit and idles out; `quiche` — the image runs under emulation, the client exits with code 254 on `multiplexing` and the rebind cases; the server stops the transfer after the port change (130–190 KB of 10 MB, every run): the simulator's 25-packet queue drops a slow-start burst right before the 1 s rebind, quiche's `set_active_path` runs loss detection on the old path once (`Recovery::on_path_change` → `detect_lost_packets`, time and packet threshold against the ACKs seen so far) and never again — the inactive path has no PTO and our ACKs on the new path only drive the new path's recovery — so packets sent in the last ~30 ms before the migration (here pn 300–346, one of them the retransmission of the 153-byte hole at offset 144121) are never retransmitted; `kuicksilver-native->picoquic:rebind-port` — analysed in the final review: not Native-specific but a race in the simulator. The runner's first rebind happens at 1 s; when picoquic's first Initial lands 0.5 ms before it, the repeated Initials come from the new port, and the server (before the fix) kept answering to the old one until the handshake timeout expired. Fixed (row "RFC 9000 §9, §8.1 (rebind during the handshake)"): after the fix the handshake completes, the file is downloaded (JVM 13 s, Native 23 s for 10 MiB), the first packet to the new port is a PATH_CHALLENGE and picoquic answers it. The remaining red in the `rebind-*` cells with picoquic (roughly every third run, JVM and Native alike) is a runner artifact: picoquic coalesces the PATH_RESPONSE into one datagram with its Handshake packet, while the runner's check looks only at the first QUIC layer of the datagram (`testcases_quic.py`, `path_response.data` of `p["quic"]`) and considers the challenge unanswered (pcap of local run 20261008-113008, answer at 2.064 s). The same traces show that the server repeats PATH_CHALLENGE to the old address every PTO without exponential backoff (§8.2.4 "no more often than Initial") — deferred as a minor finding.
