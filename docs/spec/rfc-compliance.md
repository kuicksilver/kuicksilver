# Kuicksilver — RFC compliance matrix

Date: 2026-10-02, updated 2026-10-08 (K3–K5 and the full review). Status: living document, updated per milestone. Legend: ✅ implemented · 🔶 partial · ⬜ planned (milestone) · ❌ not planned (reason).

Milestones K0–K5 are implemented (TLS, QUIC v1/v2, HTTP/3, Ktor engines); the "Status" column shows the milestone in which the behaviour appeared and the tests that pin it. ⬜ rows are what is left for K6 and after v1.

`kuicksilver-native->picoquic:rebind-port` — analysed in the final review: not Native-specific but a race in the simulator. The runner's first rebind happens at 1 s; when picoquic's first Initial lands 0.5 ms before it, the repeated Initials come from the new port, and the server (before the fix) kept answering to the old one until the handshake timeout expired. Fixed (row "RFC 9000 §9, §8.1 (rebind during the handshake)"): after the fix the handshake completes, the file is downloaded (JVM 13 s, Native 23 s for 10 MiB), the first packet to the new port is a PATH_CHALLENGE and picoquic answers it. The remaining red in the `rebind-*` cells with picoquic (roughly every third run, JVM and Native alike) is a runner artifact: picoquic coalesces the PATH_RESPONSE into one datagram with its Handshake packet, while the runner's check looks only at the first QUIC layer of the datagram (`testcases_quic.py`, `path_response.data` of `p["quic"]`) and considers the challenge unanswered (pcap: `build/interop/20261008-113008`, answer at 2.064 s). The same traces show that the server repeats PATH_CHALLENGE to the old address every PTO without exponential backoff (§8.2.4 "no more often than Initial") — deferred as a minor finding.
