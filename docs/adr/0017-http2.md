# ADR-0017. HTTP/2 in 0.3.0: a `kuicksilver-http2` module next to `kuicksilver-http3`

Date: 2026-11-04. Status: accepted (approved by the owner 2026-10-22; scope widened by the owner 2026-11-04; WebSocket
over HTTP/2, RFC 8441, implemented 2026-11-12). Supersedes ADR-0009.

## Context

ADR-0009 left HTTP/2 out of v1: the client falls back to HTTP/1.1 where HTTP/3 is not available (UDP blocked, no
`Alt-Svc`, a proxy). That fallback costs up to `maxConnectionsPerRoute` (100) TCP and TLS connections per origin, each
with its own handshake and congestion window, and no multiplexing, while almost every CDN and API in front of a client
speaks h2. HTTP/2 makes the TCP fallback the second-best path instead of the worst.

An HTTP/2 server is also the most attacked HTTP surface of the last years: the 2019 flood family (CVE-2019-9512 to
CVE-2019-9518), Rapid Reset (CVE-2023-44487), the CONTINUATION flood (CVE-2023-45288, CVE-2024-27316 and the 2024
advisories of other stacks) and MadeYouReset (CVE-2025-8671). Every limit has to be in the core from the first commit,
with a `negative_*` test each.

## Decision

- **A new published KMP module, `kuicksilver-http2`**, beside `kuicksilver-http3`: HTTP/2 needs neither QUIC nor TLS
  and runs over any byte stream; the Ktor engines bring the TCP socket and TLS (`kuicksilver-ktor-network`) and depend
  on `kuicksilver-http3`, `kuicksilver-http2` and `kuicksilver-ktor-network` (ADR-0005, clarification 2026-11-04).
- **Its only project dependency is `kuicksilver-native`, for the API annotations** (`ExperimentalKuicksilverApi`,
  `InternalKuicksilverApi`). The plan approved on 2026-10-22 said "no project dependency at all"; that is not possible
  while the annotations live in `kuicksilver-native`: a second copy of `io.kuicksilver.annotations` in this module
  would break Android builds (AGP's duplicate-class check) whenever both artifacts are on the classpath, which they
  always are in the engines. Every consumer of this module (the two engines) already depends on `kuicksilver-native`,
  so the edge costs nothing in practice. The owner kept this edge for 0.3.0 (2026-11-05). Its costs: a consumer of
  `kuicksilver-http2` alone would download the native artifact (the JNI libraries in the JVM jar, the `ksl` cinterop
  klibs) and the layer rule names one more edge. The way out does not break anyone: a `kuicksilver-annotations`
  artifact with the same package and class names, which `kuicksilver-native` and this module both depend on with
  `api`, so the classes stay on every consumer's classpath under the same names.
- **Sans-IO core** (ADR-0004): the packages `io.kuicksilver.http2.frame` (RFC 9113 sections 4 and 6), `hpack`
  (RFC 7541) and `core` (connection and stream state, flow control, SETTINGS, PING, GOAWAY and the flood limits) take
  bytes in and give bytes out, with time as a parameter; `checkHttp2Architecture` runs `tools/check/sans-io.sh` on
  them. A coroutine runtime over Ktor's byte channels comes with the engine integration.
- **Copies under a generator, not a shared module.** The Huffman table (RFC 7541 appendix B) is the one QPACK uses;
  `tools/http/gen-tables.py` writes this module's copy and its static table (appendix A) from the RFC text, together
  with the RFC 7541 appendix C vectors in `tools/vectors/`, and `--check` fails when either module's Huffman table
  body differs from the generated one; `HuffmanTableParityTest` compares the table's SHA-256 with the generator's. The
  Huffman decoder and the prefixed-integer and string primitives are copied from `kuicksilver-http3` (about 300 lines,
  cited in their KDoc). A shared `kuicksilver-http-common` module would add a publication, a BOM entry, ABI dumps and a
  stability promise for code that hardly changes.
- **Public API is minimal:** `Http2Settings` and `Http2ErrorCode` under `@ExperimentalKuicksilverApi`; the codec, HPACK
  and the core are `internal` until the engines need them, then `@InternalKuicksilverApi`. The module is published to
  Maven Central and listed in the BOM; `docs/stability.md` lists it as experimental.
- **No h2c** (neither prior knowledge nor `Upgrade: h2c`): HTTP/2 only after ALPN `h2` over TLS (RFC 9113 sections 3.2
  and 3.3 make cleartext optional).
- **No server push**: the client sends `SETTINGS_ENABLE_PUSH = 0` and refuses PUSH_PROMISE; the server never pushes.
- **RFC 9218 priorities on h2 (update 2026-11-12, owner decision; it replaces "no RFC 7540 priorities and no
  PRIORITY_UPDATE on h2")**: a server ignores RFC 7540 signals (PRIORITY frames and HEADERS priority fields are parsed
  for their errors only; RFC 9113 section 5.3.2 deprecates them) and says so with `SETTINGS_NO_RFC7540_PRIORITIES = 1`
  (RFC 9218 section 2.1). It schedules each response's DATA by the request's `Priority` field, the client's
  PRIORITY_UPDATE frames (section 7.1, with the section 7 buffering for streams not open yet) and the response's own
  field (section 8). A client leaves the setting out and follows section 2.1.1: its request HEADERS carry an RFC 7540
  signal (dependency 0, not exclusive, a weight from the urgency, Chromium's mapping) next to the `Priority` field until
  the server's SETTINGS say `SETTINGS_NO_RFC7540_PRIORITIES = 1`; it sends PRIORITY_UPDATE before those SETTINGS and
  while they say 1, never after a server left the setting at 0, and an RFC 7540 PRIORITY frame with a reprioritization
  until they say 1. Interop: a libnghttp2 server of the releases that still implemented RFC 7540 priorities, with
  `server_fallback_rfc7540_priorities` set, falls back to RFC 7540 scheduling for a client that does not send
  `SETTINGS_NO_RFC7540_PRIORITIES = 1` — ours. Such a server schedules our requests by the weights we send, not by the
  `Priority` field: all of them depend on stream 0, so it shares bandwidth in proportion to the weights (256 for u=0 down
  to 1 for u=7) instead of serving urgencies strictly in order, and ignores the incremental parameter. The option does
  nothing in current nghttp2 (1.71.90, which no longer implements RFC 7540 priorities).
- **Never-indexed fields** (RFC 7541 §7.1.3): the encoder never indexes `authorization`, `proxy-authorization`,
  `set-cookie` and `cookie` values under 20 bytes (owner, 2026-11-05: keep this policy). Later, with the engines' needs:
  an API for the application to mark its own fields as sensitive, and the never-indexed bit exposed on decoding for
  intermediaries.
- **The driver contract of the connection core** (for the engine integration): the driver calls `consumed` as the
  application reads and `release` for every stream once it is done with it, on the client too (a response read to its
  end, or abandoned); unread content is credited back to the connection then. A client that never releases its streams
  keeps them in the core and, after a GOAWAY, never sees the connection close. A server answers a field section marked
  `tooLarge` with 431; a client fails that request.
- **No connection coalescing** (RFC 9113 section 9.1.1) in 0.3.0.
- **Scope of 0.3.0 (owner, 2026-11-04):** the whole HTTP/2 section ships in 0.3.0: the client, the server (with its
  flood defences, h2spec in the release gate and its own fuzz target) and WebSocket over HTTP/2 (RFC 8441). The code
  freeze for it is 2026-11-25. This replaces the "client required, server stretch, RFC 8441 later" plan of 2026-10-22.
  Defaults as approved on 2026-10-22: the client offers `h2` when the engine's HTTP/2 support is enabled (default on);
  the server's HTTP/2 is opt-in (`http2 = false`) in 0.3.0.
- **Server engine (update 2026-11-06, task H2.6):** HTTP/2 is offered (`h2` before `http/1.1` in ALPN) only on TLS
  connectors and only over TLS 1.3, which is all the server engine negotiates: a TLS 1.2 renegotiation could not be
  refused as RFC 9113 section 9.2.1 requires (the client's reason for the same rule, plan item H2.4b). The engine keeps
  its HTTP/1.1 deadlines for HTTP/2 (`requestHeaderTimeoutSeconds` for the preface and every field block,
  `connectionIdleTimeoutSeconds` for request content and idle connections, the send-stall deadline for the client's
  window), and stops with the core's two-step GOAWAY. RFC 8441 was not part of this step (see below).
- **Server flood defences (update 2026-11-06, task H2.7):** the per-connection limits of the core are the defence;
  the engine adds the send-stall deadline (on progress) for what a connection that is over still has to write, and an
  opt-in backoff by address (`http2RepeatOffenderPenalty`, off by default; decided in review 2026-11-06): three
  connections ending in a flood limit's ENHANCE_YOUR_CALM within a minute close the address's TCP connections at accept,
  before TLS, for the penalty (an IPv4-mapped peer as its IPv4 address, an IPv6 one by its /56). Off by default because
  one flooder behind a shared address (CGNAT, a corporate NAT, an L4 load balancer or Kubernetes Service with SNAT, a TCP
  proxy) would lock out everyone behind it; RFC 9113 section 10.5 does not ask for it, and Go's and nghttp2's servers ban
  no addresses. Enable it only when the server is directly exposed and sees real client addresses. h2spec 2.6.0 (all 146 cases) is part of the release gate
  (`tools/interop/h2spec.sh`).
- **WebSocket over HTTP/2 (update 2026-11-12, task H2.8, RFC 8441):** the server engine's `webSocketsOverHttp2` (on by
  default, as `webSocketsOverHttp3`; it acts only with `http2`, which stays opt-in) advertises
  SETTINGS_ENABLE_CONNECT_PROTOCOL and serves `webSocket {}` routes over an Extended CONNECT as over HTTP/3 (RFC 9220):
  the request is shown to Ktor as its HTTP/1.1 upgrade request, answered `:status 200`, and the stream carries the
  frames. The client engine opens a `wss` WebSocket over HTTP/2 only on a connection to its origin that is there already
  and whose server allowed Extended CONNECT, after that server's SETTINGS arrived; otherwise its own connection offers
  `http/1.1` only, as in 0.2 (Chromium's choice: no HTTP/2 connection is opened for a WebSocket, so a server without RFC
  8441 never costs an extra connection). No client switch of its own: `http2 { enabled = false }` turns it off with HTTP/2.

## Consequences

- One more published artifact (Maven Central, BOM, SBOM, ABI dumps) and one more sans-IO core with its architecture
  check and fuzz targets (`http2.frames`, `http2.hpackDecode`; the connection targets come with the engines).
- A larger attack surface on the server; its limits live in `Http2Settings` and the core, each with a row in the threat
  model (section 3.23) and a `negative_*` test.
- Servers with a broken h2 stack (old proxies, middleboxes) that got HTTP/1.1 before now get h2; the engine's fallback
  rules and a switch to turn h2 off cover them.
- Two copies of the Huffman table and the integer and string primitives; drift is caught by the generator's check, the
  parity test and the shared vectors.

## Alternatives rejected

- **`kuicksilver-http-common`** shared by http2 and http3: fewer copies, but another artifact and ABI for about 700
  lines that rarely change.
- **HTTP/2 inside `kuicksilver-ktor-network`**: no new artifact, but a protocol with HPACK and a state machine inside the
  socket layer, without the sans-IO check, and a mixed ABI.
- **HTTP/2 inside `kuicksilver-http3`** or depending on it: every h2 user would pull QUIC, and the http3 → quic layer
  would be false.
- **A copy of the annotations in `kuicksilver-http2`** (to have no project dependency): duplicate classes on Android.
