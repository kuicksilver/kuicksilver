class CertificateRevocationList(der: ByteArray)

A certificate revocation list (RFC 5280 section 5) in DER form, for TrustConfig.AnchoredCa: every certificate on a path that trust verifies is checked against the CRL of its issuer, when one of the configured CRLs is. The CRL itself is checked when a handshake uses it (its signature under the issuer's key, thisUpdate and nextUpdate): an expired CRL fails every handshake whose path it covers (VerifyReason.UnknownRevocationStatus), so replace it before its nextUpdate (TrustConfig.ReloadableCa on a server).

OcspStapling
Link copied to clipboard
class OcspStapling(response: ByteArray? = null)

The OCSP response (RFC 6960, DER OCSPResponse) a server staples for its certificate (RFC 6066 section 8; in TLS 1.3 in the leaf's CertificateEntry, RFC 9846 section 4.5.1.1), which RFC 9325 section 7.5 asks servers to support. Set on a server's TlsConfig.Builder.ocspStapling; update replaces the response at run time (fetch a fresh one from the CA's responder before the current one's nextUpdate). Each handshake takes the current response when the ClientHello arrives, and staples it only when the client asked for it and the response is for the certificate the handshake presents (its issuer the certificate of the configured chain that issued it), verifies, and is inside its validity interval at that moment: a stale response, or one for another certificate (after the identity was reloaded), is never sent, and the handshake goes on without one.

RevocationPolicy
Link copied to clipboard
enum RevocationPolicy : Enum<RevocationPolicy>

How a client treats the revocation status of the server's certificate that the server staples (OCSP, RFC 6066 section 8 and RFC 9846 section 4.5.1.1), the strategy RFC 9325 section 7.5 asks for ("TLS implementations MUST implement a strategy to distrust revoked certificates"). It applies where ksl's own verifier checks the chain: TrustConfig.AnchoredCa, and TrustConfig.Platform on Linux Native, also inside TrustConfig.Pinned and TrustConfig.ExpectedName. Properties

alertCode
Link copied to clipboard
val VerifyReason.alertCode: Int

The TLS alert code that TlsException.Verify produces (RFC 9846 section 6.2) when the reason comes from a verifier that chooses the alert (a CertificateVerifier, the platform, pins). Where ksl decides, the alert sent follows OpenSSL: a failed stapled OCSP check is always bad_certificate_status_response (113, RFC 6066 section 8), whatever the reason (VerifyReason.Revoked, VerifyReason.InvalidStatusResponse, VerifyReason.UnknownRevocationStatus) and also with TlsConfig.genericAlerts; a configured CRL gives the alert OpenSSL maps its error to (ssl_x509err2alert): certificate_revoked (44) for a revoked certificate, certificate_expired (45) for an expired CRL, bad_certificate (42) for a CRL not valid yet, with a bad time field or a signature that does not decrypt, decrypt_error (51) for a CRL signature that does not verify, unknown_ca (48) when no usable CRL or CRL issuer is found, and certificate_unknown (46) for a CRL of another scope, an issuer without cRLSign or an unknown critical CRL extension.

expect fun keylogFile(path: String): KeylogSink

A KeylogSink appending RFC 9850 lines to path; the file is created with mode 0600 (docs/guide/tls.md, Key logging). The path is checked here, before any secret exists: a symlink, a file that is not a regular file, has more than one hard link or belongs to another user, or a file system without POSIX permissions throws IllegalArgumentException; an existing file readable by the group or others is tightened to 0600 (Windows only creates the file). On the JVM the file is opened once, here, and every line goes through that descriptor, so a file removed and recreated at the path later receives nothing; the JVM sink is also java.io.Closeable and keeps the descriptor until it is closed (or collected, or the process exits). Kotlin/Native reopens the file for every line without following links and repeats the checks on the new descriptor. A line that cannot be written is dropped, not retried. The library never consults SSLKEYLOGFILE on its own; keylogFromEnvironment reads it when the application calls it.
