Reloadable

class Reloadable : TlsIdentity, AutoCloseable(source)

A server (or client) identity that can be replaced while the process runs: certificate rotation without a restart. Made by TlsIdentity.reloadable; use it as TlsConfig.identity (or a connector's identity) like an InMemory.

One identity per handshake. Every TLS handshake (TCP connections and QUIC sessions alike) takes the current snapshot when the client's ClientHello arrives (over TCP when its first bytes are there, not at the accept; over QUIC with its first Initial) and runs on an OpenSSL context built from that snapshot's chain and key, so a handshake presents a consistent pair (RFC 9846 section 4.5.1, Certificate, and 4.5.2, CertificateVerify, are made from the same identity) whatever reload does meanwhile. The handshakes of one server configuration share one context per snapshot: the first handshake after a reload builds one from the new identity, and the old one is freed once the identity it was built from is closed (the reload closes it) and its last connection is gone. Handshakes in progress and established connections keep the identity they started with; reload affects every handshake whose ClientHello arrives after it returns, also on a connection accepted before.

Ownership. The reloadable identity owns the InMemory it was made with and each one reload accepted: reload closes the identity it replaces, and close closes current. A closed InMemory frees its native key only when the last context built from it is gone, so replacing an identity never pulls the key out from under a running connection. Do not close current yourself. An identity reload refused stays the caller's to close.

Resumption and 0-RTT. Every server binds its session tickets to the leaf certificate they were issued under (RFC 9846 section 4.7.1): after a reload to another certificate, a ticket from before it resumes nothing, the client runs a full handshake and sees the new certificate, and 0-RTT of such a ticket is refused (the replay register is not reset). Independently of reloads, a chain of renewed tickets ends 7 days after the full handshake that authenticated it, and at the leaf's notAfter. A resumed connection presents no certificate (RFC 9846 section 2.2): it keeps the identity of the session it resumes, which is the current one. After a key compromise, a reload is enough to stop new handshakes and resumptions with the old key; connections already established run on until they close.

Checks. reload refuses a closed identity, one whose leaf certificate has expired, and one whose leaf is not valid yet (notBefore more than 5 minutes ahead of the clock: a certificate staged for later is never served early); the pairing of key and chain was already checked when the InMemory was built (fromPem, fromDer), so a mismatched pair never gets here. next must not be closed by anyone else: an identity closed during the reload is refused.
