ReloadableCa

class ReloadableCa : TrustConfig(source)

A server's client-certificate CA bundle that can be replaced at run time (made by TrustConfig.reloadable): the client CA rotates without a restart, as TlsIdentity.Reloadable rotates the server certificate. Servers only: wherever an AnchoredCa verifies client certificates (clientAuth Optional or Required), alone or as the base of Pinned; a client configuration with one throws TlsException.Config.

The rule. After reload returns, no handshake accepts a client certificate that only a removed CA vouches for, over TCP and QUIC alike and however the client times its flights; connections established before are not affected. A handshake takes the current bundle when the client's ClientHello arrives (over TCP when its first bytes are there, not at the accept; over QUIC with its first Initial) and OpenSSL verifies the client's certificate against it; when the handshake completes and a reload has replaced that bundle with other certificates meanwhile, the certificate is verified again against the bundle current then, as a handshake would (OpenSSL's security level included), the pins of a Pinned around this trust are checked on the path built under it, and the handshake fails unless both pass. A reload to the same certificates changes nothing. The one case this refuses that a fresh handshake would accept: a session resumed across a reload that changed the certificates carries only the client's leaf, so it passes only if that leaf chains to the new bundle without intermediates. Close connections of a compromised CA yourself. The handshakes of one server configuration share one OpenSSL context per identity and bundle; the first handshake after a reload builds one with the new bundle and drops the old one from the shared contexts, which is freed once that has happened and its last connection is gone (a handshake that read the old bundle while the new one's context was built gets a context of its own, freed with it). With clientAuth None the bundle plays no part: a reload changes nothing then. The server's CertificateRequest carries no certificate_authorities extension (RFC 9846 section 4.3.4: "The server MAY send it"), so no CA list is announced that a reload would have to change.

Resumption. A session resumes only under the bundle it was authenticated with: after a reload a ticket issued before it resumes nothing (RFC 9846 section 4.7.1: "A server MAY treat a ticket as valid for a shorter period"); the client runs a full handshake, and its certificate is verified against the new bundle. A client whose CA was dropped cannot get back in with a ticket.

Checks. reload refuses a bundle in which no certificate is valid now (each expired, or not valid yet beyond 5 minutes of clock skew): it could accept no client. A bundle with some expired certificates is accepted (they anchor nothing). The pins of a Pinned around this trust do not change with a reload.
