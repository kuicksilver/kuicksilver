SessionTicketConfig

class SessionTicketConfig(keys: List<ByteArray>? = null, val rotateEvery: Duration = 1.days, val ticketLifetime: Duration = 12.hours)(source)

Server-side session tickets: a current key and previous keys; rotation at most weekly, lifetime at most half of it. Invalid values throw TlsException.Config on construction. A TLS-over-TCP server always issues tickets with these keys and lifetime; a QUIC server issues tickets only when it accepts 0-RTT (QuicServerConfig.earlyData), and then with these keys and lifetime too. Clients ignore it.

The keys never live on the Kotlin heap (threat model 3.7): generated keys are made and rotated inside the native library, and explicit keys are copied there on construction, after which every array in the list is zeroed.

Parameters

keys

explicit 80-byte entries (name 16 | AES-256 32 | HMAC-SHA256 32, at most 64), first encrypts, for servers in several processes that must resume each other's tickets; null (the default) = keys generated in this process. The arrays are zeroed when the constructor returns, also when it throws; keep the source of the keys (a secret store), not the arrays. Explicit keys are not rotated by the library: construct a new configuration with the new key first and the old one after. Each distinct set stays in native memory for the life of the process (at most 1024 distinct sets).

rotateEvery
Link copied to clipboard
val rotateEvery: Duration

how often the process-wide generated keys rotate (default 1 day, positive, at most 7 days); the previous key still decrypts until the next rotation. The generated keys are one set per process, shared by every server that uses them: configurations with different periods rotate the same keys, so the shortest period in use sets the pace (a ticket then resumes for at least one such period). Explicit keys are not rotated by the library. A longer period lets one stolen ticket key decrypt more resumed sessions (RFC 9846 section 4.7.1).

val ticketLifetime: Duration

how long an issued ticket resumes (default 12 hours, at least 1 second, at most rotateEvery / 2, whole seconds); a longer lifetime widens the window in which resumptions can be linked to one client.
