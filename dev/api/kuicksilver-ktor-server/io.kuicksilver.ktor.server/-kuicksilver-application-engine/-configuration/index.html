connectionIdleTimeoutSeconds
Link copied to clipboard
var connectionIdleTimeoutSeconds: Int

Seconds an HTTP/1.1 connection stays open without a request: then it is closed, both directions. On a keep-alive connection requestHeaderTimeoutSeconds also runs from the end of the last response, so the smaller of the two closes an idle connection. A response the client reads nothing of (its socket takes nothing) ends the connection after the longer of this and 5 minutes: the engine sees a client's reading progress about 1 MiB at a time (the buffer in front of the socket), and 1 MiB in 5 minutes keeps clients down to about 3.4 KiB/s. A closing connection sends what is left for as long as the client takes it, and is aborted after the same time without progress. A request body that sends no byte for this long (counted after 100 Continue when the client asked for it) fails the handler's read; the client gets 408 when no response has started, and the connection closes. Each wait for body bytes has its own deadline, so a slow but moving upload is read in full.

http2
Link copied to clipboard
var http2: Boolean

Serve HTTP/2 (RFC 9113) on TLS connectors: ALPN offers h2 before http/1.1, so a client that offers both gets HTTP/2 (docs/guide/ktor.md, "HTTP/2 on the server"). Off by default in 0.3.0, so the ALPN of a TLS connector stays http/1.1 unless this is set. Plain connectors are not affected: they serve HTTP/2 only with their own opt-in, h2c (KuicksilverPlainConnector.Builder.h2c); without it a client's PRI * preface is answered 505 HTTP Version Not Supported, as before. Over TLS 1.3, and over TLS 1.2 on a connector that allows it (versions = TlsVersions.Tls12And13; RFC 9113 section 9.2). WebSockets come over HTTP/2 too (RFC 8441), unless webSocketsOverHttp2 is turned off.

http2RepeatOffenderPenalty
Link copied to clipboard
var http2RepeatOffenderPenalty: Duration

Off (Duration.ZERO, the default): each HTTP/2 connection that breaks a flood limit of http2Settings is ended with GOAWAY ENHANCE_YOUR_CALM, and that is all. Positive: a client address whose HTTP/2 connections end that way three times within a minute has its TCP connections (HTTP/1.1 too) closed at accept, before the TLS handshake, for this long (docs/guide/ktor.md, "HTTP/2 on the server"; threat model 3.23). An IPv6 client counts by its /56, an IPv4-mapped one by its IPv4 address; a slow field block is not a strike. Enable it only where the server sees the real address of each client (directly exposed, or behind a proxy that keeps client addresses, such as one that preserves the source IP): behind a NAT, a load balancer that rewrites source addresses (SNAT, Kubernetes externalTrafficPolicy: Cluster) or a TCP proxy, every client shares the proxy's address and one flooder locks them all out. EngineMain key kuicksilver.http2RepeatOffenderPenalty (a duration such as 30s; 0 is off).

identityReloadInterval
Link copied to clipboard
var identityReloadInterval: Duration?

How often EngineMain looks at the PEM files of kuicksilver.tls.certificateChain and kuicksilver.tls.privateKey for a renewed certificate (configuration key kuicksilver.tls.reloadInterval, e.g. 1h); null (the default) reads them once at startup. A new chain is applied once two reads a second apart agree and the key matches it; a failure keeps the identity in use, is logged, and is retried after 1 s, then twice as long each time up to this interval. New handshakes get the new certificate, running connections keep theirs (docs/guide/ktor.md, "Certificate rotation"). The client CA file of kuicksilver.tls.clientCa, when set, is watched at the same interval and by the same rules: new handshakes verify client certificates against the new bundle. It needs those two keys: the server refuses to start with it set otherwise. At least 1 second.

maxTcpConnections
Link copied to clipboard
var maxTcpConnections: Int

The most TCP connections each connector holds at once, HTTP/1.1 and HTTP/2 alike, counted from accept (TLS handshakes included) until the socket is released. At the limit the connector stops accepting: the OS backlog holds new clients (their connect succeeds, nothing is read from them) until a connection closes, and the server spends no descriptor or TLS work on them. When the backlog is full too (511 on the JVM, 50 on Kotlin/Native) the OS drops further connection attempts (Linux by default; the client's TCP retries them) or resets them. The default does not protect a process whose descriptor limit is lower (ulimit -n: 256 in a macOS shell, often 1024 on Linux): raise that limit or set this below it (docs/guide/ktor.md, "Connection limits"). At least 1; default 10,000. EngineMain key kuicksilver.maxTcpConnections.

maxTcpConnectionsPerIp
Link copied to clipboard
var maxTcpConnectionsPerIp: Int?

The most TCP connections one client address holds at once on a connector, HTTP/1.1 and HTTP/2 alike; null (the default) turns the limit off. Behind a reverse proxy, a load balancer, Kubernetes source NAT or any NAT every client shares one address, and an HTTP/1.1 proxy opens an upstream connection per request in flight (and one per WebSocket or SSE stream): enable it (256, say) only when the server faces its clients directly. A connection over it is reset right after accept, before its TLS handshake (its address is not known earlier), which a proxy in front reports as 502 or 503, and it is reported to KuicksilverServerEventListener.connectionRefused with the reason per-IP limit. An address is its bytes, never a name: an IPv4-mapped client as its IPv4 address, an IPv6 client by its whole address (as QUIC maxConnectionsPerIp), so a client holding a /64 gets around it. At least 1, or null. EngineMain key kuicksilver.maxTcpConnectionsPerIp (0 or absent is off).

quicEarlyData
Link copied to clipboard
var quicEarlyData: Boolean

Accept 0-RTT on HTTP/3 (off by default; ADR-0015). Early requests can be replayed by an attacker: by default only GET, HEAD and OPTIONS run before the handshake completes (http3Settings.earlyData decides), every other request waits for it. Handlers of early requests must be free of side effects; see ApplicationRequest.receivedEarly. A request a gateway marked Early-Data (RFC 8470 section 5.1) is treated as early whatever this setting.

requestHeaderTimeoutSeconds
Link copied to clipboard
var requestHeaderTimeoutSeconds: Int

Seconds a client has to send a complete HTTP/1.1 request head (request line and header fields), counted from the accepted TCP connection for the first request (the TLS handshake included) and from the end of the previous response for the next one on a keep-alive connection; bytes that trickle in do not extend it. A client that sent part of a head by then gets 408 Request Timeout and the connection closes; one that sent nothing (an idle keep-alive connection, or a connection that never spoke) is closed without a response. It also bounds the field-block deadline maxHeaderBlockTime of http2Settings and http3Settings. Positive; default 30.

udpSocketCount
Link copied to clipboard
var udpSocketCount: Int

Endpoint loops on the UDP port, as Ktor-Netty's udpSocketCount, on every platform with a QUIC server: a socket per loop with kernel SO_REUSEPORT flow hashing on Linux and Android, one socket whose datagrams are routed to the loops by connection ID in process on macOS, iOS and Windows (docs/guide/quic.md, "Several loops on one port"). One connection runs on one loop. Where the accelerated socket cannot open (a JVM on the portable socket), more than 1 cannot run: the engine logs why and serves HTTP/1.1 only on that connector.

webSocketMaxMessageSize
Link copied to clipboard
var webSocketMaxMessageSize: Long

The largest WebSocket message, and so frame, the server takes from a client, in bytes (RFC 6455 section 10.4: an implementation "SHOULD impose a limit on frame sizes and the total message size after reassembly"); 16 MiB by default, as PerMessageDeflate's maxInflatedMessageSize. A frame whose header claims more, or that takes its message past it, closes the connection with 1009 (message too big) before any of its payload is read; a compressed message is held to the smaller of this and the extension's limit, counted inflated. Over HTTP/1.1, HTTP/2 and HTTP/3 alike; Ktor's WebSockets { maxFrameSize } applies on top of it.

webSocketsOverHttp2
Link copied to clipboard
var webSocketsOverHttp2: Boolean

Accept WebSockets over HTTP/2 (RFC 8441) on the connections of http2: their SETTINGS carry SETTINGS_ENABLE_CONNECT_PROTOCOL = 1, and an Extended CONNECT with :protocol = websocket reaches Ktor's webSocket {} routes as an upgrade request, answered :status 200 (docs/guide/ktor.md, "WebSockets over HTTP/2"). On by default, as webSocketsOverHttp3; it has no effect while http2 is off. When false the parameter is not sent, and a client keeps opening its WebSockets over HTTP/1.1. EngineMain key kuicksilver.webSocketsOverHttp2.
