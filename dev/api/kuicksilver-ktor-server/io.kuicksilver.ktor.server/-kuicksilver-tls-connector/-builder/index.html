keyExchangeGroups
Link copied to clipboard
var keyExchangeGroups: KeyExchangeGroups

The key-exchange groups of TCP and QUIC handshakes, in the server's order of preference (TlsConfig.Builder.keyExchangeGroups); default KeyExchangeGroups.Default. The server takes the first of them a client sent a key share for, else asks for the first the client supports with a HelloRetryRequest; a client with none of them is refused with handshake_failure. Key shares are a client's setting: a list with them makes the server's start fail. With versions Tls12And13 the list needs an elliptic curve, the hybrids being TLS 1.3 only, and with clientAuth it also limits the curves of a TLS 1.2 client's ECDSA certificate (RFC 8422 section 5.1): without secp256r1 a P-256 client certificate is refused with illegal_parameter.

sniSelector
Link copied to clipboard
var sniSelector: suspend (ClientHelloInfo) -> ServerTlsOverride??

Picks an identity per SNI name (TlsConfig.Builder.sniSelector), on TCP and HTTP/3 connections alike: one selector answers both, so a name gets the same certificate, client-certificate policy and staple over HTTP/1.1, HTTP/2 and HTTP/3, and the Alt-Svc the TCP side advertises leads to a QUIC endpoint that presents the same identity. On HTTP/3 it runs off the connection's loop, as on TCP inside the handshake. An answer's alpn restricts the name: without one the name gets every protocol of the connector; with one, TCP negotiates from it without h3 (QUIC only, RFC 9114 section 3.1: a list of h3 alone ends the name's TCP handshake with no_application_protocol; a client without ALPN speaks HTTP/1.1, RFC 9113 section 3.3, refused there when the list leaves http/1.1 out), and HTTP/3 is served (and advertised with Alt-Svc on that name's TCP responses) only when it lists h3, else the QUIC handshake ends with no_application_protocol. Return the same TrustConfig and OcspStapling objects for a name, so that its handshakes share one TLS context. Null with SNI present refuses the handshake (unrecognized_name); null for a ClientHello without SNI leaves the connector's own identity to answer it. A request on such a connection must be for the name its identity was chosen for (else 421, RFC 9110 section 7.4). Null by default.

trustedGateway
Link copied to clipboard
var trustedGateway: Boolean

False by default: a request for an https URI whose host the certificate presented on its connection does not name (subjectAltName, as a client checks it) is answered 421 Misdirected Request and never reaches the application, on HTTP/1.1, HTTP/2 and HTTP/3 alike (RFC 9110 section 7.4; on HTTP/2 and HTTP/3 the connection stays open for other requests). A browser that reuses a connection for another host of the same address sends such requests. True turns the check off for this connector: only when every client of it is a trusted gateway (RFC 9110 section 7.4: "Unless the connection is from a trusted gateway") that forwards requests for names this certificate does not carry, such as a TLS-terminating proxy that re-encrypts with an internal certificate.

versions
Link copied to clipboard
var versions: TlsVersions

The TLS versions TCP connections may negotiate: TlsVersions.Tls13 (the default) refuses a client without TLS 1.3 with a protocol_version alert (RFC 9846 appendix E.2); TlsVersions.Tls12And13 also serves TLS 1.2 clients (RFC 9325 section 3.1.1: "Implementations MUST support TLS 1.2"), and a client that offers TLS 1.3 still gets it. TLS 1.2 runs under the RFC 9325 profile: ECDHE with AES-GCM or ChaCha20-Poly1305 only (no static RSA, no CBC, no SHA-1 MAC), Extended Master Secret required, no renegotiation, no compression; a TLS 1.2 session resumes for at most SessionTicketConfig.ticketLifetime after its full handshake, however often its ticket is renewed (at most half a rotateEvery period; explicit ticket keys are rotated by the application, which then keeps that period itself). HTTP/2 (when on) is offered over TLS 1.2 as well (RFC 9113 section 9.2); with a certificate without an rsaEncryption key (an EC or an RSA-PSS one) the start logs a warning, since RFC 9113 section 9.2.2 asks such deployments to support TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256. HTTP/3 stays TLS 1.3 (RFC 9001 section 4.2).
