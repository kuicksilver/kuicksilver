acceptQueue
Link copied to clipboard
val acceptQueue: Int

Handshaken connections waiting for accept() (shared by all loops), never more. While this many wait, a new client Initial is answered statelessly with an Initial CONNECTION_CLOSE carrying CONNECTION_REFUSED (0x02), under the stateless rate limits, so the client fails at once instead of at its handshake timeout and no TLS handshake is spent on it; a handshake admitted earlier that completes while this many wait is closed with CONNECTION_REFUSED instead of joining the queue. Handshakes in flight are not counted (unvalidated, possibly spoofed Initials must not lock real clients out); they are bounded by maxConnections, maxConnectionsPerIp and the ConnectionAdmission policy.

dispatcher
Link copied to clipboard
val dispatcher: CoroutineDispatcher?

The single-threaded dispatcher of the endpoint loop; null means Dispatchers.Default.limitedParallelism(1). While datagrams keep coming, the loop reads the ones already queued at the socket on this dispatcher's thread. On its own dispatcher (null here) it also waits there for the next ones, at most 1 ms at a time and never past its next timer (not on Windows); on a dispatcher supplied here it never waits, as other work shares the thread (a UI, or a second endpoint whose datagram it would be waiting for).

loops
Link copied to clipboard
val loops: Int

Endpoint loops sharing the port, each on its own thread (docs/guide/quic.md, "Several loops on one port"); more than one needs a server. Where the accelerated socket is granted SO_REUSEPORT (Linux, Android) each loop has its own socket and the kernel balances the flows; elsewhere (Apple, Windows, a caller-supplied io) the loops share one socket, whose receiver hands each datagram to the loop its connection ID names. One connection lives on one loop either way. Without the accelerated transport (and no io) bind throws UnsupportedOperationException.
