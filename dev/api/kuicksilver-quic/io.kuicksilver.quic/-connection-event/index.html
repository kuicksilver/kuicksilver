StreamFinalSize
Link copied to clipboard
class StreamFinalSize : ConnectionEvent

The final size of one half of stream id is fixed (RFC 9000 section 4.5): for sending, once the sending half's reset was queued (RESET_STREAM, RESET_STREAM_AT, or the answer to the peer's STOP_SENDING) or its FIN first went out; for the receiving half, once the peer's FIN, RESET_STREAM or RESET_STREAM_AT told it, whether or not the bytes were read. size is the flow-control credit the stream consumed. Raised once per half; for a client stream sent in 0-RTT only after the server accepted it (a rejection drops the stream instead).

StreamFinished
Link copied to clipboard
class StreamFinished : ConnectionEvent

Stream id is done in both directions — its sending half acknowledged, or reset with that RESET_STREAM acknowledged (RFC 9000 section 3.1), its receiving half read to the end or reset and consumed — and was retired: its state is gone and, for a peer stream, its credit returns through MAX_STREAMS (for one that ended with our reset, at that reset's acknowledgment, when this is raised). Raised once.

class StreamsAvailable : ConnectionEvent

The peer raised its stream limit (bidi or unidirectional) with MAX_STREAMS (RFC 9000 section 4.6) after ConnectionCore.openStream was refused at the old one: retry the open. Raised once per refusal.

StreamWritable
Link copied to clipboard
class StreamWritable : ConnectionEvent

Stream id can make progress again: acknowledgements freed send-buffer room after ConnectionCore.writeStream took fewer bytes than offered, or the peer raised its flow-control credit (MAX_STREAM_DATA, MAX_DATA; RFC 9000 section 4.1) while the stream had data waiting to be sent. Retry the write; the event is a hint, a write may still take fewer bytes when other streams share the buffer. Also, for a stream whose QuicStream.sendReleased is followed, once acknowledgements or a reset released some of its buffered bytes.
