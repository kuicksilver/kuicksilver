QuicEndpoint

interface QuicEndpoint : AutoCloseable(source)

A bound UDP endpoint hosting QUIC connections: one endpoint loop, or QuicEndpointConfig.loops of them on one port (docs/architecture.md, kuicksilver-quic).

close() closes every connection with CONNECTION_CLOSE (code 0) and then the socket. It is asynchronous: it returns at once and the loop finishes the work, so a port reused right after may still be bound for a moment; connect and accept throw QuicException.EndpointClosing from then on. closeAndJoin waits for that work.

connect

abstract suspend fun connect(remote: InetSocketAddress, config: QuicClientConfig): QuicConnection

Opens a connection; returns once the handshake completed. Failures are QuicException.ConnectionLost; cancellation is never wrapped, and a cancelled call closes the connection it started. QuicException.ConnectionLost.Internal when 16 draws of a connection ID all hit one the endpoint loop already routes (RFC 9000 section 10.3.2: an ID belongs to one connection; only likely with a short connectionIdLength and many connections).

connectEarly
Link copied to clipboard
open suspend fun connectEarly(remote: InetSocketAddress, config: QuicClientConfig): QuicConnection

As connect for a client with QuicClientConfig.earlyData: returns as soon as 0-RTT keys exist, so what the application writes before the handshake completes travels in 0-RTT (RFC 9001 section 4.6). Without a usable ticket it returns at handshake completion, and under EarlyDataState.Required it then throws QuicException.ConnectionLost.ZeroRttRejected. Early data can be replayed by an attacker: write early only what is safe to execute twice, and use QuicConnection.awaitHandshake before the rest. When the server rejects 0-RTT, every stream opened before the handshake completed is reset (RFC 9001 section 4.6.2: the client "MUST reset the state of all streams") and fails with QuicException.StreamError.EarlyDataRejected; nothing of it reached the server, and the application sends again on new streams what it still wants.

updateLoadBalancer
Link copied to clipboard
open suspend fun updateLoadBalancer(config: QuicLbConfig?)

Switches the server's connection IDs to another QUIC-LB configuration (draft-ietf-quic-load-balancers-21 section 3.1, experimental; docs/guide/quic.md, "Behind a load balancer"); the endpoint must have been built with QuicEndpointConfig.loadBalancer. New IDs use config from the return on; every live server connection gets one NEW_CONNECTION_ID of it that retires its earlier IDs, which keep routing (and may be answered with a Stateless Reset) until the next change. With null the endpoint issues unroutable IDs (codepoint 0b111, section 3.2): new connections get one ID and disable_active_migration, live ones keep theirs. Deliver the configuration to the load balancers first (section 3.1). The configuration is built on Dispatchers.IO (a nonce reservation's first store may fsync) and switched to on the endpoint's loops, one update at a time; once switched, cancelling the caller does not undo it. The call waits for the configuration's nonce reservation (its first store) and for the loop it switches on, and cannot be cancelled while it does: a QuicLbNonceReservation that hangs, or a wedged loop, holds it and every later update. In a group the switch happens on loop 0, and the other loops move their connections after the call returns (in the background, without the caller waiting on any of them); a loop that does not do so within 5 s is logged at Warn and moves them at its next receive batch.
