earlyData
Link copied to clipboard
var earlyData: Boolean

Default false. True issues session tickets that allow 0-RTT and accepts early data (RFC 9001 section 4.6): fresh (OpenSSL's ±10 s ticket-age check), once per ticket (the server's replay register) and only for the configuration that issued the ticket. A connection then reaches accept() as soon as its 0-RTT is accepted, before the handshake completes: early data can still be a replay, so the application acts on anything not safe to repeat only after QuicConnection.awaitHandshake(). Not with client certificates.

Application settings a 0-RTT client relies on (HTTP/3 SETTINGS, RFC 9114 section 7.2.4.2), bound into tickets with the ALPN and the transport limits: a ticket from another configuration gets no early data. At most 256 bytes.

newTokenLifetime
Link copied to clipboard
var newTokenLifetime: Duration?

Default 24 hours; null issues none. Once a connection's handshake is confirmed the server sends the client one NEW_TOKEN token (RFC 9000 section 8.1.3), and another after the client moved to a new IP address (at most four per connection). A client that presents one on its next connection from the same IP address, within this lifetime and for the first time, counts as validated (ConnectionAttempt.addressValidated): no Retry under ConnectionAdmission.AlwaysRetry and no anti-amplification limit on the first flight. A token that does not validate is treated as absent, never refused. Tokens are sealed with keys that live only in this process (rotated hourly); at most 7 days.

newTokenReplayCapacity
Link copied to clipboard
var newTokenReplayCapacity: Int

Default 1,048,576 (1..16,777,216). A NEW_TOKEN token validates one connection: the server remembers each one it accepted for at least newTokenLifetime in a register sized for this many per lifetime, made when the first token is shown (32 MiB at the default; about 32 bytes per token, rounded up to a power of two per stripe). Past that, a returning client's token is treated as absent (it may get a Retry) until older entries age out: never a second use. All loops of the endpoint share it.

preferredAddress
Link copied to clipboard
var preferredAddress: PreferredAddress?

Default null. Otherwise the endpoint also listens on these addresses (a socket per family; every loop of a group shares the port, as for the main one) and advertises them in preferred_address with its sequence-1 connection ID (RFC 9000 sections 9.6 and 18.2). A client that follows (QuicConfig.followPreferredAddress) validates the new path after the handshake and moves there; the server moves too once the client's address is validated on the preferred socket, and the original path closes. Only connections live there: a new Initial on a preferred socket is dropped. A move to it is taken even with allowMigration = false, from the client's current address only.
