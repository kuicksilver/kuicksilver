clearOnNetworkChange
Link copied to clipboard
var clearOnNetworkChange: Boolean

Forget alternatives without persist=1 when the network changes, as RFC 7838 section 2.2 says a client SHOULD; true by default (before 0.2.1, false). False keeps them across networks. The network is networkId, or the networks connectionMigration follows while networkId is not set. With networkId a change is also seen across restarts, against the network the store's entries were learned on (AltSvcStore.networkId); with the followed networks a start counts as a change (Http3ConnectionMigration.networks). Without either source the engine sees no change.

connectionMigration
Link copied to clipboard
var connectionMigration: Http3ConnectionMigration?

Lets pooled HTTP/3 connections follow the device's network (connection migration, RFC 9000 section 9; docs/guide/ktor.md, "Connection migration"): on a switch from Wi-Fi to the mobile network, a connection moves to a socket bound to the new network over a validated path with a fresh connection ID, so a download over HTTP/3 carries on. Null (the default) leaves every connection on the socket it was opened on, as in 0.2: it survives only if the system routes that unbound socket over the new network and the server takes it as a NAT rebinding, and may die at its idle timeout otherwise. Http3ConnectionMigration.followDefaultNetwork(connectivity) on Android and Http3ConnectionMigration.followDefaultNetwork() on iOS and macOS follow the system's default network; see Http3ConnectionMigration for other platforms and the rules. While networkId is not set, the networks the hook follows (Http3ConnectionMigration.networks) are the engine's network: a change resets broken marks and drops non-persistent alternatives as a networkId change does.

diagnosticsLogLevel
Link copied to clipboard
var diagnosticsLogLevel: LogLevel?

The level at which the engine's logger gets one line per answered call that HTTP/3 could have served but did not (docs/guide/ktor.md, "Why did this request not use HTTP/3?"): a lost race, a fallback, a broken alternative, a proxy, HTTP/3 turned off. LogLevel.Info by default, which the default logger (warnings and up) leaves out; calls over HTTP/3, and calls HTTP/3 was never a candidate for (http://, H1Only, Auto without Alt-Svc), are logged at LogLevel.Debug. Null writes no line. The line names the method, scheme, host, port and path, never the query or the user info: kuicksilver: GET https://example.com/ -> HTTP/1.1 (fallback=HandshakeTimeout, alt=example.com:443 via AltSvc, raced, headStart=10ms, h3Failure=Timeout, marked broken).

earlyData
Link copied to clipboard
var earlyData: Boolean

Resume HTTP/3 connections with 0-RTT (off by default; ADR-0015): the engine keeps the servers' session tickets for its lifetime and sends GET, HEAD and OPTIONS requests without a body before the handshake completes; every other request waits for it, and a 425 Too Early is retried once. Early requests can be replayed by an attacker (RFC 9846 section 8): turn this on only for servers whose safe methods are free of side effects.

endpoint
Link copied to clipboard
var endpoint: QuicEndpointConfig

The client QUIC endpoint (dispatcher, crypto provider, socket factory). Its connectionIdLength and the one of KuicksilverEngineConfig.quic are kept equal: the one left at its default follows the other, and two different explicit values fail the engine's creation with IllegalArgumentException. The engine binds it to the wildcard address (0.0.0.0:0, dual-stack); connections to a loopback server leave from up to two more endpoints of this configuration, one per family, bound to 127.0.0.1 (for 127.0.0.0/8 and its IPv4-mapped form) and ::1, each created at its first use, so that no other local process holding that port on the loopback address gets the server's replies. The endpoints share the engine's session tickets.

hardDelay
Link copied to clipboard
var hardDelay: Duration?

Head start of HTTP/3 over HTTP/1.1 on a network where QUIC was confirmed; null: 1.5 x the host's smoothed RTT, or 250 ms without history, clamped to 100 ms..2 s. An explicit value must be 10 ms..2 s (RFC 8305 section 5), or Duration.INFINITE for HTTP/1.1 only after HTTP/3 failed, on every network; another one fails the engine's creation with IllegalArgumentException. On a network where QUIC was never confirmed the head start is 10 ms, whatever finite value is set.

http3Allowed
Link copied to clipboard
var http3Allowed: () -> Boolean

A kill switch for HTTP/3 (docs/guide/ktor.md, "Turning HTTP/3 off remotely"), called once per https:// request (not with Http3DiscoveryMode.H1Only) on the call's coroutine before anything connects: it must be quick and must not block, such as reading an AtomicBoolean or a StateFlow.value that your remote configuration updates. While it returns false, requests go over TCP as with H1Only (ProtocolReason.Http3Disabled; HTTP/2 stays on: this switch is HTTP/3's only, http2 { enabled } is HTTP/2's), open HTTP/3 connections take no new requests (calls running on them finish; idle ones close after idleTimeout, or at once with HttpClient.closeHttp3Connections()), and Alt-Svc is still learned, so switching back needs no warm-up. With Http3DiscoveryMode.H3Only a request fails with UnsupportedOperationException instead, before any connection: that mode never uses TCP, and so does HttpClient.webTransport (WebTransport has no TCP fallback). A switch that throws an Exception counts as true (HTTP/3 allowed), so a broken configuration cannot break traffic; the engine logs that once per 5 minutes at most. HttpClient.closeHttp3Connections() also drains open WebTransport sessions.

httpsRecordExtraWait
Link copied to clipboard
var httpsRecordExtraWait: Duration

How long a request waits for the HTTPS records after the origin's addresses resolved (50 ms by default, as Chromium): an answer that comes later is cached for the next request, and this one goes on without records. 50 ms (RFC 9460 section 5.1: an optimistic connection SHOULD wait that long) to 1 s; any other value fails the engine's creation with IllegalArgumentException. The connect timeout bounds the whole wait.

httpsRecords
Link copied to clipboard
var httpsRecords: HttpsRecordSource

Where Http3DiscoveryMode.Auto looks up HTTPS resource records (RFC 9460; docs/guide/ktor.md, "HTTPS records"): HttpsRecordSource.Off (the default), the system resolver (HttpsRecordSource.System) or your DNS-over-HTTPS exchange (HttpsRecordSource.Exchange). An https:// request to a host name asks for the origin's records (the name for port 443, _<port>._https.<name> otherwise), follows AliasMode records, and connects to their endpoints in priority order over the transports each allows (HTTP/3 and TCP racing for alpn=h3, TCP to the record's target and port), then to the origin as without records; the certificate is checked against the origin's name whatever the target. The address hints are not used, nor is ech (a record that requires it is skipped). A cached Alt-Svc alternative is tried first. No lookup is made for Http3DiscoveryMode.Preferred, Http3DiscoveryMode.H3Only, quicHints, IP addresses, requests through a proxy, or while http3Allowed says no. An http:// request (in every discovery mode) first asks for the records of its https URL and, when the origin has any usable one, gets a 307 to that URL from the engine instead (RFC 9460 section 9.5). Answers are cached for their TTL (at most 1 day; "no records" for the SOA's negative TTL, not at all without one; at most 1000 names) until the network changes, and only when the engine sees the network: networkId is set, or connectionMigration follows one (RFC 9460 section 12); a failed lookup is not cached.

maxWebTransportSessions

var maxWebTransportSessions: Int

WebTransport sessions (HttpClient.webTransport) open at once on this client, over all its connections (they share the pooled ones, up to settings.webTransportMaxSessions a connection); one more fails at once with IllegalStateException, nothing waits. 64 by default, at least 1 (draft-ietf-webtrans-http3-16 section 8: "a WebTransport client SHOULD limit the number of outgoing sessions it will open").

networkId
Link copied to clipboard
var networkId: () -> String?

Identifies the current network; a change resets "broken" marks, QUIC confirmation and the HTTPS record cache, and drops alternatives without persist=1 (clearOnNetworkChange). null: one network. While it is not set, the networks connectionMigration follows (Http3ConnectionMigration.networks) are the network, when it has them (the followDefaultNetwork factories do); without either, the engine sees no network change and keeps no HTTPS records of its own (httpsRecords): RFC 9460 section 12 requires that cache to be flushed on network changes.

var webTransportIgnoresConnectUdpProxy: Boolean

WebTransport (HttpClient.webTransport) to a URL connectUdpProxy applies to connects directly instead of being refused; false by default. WebTransport sessions do not go through the CONNECT-UDP tunnel, so this exposes the client's address to the origin, which the proxy otherwise hides. Separate from webTransportIgnoresProxy, which is about HTTP and SOCKS proxies only.

webTransportIgnoresProxy
Link copied to clipboard
var webTransportIgnoresProxy: Boolean

HttpClient.webTransport connects directly even when a proxy applies to the URL; false by default, so such a call fails with UnsupportedOperationException (WebTransport runs over UDP, which an HTTP proxy does not carry). Turn it on only when a direct path to those servers is wanted despite the proxy.
