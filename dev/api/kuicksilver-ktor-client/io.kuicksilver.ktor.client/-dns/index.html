Dns

fun interface Dns(source)

The name resolution of the Ktor client engine (KuicksilverEngineConfig.dns), after OkHttp's Dns: the addresses of a host name, which the engine then connects to with Happy Eyeballs (RFC 8305) over TCP (HTTP/1.1, HTTP/2) and QUIC (HTTP/3). Dns.System is the default; an application gives its own to use another DNS server (DNS over HTTPS, say), a fixed address for a name, or a policy of its own. It must be safe for concurrent use. docs/guide/ktor.md, "Name resolution".

The contract:

  • lookup suspends and must not block its thread: the engine calls it in the call's coroutine, on the engine's dispatcher, never under an engine lock. Wrap a blocking resolver with Dns.blocking, which runs it on threads of its own.

  • It is part of connecting: the connect timeout (connectTimeout, or HttpTimeout's) bounds it with the rest, and a lookup still running then is cancelled and the call fails with Ktor's ConnectTimeoutException; so is it when the call is cancelled. A CancellationException it throws while its caller is still active (a withTimeout of its own) is a failed lookup, not a cancellation.

  • Any exception it throws is a failed lookup, as is an empty list or one without a usable address: the connection fails with the engine's IOException for a name that does not resolve ("could not be resolved", with the resolver's exception as the cause; "resolved to no address"). An IOException is kept as it is; another exception is wrapped.

  • The order of the answer is a tie-break only: the engine sorts the addresses by RFC 6724 section 6 and interleaves the two families (RFC 8305 section 4, "the client MUST sort the addresses"), as it does the system's. Duplicates are dropped, an IPv4-mapped IPv6 address counts as the IPv4 address, and at most Dns.MAX_ADDRESSES_PER_FAMILY addresses of each family are kept, the first ones. Unspecified (0.0.0.0/8, ::), multicast (224.0.0.0/4, ff00::/8) and limited broadcast (255.255.255.255) addresses are dropped, never connected to: RFC 1122 section 3.2.1.3 and RFC 4291 section 2.5.2 never allow them as a destination, RFC 9293 section 3.9.1 (MUST-46) makes a TCP open to them an error, and a connect to 0.0.0.0 reaches the host's own listeners on Linux and macOS. The system's answers get the same check.

  • It gets host names only, without brackets or port. An IP address literal in a URL is its own address and never reaches it (one no connection may go to, such as 0.0.0.0 or ff02::1, fails the call); nor does a host with the form of an IPv4 address that is not a dotted quad (127.1 is 127.0.0.1, as every platform reads it; 010.0.0.1 or 0x7f.1 read differently by different platforms, and 256.1.1.1, fail the call: no host name has that form, RFC 1123 section 2.1). The engine reads such hosts the same way with Dns.System.

  • It is asked once per name per request: both sides of the HTTP/3 and TCP race, and a fallback, connect to that one answer. The engine keeps no answer beyond the request: caching (and its TTL) is the resolver's. A FamilyDns is asked for each address family on its own instead (RFC 8305 section 3), the two at once.

  • What it is asked for: the origin's name for a direct connection, over TCP and QUIC, WebSocket and WebTransport alike; an Alt-Svc alternative's host and an HTTPS record's TargetName (the A and AAAA records an HTTPS answer carries are used as RFC 9460 section 5 says, and the resolver is asked for the families they lack); a proxy's name. Through an HTTP proxy and a socks5h proxy the origin's name goes to the proxy and is never resolved here; through socks5 it is resolved here and the proxy gets the addresses. Not through it: HTTPS records (http3.httpsRecords), the NAT64 prefix discovery (ipv4only.arpa), and a proxy auto-configuration script's dnsResolve, which stay with the system.

The answers are trusted as routing only, never as the server's identity: TLS sends the URL's host name as SNI and verifies the certificate (and pins) against that name, whatever address the resolver gave, over TCP and QUIC (threat model 3.25). Connections are pooled per origin, never per address: two destinations of one origin (its host and an alternative) whose answers hold the address an HTTP/3 connection uses share it (RFC 9114 section 3.3), with the origin's TLS settings either way; no connection is shared across origins.
