webTransport

suspend fun HttpClient.webTransport(urlString: String, protocols: List<String> = emptyList(), headers: Http3Headers = Http3Headers.Empty): WebTransportSession(source)

Opens a WebTransport session (draft-ietf-webtrans-http3-16) to urlString, an https URL. Sessions share the engine's pooled HTTP/3 connection to the URL's host and port with each other and with requests (RFC 9114 section 3.3: one connection per address and port), as long as the server allows it: with WebTransport flow control on both sides (draft-16 section 5.1) a connection carries up to http3 { settings.webTransportMaxSessions } sessions (4 by default) and as many as the server accepts (section 5.2: a session it refuses with H3_REQUEST_REJECTED is opened again on another connection to the same server, which the next sessions share too, unless none of this client's sessions was on the refusing connection: that is the server's rate, and the refusal is thrown as io.kuicksilver.http3.Http3Exception.RequestNotProcessed); without flow control a connection carries one session, and each further one gets a connection of its own. A pooled connection that is not WebTransport-capable (opened for requests without WebTransport's SETTINGS and reset_stream_at) is replaced by one that is, which carries the origin's requests from then on; the old one finishes its requests and closes. A connection stays open while a session or a request uses it, and then idles as any pooled connection does; an extra connection a server's limit made closes with its last session. protocols are offered in WT-Available-Protocols; headers go with the CONNECT (an origin, for a server that checks it).

The engine's connectTimeout bounds the connection setup (io.ktor.client.network.sockets.ConnectTimeoutException); then the server's SETTINGS and its answer to the CONNECT are waited for up to ten seconds each. A server without WebTransport fails with io.kuicksilver.http3.Http3Exception.Settings, a refusal with io.kuicksilver.http3.Http3Exception.ConnectRejected (a 429 too: the server's own rate limit, section 5.2, is the application's to handle); there is no fallback to HTTP/1.1 or HTTP/2, which carry no WebTransport here. When the connection is lost, every session on it ends with the connection's reason (WebTransportSession.closed). Needs the Kuicksilver engine (IllegalStateException otherwise) and an open client (IllegalStateException after close()).

Refused with UnsupportedOperationException: under http3 { discovery = H1Only }, which turns HTTP/3 off, while http3 { http3Allowed } returns false (read once per call; one that throws allows it), and when a proxy applies to the URL (WebTransport runs over UDP, which an HTTP proxy does not carry) unless http3 { webTransportIgnoresProxy = true } asks to connect directly. At most http3 { maxWebTransportSessions } (64) sessions are open at once on the client; one more fails at once with IllegalStateException.

The connection goes straight to the URL's host and port: Alt-Svc is not consulted, and the CONNECT never goes in 0-RTT. The resolved addresses are tried in order within the connect timeout. Closing the client ends the sessions still open with their connections, without a close capsule; HttpClient.closeHttp3Connections() sends each open session WT_DRAIN_SESSION and its connection a GOAWAY, asking the server to wind it down. A session still being set up when it runs is drained as soon as it opens, or, when its CONNECT had not gone out yet, the call fails with IllegalStateException naming closeHttp3Connections().
