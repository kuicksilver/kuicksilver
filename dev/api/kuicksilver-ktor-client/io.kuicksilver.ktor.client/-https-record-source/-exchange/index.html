Exchange

class Exchange(val secure: Boolean = false, val exchange: suspend (query: ByteArray) -> ByteArray) : HttpsRecordSource(source)

Lookups through exchange: it gets a DNS query in wire format (RFC 1035 section 4.1, ID 0 and RD set, as RFC 8484 section 4.1 asks for DNS over HTTPS) and returns the response in wire format, for example the body of a POST to a DoH server with Content-Type: application/dns-message. The engine has no DoH client of its own. An exchange that throws, or returns something that is not the response to the query, counts as a failed lookup; so does a response over 65535 bytes (RFC 8484 section 6: "This media type restricts the maximum size of the DNS message to 65535 bytes").

The engine checks that the response answers the question it asked, but not its ID: every query has ID 0, so the exchange must tie a response to its query itself, which is what the ID is for: it "can be used by the requester to match up replies to outstanding queries" (RFC 1035 section 4.1.1). DNS over HTTPS does (the response is the one to its HTTP request), and so does DNS over TLS that matches responses to queries. An exchange over plain UDP or TCP must not send ID 0 as is: it sets a random ID of its own in the query (bytes 0 and 1), accepts only a response with that ID from the server it asked, and may hand it back with either ID; otherwise an off-path attacker who guesses the question can forge the answer.

val secure: Boolean

Whether the exchange's answers are cryptographically protected (DNS over HTTPS or TLS, or DNSSEC-validated). Then a resolution that fails (an error answer such as SERVFAIL, a transport error, a timeout) abandons the request instead of going on without records, as RFC 9460 section 3.1 asks, so an active attacker who drops the answers cannot downgrade the connection; the request also waits for the answer (up to the connect timeout, 30 s at most) instead of Http3ClientConfig.httpsRecordExtraWait. False (the default) treats failures as "no records".
