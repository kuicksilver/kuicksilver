maxHeaderBlockTime
Link copied to clipboard
var maxHeaderBlockTime: Duration

How long one field section (a HEADERS frame: request or response head, interim response, trailers) may take to arrive, from its frame header to its last byte; positive, 10 s by default (as Http2Settings.maxHeaderBlockTime). A server also counts a request's head from the first byte of its stream (frames before the HEADERS and a stream that sends nothing included) to its decoded HEADERS. A request head that misses it is rejected with H3_REQUEST_REJECTED before the application sees it (RFC 9114 section 4.1.1), so the client may send it again; other field sections cancel their request with H3_REQUEST_CANCELLED. The connection lives on either way.

webTransport
Link copied to clipboard
var webTransport: Boolean

WebTransport over HTTP/3 (draft-ietf-webtrans-http3-16); false by default. A server advertises SETTINGS_WT_ENABLED, SETTINGS_WT_MAX_SESSIONS (draft-14: webTransportMaxSessions with flow control, else 1) and SETTINGS_ENABLE_WEBTRANSPORT (draft-02), so browsers that still speak the older drafts find theirs; a client advertises the first and the last. Both add the non-zero SETTINGS_WT_INITIAL_* values that declare WebTransport flow control (section 5), which lets several sessions share a connection. build refuses it without enableConnectProtocol and h3Datagram: sessions are Extended CONNECT requests and carry HTTP datagrams.

webTransportInitialMaxData
Link copied to clipboard
var webTransportInitialMaxData: Long

Stream body bytes the peer may send in each WebTransport session (section 5.5.3), 0..2^62-1; 3 932 160 by default (4 sessions fill the default largest QUIC connection window, 15 MiB). The limit rises with WT_MAX_DATA as the bytes are consumed: taken by the application, all of a stream that ended cleanly once it was handed to its input, a reset or stopped stream's by its final size.

webTransportInitialMaxStreamsBidi
Link copied to clipboard
var webTransportInitialMaxStreamsBidi: Long

Bidirectional streams the peer may open in each WebTransport session (section 5.5.2), 0..2^60; 24 by default, so 4 sessions and their CONNECT streams fit the default 100 QUIC streams. The limit rises with WT_MAX_STREAMS as the peer's streams end. When this, webTransportInitialMaxStreamsUni and webTransportInitialMaxData are all 0, we do not declare WebTransport flow control (section 5.1) and a connection carries one session.

webTransportMaxSessions
Link copied to clipboard
var webTransportMaxSessions: Int

WebTransport sessions on one connection when flow control is on (both sides sent a non-zero SETTINGS_WT_INITIAL_*, draft-ietf-webtrans-http3-16 section 5.1), 1..65535; 4 by default. A server resets a CONNECT beyond it with H3_REQUEST_REJECTED (section 5.2), and a client opens another connection instead of putting more on one. The per-session limits below, times this, must fit the QUIC connection's (Http3Endpoint refuses a configuration where they do not, and the connection's receive window is kept at the open sessions' sum): no session can then hold every stream slot or the whole connection window. Http3Connection.client and server on a QUIC connection made by the caller cannot check this: its configuration must fit them the same way.
