Http3ServerRequest

interface Http3ServerRequest(source)

A request as a server sees it (RFC 9114 section 4.1). Respond with respond; interim responses first with sendInformational.

The request holds one of the client's streams, so that a client that resets its requests at once cannot have more of them running than it may open streams (RFC 9114 section 10.5; Rapid Reset, CVE-2023-44487). The stream goes back to the client once the application is done with the request, which is when the first of these happens:

  • its response ended: Http3ResponseWriter.finish returned or failed, its output was closed or cancelled, or the stream of acceptConnect ended in both directions;

  • reset was called;

  • respond or acceptConnect failed (the exception tells the application the request is over);

  • the application read the request's failure from body (a read, or ByteReadChannel.closedCause, showed the client's reset or another error): from then on the request is over for the transport, also if the application keeps working on it. A request the application drops without any of these keeps its stream until the connection ends. The Ktor engine gives the stream back when its handler returns instead, and cancels the handler when the client abandons the request.

abstract val body: ByteReadChannel

The request content from DATA frames; it ends at the client's FIN (and trailers, if any). A body cut short — the client's reset, a lost connection — fails every read with its cause (Http3Exception or the connection's io.kuicksilver.quic.QuicException.ConnectionLost) and is never isClosedForRead, so it cannot pass for complete. Content still unread when the response is complete is dropped with STOP_SENDING H3_NO_ERROR.

acceptConnect
Link copied to clipboard
abstract suspend fun acceptConnect(headers: Http3Headers = Http3Headers.Empty): Http3Stream

Accepts an Extended CONNECT (RFC 9220): :status 200, then the stream carries data both ways. Unknown protocols deserve 501 instead. A request that enables the Capsule Protocol (Capsule-Protocol: ?1) with content-length, content-type or transfer-encoding is malformed (RFC 9297 section 3.2): it is answered 400 and stopped with H3_MESSAGE_ERROR instead (RFC 9114 section 4.1.2), and Http3Exception.MessageError is thrown.

acceptWebTransport
Link copied to clipboard
suspend fun Http3ServerRequest.acceptWebTransport(headers: Http3Headers = Http3Headers.Empty, protocol: String? = null): WebTransportSession

Server: accepts a WebTransport session (Http3ServerRequest.isWebTransport must be true, IllegalStateException otherwise). Waits up to ten seconds for the client's SETTINGS (section 7.1); without them, or without SETTINGS_H3_DATAGRAM=1, the request is malformed (section 3.1): it is answered with 400 and Http3Exception.Settings is thrown. A request with content-length, content-type or transfer-encoding cannot carry the session's capsules (RFC 9297 section 3.2): it is answered with 400 and Http3Exception.MessageError is thrown. Then answers 200 with headers, WT-Protocol when protocol is set (it must be one of Http3ServerRequest.availableProtocols, IllegalArgumentException otherwise) and, for a draft-02 client, the sec-webtransport-http3-draft: draft02 field it requires. Streams the client opened for the session before this are delivered to it. To refuse a session, answer with Http3ServerRequest.respond instead (a 4xx).

respond
Link copied to clipboard
abstract suspend fun respond(status: Int, headers: Http3Headers = Http3Headers.Empty, priority: StreamPriority? = null): Http3ResponseWriter

Sends the final response HEADERS; the body goes through the returned writer. priority overrides the client's signal for the scheduling of the response; without it a priority field in headers is sent and merged into the stream's current priority (RFC 9218 section 8: a parameter it leaves out keeps that value). Either way later PRIORITY_UPDATEs from the client no longer change the scheduling. A CONNECT without a signal from its client has the defaults (section 4), and a field such as u=1 keeps i=?0. A response to HEAD, and a 204 or 304, has no content (RFC 9110 sections 9.3.2, 15.3.5, 15.4.5): what is written to its writer is dropped, while its content-length is sent as given. Fields the client would have to treat as malformed throw IllegalArgumentException and reset the stream with H3_REQUEST_CANCELLED, among them capsule-protocol outside a 2xx (RFC 9297 section 3.4) and, for a CONNECT, a 2xx that enables the Capsule Protocol with content-length, content-type or transfer-encoding, or as a 204, 205 or 206 (section 3.2).
