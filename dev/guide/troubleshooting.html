Troubleshooting

What this page is for. It lists the symptoms you may see with Kuicksilver (an exception, a log line, a counter that does not move), what causes each one and what to do about it.

Before you start

  • Have the exact text or code of the failure: the exception type and message, the log line, or the counter name.
  • Know the module you use (QUIC, HTTP/3, the Ktor client or server) and its version. The entries describe 0.3.0 behaviour; some entries name the release that changed the behaviour ("since 0.2.1", "since 0.3.0"); the CHANGELOG lists every change.
  • A logger or a counter helps more than guessing; Getting more information shows how to turn them on.

How to use this page. Search the page for the exact text, or find it in Find your symptom; the table sends you to the entry. Every option named here is listed with its default in the configuration reference.

A failed connection's cause is always a QuicException: QuicConnection.closed completes with it, and every waiting call (openBidi, acceptStream, the stream channels, sendDatagram) fails with the same instance. Look at its type and fields before its message.

Connecting

connect fails with "Handshake timeout after 10s"

QuicException.ConnectionLost.Timeout with kind = TimeoutKind.Handshake: nothing the handshake needed came back within QuicConfig.handshakeTimeout (10 s).

Which timeout fired. A raw QUIC connect has one timer, QuicConfig.handshakeTimeout. The Ktor client has two for an HTTP/3 setup, and the earlier one ends it: the connect timeout (HttpTimeout's connectTimeoutMillis, else the engine's connectTimeout, 10 s) and the QUIC handshake timer (engine { quic = quicConfig { handshakeTimeout = ... } }, 10 s; with http3 { earlyData = true } it is cut to the connect timeout). Either way the response's diagnostics say fallback = HandshakeTimeout; h3Failure tells them apart: a ConnectTimeoutException is the connect timeout, a QuicException.ConnectionLost.Timeout (h3Failure=Timeout in the engine's log line) is the handshake timer. In H3Only mode the call fails with that exception itself. On the server, EndpointStats.handshakesFailedTimeout counts handshakes its own handshakeTimeout ended (the Ktor server sets it through quic).

Finding the cause, in order. Each step rules out a row of the table below:

  1. Does TCP work to the same host and port (curl -sI https://host:port/)? If not, the host or the port is wrong, or the server is down: this is not a QUIC problem.
  2. Does curl --http3-only -sI https://host:port/ connect from the same network as the client? If it does, the problem is the client's network or its configuration (a VPN, a proxy, H1Only); if it does not, go on.
  3. Does UDP reach the server? sudo tcpdump -ni any udp port <port> on the server, or EndpointStats.datagramsReceived (Ktor server: engine.http3Stats) while the client tries. Nothing arrives: a firewall, a security group, a missing UDP port mapping or load balancer listener (first row).
  4. Initials arrive: are they refused or dropped? connectionsRefusedLimits, initialsDropped and statelessRateLimited growing point at the limits (second row, and source NAT below).
  5. The server answers (datagramsSent grows, tcpdump shows packets going out): does the client get them? Compare the source address of the answers with the address the client sent to (reply addresses below), and look for a tunnel with a small MTU on the path.
  6. The handshake starts and stalls: a qlog of both sides (QUIC: qlog) shows where, for instance retransmitted Initials (loss) or a long pause after the server's certificate (the platform verifier).

connect fails at once with TransportClosed(code = 0x02)

"transport closed by Peer: code 0x2": the server refused with CONNECTION_REFUSED. A Kuicksilver server does that statelessly when its accept queue is full (QuicEndpointConfig.acceptQueue, 128 connections waiting for accept()) or while it shuts down (QuicEndpoint.shutdown, the Ktor server's stop). A handshake that completes into a full queue is closed with the reason "accept queue full". The server counts them in connectionsRefusedAcceptQueue and connectionsRefusedShutdown.

Fix on the server: accept faster (one coroutine per connection, incomingConnections()), or raise acceptQueue for bursty arrivals. On the client, retry after a delay; during a shutdown, connect to another instance. The Kuicksilver Ktor client does this by itself: the call falls back to HTTP/1.1 (fallback = Refused), the alternative is not marked broken, and the next call tries HTTP/3 again (Ktor: Racing and fallback).

The handshake fails with a certificate error

The client closes with a TLS alert: TransportClosed(code = 0x0100 + alert, initiator = Local) whose cause is a TlsException.Verify with a reason: VerifyReason; over TCP you get the TlsException.Verify itself (on the JVM a javax.net.ssl.SSLException). The server sees TransportClosed(initiator = Peer) with a TlsException.AlertReceived ("TLS alert received from the peer: ()") and counts it in handshakesFailedTls.

Decide on reason, not on the message text ("certificate verification failed: ", for example Expired or HostnameMismatch(expected=…, presented=[…])):

VerifyReason Alert Usual cause and fix
UnknownIssuer 48 the chain does not lead to a trusted root: a private CA without TrustConfig.AnchoredCa, a server that does not send its intermediates, the JVM's cacerts lacking a corporate root (the JVM verifier uses the JDK store, not the OS store). Also the fallback for platform failures without a better mapping
HostnameMismatch(expected, presented) 42 the certificate's names (presented) do not include serverName; connecting by IP literal to a certificate without that IP is the common case. Fix the name, or use TrustConfig.ExpectedName behind a proxy; the check cannot be disabled
PinMismatch(chainPins) 42 no pin of TrustConfig.Pinned matches the validated chain (or a TrustConfig.Tofu key changed); chainPins lists what the chain has, leaf first. Rotate pins before rotating keys
Expired, NotYetValid 45 certificate dates, or a wrong device clock
Revoked, UnknownRevocationStatus 44, 48 the platform verifier's revocation policy (JVM PKIX, Apple, Windows soft-fail on the leaf)
InvalidPurpose 43 the key usage or extended key usage forbids TLS server (or client) authentication
BadSignature, BadEncoding, NoCertificate 42 a damaged chain, or a server that requires a client certificate the client did not configure (identity)
CertificateTransparency 46 Android's CT policy rejected the chain
Custom(text) 46 your CertificateVerifier or the platform said text

Linux Kotlin/Native without a CA store (distroless or scratch images) fails earlier, when the client configuration is built: TlsException.Config "invalid TLS configuration: ", the native message being "ksl: no CA certificates for TrustConfig.Platform; searched ; install ca-certificates, set SSL_CERT_FILE or SSL_CERT_DIR, or use AnchoredCa". When SSL_CERT_FILE or SSL_CERT_DIR is set, only those are searched (TLS: Linux trust store).

The handshake fails with an ALPN mismatch

QUIC needs both sides to agree on an application protocol (RFC 9001 section 8.1). Without a common one the server closes with the TLS alert no_application_protocol (120): the client sees TransportClosed(code = 0x0178, initiator = Peer), and the server counts it in handshakesFailedTls.

The handshake fails with unrecognized_name, missing_extension or internal_error (server with an sniSelector)

A server whose TlsConfig (or Ktor tlsConnector) has an sniSelector ends a handshake itself in three cases; a QUIC client sees TransportClosed(initiator = Peer) with the code, a TCP client TlsException.AlertReceived:

Code (QUIC) Alert Cause and fix
0x0170 unrecognized_name (112) the selector answered null for the ClientHello's server name: it does not serve that name. Add it, or answer with a default identity
0x016d missing_extension (109) the ClientHello had no server name (the client connected to an address), the selector answered null and the server has no identity of its own. Give the server one, answer serverName == null too, or connect by name
0x0150 internal_error (80) QUIC only: the selector threw, or its override does not suit QUIC (an empty alpn). The client reads no detail; the server's failure carries the exception as its cause

Connections are refused or dropped

A server endpoint answers a new client in one of three ways: it accepts, it refuses with CONNECTION_REFUSED (0x2, the client knows at once), or it drops the Initial silently (the client waits for its handshake timeout). The counters of QuicEndpoint.stats / Http3Endpoint.stats (EndpointStats) tell which:

Counter The client sees Cause Action
connectionsRefusedAcceptQueue TransportClosed(code = 0x02) acceptQueue (128) handshaken connections wait for accept() accept faster, or raise acceptQueue (Ktor server: quicAcceptQueue)
connectionsRefusedShutdown TransportClosed(code = 0x02) QuicEndpoint.shutdown (the Ktor server's stop) is running connect to another instance; wait for the new one
connectionsRefusedLimits, initialsDropped nothing, then "Handshake timeout after 10s" maxConnections (10 000) or maxConnectionsPerIp (256) reached (Ktor server: quicMaxConnections, quicMaxConnectionsPerIp), initialQueueCap overflow, or an Initial from a reflective source port (53, 123, 1900, 5353, 11211) raise the limit in quicEndpointConfig { } (Ktor server: QUIC connection limits), or find the client that holds the connections; a NAT puts many users behind one IP
connectionsRefusedAdmission nothing, or the ConnectionAdmission close code your ConnectionAdmission said Drop or Close(code), or the Ktor server is in Drain (it refuses new QUIC clients through its admission policy: TransportClosed(code = 0x02)); the default asks an unvalidated client for a Retry (it does not drop it) above 256 handshakes in flight or 8 MiB of handshake data check the admission policy and its maxInflightHandshakes

The Ktor engines have their own limits: the client waits for a free connection beyond maxConnectionsCount or maxConnectionsPerRoute and fails with ConnectTimeoutException when the connect timeout runs out first (requests wait and then fail).

QuicClientConfig or QuicServerConfig cannot be built

TlsException.Config from build() means the TlsConfig cannot carry QUIC (RFC 9001 section 4): "QUIC requires TLS 1.3 only", "QUIC requires a non-empty ALPN list" or "TLS_AES_128_CCM_8_SHA256 is not allowed in QUIC". A client without a reference identity fails with "a client needs serverName (or ExpectedName) as the reference identifier". IllegalArgumentException from a builder names the value out of range, for example "keepAlive must be at most 3/4 of maxIdleTimeout", "initialRtt must be positive and at most 10 s" or "server QuicConfig.connectionIdLength () must equal the endpoint's connectionIdLength () …".

Connections that end

"Idle timeout after 30s"

ConnectionLost.Timeout with kind = TimeoutKind.Idle: nothing arrived for the idle timeout both peers agreed on, the smaller of our QuicConfig.maxIdleTimeout (30 s) and the peer's, never below 3 x PTO; duration is that value. No CONNECTION_CLOSE is sent.

  • A quiet but wanted connection (a push channel waiting for events): set QuicConfig.keepAlive to a PING interval of at most 3/4 of maxIdleTimeout, for example keepAlive = 10.seconds; PINGs then go out at least every half of the effective idle timeout, also when the peer's is shorter. A NAT on the path may forget an idle UDP mapping sooner than 30 s; keep-alive covers that too.
  • The peer's timeout is shorter: the effective value is the minimum; raise it on both sides, or keep the connection busy with keepAlive. The Ktor server takes quicMaxIdleTimeout (when quic is not assigned; otherwise set maxIdleTimeout in quic).
  • The peer vanished (a server restarted without a Stateless Reset, a phone lost coverage): the timeout is the intended outcome. A client that follows networks (Network changes) survives a change of network instead.
  • A stalled sender: if the application had data to send, check QuicConnection.stats (cwnd, bytesInFlight, ptoCount) and the qlog; report the trace if the connection stopped sending with credit available.

maxConnectionLifetime on the server endpoint ends connections deliberately: TransportClosed(code = 0) with the reason "connection lifetime reached". The Ktor client's idleTimeout (5 minutes) is a separate pool timer that closes unused connections on the client side.

StatelessReset or ApplicationClosed

  • ConnectionLost.StatelessReset ("stateless reset received"): the peer lost the connection's state and could still prove it was the endpoint that issued the connection ID (RFC 9000 section 10.3), for example a peer that keeps its reset key across a restart. Reconnect. A Kuicksilver peer cannot do that after a restart, and neither can another instance behind a load balancer: reset tokens come from a key of the endpoint that issued the connection (QUIC: Stateless reset). Such an endpoint may answer with a Stateless Reset (only to a short-header packet whose connection ID has its format and loop index, or with QUIC-LB its configuration and server ID, and within its stateless rate limit), but its token does not match, so the client ignores it (counted in ConnectionStats.invalidResets), and the connection ends with "Idle timeout" instead (Idle timeout). Behind a load balancer, keep each client on one instance (Deploying the HTTP/3 server: Connection IDs and several instances), or let a QUIC-LB load balancer route by connection ID (QUIC: Behind a load balancer).
  • ConnectionLost.ApplicationClosed ("application closed by <Local|Peer>: code ()"): an application close(code, reason). Over HTTP/3, Http3Exception.fromQuic(e) reads the code as an HTTP/3 error (Http3Exception.Protocol with an Http3ErrorCode, H3_NO_ERROR after a graceful GOAWAY).

TransportClosed with a protocol error

"transport closed by <Local|Peer>: code 0x ()". code is a TransportError (RFC 9000 section 20), frameType the frame that triggered it (0 if none), initiator who detected it.

Code Typical reason Meaning
0x03 FLOW_CONTROL_ERROR "data beyond the flow control limit: > " the peer sent beyond the window we granted: a peer bug
0x04 STREAM_LIMIT_ERROR "stream exceeds the limit of " the peer opened more streams than maxBidiStreams / maxUniStreams allowed
0x0a PROTOCOL_VIOLATION "excessive peer activity ()" glitch protection: the peer kept sending frames that do no work (QUIC: Glitch protection); glitchProtection = false turns it off for a peer you trust
0x0f AEAD_LIMIT_REACHED "AEAD integrity limit reached", "AEAD confidentiality limit reached without a possible key update" too many forged packets, or a peer that never allowed a key update
0x0100 + alert the TLS message see certificate errors

ConnectionLost.Internal is a bug or a failing endpoint loop: the connection is dropped without CONNECTION_CLOSE (the peer sees an idle timeout). A loop that died is logged at Error ("endpoint

loop : ; closing the endpoint"), and exceptions that escaped a loop coroutine are counted in EndpointStats.uncaughtFailures. Please report it with the stack trace of its cause.

0-RTT is rejected

  • StreamError.EarlyDataRejected on a stream opened before the handshake completed: the server rejected 0-RTT, and the client reset every such stream (RFC 9001 section 4.6.2); nothing of it reached the server. Send it again on a new stream after awaitHandshake() (the HTTP/3 client does this itself for its early requests).
  • ConnectionLost.ZeroRttRejected ("0-RTT rejected"): the server rejected 0-RTT and chose another ALPN than the ticket's, or the client asked for EarlyDataState.Required and got no 0-RTT. Retry on a new connection with connectEarly off or Allowed.
  • 0-RTT never happens: the server needs QuicServerConfig.earlyData = true (Ktor server quicEarlyData); a server that asks for client certificates cannot accept 0-RTT (building a QuicServerConfig with earlyData = true and a clientAuth other than None throws IllegalArgumentException "earlyData cannot be combined with client certificates", and the Ktor server's start fails the same way); a ticket is single-use and lives in the endpoint (or Ktor engine) that received it, and a server whose configuration changed (ALPN, transport limits, HTTP/3 SETTINGS) refuses old tickets. The counters zeroRttOffered, zeroRttAccepted and zeroRttRejected, and ConnectionListener.onZeroRtt, show the outcome. Background: ADR-0015.

Migration and network changes

migrate throws PathValidationException

PathValidationException is an IllegalStateException with a reason: PathFailureReason; the connection stays on its old path and the new socket is closed.

reason Message Cause and fix
ValidationTimeout "path validation failed" no PATH_RESPONSE within max(3 x PTO, 6 x initialRtt): the new network cannot reach the server (a captive portal, no route, UDP blocked there)
NoSpareConnectionId "path validation failed: no spare connection ID from the peer" the network changed before the server's spare connection IDs arrived (right after the handshake) and none came in time; retry, which NetworkMigrator does on its own as soon as one arrives

migrate and addPath also throw IllegalStateException for "only a client migrates (RFC 9000 section 9)", "migration before the handshake is confirmed (RFC 9000 section 9)", "the peer advertised disable_active_migration" (reconnect instead) and "at most 4 paths". When the active path fails and no other validated path remains, the connection ends with ConnectionLost.NoViablePath ("no viable path"). The same reasons arrive as PathEvent.Failed.reason and ConnectionEvent.PathFailed.reason.

NetworkMigrator reports Failed or SourceFailed

MigrationEvent.Failed(network, cause): the migration to network failed (the causes above, or openIo threw); the connection stays where it was. MigrationEvent.SourceFailed(cause) is the last event: the network flow threw (on Android, TooManyRequestsException when the app registers more than about 100 network callbacks; followDefaultNetwork shares one callback per ConnectivityManager to avoid it). NetworkLost means no network for now; the connection waits for its idle timeout. Android needs ACCESS_NETWORK_STATE, which the kuicksilver-quic AAR declares.

PathEvent.SocketLost after an iOS app comes back

iOS reclaims the sockets of a suspended app; sendmsg/recvmsg then fail with ENOTCONN, EBADF, EPIPE or ENOTSOCK, and a vanished interface with ENETDOWN, ENETUNREACH or EHOSTUNREACH. Kuicksilver turns these into SocketDefunctException, stops using the socket and reports PathEvent.SocketLost(path, cause); the connection is not closed. Call QuicConnection.rebind() (or let followDefaultNetwork / NetworkMigrator do it). A client endpoint whose own socket is gone refuses new connections with SocketDefunctException "the endpoint's socket is gone: bind a new endpoint"; bind a new QuicEndpoint. A server endpoint's socket loss ends the endpoint. Details: QUIC: Suspended apps and lost sockets.

Throughput and packet size

Transfers stall over a VPN or tunnel (MTU black hole)

DPLPMTUD raises the packet size above 1200 bytes only on sockets that set DF. A path that silently drops large packets (a tunnel with a small MTU that does not send ICMP) is detected: three lost packets above 1200 bytes, or two PTOs in a row while a large packet is unanswered, bring the connection back to 1200 and pause the search for 60 s (QUIC: Path MTU). Each drop costs a few round trips.

  • Watch ConnectionStats.pathMtu, ConnectionEvent.MtuUpdated and the qlog.
  • On a path you know is constrained, set QuicConfig.pmtud = false (stays at 1200) or lower maxUdpPayloadSize (default 1452, 1200..65527; a QuicEndpoint refuses more than 1500 with "maxUdpPayloadSize exceeds the endpoint runtime's 1500-byte datagram slots").
  • pathMtu stuck at 1200 on a healthy path means the socket has no DF: the portable socket is in use (the accelerated socket is not used).

Throughput is far below the link

  • Loss-based collapse on lossy paths (radio, long-haul): try quicConfig { congestionController = { Bbr() } } (experimental; QUIC: Choosing a congestion controller).
  • Receive windows: a slow reader keeps the initial windows (512 KiB per stream, 768 KiB per connection); they grow to maxStreamWindow (6 MiB) and maxConnectionWindow (15 MiB) only while the application reads a whole window in under four RTTs. On a long fat path, raise initialStreamWindow / initialConnectionWindow and the maxima.
  • Send buffer: maxSendBuffer (4 MiB) bounds unacknowledged data per connection; writers wait beyond it.
  • The socket refuses datagrams: a rising ConnectionStats.datagramsDroppedSocket (or EndpointStats.datagramsDroppedSocket) means the send buffer, not the network, is the bottleneck.
  • ECN: ConnectionStats.ecnState is Failed when a path bleached or mangled marks; that is harmless, ECN is just off.

Platforms

The accelerated socket is not used

The accelerated ksl socket brings batching, ECN, DF (so PMTUD) and, on Linux, GSO/GRO. When it cannot open, the endpoint uses the portable socket (NIO on the JVM, ktor-network on Kotlin/Native): MTU 1200, no ECN marks read, one datagram per call.

  • When a bind of the accelerated socket is refused, the logger says once per process at Warn: "accelerated UDP socket refused on
    (); using the portable socket". The reason is the failing system call and its error (": ", on Windows ": WSA error ").
  • When the one-time loopback probe fails, for example because a sandbox refuses every bind, the same once-per-process warning reads "accelerated UDP socket unavailable (); using the portable socket". Without a logger line (a KuicksilverLogger.None endpoint), tell by QuicConnection.stats.pathMtu staying at 1200 and ecnState never reaching Capable.
  • A QUIC server on Kotlin/Native needs the accelerated socket; without it bind with a server throws UnsupportedOperationException ("a QUIC server on Kotlin/Native needs the accelerated ksl socket (Linux, Apple, Windows), which is unavailable here"), and the Ktor server serves HTTP/1.1 only, logging "HTTP/3 is not served on port : ".

A QUIC-LB configuration is refused

QuicEndpointConfig.Builder.build() refuses a loadBalancer whose 1 + serverId + nonceLength differs from connectionIdLength ("loadBalancer connection IDs are N bytes…"), a connectionIdLength below 8, an endpoint without a server, and a plaintext configuration (no key) next to a preferredAddress. updateLoadBalancer throws IllegalStateException on an endpoint built without loadBalancer (the Ktor engine: without quicLoadBalancer), and IllegalArgumentException for another length, for a server ID this endpoint used in clear that is now encrypted, or the other way round (draft-ietf-quic-load-balancers-21 section 9.7: give the encrypted configuration other server IDs), and for a configId the current or previous configuration still holds with another key, server ID or nonce length ("configId N still names the configuration before it": use another codepoint, or wait one more change). EndpointStats.loadBalancerNoncesExhausted above 0, with the Warn line "QUIC-LB: the nonces of configuration … are spent", means the endpoint issues unroutable IDs: roll out a configuration with a new key. loadBalancerReservationFailures above 0, with the Warn line "QUIC-LB: the nonce reservation could not be stored", means QuicLbNonceReservation.store threw (a full disk, say): fix the store; it is retried after a back-off. IllegalArgumentException "every configuration with this key … must bring the same nonceReservation" means two configurations of one key (or, in clear, one nonce length) disagree about the reservation. "a plaintext configuration needs a nonceReservation" means a QuicLbConfig without a key and without a reservation: plaintext nonces must survive a restart (draft section 9.6), so give it a QuicLbNonceReservation, or a key. See QUIC: Behind a load balancer.

UnsupportedOperationException for loops > 1

Since 0.3.0 loops > 1 runs on every platform: where the kernel does not balance SO_REUSEPORT sockets (macOS, iOS, Windows) or with a custom io, the loops share one socket (QUIC: Several loops on one port). bind still throws "loops > 1 needs the accelerated transport" where the accelerated socket cannot open (a sandbox that refuses bind, a platform without ksl_udp) and no io is given: use loops = 1 there (Ktor server: udpSocketCount = 1), or several processes behind a QUIC-aware load balancer (a QUIC-LB one: QUIC: Behind a load balancer) (Deploying the HTTP/3 server: Connection IDs and several instances).

Datagrams lost with loops > 1 on macOS or Windows

EndpointStats.datagramsDispatchDropped above 0: a loop fell more than 512 datagrams behind the socket's receiver (more loops than cores, a blocking call on the loop, a flood of one loop's connection IDs). Its peers retransmit; the other loops are not held up. Use fewer loops than cores and keep blocking work off the endpoint's dispatchers.

Windows

  • The accelerated socket is Winsock with SO_EXCLUSIVEADDRUSE: a port another socket holds is refused, and only one loop per port runs. ECN needs a Windows that accepts IP_ECN (probed when the socket opens, verified on Windows 11); USO/URO are used where Windows grants them (DatagramIo.capabilities tells).
  • A wildcard bind (0.0.0.0 or ::) is dual-stack; on a host without IPv6, 0.0.0.0 falls back to an IPv4 socket.
  • TrustConfig.Platform verifies with CryptoAPI and the Windows root store, fetching missing intermediates through AIA; a revoked leaf is Revoked, an unknown revocation status is ignored.
  • A server must be allowed through the Windows firewall for inbound UDP and TCP on its port (Deploying the HTTP/3 server).
  • keylogFile on the JVM is refused (Windows has no POSIX permission view); on Kotlin/Native the file is only created (key logging is refused).

macOS and iOS

  • App Sandbox (macOS): a client needs com.apple.security.network.client, an app that accepts connections (a QUIC endpoint with server, the Ktor server) also com.apple.security.network.server. Test the signed, sandboxed build: a refused bind may only show as the portable-socket symptoms. Publishing on the App Store has the entitlement templates.
  • Local network (iOS 14+, macOS 15+): talking to LAN devices needs NSLocalNetworkUsageDescription (and NSBonjourServices for Bonjour); without it the system blocks the traffic. Loopback and Internet traffic need neither.
  • App Transport Security does not apply to Kuicksilver's own sockets.
  • One endpoint loop per port; no GSO/GRO on Darwin.
  • See iOS for NAT64, backgrounding and the device checklist.

Android

INTERNET (declared by the kuicksilver-native AAR) and ACCESS_NETWORK_STATE (by kuicksilver-quic, for followDefaultNetwork) come with the libraries. Doze and app standby cut network access whatever Kuicksilver does; a frozen background process reconnects when it runs again.

Code shrinking (R8, isMinifyEnabled or optimization { enable = true }): libksl's JNI_OnLoad finds the natives of io.kuicksilver.native.KslNative and the field PacketBuffer.buffer by name, so R8 must neither remove nor rename them. The kuicksilver-native AAR carries these rules as proguard.txt, and R8 applies them without any setup (since 0.2.1; with 0.2.0 a minified release build failed to load the library, KslLoader.availability() answered Unavailable with LoadFailed, while debug builds worked). Add them to the app's own rules only if the build ignores consumer rules from dependencies:

-keep,includedescriptorclasses class io.kuicksilver.native.KslNative {
    native <methods>;
}
-keep class io.kuicksilver.native.PacketBuffer {
    java.nio.ByteBuffer buffer;
}

A JVM application that shrinks its jar (ProGuard in a Compose Desktop release build, R8 for a server) needs the same rules. The kuicksilver-native jar carries them as META-INF/proguard/kuicksilver-native.pro, which R8 reads by itself; with ProGuard, add the lines above to its configuration unless your setup applies rules embedded in jars.

The Ktor client engine is found by HttpClient() (without an engine argument) through ServiceLoader, which creates io.kuicksilver.ktor.client.KuicksilverEngineContainer by name. The kuicksilver-ktor-client AAR and jar carry its keep rule in the same way (proguard.txt, META-INF/proguard/kuicksilver-ktor-client.pro; since 0.2.1). Without it, a shrunk JVM application lost the class and its META-INF/services entry, and HttpClient() picked another engine or none. With ProGuard, or a build that ignores embedded rules, add:

    public <init>();

Ktor engines

The engine fails to start with a Ktor version error

IllegalStateException: "Kuicksilver's Ktor engines support Ktor 3.6.x, but is on the classpath. …". Creating HttpClient(Kuicksilver) checks ktor-client-core, ktor-http-cio, ktor-network, ktor-io and ktor-websockets; starting the server checks ktor-server-core, ktor-http-cio, ktor-network and ktor-io. Align every io.ktor dependency to 3.6.x, best with platform("io.ktor:ktor-bom:3.6.<patch>"), and look for a library that pulls a newer Ktor (./gradlew dependencies). -Dkuicksilver.ktor.versionCheck=false skips the check at your own risk (Ktor: Supported Ktor versions).

QUIC misbehaves in production

When HTTP/3 causes trouble on some networks or after a release and you need it off before a fix ships, flip http3 { http3Allowed } from your remote configuration and, to drop the open connections at once, call client.closeHttp3Connections(): requests go over HTTP/1.1 from the next one on, calls in flight finish, and switching back needs no warm-up (Ktor: Turning HTTP/3 off remotely). Clients in H3Only mode fail instead of using TCP. Before that, response.kuicksilverDiagnostics and a qlog trace (Getting more information) usually tell what goes wrong.

Requests go through a proxy, or not, unexpectedly

Since 0.3.0 the Ktor client follows the platform's proxy settings by default (proxyResolver = ProxyResolvers.System), so a request may go through a proxy you did not configure in code, over HTTP/1.1 (protocolSelected reports ProtocolReason.Proxy). Set proxyResolver = ProxyResolvers.None to connect directly, exempt the host in the settings (no_proxy, the OS bypass list), or set proxy explicitly. On macOS, iOS and Windows a proxy auto-configuration (a PAC URL or script, or WPAD) is run (on Apple platforms by the engine itself, on Windows by WinHTTP), and a lookup waits for it at most 5 seconds; one that cannot be fetched or run in that time makes the engine log one warning ("proxy auto-configuration (PAC or WPAD) script that could not be fetched or run") and those requests use the next setting (on Windows the fixed proxy), else connect directly. On Windows, when automatic detection finds no script, the engine logs that once at Info level instead ("detect the proxy automatically (WPAD), and no proxy auto-configuration script was found"), as detection is on by default there: those requests use the fixed proxy setting, if any, else connect directly, and detection runs again after 5 minutes. Set proxy or a proxyResolver of your own to decide the route yourself. A request that fails with UnsupportedOperationException ("the proxy URL's scheme is not supported") has a proxy setting the engine cannot use, such as socks4://; it is never bypassed. The message does not name the scheme a proxy URL from the environment gave: a user name before :// reads as one.

Requests through an https:// proxy fail with ProxyTlsException

The TLS handshake with the proxy itself failed; nothing of the request was sent. Its cause says why: a TlsException.Verify whose reason is HostnameMismatch means the proxy's certificate does not name the proxy's host as configured (an address where the certificate names a host, or the reverse; the origin's ExpectedName and pins do not apply to the proxy), another reason that its chain is not trusted: the proxy's trust is the engine's trust without pins unless proxyTls = { trust = ... } says otherwise, so a proxy under a corporate CA needs that CA there. An alert or a closed connection usually means the proxy does not speak TLS on that port (an http:// proxy named as https://). A failure of the origin's TLS behind the proxy is a TlsException, not a ProxyTlsException.

H3Only requests time out

With Http3DiscoveryMode.H3Only there is no fallback: when UDP is blocked the call fails with Ktor's ConnectTimeoutException (the engine's connectTimeout, 10 s, or HttpTimeout's connect timeout) or the QUIC ConnectionLost.Timeout ("Handshake timeout after 10s"), whichever comes first. Use Preferred where TCP must remain possible.

Requests wait and then fail with ConnectTimeoutException

HTTP/1.1 requests beyond maxConnectionsPerRoute (100) or maxConnectionsCount (1000) wait in FIFO order and share the connect timeout. Over HTTP/2 a request waits only when every connection of its route is at the server's SETTINGS_MAX_CONCURRENT_STREAMS and the route has no room for another connection. A pile-up usually means response bodies that are never read or closed, which keep their connections. Read or cancel every body; raise the limits only for real concurrency. HTTP/3 requests instead wait for the server's stream credit (MAX_STREAMS) until the request or socket timeout (Ktor: Connection pool).

A WebSocket over HTTP/1.1 fails with ConnectTimeoutException ("The WebSocket was not connected within the connect timeout") when the server accepted the connection but did not answer the opening handshake within the connect timeout. WebSockets to one IP address connect one at a time (RFC 6455 section 4.1), so the next one to that address waited for this one until then. That queue does not count against the connect timeout of the WebSockets in it: many WebSockets started at once to one address connect one after another, bounded only by each call's request timeout (HttpTimeout) or its cancellation.

A TLS 1.2 client cannot connect to the server

A client without TLS 1.3 (an older Android or JDK, an embedded HTTP stack, some scanners) gets a protocol_version alert: a TLS connector speaks TLS 1.3 only unless it allows TLS 1.2 with versions = TlsVersions.Tls12And13, the EngineMain key kuicksilver.tls.versions = tls12And13, or Ktor's enabledProtocols = listOf("TLSv1.2", "TLSv1.3") (TLS 1.2 on the server). A TLS 1.2 client that still gets handshake_failure offers none of the profile's suites (only CBC, SHA-1 or static RSA ones), offers only RSA suites to a server with an ECDSA certificate, or leaves out Extended Master Secret: these are refused on purpose (RFC 9325 sections 3.5, 4.1 and 4.2). At startup, "kuicksilver.tls.versions applies to the port of kuicksilver.tls.certificateChain" means the key was set next to -sslPort: set ktor.security.ssl.enabledProtocols for that port instead; and "the Kuicksilver engine serves [TLSv1.3] or [TLSv1.2, TLSv1.3]" means enabledProtocols asked for TLS 1.2 alone or an older version.

A chunked body fails with "Whitespace before the end of a chunk size line"

The peer wrote a chunk-size line with SP or HTAB right before its CRLF (5 \r\n). RFC 9112 section 7.1 allows whitespace in that line only before the ; of a chunk extension and around its =; since 0.2.1 both engines refuse any other (the server with 400, the client by failing the response), because a recipient that reads such a line otherwise than an intermediary is open to request smuggling. Fix the peer: it is out of the grammar, even where other implementations tolerate it.

H3BodyConsumed

"421 Misdirected Request from the alternative, and the request body was already consumed": a streamed ReadChannelContent body that HTTP/3 already read cannot be replayed on another connection. The same holds over HTTP/2 for a request the server did not process (GOAWAY, REFUSED_STREAM) or answered with HTTP_1_1_REQUIRED. Send bodies the engine can replay (bytes, a WriteChannelContent writer) when such retries matter.

Calls over HTTP/2 fail, or a server misbehaves with HTTP/2

The client offers HTTP/2 to every https:// server over TCP since 0.3.0 (Ktor: HTTP/2 on the client). A server or middlebox whose HTTP/2 is broken shows as Http2Exception failures (StreamReset, ConnectionClosed, MalformedMessage) where HTTP/1.1 worked before. engine { http2 { enabled = false } } offers only http/1.1 again, as in 0.2; report the server's behaviour (with the Http2Exception and its code).

  • A server that answers HTTP_1_1_REQUIRED is honoured: the route offers only http/1.1 for 5 minutes, doubling up to 2 days at each new refusal, and the request goes again over HTTP/1.1 when that is safe (idempotent with a body that can be sent again, or not processed). Otherwise, a POST say, the call fails with Http11RequiredException: send it again and it goes over HTTP/1.1. ProtocolDiagnostics.fallback is H2Refused for those calls, and the diagnostics line says fallback=H2Refused with the HTTP/3 reason as h3Fallback=.
  • Http2Exception.MalformedMessage: the server's response broke RFC 9113 section 8 (a connection-specific field such as transfer-encoding or connection, an uppercase field name, a content-length that does not match the body). Fix the server; the engine does not accept such responses over HTTP/2.
  • Http2Exception.FieldSectionTooLarge: the response's header fields exceed http2 { settings.maxHeaderListSize } (64 KiB); raise it only for a server you trust.
  • Http2Exception.ConnectionClosed mentioning PING: pingInterval is set and the server did not answer a PING within it; raise the interval or leave it at Duration.INFINITE.

The server serves HTTP/1.1 but no HTTP/3

The server logs why:

  • "HTTP/3 is not served on port : ": the platform cannot run a QUIC server here.
  • "HTTP/3 is not served: no TCP + UDP pair free on one port number after 16 attempts ()": port = 0, and neither the UDP twin of a TCP port nor the TCP twin of a UDP port the OS picked was free.
  • A fixed port whose UDP side is taken fails the start instead.

Without HTTP/3 the server sends no Alt-Svc. Also check http3 = true, that a firewall passes UDP to the port, and that altSvc is on so clients learn about HTTP/3 (Deploying the HTTP/3 server has a checklist for the network in front of the server). Alt-Svc: clear instead of h3=…, or new QUIC clients refused with CONNECTION_REFUSED (0x2) while HTTP/1.1 answers, mean engine.http3Advertising is Clear or Drain (Ktor: Turning HTTP/3 off on the server).

The server answers 421 Misdirected Request

Since 0.3.0 a TLS connector answers 421 to a request whose host the certificate of its connection does not name, and the application never sees the request (neither routing nor plugins such as CallLogging) (RFC 9110 section 7.4 requires the rejection). Browsers that reuse a connection for another host retry on a new connection and need nothing; the other causes are configuration. The engine logs each 421 at debug level with the reason:

  • "421 Misdirected Request for : the certificate of this connection does not name it": the certificate's subjectAltName must list every host and address clients use, localhost, 127.0.0.1 and the server's IP addresses included (as IP entries: a DNS entry 127.0.0.1 does not count). Wildcards cover one label (*.example.com covers api.example.com, not example.com or a.b.example.com), and the subject CN is never used. Clients that pin the key or use TrustConfig.ExpectedName to accept a certificate that names something else get 421 too: reissue the certificate with the name they connect to.
  • "421 Misdirected Request for : the sniSelector chose this connection's TLS settings for another name": with an sniSelector, a request must be for the connection's SNI name, or an address when the client sent no SNI. A client that sends one name in TLS and another in Host (some test tools, curl --resolve set up for another name) gets this; send the same name in both. The same holds over HTTP/3, whose handshake the same selector chose for.
  • "421 Misdirected Request for : an https request over a plain connection": a plain connector received GET https://… HTTP/1.1. Send origin-form requests, or terminate TLS here.
  • "421 Misdirected Request for : not a valid host name or address": an internationalised name must arrive as an A-label (xn--…).

Only when every client of a connector is a trusted gateway, such as a TLS-terminating proxy that re-encrypts with an internal certificate or forwards absolute https:// targets, turn the check off for that connector: tlsConnector { trustedGateway = true } or plainConnector { trustedGateway = true } (Ktor: Misdirected requests). Never set it on a connector that clients reach directly.
