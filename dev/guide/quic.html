QUIC with Kuicksilver

What this page is for. It explains the QUIC layer on its own: configuring, binding an endpoint, opening streams, and the transport features (0-RTT, migration, congestion control, load balancing, datagrams, qlog). For HTTP/3 see HTTP/3; for Ktor see Ktor engines.

Before you start

  • Dependency: io.kuicksilver:kuicksilver-quic:0.3.0 or newer (it brings kuicksilver-tls). Built with Kotlin 2.4.20: JVM and Android need Kotlin 2.3 or newer, Kotlin/Native 2.4.x (Kotlin version).
  • Platforms: JVM 17 or newer, Android minSdk 24, iOS 15, macOS 12 (macOS 11 on the JVM), Linux, Windows (Platforms).
  • A TlsConfig with ALPN set: a server needs an identity (certificate chain and private key), a client needs a trust configuration (TLS: Configuration).

Minimal example. A complete example runs both sides of an application protocol of your own (its ALPN, a stream, datagrams) with every value defined; Binding an endpoint and connecting opens a connection; Opening a stream and echoing and Accepting on the server are the two sides of an echo.

Kuicksilver's QUIC layer (io.kuicksilver:kuicksilver-quic) implements QUIC v1 (RFC 9000/9001/9002) and, when configured, the compatible version negotiation of RFC 9368/9369 towards QUIC v2 (RFC 9369). There are two levels of API: a coroutine wrapper (QuicEndpoint/QuicConnection/QuicStream) for applications, and a sans-IO core (ConnectionCore/EndpointCore) for callers with their own event loop (ADR-0004). The code blocks below compile and run as GuideSamplesTest (kuicksilver-quic/src/jvmTest).

A complete example: custom ALPN, streams and datagrams

Two programs that speak a protocol of their own over QUIC, without HTTP: the server runs on the JVM (or on Kotlin/Native Linux, Apple or Windows, which serve on the accelerated socket), the client on any target, a Kotlin/Native executable included. Both name the same ALPN; the client verifies the server against a private CA. The block is common code: a test compiles it for the JVM and every Kotlin/Native target and runs it with the common tests.

val dir = "/etc/my-proto"   // where the PEM files are
// guide:quic:custom-alpn
// the PEM files, read with kotlinx-io: common code, the same on every target
val chainPem = SystemFileSystem.source(Path(dir, "fullchain.pem")).buffered().use { it.readString() }   // leaf first
val keyPem = SystemFileSystem.source(Path(dir, "privkey.pem")).buffered().use { it.readString() }       // PKCS#8
val caPem = SystemFileSystem.source(Path(dir, "ca.pem")).buffered().use { it.readString() }             // the client trusts it
val scope = CoroutineScope(Dispatchers.Default)
// ALPN: both sides list it, or the handshake ends with no_application_protocol (120)
val myProtocol = listOf("my-proto/1")
// the server: JVM, or Kotlin/Native on Linux, Apple and Windows
val serverTls = tlsConfig(TlsRole.Server) {
    alpn = myProtocol
    identity = TlsIdentity.fromPem(chainPem, keyPem.toCharArray())
}
val server = QuicEndpoint.bind(
    InetSocketAddress("0.0.0.0", 4433),
    quicEndpointConfig { this.server = quicServerConfig(serverTls) { quic = quicConfig { maxIdleTimeout = 30.seconds } } },
)
val serving = scope.launch {
    server.incomingConnections().collect { connection ->
        launch {
            // datagrams: each one sent back as it comes
            try {
                connection.datagrams.collect { d: Datagram -> connection.sendDatagram(d.data) }
            } catch (e: IOException) { /* the flow ends with the connection's QuicException.ConnectionLost */ }
        }
        launch {
            // streams: one line in, one line out (the flow completes when the connection ends)
            connection.incomingStreams().collect { stream ->
                launch {
                    try {
                        val line = stream.input.readLine(LineEnding.Lenient) ?: return@launch
                        stream.output.writeStringUtf8("echo: $line\n")
                        stream.output.flushAndClose()
                    } catch (e: IOException) { /* the client reset the stream or left */ }
                }
            }
        }
    }
}
// the client: any target, Kotlin/Native included
val clientTls = tlsConfig(TlsRole.Client) {
    serverName = "server.test"   // SNI, and the name the server's certificate must carry
    alpn = myProtocol
    trust = TrustConfig.AnchoredCa(Certificate.parsePem(caPem))   // a private CA; TrustConfig.Platform for a public one
}
val client = QuicEndpoint.bind(InetSocketAddress("0.0.0.0", 0))
val connection = client.connect(InetSocketAddress("server.test", 4433), quicClientConfig(clientTls))
val stream = connection.openBidi()
stream.output.writeStringUtf8("ping\n")
stream.output.flushAndClose()
val reply: String? = stream.input.readLine(LineEnding.Lenient)    // "echo: ping"
connection.sendDatagram("tick".encodeToByteArray())               // a ByteArray out; datagrams are never retransmitted
val echoed: Datagram = connection.datagrams.first()               // a Datagram in; its payload is echoed.data, a ByteArray
connection.close(code = 0, reason = "done")
client.close()
  • ALPN. Any non-empty list of protocol names; the server picks the first of its own that the client offers. Without a common one the server closes with the TLS alert no_application_protocol (120) and the client sees TransportClosed(code = 0x0178) (troubleshooting).
  • Names. connect resolves a host name in the InetSocketAddress once, through the system resolver, and uses the first address; serverName in the TLS configuration is what goes into SNI and what the certificate is checked against, so connecting to an IP literal with serverName set works.
  • Reading lines. readLine(LineEnding.Lenient) (ktor-io) reads one line and accepts both \n and \r\n; it returns null at the end of the stream. The other samples on this page and the README read the same way.
  • Datagrams. sendDatagram takes a ByteArray; datagrams is a Flow<Datagram> whose data is the payload. Both sides support datagrams by default; see Datagrams for the queues, the size limit and what trySendDatagram answers.

Configuration

A QuicConfig is immutable; build it with the quicConfig DSL. It carries the transport settings (windows, idle timeout, versions, congestion controller, migration, resource limits); TLS identity and trust come from the usual TlsConfig (docs/guide/tls.md). The configs that wrap it have DSL entry points of their own: quicClientConfig(tls) { }, quicServerConfig(tls) { } and quicEndpointConfig { } (each Builder stays available). Every option with its default and range is in the configuration reference.

// guide:quic:config
val quic = quicConfig {
    maxIdleTimeout = 30.seconds
    initialStreamWindow = 512 * 1024L
    maxBidiStreams = 100
    versions = listOf(VersionProfile.V1)   // preference order; listOf(VersionProfile.V2, VersionProfile.V1) opts into v2 (RFC 9368/9369)
    greaseQuicBit = true                    // RFC 9287
}

QUIC is stricter than TLS over TCP about the TlsConfig it accepts (RFC 9001 section 4): TLS 1.3 only, a non-empty alpn list, and no TLS_AES_128_CCM_8_SHA256. Building a QuicClientConfig or QuicServerConfig from a config that breaks one of these throws TlsException.Config right away, not at the first connect.

initialRtt is the round-trip time assumed before the first sample (default 333 ms, RFC 9002 §6.2.2; allowed range (0, 10 s]). Until an ACK gives a real sample, a lost flight is resent after a PTO of 3 x initialRtt, doubling each time: 1 s, 2 s, 4 s at the default, so a handshake under heavy loss gets three retransmissions within a peer's typical 10 s handshake timeout. A lower value repairs a lost first flight sooner at the price of spurious retransmissions when the real RTT is longer (quic-go starts at 100 ms: 300 ms, 600 ms, 1.2 s ...). Consider lowering it when the peers use X25519MLKEM768 (each first flight spans two datagrams, so a loss is twice as likely) or for mobile clients on lossy radio links with modest RTTs; keep the default for satellite or other long-RTT paths. It also sets the floor of a path validation, max(3 x PTO, 6 x initialRtt) (RFC 9000 §8.2.4).

// guide:quic:initial-rtt
val lossyMobile = quicConfig { initialRtt = 100.milliseconds }

Flow control: each stream starts with a receive window of initialStreamWindow (default 512 KiB) and the connection with initialConnectionWindow (768 KiB). A window is updated each time the application has read a quarter of it and doubles, up to maxStreamWindow (6 MiB) / maxConnectionWindow (15 MiB), only while the application reads a whole window in less than four smoothed RTTs, that is faster than the window lets the peer send (quic-go's auto-tuning rule); the connection window stays at least 1.5 x the largest stream window. A busy reader's window settles at 4–8 x the bandwidth-delay product, a slow reader keeps the initial window, and the ceilings bound the unread data one connection can hold. The defaults are quic-go's. A sender blocked by a window repeats DATA_BLOCKED / STREAM_DATA_BLOCKED while it stays blocked, and the receiver answers a stale report with its current limit, so a lost window update costs a few PTOs, not a stall. The repeats come 1, 2, 4 and then 8 PTOs apart for the first 32, then twice as far apart each time, up to a third of the idle timeout (the smaller of both sides' maxIdleTimeout; 10 s when both are zero). They are acknowledged, so a connection blocked because its peer stopped reading stays open, at the cost of about three small packets per idle period (about 95 in 10 minutes with the default 30 s); bound such a wait in the application if it must not last. A report at a new limit goes out at once and starts the fast gaps again.

A client that prefers v2 but must start in v1 (the widely deployed version) sets initialVersion = VersionProfile.V1 with versions = listOf(VersionProfile.V2, VersionProfile.V1): the first flight is v1, the server upgrades it through compatible version negotiation (RFC 9368 section 2.3).

Binding an endpoint and connecting

A socket error inside the endpoint loop ends the endpoint: every connection fails with ConnectionLost.Internal, accept() and connect() throw EndpointClosing. A send that the socket refuses (a packet filter answering EPERM, an unreachable route) only loses that batch of datagrams; loss detection resends what mattered. close() closes the socket first, waits for a receive that is still inside the socket call, and frees the packet buffers only then. On a closed connection trySendDatagram throws the connection's ConnectionLost instead of answering QueueFull, and a write on a stream the peer stopped with STOP_SENDING fails with ClosedWriteChannelException whose cause is StreamError.Stopped, including flushAndClose().

QuicEndpoint.bind starts one endpoint loop that drives every connection it owns (docs/architecture.md, kuicksilver-quic). A client-only endpoint needs no server in its QuicEndpointConfig.

The endpoint's socket comes from DatagramIo.open(local, prefer). On Linux and Android the default (IoPreference.Accelerated) is the ksl socket: batches of up to 64 datagrams per syscall with UDP GSO and GRO, ECN marks read and written per datagram, DF in probe mode for PMTUD, and SO_REUSEPORT for several loops on one port. On macOS and iOS (JVM and Kotlin/Native) it is the same ksl socket without GSO and GRO, which Darwin lacks: batches leave as one sendmsg per datagram, ECN marks and DF work as on Linux, and SO_REUSEPORT is not offered (several loops share one socket there, Several loops on one port). On Linux, Android and Apple a wildcard address (0.0.0.0 or ::) gives a dual-stack socket, as NIO does: one socket bound to :: sends to and receives from IPv4 and IPv6 peers, and IPv4 peers appear as IPv4 addresses. A specific address keeps its own family. On Windows (Kotlin/Native and the JVM) the ksl socket is Winsock: WSASendMsg/WSARecvMsg, USO/URO and ECN where the Windows version grants them (io.capabilities tells), DF, an exclusive bind and no SO_REUSEPORT (several loops share one socket); a wildcard address gives a dual-stack socket there too (on a host without IPv6, 0.0.0.0 falls back to an IPv4 socket). With IoPreference.Portable, or where ksl cannot open its socket, the portable socket is used (NIO on the JVM, ktor-network on Native); io.capabilities says what the socket can do and the core adapts (ECN validation, PMTUD) per path. A QUIC server on Kotlin/Native needs the accelerated socket (Linux, Apple, Windows): without it bind with a server throws UnsupportedOperationException, since the portable Native socket is client-only (ADR-0006). Socket buffer sizes, GSO and GRO on a server host: Deploying the HTTP/3 server: The host.

// guide:quic:client-connect
val client = QuicEndpoint.bind(InetSocketAddress("0.0.0.0", 0))
val connection = client.connect(
    serverAddress,   // an InetSocketAddress; the TLS config carries the name to verify
    quicClientConfig(tlsClientConfig) { this.quic = quic },
)

Opening a stream and echoing

QuicStream exposes a ktor-io ByteReadChannel/ByteWriteChannel pair; closing output sends a FIN, cancelling input sends STOP_SENDING and the connection survives.

Only the peer's FIN, with every byte before it read, ends input: then isClosedForRead is true, readAvailable returns -1 and closedCause is null. Any other end — a RESET_STREAM, a connection closed by either side (also with code 0), an idle timeout, a stateless reset, our own stopSending — fails every read with its cause (QuicException.StreamError.Reset, QuicException.ConnectionLost, …): readAvailable, readByte, readRemaining, copyTo and the rest throw instead of reporting an end, and the channel is not isClosedForRead. A loop that stops at -1 therefore cannot take a truncated stream for a complete one; closedCause still says why a channel failed. (ktor-io's own ByteChannel reports a cancelled channel as closed and answers -1 from readAvailable; QuicStream.input does not.)

// guide:quic:echo
val stream = connection.openBidi()
stream.output.writeStringUtf8("ping\n")
stream.output.flushAndClose()
val reply = stream.input.readLine(LineEnding.Lenient)
connection.close(code = 0, reason = "done")

Accepting on the server

The server side accepts connections whose handshake already completed, then streams the peer opened in id order.

// guide:quic:server-accept
val server = QuicEndpoint.bind(
    InetSocketAddress("0.0.0.0", 4433),
    quicEndpointConfig { this.server = quicServerConfig(tlsServerConfig) { this.quic = quic } },
)
val incoming = server.accept()
val echoed = incoming.acceptStream()
echoed.output.writeStringUtf8(echoed.input.readLine(LineEnding.Lenient) ?: "")
echoed.output.flushAndClose()

A server that serves several names gives its TlsConfig an sniSelector: each handshake's identity is chosen from its ClientHello as over TCP (TLS: Certificate per name). The selector runs off the connection's loop while that handshake waits; a name it refuses closes the connection with CRYPTO_ERROR unrecognized_name (0x170), a failing selector with internal_error (0x150). QuicConnection.localCertificates is the chosen chain. Retry and the admission policy act before any TLS session exists, so they are the same with or without a selector.

0-RTT (opt-in, experimental)

0-RTT lets a returning client send data with its first flight instead of one round trip later (RFC 9001 section 4.6; design in ADR-0015). It is off on both sides by default.

Replay warning. An attacker who sees the client's first flight can send it to the server again (RFC 9846 section 8). Write early only what is safe to execute twice, and act on anything else only after awaitHandshake(). The server limits replays (OpenSSL's ticket-age check, a window 10 s wide, one use per ticket in a replay register shared by the endpoint's loops, tickets bound to the configuration that issued them), but a replay into another server process with shared ticket keys passes the age check alone.

// guide:quic:zero-rtt
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val server = QuicEndpoint.bind(addr, quicEndpointConfig {
    this.server = quicServerConfig(tlsServerConfig) { earlyData = true }   // tickets that allow 0-RTT
})
val client = QuicEndpoint.bind(InetSocketAddress("0.0.0.0", 0))
val config = quicClientConfig(tlsClientConfig) { earlyData = EarlyDataState.Allowed }
val first = client.connect(addr, config)             // a full handshake; the server's ticket arrives shortly after it
// ... the application uses `first`; once the ticket is in, later connections of this endpoint can resume
val c = client.connectEarly(addr, config)            // returns once the 0-RTT keys exist (a full handshake without a ticket)
val s = c.openBidi(); s.output.writeFully(safeRequest); s.output.flush()   // travels in 0-RTT
c.awaitHandshake()                                   // from here the connection is authenticated
println("0-RTT accepted: ${c.earlyDataAccepted}")    // false: the server refused it; null: there was no ticket yet

The ticket is not there the moment connect returns: the server sends it after the handshake, so a connectEarly right after the first connect usually finds none and does a full handshake (earlyDataAccepted is then null).

  • Tickets are kept per client endpoint, used once, and checked against the current trust again before use. The remembered transport parameters (RFC 9000 section 7.4.1) set the limits of 0-RTT. Closing the endpoint drops them.
  • Rejection. When the server refuses 0-RTT (a changed configuration, a stale or replayed ticket), the client resets every stream it opened before the handshake completed (RFC 9001 section 4.6.2: it "MUST reset the state of all streams"): they fail with QuicException.StreamError.EarlyDataRejected, nothing of them reached the server, and earlyDataAccepted is false. The connection goes on with the server's new limits; send again on new streams what you still want. Http3Connection.request does that itself for its early requests. If the server chose another ALPN, or EarlyDataState.Required was asked for, the connection closes with QuicException.ConnectionLost.ZeroRttRejected.
  • Server side. With earlyData = true, accept() returns a connection as soon as its 0-RTT is accepted, so the application can answer in 0.5-RTT. QuicStream.receivedEarly marks streams whose data came in 0-RTT. earlyDataContext binds application settings into tickets, and Http3Endpoint puts its SETTINGS there.
  • Client certificates. A server that asks for client certificates cannot accept 0-RTT: building a QuicServerConfig with earlyData = true and a clientAuth other than None throws IllegalArgumentException ("earlyData cannot be combined with client certificates"), and the Ktor server's quicEarlyData fails the start the same way. A client with an identity may still ask for 0-RTT; such a server never offers it.
  • Keys. The client drops its 0-RTT key when the 1-RTT key arrives. The server drops its 0-RTT key 3 PTO after the first 1-RTT packet (RFC 9001 section 4.9.3).

Address tokens (NEW_TOKEN)

A server sends each client an address-validation token once the handshake is confirmed (see Admission and endpoint limits). A client that keeps it and shows it on its next connection to that server skips the Retry round trip a busy or AlwaysRetry server asks unvalidated clients for, and the server's first flight is not held to three times what the client sent. Clients keep nothing by default: give the client configuration a tokenStore (experimental).

// guide:quic:token-store
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val tokens = MemoryTokenStore(maxServers = 256, tokensPerServer = 4)   // share it between connections
val config = quicClientConfig(tlsClientConfig) { tokenStore = tokens }
val first = client.connect(addr, config)    // the server's NEW_TOKEN lands in `tokens` after the handshake
val next = client.connect(addr, config)     // its Initials carry the token: no Retry

Privacy. A token is an identifier the server gave this client: a connection that presents it tells the server it comes from the same client as the earlier one, even from another network. Keep a store only where the server may link the connections anyway, and drop it when the user or the network identity changes.

  • Keys. Tokens are kept under "<server name>:<port>" (the TLS server name), or the IP literal and port without one, so a token never goes to another name on the same address (RFC 9000 section 8.1.3).
  • Single use. take removes the token; the server sends a fresh one on every connection. A Retry replaces the token for the rest of that connection's Initials.
  • Bounds. A connection keeps at most eight NEW_TOKEN tokens of at most 1024 bytes each; every further NEW_TOKEN frame spends a glitch token (Glitch protection). MemoryTokenStore keeps the newest tokensPerServer per key and the maxServers keys used most recently (quic-go's LRU store).
  • Your own store. take runs in the coroutine that calls connect, put on the endpoint loop; both should be quick. A call that has not returned after 250 ms is cancelled (a warning, once per endpoint loop), and a store that throws is logged as a warning: either way the connection goes on without a token, so connect never waits longer than that for the store.
  • One process. A server's token keys live only in its process: a token survives neither a server restart nor a move to another server instance behind the same name (no shared keys between processes in 0.3.0). Such a token is treated as absent, so the client only loses the round trip it would have saved. A token presented to a server that no longer accepts it (another process, an expired one) costs nothing: the server treats it as absent.

Serving many connections

incomingConnections() turns accept() into a Flow that completes when the endpoint closes, and incomingStreams() does the same for acceptStream(): it completes when the connection ends for any reason, whose cause stays in closed. Cancelling a collector leaves the endpoint or the connection alone.

// guide:quic:incoming
supervisorScope {                                     // one failing connection or stream does not stop the others
    server.incomingConnections().collect { connection ->
        launch {
            connection.incomingStreams().collect { stream ->
                launch {
                    try {
                        if (stream.isUnidirectional) { stream.input.discard(); return@launch }   // a peer's uni stream: input only
                        val line = stream.input.readLine(LineEnding.Lenient) ?: return@launch
                        stream.output.writeStringUtf8(line + "\n")
                        stream.output.flushAndClose()
                    } catch (e: IOException) { /* the peer reset the stream or left */ }
                }
            }
        }
    }
}

A stream id says who opened it and in which directions (RFC 9000 section 2.1): isUnidirectional and isClientInitiated read it. A unidirectional stream has one half: ours only output, the peer's only input; touching the missing half throws IllegalStateException.

Congestion control

Every path runs CUBIC with HyStart++ (RFC 9438, RFC 9406) by default; NewReno stays available through quicConfig { congestionController = { NewReno() } }, and any CongestionController implementation can be plugged in. The controller sees packets sent, acknowledged and lost, ECN marks, MTU changes and RTT samples (onRttSample), and answers with the window, the pacing rate and the burst size. Every ECN-CE report reaches onEcnCe, and like onLoss the controller reduces at most once per recovery period, which losses and CE reports share (RFC 9002 appendix B.6): a custom controller applies that check itself. A connection that migrates to a new IP starts the new path from the initial window; a NAT rebinding keeps the state.

Choosing a congestion controller

Controller Select with When
Cubic (default) nothing general use; shares a bottleneck predictably with TCP and other QUIC stacks
NewReno congestionController = { NewReno() } reference behaviour, tests
Bbr (experimental) congestionController = { Bbr() } lossy paths (radio, long-haul) and deep buffers where a loss-based controller collapses or bloats the queue

Bbr implements BBRv3 as specified by draft-ietf-ccwg-bbr-06: it paces at a windowed maximum of measured delivery rates and keeps about two bandwidth-delay products in flight, probes for more bandwidth every 2 to 3 seconds (or sooner on short paths), and drains the queue for 200 ms every 5 seconds (ProbeRTT) to refresh its minimum RTT. Loss counts only above 2 % of a probe's flight, and outside probes it trims the short-term model by 30 % per lossy round; an ECN-CE mark counts as a loss. When every packet of a loss episode is acknowledged after all (reordering, a delay spike), BBR undoes the episode: window, bounds and the interrupted probe or Startup come back. After an idle period it paces at its bandwidth estimate instead of bursting its window, and it is paced even on sub-millisecond paths. A new peer address starts a fresh model; a NAT rebinding keeps it. PMTUD changes keep the model in bytes and move the 4-datagram floor.

When to use it: lossy paths (radio, long-haul) where a loss-based controller collapses, deep buffers where it bloats the queue, and paths with reordering. Keep CUBIC where the flow shares a bottleneck with TCP or other QUIC stacks and fairness matters more than throughput.

Path MTU

Datagrams start at 1200 bytes. On a socket that sets DF, DPLPMTUD (RFC 8899) probes upwards with PING+PADDING packets towards min(maxUdpPayloadSize, the peer's max_udp_payload_size) (1452 by default; QuicEndpoint refuses a value above its 1500-byte datagram slots at bind/connect, the sans-IO core takes up to 65527), twenty bytes at a time, at most three tries per size; probes are not congestion controlled and their loss is not a congestion signal. Three consecutive lost large packets, or two PTOs in a row while sending above 1200, mean the path shrank: the connection drops back to 1200, tells the congestion controller, waits a minute, and searches again; a successful search repeats every ten minutes. The core raises MtuUpdated(path, mtu), stats.pathMtu and maxDatagramSize follow, and queued datagrams that no longer fit are dropped (stats.datagramsDroppedSend). pmtud = false keeps 1200. The portable socket sets DF where the JDK has the option (IP_DONTFRAGMENT, JDK 19 and later; RFC 9000 section 14: "MUST be set if possible") but reports no DF capability, so there the MTU stays 1200 and the search does not run; the accelerated socket sets DF (in probe mode on Linux, Android and Windows; Darwin has no probe mode) and the search runs (1452 on loopback).

ICMP helps only as a hint (pmtudIcmpHints, experimental, on by default; RFC 8899 section 4.6). On Linux and Android the accelerated socket reads ICMP Packet Too Big messages, and every accelerated socket reports a send the kernel refused as too large (EMSGSIZE). A Packet Too Big counts only when it quotes one of the connection's own packets on its active path and leaves at least 1200 bytes of payload, and an endpoint looks at no more than 64 a second (EndpointStats.ptbAccepted, ptbIgnored). A reported size above the one in use ends the larger probes at once instead of after three lost tries. One below it drops the MTU to 1200 at once, provisionally: a probe of the old size follows, and when it is acknowledged the old size comes back and further Packet Too Big messages are ignored for ten minutes (only a probe sent after the drop counts); when it is lost the search starts again from 1200, trying the reported size first (without the minute's black-hole pause). EMSGSIZE on a probe settles that size at once. ICMP is easy to forge, so nothing else trusts it: a forged message costs about one probe round trip at 1200 bytes every ten minutes (the probe goes once the congestion window has room for it), and with zero-length connection IDs, where the quote proves only the address and port, a Packet Too Big is ignored altogether. A congestion window still at its initial value when the size drops stays at the smaller initial window after a restore: an MTU change never raises the window in bytes (RFC 8899 section 3 item 7).

ECN

Each path validates ECN before relying on it (RFC 9000 section 13.4): the first ten packets go out with ECT(0); the peer's ACK_ECN counts must appear, never shrink and cover every newly acknowledged marked packet, and the path must not lose all ten test packets. A path that fails never marks again; a new path validates afresh. Received marks are counted per packet number space only for datagrams whose packets were processed, and a CE increase reported by the peer is one congestion event per recovery period, the same recovery period a loss starts. The portable socket marks every datagram through IP_TOS (ecnSend) but cannot read marks, so with it the peer's validation of our direction needs an accelerated socket on the peer; the accelerated socket (Linux, Android, Apple, and Windows where IP_ECN is accepted, probed when the socket opens) marks and reads per datagram, and two of them validate both directions (Capable). Because the portable socket marks the whole socket, a failed validation on any of its paths clears IP_TOS for every connection on it (they all show Disabled from then on: a socket's capabilities that lose ecnSend or df reach the paths already on it, which stop marking or stop PMTUD and fall back to 1200 bytes; a gain applies to new paths only); the accelerated socket keeps marking, and only the failed path sends NotEct, so one client whose path bleaches marks does not turn ECN off for the server's other clients. stats.ecnState (an EcnState) says where a connection stands: Disabled, Testing, Unknown, Capable or Failed.

Key update

The core rotates 1-RTT keys as RFC 9001 section 6 describes: the next generation is derived when the current one is installed, a peer's update is followed automatically, and packets of the previous phase still decrypt until three PTOs after the first packet of the new phase arrived. A caller driving ConnectionCore directly can start an update once the handshake is confirmed and, for a later update, three PTOs after the peer acknowledged the current phase (section 6.5):

// guide:quic:key-update
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
if (core.initiateKeyUpdate(now)) println("key phase ${core.stats.keyUpdates}")   // false while RFC 9001 section 6.1 forbids it

The coroutine API exposes the same as QuicConnection.keyUpdate(), which suspends until RFC 9001 section 6.1 allows the update:

// guide:quic:key-update-api
connection.keyUpdate()
println(connection.stats.keyUpdates)   // ours and the peer's

The AEAD limits of RFC 9001 section 6.6 are enforced without configuration: at 7/8 of the confidentiality limit of an AES-GCM key the core updates keys on its own, and a connection that cannot update in time closes with AEAD_LIMIT_REACHED; too many packets failing authentication close it the same way (stats.authenticationFailures).

Stateless reset

When a peer that keeps its reset key loses its state (a restart, a crash) it answers our packets with a Stateless Reset (RFC 9000 section 10.3). The connection then completes closed with QuicException.ConnectionLost.StatelessReset, every stream fails with the same cause, and nothing more is sent. Tokens are derived from a per-endpoint key that lives inside the native layer, so a server that restarts cannot reset connections of its previous life; a client has no way to learn the key from the connection IDs it sees. Datagrams that merely look like a reset are counted in stats.invalidResets and ignored.

Migration and paths

Preferred address (server, experimental). quicServerConfig(tls) { preferredAddress = PreferredAddress(ipv4, ipv6) } makes the endpoint also listen on those addresses and offer them to clients in preferred_address (RFC 9000 section 9.6), for example a server behind an anycast or load-balanced address that wants clients on its own unicast address. A client that moves there validates the path first; the server switches its connection to the preferred socket only once it validated the client's address there too (until then everything non-probing leaves the original socket), reports PathChangeReason.PreferredAddress and closes the original path. Nothing else happens on a preferred socket: a new connection is never started there, and nothing is answered statelessly. With allowMigration = false a move to the preferred address is still taken, but only from the client's current address. With several loops every loop listens on the preferred addresses as on the main one: with SO_REUSEPORT where the kernel balances, else on one shared socket per address. Each preferred socket binds the literal address it advertises (there is no NAT indirection: behind a NAT, advertise an address the server owns), which must not be the endpoint's own (bind refuses the same IP and port, the port of a socket bound to 0.0.0.0 for an IPv4 address, or the port of one bound to :: for either family) nor use a reflection port (53, 123, 1900, 5353, 11211). If a preferred socket fails later, the endpoint degrades rather than failing. The preferred address is served by every loop or by none, so with several loops the whole group takes it down: every loop closes its preferred sockets and stops offering the address to new connections; connections that had moved there are closed with INTERNAL_ERROR, and a validation of the preferred address still under way fails, leaving its connection on the original address (RFC 9000 section 9.6.1). The close is attempted, but no socket is left on the preferred address to send it from, so a client that had moved there may not receive it and ends at its idle timeout instead. Datagrams still arriving for the preferred address are dropped (datagramsDroppedStateless), never answered from the main socket. The failure is logged as a warning and counted once in EndpointStats.preferredAddressFailures; everything on the main socket goes on.

A client follows a server's preferred address by default (followPreferredAddress, experimental; RFC 9000 section 9.6): once the handshake is confirmed it validates a path to the address of the family it uses, with the server's sequence-1 connection ID, and moves there when the server answers. Only probes go there before that, and a failed validation leaves the connection where it was. A server reached on a public address cannot send the client to a loopback, link-local or private address, and nobody to an unspecified, multicast or broadcast one (the Alt-Svc rule). The server's disable_active_migration does not stop the move, and after it the client may migrate. A migrate while the preferred address is still being validated validates both from the new socket (RFC 9000 section 9.6.3): the original address on the new path, and the preferred address once more. If the preferred address answers first, the new path takes it, and migrate moves the connection there (the returned PathEvent.Changed names the new path, whose remote is the preferred address); otherwise the move goes to the original address, and the preferred address, should it still validate, moves the connection there with PathChangeReason.PreferredAddress.

A server follows a client that changes address (RFC 9000 section 9). The first 1-RTT packet from a new address opens a path under validation: the server sends a PATH_CHALLENGE there (and to the previous address, against an off-path attacker replaying the client's packets), limits what it sends to the unvalidated address to three times what it received from it, and moves the connection only on a non-probing packet with the highest packet number seen. A NAT rebinding (same IP, new port) keeps the congestion window and RTT; a new IP starts from the initial window. When the new path never answers within three times the larger of the PTO and a new path's PTO (about 3 s) the server returns to the last validated path. A rebinding that happens before the handshake is complete (the client's retransmitted Initials arrive from a new port) cannot be answered yet: the server follows the latest decrypted Initial or Handshake packet, with a fresh three-times budget for the new address, sends a PATH_CHALLENGE there first and repeats it every PTO (the client answers once it holds 1-RTT keys), and lets the handshake itself validate the address: a challenge that is never answered settles the path rather than closing the connection. A PATH_CHALLENGE of the active path always travels in its own 1200-byte datagram ahead of everything else, and no PMTU probe goes to an address still under validation. The core reports PathEvent.Changed(old, new, reason), PathEvent.Validated(path) and PathEvent.Failed(path) events, and pathState(id) answers for any path (Closed once a path was closed or evicted, Unknown for an id never issued). Every migration and every 10 000 packets the connection switches to an unused connection ID of the peer and retires the old one; a connection ID the peer retired keeps routing for 3 × PTO so packets in flight still arrive (at most 32 retired IDs per connection route at once; beyond that the oldest stops early). allowMigration = false advertises disable_active_migration and drops datagrams from other addresses; a move to a loopback or link-local address from a connection that did not start on one is refused unless allowMigrationToLoopback is set.

A client moves on its own with a second socket:

// guide:quic:migration
val change = connection.migrate(DatagramIo.open(InetSocketAddress("0.0.0.0", 0)))   // addPath + probe + switchTo
println("now on ${change.new.localAddress} (${change.reason})")

addPath(io) opens a path through another socket, probe() validates it with a PATH_CHALLENGE (and re-validates a path already validated), switchTo() moves the connection, close() forgets the path and closes its socket on the loop (on the active path it throws IllegalStateException and changes nothing). migrate does the three in a row and throws PathValidationException (an IllegalStateException, "path validation failed") when the new socket never hears back, leaving the connection where it was.

Migration timing: a probe on a new path must carry a connection ID of the server that no other path used, so an observer cannot link the two networks (RFC 9000 section 9.5). The server issues its spare IDs, up to the client's active_connection_id_limit (default 4), in its first 1-RTT flight (section 5.1.1), so they normally arrive with the handshake. If the network changes before they did (a lost datagram, a peer that issues late), probe() does not reuse the active path's ID: it waits up to three times the larger of the PTO and a new path's PTO (about 3 s) for a NEW_CONNECTION_ID, probes as soon as one arrives, and otherwise fails with PathFailureReason.NoSpareConnectionId (PathEvent.Failed.reason, PathValidationException.reason) rather than as a silent path. Migrating right after connect() therefore needs no wait of its own. paths lists the live paths (the first is the one the connection started on), activePath is the one it sends on now, and pathEvents reports Validated, Failed and Changed, for the peer's moves too, and SocketLost when the system took a path's socket away (see Suspended apps and lost sockets). Migration needs a confirmed handshake and a server that did not advertise disable_active_migration; when the active path fails validation and no other validated path remains, the connection closes with ConnectionLost.NoViablePath.

Network changes

A phone moves between Wi-Fi and cellular; the connection can follow it instead of dying with the old network. NetworkMigrator (experimental) watches a Flow of the platform's network handles and migrates a client connection whenever the network changes:

// guide:quic:network-migrator
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val migrator = NetworkMigrator(connection, networks, { DatagramIo.open(InetSocketAddress("0.0.0.0", 0)) }, scope)
val log = scope.launch { migrator.events.collect { println("network: $it") } }
migrator.start()

The first network the flow reports is the one the connection is on already. Each different network gets a socket from openIo and a migrate (new path, PATH_CHALLENGE, switch); on success the previous path and its socket are closed and events reports MigrationEvent.Migrated(old, new, path). When the new network never answers, openIo throws or the server advertised disable_active_migration (RFC 9000 section 18.2), the new socket is closed, the connection stays where it was and events reports Failed(network, cause). When the cause is a PathValidationException with NoSpareConnectionId (the network changed before the server's spare connection IDs arrived and none came in time), the migrator tries the same network again as soon as one arrives, unless the network changed meanwhile. A null means no network: NetworkLost is reported and the migrator waits; the connection is not closed (its idle timeout decides), and if the same network comes back nothing moves. Repeated values are ignored, and a change during a migration supersedes it: the unfinished path is closed and nothing is reported for it (openIo itself is not cancelled, so keep it short: the socket it returns is closed). The path closed after a migration is the one the connection was really on, also when it moved since (a fallback, the peer). network is the network the connection is on as far as the migrator knows. close() (thread-safe, like start()) stops following: a migration that has not switched yet is abandoned and its path and socket closed, one already switching completes and reports Migrated; the connection stays open. The migrator also stops when the connection ends, without a Failed for the migration it cut short. If the network flow throws, SourceFailed(cause) is the last event and the migrator stops; the exception never reaches scope. Only a client migrates (RFC 9000 section 9): a server connection is refused with IllegalArgumentException.

On Android, followDefaultNetwork does the wiring (API 24+):

// guide:quic:android-follow
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val cm = context.getSystemService(ConnectivityManager::class.java)
val migrator = connection.followDefaultNetwork(cm, lifecycleScope)   // started; migrator.close() stops it
lifecycleScope.launch { migrator.events.collect { Log.i("quic", "$it") } }

It feeds ConnectivityManager.registerDefaultNetworkCallback into a started NetworkMigrator (cm.defaultNetworks() is the flow alone). All migrators of one ConnectivityManager share a single callback, registered with the first and unregistered after the last, because Android refuses more than about 100 callbacks per app (TooManyRequestsException, reported as SourceFailed). It opens each new socket with DatagramIo.open(local, network, prefer), which binds it to that network with Network.bindSocket before it carries a datagram: the portable socket before bind, the accelerated one through a duplicate of its descriptor that is closed again. The default network at the call is taken as the one the connection is on (a socket that is not bound to a network follows the default one). The AAR declares ACCESS_NETWORK_STATE, which the callback needs; nothing else is added to the manifest. What stays with the app: the callback only fires while the process runs, so a connection in a background process that Android froze or killed moves (or is lost) when the app is back; Doze and app standby cut network access whatever the default network is; and a server that advertised disable_active_migration is never moved (Failed events), so the app reconnects instead. As in Chromium's QUIC session pool, losing the network does not close the connection: if no network returns within the idle timeout, the connection closes as usual.

On iOS and macOS, followDefaultNetwork(scope) does the same with the Network framework:

// guide:quic:apple-follow
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val migrator = connection.followDefaultNetwork(scope)   // started; migrator.close() stops it
scope.launch { migrator.events.collect { println("quic: $it") } }

nwPathUpdates() is the flow alone: one NWPathMonitor (C API, on its own dispatch queue) per process, started with the first collector and cancelled after the last, reporting an NwPathKey for a satisfied path (the preferred interface's index and kind, Wifi, Cellular, Wired, Loopback or Other) and null while the path is not satisfied; a path update that keeps the interface (a new address, a DNS change) is not a new network. Each new socket comes from DatagramIo.open(local, interfaceIndex, prefer), which sets IP_BOUND_IF (IPV6_BOUND_IF for an IPv6 address) on the accelerated socket before it carries a datagram, so the connection leaves through the new interface even before the system prefers it. The portable socket cannot be bound: when the accelerated one is refused it is unbound and follows the default route. No entitlement or Info.plist key is needed for a client; a server on the local network needs NSLocalNetworkUsageDescription.

Suspended apps and lost sockets

iOS reclaims the sockets of an app it suspends: back in the foreground, sendmsg and recvmsg fail with ENOTCONN, EBADF, EPIPE or ENOTSOCK, and an interface that went away answers ENETDOWN, ENETUNREACH or EHOSTUNREACH. Both transports (the accelerated ksl socket and the portable ktor-network one) turn these errors into SocketDefunctException; a custom DatagramIo throws it for the same conditions. The endpoint loop then stops reading and writing that socket, without retrying it in a loop, and every connection reports PathEvent.SocketLost(path, cause) for its paths on it; the connection is not closed. Recovery is a move to a fresh socket:

// guide:quic:socket-lost
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
connection.pathEvents.collect { e ->
    if (e is PathEvent.SocketLost && e.path.id == connection.activePath?.id) connection.rebind()
}

rebind(local, prefer) opens DatagramIo.open on the wildcard address of the peer's family (the loopback address of its family for a peer on 127.0.0.0/8 or ::1), migrates there (the new path is validated first) and closes the path it left. Like any migration it needs an unused connection ID of the server (RFC 9000 section 9.5), which arrives within a round trip after the handshake: the probe waits for one, and if none comes in time the move fails with PathValidationException (PathFailureReason.NoSpareConnectionId) and the connection stays where it was. A NetworkMigrator (and so followDefaultNetwork) does this on its own when the active path's socket is lost while a network is up, reported as Migrated with old == new, and tries again once a spare ID arrives. Until a move, the connection's idle timeout runs: a suspension longer than the idle timeout (and than the server's) ends the connection as usual, so an app that returns after minutes reconnects, ideally with 0-RTT. A client endpoint whose own socket was lost keeps its connections for the move but refuses connect at once with SocketDefunctException: bind a new endpoint. A server endpoint's own socket is the exception: its clients address that port, so a lost server socket ends the endpoint as before. iOS gives a suspended app no CPU, so nothing runs during the suspension; beginBackgroundTask buys about 30 seconds to finish a transfer, and only the foreground can serve.

Glitch protection

Every connection carries a token bucket (1000 tokens, 33 back per second) that pays for work the peer makes us do without moving anything forward: a STREAMS_BLOCKED repeating the same limit, a NEW_CONNECTION_ID for a sequence number we already hold, a RETIRE_CONNECTION_ID for an ID that is already retired (one for a sequence number we never issued is a PROTOCOL_VIOLATION) or one that retires more than twice the IDs we keep issued within 3 PTO (its replacement then waits until an earlier retired ID stops routing), a third PING-only packet within one RTT (the two probes of a PTO may both be PING-only, so a pair is free). A 1-RTT packet that fails to decrypt is discarded silently and spends nothing: anyone who has seen a connection ID can forge such packets (RFC 9000 section 12.2). A MAX_DATA, MAX_STREAM_DATA or MAX_STREAMS that raises nothing is ignored for free: it is what a retransmitted or reordered update looks like (quic-go repeats MAX_STREAMS in every packet until it is acknowledged, a thousand times in one interop run). So is a DATA_BLOCKED or STREAM_DATA_BLOCKED: a stale one is answered with the current MAX_DATA / MAX_STREAM_DATA at once, at most once per RTT per connection or stream, and a repeat within that RTT is not answered (quiche reports DATA_BLOCKED in almost every packet of a download, about a thousand times in two seconds). An empty bucket closes the connection with PROTOCOL_VIOLATION and the reason excessive peer activity (0x10=…), listing the frame types that spent the tokens; closed then completes with ConnectionLost.TransportClosed(code = 0x0a). Honest peers never spend: retransmitted data, keep-alive PINGs and real flow-control updates cost nothing, and stats.glitchTokensSpent stays at zero through a lossy transfer. Set glitchProtection = false in quicConfig { } to turn it off for a connection.

Several loops on one port

A server endpoint can run loops endpoint loops, each with its own single-threaded dispatcher, its own admission state and its own reset key; the Retry and NEW_TOKEN keys are shared by the loops, so a token one loop issued validates a client on any of them. The loop that admits a connection owns it for life: its index is the routing byte of every connection ID that loop issues (with a QUIC-LB configuration, the loop the ID hashes to). accept() is one queue over all loops, connect picks loops in turn, and a connection it opens issues connection IDs that name its loop as well. No loop ever answers a Stateless Reset for a connection ID that names another loop. The loops share the port in one of two ways, chosen by the platform (there is no switch):

  • Kernel balancing (Linux, Android): each loop has its own accelerated socket bound with SO_REUSEPORT, and the kernel hashes every client flow onto one of them. Receiving, decrypting and sending all run in parallel. A datagram that lands on another loop after a NAT rebind is copied to the owner.
  • In-process routing (macOS, iOS, Windows, and any endpoint with a caller-supplied io): the loops share one socket. Darwin hands a port's unicast datagrams to one SO_REUSEPORT socket only, and Windows binds with SO_EXCLUSIVEADDRUSE, so neither can balance. One receiver thread reads the socket and hands each datagram to the loop its connection ID names (a new client's Initial goes to a loop chosen by a keyed hash of its connection ID, the same loop for its retransmissions); every loop sends through its own clone of the socket (ksl_udp_sender), or through the caller's socket under a lock. A migrated or rebound client reaches its loop directly. A Stateless Reset from a peer, which names no connection ID of ours, goes to the loop whose connection holds the peer's reset token, and an ICMP Packet Too Big (Linux and Android) to every loop, each checking it against its own connections. A loop that falls behind has 512 datagrams waiting at most: the receiver drops the rest for that loop, counted in EndpointStats.datagramsDispatchDropped, and never waits for it, so the other loops go on. Each loop's ring holds 512 slots of 1500 bytes on the heap, 768 KB per loop for each shared socket (the main one and each preferred address). A failed socket fails the loops as their own would: the main one ends the endpoint, a preferred-address one takes the preferred address down.

What each mode buys: handshakes (most of a server's CPU) and the work of many connections spread over the loops in both. In-process routing keeps receiving sequential: one receive system call per datagram on Darwin, so a bulk transfer over many connections gains less than handshakes do, and the gain stops where that one receiver is saturated. One connection never runs faster with more loops: it lives on one loop, by design. More loops than cores gain nothing. Measured on an Apple Silicon Mac with in-process routing (Benchmarks: Several loops on one socket): 4 loops complete 3.3–3.5 times the handshakes of one; 8 bulk connections move 1.2–1.3 times the bytes, where the receiver's one recvmsg per datagram is saturated.

Inside each loop a flush visits only the connections something happened to since the last one, and the timers sit in a heap, so neither grows with the number of idle connections.

// guide:quic:loops
val withLoops = QuicEndpointConfig.Builder().apply { this.server = serverConfig; loops = 4 }.build()

QuicEndpoint.bind(InetSocketAddress("0.0.0.0", 4433), withLoops) then starts the four loops on port 4433.

Behind a load balancer

Experimental, after draft-ietf-quic-load-balancers-21 (QUIC-LB; a draft, not an RFC, so the format may still change). Several servers behind one address normally rely on the load balancer hashing the 4-tuple, which breaks when a client's address changes (Deploying: Connection IDs and several instances). A QUIC-LB load balancer routes by connection ID instead: each server writes its server ID into every connection ID it issues, and the balancer reads it back. Give the endpoint the configuration your load balancer's configuration agent assigned this server:

// guide:quic:load-balancer
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val lbKey = KslQuicCrypto.newLoadBalancerKey(keyBytes) // wipes keyBytes; the endpoint takes its own copy
val lb = QuicLbConfig(configId = 1, serverId = byteArrayOf(0x31, 0x44, 0x1a), nonceLength = 4, key = lbKey)
val behindLb =
    quicEndpointConfig {
        server = serverConfig
        loadBalancer = lb   // 1 + 3 + 4 = 8 bytes: the default connectionIdLength
    }

A connection ID is then first octet || server ID || nonce: the first octet carries configId (0..6) in its three high bits and the length of the rest in its five low bits. With an AES key the server ID and nonce are encrypted (one AES block when they are 16 bytes together, a four-pass Feistel network otherwise), so only the load balancer can tell which server a connection is on; without one they travel in clear, and the server then hands each connection only its handshake ID (no NEW_CONNECTION_ID, as the draft asks, so clients cannot migrate to a new ID). The key bytes go into the native layer once (newLoadBalancerKey wipes your array); an endpoint takes its own copy when it is given the configuration, so you may close your handle after bind or updateLoadBalancer. connectionIdLength must equal 1 + serverId + nonceLength and be at least 8; a plaintext configuration cannot be combined with a preferredAddress.

Nonces come from a counter, permuted with a key derived from the configuration key (in clear, a key of the process), so they show no pattern and none repeats: every endpoint of the process that uses the same key and nonce length (in clear, the same nonce length), with any server ID, draws from one counter. These counters live as long as the process. The draft forbids reusing a nonce (section 9.6), and a new process knows nothing of the last one's counter, so either give the configuration a nonceReservation, or give each process start a key no earlier process used (a fresh key per start and per instance). A plaintext configuration (no key) must have a reservation: its nonces travel in clear, and QuicLbConfig refuses one without. A reservation stores a high-water mark durably (load(), store(mark), for instance an fsync'd file per key), one block of 65,536 nonces ahead of need, and the next process starts past it; in clear it also keeps a 16-byte random secret() that keys the permutation. A crash skips the rest of a block and never reuses one. A failed store is retried after a back-off counted in receive batches (one, doubling to 1,024, times the loops; about one store a round, nothing drawn meanwhile) and counted in EndpointStats.loadBalancerReservationFailures; once the reserved nonces are used up, the requests in between get an unroutable ID.

To roll out a new configuration (a new key, say), give it to the load balancers first, then to each server:

// guide:quic:load-balancer-update
val nextKey = KslQuicCrypto.newLoadBalancerKey(nextKeyBytes)
val next = QuicLbConfig(configId = 2, serverId = byteArrayOf(0x31, 0x44, 0x1a), nonceLength = 4, key = nextKey)
endpoint.updateLoadBalancer(next)

New connection IDs use it at once, and every live connection gets one NEW_CONNECTION_ID under it that retires its earlier IDs; those keep routing (and can still be answered with a Stateless Reset) until the client retired them. A second change while a connection's client has not yet retired what the first one asked for waits for those retirements (RFC 9000 section 5.1.2), then goes out. A codepoint that the current or previous configuration holds can only be given that same configuration again. Pass null when the server has no valid configuration: it then issues unroutable IDs (codepoint 0b111, which the balancer routes by 4-tuple), gives new connections a single ID and disable_active_migration, and live connections keep the IDs they have and get no new ones. The same happens on its own when a configuration's nonces run out: after 2^(8 x nonceLength) nonces of its key (2^32 for 4 bytes, shared by every endpoint of the process with that key; Retry packets and connection attempts draw them too, at most at the stateless rate limits), counted in EndpointStats.loadBalancerNoncesExhausted and logged at Warn; then roll out a new key. A connection that had its full set of IDs then keeps them and gets no more; one whose configuration changes to plaintext gets exactly one plaintext ID. A server ID used in clear must never be used encrypted, or the other way round (the call refuses it).

The Ktor server takes the configuration as quicLoadBalancer and changes it with engine.updateLoadBalancer(next); Http3Endpoint.updateLoadBalancer does the same for an HTTP/3 endpoint, and EndpointCore.updateLoadBalancer for a sans-IO endpoint driven by your own loop.

With several loops on one port, every loop issues IDs of the same configuration; the loop that owns an ID is the one it hashes to under a key the loops share (whatever the ID's codepoint), so a datagram that lands on another loop is still forwarded to its owner. A loop that draws a nonce whose ID hashes to another loop keeps it for that loop (up to 1,024 per loop); past that it issues the ID itself and the group records the exception (up to 65,536 live IDs, each leaving with its ID; when that many live, the nonce is spent unused rather than any live exception dropped). The SCID of a Retry takes no exception (a client that never comes back would never release it): its nonce is spent unused past a full pool, counted in EndpointStats.loadBalancerNoncesWasted. After a Retry the connection keeps that SCID as its one server ID; one of the previous configuration then gets the change's NEW_CONNECTION_ID that retires it, and an unroutable one made only because no nonce was reserved is replaced. An update builds the new configuration on Dispatchers.IO (a reservation's first store may fsync there), off the endpoint's loops, and switches to it on them, one update at a time; a caller cancelled after the switch leaves it in force. The call cannot be cancelled while it waits for the reservation's store or for a loop: a store that hangs, or a wedged loop, holds it (a group switches on loop 0 and the other loops move their connections in the background, after the call returned; one that does not within 5 s is logged and moves them at its next receive batch). Later stores run on the loop that draws past half a block; after a failed store the retries are paced by the receive batches of every loop (never by the requests themselves, so a flood of them cannot drive it), with the back-off scaled by the number of loops, so the group makes about one try a round however its traffic is spread. The hash also takes a client's random first Initial DCID for one of ours one time in 32 (when its first octet happens to encode our length); that client's datagrams then all go to the loop the DCID hashes to: an extra copy between loops for about 1 in 32 new connections. The Stateless Reset rule stays: a loop answers an unknown connection ID only when the stateless rate limit would let the answer out, it carries the current or previous configuration's codepoint, decrypts to this server's ID (within a budget of decryptions a second, per address and in total) and hashes to that loop; unroutable IDs are never answered.

Admission and endpoint limits

A server decides per new client Initial whether to create a connection. handleDatagram runs only cheap checks on an unknown Initial (1200 bytes, a supported version, a DCID of at least 8 bytes, no reflective source port such as 53 or 123) and copies it into a bounded queue of initialQueueCap (1024) entries; the loop then calls processPending once per receive batch. That step checks the Retry token, the accept queue, the hard limits (maxConnections, maxConnectionsPerIp, 256 per IP by default; both count the whole endpoint, every loop, as acceptQueue does) and asks ConnectionAdmission.admit(attempt), which answers Allow, Retry, Drop or Close(code). acceptQueue (128 by default, shared by all loops) counts only the connections waiting for accept(), not the handshakes in flight (unvalidated Initials from spoofed sources must not lock real clients out). While it is full, a new client Initial is answered statelessly with an Initial CONNECTION_CLOSE carrying CONNECTION_REFUSED (0x02), under the same rate limits as Retry and Version Negotiation: the client's connect fails at once with ConnectionLost.TransportClosed(code = 0x02) and no TLS handshake is spent on it. The queue never holds more: a handshake admitted earlier that completes while acceptQueue connections wait is closed with CONNECTION_REFUSED as well. An application whose accept() loop lags behind bursts raises acceptQueue. Handshakes in flight are bounded by maxConnections, maxConnectionsPerIp and the admission policy (Retry).

// guide:quic:admission
val config = quicEndpointConfig {
    server = serverConfig
    admission = ConnectionAdmission.default(maxInflightHandshakes = 256, maxHandshakeBufferBytes = 8L * 1024 * 1024)
    maxConnectionsPerIp = 64
    maxConnectionLifetime = 12.hours        // closed with NO_ERROR when it passes
}

The default policy asks an unvalidated client for a Retry when the attempt would be more than maxInflightHandshakes concurrent handshakes or the unfinished handshakes already hold more than maxHandshakeBufferBytes, and always lets in a client whose Retry or NEW_TOKEN token already validated its address (the hard limits still apply); ConnectionAdmission.AlwaysRetry makes every unvalidated client prove its address first. A Retry for an attempt whose Retry token already validated the address is a contract violation: the endpoint drops the Initial and counts it in EndpointStats.admissionContractViolations instead of sending a second Retry. An exception out of admit is treated as Drop and counted the same way. Stateless answers (Retry, Version Negotiation, Stateless Reset, INVALID_TOKEN close) are rate limited per address (statelessPerAddressPerSecond, 8) and in total (statelessTotalPerSecond, 1000). QuicEndpoint.stats exposes every counter, summed over the loops (see Observability).

NEW_TOKEN. Once a connection's handshake is confirmed, the server sends the client one address-validation token (RFC 9000 section 8.1.3), and one more each time the client is validated on a new IP address, at most four per connection. A client that shows such a token on a later connection from the same IP address arrives as a validated ConnectionAttempt (addressValidated = true): AlwaysRetry lets it in without a Retry, and the server's first flight is not held to three times what the client sent. The token is 0x02 | nonce | AEAD(issuedAt) under keys that live only in this process (shared by every loop, rotated hourly; tokens do not survive a restart and do not work on another instance), bound to the client's IP address but not its port, valid for QuicServerConfig.newTokenLifetime (24 hours; null issues none) and accepted once: a register of the tokens it accepted, kept for at least the lifetime, treats a second use as no token.

The register holds at least newTokenReplayCapacity tokens per lifetime (1,048,576 by default, 32 MiB allocated when the first token is shown; about 32 bytes per token, rounded up to a power of two). It never forgets a token early: once it is full (first in parts, as its 64 stripes fill unevenly), a returning client's token is treated as absent, not accepted twice, so the client gets whatever the policy gives a client without a token (a Retry under AlwaysRetry or under load). Entries age out one to two lifetimes after they were added. A server that expects more returning clients per lifetime raises the capacity or shortens the lifetime (the register only has to cover one lifetime); a rising newTokensRejected with normal traffic says it is full. An attacker can fill it only with tokens it was issued: one completed handshake per token (four per connection at most, each for another IP it owns), each shown once from its IP, so filling the default takes over a million connections within a day, about 12 a second for 24 hours, and costs honest clients only the round trip their tokens would have saved.

A token that does not validate (forged, expired, another IP, used before) is never refused with INVALID_TOKEN; the Initial is treated as one without a token, and newTokensRejected counts it. A policy may still answer a token holder with a Retry. Clients keep tokens only with a tokenStore (Address tokens).

// guide:quic:new-token
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val config = quicEndpointConfig {
    server = quicServerConfig(tlsServerConfig) { newTokenLifetime = 6.hours }   // null: issue none
    admission = ConnectionAdmission.AlwaysRetry   // returning clients with a token skip the Retry
}

Reliable stream reset (experimental)

QuicConfig.resetStreamAt = true advertises reset_stream_at (draft-ietf-quic-reliable-stream-reset). When the peer advertised it too, QuicStream.resetAt(code, reliableSize) abandons a stream like reset but keeps delivering its first reliableSize bytes, retransmitting them as needed; the peer reads them and then fails with the reset. Only bytes already flushed to the stream count (a larger size is cut to them). Without the peer's parameter resetAt is a plain reset, and the prefix may be lost. The frame waits until every reliable byte was sent once, so its final size stays within the peer's flow control (draft-11 section 4): with little credit the reset reaches the peer later, after the reliable bytes. Both codepoints of the parameter are sent and accepted, 0x1d and the unregistered one of earlier drafts, as quic-go does. A server that accepts 0-RTT but drops a remembered reset_stream_at is treated like one that lowers a limit (PROTOCOL_VIOLATION). Once RESET_STREAM_AT is in play on a stream, a later reset with another error code is STREAM_STATE_ERROR. A peer that sends RESET_STREAM_AT without our parameter, or with a reliable size above its final size, closes the connection with FRAME_ENCODING_ERROR. QuicConnection.resetStreamAtEnabled tells whether both sides advertised the parameter. WebTransport uses it to keep a stream's header.

Final sizes (experimental)

QuicStream.sentFinalSize and QuicStream.receivedFinalSize are Deferred<Long> values that complete with the final size of each half of a stream (RFC 9000 section 4.5), the flow-control credit it used as both sides count it. The sending half's size is known once its reset is queued (reset, the reset that answers the peer's STOP_SENDING, or resetAt once its frame goes out) or once its FIN first went out; the receiving half's as soon as the peer's FIN, RESET_STREAM or RESET_STREAM_AT arrives, also when the bytes were never read or after stopSending. A protocol that counts data across streams, such as WebTransport flow control (draft-ietf-webtrans-http3-16 section 5.4), needs it for a stream that was reset. The size counts every byte of the stream, an application's own header too: WebTransport subtracts its stream header itself. A stream sent in 0-RTT reports its size only after the server accepted the early data; a rejection fails both with QuicException.StreamError.EarlyDataRejected, a lost connection with its ConnectionLost, and a half the stream does not have at once with IllegalStateException. Every caller gets the same Deferred: await it, never cancel it. In the sans-IO core the same moments raise ConnectionEvent.StreamFinalSize, once per half.

QuicStream.receivedOffset is a StateFlow<Long> of the highest offset of the peer's half received so far, read or not and in order or not, and then its final size: what QUIC flow control counts (RFC 9000 section 4.1), so a protocol with limits of its own across streams can check bytes nobody has read yet.

QuicStream.sendReleased is the sending counterpart: a StateFlow<Long> of the bytes of our half the connection's send buffer (maxSendBuffer, shared by every stream) has let go of, acknowledged by the peer or dropped by a reset, and all of them once the stream retired or the connection ended. The bytes written minus these are what the stream holds of the shared buffer: a stream the peer never reads keeps what its window did not let out, and a protocol multiplexing users that do not trust each other over one connection (WebTransport sessions) can cap each user's share with it. It is kept up to date from its first read on, which catches up with what was released before.

Datagrams (RFC 9221)

Both sides advertise max_datagram_frame_size (65 535 by default; maxDatagramFrameSize = 0 turns the extension off and rejects DATAGRAM frames). On the sans-IO core, maxDatagramPayload says how many bytes fit one frame for the current peer and MTU, less 32 bytes kept for a short ACK next to a full-size datagram (0 when the peer does not support datagrams); a DatagramSender set on the core is asked for frames while each 1-RTT packet is built with an open congestion window, and learns through onAcked / onLost what became of each id — datagrams are never retransmitted. Received payloads wait in a queue of 128 (datagramReceiveQueue); when it is full the oldest is dropped and counted in stats.datagramsDropped (which also counts received UDP datagrams the connection discarded unprocessed: from an unknown server address, a late Initial, a full undecryptable-packet buffer). The core raises DatagramsReadable and hands them out with readDatagram.

On a QuicConnection:

// guide:quic:datagrams
connection.sendDatagram(reading, DatagramPolicy.LatestWins(key = "temperature"))   // replaces a queued reading of the same key
when (val r = connection.trySendDatagram(frame, DatagramPolicy.Reject)) { DatagramSendResult.QueueFull -> dropFrame(); DatagramSendResult.Closed -> stop(); else -> {} }
peer.datagrams.collect { d -> handle(d.data) }   // on the receiving end (the other connection of the pair)

sendDatagram copies the payload into the loop's send queue of 32 datagrams / 1 MiB (datagramSendQueue, datagramSendQueueBytes). DropOldest (the default) and LatestWins never wait: a full queue drops its oldest entry, or the entry with the same key. The hand-over to the loop is bounded too (at most another datagramSendQueue datagrams), so a burst that outruns the loop drops its oldest datagrams even on an idle network; send a burst you cannot lose under Reject. Reject makes trySendDatagram answer QueueFull and sendDatagram suspend until room returns. trySendDatagram never enters the loop and allocates only the copy plus a small wrapper. A payload above maxDatagramSize (a StateFlow, following the path MTU) gives TooLarge / DatagramTooLarge; without datagram support on either side you get Unsupported / DatagramUnsupported. datagrams reads the core's 128-entry queue directly, so what nobody collected in time is dropped there and counted in stats.datagramsDropped (beside the UDP datagrams the connection discarded unprocessed). Datagrams go ahead of stream data; experimental: sendDatagram(data, policy, priority) and trySendDatagram(data, policy, priority) schedule one by RFC 9218 urgency instead, so it does not go ahead of strictly more urgent streams' data (the sans-IO hook is DatagramSender.nextUrgency). The urgency is strict both ways: more urgent bulk streams hold such datagrams back, and the datagrams go ahead of streams of the same or a lower urgency, so a flood of them starves those. The send queue keeps one FIFO per urgency: a datagram never waits behind a less urgent one, and datagrams of one urgency leave in the order they were queued (all RFC 9221 asks). HTTP/3 sends every HTTP datagram at its request stream's priority this way (WebTransport, draft-ietf-webtrans-http3-16 section 3.4).

Testing your application

io.kuicksilver.testing.MemoryNetwork (module kuicksilver-testing) is a UDP network in memory: every open(address) binds a DatagramIo there, and a datagram reaches the socket bound to its destination or vanishes. Give it to endpoints through QuicEndpointConfig.io and the whole stack runs unchanged, OpenSSL TLS included, on every platform and without ports. cut(address) makes an address go dark (and restore brings it back), mtu drops larger datagrams, dropped counts what vanished; it is safe to share between endpoint loops on different threads. Like a UDP socket, each socket holds at most receiveBuffer unread datagrams (256 by default) and drops what arrives on top, a datagram larger than the receiver's slot is dropped rather than truncated, and open on port 0 binds a free ephemeral port (49152 and up) unless assignEphemeralPorts = false. Marks are always bleached: sockets report no ECN.

// guide:quic:memory-network
val network = MemoryNetwork()
val wifi = InetSocketAddress("10.0.0.1", 50000)
val server = QuicEndpoint.bind(InetSocketAddress("10.0.0.2", 443), quicEndpointConfig { this.server = serverConfig; io = { network.open(it) } })
val client = QuicEndpoint.bind(wifi, quicEndpointConfig { io = { network.open(it) } })
val connection = client.connect(server.localAddress, quicClientConfig(tlsClientConfig))
val accepted = server.accept()
echo(connection, accepted, 1024)                                       // ... the application talks
network.cut(wifi)                                                      // the Wi-Fi goes dark
connection.migrate(network.open(InetSocketAddress("10.0.0.3", 50000)))   // and the client moves to LTE

samples/realtime-telemetry is a complete application built this way: its common tests run over MemoryNetwork, its JVM and macOS tests over real UDP.

Lifecycle and errors

A connection ends exactly once, and closed completes with the reason: ApplicationClosed (ours or the peer's close(code)), TransportClosed (a protocol error, a TLS alert as 0x0100 + alert), Timeout, StatelessReset, NoViablePath, VersionNegotiation or Internal. From then on everything that waits on the connection fails with that same exception: openBidi, acceptStream, sendDatagram, keyUpdate, addPath, exportKeyingMaterial, the stream channels (a writer waiting for send-buffer room gets ClosedWriteChannelException with it as the cause) and the datagrams flow, which throws it even after a local close; incomingStreams() completes instead. trySendDatagram throws it too rather than answering QueueFull, so a caller retrying on QueueFull cannot spin on a dead connection. Cancelling your own coroutine is never turned into a QuicException; a cancelled connect closes the connection it started (CONNECTION_CLOSE, then the closing period). After QuicEndpoint.close(), accept() throws EndpointClosing even for connections that had completed their handshake and were still waiting in the accept queue.

close(code, reason) suspends until the CONNECTION_CLOSE is sent; close() from AutoCloseable sends code 0 without waiting. QuicEndpoint.close() is asynchronous too: it closes every connection and the socket on the loop after it returns, and connect/accept throw EndpointClosing from then on. pathEvents is a hot flow without replay, so start collecting it before migrate or probe. stats can be read from any thread; it is a snapshot whose fields are read without a lock.

Logger. QuicEndpointConfig.logger takes a KuicksilverLogger: two methods, isEnabled(level) and log(level, message, cause), so bridging it to SLF4J, Logcat or os_log is a few lines and the library depends on no logging framework. The default, KuicksilverLogger.Stderr, writes warnings and errors to standard error (what the library did before it had a logger); KuicksilverLogger.None drops everything and KuicksilverLogger.stderr(level) picks another threshold. Debug logs each connection's lifecycle (opened, handshake complete, path change, 0-RTT outcome, close with its reason), Info the endpoint's (shutting down, closing), Warn degradations (a fallback to the portable socket, a failing listener or qlog sink), Error a loop that died. A logger that throws is ignored and counted in listenerFailures. A line is built only when its level is enabled. The library never logs secrets: keys, traffic secrets, session tickets, Retry and address-validation tokens and reset tokens stay out of every level; connection IDs and addresses are logged.

Connection listener. QuicEndpointConfig.listener takes a ConnectionListener whose callbacks report onOpened, onHandshakeCompleted, onZeroRtt (accepted or rejected), onPathChanged and onClosed with the ConnectionLost reason: who closed (initiator), the code and, for a transport error, the frame type. They run on the loop that owns the connection, in order, exactly once each for opened and closed, so they must not block; an exception out of one, a CancellationException included, is logged and counted in listenerFailures, and the connection goes on. ConnectionInfo.id is the original destination connection ID in hex, the same name the connection's qlog trace has.

// guide:quic:observability
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val observed = quicEndpointConfig {
    this.server = quicServerConfig(tlsServerConfig)
    logger = KuicksilverLogger.stderr(LogLevel.Info)
    listener = object : ConnectionListener {
        override fun onClosed(connection: ConnectionInfo, reason: QuicException.ConnectionLost) {
            println("${connection.id} ${connection.remoteAddress}: ${reason.message}")
        }
    }
}

Graceful shutdown

QuicEndpoint.shutdown(grace) takes an endpoint out of service without cutting connections short. From the call on, a new client's Initial is refused at once with a stateless CONNECTION_CLOSE carrying CONNECTION_REFUSED (the refusal of a full accept queue, under the same rate limits; counted in connectionsRefusedShutdown) and connect throws EndpointClosing; handshakes already in flight go on and still reach accept(). The live connections get grace to finish; QUIC itself has no "go away" signal, so tell your peers through your application protocol (HTTP/3 has GOAWAY: Http3Endpoint.shutdown and the Kuicksilver Ktor server's stop(gracePeriod, timeout) send it). Once the last connection has closed, or at the deadline, whatever is left is closed with an application CONNECTION_CLOSE (code, 0 by default) and the endpoint closes; shutdown returns when the socket is released, like closeAndJoin. Calling it again, or close(), ends the grace period at once.

// guide:quic:shutdown
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
server.shutdown(grace = 30.seconds)

qlog

DirectoryQlogSink writes one JSON-SEQ file per connection (schema draft-ietf-quic-qlog-main-schema/quic-events 0.3; an HTTP/3 connection adds its own events, HTTP/3: qlog), named <odcid>_<client|server>_<random>.sqlog after the connection's original destination CID. On a server the client chooses that CID, so the sink treats the name as hostile: the directory is created owner-only (0700) when missing and refused when it is a symbolic link, belongs to another user, or is writable by group or others without the sticky bit (keep it out of /tmp); every file is created exclusively and never through a link, and the random suffix gives a client that reuses a CID a file of its own. qlog on a public server is a disk-exhaustion surface, so the sink has two ceilings besides the fixed 64 MiB per connection (fixed limits): at most maxOpenTraces traces open at once (256) and maxTotalBytes written over its lifetime (1 GiB); beyond them connections are not traced (DirectoryQlogSink(dir, maxOpenTraces, maxTotalBytes), experimental). HTTP header and trailer values are redacted in the trace unless the sink sets logHeaderValues (the constructor's fourth parameter, experimental).

val qlogDir = "/var/log/kuicksilver/qlog"
// guide:quic:qlog
val quicWithQlog = quicConfig { qlog = DirectoryQlogSink(qlogDir) }

On Android, qlogDirectory(context, name = "kuicksilver-qlog") (experimental, 0.3.0, in io.kuicksilver.quic.qlog) returns a DirectoryQlogSink for the directory name in the app's cache directory. It creates the directory owner-only (0700) at once and checks it like any other. The cache directory is private to the app, is not backed up, and is the first thing the system clears when storage runs low. Pull the traces with adb shell run-as <package> ls cache/kuicksilver-qlog (debuggable builds). The helper works in release builds too, since a trace holds no keys. Below API 26 it throws IllegalArgumentException: without java.nio.file the directory cannot be checked, so qlog is refused there.

A sink is called on the endpoint loop, so a file sink on a slow disk would slow every connection of the loop. Wrap it in AsyncQlogSink: the loop only queues records, and one writer on Dispatchers.IO (one thread at a time) opens, writes and closes the files. Its queue holds queueCapacity records (8192) over all connections; a record that finds it full is dropped and counted in dropped, so a stalled disk loses trace lines, never throughput. sampleEvery = n traces one connection in n; flush() waits for what is queued and close() stops the writer after it.

// guide:quic:qlog-async
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val quicWithAsyncQlog = quicConfig { qlog = AsyncQlogSink(DirectoryQlogSink(qlogDir), sampleEvery = 10) }

The sans-IO core directly

ConnectionCore has no coroutines and no sockets (ADR-0004): handleDatagram feeds it a received datagram, poll fills a PacketBatch with what it wants to send, nextTimeoutOrNever/onTimeout drive its one timer, nextEvent drains application-visible events. A caller with its own loop (for example a real-time protocol with its own scheduler) can drive it directly instead of going through QuicEndpoint.

// guide:quic:core-loop
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val core = ConnectionCore.client(quic, tlsClientConfig, KslQuicCrypto, remote, Random, now)
val out = PacketBatch(capacity = 4)
try {
    while (running) {
        val n = core.poll(out, now)
        for (i in 0 until n) send(out.buffer(i), out.length(i), out.address(i)!!)
        val deadline = core.nextTimeoutOrNever()          // TimeMark.NEVER when no timer is armed; nextTimeout() is the nullable form
        val datagram = receiveOrWaitUntil(deadline)       // your socket; returns null when the deadline passed first
        now = clock()
        if (datagram != null) core.handleDatagram(datagram.buffer, datagram.length, datagram.from, Ecn.NotEct, now)
        else if (deadline <= now) core.onTimeout(now)
        while (true) { val event = core.nextEvent() ?: break; handle(event) }
    }
} finally { out.close() }

Stream events tell such a loop when to retry instead of polling: StreamReadable after new data, an end or a reset; StreamWritable once acknowledgements free send-buffer room after writeStream took fewer bytes than offered, or once the peer's MAX_STREAM_DATA/MAX_DATA gives credit to data that was waiting; StreamsAvailable once MAX_STREAMS raises a limit that refused openStream; StreamFinished once a stream is done in both directions and retired.

core is reached through QuicConnection.core too (@ExperimentalKuicksilverApi), but it must only be touched from the endpoint loop that owns it when the connection came from QuicEndpoint.
