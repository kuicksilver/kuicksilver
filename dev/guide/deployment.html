Deploying the HTTP/3 server

What this page is for. It is for the person who runs embeddedServer(Kuicksilver) in production and needs HTTP/3 to work: ports, firewalls, containers, load balancers, certificates, host settings and how to check from both ends.

Before you start

  • A server built with io.kuicksilver:kuicksilver-ktor-server (version 0.3.0 or newer) and Ktor 3.6.x, on JVM 17 or newer or as a Kotlin/Native server on Linux, macOS or Windows (Platforms).
  • A certificate chain and private key (PEM) for the host name clients use. HTTP/3 uses the same certificate as TLS over TCP.
  • Control over the network path: you can open the same port number on TCP and on UDP.

Minimal example. The server that this page deploys is the one in Ktor engines: Minimal example (a tlsConnector with an identity; it serves HTTP/1.1 on TCP and HTTP/3 on UDP, same port). What has to reach it is in Ports and Alt-Svc, and Checking a deployment shows how to test it.

Imports. The Kotlin blocks on this page use these imports (the rest of the server's imports are in Ktor engines: Imports):

// guide:deployment:imports
import io.ktor.server.application.ApplicationCallPipeline
import io.ktor.server.application.call
import io.ktor.server.engine.embeddedServer
import io.ktor.server.response.header
import io.ktor.server.response.respondText
import io.ktor.server.routing.get
import io.ktor.server.routing.routing
import io.kuicksilver.annotations.ExperimentalKuicksilverApi
import io.kuicksilver.ktor.server.Http3Advertising
import io.kuicksilver.ktor.server.Kuicksilver
import io.kuicksilver.ktor.server.KuicksilverApplicationEngine

This guide is for running embeddedServer(Kuicksilver) in production with HTTP/3 working: what has to reach the server, what the host and the network in front of it need, and how to check from both ends why a client does or does not use HTTP/3. The engine's options are in Ktor: Server and the configuration reference; error messages are in troubleshooting. This page links there instead of repeating them.

Statements about other products (Docker, Kubernetes, cloud load balancers, proxies) were checked against their documentation on 2026-11-05 and link to it. Products and details this page does not name were not checked: read their documentation before you rely on them.

How a client gets to HTTP/3

  1. The client connects over TCP and TLS (HTTP/1.1; the TCP side's ALPN is http/1.1).
  2. The response carries Alt-Svc: h3=":<port>"; ma=86400 (RFC 7838): HTTP/3 is on UDP, on that port of the same host, for 24 hours.
  3. The client opens QUIC to that UDP port. The TLS handshake there uses the origin's host name (SNI) and checks the same certificate, with ALPN h3.
  4. The client caches the alternative. If UDP does not get through it falls back to TCP; the Kuicksilver client then marks the alternative broken for a while (Ktor: Racing and fallback).

So the TCP port, the UDP port, the Alt-Svc header and the certificate all have to work for HTTP/3. When one of them is missing, clients quietly stay on HTTP/1.1.

Ports and Alt-Svc

Every tlsConnector serves HTTP/1.1 on TCP and HTTP/3 on UDP with the same port number and the same host (default 0.0.0.0), and so does a plain connector when the configuration has an identity (with EngineMain, the kuicksilver.tls.* keys). The engine binds both as a pair: a fixed port whose UDP side is taken fails the start (Ktor: HTTP/3 on the server). Open, forward and publish both <port>/tcp and <port>/udp everywhere on the way.

The engine's Alt-Svc names the port it bound, h3=":<bound port>" (no host: the same host as the request). That is right only when clients reach the UDP port under the same number. When a NAT, a container port mapping or a load balancer exposes another number, clients would try the wrong port. Two fixes:

  • Map the same number on both sides (443 outside to 443 inside), so the engine's header is right as it is.
  • Or let the application send its own Alt-Svc. The engine never replaces an Alt-Svc the application set, so the application then also follows the run-time switch engine.http3Advertising (Turning HTTP/3 off without a restart) itself. Use it only on connectors that do serve HTTP/3: not on a plain connector without TLS, and not when the start logged "HTTP/3 is not served ..." (a UDP bind failure, a platform without a QUIC server, udpSocketCount above 1 without the accelerated socket); there the header would send clients to a port where nothing answers:
// guide:deployment:public-alt-svc
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val publicPort = 443   // the UDP port clients reach (the load balancer's or the NAT's), not the one bound here
lateinit var engine: KuicksilverApplicationEngine
val server = embeddedServer(Kuicksilver, configure = {
    tlsConnector(identity) { port = 8443 }
}) {
    intercept(ApplicationCallPipeline.Plugins) {
        // an Alt-Svc the application sets is never replaced, so it follows engine.http3Advertising itself
        val h3 = engine.http3Advertising == Http3Advertising.On
        call.response.header("Alt-Svc", if (h3) "h3=\":$publicPort\"; ma=86400" else "clear")
    }
}
engine = server.engine

The sample also sends its header on HTTP/3 responses, where the engine sends none under On; that only repeats what the client already uses.

The client side has its own rule: the Kuicksilver client ignores an alternative on an unprivileged port (1024 and up) for an origin on a privileged one, as Chromium does (Ktor: Discovery and Alt-Svc). So for an origin on https://host/ (port 443), HTTP/3 must also be reachable on a port below 1024, in practice UDP 443.

ma=86400 means clients remember the alternative for a day. To withdraw HTTP/3, use Clear or Drain (Turning HTTP/3 off without a restart), which send Alt-Svc: clear, rather than closing the UDP port, and keep that mode for at least 24 hours: clear only reaches clients that come back over TCP, so a client that cached the alternative and returns within its ma still tries QUIC. Clients that find the UDP port closed wait for their QUIC attempt to time out before they fall back. altSvc = false (kuicksilver.altSvc with EngineMain) stops the engine's header entirely: then only clients that try HTTP/3 without being told (the Kuicksilver client's Preferred mode or quicHints, curl --http3) use it.

The engine does not publish DNS HTTPS records (RFC 9460); publishing one in your DNS zone is up to you. A record such as example.com. 300 IN HTTPS 1 . alpn=h3,h2 lets clients that look them up (browsers, and the Kuicksilver client with http3 { httpsRecords = ... }, see HTTPS records) use HTTP/3 from the first request; for a port other than 443 the name is _<port>._https.<host>.

Firewalls and security groups

  • Allow inbound UDP on the port, next to TCP: in the host firewall (ufw, firewalld, nftables; Windows Defender Firewall, see troubleshooting: Windows) and in the cloud's security group or network ACL. A rule for TCP 443 alone is the most common reason a server serves HTTP/1.1 but no client ever arrives over QUIC.
  • Answers leave from the same UDP port, and from the address the kernel's route picks (the address the client sent to only on a host with one address; see Reply addresses). A stateful firewall allows them once the inbound flow is allowed. A stateless network ACL needs an outbound rule for UDP from the port to the clients' ports.
  • Many corporate and guest networks block UDP 443 on the client side. You cannot fix that from the server. Clients fall back to TCP: the Kuicksilver client reports FallbackReason.HandshakeTimeout and then BrokenAlternative (Ktor: Why did this request not use HTTP/3?).

Containers

Docker

Docker publishes TCP unless a mapping says /udp; publish both protocols on the same number (Docker: port publishing: "-p 8080:80/udp Map port 8080 on the Docker host to UDP port 80 in the container"):

docker run -p 443:443/tcp -p 443:443/udp my-server-image

EXPOSE 443/tcp 443/udp

EXPOSE only documents ports; the -p mappings publish them. With -p 8443:443/udp (another host port) the engine's Alt-Svc names 443, which is wrong outside: map the same number or send your own header (Ports and Alt-Svc). On Linux, --network host skips Docker's port mapping, and the engine binds the host's ports directly.

The UDP buffer limits are kernel settings of the host (UDP socket buffers). Set them on the host (the Kubernetes node), not in the image.

The image

  • A glibc base image. The native library inside the JVM jar is built for glibc 2.17 or newer and needs libresolv.so.2 (part of glibc) since 0.3.0. musl is not supported: on an Alpine image (or any -alpine tag) the library does not load, KslLoader.availability() is Unavailable and the server cannot start its TLS connectors. Use an image built on a glibc distribution (Debian, Ubuntu, RHEL and its derivatives). A Kotlin/Native server on Linux needs glibc too (2.19 on x64, 2.25 on arm64), plus the system zlib (libz.so.1) and libresolv.so.2, so scratch and images without a C library do not work; a Native client that verifies with TrustConfig.Platform also needs a CA bundle (ca-certificates; TLS: Linux trust store). Platforms has every floor.
  • A read-only root file system, or a noexec temporary directory. On the JVM the native library is extracted on first use into <java.io.tmpdir>/kuicksilver-native-<user> and loaded from there (TLS: Native library availability). With readOnlyRootFilesystem: true that write fails, and with a noexec /tmp the load fails ("... if the work directory is mounted noexec set -Dkuicksilver.native.workdir"). Set -Dkuicksilver.native.workdir to a directory on a writable volume that allows executables, such as an emptyDir. Name a directory below the volume's mount point: the loader creates it with owner-only permissions and refuses a directory that another user owns or can write to, as the root of a volume often is. The loader does not check the directories above a -Dkuicksilver.native.workdir (the volume root among them): whoever else can write to one of them could rename the work directory, so keep processes of other users off that volume. An emptyDir mounted at /tmp instead is world-writable without the sticky bit: the library then goes to the user's cache directory when it is writable, else it stays in /tmp and every start logs the warning "native library work directory … is writable by others without the sticky bit". Setting -Dkuicksilver.native.workdir to a directory below the mount point, as above, avoids both.
  • Port 443 without root. On Linux, binding a port below 1024, TCP and UDP alike, needs CAP_NET_BIND_SERVICE, or a network namespace whose net.ipv4.ip_unprivileged_port_start is at or below the port. In Kubernetes that sysctl is a "safe" one since 1.22, so a pod may set it without node changes (not together with hostNetwork; Kubernetes: sysctls); with Docker, docker run --sysctl net.ipv4.ip_unprivileged_port_start=443 ... does the same. Docker's own documentation says non-root containers cannot bind ports below 1024 "especially in Kubernetes and Docker Engine < 20.10" (Docker: Hardened Images, troubleshooting), so a newer engine may already allow it: docker run --rm my-server-image cat /proc/sys/net/ipv4/ip_unprivileged_port_start prints the value your containers get. On a host with systemd, AmbientCapabilities=CAP_NET_BIND_SERVICE next to User= in the unit grants the capability to the server process alone. Or bind an unprivileged port (8443) and map 443 to it in front: then the engine's Alt-Svc names 8443, so send your own header (Ports and Alt-Svc).

A pod spec with all three (a non-root user, a read-only root file system, port 443):

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001                 # a non-root user ID
    sysctls:
      - name: net.ipv4.ip_unprivileged_port_start
        value: "443"
  containers:
    - name: my-server
      image: my-server-image          # a glibc base, not Alpine
      securityContext:
        readOnlyRootFilesystem: true
      env:
        - name: JAVA_TOOL_OPTIONS
          value: "-Dkuicksilver.native.workdir=/var/lib/ksl/native"
      ports:
        - { containerPort: 443, protocol: TCP }
        - { containerPort: 443, protocol: UDP }
      volumeMounts:
        - { name: ksl, mountPath: /var/lib/ksl }
  volumes:
    - { name: ksl, emptyDir: {} }

Kubernetes

A Service carries the TCP and the UDP port as two entries with the same number:

apiVersion: v1
kind: Service
metadata:
  name: my-server
spec:
  type: LoadBalancer
  externalTrafficPolicy: Local   # keeps the client's address; see "The client's address" below the manifest
  selector:
    app: my-server
  ports:
    - name: https
      protocol: TCP
      port: 443
      targetPort: 443
    - name: h3
      protocol: UDP
      port: 443
      targetPort: 443

The pod spec should declare containerPort: 443 with protocol: TCP and another with protocol: UDP as well (containerPort is informational: the Service's targetPort decides where traffic goes).

  • Mixed protocols in one LoadBalancer Service are stable since Kubernetes 1.26 (the MixedProtocolLBService gate is removed), but "The set of protocols that can be used for load balanced Services is defined by your cloud provider; they may impose restrictions beyond what the Kubernetes API enforces" (Kubernetes: Service, load balancers with mixed protocol types). Check that your provider's load balancer controller supports TCP and UDP on one port. Where it does not, use two Services (one TCP, one UDP) behind the same address if the provider can share one, or a load balancer you configure yourself.
  • The client's address. With the default externalTrafficPolicy: Cluster, packets may be source-NATed to a node's address. "If you set service.spec.externalTrafficPolicy to the value Local, kube-proxy only proxies proxy requests to local endpoints, and does not forward traffic to other nodes. This approach preserves the original source IP address" (Kubernetes: Using Source IP). This matters more for QUIC than for TCP. The QUIC endpoint limits connections per client IP address (quicMaxConnectionsPerIp, 256): behind a source NAT raise it or turn it off (QUIC connection limits); the TCP connectors' per-address limit, maxTcpConnectionsPerIp, is off by default and should stay off behind a source NAT. Behind a source NAT, every client counts against the node's address, and so does the stateless answer limit (8 per second per address): Retry packets and refusals beyond it are dropped, and those clients see a handshake timeout instead. Address validation tokens are also bound to the address the server sees.
  • Rolling updates. A graceful stop already does what an HTTP/3 client needs (Ktor: Graceful stop): GOAWAY to every live HTTP/3 connection, and new QUIC clients refused with CONNECTION_REFUSED (under the stateless rate limit) instead of timing out. Stop the server with Ktor's shutdownGracePeriod and shutdownTimeout; the larger of the two bounds the stop (keep the timeout ≥ the grace period), so keep the preStop delay plus shutdownTimeout below the pod's terminationGracePeriodSeconds. Clients like the Kuicksilver client recover quickly: it treats CONNECTION_REFUSED as transient, and a connection the pod closes with H3_NO_ERROR after its GOAWAY (at the end of the grace period) as an orderly end; either way the affected call falls back to TCP once (when it may be repeated) and the next one tries HTTP/3 again, which another pod may take. Neither marks the alternative broken (Ktor: Racing and fallback; before 0.3.0 both did, for 5 minutes doubling up to 2 days). Switching a pod to Http3Advertising.Drain before it stops has a cost: its responses send Alt-Svc: clear for the whole origin, not just that pod, so clients that get one drop the alternative until another response announces it again. Use Drain to take HTTP/3 out of service, not for routine restarts.

Health checks

The kubelet probes a container with exec, grpc, httpGet or tcpSocket (Kubernetes: probes): none of them speaks UDP, so the probes check the TCP side and the HTTP/3 side is watched from outside.

  • Readiness and liveness go to an HTTP route over TLS: httpGet with scheme: HTTPS ("the kubelet sends an HTTPS request skipping the certificate verification", same page), on the TLS connector's port.
  • The HTTP/3 side is checked by a canary outside the cluster (curl --http3-only, as in Checking a deployment, or a Kuicksilver client in H3Only mode) and by the endpoint counters as metrics: datagramsReceived that stops growing while TCP traffic goes on means UDP no longer reaches the pod; connectionsRefusedLimits growing means clients hit quicMaxConnections or quicMaxConnectionsPerIp (QUIC connection limits); handshakesFailedTimeout growing means clients start handshakes that never finish (lost answers, Reply addresses).
  • Drain is not unreadiness. Under Clear or Drain the pod still serves HTTP/1.1 and HTTP/2, so keep its probes passing; http3Advertising is part of the metrics instead. A graceful stop stops accepting TCP connections, so the probes fail during it on their own; a preStop delay lets the Service drop the pod before that.
// guide:deployment:health
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
lateinit var engine: KuicksilverApplicationEngine
val server = embeddedServer(Kuicksilver, configure = {
    tlsConnector(identity) { port = 443 }
}) {
    routing {
        // for the readiness and liveness probes: the kubelet probes over TCP (httpGet with scheme HTTPS)
        get("/healthz") { call.respondText("ok") }
        // for a metrics scraper: is QUIC arriving, and is it refused?
        get("/metrics/quic") {
            val s = engine.http3Stats
            call.respondText(
                "datagrams_received ${s.sumOf { it.datagramsReceived }}\n" +
                    "connections_active ${s.sumOf { it.connectionsActive }}\n" +
                    "refused_limits ${s.sumOf { it.connectionsRefusedLimits }}\n" +
                    "handshakes_failed_timeout ${s.sumOf { it.handshakesFailedTimeout }}\n" +
                    "http3_advertising ${engine.http3Advertising}\n",
            )
        }
    }
}
engine = server.engine

      readinessProbe:
        httpGet: { path: /healthz, port: 443, scheme: HTTPS }
        periodSeconds: 10
      livenessProbe:
        httpGet: { path: /healthz, port: 443, scheme: HTTPS }
        periodSeconds: 20
        failureThreshold: 3

Keep /metrics/quic off the public internet (a separate connector or port, or a network policy); the counters say nothing secret, but they are not for clients.

Load balancers and proxies

What can sit in front of the server

In front HTTP/3 reaches Kuicksilver? Notes
Nothing (public address on the host) yes the simplest setup
An L4 load balancer that passes UDP through (cloud network load balancer, kube-proxy, IPVS, nginx stream) yes per-flow routing, see connection IDs; with direct server return (IPVS-DR, a VIP on lo) bind host to the VIP, see reply addresses
An L7 proxy that terminates HTTP/3 itself (CDN, nginx http, other reverse proxies) no the proxy speaks HTTP/3 to clients and HTTP/1.1 (or HTTP/2) to the server; Kuicksilver then serves only that TCP side. Set altSvc = false (or strip the header at the proxy): the engine's h3=":<bound port>" would otherwise pass through and point clients at that port on the proxy's host

Notes on specific products (checked 2026-11-05):

  • AWS Network Load Balancer. Listeners support "TCP, TLS, UDP, TCP_UDP, QUIC, TCP_QUIC"; "To support both TCP and UDP on the same port, create a TCP_UDP listener", and its target groups must use TCP_UDP (AWS: NLB listeners). Client IP preservation "can't be disabled for UDP, TCP_UDP, QUIC, and TCP_QUIC target groups" (AWS: NLB target groups), so the per-IP limit sees real clients. Use TCP_UDP with Kuicksilver. The QUIC and TCP_QUIC listeners route by QUIC connection ID: not verified with Kuicksilver's QUIC-LB connection IDs (Connection IDs and several instances).
  • Cloudflare (proxied hostname): HTTP/3 ends at Cloudflare's edge; "HTTP/3 connection to the origin is not yet supported" (Cloudflare: HTTP/3). Cloudflare then reaches a Kuicksilver origin over TCP, and the origin's UDP port only serves clients that reach it directly. Set altSvc = false on the origin, so its Alt-Svc does not reach clients through Cloudflare.
  • nginx as an L7 proxy terminates HTTP/3 itself and talks to the upstream with proxy_http_version 1.0 | 1.1 | 2 (HTTP/2 since 1.29.4, HTTP/1.1 the default since 1.29.7; nginx: proxy_http_version). A Kuicksilver upstream serves HTTP/1.1; set altSvc = false on it, or drop the header with proxy_hide_header Alt-Svc. For UDP passthrough, the stream module's listen ... udp "configures a listening socket for working with datagrams", with reuseport "to handle packets from the same address and port in the same session" (nginx: stream listen). By default nginx connects to the upstream from its own address, so every client shares nginx's address against the per-IP limit (QUIC connection limits).
  • Google Cloud (GKE) and Azure: whether their load balancers take TCP and UDP on one port in one Service was not verified for this page; see their documentation.
  • HAProxy, Envoy, Caddy, other CDNs: not verified. The table above still applies: find out whether the product passes QUIC through at layer 4 or terminates HTTP/3.

NATs and idle connections

A QUIC connection with no packets for the idle timeout ends (maxIdleTimeout, 30 s by default, the smaller of both sides'). A NAT, a stateful firewall or the node's connection tracking can forget an idle UDP flow sooner. RFC 9000 section 10.1.2: "Though REQ-5 in [RFC4787] recommends a 2-minute timeout interval, experience shows that sending packets every 30 seconds is necessary to prevent the majority of middleboxes from losing state for UDP flows". What happens then:

  • The client sends next: its packet gets a new mapping, often a new port, and the server sees a NAT rebinding. The connection survives (path validation, QUIC: Migration and paths), unless a 4-tuple hashing load balancer sends the new flow to another instance (Connection IDs and several instances).
  • The server sends next (a response the client waits for, a WebSocket message): its packets go to the forgotten mapping and are lost until the client sends something.

QuicConfig.keepAlive sends a PING often enough to keep the path warm, at least every half of the effective idle timeout, at most 3/4 of maxIdleTimeout. Set it on the side that keeps a quiet connection it cares about, usually the client: on the Ktor client engine { quic = quicConfig { keepAlive = 15.seconds } }, on the Ktor server quic = quicConfig { keepAlive = 15.seconds } (every connection of the listener then sends a PING that often, which a server with many idle clients pays for). The Ktor client closes HTTP/3 connections that carry no request after its own idleTimeout (5 minutes) whatever keepAlive says. TCP has the same problem with longer timers (ktor.deployment.connectionIdleTimeoutSeconds, 45 s, closes idle HTTP/1.1 connections first).

A process that was frozen (an Android app frozen in the background or in Doze, a laptop that slept, a debugger stopped at a breakpoint) wakes with its idle timers overdue. Before an idle timer closes a connection, the endpoint reads what its sockets hold, without waiting, and processes it: a packet the peer sent meanwhile keeps the connection, and only a connection none of whose packets arrived closes (RFC 9000 section 10.1). Such a close can come up to about 100 ms after the deadline on the accelerated socket, which ends its receive in flight with its current wait. A DatagramIo of your own is not read this way. After a long freeze the peer has usually closed its side by its own idle timer, so keep-alive still decides whether a quiet connection survives.

Reply addresses

A client drops QUIC packets from an address it did not send to (RFC 9000 section 9), so every answer must leave from the address the client used. With the default host = "0.0.0.0" (or ::) the engine's accelerated UDP socket (Linux, Android, macOS, iOS, Windows; 0.3.0) learns the destination of every datagram (IP_PKTINFO / IPV6_PKTINFO) and sends that connection's packets, and any stateless answer to it, from that address. This covers a host with several addresses, a secondary IP, a floating or virtual IP (keepalived) and a VIP on lo for IPVS direct routing or similar direct server return. A connection keeps the server address its client first reached: packets of the same client that later arrive at another of the server's addresses are processed, and the answers still leave from the first one (only a client migrates, and it does so by changing its own address).

Before 0.3.0, and still with the portable socket (IoPreference.Portable, the JVM without the native library, a Kotlin/Native target without ksl_udp; the log says "using the portable socket" when it falls back), the kernel picks the source from the route to the client: on such hosts the answers leave from the wrong address and QUIC never connects while TCP works. There, bind the connector's host to the address clients send to (one connector per address when there are several).

Connection IDs and several instances

A QUIC connection is identified by connection IDs, not by the 4-tuple, so it survives a client's change of address (NAT rebinding, Wi-Fi to cellular; QUIC: Migration and paths). An L4 load balancer that hashes the 4-tuple does not know this:

  • While the client's address and port stay the same, all its packets reach the same instance, and everything works.
  • When they change, the packets may hash to another instance. That instance has no state for the connection and cannot end it either: Stateless Reset tokens come from a key of the endpoint that issued the connection (QUIC: Stateless reset). The connection then stalls until the client's idle timeout and the client reconnects. With a single instance behind the load balancer this cannot happen.
  • Retry tokens and NEW_TOKEN address tokens are sealed with keys of one server process. A Retry token is valid for 10 s and bound to the client's address and port; one that another instance issued does not open, so the attempt is refused with a stateless CONNECTION_CLOSE carrying INVALID_TOKEN (RFC 9000 section 8.1.3) and that connection attempt fails. Under per-flow routing the Initial after a Retry comes from the same 4-tuple and reaches the same instance, so this happens only when the flow moves within those seconds. A NEW_TOKEN token from another instance counts as no token (QUIC: Admission and endpoint limits): the client may be asked for a Retry again, at the cost of a round trip.

QUIC-LB (draft-ietf-quic-load-balancers-21) lets a load balancer route by a server ID encoded in the connection ID. Since 0.3.0 the engine offers it, experimentally: quicLoadBalancer = QuicLbConfig(...) with the values your load balancer's configuration agent assigned each instance, and engine.updateLoadBalancer(next) to roll out a new configuration (QUIC: Behind a load balancer). Without a QUIC-LB load balancer, put one instance behind each address, or accept that a client that changes address while connected to a multi-instance pool reconnects. The engine does not offer a QUIC preferred address (QuicServerConfig.preferredAddress, QUIC: Migration and paths) either; that needs the QUIC API directly.

The host

UDP socket buffers

A QUIC server receives everything through one UDP socket per loop. A burst that does not fit into the socket's receive buffer is dropped by the kernel, and QUIC sees it as loss. Kuicksilver asks for large buffers itself; the OS caps what it gets:

Platform (socket) What Kuicksilver asks for What limits it
Linux, Android (accelerated ksl socket) SO_RCVBUF and SO_SNDBUF of 7 MiB net.core.rmem_max and net.core.wmem_max: Linux silently caps a larger request to them (socket(7)). The default is distribution-dependent and often about 208 KiB
macOS, iOS (accelerated ksl socket) 7 MiB, halved until the kernel accepts it (the last try is 448 KiB; after that the OS default stays) kern.ipc.maxsockbuf (on macOS 8 MiB by default, less overhead; iOS not checked)
Windows (accelerated ksl socket) 7 MiB, once Windows' own limits
JVM portable socket (when ksl is not used) 8 MiB the same OS limits

Kuicksilver does not read the size back, does not log it, and does not use SO_RCVBUFFORCE. The engine has no option for it ("UDP socket buffer sizes are not configurable yet", Ktor: HTTP/3 on the server). On Linux, raise the limits so the request is granted in full (values in bytes; 8 MiB, 8 388 608, covers the 7 MiB of the ksl socket and the 8 MiB of the JVM portable socket):

sysctl net.core.rmem_max net.core.wmem_max          # what the host allows now
sudo sysctl -w net.core.rmem_max=8388608 net.core.wmem_max=8388608
# keep it across reboots
printf 'net.core.rmem_max=8388608\nnet.core.wmem_max=8388608\n' | sudo tee /etc/sysctl.d/90-quic.conf

Signs that the buffer is too small: receive errors growing under load (netstat -su, "receive buffer errors", or RcvbufErrors in /proc/net/snmp) and losses in a qlog trace that the network does not explain. These counters are per network namespace: for a server in a container, read them inside it (or with nsenter -t <pid> -n).

GSO, GRO and several loops

On Linux and Android the accelerated socket sends runs of equal-sized datagrams with one sendmsg and UDP_SEGMENT (GSO), and receives coalesced datagrams with UDP_GRO. It probes both when the socket opens, and turns GSO off by itself if the kernel or the driver fails a send with it. Darwin has neither (one datagram per call). Windows uses USO and URO where the system grants them. Nothing needs to be set, but older kernels lack the options: UDP GSO arrived in Linux 4.18 and UDP GRO in 5.0. The engine does not log whether they were granted; DatagramIo.open(...).capabilities (gsoMaxSegments, gro) shows it for a socket you open yourself on the same host (QUIC: Binding an endpoint and connecting).

udpSocketCount (kuicksilver.udpSocketCount, default 1) runs that many endpoint loops on the port. On Linux and Android each has its own socket on SO_REUSEPORT, and the kernel spreads client flows over them; a connection whose packets the kernel hashes onto another loop's socket (after a NAT rebinding) is forwarded inside the process. On macOS, iOS and Windows the loops share one socket, whose receiver hands each datagram to the loop its connection ID names, so a rebound client needs no forwarding at all. Either way several loops have none of the load balancer problems above, and one connection is no faster with more loops (QUIC: Several loops on one port). Only a JVM that fell back to the portable socket cannot run more than one: there the start does not fail, the engine logs "HTTP/3 is not served on port : ..." and serves HTTP/1.1 alone, without Alt-Svc (troubleshooting).

If the accelerated socket cannot open, the JVM falls back to a portable socket without these features, with a warning in the log; a Kotlin/Native server then serves HTTP/1.1 only (troubleshooting: The accelerated socket is not used).

MTU

QUIC starts at 1200-byte packets and raises them with DPLPMTUD. Tunnels with a small MTU (VPNs, some overlay networks) are covered by black-hole detection (QUIC: Path MTU, troubleshooting).

Certificates

  • One identity serves both sides: the same chain and key over TCP and over QUIC. The certificate must cover the host name clients use for the origin. The alternative in Alt-Svc has no host of its own, so the name is the same.
  • A tlsConnector with an sniSelector picks each name's identity on TCP and QUIC alike, so the Alt-Svc of a name's TCP responses leads to a QUIC handshake that presents that name's certificate (Ktor: Certificate per name).
  • Renewed certificates can be put in place without a restart: a TlsIdentity.Reloadable and reload(...), or with EngineMain the key kuicksilver.tls.reloadInterval that watches the PEM files of kuicksilver.tls.certificateChain and kuicksilver.tls.privateKey (Ktor: Certificate rotation, TLS: Rotating the server certificate). Handshakes whose ClientHello arrives after the reload, on TCP and QUIC, take the new certificate; open connections keep theirs.
  • The CA bundle that verifies client certificates (mTLS) rotates the same way: a TrustConfig.ReloadableCa as the connector's trust and reload(...), or with EngineMain the keys kuicksilver.tls.clientAuth and kuicksilver.tls.clientCa, whose file kuicksilver.tls.reloadInterval also watches (TLS: Rotating the client CA). Once the reload returns no handshake accepts a client certificate that only a dropped CA vouches for (one in progress is checked again when it completes), a session ticket does not get such a client back in, and connections it already holds go on until they close.

Turning HTTP/3 off without a restart

On the server, engine.http3Advertising (experimental) is read per response and per new QUIC client (Ktor: Turning HTTP/3 off on the server):

Value Use it when
On normal operation
Clear HTTP/3 should stop being offered, but connections that use it may finish in their own time
Drain HTTP/3 must go now: GOAWAY to live connections, new QUIC clients refused with CONNECTION_REFUSED (within the stateless rate limit; beyond it they time out), so they fall back at once; a Kuicksilver client does not mark the alternative broken for the refusal and is back on HTTP/3 as soon as the server announces it again

The UDP socket stays bound in every mode. To block UDP for good, use the firewall, after at least 24 hours (ma=86400) in Drain or Clear, so that returning clients have dropped the cached alternative first; clients that do not come back within that time have let it expire. The value is per engine and starts at On. Behind a load balancer, set it on every instance.

On the client, an application can switch HTTP/3 off from its remote configuration with http3 { http3Allowed } and take open connections out of use with client.closeHttp3Connections() (Ktor: Turning HTTP/3 off remotely).

Security limits

The HTTP/3 listener runs the QUIC endpoint's protections (QUIC: Admission and endpoint limits, threat model 3.1 and 3.2):

  • Amplification. Before a client's address is validated, the server sends at most three times what it received (RFC 9000 section 8.1).
  • Retry. quicAdmission (a ConnectionAdmission) decides per new client. The default asks unvalidated clients for a Retry under handshake load; ConnectionAdmission.AlwaysRetry always does. Clients that bring a valid address token skip it.
  • Hard limits. quicMaxConnections 10 000, quicMaxConnectionsPerIp 256 and quicAcceptQueue 128 per listener (QUIC connection limits), and stateless answers (Retry, refusals, Version Negotiation, Stateless Reset) rate-limited to 8 per second per address and 1000 in total, which the engine does not let you change. What goes beyond is dropped and such clients see a handshake timeout; a full accept queue instead refuses at once with CONNECTION_REFUSED. This is why a source NAT in front of the server matters (Kubernetes): every client behind it shares both per-address limits.
  • TCP connection limits. maxTcpConnections (10 000 per connector: at the limit the connector stops accepting and the OS backlog holds new clients; keep it below ulimit -n) and maxTcpConnectionsPerIp (off by default: behind a proxy, load balancer, SNAT or NAT every client shares one address; enable it, e.g. 256, only when the server faces clients directly; one more from that address is reset at accept, which a proxy reports as 502/503), HTTP/1.1 and HTTP/2 alike (Connection limits).
  • Transport and HTTP/3 settings. quic (a QuicConfig: idle timeout, windows, congestion control), http3Settings, and on TCP requestHeaderTimeoutSeconds and connectionIdleTimeoutSeconds against slow clients (Ktor: Server).

QUIC connection limits

Three engine options (experimental, 0.3.0) set the QUIC endpoint limits of every HTTP/3 listener. Each bounds the listener as a whole, over all its udpSocketCount loops, whatever loop a connection lands on (configuration; with EngineMain the keys kuicksilver.quicMaxConnections, kuicksilver.quicMaxConnectionsPerIp, 0 for off, and kuicksilver.quicAcceptQueue):

Option Default Over the limit
quicMaxConnections 10 000 a new client's Initial is dropped silently; counted in connectionsRefusedLimits
quicMaxConnectionsPerIp 256 (null is off) the same, per client IP address (ports ignored)
quicAcceptQueue 128 handshaken connections the accept loop has not taken yet; a new client is refused with CONNECTION_REFUSED (connectionsRefusedAcceptQueue)

The per-address limit counts the address the server sees. Raise it (up to quicMaxConnections) or set it to null when many clients reach the server from one address:

  • a NAT or carrier-grade NAT in front of many users (an office, a campus, a mobile network);
  • Kubernetes kube-proxy with externalTrafficPolicy: Cluster, which may source-NAT packets to a node's address (Kubernetes); with Local the client's address is kept and the default fits;
  • a UDP load balancer or proxy that sends from its own address (nginx stream by default, What can sit in front of the server). The engine reads no PROXY protocol header on UDP, so such a proxy cannot pass the client's address on.

A client over the per-address limit gets no answer and fails at its handshake timeout; a Kuicksilver client then falls back to TCP and marks the alternative broken. Keep quicMaxConnections as the overall bound, and keep the limit where the server sees real client addresses: it is what stops one address from taking every connection slot. The stateless answer limit (8 per second per address) still applies to everyone behind a shared address.

// guide:deployment:quic-limits
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val server = embeddedServer(Kuicksilver, configure = {
    tlsConnector(identity) { port = 443 }
    quicMaxConnectionsPerIp = 4_096   // behind kube-proxy (externalTrafficPolicy: Cluster): clients share node addresses
}) {
    routing { get("/") { call.respondText("ok") } }
}
server.start(wait = false)
// for a metrics gauge: clients dropped by quicMaxConnections or quicMaxConnectionsPerIp since the start
val refusedByLimits = server.engine.http3Stats.sumOf { it.connectionsRefusedLimits }

Observability

  • The application's log gets the engine's own messages, such as "HTTP/3 is not served on port ...". The logger (warnings on standard error by default) gets the QUIC endpoints' diagnostics, such as the fallback to the portable socket; logger = KuicksilverLogger.stderr(LogLevel.Debug) adds each QUIC connection's lifecycle.

  • eventListener (KuicksilverServerEventListener) hears connections per protocol (connectionOpened with HTTP/3.0), failed TLS handshakes and requests, which you can count; connectionListener hears every QUIC connection with its close reason.

  • qlog = AsyncQlogSink(DirectoryQlogSink(dir), sampleEvery = 100) writes a trace per sampled connection, for qvis.

  • engine.http3Stats (experimental, 0.3.0) returns the QUIC endpoint counters (EndpointStats) of every HTTP/3 listener, one per connector serving HTTP/3; each read is a fresh snapshot, safe from any thread, for a metrics gauge. datagramsReceived answers "does any QUIC arrive at all?"; connectionsRefusedLimits growing means clients hit quicMaxConnections or quicMaxConnectionsPerIp (QUIC connection limits), connectionsRefusedAcceptQueue the accept queue, connectionsRefusedAdmission the admission policy.

See Ktor: Observability for a sample of the listeners. A debug log or a packet capture answers the same question without code.

Checking a deployment

From a machine outside your network:

# 1. TCP side: the Alt-Svc header (h3 with the public port; "clear" under Clear or Drain)
curl -sI https://example.com/ | grep -i '^alt-svc'

# 2. UDP side: HTTP/3 only, no fallback (needs a curl built with HTTP/3: `curl -V` lists HTTP3)
curl --http3-only -sI https://example.com/

# 3. On the server: does UDP arrive at all?
sudo tcpdump -ni any udp port 443

curl --http3-only tries QUIC on the URL's port. When Alt-Svc advertises another port, test that one (https://example.com:<advertised port>/). Run tcpdump on the port the engine bound; for a container, inside its network namespace (nsenter -t <pid> -n tcpdump ...) or on the host's published port.

curl --http3-only fails when QUIC does not get through, so it tells a blocked UDP path apart from a client that just chose TCP (curl: HTTP/3). The repository runs this block as it stands against the engine in a container (tools/check/deployment-guide.sh), so the commands stay current.

From a Kuicksilver client, every response says how it was served and, if not over HTTP/3, why: response.kuicksilverDiagnostics?.fallback, or one log line per call with engine { logger = KuicksilverLogger.stderr(LogLevel.Info) } (Ktor: Why did this request not use HTTP/3?). Keep in mind that in Auto mode the first call to an origin goes over HTTP/1.1 (NoAlternative) unless a FileAltSvcStore remembers the alternative from an earlier run; HTTP/3 starts from the next call.
