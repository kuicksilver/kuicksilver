TLS with Kuicksilver

What this page is for. It explains the TLS layer on its own: building a TlsConfig, trust and certificate checks, TLS over a socket or any channel, session resumption, key logging and key exchange groups. QUIC, Ktor and the socket wrapper all use the same configuration object.

Before you start

  • Dependency: io.kuicksilver:kuicksilver-tls:0.3.0 or newer (the socket wrapper is io.kuicksilver:kuicksilver-ktor-network). Built with Kotlin 2.4.20: JVM and Android need Kotlin 2.3 or newer, Kotlin/Native 2.4.x (Kotlin version).
  • Platforms: JVM 17 or newer, Android minSdk 24, iOS 15, macOS 12 (macOS 11 on the JVM), Linux, Windows (Platforms).
  • A client needs the server's name and a trust configuration; a server needs a TlsIdentity (certificate chain and private key).

Minimal example. Configuration builds a client and a server TlsConfig; TLS over a socket runs a handshake over TCP.

Kuicksilver's TLS layer (io.kuicksilver:kuicksilver-tls) runs TLS 1.3 (RFC 9846; the default, as RFC 9852 asks) and, when asked, TLS 1.2 under the RFC 9325 profile as narrowed by RFC 10015 (ECDHE and AEAD only) over OpenSSL 3.5 on every Kotlin Multiplatform target. The same configuration object drives QUIC handshakes, TLS over TCP and the ktor-network socket wrapper. The code blocks below compile and run as GuideSamplesTest.

Native library availability

The TLS layer runs on the native library libksl, shipped for the platforms listed in the README. An application that must also run elsewhere (another OS or CPU architecture) checks once at startup and keeps another transport, instead of catching KslException from the first connection:

// guide:tls:availability
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
if (!KslLoader.isAvailable()) fallBackToTcp()   // never throws; the outcome is cached for the process

KslLoader.isAvailable() and KslLoader.availability() are experimental (@ExperimentalKuicksilverApi); the latter says why: NativeAvailability.Unavailable.reason is NoLibraryForPlatform, LoadFailed, IntegrityMismatch (the SHA-256 manifest check refused the library) or AbiMismatch, with the original exception as cause. The check makes the same single load attempt as KslLoader.ensureLoaded(); after a failure, ensureLoaded() throws that same exception without retrying.

On the JVM the library is extracted once into <java.io.tmpdir>/kuicksilver-native-<user> (or -Dkuicksilver.native.workdir=<dir>, for a noexec temp directory) and verified against the jar's SHA-256 manifest on every start. The loader creates the directory, and any missing parent, owner-only (rwx------, or on Windows an ACL with one entry for you) and checks it: it must be a real directory that you own and that nobody else can write. A -Dkuicksilver.native.workdir that fails the check gives IntegrityMismatch; when the default directory fails it (another user created it first, or it is a link), the process uses a new private directory next to it and prints a warning. An elevated Windows process uses kuicksilver-native-<user>-admin. When a directory above the default one lets another user rename it (writable by others without the sticky bit /tmp has, or owned by another user), the library goes to $XDG_RUNTIME_DIR/kuicksilver-native or the user's cache directory instead, and when neither can be used it stays in the temporary directory with a warning (troubleshooting). The library is written owner-only (rw-------) through a new file and an atomic rename; a copy that another user owns or may write is replaced, not reused, and one that cannot be replaced (Windows, another process has it loaded) is written next to it under a name with its hash. The file is kept between runs and shared between JVMs of the same user: its name carries the ksl ABI version.

Configuration

A TlsConfig is immutable; build it with the tlsConfig DSL. A client needs a server name (its reference identifier) and a trust configuration; a server needs an identity or an SNI selector.

// guide:tls:client-config
val client = tlsConfig(TlsRole.Client) {
    serverName = "server.test"          // SNI and the name the certificate must match
    alpn = listOf("h2", "http/1.1")
    trust = TrustConfig.Platform        // the OS trust store (JDK, Android NSC, SecTrust, Windows)
}

// guide:tls:server-config
val identity = TlsIdentity.fromPem(chainPem, keyPem.toCharArray())   // the key array is zeroed; the key now lives in OpenSSL only
val server = tlsConfig(TlsRole.Server) {
    alpn = listOf("http/1.1")
    this.identity = identity
}

A TLS-over-TCP client that sends no ALPN extension completes the handshake without ALPN by default, as with OpenSSL and Go's crypto/tls. A server whose protocols imply one for such a client sets alpnFallback (experimental), e.g. http/1.1: RFC 9113 section 3.3 says "HTTP/2 connections over TLS MUST use protocol negotiation in TLS", so a client without ALPN speaks HTTP/1.1. Such a client then completes the handshake only where the protocols in effect for its connection (alpn, or the sniSelector answer's) name the fallback; elsewhere the handshake ends with no_application_protocol (120). That is the alert RFC 7301 section 3.2 gives a server that "supports no protocols that the client advertises", and the one RFC 9001 section 8.1 requires when "an application protocol is not negotiated" over QUIC; missing_extension (109) is for an extension "mandatory to send for the offered TLS version" (RFC 9846 section 6.2), which ALPN over TCP is not. The rule holds at every ClientHello, the second one after a HelloRetryRequest included: RFC 9846 section 4.2.2 has the client "send the same ClientHello without modification" there but does not tell a server to compare the two, and OpenSSL does not, so a client that drops ALPN from its second ClientHello is judged as one that never sent it; the handshake is checked once more when it completes. A ClientHello whose ALPN extension is present but malformed (RFC 7301 section 3.1: a non-empty list of non-empty names) gets decode_error (50), with or without the fallback, as OpenSSL answers it. An empty list in effect (no ALPN) takes any client. The fallback cannot be h3, and a server over TCP selects from its alpn without h3 (RFC 9114 section 3.1: HTTP/3 runs over QUIC only); a list of h3 alone serves nothing over TCP, and every TCP handshake ends with no_application_protocol. QUIC ignores alpnFallback: a QUIC client without ALPN is always refused (RFC 9001 section 8.1). The Ktor server's TLS connector sets it to http/1.1.

Rotating the server certificate

A server identity can be replaced while the server runs (experimental, 0.3.0): wrap it with TlsIdentity.reloadable(identity), use the result as the identity, and call reload(TlsIdentity.fromPem(...)) when a renewed certificate arrives. Every handshake whose ClientHello arrives afterwards, over TCP and QUIC alike, presents the new chain and key, also on a TCP connection accepted before the reload; handshakes in progress and established connections keep the identity they started with, and nothing they hold is freed under them.

  • Bad input never replaces the identity in use. A key that does not match the leaf already fails in fromPem or fromDer; reload refuses a closed identity, a leaf certificate that has expired, and one that is not valid yet (notBefore more than 5 minutes ahead: a certificate staged for later is never served early), all with TlsException.Config, and the old identity goes on serving.
  • Ownership. The reloadable identity owns what it serves: reload closes the identity it replaces, close() the current one. An identity reload refused is still yours to close.
  • Resumption. Every server binds its session tickets to the leaf certificate they were issued under, so after a reload to another certificate a ticket from before it resumes nothing: the client runs a full handshake and sees the new certificate, and that ticket's 0-RTT is refused. A resumed connection carries no certificate (RFC 9846 section 2.2) and keeps the identity of its session, which is therefore the current one. After a key compromise, a reload stops both new handshakes and resumptions with the old key; connections already established run until they close.

Independently of reloads, resumption is bounded on every server (RFC 9846 section 4.7.1 recommends limiting the total lifetime of resumption keying material and taking the certificate's lifetime into account): each resumption renews the ticket, but a chain of renewals ends 7 days after the full handshake that authenticated it (BoringSSL's SSL_DEFAULT_SESSION_AUTH_TIMEOUT) and at the leaf's notAfter; then the client runs a full handshake.

The Ktor server engine can also watch the PEM files itself; see Certificate rotation.

Rotating the client CA

The CA bundle a server verifies client certificates with (clientAuth Optional or Required) can also be replaced while the server runs (experimental, 0.3.0). Wrap the bundle with TrustConfig.reloadable(TrustConfig.AnchoredCa(roots)) and use the result as the server's trust, alone or as the base of Pinned. Call reload(TrustConfig.AnchoredCa(newRoots)) when the bundle changes. It follows the rules of the identity above:

  • The rule. After reload returns, no handshake accepts a client certificate that only a removed CA vouches for, over TCP and QUIC alike, however the client times its flights. A handshake takes the bundle current when its ClientHello arrives (over TCP when its first bytes are there, not at the accept) and OpenSSL verifies against it; if a reload replaced that bundle with other certificates before the handshake completes, the certificate is verified again against the bundle current then, as a fresh handshake would (OpenSSL's security level, and the pins of a Pinned around the bundle on the path built under it), and the handshake fails unless it passes. A reload to the same certificates changes nothing. One case is refused that a fresh handshake would accept: a session resumed across a reload that changed the certificates holds only the client's leaf, so it passes only if that leaf chains to the new bundle without intermediates (the client then runs a full handshake on its next connection). Connections established before the reload are not affected: a client of a CA you dropped that is already connected stays connected until its connection closes. Close such connections yourself if the CA was compromised.
  • Shared contexts. The first handshake under the new bundle replaces the old bundle's shared OpenSSL context, which is freed with its last connection. With clientAuth None the bundle plays no part, and a reload changes nothing.
  • Non-CA certificates. Every certificate of the bundle is a trust anchor, also a leaf: a client presenting exactly that certificate is accepted. EngineMain warns about such certificates in its CA file.
  • Bad input never replaces the bundle in use. reload refuses a bundle in which no certificate is valid now (each expired, or not valid yet beyond 5 minutes of clock skew) with TlsException.Config, and the old bundle stays.
  • Resumption. A session resumes only under the bundle it was authenticated with. After a reload, a ticket from before it resumes nothing (RFC 9846 section 4.7.1: "A server MAY treat a ticket as valid for a shorter period"). The client runs a full handshake and its certificate is verified against the new bundle, so a ticket never lets a client of a dropped CA back in.
  • What the client sees. The server sends no certificate_authorities extension in its CertificateRequest (RFC 9846 section 4.3.4: "The server MAY send it in the CertificateRequest message"), so clients pick their certificate without a CA list from the server, before and after a reload.
  • Servers only. A client configuration with a ReloadableCa throws TlsException.Config; a client trusts its server through AnchoredCa.
// guide:tls:client-ca-rotation
@file:OptIn(ExperimentalKuicksilverApi::class)   // experimental API (at the top of the file)
val clientCa = TrustConfig.reloadable(TrustConfig.AnchoredCa(Certificate.parsePem(caBundlePem)))
val mtlsServer = tlsConfig(TlsRole.Server) {
    alpn = listOf("h3")
    identity = serverIdentity
    clientAuth = ClientAuth.Required
    trust = clientCa
}
// later, when the bundle changes:
clientCa.reload(TrustConfig.AnchoredCa(Certificate.parsePem(renewedBundlePem)))

The Ktor server engine can watch the CA file too: EngineMain's kuicksilver.tls.clientCa with kuicksilver.tls.reloadInterval (Certificate rotation).

Certificate per name (SNI)

A server's sniSelector chooses each handshake's identity from the ClientHello (RFC 6066 section 3), over TCP (TlsConnection) and QUIC (QuicTlsSession, HTTP/3) alike. It sees a ClientHelloInfo (the server name, null without SNI; the ALPN offer; the signature schemes) while the handshake is paused, and returns a ServerTlsOverride(identity, alpn, clientAuth, trust) (with ocspStapling and keyExchangeGroups, experimental) or null:

  • an override: its chain and key answer, and its alpn, clientAuth, trust, staple and key-exchange groups replace the configuration's for that connection (localCertificates reports the chosen chain). Over TCP its alpn goes without h3, which identifies HTTP/3 over QUIC only (RFC 9114 section 3.1); a list of h3 alone serves the name over QUIC only, and its TCP handshake ends with no_application_protocol (120, RFC 7301 section 3.2), as does that of a client without ALPN where alpnFallback is set and the list leaves it out (Configuration);
  • null for a ClientHello with a server name: the handshake ends with unrecognized_name (112), the fatal choice RFC 6066 section 3 offers for a name the server does not recognize;
  • null for a ClientHello without one: the configuration's own identity; a configuration without one ends the handshake with missing_extension (109, RFC 9846 section 9.2; TLS 1.2 has no such alert and gets handshake_failure).

A selector that throws, or an override the configuration's rules refuse, ends that handshake: over TCP with the exception, over QUIC with internal_error (80) and the exception as the cause of the failure (the CONNECTION_CLOSE reason the client reads carries none of its text). Over QUIC the handshake pauses at DriveResult.WantSni; the QUIC endpoint runs the selector off the connection's loop (QuicTlsSession.selectSni, then resumeSni on the loop), and a connection that ends meanwhile cancels it and frees what it built. A QUIC override needs a non-empty alpn like any QUIC configuration, and one with client certificates gets neither tickets nor 0-RTT, as a QUIC server with client certificates never does.

Session tickets are bound to the server name and to the certificate they were issued under: a ticket resumes, and its 0-RTT is accepted, only when the same name selects the same certificate again (RFC 6066 section 3, RFC 9846 section 4.7.1). Otherwise the handshake is a full one and issues a new ticket. A Kuicksilver client does not even offer a ticket under another name than its own.

The context built for an answer is kept and shared by the next handshakes with the same answer (the same identity, trust and OcspStapling objects, equal alpn, clientAuth and keyExchangeGroups), so a selector that returns ServerTlsOverride(identity) for a known identity costs a handshake little; a TlsIdentity.Reloadable still reaches the next handshake after a reload. Hand out the same TrustConfig and OcspStapling objects for a name: a new object per call is a new answer and builds a context each time. Up to 64 answers are kept per configuration, the least recently used going first, and their contexts are counted apart from the configuration's own, so many answers never push those out.

Trust

Host names are always checked (RFC 9525) and the check cannot be disabled; it can be redirected with ExpectedName for proxies (ExpectedName wraps Platform, AnchoredCa or Custom; to pin as well, put it inside Pinned — except around Custom, which Pinned refuses directly and through ExpectedName: Pinned(pins, base = ExpectedName(name, base))). Pins are an additional check against the validated chain, never a replacement for it.

// guide:tls:trust
val pinned = TrustConfig.Pinned(
    pins = setOf(SpkiSha256.parse("sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")),
    scope = PinScope.Leaf,
    base = TrustConfig.AnchoredCa(listOf(rootCertificate)),   // or Platform
)

Private CAs usually arrive as PEM files. Certificate.parsePem returns every CERTIFICATE block of a file in order (a bundle, a chain), skips other blocks such as keys, and parses each certificate on the spot, so a damaged file fails at startup with TlsException.Config rather than at the first handshake:

// guide:tls:pem-roots
val roots = Certificate.parsePem(caPem)   // every CERTIFICATE block, in order; TlsException.Config if none
val trust = TrustConfig.AnchoredCa(roots)

Every certificate given to AnchoredCa is a trust anchor, also one that is not self-signed: anchoring at an intermediate CA accepts the chains that reach it, without its issuers (OpenSSL X509_V_FLAG_PARTIAL_CHAIN, as JDK TrustAnchors, Apple anchor certificates and Go's root pools behave).

Platform trust

TrustConfig.Platform hands the chain to the platform's own verifier. ksl checks the reference identifier with the shared RFC 9525 matcher afterwards on every platform, so a platform matcher can only make the decision stricter; pins (Pinned) are compared against the chain the platform built, never against certificates the peer merely sent.

Every peer chain is held to OpenSSL's security level 2 (RFC 9325 section 4.5): every key needs 112 security bits (RSA 2048 bits, an elliptic curve 224 bits), and every certificate signature too, except the trust anchor's: no SHA-1 or MD5 (RFC 9846 section 4.5.1.3). A weaker chain ends the handshake with bad_certificate and TlsException.Verify with VerifyReason.WeakKey or VerifyReason.WeakSignature; there is no switch to turn it off. The JDK, Android and Windows verifiers would accept 1024-bit RSA on their own. Which certificates count depends on the trust:

  • Platform (also under Pinned and ExpectedName): the platform is asked first, and after its yes ksl checks the path the platform built, leaf first and its trust anchor last (Android's X509TrustManagerExtensions, Apple's SecTrustCopyCertificateChain, Windows' chain, and on the JVM the path rebuilt with the JDK's PKIX builder to the trust manager's roots), as OpenSSL checks its own path: every key, the anchor's included, and every signature but the anchor's. A certificate the server sends that the platform does not use, such as an extra cross-certificate above the root the platform trusts (signed with SHA-1 by an old root, say), does not count, as with OpenSSL. If the platform does not say which path it took, the certificates the server sent are checked as for Custom. When the platform itself refuses a chain with an MD5, SHA-1 or small-key certificate in it (the JDK, Apple and Windows do), the refusal is still reported as WeakSignature or WeakKey with bad_certificate. This holds even when the chain is not trusted at all (RFC 9846 section 4.5.1.3 does not depend on trust; OpenSSL would send unknown_ca), and it takes precedence over the platform's own reason: an expired or revoked chain that also has a weak certificate among those sent is reported as WeakKey or WeakSignature. The chain is refused either way. On Linux Native Platform is OpenSSL's own verifier with the system store, which checks its own path the same way.
  • AnchoredCa: OpenSSL checks the path it builds to your roots.
  • Custom and Tofu: the certificates the peer sent are checked before your verifier or the TOFU store is asked: every presented certificate reachable from the leaf through issuers whose key verifies the signature (each such issuer is followed, so cross-certificates are all checked), only a really self-signed certificate's own signature exempt. This is stricter than OpenSSL for an extra cross-certificate the server sends above the anchor your verifier trusts: it is checked and refuses the chain. A certificate on no verified path from the leaf is not looked at.

The endpoint's own chain is held to the same rules when the identity is made (TlsIdentity.fromDer, fromPem and the JVM key store factories throw TlsException.Config for a SHA-1- or MD5-signed certificate or a key under 112 bits), for a server and for a client certificate alike.

Linux trust store

On Linux Native the bundled OpenSSL has no built-in certificate directory, so ksl looks for the system store when a client context with TrustConfig.Platform is built, in this order:

  1. SSL_CERT_FILE (a PEM bundle) and SSL_CERT_DIR (a directory of PEM certificates, hashed with c_rehash or not). When either variable is set, only these are used, as in Go's crypto/x509: a configured store never silently becomes another one.
  2. Otherwise the first bundle that loads, from Go's list: /etc/ssl/certs/ca-certificates.crt (Debian, Ubuntu, Gentoo), /etc/pki/tls/certs/ca-bundle.crt (Fedora, RHEL 6), /etc/ssl/ca-bundle.pem (openSUSE), /etc/pki/tls/cacert.pem, /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem (CentOS, RHEL 7 and later), /etc/ssl/cert.pem (Alpine), and /usr/local/etc/openssl/cert.pem.
  3. Otherwise the first of /etc/ssl/certs and /etc/pki/tls/certs that holds certificates. A directory with c_rehash links is searched by OpenSSL's hash lookup; any other directory is read like Go reads it: every PEM file in it loads. A directory without either does not count.

When nothing is found (a distroless or scratch image without ca-certificates), building the configuration fails with TlsException.Config naming every path searched:

invalid TLS configuration: ksl: no CA certificates for TrustConfig.Platform; searched /etc/ssl/certs/ca-certificates.crt, ...,
/etc/pki/tls/certs/; install ca-certificates, set SSL_CERT_FILE or SSL_CERT_DIR, or use AnchoredCa

Install the distribution's ca-certificates package, copy a bundle into the image and point SSL_CERT_FILE at it, or ship your roots with TrustConfig.AnchoredCa.

TrustConfig.Tofu stores the first key seen for a name; TrustConfig.Custom hands trust to your verifier and still runs the shared name check afterwards (it is marked @DelicateKuicksilverApi for that reason).

Certificate revocation

RFC 9325 section 7.5 requires "a strategy to distrust revoked certificates". Kuicksilver has three parts, all experimental in 0.3.0:

  • Stapled OCSP (clients). TlsConfig.revocation (RevocationPolicy, default StapledIfPresent) asks the server for a stapled OCSP response (status_request, RFC 6066 section 8) and checks it as RFC 6960 section 3.2 says: it must name the server's certificate and the issuer the verifier trusted, be signed by that issuer or by a responder the issuer delegated (id-kp-OCSPSigning), and be inside its validity interval (5 minutes of clock skew). A response saying revoked fails with VerifyReason.Revoked; one that fails a check fails with VerifyReason.InvalidStatusResponse; both send bad_certificate_status_response (113), also with genericAlerts (OpenSSL chooses that alert). A delegated responder must also carry no unknown critical extension, meet the security level, and not be listed on a configured CRL of the issuer. A server that staples nothing, or a response saying "unknown", passes under StapledIfPresent (OCSP clients "typically 'soft-fail'", RFC 9325 section 7.5) and fails under RequireStapled (VerifyReason.UnknownRevocationStatus, alert 113); a certificate marked must-staple (RFC 7633) fails without one under every policy but Off, and so does a required staple for a leaf that is itself the trust anchor (no issuer to check a response against). The check runs where ksl verifies the chain: AnchoredCa, and Platform on Linux Native, also inside Pinned and ExpectedName. Elsewhere under Platform the OS verifier decides: Apple and Windows apply their own revocation policy, while on Android (its blocklist only) and the JVM (off unless the application enables it, e.g. com.sun.net.ssl.checkRevocation) nothing checks revocation; use AnchoredCa where that matters. A Custom or Tofu verifier decides alone; RequireStapled with them is refused (TlsException.Config). A session resumes only while the response its full handshake checked is fresh.
  • CRLs (clients and servers). TrustConfig.AnchoredCa(roots, crls) checks every certificate on the verified path against its issuer's CRL when one of crls is from that issuer (CertificateRevocationList.parsePem reads X509 CRL blocks). Revoked fails with VerifyReason.Revoked (alert 44); a CRL that expired fails with VerifyReason.UnknownRevocationStatus (alert 45), so replace CRLs before their nextUpdate; a CRL whose signature does not verify (alert 51), a configured CRL of the issuer that OpenSSL cannot use for the certificate (alert 48) or that does not cover it (a distribution point it does not name, alert 46) fails with VerifyReason.UnknownRevocationStatus as well. So does a configured CRL whose issuer is neither among the roots nor on the path: with AnchoredCa(roots = [intermediate], crls = [the root's CRL, ...]) the intermediate's own status cannot be verified, and its certificates fail (fail closed; leave that CRL out, or anchor at the root). A certificate whose issuer has none of the configured CRLs is not checked. Only complete, direct CRLs are supported: delta CRLs, indirect CRLs and CRLs limited to some revocation reasons are refused when the trust is made (TlsException.Config). On a server, a TrustConfig.ReloadableCa reload to the same roots with new CRLs applies them to the next handshakes, as a CA reload does (tickets authenticated under the old CRLs resume nothing).
  • Stapling (servers). TlsConfig.ocspStapling (or ocspStapling of the Ktor TLS connector) holds the OCSP response for the server's certificate, fetched by the application from its CA's responder. It is stapled over TCP and QUIC only to clients that ask, and only when it is for the leaf the handshake presents (the chain must include the issuer) and fresh at that moment; a stale response is silently not sent. A response is at most 2^24-5 bytes, and TLS 1.3 and QUIC staple one only up to 65527 bytes (it must fit the certificate's extensions, RFC 8446 section 4.4.2); a larger one is not sent there and the handshake goes on (RFC 6066 section 8: a server may send none). Over QUIC a large staple makes the server's first flight exceed three times what the client sent before its address is validated (RFC 9000 section 8.1), so the server sends the rest only as more client packets arrive: each such limit costs extra round trips. Call update with a fresh response before the current one's nextUpdate; isUsableFor(chain) says whether the current one would be stapled. An identity chosen by sniSelector staples the response of its own ServerTlsOverride(identity, alpn, clientAuth, trust, ocspStapling), and never the default identity's, over TCP and QUIC alike.
// guide:tls:revocation
val crls = CertificateRevocationList.parsePem(crlPem)
val client = tlsConfig(TlsRole.Client) {
    serverName = "api.example.com"
    trust = TrustConfig.AnchoredCa(roots, crls)
    revocation = RevocationPolicy.StapledIfPresent   // the default
}
val stapling = OcspStapling(ocspResponseDer)      // later: stapling.update(fresher)
val server = tlsConfig(TlsRole.Server) {
    identity = serverIdentity                       // leaf and its issuer
    ocspStapling = stapling
}

Not offered: OCSP requests from the client itself, OCSP for intermediate certificates, fetching CRLs from their distribution points.

TLS over a socket

// guide:tls:socket
val selector = SelectorManager(Dispatchers.IO)
val socket = aSocket(selector).tcp().connect("server.test", 443).tls(client)
val write = socket.openWriteChannel(autoFlush = true)
val read = socket.openReadChannel()
write.writeStringUtf8("GET / HTTP/1.1\r\nHost: server.test\r\n\r\n")
val status = withTimeout(10.seconds) { read.readLine(LineEnding.Lenient) }   // the status line
socket.close()   // sends close_notify, then closes the TCP socket

close() returns at once and finishes in the background: it sends what is queued and close_notify, then closes the TCP socket. On a client (Socket.tls) it drops what is left after 3 s in all (a peer that stopped reading) and closes the socket anyway; on a server (Socket.tlsServer) it waits for the client to take everything, however slowly it reads, so bound the connection yourself (an idle or stall timeout) where a client may never read.

The same works on the server side with Socket.tlsServer(config) after ServerSocket.accept().

Middleboxes

A TLS 1.3 client over TCP (Socket.tls, TlsConnection.client, the Ktor client's HTTP/1.1 and HTTP/2) runs without middlebox compatibility mode (RFC 9846 appendix E.4): its ClientHello has an empty session ID and it sends no dummy change_cipher_spec. That way it switches to the handshake keys with the ServerHello, and an alert it sends after that (a refused certificate, name or pin) is encrypted, as RFC 9846 appendix A.1 asks; in compatibility mode the alert went out in the clear and a server reading under the handshake keys (the JDK's, for one) could not read it. The cost: a firewall or inspection box that lets TLS 1.3 through only when it looks like a TLS 1.2 session resumption can drop these handshakes (a reset or a timeout right after the ClientHello or ServerHello). The field measurements behind appendix E.4 date from 2017; such boxes are rare now, and there is no setting to turn the mode back on. On such a network, update or bypass the box, or use HTTP/3 (QUIC never uses the mode). Servers are not affected: a ksl server keeps the mode and answers a client that sends a session ID with change_cipher_spec, as appendix E.4 requires.

Resumption and trust

A resumed handshake carries no certificates, so the client checks the chain it cached from the full handshake again before it offers the ticket (ADR-0011): under AnchoredCa and the Linux Platform store ksl verifies it again against the trust store, the current time, the name and the purpose; under the other platform verifiers and Custom the verifier runs again on it. Pins are then checked against the cached validated chain. A chain that no longer passes (an expired leaf, for example) means a full handshake, not a failure. A server holds only the client's leaf of a resumed session: its verdict travels with the ticket, which resumes only under the same trust configuration and lives at most SessionTicketConfig.ticketLifetime.

TLS over any channel

TlsConnection.client(transportIn, transportOut, config) and TlsConnection.server(...) run TLS over any pair of ktor-io channels, so a TLS session can live inside a QUIC stream or a test harness. input and output carry plaintext; shutdown() sends what is still queued and close_notify, waits for the peer's, and closes after 3 s in all at the latest, also when the peer stopped reading. close() ends the connection at once. Cancelling the job of the context passed to client/server ends it the same way: input and output fail and the native session is freed, without a close(). When the transport fails (a reset), the TlsException.Protocol of the handshake or of the input carries the transport's failure as its cause.

Key logging

Secrets never leave native memory unless you ask. That includes the TCP client's session cache: a ticket kept for resumption is a handle to a native OpenSSL session, never its serialized bytes, and the secret is wiped when the entry is used, replaced, evicted or expires, or when the engine that owns the cache closes. Each Ktor client engine keeps its own cache of at most 384 sessions, six tickets for each of 64 origins (the least recently stored one is evicted first); Socket.tls and TlsConnection.client share one process-wide cache with the same bound (the cache itself is internal API). TlsConfig.keylog accepts a KeylogSink (RFC 9850 lines); the SSLKEYLOGFILE variable is not read on the library's own and is ignored by the bundled OpenSSL; only keylogFromEnvironment(), called by the application, turns it into a sink. A libksl built against the system OpenSSL (Linux only, loaded with -Dkuicksilver.native.path or -Dkuicksilver.native.system=true) refuses to load while it is set, since that libssl might honour it (KslException.NativeLoad "SSLKEYLOGFILE is set and the system libssl may honour it; unset it (keylog)"). keylogFile(path) creates the file with mode 0600 and checks it before the first line: a symlink at the path, a file that is not a regular file, has more than one hard link or belongs to another user, or a file system without POSIX permissions is refused with an IllegalArgumentException, and an existing file that is readable by the group or others is tightened to 0600 (on the JVM, Linux and Apple). The JVM on Windows has no POSIX permission view and refuses the file; on Kotlin/Native Windows the file is only created, so keep it in a directory that only you can write. On the JVM the file is opened once, when the sink is created, and every line goes through that descriptor, so a file removed and recreated at the path later receives nothing; the JVM sink is also java.io.Closeable (close it when you are done, otherwise the descriptor stays open until the channel is collected or the process exits). Kotlin/Native reopens the file without following links for every line and repeats the checks on the new descriptor. A FIFO at the path is refused without waiting for a reader (Native opens with O_NONBLOCK; the JVM checks the path before it opens it), so a planted FIFO cannot stall keylogFile or the endpoint loop.

val path = "debug/kuicksilver-keys.txt"   // a directory only you can write
// guide:tls:keylog
val debugClient = tlsConfig(TlsRole.Client) {
    serverName = "server.test"
    keylog = keylogFile(path)   // @DelicateKuicksilverApi
}

Key exchange groups

By default both roles negotiate key exchange from one list: X25519MLKEM768, X25519, secp256r1, X448, secp384r1, secp521r1 (KeyExchangeGroups.Default). A client sends key shares for the post-quantum hybrid and for X25519, so a server of either kind picks its group in one flight.

A server picks by its own order, a group the client sent a key share for first: among the client's shares it takes the first group of its list, so it takes the client's X25519 share when that is all the client sent, even if the client also lists the hybrid as supported (OpenSSL's default would answer with a HelloRetryRequest for X25519MLKEM768, and that extra round trip doubled the handshake under loss against ngtcp2, picoquic and quiche, interop handshakeloss). With no usable share it asks with a HelloRetryRequest for the first group of its list the client supports (RFC 9846 section 4.2.1); with no group in common the handshake ends with handshake_failure (40; over QUIC, CRYPTO_ERROR 0x0128). A server that took another group than its first names its list in its EncryptedExtensions (RFC 9846 section 4.3.7).

keyExchangeGroups (experimental) replaces the list, most preferred first, for clients, servers and sniSelector answers (ServerTlsOverride.keyExchangeGroups). A client's keyShares are the groups it sends shares for in its first ClientHello, 1 to 4 of them; left out, the first group and the first later one of the other kind (hybrid or classical), as BoringSSL does:

// guide:tls:key-exchange-groups
val client = tlsConfig(TlsRole.Client) {
    serverName = "server.test"
    keyExchangeGroups = KeyExchangeGroups(
        groups = listOf(KeyExchangeGroups.X25519MLKEM768, KeyExchangeGroups.X25519, KeyExchangeGroups.SECP256R1),
        keyShares = setOf(KeyExchangeGroups.X25519),   // one small share; a server that wants the hybrid asks again
    )
}

The names are X25519MLKEM768, SecP256r1MLKEM768, SecP384r1MLKEM1024, x25519, x448, secp256r1, secp384r1 and secp521r1 (the constants of KeyExchangeGroups, case ignored). An unknown name, a duplicate, an empty list or key shares outside the list throw TlsException.Config when the KeyExchangeGroups is made; build() throws it for a group the OpenSSL in use does not provide (a system OpenSSL built without one, a FIPS provider), for keyShares on a server and for Tls12And13 without an elliptic curve in the list (TLS 1.2 has no hybrid). In TLS 1.2 the list also names the curves of the peer's ECDSA certificates an endpoint accepts (RFC 8422 section 5.1): a client without secp256r1 refuses a TLS 1.2 server's P-256 certificate with handshake_failure, and a server without it refuses a TLS 1.2 client's P-256 certificate with illegal_parameter (47; OpenSSL holds client certificates to the server's own list). TLS 1.3 negotiates signatures apart. A HelloRetryRequest costs a round trip and rejects 0-RTT (RFC 9001 section 4.6.2); a session ticket resumes under other groups, its key exchange being fresh. TlsConnection.keyExchangeGroup, QuicTlsSession.keyExchangeGroup and QuicConnection.keyExchangeGroup report the group a handshake used; a TLS 1.2 abbreviated handshake (a resumption) uses none.

Certificate compression

Both roles compress certificate chains with TLS certificate compression (RFC 8879) by default, over QUIC and TCP alike, TLS 1.3 only: a client offers brotli, then zlib, and a server sends its chain compressed with the first of the client's algorithms; a server that asks for a client certificate offers the same two, and the client compresses its certificate. A peer without it sends and gets plain certificates. Over QUIC a smaller chain keeps more of a server's first flight inside the amplification limit before the client's address is validated (RFC 9000 section 8.1): measured with the test chains, a 13.7 KB leaf and its intermediate shrink the server's first flight from 15,523 to 2,689 bytes, and a WebPKI-like RSA-2048 leaf and intermediate about a quarter (2,464 to 1,876 bytes of Certificate message).

  • A server compresses its chain once, when the context for its identity is built; a chain neither algorithm makes smaller goes out uncompressed. A session that staples an OCSP response sends its Certificate uncompressed: over TLS 1.3 the response is part of the message, and the chain compressed beforehand has none.
  • What a peer sends is held to the certificate list bound of 100 KiB, compressed or not: an announced uncompressed length above it, data that does not decompress to exactly that length, or a decompression that runs past it ends the handshake with bad_certificate (42); an algorithm that was not offered with illegal_parameter (47).
  • TlsConnection.peerCertificateCompression and QuicConnection.peerCertificateCompression (experimental) tell which algorithm the peer's chain came in, null for a plain one or none (a resumption carries no certificate).
  • certificateCompression = false (experimental) turns it off for a configuration: no offer, and a compressed certificate from the peer is an unexpected_message (10).

The algorithms are built into the bundled OpenSSL from pinned, verified releases of zlib and brotli (ADR-0025). On Android and iOS only brotli's decoder is built, to keep the library small (about 230 KB added, against about 510 KB with the encoder elsewhere): there a server compresses its chain with zlib, and a client sends its own certificate uncompressed; both still take brotli and zlib from the peer.
