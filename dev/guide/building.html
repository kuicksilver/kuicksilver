Building from source

What this page is for. It is for the person who builds Kuicksilver from a checkout instead of taking it from Maven Central: a snapshot of main, a patched copy, or a build with their own compiler and flags for the native code (for example to add hardening flags a distribution requires).

Before you start. The tools the build needs are listed in CONTRIBUTING.md, Building: a JDK, a C compiler, Docker for the Linux and Windows native code, the Android NDK for the AAR and, on macOS, Xcode for the Apple targets.

What the build makes

Gradle builds the Kotlin code; the native code is built by scripts that the Gradle tasks call:

Native output Script Gradle task
Static OpenSSL per target, in build/openssl/<target> tools/openssl/build.sh (Linux and Windows targets inside Docker: tools/openssl/build-docker.sh) :kuicksilver-native:opensslBuild<Target>
The JVM's JNI library for this machine tools/build-jni.sh :kuicksilver-native:buildJniHost
The Android libksl.so per ABI tools/build-android-so.sh :kuicksilver-native:buildAndroidJni
libksl.a for each Kotlin/Native target tools/build-ksl-a.sh :kuicksilver-native:buildKslA<Target>

To publish a build into the local Maven repository, run ./gradlew --max-workers=2 publishToMavenLocal (every target), or the JVM-only variant in Install.

Your compiler and flags

The native build scripts take the standard variables from the environment and add them to their own flags; they never replace the project's flags with yours:

Variable Where it goes
CPPFLAGS, CFLAGS after the project's compile flags, on every compile line of libksl and of OpenSSL
LDFLAGS after the project's link flags, on the link line of the JNI library and of the Android libksl.so; OpenSSL and libksl.a are static archives and are not linked, so there it has no effect
CC the compiler of the JNI library on macOS (default clang) and on Linux (default gcc), of libksl.a for macOS, and of OpenSSL for macOS and for Linux outside Docker (passed to Configure). Every other target has a compiler of its own and ignores it: Android (the NDK's clang), iOS (Xcode's SDK compilers), the Kotlin/Native Linux and Windows targets (Kotlin/Native's LLVM and sysroots), the OpenSSL builds in Docker (the images' compilers) and the Windows JNI library (x86_64-w64-mingw32-gcc). A glob character in CC (*, ?, [) is refused.

Because your flags come last, where one of them conflicts with a project flag, yours wins (the compiler takes the later one). The project compiles libksl with -Werror, so a flag of yours that makes the compiler warn fails the build; add -Wno-error=<warning> for it. A flag that a target's toolchain does not know fails that target's build.

For example, to build the JNI library on a Linux host with stack protection, _FORTIFY_SOURCE and full RELRO:

export CFLAGS="-fstack-protector-strong -D_FORTIFY_SOURCE=2" LDFLAGS="-Wl,-z,relro,-z,now"
./gradlew --max-workers=2 :kuicksilver-native:buildJniHost

What else to know:

  • OpenSSL. Its Configure would read CPPFLAGS, CFLAGS and LDFLAGS from the environment and use them instead of the target's own flags, so tools/openssl/build.sh takes them out of its environment and passes them as Configure options after the project's. Each must therefore be one word that starts with - (or /, the argument of the flag before it) and is not one of Configure's own options (-d, -v, -w, -t, -rpath, -R, -framework, --prefix= and the other -- options of Configure); a % is refused too (Configure decodes %xx). It also refuses -no-<feature> (other than -no-integrated-as), which Configure rewrites to no-<feature> and so would turn a feature off, -shared or --shared, which it rewrites to enable-shared, -static, which turns off static, PIC and thread support, and a word that starts with /D or /I, which it reads as a define or an include directory (the argument of -include /Data/x.h, say; write such paths another way, for example relative to the source). A -D or -U of an OPENSSL_* macro is refused as well: the libraries would no longer match the headers installed with them (configure-flags.txt decides those macros). The script refuses anything else before it starts. Every script reads your flags word by word and never expands a glob in them. CXXFLAGS and LDLIBS are not used. Your flags are recorded in build/openssl/<target>/configure-target.txt and provenance.txt, together with one word, builder-flags-sha256=<hash>, that stands for all of them and, for macOS and Linux, CC (for Linux, any CC but the Docker image's own compiler inside that image; on a bare Linux host the same path counts too), paths included; that word and the build cache's key change with any of them, so a build with other flags or another compiler is never taken from the cache or reused. The Docker builds get the same three variables.
  • Debug symbols. The JNI library and the Android libksl.so are stripped, as the release checks require. For a local build you want to debug or profile, KSL_KEEP_DEBUG=1 skips the strip, and CFLAGS=-g adds debug information: KSL_KEEP_DEBUG=1 CFLAGS=-g ./gradlew --max-workers=2 :kuicksilver-native:buildJniHost. On Linux, Windows and Android the library then keeps its symbol table and its debug sections; on macOS the linker leaves no local symbols to strip, and clang writes the debug information next to the library as libksl_*.dylib.dSYM. A release never keeps them: it unsets KSL_KEEP_DEBUG like the variables above, and tools/check/native-release.sh refuses a library with debug sections. The static archives (libksl.a, OpenSSL) are never stripped.
  • Gradle. CC, CPPFLAGS, CFLAGS, LDFLAGS and KSL_KEEP_DEBUG are inputs of the native tasks: changing one rebuilds what it affects. With -Pkuicksilver.openssl.prebuilt=true an existing OpenSSL build is reused only when it was configured with the flags you have now; otherwise the build stops and says the directory is stale.
  • Reproducibility. The published artifacts are built with the project's own compiler, flags and paths only: the release script (tools/release/local-release.sh), the double build of the release gate (tools/check/double-build.sh) and the rebuild of tools/verify/verify-release.sh first unset every environment variable known to change a native build (tools/clean-build-env.sh lists them: the variables above, OPT, clang's and gcc's CCC_OVERRIDE_OPTIONS, CPATH, C_INCLUDE_PATH, LIBRARY_PATH, SDKROOT and the like, AR and RANLIB, OpenSSL's __CNF_* and OPENSSL_LOCAL_CONFIG_DIR, CROSS_SYSROOT, Perl's PERL5OPT and PERL5LIB, the loaders' LD_PRELOAD and DYLD_INSERT_LIBRARIES, LD_RUN_PATH, MAKEFLAGS, and the scripts' own KSL_OPENSSL_* locations: the variables we know of; one found later is added there), and the hosted jobs that build the libraries a release reuses fail if one is set (the pinned NDK's LLVM tools their setup names, and an SDKROOT that is the selected Xcode's macOS SDK, give the same build and pass). A build with your own flags is therefore not byte-identical to a release, and comparing it with one (verifying.md) is expected to differ.
  • Tests. tools/check/native-flags-test.sh checks all of the above (it runs in the gate's reproducibility step). The C tests (tools/c-test.sh) are a test build with sanitizers: they honour CC, and take extra flags as their second argument instead of CFLAGS.
